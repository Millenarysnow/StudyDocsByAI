# 第 0.1 章 · 序章：阅读环境、Section 地图与心智模型

> **本章目标**：在你读到这一行之后，你脑子里应该装得下 ImGui 仓库的物理布局、它把 11000+ 行 `imgui.cpp` 切成了哪些"逻辑章节"、以及看完一帧 UI 出现在屏幕上的全过程时，应该用哪三个心智模型去对齐它。
>
> **本章不讲**：具体的 API、具体的源码细节。这些会从第 0.2 章开始铺开。

---

## 0.1.0 我们为什么要读源码

任何 GUI 库都会鼓励你"先把它当黑盒用，遇到问题再说"。这个建议在 90% 的库上都成立。但在 ImGui 上不成立，原因有三条：

1. **ImGui 在公开 API 之外有一份等量重要的"半公开 API"**——`imgui_internal.h`。这个头文件不是私有的（任何人都可以 `#include`），但官方明确说"我们不保证其稳定性"。如果你做的是"贴墙打孔"的高级控件——节点编辑器、时间线、图表、自定义布局——你**必然**要进 internal。internal 不是文档，是源码。
2. **ImGui 的工程文化是"公开调试一切"**：`ShowMetricsWindow` / `ShowDebugLogWindow` / `ShowIDStackToolWindow` 把内部状态直接画给你看。这意味着排查问题时，"读源码"和"读你自家代码"的负担差距没有那么大——因为大部分内部状态，你已经在 Metrics 窗里看见了。
3. **ImGui 是"少有的代码量小到可以读完的工业级 UI 库"**：核心 .cpp 不到 4 万行，没有依赖（没有 STL、没有 Boost、没有第三方），只有 stb 系列单文件库。和 Qt（百万行）、Web 浏览器渲染器（千万行）相比，"读完它"是一个真实可达的目标。

但是——**直接 `vim imgui.cpp` 跳到第 1 行往下读会挫败感很强**。不是因为代码难懂，是因为代码量大、跳转频繁、概念互相依赖。这一章要解决的就是这个问题：给你一张"阅读地图"。

## 0.1.1 仓库物理布局：6 个核心 .cpp + 2 个核心 .h

打开 `E:\Repo\imgui\`，你会看到一个相当扁平的目录结构。先看根目录的核心文件：

```
imgui/
├── imgui.h                    ← 公开 API 契约（所有用户必须 include 它）
├── imgui_internal.h           ← 私有 API + 内部数据结构（魔改者必读）
├── imconfig.h                 ← 编译期开关（所有 IMGUI_XXX 宏的"门面"）
│
├── imgui.cpp                  ← Context、Window、Layout、ID Stack、输入、Nav、Drag&Drop、Settings、Metrics
├── imgui_widgets.cpp          ← 所有控件（Button、Slider、Combo、TreeNode、Tab、MenuBar...）
├── imgui_draw.cpp             ← ImDrawList / Path / 字体渲染 / 图集 build
├── imgui_tables.cpp           ← 表格控件（独立成文件因为代码量大）
├── imgui_demo.cpp             ← Demo 窗口（不依赖、可剥离的"活文档"）
│
├── imstb_rectpack.h           ← 字形 Pack 算法（stb_rect_pack 的内嵌副本）
├── imstb_textedit.h           ← 文本输入框引擎（stb_textedit 的内嵌副本）
├── imstb_truetype.h           ← TrueType 字体光栅化（stb_truetype 的内嵌副本）
│
├── backends/                  ← 平台后端（Win32/SDL/GLFW...）+ 渲染后端（GL/DX/Vulkan/Metal/WGPU/SDLGPU...）
├── examples/                  ← 各 Backend 组合的可运行示例工程
└── misc/                      ← FreeType 集成、std::string 适配、字体压缩工具
```

**两条阅读建议**：

- **核心 .cpp 之间不是"层级"关系，而是"切片"关系**：你不会"读完 imgui.cpp 再开始 imgui_widgets.cpp"，而是会"在 `Begin()` 里跳到 imgui_draw.cpp 的 `ChannelsSplit`，再跳回 imgui.cpp 的 `ItemAdd`"。
- **`imstb_*.h` 三件套是 stb 库的内嵌副本**：直接基于公网版本魔改了一些。**几乎不需要去读**，但要知道它们存在——尤其是 `imstb_truetype.h`，决定了字体光栅化的所有细节。

接下来看 `backends/`：

```
backends/
├── imgui_impl_win32.cpp/.h          ← 平台后端：Win32 消息泵
├── imgui_impl_glfw.cpp/.h           ← 平台后端：GLFW
├── imgui_impl_sdl2.cpp/.h           ← 平台后端：SDL2
├── imgui_impl_sdl3.cpp/.h           ← 平台后端：SDL3
│
├── imgui_impl_opengl3.cpp/.h        ← 渲染后端：OpenGL 3+
├── imgui_impl_opengl2.cpp/.h        ← 渲染后端：OpenGL 2.x（legacy）
├── imgui_impl_dx11.cpp/.h           ← 渲染后端：DirectX 11
├── imgui_impl_dx12.cpp/.h           ← 渲染后端：DirectX 12
├── imgui_impl_vulkan.cpp/.h         ← 渲染后端：Vulkan
├── imgui_impl_metal.cpp/.mm         ← 渲染后端：Metal（苹果）
├── imgui_impl_wgpu.cpp/.h           ← 渲染后端：WebGPU
├── imgui_impl_sdlgpu3.cpp/.h        ← 渲染后端：SDL GPU
└── imgui_impl_null.cpp/.h           ← 渲染后端：无（用于 headless 测试）
```

**关键概念：Backend 一分为二**

ImGui 的"Backend"实际上**不是一个**，而是**两个独立的**模块组合：

| 类型 | 责任 | 典型文件 | 调用时机 |
|---|---|---|---|
| **Platform Backend** | 输入事件 / 鼠标坐标 / 键盘 / 剪贴板 / OS 窗口创建（多视口） | `imgui_impl_glfw.cpp`、`imgui_impl_sdl3.cpp`、`imgui_impl_win32.cpp` | `NewFrame` 之前调用 `XXX_NewFrame` |
| **Renderer Backend** | 顶点/索引 buffer 上传 / Draw call 提交 / 字体纹理上传 / Scissor 裁剪 | `imgui_impl_opengl3.cpp`、`imgui_impl_vulkan.cpp`、`imgui_impl_dx11.cpp` | `Render` 之后调用 `XXX_RenderDrawData` |

你会看到 `examples/` 里出现的工程名都是 `example_<platform>_<renderer>` 的形式，例如 `example_glfw_opengl3`、`example_win32_directx11`。这正是因为两套 Backend 是**正交独立**的——你可以 GLFW + Vulkan、SDL + DX11、Win32 + WGPU 任意组合。

**对自研引擎的启示**：你**不需要**用官方的 `imgui_impl_*`。Hazel 那种"自管所有窗口/输入/渲染"的引擎，更应该写自己的 Platform / Renderer 桥接层（这是第 5.4 章的实战内容）。但**第一次集成时**直接用官方 backend 是 OK 的——它能让你跑起来，先看到东西再优化。

## 0.1.2 公共 API（imgui.h）vs 私有 API（imgui_internal.h）

这是一个重要的认知分界。

**imgui.h** 是 ImGui 对**应用层**的承诺：

- 这里声明的所有 `ImGui::XXX()` 函数、所有公开的 `struct ImGuiXxx`、所有 `enum ImGuiXxxFlags_`，**官方承诺保持向后兼容**——除非你看到注释里明确写 "obsolete in 1.XX"。
- 跨版本升级 ImGui，只要你只用了 `imgui.h` 里的东西，**90% 概率不需要改你的代码**。

**imgui_internal.h** 是 ImGui 对**自身**的内部接口：

- 这里声明的所有结构体（`ImGuiContext`、`ImGuiWindow`、`ImGuiTable`...）、所有未导出的内部函数，**官方明确不保证稳定性**——版本之间随时可能改名、改字段、改语义。
- 但是它**不是私有的**：你随时可以 `#include "imgui_internal.h"` 来访问内部 API。
- 你**必须**用它的场景：写自定义 Widget（要 `ItemAdd` / `ItemHoverable` / `ButtonBehavior`）、写自定义 Layout、深度对接引擎渲染、读取/操控窗口的内部状态。

**心智模型对照**：

```
应用层 (your editor.cpp)
        │
        │  只 #include "imgui.h"
        ▼
┌──────────────────────────────────────┐
│  imgui.h  ← 稳定 API 契约              │  ← 官方承诺：升级不破坏
└──────────────────────────────────────┘
        │
        │  魔改时 #include "imgui_internal.h"
        ▼
┌──────────────────────────────────────┐
│  imgui_internal.h  ← 私有但开放         │  ← 升级可能破坏，需要 IMGUI_VERSION_NUM 守护
└──────────────────────────────────────┘
        │
        │  内部实现细节（你只看不写）
        ▼
┌──────────────────────────────────────┐
│  imgui*.cpp  ← 实现源码                │  ← 完全可读、完全可改
└──────────────────────────────────────┘
```

**实操守则**（这条会贯穿全系列）：

- 在你的应用代码里：只 include `imgui.h`，能用公开 API 就不用 internal。
- 在你的自定义 Widget 库 / 编辑器扩展里：可以 include `imgui_internal.h`，但所有访问 internal 字段的地方**必须**包裹一层 `#if IMGUI_VERSION_NUM >= NNNNN` 守护——这是为了防止你某天升级 ImGui 时，编译失败比"运行时随机闪退"好得多。
- 永远不要直接 `#include "imgui.cpp"`：`imgui.cpp` 里有大量 `static` 函数和 `static` 全局变量，不是给你用的。

## 0.1.4 三个核心心智模型

这一节是本章最重要的部分。后面所有章节都会**反复**回到这三个模型。

### 心智模型 ①：帧循环单线时间轴

ImGui 的全部代码都活在**一根时间轴**上：

```
        ┌───────────────────────────────────────────────────────────┐
        │                       一帧的时间轴                            │
        ├───────────────────────────────────────────────────────────┤
        │                                                           │
  ▼ Backend 把输入事件灌进来：                                          │
  │     io.AddKeyEvent / io.AddMousePosEvent / ...                   │
  │                                                                  │
  ▼ ImGui::NewFrame()                                                │
  │     - 处理输入事件队列                                              │
  │     - 推进时间、动画、光标闪烁                                        │
  │     - 重置上一帧的"逐帧状态"（CurrentWindow、CursorPos、_Path 等）     │
  │                                                                  │
  ▼ 用户代码：                                                         │
  │     ImGui::Begin("MyWindow");                                    │
  │     ImGui::Button("Click");        ← 此时立即被求值是否点击           │
  │     ImGui::SliderFloat(...);                                     │
  │     ImGui::End();                                                │
  │     （随便多少个 Begin/End 都行）                                   │
  │                                                                  │
  ▼ ImGui::Render()                                                  │
  │     - 把所有 ImGuiWindow::DrawList 收集到 ImDrawData               │
  │     - 多视口模式下还要分到各 Viewport                                │
  │                                                                  │
  ▼ Backend 把 ImDrawData 渲染到 GPU：                                │
  │     ImGui_ImplOpenGL3_RenderDrawData(ImGui::GetDrawData());      │
  │                                                                  │
  ▼ Backend 交换 swap chain                                          │
        └───────────────────────────────────────────────────────────┘
                                  │
                                  ▼
                            （进入下一帧）
```

**关键性质**：

- **没有"事件回调"**：你不会写 `button.onClick(...)`。`ImGui::Button("X")` 直接返回 `bool` 表示"这一帧用户是否点了它"。
- **没有"持久 widget 对象"**：你以为 `ImGui::Button("X")` 创建了一个按钮，**错**。它没创建任何东西。它执行了一段代码：(1) 计算这个按钮在屏幕上的位置和大小，(2) 检查鼠标是否在这个矩形内、是否按下，(3) 把按钮的几何画进 DrawList，(4) 返回 bool。
- **状态持久化靠 ID Hash**：那些"看起来"持久的状态（比如 SliderFloat 当前的 0.7 值，由你的 `float v` 变量持有；比如折叠树的展开状态），有一部分由 ImGui 通过 ID 哈希存进 `ImGuiStorage` 里。
- **每帧都重建一切**：上面的 `ImDrawData` 每帧从零开始构建。但底层的 `ImVector` 不释放内存——它的 capacity 跨帧保留，只有 size 重置为 0。这就是 ImGui 能"每帧重建 UI 但运行时近乎零分配"的核心机制（详见第 2.1 章）。

**易错点**：

- 不要在 `NewFrame` 之前写 ImGui 代码，否则 `g.HoveredId` 等"逐帧状态"可能是上一帧的脏数据。
- 不要在 `Render` 之后改 ImGui 状态：你改了也不会反映到这一帧的 DrawData，但可能干扰下一帧的初始化。
- 不要跨帧持有 `ImGuiWindow*`：窗口在某些情况下会被回收/重建，跨帧持有指针等于持有悬挂指针。

### 心智模型 ②：ID Stack 即"逻辑路径"

ImGui 是 **immediate mode**——这意味着你**没有**"widget 对象树"。但你显然又需要一种方法把"昨天那个 Slider 的值"和"今天这个 Slider 的值"对应起来。这个方法就是 **ID**。

```
ImGui::Begin("MyWindow");           // PushID("MyWindow")  → 进入命名空间
  ImGui::PushID("Settings");        // PushID("Settings")  → 嵌套命名空间
    ImGui::SliderFloat("Speed", &v, 0, 1);   // ID = Hash("Settings/Speed")
    ImGui::SliderFloat("Mass",  &m, 0, 1);   // ID = Hash("Settings/Mass")
  ImGui::PopID();
ImGui::End();
```

每个控件的最终 ID 是由"当前 ID 栈"+"控件 label"哈希出来的（具体哈希算法第 4.1 章详解）。换句话说，**控件的 ID = 控件在源码中的逻辑路径**。

**为什么这是核心心智模型**：

- 你不写"Widget 树"，但 ID 栈**等价于**一棵虚拟的 Widget 树。
- 所有跨帧持久化（鼠标悬停、焦点、文本框光标位置、TreeNode 展开、滚动条位置）都靠 ID 索引。
- 99% 的"控件状态丢失/串台"bug 都是 ID 冲突导致的。

**最常见的 ID 冲突场景**：

```cpp
for (int i = 0; i < n; i++)
    ImGui::Button("Delete");     // ❌ n 个按钮共享同一个 ID
                                 //   只有第一个能被点击
```

正确写法（第 4.1 章会详细讲多种修法）：

```cpp
for (int i = 0; i < n; i++)
{
    ImGui::PushID(i);
    ImGui::Button("Delete");
    ImGui::PopID();
}
```

或者借助 `"###"` 显式 ID：

```cpp
for (int i = 0; i < n; i++)
    ImGui::Button(("Delete##" + std::to_string(i)).c_str());
    // "##xxx" 后缀只参与 ID 哈希，不显示
```

**记忆法**：每次写一个新控件，问自己"它的 ID 路径是什么？"——这是 ImGui 程序员的肌肉记忆。

### 心智模型 ③：顶点缓冲是唯一对外契约

无论 ImGui 多复杂，它和"GPU"的对接面**极简**：

```
ImGui Core
        │
        │  (CPU 端)
        ▼
┌──────────────────────────────────┐
│  ImDrawData                      │
│   ├ ImVector<ImDrawList*>        │
│   │      ├ VtxBuffer (顶点数组)   │
│   │      ├ IdxBuffer (索引数组)   │
│   │      └ CmdBuffer (Draw 命令)  │
│   ├ DisplayPos / DisplaySize     │
│   └ FramebufferScale             │
└──────────────────────────────────┘
        │
        │  Backend 读取它，提交到 GPU
        ▼
        GPU 画三角形
```

ImGui **不知道**也**不关心**:
- 你用的是 OpenGL / Vulkan / DX11 / Metal 还是别的什么。
- 你的渲染线程在哪。
- 你的 framebuffer 是不是 SRGB。
- 你的 swap chain 怎么调度。

ImGui **只承诺**：
- 给你一份 `ImDrawData`，里面是若干 ImDrawList，每个 list 里是连续的 VB/IB/Cmd。
- 顶点格式默认是 `pos(2 floats) + uv(2 floats) + col(uint32)` = 20 字节。
- 索引格式默认 `unsigned short`（16-bit），可以编译期切到 32-bit。
- 每个 `ImDrawCmd` 大致对应**一次 GPU draw call**（除非它是 callback）。
- 每个 `ImDrawCmd` 携带 `ClipRect`（屏幕空间裁剪矩形）、`TexRef`（纹理句柄）、`VtxOffset/IdxOffset/ElemCount`（在 VB/IB 里的范围）。

**这个契约的工程意义**：

- 它是 ImGui "可以接入任何引擎、任何渲染 API" 的根本原因——只要你的引擎能把"一组顶点 + 一个纹理 + 一个 ClipRect" 画到屏幕上，你就能集成 ImGui。
- 它意味着 ImGui 的"渲染层"和你的"引擎渲染层"**没有**生命周期纠葛——`ImDrawData` 就是一份数据快照。
- 它意味着**多线程隔离的天然边界就在这条契约上**：UI 构建在线程 A 完成，把 `ImDrawData` 交给线程 B 渲染（前提是 B 在 A 释放 DrawData 之前完成）。第 6.2 章会展开。

## 0.1.5 调试三件套：Demo / Metrics / Debug Log

读 ImGui 源码的最佳搭档不是 IDE 的 "Go to Definition"，而是它自带的三个调试窗口。

### Demo 窗口（`ImGui::ShowDemoWindow`）

```cpp
bool show = true;
ImGui::ShowDemoWindow(&show);
```

**它的真正价值不是"演示"，是"活文档"**。`imgui_demo.cpp` 里的每一段代码都是一个**可立即运行的最小示例**。

实际操作姿势：

1. 你想知道"某个功能怎么用"——例如 `BeginTabBar / TabItem`、`Selectable` 多选、`ImGui::Combo` 用法——直接在 Demo 窗里翻到对应章节，**右键 → "Open Source"** 跳到源码（如果你的环境支持），或者在 `imgui_demo.cpp` 里搜 Demo 上的章节名。
2. Demo 还内置了 **Tools** 子菜单：Style Editor（实时改主题）、Font Selector、Item Picker、ID Stack Tool、Debug Log——这些是你后面调试自家 UI 的主战场。

### Metrics 窗口（`ImGui::ShowMetricsWindow`）

```cpp
ImGui::ShowMetricsWindow();
```

这是 ImGui **暴露内部状态最详尽**的窗口。你能在这里看到：

- **Tools**: Item Picker（鼠标点哪个控件就高亮哪个 ID）、ID Stack Tool（反查某个 ID 是怎么哈希出来的）。
- **Windows**: 所有 `g.Windows` 里的窗口列表，每个的位置、大小、Active、Hovered、Focused、DrawList 顶点/索引数。
- **Tables**: 当前活跃的 ImGuiTable 列表。
- **DrawLists**: 每个 ImDrawList 的 ClipRect、Vtx/Idx 数量，可以单击展开看每个 ImDrawCmd。
- **Viewports**: 多视口模式下每个 Platform Window 的状态。
- **IO**: `ImGuiIO` 的所有字段（鼠标、键盘、配置 flag）。
- **Inputs**: 当前帧 `g.InputEventsQueue` / `g.InputEventsTrail` 的事件流。

**核心用法**：当你的 UI 出问题时（鼠标悬停不响应、按键被吃掉、控件位置错乱、Draw call 数量爆炸），第一反应不是 print 调试，是开 Metrics。

### Debug Log 窗口（`ImGui::ShowDebugLogWindow`）

```cpp
ImGui::ShowDebugLogWindow();
```

Debug Log 把 ImGui 内部的关键事件**实时打印**：

- **ActiveID** 变更：哪个 ID 变成了 active、上一个 active 是谁、原因是什么。
- **Focus** 变更：哪个窗口/控件获得了焦点。
- **Clipper** 跳过的范围（用于排查 ListClipper 问题）。
- **Selection** 多选请求。
- **InputRouting** 快捷键路由的判定过程。
- **Nav** 键盘/手柄导航的目标变化。
- **Popup / Modal** 的开/关时序。

**典型场景**：你写一个自定义控件，`IsItemActive()` 返回 `false`——你不知道是 "ItemAdd 时没注册" 还是 "ButtonBehavior 没把 ActiveID 设上去"。打开 Debug Log，勾上 **ActiveId** 类别，再点你的控件——它会告诉你 ActiveId 变更的全过程。

## 0.1.6 阅读源码的工具链建议

### 必备：跳转工具

ImGui 的代码在 SECTION 内部相对自洽，但**跨 SECTION** 跳转频繁（例如 `Begin()` 会调用十几个函数，分散在 5 个 SECTION）。你需要：

- **VS Code + clangd 扩展**：开箱即用的 Go-to-Definition / Find-References / Symbol Tree。配置 `compile_commands.json`（用 CMake 的 `-DCMAKE_EXPORT_COMPILE_COMMANDS=ON` 生成）。
- **Visual Studio**：Intellisense 在 ImGui 这种 C 风格代码里出乎意料地好用。开 `Ctrl+Click` 跳转。
- **CLion / Rider**：JetBrains 的索引很重，但跨文件跳转最可靠。
- **不建议**：vim/neovim 的 ctags/cscope 在 11000 行 + 大量同名 static 函数的场景下**经常误跳**。除非你已经很熟练，否则不要为了"看起来酷"折磨自己。

### 必备：调试器

调试器才是真正能让你"理解 ImGui 怎么运行"的工具。两个高频用法：

**用法 1：条件断点跟踪 ID**

```
断点位置: ItemAdd（imgui.cpp 中 [SECTION] ITEM SUBMISSION）
条件: id == 0xC1A23B4D   ← 用 Metrics 的 ID Stack Tool 拿到你目标控件的 ID
```

这个断点会在"某个特定控件被注册到布局系统"时停下，你就能看到调用栈、当前窗口、当前 ID 栈。

**用法 2：监视 `GImGui->HoveredId / ActiveId`**

把 `g.HoveredId`、`g.ActiveId`、`g.NavId`、`g.LastItemData.ID` 加进 Watch 窗口。在你怀疑"焦点被偷"时单步走，看哪一步把它改没了。

### 推荐：Stencil 工具

**`Find In Files`** 当然是基础。但 ImGui 还有一些"非常 ImGui 的"搜索目标：

- 搜 `[SECTION]` 找所有章节锚点。
- 搜 `// FIXME-` 找官方自己标的待办（`FIXME-MULTITHREADING` / `FIXME-SETTINGS` / `FIXME-PRESERVED-VS-RECOVERED` 等等）。看 FIXME 是了解项目"边角问题"最快的方式。
- 搜 `IMGUI_DEBUG_LOG_` 找所有 Debug Log 的事件触发点——这是反向定位"某个事件在哪发生"的捷径。

### 推荐：图表工具

读源码常常需要画依赖图。两个轻量级方案：

- **PlantUML**：用文本描述时序图、类图。文本可以提交到代码库。
- **Graphviz / dot**：调用关系图。例如把 `Begin()` 的 50 个被调函数画成一张 dot 图。

但**别陷在画图里**。本系列每章都会给你 ASCII 时序图作为"够用版"，你不需要为每个函数画 graphviz。

## 0.1.7 本系列贯穿用的"调试三件套"工作流

很多读者读到这里会问：我每天打开 ImGui 项目时，应该按什么顺序操作？给你一个**标准开局流程**：

```
1. 打开你的引擎/Editor 工程，跑起来。
2. 在第一个 ImGui 调用之前调用 ImGui::ShowDemoWindow(&show_demo);
   （只在 Debug 构建里显示）
3. 同时调用 ImGui::ShowMetricsWindow(&show_metrics);
   ImGui::ShowDebugLogWindow(&show_debug_log);
4. 在 Demo 窗里翻你今天要碰的那个功能（比如要写 Slider，先看 Demo 里的 SliderFloat 例子）。
5. 在 Metrics → Tools 里开 Item Picker，确认你认为是"那个控件"的东西，确实是那个 ID。
6. 写自己的代码。
7. 出问题时：
   a. 先看 Metrics → Windows → 你的窗口 → DrawList，看 Vtx/Idx 数量是否合理。
   b. 再看 Metrics → IO，看输入有没有进 ImGui。
   c. 最后看 Debug Log → ActiveId/Focus 类别，看焦点流转是否如你预期。
```

**这套流程会让你 80% 的 UI bug 在第一次打印之前就被定位**。

## 0.1.8 给"第一次读源码"的人：从哪一行开始？

如果你是第一次打开 `imgui.cpp`，以下是**推荐的阅读顺序**（不是从第 1 行往下）：

1. **`imgui.cpp:60-101`**：读完整个 SECTION 目录。给自己一张全局地图。
2. **`imgui_internal.h:10-42`**：再读 internal 的 SECTION 目录。理解"内部数据结构"和"主流程"是分开组织的。
3. **`imgui.cpp:[SECTION] CONTEXT AND MEMORY ALLOCATORS`**（约 1414-1453 行，仅 40 行）：理解 `GImGui` 是什么、为什么是单例、怎么自定义分配器。
4. **`imgui.h` 顶部到 `IMGUI_VERSION_NUM`**：理解版本号、IM_ASSERT、IMGUI_API 这些基础宏。
5. **`imgui.h` 中 `struct ImVector`**（约第 2207 行）：60 行代码，但是是后面所有数据结构的基石。
6. **`imgui.h` 中 `struct ImDrawCmd / ImDrawVert / ImDrawData`**（约 3180、3201、3445 行）：3 个核心结构体，每个 20-30 行。
7. **`backends/imgui_impl_opengl3.cpp::ImGui_ImplOpenGL3_RenderDrawData`**（约第 536 行起）：完整看完一个 Backend 是怎么消费 `ImDrawData` 的——大约 200 行，看完你就知道"画 ImGui"是什么意思。
8. **`imgui_demo.cpp`** 的第一个 `ImGui::ShowDemoWindow` 函数：随便挑一个章节看它怎么用 ImGui API 写 UI。

完成上面 8 步，你就有了一份"工作模型"。**接下来，本系列的第一部分会带你从这里出发，按"现代架构 → 数据结构 → 渲染管线 → 状态机 → 魔改实战"一路深入**。
