## 6.1.0 一段开场白：为什么这一章必要

ImGui 是**显式单线程库**。但你的引擎大概率是多线程的：

- 主线程跑游戏逻辑。
- 渲染线程提交 GPU 命令。
- 资源线程异步加载贴图 / 模型 / 音频。
- 物理线程（PhysX / Bullet）独立 tick。
- Job System 把所有可并行任务抢占式分配到 N 核。

把 ImGui 接到这种引擎里，**不知道哪里能并发、哪里必须串行**就是定时炸弹——半年后某天某个用户切了高 fps + 复杂场景时随机崩溃，你 grep "thread" 才发现 ImGui 不是线程安全的。

本章把 ImGui 的多线程契约**写白**——所有可以做的、不能做的，都给出源码证据。

## 6.1.1 C++ 多线程基础最小够用集

如果你已经熟悉这部分，直接跳到 6.1.2。

### 数据竞争（Data Race）

C++ 标准定义：

> 两个或多个线程对**同一非原子变量**做访问，至少一个是写——构成数据竞争 → **未定义行为**。

```cpp
int counter = 0;

void thread_a() { counter++; }   // 读 + 加 + 写
void thread_b() { counter++; }   // 同上

// 启动两个线程同时跑 1 万次：
// 期望 counter == 20000
// 实际 counter 可能是 12345（因为读-写之间被另一个线程抢断）
```

**"未定义行为"不是"结果不对"** —— 是**编译器可以做任何事**。包括：

- 优化掉某些读 / 写。
- 假设变量不会被其他线程改，做寄存器缓存。
- 重排指令顺序。

数据竞争**永远不应该发生**——不是"99% 不会出问题"，是**任何**情况下都不能写。

### 解决方案 1：`std::atomic`

```cpp
std::atomic<int> counter{0};

void thread_a() { counter.fetch_add(1); }
void thread_b() { counter.fetch_add(1); }
// counter 最终 == 20000，保证。
```

`std::atomic<T>` 提供"无锁 + 原子"的读写。CPU 用专门的 LOCK 前缀指令实现。

### 解决方案 2：`std::mutex`

```cpp
std::mutex mtx;
int counter = 0;

void thread_a() {
    std::lock_guard<std::mutex> lock(mtx);
    counter++;
}
```

互斥量保证"任何时刻只有一个线程进入临界区"。比 atomic 慢但能保护多个变量、复杂操作。

### 内存序（Memory Order）

```cpp
std::atomic<int> x{0}, y{0};

// Thread A:
y.store(1, std::memory_order_relaxed);
x.store(1, std::memory_order_relaxed);

// Thread B:
while (x.load(std::memory_order_relaxed) != 1);
int v = y.load(std::memory_order_relaxed);   // v 不一定 == 1！
```

**relaxed 序**只保证单变量原子，不保证操作之间的可见顺序。CPU / 编译器可重排指令。

ImGui 的代码**几乎不用 atomic**——也就**不能依赖任何内存序保证**。所有跨线程通信必须靠**互斥量**或**约定的"happens-before"关系**（例如线程 A 完成后启动线程 B，线程 B 中读取到的 A 写入是可见的）。

### `thread_local` 关键字

```cpp
thread_local int my_value = 0;

// 每个线程有自己的 my_value 副本
// 线程 A：my_value = 1
// 线程 B：my_value = 2
// 互不干扰
```

C++11 引入。底层依赖 OS 的 TLS（Thread Local Storage）：

- Windows：`__declspec(thread)` 或 fiber-local storage。
- Linux：`__thread` 或 GCC TLS section。
- 访问开销：通常多一次间接（fs/gs 段寄存器读取），但可以忽略。

**`thread_local` 的关键性质**：每个线程**独立初始化 + 独立销毁**。

```cpp
struct Logger {
    Logger()  { printf("Logger created\n"); }
    ~Logger() { printf("Logger destroyed\n"); }
};

thread_local Logger g_logger;
// 主线程进入 main → 创建 Logger
// std::thread 启动 → 那个线程也创建一个 Logger
// 线程退出 → 该线程的 Logger 销毁
// main 退出 → 主线程的 Logger 销毁
```

### 内存屏障与 acquire / release

```cpp
std::atomic<bool> ready{false};
int data = 0;

// Thread A (生产者)：
data = 42;
ready.store(true, std::memory_order_release);   // 屏障：data 的写在 ready 之前可见

// Thread B (消费者)：
if (ready.load(std::memory_order_acquire)) {     // 屏障：之后的 data 读不会被重排到这之前
    assert(data == 42);   // 一定为 true
}
```

`release / acquire` 配对使用——产生"happens-before"关系。比 relaxed 强、比 seq_cst 弱。

ImGui **不使用**这种细粒度同步——它**完全单线程**。

## 6.1.2 ImGui 的"全局指针"机制

回看 `imgui.cpp:1437~1439`：

```cpp
#ifndef GImGui
ImGuiContext*   GImGui = NULL;
#endif
```

**这个全局变量是 ImGui 整个 API 的隐式参数**。所有 `ImGui::Begin` / `Button` / 等调用都通过它访问 Context 状态。

```cpp
// 任意 ImGui::XXX 函数开头：
void ImGui::SomeFunction() {
    ImGuiContext& g = *GImGui;     // 读全局指针
    ImGuiWindow* window = g.CurrentWindow;
    // ...
}
```

**没有任何同步**——`GImGui` 就是个普通指针。

### 多线程下 `GImGui` 的危险

```cpp
// Thread A:
ImGui::CreateContext();   // GImGui = ctx_a
ImGui::Begin("WindowA");  // 改 ctx_a 的 CurrentWindow

// Thread B:
ImGui::CreateContext();   // GImGui = ctx_b（全局指针被覆盖！）
ImGui::Begin("WindowB");  // 此时 Thread A 看不到自己的 ctx_a 了
```

——**完全混乱**。两个线程共享 `GImGui`，互相覆盖。

## 6.1.3 证据 1：`imgui.cpp:1427~1434` 官方"not thread-safe"声明

```cpp
// imgui.cpp:1424~1436 完整段
// Current context pointer. Implicitly used by all Dear ImGui functions. Always assumed to be != NULL.
// - ImGui::CreateContext() will automatically set this pointer if it is NULL.
//   Change to a different context by calling ImGui::SetCurrentContext().
// - Important: Dear ImGui functions are not thread-safe because of this pointer.   ← ★ 这是"宣言"
//   If you want thread-safety to allow N threads to access N different contexts:
//   - Change this variable to use thread local storage so each thread can refer to a different context, in your imconfig.h:
//         struct ImGuiContext;
//         extern thread_local ImGuiContext* MyImGuiTLS;
//         #define GImGui MyImGuiTLS
//     And then define MyImGuiTLS in one of your cpp files. Note that thread_local is a C++11 keyword, earlier C++ uses compiler-specific keyword.
//   - Future development aims to make this context pointer explicit to all calls. Also read https://github.com/ocornut/imgui/issues/586
//   - If you need a finite number of contexts, you may compile and use multiple instances of the ImGui code from a different namespace.
// - DLL users: read comments above.
```

**逐句解读**：

> `// - Important: Dear ImGui functions are not thread-safe because of this pointer.`

**核心声明**：所有 ImGui 函数**不是**线程安全的——根本原因是 `GImGui` 全局指针。

> `// If you want thread-safety to allow N threads to access N different contexts:`

——**N 线程对应 N Context** 是官方支持的模式。但**单 Context 跨线程并发**不支持。

> `//   - Change this variable to use thread local storage`

**官方推荐配方**：把 `GImGui` 改成 `thread_local`。每个线程有自己的"当前 Context"指针。

### 完整 `thread_local` 配方

```cpp
// imconfig.h
struct ImGuiContext;
extern thread_local ImGuiContext* MyImGuiTLS;
#define GImGui MyImGuiTLS
```

```cpp
// MyImGuiTLS.cpp（任意一个 .cpp 文件）
#include "imgui.h"
thread_local ImGuiContext* MyImGuiTLS = NULL;
```

**配置后的效果**：

- `GImGui` 不再是全局变量——是 `MyImGuiTLS` 这个 thread_local 变量的别名。
- 每个线程有独立的 `MyImGuiTLS`。
- 一个线程 `SetCurrentContext(ctx_a)`，另一个线程仍可以 `SetCurrentContext(ctx_b)`，互不干扰。

### 注意事项

`thread_local` 是 C++11——某些古旧编译器可能不支持。fallback：

- MSVC: `__declspec(thread)`
- GCC/Clang 4.0+: `__thread`

但 ImGui 1.92 的最低编译器要求已经支持 `thread_local`，直接用即可。

## 6.1.4 证据 2：`IMGUI_SET_CURRENT_CONTEXT_FUNC` 钩子

```cpp
// imgui.cpp:4072~4079
void ImGui::SetCurrentContext(ImGuiContext* ctx)
{
#ifdef IMGUI_SET_CURRENT_CONTEXT_FUNC
    IMGUI_SET_CURRENT_CONTEXT_FUNC(ctx); // For custom thread-based hackery you may want to have control over this.
#else
    GImGui = ctx;
#endif
}
```

**`IMGUI_SET_CURRENT_CONTEXT_FUNC` 是给"自定义线程方案"的扩展点**。

如果你用 `thread_local GImGui` 模式：

```cpp
// imconfig.h
extern thread_local ImGuiContext* MyImGuiTLS;
#define GImGui MyImGuiTLS
#define IMGUI_SET_CURRENT_CONTEXT_FUNC(ctx)  (MyImGuiTLS = (ctx))
```

`SetCurrentContext` 调用时走你的宏 → 设置 thread_local 变量。

如果你不定义，默认 `GImGui = ctx`——编译时 `GImGui` 被宏展开成 `MyImGuiTLS`，所以仍然走 thread_local。**但定义 `IMGUI_SET_CURRENT_CONTEXT_FUNC` 显式更清晰**。

## 6.1.6 证据 4：`FIXME-MULTITHREADING` 在 `AddXxxEvent` 队列处

```cpp
// imgui.cpp:10546~10548 (UpdateInputEvents 末尾)
// Remaining events will be processed on the next frame
// FIXME-MULTITHREADING: io.AddKeyEvent() etc. calls are mostly thread-safe apart from the fact they push to this
// queue which may be resized here. Could potentially rework this to narrow down the section needing a mutex? (#5772)
if (event_n == g.InputEventsQueue.Size)
    g.InputEventsQueue.resize(0);
else
    g.InputEventsQueue.erase(g.InputEventsQueue.Data, g.InputEventsQueue.Data + event_n);
```

**逐句解读**：

> `// FIXME-MULTITHREADING: io.AddKeyEvent() etc. calls are mostly thread-safe apart from the fact they push to this queue which may be resized here.`

——`AddKeyEvent` 等**几乎**线程安全。**但**它们把事件推到 `g.InputEventsQueue`——这里 `UpdateInputEvents` 可能 `resize(0)` 同一个队列。**两线程同时操作 ImVector** = data race = UB。

### 实际场景

```cpp
// Thread A (OS 输入线程，例如 Win32 消息泵)：
io.AddKeyEvent(ImGuiKey_A, true);
   ↓ 内部：g.InputEventsQueue.push_back(event)

// Thread B (ImGui 渲染线程)：
ImGui::NewFrame();
   ↓ 内部：UpdateInputEvents(...)
        遍历 InputEventsQueue（A 可能正在 push_back）
        InputEventsQueue.erase(...) （A 可能在 push_back 时 ImVector 扩容）
```

**Thread A 的 push_back 可能触发 ImVector 扩容（IM_ALLOC + memcpy + IM_FREE 旧块）**——Thread B 同时遍历这个 ImVector → 读到悬挂指针 / 半完成的数据。

### 临时 workaround

如果你**必须**从另一个线程调 `AddKeyEvent`，得加 mutex：

```cpp
std::mutex g_imgui_input_mutex;

// OS 输入线程：
{
    std::lock_guard<std::mutex> lock(g_imgui_input_mutex);
    io.AddKeyEvent(ImGuiKey_A, true);
}

// ImGui 主线程：
{
    std::lock_guard<std::mutex> lock(g_imgui_input_mutex);
    ImGui::NewFrame();
}
```

但更简单的方案：**让 OS 输入事件传递给主线程的事件队列**——主线程自己调 `AddKeyEvent`：

```cpp
// OS 输入线程（在你引擎的 OS 抽象层）：
void OnGlfwKeyCallback(int key, bool down) {
    // 不直接调 AddKeyEvent
    // 推到一个无锁队列
    g_engine_input_queue.Push({key, down});
}

// 主线程的 ImGuiLayer::Begin：
{
    InputEvent ev;
    while (g_engine_input_queue.Pop(ev)) {
        ImGui::GetIO().AddKeyEvent(ev.key, ev.down);   // ← 在主线程调
    }
}
ImGui::NewFrame();
```

这是 99% 引擎采用的设计——OS 输入只往**单一队列**发，主线程消费。从根本上避免跨线程调 `AddXxxEvent`。

## 6.1.7 证据 5：字体子系统不再线程安全

```cpp
// imgui.cpp:503~504
//                       - Fonts: **IMPORTANT** on Thread Safety:
//                          - A few functions such as font->CalcTextSizeA() were, by sheer luck (== accidentally) thread-safe even though we had never provided that guarantee.
//                          - They are definitively not thread-safe anymore as new glyphs may be loaded.
```

**1.92 的动态字体系统**（`IMGUI_HAS_TEXTURES`）让字体图集可以在运行时动态扩展。这**意味着**：

- `font->CalcTextSizeA(text)` 内部可能触发"新字形烘焙 + 图集纹理更新"。
- 这些操作改 `ImFontAtlas` 的内部数据——同时另一个线程也在访问 → race。

**之前**（1.91 之前）：字体图集在 NewFrame 之前一次性 build，运行时只读 → 偶然线程安全。
**现在**（1.92+）：字体图集动态 build → 不再线程安全。

实战影响：如果你之前的多线程代码"巧合地"正确，升级 1.92 后必须审视。

## 6.1.8 单 Context 多线程并发：明确的 NO

汇总所有证据，**单 Context 多线程**绝对禁止的操作：

| 跨线程操作 | 原因 |
|---|---|
| 一线程 `NewFrame`，另一线程 `Begin/Button` | `g.WithinFrameScope` race |
| 一线程在跑 widget，另一线程 `Render` | `LastItemData` / `DrawList` race |
| 多线程同时 `AddKeyEvent` | `InputEventsQueue` race |
| 多线程同时调 `font->CalcTextSizeA` | 动态字形烘焙 race |
| 多线程访问 `ImGuiStorage` | sorted vector 二分查找时被另一线程插入 |
| 跨线程持有 `ImGuiWindow*` | window 可能被销毁 / 字段被改 |

**所有这些"绝对不能"** —— 没有 workaround，只有"避免"。

## 6.1.9 单 Context 单线程 + 多线程渲染：边界情况

有一种**有限的多线程**是允许的：

```
Thread A (UI 线程)：
   NewFrame
   构建所有 widget
   Render → 产生 ImDrawData
   把 ImDrawData 指针交给 Thread B
   等待 Thread B 完成（双缓冲）
   下一帧

Thread B (渲染线程)：
   收到 ImDrawData
   遍历 CmdLists
   上传 VB / IB 到 GPU
   提交 draw call
   通知 Thread A 完成
```

**为什么这个 OK**：

- Thread A 完成 Render 后**不**修改 ImDrawData。
- Thread B 只**读** ImDrawData，**不**改。
- 双缓冲：Thread A 在准备帧 N+1 时，Thread B 处理帧 N。

这是**双缓冲 ImDrawData** 的设计——`backends/imgui_impl_vulkan.cpp` 等高级 backend 用过类似模式。

但请注意：**`ImDrawData::CmdLists` 是 `ImVector<ImDrawList*>`——指向 `g.Windows[i]->DrawList`**。下一帧 Thread A 调 `NewFrame` 会改 DrawList 内容！如果 Thread B 还在读 → race。

**真正安全的做法**：克隆 ImDrawData。

```cpp
// imgui.h:3392
ImDrawList* ImDrawList::CloneOutput() const;
```

——产生一份独立副本。Thread A 渲染完后克隆每个 DrawList → 把克隆后的 DrawData 给 Thread B → Thread A 可以马上开始下一帧。

实际有现成项目：[`imgui_threaded_rendering`](https://github.com/ocornut/imgui_club/tree/main/imgui_threaded_rendering) ——演示这个模式。

## 6.1.10 多 DLL 边界陷阱（从第 2.3 章 + 多线程视角再看）

回到第 2.3 章的 DLL 问题——**每个 DLL 各自的 `GImGui`**。在多线程下问题更复杂：

```
HazelEngine.dll：
  thread_local ImGuiContext* MyImGuiTLS = NULL;   // 这个 DLL 的 thread_local

HazelEditor.dll：
  thread_local ImGuiContext* MyImGuiTLS = NULL;   // 不同 DLL 的 thread_local
                                                    // 两者完全独立！
```

每个 DLL 内部都有自己的 `MyImGuiTLS` 实例（thread_local 也分模块）。线程 A 在 HazelEngine.dll 里调 `SetCurrentContext(ctx)` → 只影响 HazelEngine.dll 的 thread_local。**HazelEditor.dll 内的 thread_local 仍然是 NULL**——HazelEditor.dll 调 ImGui::Begin 时崩溃。

### 解决方案

**每个 DLL 加载时自己同步**：

```cpp
// HazelEngine.dll 加载 HazelEditor.dll 后
extern "C" __declspec(dllexport)
void HazelEditor_OnLoad(ImGuiContext* ctx, /* allocator */) {
    ImGui::SetCurrentContext(ctx);    // 设置 HazelEditor.dll 自己的 thread_local
    ImGui::SetAllocatorFunctions(...);
}
```

**每条新启动的线程也要同步**：

```cpp
std::thread t([]() {
    // 新线程的 thread_local 默认是 NULL
    ImGui::SetCurrentContext(my_ctx);  // 必须设
    
    // 现在可以调 ImGui API
    // ...
});
```

——thread_local 是**新启动线程时默认零初始化**的。每个线程进 ImGui 域之前必须 SetCurrentContext。

## 6.1.11 Test Engine 与 Headless 模式

`imgui_test_engine` 是 ImGui 自动化测试套件。它的设计需要：

- 多个测试**并行**运行（CI 加速）。
- 每个测试有自己的 ImGui Context。

`imgui_test_engine` 的实现就是**多线程 + thread_local GImGui** 模式：

```cpp
// 简化伪代码
void RunTest(TestCase& tc) {
    ImGuiContext* ctx = ImGui::CreateContext();
    ImGui::SetCurrentContext(ctx);   // 该线程的 thread_local
    
    // 模拟用户交互
    tc.func();
    
    ImGui::DestroyContext(ctx);
}

// 启动 N 个测试线程
for (int i = 0; i < num_tests; i++) {
    threads[i] = std::thread([&, i]() { RunTest(tests[i]); });
}
```

——**N 线程 N Context**——这是官方支持的并发模式。

## 6.1.12 实战：在 Hazel 引擎里实现"线程安全的输入注入"

最常见的问题：OS 输入回调可能从**输入线程**触发，而 ImGui 在**主线程**处理。

### 错误做法（直接调 AddKeyEvent）

```cpp
// 由 OS 调用（可能在任意线程）
void OnGlfwKeyCallback(int key, bool down) {
    ImGui::GetIO().AddKeyEvent(...);   // ❌ 可能在错误线程
}
```

### 正确做法 1：让所有回调走主线程的 PollEvents

GLFW 的标准模式：

```cpp
// 主循环（主线程）：
glfwPollEvents();   // 同步调用，所有 callback 在这里执行

// callback 是 GLFW 在 PollEvents 内部直接调用——保证主线程
void GlfwKeyCallback(int key, bool down) {
    ImGui::GetIO().AddKeyEvent(...);   // ✅ 主线程
}
```

GLFW / SDL / Win32 大部分输入 API 都遵守"PollEvents 同步分发回调"模式——天然线程安全。

### 正确做法 2：跨线程时用无锁队列

```cpp
struct EngineInputEvent {
    enum Type { Key, Mouse, Char };
    Type type;
    union {
        struct { int key; bool down; } key_data;
        struct { float x, y; } mouse_data;
        struct { unsigned int codepoint; } char_data;
    };
};

class LockFreeInputQueue {
    moodycamel::ConcurrentQueue<EngineInputEvent> q;
public:
    void Push(EngineInputEvent ev) { q.enqueue(ev); }
    bool TryPop(EngineInputEvent* ev) { return q.try_dequeue(*ev); }
};

LockFreeInputQueue g_input_q;

// 任意线程：
void OnRawInput(int key, bool down) {
    EngineInputEvent ev;
    ev.type = EngineInputEvent::Key;
    ev.key_data = { key, down };
    g_input_q.Push(ev);
}

// 主线程 ImGuiLayer::Begin：
EngineInputEvent ev;
while (g_input_q.TryPop(&ev)) {
    switch (ev.type) {
        case EngineInputEvent::Key:
            ImGui::GetIO().AddKeyEvent(HazelKeyToImGuiKey(ev.key_data.key), ev.key_data.down);
            break;
        // ...
    }
}
ImGui::NewFrame();
```

——所有跨线程通过**单一无锁队列**汇集，主线程消费。`moodycamel::ConcurrentQueue` 是流行的无锁队列实现。

```cpp
// 启动 4 个线程，每个 1 秒内 push 1 万次 key 事件
std::vector<std::thread> stress_threads;
for (int i = 0; i < 4; i++) {
    stress_threads.emplace_back([]() {

// 主线程 1 秒内调 60 次 NewFrame/Render
for (int frame = 0; frame < 60; frame++) {
```

## 6.1.14 本章小结

ImGui 多线程契约的 6 条铁则：

1. **`GImGui` 默认是全局指针——单 Context 跨线程并发 = UB**。
2. **N 线程 N Context 模式**通过 `thread_local GImGui` 实现，是官方推荐方案。
3. **`AddXxxEvent` 不完全线程安全**——`InputEventsQueue.resize` 与 `push_back` 不同步。
4. **1.92 字体子系统因动态烘焙不再线程安全**——以前"巧合"的并发用法现在会崩。
5. **DLL 边界 + 多线程**：每个 DLL 自己的 thread_local，每条新线程自己 SetCurrentContext。
6. **唯一可并发的环节**：UI 线程产出 `ImDrawData` → 渲染线程读 `ImDrawData`（双缓冲 / 克隆）。

**记住的 4 个 issue 编号**（与官方未来工作相关）：

- #586：让 Context 显式作为参数。
- #5772：`InputEventsQueue` 的 mutex 化。
- #5856 / #6293 / #8069：多 Context 并行实验。

跟踪这些 issue 能让你提前知道 ImGui 团队的多线程演进方向。
