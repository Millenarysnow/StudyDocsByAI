# 第 0.3 章 · 内存模型 101：从栈堆对齐到 Trivially Relocatable

> **本章目标**：补齐你看 ImGui 容器实现（`ImVector` / `ImPool` / `ImChunkStream`）和分配器代码时所需的全部内存模型基础。读完后，你应该能**理直气壮**地接受 `memcpy(&Data[Size], &v, sizeof(v))` 拷一个有构造函数的对象——并能**严格说出**这种代码的合法边界。

## 0.3.0 这一章为什么必要

打开 `imgui.h:2255`，你会看到：

```cpp
inline void push_back(const T& v) {
    if (Size == Capacity) reserve(_grow_capacity(Size + 1));
    memcpy(&Data[Size], &v, sizeof(v));   // ← 用 memcpy 而不是赋值
    Size++;
}
```

打开 `imgui.h:2249`：

```cpp
inline void resize(int new_size, const T& v) {
    if (new_size > Capacity) reserve(_grow_capacity(new_size));
    if (new_size > Size)
        for (int n = Size; n < new_size; n++)
            memcpy(&Data[n], &v, sizeof(v));   // ← memcpy 一个对象
    Size = new_size;
}
```

打开 `imgui.h:2251`：

```cpp
inline void reserve(int new_capacity) {
    if (new_capacity <= Capacity) return;
    T* new_data = (T*)IM_ALLOC((size_t)new_capacity * sizeof(T));
    if (Data) {
        memcpy(new_data, Data, (size_t)Size * sizeof(T));   // ← memcpy 整个数组
        IM_FREE(Data);
    }
    Data = new_data;
    Capacity = new_capacity;
}
```

`T` 是模板参数，可能是 `int`，也可能是 `ImGuiWindow*`（指针），但更可能是 **带构造函数和成员的复杂结构体**——例如 `ImGuiTabItem`、`ImDrawCmd`、`ImGuiInputEvent`。

如果你下意识觉得"`memcpy` 一个有构造函数的对象一定是 UB"，本章会告诉你：

- ImGui 这样做是**有意为之**，遵循一组**清晰但不宽松**的规则。
- 这组规则的核心叫 **Trivially Relocatable**——一个 C++ 标准还没正式接受、但工业界（Folly / EASTL / ImGui / 各大游戏引擎）已经在用的概念。
- 你需要知道**哪些类型遵守了规则**（可以放进 ImVector）、**哪些类型违反了规则**（不能放进 ImVector）。

## 0.3.1 内存的"段"：栈、堆、数据段、常量段

这一节是给"内存知识不太系统"的同学的速通版。已经熟悉的可以快速浏览。

一个运行中的 C++ 进程，地址空间大致这样布局（典型 64 位 Linux/Windows，简化版）：

```
高地址  ┌─────────────────────────────┐
        │       内核空间（不可访问）        │
        ├─────────────────────────────┤
        │       栈 (Stack)             │  ← 自动变量、函数参数
        │       ↓ 向下生长              │
        │           ...                │
        │           ...                │
        │       ↑ 向上生长              │
        │       堆 (Heap)              │  ← malloc / new 分配
        ├─────────────────────────────┤
        │       BSS 段                │  ← 未初始化的全局/static 变量
        ├─────────────────────────────┤
        │       Data 段               │  ← 已初始化的全局/static 变量
        ├─────────────────────────────┤
        │       Const 段（.rodata）    │  ← 字符串字面量、const 全局
        ├─────────────────────────────┤
        │       Text 段（.text）       │  ← 代码（指令）
低地址  └─────────────────────────────┘
```

每个段的关键属性：

| 段 | 生命周期 | 大小 | 写权限 | 性能特征 |
|---|---|---|---|---|
| **Stack** | 函数返回时自动回收 | 通常 1 MB（线程默认） | 读写 | 极快，cache 命中率高 |
| **Heap** | 显式 `free`/`delete` 才回收 | 受可用 RAM 限制 | 读写 | 慢（要找空闲块、要更新元数据） |
| **BSS** | 进程结束才回收 | 编译期固定 | 读写 | 慢启动（OS 要清零） |
| **Data** | 进程结束才回收 | 编译期固定 | 读写 | 启动后立即可用 |
| **Const** | 进程结束才回收 | 编译期固定 | 只读（写会段错误） | 启动后立即可用 |
| **Text** | 进程结束才回收 | 编译期固定 | 只读 + 可执行 | 启动后立即可用 |

### 几个事实

**事实 1：栈分配是"零成本"的**

```cpp
void foo() {
    ImVec2 v = {3.0f, 4.0f};   // 栈分配，"零成本"
}
```

"零成本"指的是：**没有显式的内存分配函数调用**。CPU 实际操作只是 `sub rsp, 8`（栈指针下移 8 字节）。函数返回时 `add rsp, 8` 复位。

**但栈空间是有限的**。一个线程的栈通常 1 MB（Windows 默认 1 MB，Linux 默认 8 MB）。在栈上声明一个 `ImGuiContext`（>4KB）问题不大，但声明一个 `int huge[1024 * 1024]` 就炸了。

**事实 2：堆分配代价"看分配器"**

`malloc(N)` 内部要：

1. 在空闲块链表里找一个 ≥ N 字节的块（可能是 O(log N) 或更糟）。
2. 切分块（如果找到的块比 N 大很多）。
3. 更新元数据（已分配块的链表头）。
4. 多线程下还要锁 / 用 thread cache。

游戏引擎里 **每帧 N 次 malloc 是性能毒药**——这正是 ImGui 设计 `ImVector`"capacity 跨帧保留"模式的原因（`resize(0)` 不释放，下帧重用）。

**事实 3：写只读段会段错误**

```cpp
char* s = "hello";   // s 指向 .rodata 中的常量字符串
s[0] = 'H';          // 段错误！
```

但是：

```cpp
char s[] = "hello";  // s 是栈上的 char 数组，初始化拷贝自常量
s[0] = 'H';          // OK，改的是栈上的副本
```

ImGui 里到处都是 `const char* label`——传进来的是字符串字面量指针（指向 `.rodata`）。**你绝对不能 cast 掉 const 然后改它**。

**事实 4：BSS 段的"零初始化"是 OS 福利**

```cpp
static int big_array[1024 * 1024];   // BSS 段，自动 0 初始化
```

OS 加载程序时，BSS 段被 mmap 为"懒映射的零页"——你访问到哪页才分配那页物理内存，初始内容全是 0。这是为什么"全局变量默认 0"。

但是！**这只对 `static` / 全局变量成立**。函数内部的局部变量（栈上）**不**自动 0 初始化：

```cpp
void foo() {
    int x;       // 未初始化，值是栈上"残留"的垃圾数据
    int y = 0;   // 显式初始化为 0
}
```

ImGui 函数里大量 `ImVec2 size(0,0); int n = 0;` 这种**显式零初始化**——是为了不踩"未初始化局部变量"陷阱。

## 0.3.2 对齐（Alignment）与填充（Padding）

### 基本概念：alignof 和 alignas

每个类型都有一个**对齐要求**（alignment），表示这个类型的对象**起始地址必须是该值的整数倍**。

| 类型 | 大小 | 对齐 |
|---|---|---|
| `char` / `int8_t` | 1 | 1 |
| `short` / `int16_t` | 2 | 2 |
| `int` / `float` / `int32_t` | 4 | 4 |
| `double` / `int64_t` / 指针(64位) | 8 | 8 |
| `__m128`（SSE） | 16 | 16 |
| `__m256`（AVX） | 32 | 32 |

**为什么要对齐**：

CPU 取数据是**按 cache line**（通常 64 字节）取的，但寻址是按"对齐边界"取的。一个未对齐的 8 字节读取**可能跨越两个 cache line**，需要两次内存访问 + 拼接，性能开销 2~10 倍。x86 在 90% 情况下能容忍未对齐（性能损失），ARM 在某些指令上会**直接异常**。

**`alignof(T)` 查询对齐**：

```cpp
static_assert(alignof(int) == 4);
static_assert(alignof(double) == 8);
static_assert(alignof(ImVec2) == 4);   // 两个 float，对齐 4
static_assert(alignof(ImVec4) == 4);   // 四个 float，对齐 4
```

**`alignas(N)` 强制对齐**：

```cpp
struct alignas(16) MyVec4 {
    float x, y, z, w;
};
// sizeof(MyVec4) == 16, alignof(MyVec4) == 16
```

### 结构体的"自然填充"规则

```cpp
struct Foo {
    char a;      // 1 字节，偏移 0
    int  b;      // 4 字节，偏移 4（编译器插入 3 字节 padding）
    char c;      // 1 字节，偏移 8
                 // 末尾再填充 3 字节，让 sizeof(Foo) == 12（4 的倍数）
};
static_assert(sizeof(Foo) == 12);
static_assert(alignof(Foo) == 4);
```

**规则**：

1. **每个成员**起始偏移必须是它的 `alignof` 倍数。
2. **整个结构体**末尾要填充到 `alignof(struct)` 的倍数（这样数组里相邻元素都对齐）。
3. **结构体的 `alignof`** = 所有成员中最大的 `alignof`。

### `ImDrawVert` 为什么是 20 字节而不是 24

```cpp
// imgui.h:3201-3206
struct ImDrawVert {
    ImVec2  pos;   // 8 字节，偏移 0
    ImVec2  uv;    // 8 字节，偏移 8
    ImU32   col;   // 4 字节，偏移 16
};                 // 末尾不填充：sizeof = 20，alignof = 4
```

**关键事实**：`alignof(ImDrawVert) == 4`（因为 `ImVec2` 和 `ImU32` 的对齐都是 4）。所以末尾不需要填充到 8。`sizeof(ImDrawVert) == 20`。

如果作者**故意**把它写成：

```cpp
struct alignas(8) ImDrawVert {  // 假设强制 8 对齐
    ImVec2 pos;
    ImVec2 uv;
    ImU32  col;
    char   _pad[4];  // 手动填充
};                                // sizeof = 24
```

那么每个顶点会**多 4 字节**。一帧 ImGui UI 大约几千到几万顶点——浪费几十~几百 KB 的内存带宽。**ImGui 选择 20 字节是有意省内存**。

### GPU 顶点格式与 CPU 端对齐

GPU 顶点输入装配（IA）从 VB 里按"顶点 stride"读数据。OpenGL 里你这样描述：

```cpp
// backends/imgui_impl_opengl3.cpp:528-530
glVertexAttribPointer(loc_pos,   2, GL_FLOAT,         GL_FALSE, sizeof(ImDrawVert), (GLvoid*)offsetof(ImDrawVert, pos));
glVertexAttribPointer(loc_uv,    2, GL_FLOAT,         GL_FALSE, sizeof(ImDrawVert), (GLvoid*)offsetof(ImDrawVert, uv));
glVertexAttribPointer(loc_color, 4, GL_UNSIGNED_BYTE, GL_TRUE,  sizeof(ImDrawVert), (GLvoid*)offsetof(ImDrawVert, col));
```

`sizeof(ImDrawVert)` 就是顶点 stride。`offsetof` 是每个属性在结构体内的偏移。

**GPU 不要求顶点对齐到 16/32 字节**（不像 SIMD 寄存器）。20 字节的顶点完全 OK。

### `IMGUI_OVERRIDE_DRAWVERT_STRUCT_LAYOUT`：自定义顶点布局

```cpp
// imgui.h:3199-3213
#ifndef IMGUI_OVERRIDE_DRAWVERT_STRUCT_LAYOUT
struct ImDrawVert {
    ImVec2  pos;
    ImVec2  uv;
    ImU32   col;
};
#else
// You can override the vertex format layout by defining IMGUI_OVERRIDE_DRAWVERT_STRUCT_LAYOUT in imconfig.h
// The code expect ImVec2 pos (8 bytes), ImVec2 uv (8 bytes), ImU32 col (4 bytes), but you can re-order them or add other fields as needed to simplify integration in your engine.
// The type has to be described within the macro (you can either declare the struct or use a typedef). This is because ImVec2/ImU32 are likely not declared at the time you'd want to set your type up.
// NOTE: IMGUI DOESN'T CLEAR THE STRUCTURE AND DOESN'T CALL A CONSTRUCTOR SO ANY CUSTOM FIELD WILL BE UNINITIALIZED. IF YOU ADD EXTRA FIELDS (SUCH AS A 'Z' COORDINATES) YOU WILL NEED TO CLEAR THEM DURING RENDER OR TO IGNORE THEM.
IMGUI_OVERRIDE_DRAWVERT_STRUCT_LAYOUT;
#endif
```

**注释里的两条警告值得细读**：

1. "**The code expect ImVec2 pos (8 bytes), ImVec2 uv (8 bytes), ImU32 col (4 bytes)**"——你可以加字段，但**不能改这三个的类型/大小**。
2. "**IMGUI DOESN'T CLEAR THE STRUCTURE AND DOESN'T CALL A CONSTRUCTOR**"——你加的额外字段是**未初始化**的，必须自己清零或忽略。

**实战场景**：你在引擎里给每个顶点加一个 z 坐标（用于 3D 空间内显示 UI）：

```cpp
// 在 imconfig.h 里
#define IMGUI_OVERRIDE_DRAWVERT_STRUCT_LAYOUT  \
    struct ImDrawVert {                        \
        ImVec2 pos;                            \
        ImVec2 uv;                             \
        ImU32  col;                            \
        float  z;   /* 自定义字段 */              \
    };
```

注意：

- ImGui 内部 `pos.x / pos.y / uv.x / uv.y / col` 会照常被填充。
- `z` 由你自己在 callback 或后处理里设置。
- 整体 `sizeof(ImDrawVert)` 变成 24 字节——内存带宽多 20%。

## 0.3.3 POD / Trivially Copyable / Standard Layout / Trivially Relocatable

这是本章最关键的概念辨析。后续所有"为什么 ImGui 可以 memcpy 一个对象"都建立在这上面。

### 基础概念金字塔

```
┌────────────────────────────────────────────────┐
│  Trivially Relocatable                         │  最弱（但实用）
│  (P1144 提案；非标准)                            │
├────────────────────────────────────────────────┤
│  Trivially Copyable                            │  C++11 引入，标准
│  ⊆                                              │
├────────────────────────────────────────────────┤
│  Trivial                                       │  C++11 引入
│  ⊆                                              │
├────────────────────────────────────────────────┤
│  POD（Plain Old Data，C++03 概念）              │  最强（已废弃）
└────────────────────────────────────────────────┘
```

从下到上**约束放宽**，能描述更多类型。

### Trivial（平凡）

一个类型是 trivial，需要：
- 默认构造函数 trivial（要么没显式定义，要么 `= default`，且基类/成员的默认构造也都 trivial）。
- 拷贝构造、拷贝赋值、移动构造、移动赋值都 trivial。
- 析构函数 trivial。

**测试方法**：`std::is_trivial<T>::value`

```cpp
struct A { int x; };               // trivial
struct B { int x; B() {} };        // 不 trivial（有用户定义构造）
struct C { virtual ~C(); };        // 不 trivial（有虚析构 → 有 vtable）
```

**含义**：trivial 类型可以**用 `memcpy` 安全地拷贝、用 `memset(0)` 安全地清零**。

### Standard Layout（标准布局）

- 所有非静态数据成员**访问权限相同**（全 public 或全 private）。
- 不继承多个类（最多一层有数据成员的基类）。
- 没有虚函数 / 虚基类。
- 第一个非静态数据成员的偏移是 0（可以 cast 到第一个成员的指针）。

**含义**：standard layout 类型的内存布局是 **C 兼容的**。可以和 C 代码、其他编译器、其他语言互操作。

**测试方法**：`std::is_standard_layout<T>::value`

### Trivially Copyable（可平凡拷贝）

C++11 标准定义：
- 所有拷贝构造、拷贝赋值、移动构造、移动赋值要么没定义、要么是 trivial。
- 析构函数 trivial。

**这是 `std::memcpy` 安全使用的最低条件**（C++ 标准 [basic.types]）。

**测试方法**：`std::is_trivially_copyable<T>::value`

```cpp
struct D { int x; D(int v) : x(v) {} };  // 自定义构造，但默认拷贝 = trivial → trivially copyable
struct E { int x; E(const E&) {} };       // 自定义拷贝构造 → 不 trivially copyable
```

注意：`D` 不是 trivial（因为没默认构造），但是 trivially copyable。

### Trivially Relocatable（可平凡重定位）—— 关键概念

这是 **P1144 提案**的概念，**目前不是 C++ 标准**，但被 Folly、EASTL、Abseil、ImGui、Boost 等广泛使用。

**定义（直觉版）**：

> 一个对象是 trivially relocatable，如果"用 `memcpy` 把它的字节拷到新位置 + 把原位置当作未初始化"等价于"在新位置移动构造一个对象 + 在原位置析构掉旧对象"。

**用代码表达**：

```cpp
T* src = ...;
T* dst = ...;

// 操作 A：标准的"重定位"
new (dst) T(std::move(*src));   // 移动构造到 dst
src->~T();                       // 析构 src

// 操作 B：trivially relocatable 的快捷写法
memcpy(dst, src, sizeof(T));    // 字节拷贝
// 不调 src 的析构，src 现在被视为"未初始化"
```

**如果 `T` 是 trivially relocatable**，操作 A 和 B **行为等价**。

### 哪些类型是 Trivially Relocatable？

**一定是**：
- 所有 trivially copyable 类型（包括 `int`、`float`、原始指针、`ImVec2`、`ImDrawCmd`、`ImGuiInputEvent`...）。
- 大多数"持有数据但不持有句柄"的结构体。

**通常是（但 P1144 之前需要程序员判断）**：
- `std::vector<T>`：内部就是 `T* data; size_t size; size_t capacity;` 三个值，重定位等于移动这三个值。
- `std::string`（**不带** SSO 或 SSO 实现得当时）：内部是 ptr + size + capacity。
- `std::unique_ptr<T>`：就是个指针。
- 有 `Buf`/`Size` 字段的"自管理小对象池"（例如 ImGui 的 `ImGuiTabItem`）。

**绝对不是**：
- 含**自指针**的类型——节点指向自己内部的成员。

```cpp
struct BadNode {
    int data;
    BadNode* self;          // 指向自己
    BadNode() : self(this) {}
};
// 如果 memcpy 一个 BadNode 到新地址，新对象的 self 还指着旧地址 → 悬挂指针
```

- 含**侵入式链表节点指针**的类型，且其他节点指向它的内部。
- `std::list<T>` 的某些实现：节点内部互相指向。
- `std::function`（小对象优化时存的 lambda 可能含 self 引用）。

### 为什么"trivially copyable"还不够 ImGui 使用？

回到 `ImVector::push_back`：

```cpp
inline void push_back(const T& v) {
    if (Size == Capacity) reserve(_grow_capacity(Size + 1));
    memcpy(&Data[Size], &v, sizeof(v));
    Size++;
}
```

如果 `T = ImGuiTabItem`（一个有用户定义构造函数的结构体），是不是 trivially copyable？

让我们假设 `ImGuiTabItem` 有：

```cpp
struct ImGuiTabItem {
    ImGuiID ID;
    int     LastFrameVisible;
    float   Offset;
    // ...
    ImGuiTabItem() { memset(this, 0, sizeof(*this)); }   // 用户定义构造
};
```

这个类型：
- 有用户定义构造 → **不是** trivial
- 但拷贝构造、拷贝赋值都没定义（隐式 = trivial）→ **是** trivially copyable
- 没有 vtable、没有继承复杂关系 → **是** standard layout
- 没有自指针、没有 RAII 句柄 → **是** trivially relocatable

ImGui 需要的最低条件是 **trivially copyable**——`memcpy` 已经合法。`reserve` 里把整个数组 `memcpy` 到新地址，**对 trivially copyable 类型都是合法**。

但 **ImGui 还假设了一个更强的条件**：所有放进 `ImVector` 的类型都是 **trivially relocatable**。这个假设在 `ImVector::erase` 里体现：

```cpp
// imgui.h:2258
inline T* erase(const T* it) {
    IM_ASSERT(it >= Data && it < Data + Size);
    const ptrdiff_t off = it - Data;
    memmove(Data + off, Data + off + 1, ((size_t)Size - (size_t)off - 1) * sizeof(T));
    Size--;
    return Data + off;
}
```

`memmove` 把后面的元素**整体往前挪 1 格**——这是"重定位"操作。如果 `T` 不是 trivially relocatable（比如含自指针），这段代码会破坏对象的不变量。

### `ImVector` 注释的官方说法

```cpp
// imgui.h:2202-2203
// - Important: our implementation does NOT call C++ constructors/destructors,
//   we treat everything as raw data!
// - This is intentional but be extra mindful of that.
//   Do NOT use this class as a std::vector replacement in your own code!
```

**翻译**：

- "我们把所有东西当原始数据处理"= 假设 trivially relocatable。
- "不要把 ImVector 当 std::vector 替代品" = 因为它有这个隐含假设，普通 C++ 类型可能不满足。

## 0.3.4 `malloc / realloc / free` 的契约

C 的内存分配三件套，也是 ImGui 的底层。

### `malloc(size_t n)`

返回一块至少 `n` 字节的内存，地址对齐到 `max_align_t`（通常 8 或 16 字节，足以放任何标量类型）。

**契约**：
- 内存内容**未定义**（可能是任何垃圾数据）。
- 失败返回 `NULL`。
- `n == 0` 行为实现定义（可能返回 NULL，可能返回一个唯一非 NULL 指针）。

### `free(void* p)`

释放 `malloc` 返回的指针。

**契约**：
- `p == NULL` 是合法的（什么都不做）。
- `p` 必须是 `malloc` / `calloc` / `realloc` 返回的，不能是 `malloc` 返回值再 +1 的指针。
- **不能 double free**——UB。

### `realloc(void* p, size_t new_n)`

调整 `p` 指向的内存块大小。

**契约**：
- 如果原内存块够大，**可能原地扩展**（返回同一个 `p`）。
- 如果不够大，分配新块、拷贝旧内容到新块、free 旧块、返回新块地址。
- `p == NULL` 等价于 `malloc(new_n)`。
- `new_n == 0` 行为实现定义。

### ImGui 不用 `realloc`，为什么？

打开 `imgui.h:2251`，看 `ImVector::reserve`：

```cpp
inline void reserve(int new_capacity) {
    if (new_capacity <= Capacity) return;
    T* new_data = (T*)IM_ALLOC((size_t)new_capacity * sizeof(T));
    if (Data) {
        memcpy(new_data, Data, (size_t)Size * sizeof(T));
        IM_FREE(Data);
    }
    Data = new_data;
    Capacity = new_capacity;
}
```

**ImGui 选择"`malloc` 新块 + `memcpy` + `free` 旧块"，而不是 `realloc`**。原因有几条：

1. **`realloc` 的"原地扩展"概率不可控**：现代分配器（jemalloc / mimalloc / Windows 堆）的"原地扩展"成功率大约 30~70%。即使原地扩展，拷贝是分配器决定的，对于 trivially relocatable 类型反而绕过了 ImGui 的可控逻辑。
2. **`realloc` 失败时要释放原块**：`realloc` 失败返回 NULL，但**原块仍然有效**，需要你处理。这给错误处理增加复杂度——而 ImGui 决定不处理分配失败（见第 0.2 章）。
3. **`IM_ALLOC` 的语义比 `realloc` 更通用**：用户可以把 `IM_ALLOC` 接到自己的内存池，这种内存池可能根本不实现 `realloc`。
4. **`memcpy + free` 比 `realloc` 更"局部"**：你能在 `IM_ALLOC` 失败时立刻 IM_ASSERT，定位精确。`realloc` 失败时调用栈更深、定位难。

代价是放弃了"原地扩展"的潜在性能。但 ImGui 的 `_grow_capacity` 用 1.5× 增长策略：

```cpp
// imgui.h:2247
inline int _grow_capacity(int sz) const {
    int new_capacity = Capacity ? (Capacity + Capacity / 2) : 8;
    return new_capacity > sz ? new_capacity : sz;
}
```

1.5× 增长意味着平均下来 `push_back` 是 **O(1) 摊销**，扩容次数对数级。即使每次扩容都 memcpy，总成本也只是常数倍的"理想"realloc。

## 0.3.5 placement new 与显式析构

C++ 把"内存分配"和"对象构造"分成了两步：

```cpp
T* p = new T(args);    // 等价于：
T* p = (T*)operator new(sizeof(T));   // 步骤 1：分配内存
new (p) T(args);                       // 步骤 2：在已分配内存上构造对象
```

第二步的 `new (p) T(args)` 就是 **placement new**——它**不分配内存**，只在指定地址上调用构造函数。

对应地，析构和释放也是两步：

```cpp
delete p;              // 等价于：
p->~T();                       // 步骤 1：调用析构函数
operator delete(p);            // 步骤 2：释放内存
```

### 为什么需要分两步？

**对象池场景**：你预分配了 100 个对象大小的内存，要"按需用其中几个"。

```cpp
char buffer[sizeof(T) * 100];
T* obj = new (buffer + 5 * sizeof(T)) T(args);   // 在第 5 个槽位构造
// ... 用 obj ...
obj->~T();   // 析构，但 buffer 不释放
```

ImGui 的 `ImPool` 就是这个模式（下面会展开）。

### `IM_PLACEMENT_NEW` 的实现

回到第 0.2 章引用过的代码：

```cpp
// imgui.h:2186-2191
struct ImNewWrapper {};
inline void* operator new(size_t, ImNewWrapper, void* ptr) { return ptr; }
inline void  operator delete(void*, ImNewWrapper, void*)   {}
#define IM_ALLOC(_SIZE)                     ImGui::MemAlloc(_SIZE)
#define IM_FREE(_PTR)                       ImGui::MemFree(_PTR)
#define IM_PLACEMENT_NEW(_PTR)              new(ImNewWrapper(), _PTR)
#define IM_NEW(_TYPE)                       new(ImNewWrapper(), ImGui::MemAlloc(sizeof(_TYPE))) _TYPE
template<typename T> void IM_DELETE(T* p)   { if (p) { p->~T(); ImGui::MemFree(p); } }
```

**逐行解释**：

#### `struct ImNewWrapper {};`

一个空标签类，**唯一目的是给重载的 `operator new` 当区分用的参数**。

#### `inline void* operator new(size_t, ImNewWrapper, void* ptr) { return ptr; }`

这是一个**重载**的 `operator new`。签名：
- 参数 1：`size_t`（标准 placement new 必须有）
- 参数 2：`ImNewWrapper`（ImGui 自定义的标签）
- 参数 3：`void* ptr`（要构造的目标地址）
- 返回：`void*`（构造的目标地址，原样返回）

**关键**：这个 `operator new` 不分配任何内存，只是把 `ptr` 原样返回。

#### `IM_PLACEMENT_NEW(_PTR)              new(ImNewWrapper(), _PTR)`

展开后：`new(ImNewWrapper(), _PTR) T(args)` —— 这是 placement new 表达式：

- 编译器看到 `new(args1, args2, ...) T(constructor_args)`，会：
  1. 调用 `operator new(sizeof(T), args1, args2, ...)` 拿地址。
  2. 在该地址调用 `T` 的构造函数。

- 这里 `args1 = ImNewWrapper()`、`args2 = _PTR`，匹配上面重载的 `operator new(size_t, ImNewWrapper, void*)`，返回 `_PTR`。
- 然后在 `_PTR` 上构造 `T`。

#### 为什么不用标准 `operator new(size_t, void*)`？

标准库的 `<new>` 头里定义了：

```cpp
inline void* operator new(size_t, void* p) noexcept { return p; }
```

但 ImGui 想避免 include `<new>`（因为某些禁用异常的平台上 `<new>` 会拉进 `std::bad_alloc`）。**自己定义一个带 `ImNewWrapper` 的版本** = 不需要 include `<new>` 就能用 placement new。

这是**极致的依赖最小化**思维。

#### `IM_NEW(_TYPE)                       new(ImNewWrapper(), ImGui::MemAlloc(sizeof(_TYPE))) _TYPE`

展开：`new(ImNewWrapper(), ImGui::MemAlloc(sizeof(_TYPE))) _TYPE` 

- 调用 `MemAlloc` 拿到一块内存。
- 用 `IM_PLACEMENT_NEW` 在这块内存上构造 `_TYPE`。

完整使用方式：

```cpp
ImGuiWindow* w = IM_NEW(ImGuiWindow)("MyWindow");   // 等同于 new ImGuiWindow("MyWindow")
                                                    // 但走 ImGui::MemAlloc，可被替换的分配器
```

#### `IM_DELETE` 模板函数

```cpp
template<typename T> void IM_DELETE(T* p) {
    if (p) {
        p->~T();              // 调用析构
        ImGui::MemFree(p);    // 释放内存
    }
}
```

模板**依赖 `T` 的类型信息**。这是为什么 `IM_DELETE` 是函数模板而不是宏——宏看不到类型。

## 0.3.6 ImGui 内存四件套的接力赛

我们把 ImGui 的内存分配链路画成图：

```
你的代码（或 ImGui 内部）
        │
        │  IM_NEW(T) / IM_PLACEMENT_NEW / IM_ALLOC / IM_DELETE / IM_FREE
        ▼
┌──────────────────────────────────────────┐
│  imgui.h 的宏（编译期展开）                  │
└──────────────────────────────────────────┘
        │
        │  ImGui::MemAlloc / MemFree
        ▼
┌──────────────────────────────────────────┐
│  imgui.cpp:CONTEXT AND MEMORY ALLOCATORS  │
│  调用全局函数指针：                          │
│    GImAllocatorAllocFunc                  │
│    GImAllocatorFreeFunc                   │
└──────────────────────────────────────────┘
        │
        │  默认指向 MallocWrapper / FreeWrapper
        │  （或用户用 SetAllocatorFunctions 替换）
        ▼
┌──────────────────────────────────────────┐
│  最终：malloc / free / 用户内存池           │
└──────────────────────────────────────────┘
```

让我们逐层展开。

### 第 1 层：四个宏 + 一个模板

```cpp
// imgui.h:2189-2193
#define IM_ALLOC(_SIZE)                     ImGui::MemAlloc(_SIZE)
#define IM_FREE(_PTR)                       ImGui::MemFree(_PTR)
#define IM_PLACEMENT_NEW(_PTR)              new(ImNewWrapper(), _PTR)
#define IM_NEW(_TYPE)                       new(ImNewWrapper(), ImGui::MemAlloc(sizeof(_TYPE))) _TYPE
template<typename T> void IM_DELETE(T* p)   { if (p) { p->~T(); ImGui::MemFree(p); } }
```

**用法对照表**：

| 你想做什么 | 宏 | 等价标准 C++ |
|---|---|---|
| 分配字节 | `IM_ALLOC(N)` | `malloc(N)` |
| 释放字节 | `IM_FREE(p)` | `free(p)` |
| 在已有内存上构造对象 | `IM_PLACEMENT_NEW(p) T(args)` | `new (p) T(args)` |
| 分配 + 构造 | `IM_NEW(T)(args)` | `new T(args)` |
| 析构 + 释放 | `IM_DELETE(p)` | `delete p` |

### 第 2 层：`ImGui::MemAlloc / MemFree`

ImGui 暴露给用户的对外 API：

```cpp
// imgui.cpp 中（在 [SECTION] CONTEXT AND MEMORY ALLOCATORS 之后）
void* ImGui::MemAlloc(size_t size) {
    void* ptr = (*GImAllocatorAllocFunc)(size, GImAllocatorUserData);
#ifndef IMGUI_DISABLE_DEBUG_TOOLS
    if (ImGuiContext* ctx = GImGui)
        DebugAllocHook(&ctx->DebugAllocInfo, ctx->FrameCount, ptr, size);
#endif
    return ptr;
}

void ImGui::MemFree(void* ptr) {
#ifndef IMGUI_DISABLE_DEBUG_TOOLS
    if (ptr != NULL)
        if (ImGuiContext* ctx = GImGui)
            DebugAllocHook(&ctx->DebugAllocInfo, ctx->FrameCount, ptr, (size_t)-1);
#endif
    (*GImAllocatorFreeFunc)(ptr, GImAllocatorUserData);
}
```

**关键功能**：

1. **调用全局函数指针**：转发到用户配置的分配器。
2. **DebugAllocHook**：记录每帧的分配/释放，用于 Metrics 窗口的内存视图。

### 第 3 层：分配器函数指针

```cpp
// imgui.cpp:1444-1453
#ifndef IMGUI_DISABLE_DEFAULT_ALLOCATORS
static void* MallocWrapper(size_t size, void* user_data)    { IM_UNUSED(user_data); return malloc(size); }
static void  FreeWrapper(void* ptr, void* user_data)        { IM_UNUSED(user_data); free(ptr); }
#else
static void* MallocWrapper(size_t size, void* user_data)    { IM_UNUSED(user_data); IM_UNUSED(size); IM_ASSERT(0); return NULL; }
static void  FreeWrapper(void* ptr, void* user_data)        { IM_UNUSED(user_data); IM_UNUSED(ptr); IM_ASSERT(0); }
#endif

static ImGuiMemAllocFunc    GImAllocatorAllocFunc = MallocWrapper;
static ImGuiMemFreeFunc     GImAllocatorFreeFunc = FreeWrapper;
static void*                GImAllocatorUserData = NULL;
```

**几个细节**：

1. **`IMGUI_DISABLE_DEFAULT_ALLOCATORS` 模式**：把 `MallocWrapper` 改成 `IM_ASSERT(0)`——**强制**用户必须 `SetAllocatorFunctions`，否则一分配就崩。

2. **三个 static 变量是单例**：整个进程只有一组分配器。这就是为什么 DLL 模式下需要在每个 DLL 里调用 `SetAllocatorFunctions`——每个 DLL 的 `imgui.cpp` 都有自己的这三个 static。

3. **`GImAllocatorUserData`**：让用户分配器函数能拿到上下文（比如指向引擎 MemoryManager 的指针）。

### 第 4 层：`SetAllocatorFunctions`

```cpp
// imgui.cpp 中
void ImGui::SetAllocatorFunctions(ImGuiMemAllocFunc alloc_func, ImGuiMemFreeFunc free_func, void* user_data) {
    GImAllocatorAllocFunc = alloc_func;
    GImAllocatorFreeFunc = free_func;
    GImAllocatorUserData = user_data;
}
```

**集成到 Hazel 引擎的样板**：

```cpp
// 你的引擎初始化代码
static void* HazelImGuiAlloc(size_t size, void* user_data) {
    Hazel::MemoryManager* mgr = (Hazel::MemoryManager*)user_data;
    return mgr->Allocate(size, "ImGui");
}
static void HazelImGuiFree(void* ptr, void* user_data) {
    Hazel::MemoryManager* mgr = (Hazel::MemoryManager*)user_data;
    mgr->Free(ptr);
}

void ImGuiLayer::OnAttach() {
    // ⚠ 必须在 CreateContext 之前
    ImGui::SetAllocatorFunctions(HazelImGuiAlloc, HazelImGuiFree, &m_MemoryManager);
    ImGui::CreateContext();
    // ... 后续初始化
}
```

**关键时序**：`SetAllocatorFunctions` 必须在 `CreateContext` 之前。否则 `CreateContext` 会用默认 `malloc` 分配 Context，而后面的代码用你的分配器释放——分配器不匹配 → 崩溃。

## 0.3.7 实战：`ImPool` 怎么用 placement new + 显式析构实现槽位复用

打开 `imgui_internal.h:758-785`，这是 `ImPool` 的完整源码。我们逐段拆。

```cpp
template<typename T>
struct ImPool {
    ImVector<T>     Buf;        // Contiguous data
    ImGuiStorage    Map;        // ID->Index
    ImPoolIdx       FreeIdx;    // Next free idx to use
    ImPoolIdx       AliveCount; // Number of active/alive items (for display purpose)

    ImPool()    { FreeIdx = AliveCount = 0; }
    ~ImPool()   { Clear(); }
```

**字段**：

- `Buf`：实际存放对象的数组。
- `Map`：一个 ID→index 的哈希映射（`ImGuiStorage` 是 ImGui 自己的"有序键值对"存储）。
- `FreeIdx`：空闲槽位的"链表头"。
- `AliveCount`：活对象数量（仅显示用）。

```cpp
    T*  Add() {
        int idx = FreeIdx;
        if (idx == Buf.Size) {
            Buf.resize(Buf.Size + 1);
            FreeIdx++;
        } else {
            FreeIdx = *(int*)&Buf[idx];   // ← 关键：从槽位里读出"下一个空闲槽位"
        }
        IM_PLACEMENT_NEW(&Buf[idx]) T();  // ← 在槽位上构造对象
        AliveCount++;
        return &Buf[idx];
    }
```

**精彩部分**：`*(int*)&Buf[idx]` 把一个**已经被析构的对象槽位**当作 `int` 来读，从中取出"链表中下一个空闲槽位的索引"。这是经典的**侵入式空闲链表**——空闲槽位**就是**下一个空闲槽位的指针/索引存储位置。

完整流程：

```
初始: Buf=[], FreeIdx=0, Map={}

Add() #1:
  idx=0, Buf.resize(1) → Buf=[uninit], FreeIdx=1
  IM_PLACEMENT_NEW(&Buf[0]) T()
  → Buf=[T0], FreeIdx=1, AliveCount=1

Add() #2:
  idx=1, Buf.resize(2) → Buf=[T0, uninit], FreeIdx=2
  IM_PLACEMENT_NEW(&Buf[1]) T()
  → Buf=[T0, T1], FreeIdx=2, AliveCount=2

Remove(idx=0):
  Buf[0].~T()                    // 析构
  *(int*)&Buf[0] = FreeIdx (2)   // 把"前一个 FreeIdx"写到槽 0
  FreeIdx = 0                    // 槽 0 加入空闲链表头
  → Buf=[空闲链表节点(2), T1], FreeIdx=0, AliveCount=1

Add() #3:
  idx=FreeIdx=0
  FreeIdx = *(int*)&Buf[0] = 2    // 顺着链表走
  IM_PLACEMENT_NEW(&Buf[0]) T()
  → Buf=[T2, T1], FreeIdx=2, AliveCount=2
```

**这就是 placement new + 显式析构的最佳实例**：

- 槽位的内存**永远不释放**（直到整个 Pool 销毁）。
- 槽位的对象生命周期**显式由 placement new 和 `~T()` 控制**。
- 空闲槽位的"未初始化字节"被**复用**作为链表节点。

```cpp
    void Remove(ImGuiID key, ImPoolIdx idx) {
        Buf[idx].~T();                      // 析构对象
        *(int*)&Buf[idx] = FreeIdx;         // 把这个槽位变成链表节点
        FreeIdx = idx;                       // 加入空闲链表头
        Map.SetInt(key, -1);                 // 从 Map 中移除
        AliveCount--;
    }
```

```cpp
    void Clear() {
        for (int n = 0; n < Map.Data.Size; n++) {
            int idx = Map.Data[n].val_i;
            if (idx != -1)
                Buf[idx].~T();              // 显式析构所有活对象
        }
        Map.Clear();
        Buf.clear();                         // ImVector 释放内存
        FreeIdx = AliveCount = 0;
    }
```

注意 `Buf.clear()` —— 上一节我们提到 `ImVector::clear()` **不调用析构**。`ImPool::Clear()` 因此**自己**遍历活对象一一析构。

### 这个设计要求 `T` 满足什么？

- **必须可默认构造**（`T()` 用于 placement new）。
- **可被析构**（`~T()` 必须可调用）。
- **大小至少 ≥ `sizeof(int)`**（否则 `*(int*)&Buf[idx]` 越界）。这通常自然满足，因为 `ImPool` 用于存放 `ImGuiTabBar` / `ImGuiTable` 等结构体，都远大于 4 字节。
- **相对**地，`T` 不一定要 trivially copyable / relocatable——`ImPool` 不会 `memcpy` 对象，只 `IM_PLACEMENT_NEW + ~T()`。

但是注意：`ImPool` 内部用 `ImVector<T> Buf`，**`ImVector` 的扩容会 memcpy 整个数组**。这就要求 `T` **还是必须 trivially relocatable**——否则 `Buf.resize()` 触发扩容时，所有"活对象"的字节会被 memcpy，自指针类型会破。

**结论**：`ImPool<T>` 要求 `T` 满足：默认可构造 + 可析构 + trivially relocatable。

## 0.3.8 内存分析与调试钩子

ImGui 提供了内置的内存追踪机制。

### `g.DebugMemAllocCount` / `g.DebugMemFreeCount`

`ImGuiContext` 里有这两个字段（注释见 `imgui.cpp:692`）：

```cpp
struct ImGuiContext {
    // ...
    int DebugMemAllocCount;
    int DebugMemFreeCount;
    // ...
};
```

每次 `ImGui::MemAlloc` / `MemFree` 调用都会把对应计数 +1。在 Metrics 窗里能看到：

```
Tools → Memory → Allocations: NNN, Frees: NNN, Active: NNN
```

**用法**：在你的引擎集成时，每帧打印一次（仅 Debug）：

```cpp
ImGuiContext& g = *ImGui::GetCurrentContext();
HZ_CORE_TRACE("ImGui mem: alloc={} free={} active={}",
    g.DebugMemAllocCount,
    g.DebugMemFreeCount,
    g.DebugMemAllocCount - g.DebugMemFreeCount);
```

**判定健康的标准**：

- 启动后前几帧 `Active` 会涨（容器增长、字体加载）。
- 稳定后 `Active` 应**几乎不变**（除非新窗口打开）。
- 如果稳定后 `Active` 持续上涨 → 泄漏。

### 自定义分配器做更深层追踪

```cpp
struct ImGuiAllocStat {
    std::atomic<size_t> total_bytes{0};
    std::atomic<size_t> peak_bytes{0};
    std::atomic<size_t> alloc_count{0};
};
ImGuiAllocStat g_imgui_alloc_stat;

void* MyImGuiAlloc(size_t size, void* user_data) {
    void* p = malloc(size + sizeof(size_t));  // 多分配 8 字节存大小
    *(size_t*)p = size;
    g_imgui_alloc_stat.total_bytes += size;
    g_imgui_alloc_stat.alloc_count++;
    size_t peak = g_imgui_alloc_stat.peak_bytes.load();
    while (g_imgui_alloc_stat.total_bytes > peak)
        g_imgui_alloc_stat.peak_bytes.compare_exchange_weak(peak, g_imgui_alloc_stat.total_bytes);
    return (char*)p + sizeof(size_t);
}

void MyImGuiFree(void* ptr, void* user_data) {
    if (!ptr) return;
    void* real = (char*)ptr - sizeof(size_t);
    size_t size = *(size_t*)real;
    g_imgui_alloc_stat.total_bytes -= size;
    free(real);
}
```

通过这种 wrapper，你能拿到精确到字节的 ImGui 内存峰值。

**注意**：上面用了 `std::atomic`——多线程下分配器**可能**被并发调用（如果你启用 N Context N 线程模式）。单线程情况下用普通 size_t 即可。

## 0.3.9 对齐分配：ImGui 为什么不需要

某些场合需要"分配对齐到 16 字节的内存"——比如 SIMD 类型、GPU 上传缓冲。标准 C++ 提供：

```cpp
void* p = std::aligned_alloc(16, 1024);   // C++17
void* p = ::operator new(1024, std::align_val_t{16});   // C++17
void* p = _aligned_malloc(1024, 16);      // MSVC
posix_memalign(&p, 16, 1024);             // POSIX
```

ImGui **不用**对齐分配，因为：

1. `malloc` 已经保证 `max_align_t` 对齐（通常 8 或 16，足够大多数场景）。
2. ImGui 不存放 SIMD 类型（`__m128` / `__m256`）。`ImVec2` / `ImVec4` 都是普通 float 数组，4 字节对齐够。
3. ImDrawVert 上传到 GPU 时，stride = 20 字节本身就不是 16 对齐——而 GPU 不要求 VB 内部元素对齐到 16。

**如果你魔改 ImGui 引入 SIMD**：要在自定义 `IM_ALLOC` 实现里使用对齐分配，并保证下游所有 cast 都尊重对齐。

## 0.3.10 对象生命周期 & C++ 标准的"灰区"

C++ 标准 [basic.life] 章节定义对象生命周期：

> 一个对象的生命周期开始于：
> - 它的存储被分配，**且**
> - 它的初始化（如果有）完成。
>
> 一个对象的生命周期结束于：
> - 析构函数被调用（对于有非平凡析构的类型），**或**
> - 它占用的存储被释放/重用。

**那么"用 memcpy 把一个对象的字节拷贝到另一处"是什么语义？**

C++17 引入了 `std::launder`（[ptr.launder]）来处理这种情况。但简单用法：

```cpp
T src;
char buffer[sizeof(T)];
memcpy(buffer, &src, sizeof(T));
T* dst = std::launder(reinterpret_cast<T*>(buffer));   // C++17 必须 launder
// 现在 *dst 是合法的对象（如果 T 是 trivially copyable）
```

**ImGui 不用 `std::launder`**——它写的代码在 C++17 严格规则下处于灰区。但实践中：

- 主流编译器（GCC / Clang / MSVC）不会以"标准灰区"为由生成错误代码。
- 这是 P1144 提案想标准化的场景之一。

**如果你的 ImGui fork 要在某个严格标准检查器下编译**，可能需要自己加 launder。但 99% 的项目可以无视这个细节。

## 0.3.11 一份"能否放进 ImVector"的判定 checklist

最后给你一份决策表。**当你写自定义结构体想放进 `ImVector` 时**，逐条检查：

| 条件 | 标准类型例子（OK） | 反面例子（NG） |
|---|---|---|
| ✅ 没有自指针（`this->ptr = &this->member`） | `ImVec2`、`ImDrawCmd`、原始指针 | 含侵入式链表节点 + 其他节点引用它的内部 |
| ✅ 没有持有 RAII 句柄（OS handle / 文件句柄 / 网络连接） | `ImGuiTabItem`、`ImGuiInputEvent` | 含 `std::unique_lock`、含 `std::ifstream` |
| ✅ 没有 `std::shared_ptr` / `std::weak_ptr` 控制块（除非 SBO 关闭） | 裸指针 + 手工管理生命周期 | `std::shared_ptr<X>` 字段 |
| ✅ 拷贝构造 = 默认 / `= default` / 不存在 | `ImGuiTabBar` | 自定义拷贝构造做"深拷贝" |
| ✅ 析构函数 = 默认 / `= default` / 不存在 | `ImDrawVert` | 自定义析构（除非真的没副作用） |
| ✅ 不依赖于地址稳定（不被外部指针指着） | 一般业务结构 | 被某个 `std::map<int, T*>` 持有指针 |
| ✅ 大小 ≥ `sizeof(int)`（如果用于 `ImPool`） | 几乎所有 | 一个 `bool`-only 结构（罕见） |

如果**全部满足**：放心用 `ImVector<T>`。

如果**任一不满足**：考虑：
- 用 `ImStableVector<T, B>`（块状分配，不重定位）。
- 用 `T*` 指针 + 手工管理生命周期。
- 用 STL 容器（如果你的子系统不要求和 ImGui 内部交互）。

## 0.3.12 本章小结

让我们用一句话总结每一节：

| 节 | 一句话总结 |
|---|---|
| 0.3.1 | 进程地址空间分栈/堆/数据/常量四段，栈分配零成本，堆分配代价不可忽略。 |
| 0.3.2 | 对齐是性能（cache）和正确性（ARM 异常）的需求；结构体大小受最大成员对齐决定。 |
| 0.3.3 | Trivially Copyable < Trivially Relocatable（实践概念）；ImGui 假设元素后者满足。 |
| 0.3.4 | ImGui 用 malloc + memcpy + free 替代 realloc，理由是可控性 + 可替换分配器。 |
| 0.3.5 | placement new 在已分配内存上构造，显式析构调 `~T()`，是对象池的基础。 |
| 0.3.6 | ImGui 内存分配 4 层：宏 → MemAlloc/Free → 函数指针 → malloc/用户实现。 |
| 0.3.7 | `ImPool::Add()` 用空闲槽位字节存链表节点，placement new 复用槽位。 |
| 0.3.8 | `g.DebugMemAllocCount/FreeCount` 是免费的内存追踪起点。 |
| 0.3.9 | ImGui 不用对齐分配，因为不存 SIMD 类型，普通 malloc 对齐够用。 |
| 0.3.10 | "memcpy 一个非平凡对象"在 C++ 标准灰区，工业实践广泛接受，主流编译器都 OK。 |
| 0.3.11 | 一份"能否放进 ImVector"的判定 checklist（7 条）。 |

**最关键的两句话**（请刻在脑子里）：

1. **ImGui 的所有容器假设元素是 Trivially Relocatable**——这一假设让 `memcpy` 替代了拷贝构造，让 `memmove` 替代了"重定位"，让运行时几乎零分配。
2. **ImGui 的所有内存分配走单一全局函数指针**——这意味着进程级单一分配器、DLL 边界需手工同步、可被任意替换。
