## 6.2.0 三种主流引擎线程模型回顾

### 模型 A：单线程

```
主线程：
   while (running) {
      poll input
      update game logic
      render scene
      update + render ImGui
      swap chain
   }
```

——简单。Hazel 默认就是这个模型。瓶颈：CPU 单核利用率。

### 模型 B：双线程（Game / Render）

```
游戏线程（主）：               渲染线程：
   while (running) {              while (running) {
      poll input                     等待 game 线程的命令缓冲
      update game logic              提交命令到 GPU
      生成命令缓冲                    swap chain
      传给渲染线程
      等待上一帧完成
   }
```

——典型 AAA 引擎（虚幻 / Unity）的骨架。游戏线程 / 渲染线程**滞后一帧**。瓶颈：双线程同步。

### 模型 C：Job System（N 线程）

```
Job Scheduler 把任务分配给 N 个工作线程：
   - 物理 update job
   - AI tick job
   - 动画蒙皮 job
   - 粒子模拟 job
   - 各 layer 的 OnUpdate
   - ...
```

——所有可并行任务抢占式分配。游戏 / 渲染 / 物理 / 资源全在 N 个线程间动态调度。

每种模型下 ImGui 的"落位"不同。

## 6.2.1 方案 1：UI 完全在主线程（推荐起点）

**这是 95% 引擎的合理选择**。即使是模型 B / C，也通常**只有**主线程构建 ImGui UI——其他线程不参与。

### 代码骨架

```cpp
void Application::Run() {
    while (m_Running) {
        // ① 主线程：OS 输入 + 游戏逻辑
        m_Window->OnUpdate();   // 同步分发输入回调
        for (Layer* layer : m_LayerStack)
            layer->OnUpdate(ts);
        
        // ② 主线程：ImGui 帧
        m_ImGuiLayer->Begin();
        for (Layer* layer : m_LayerStack)
            layer->OnImGuiRender();
        m_ImGuiLayer->End();   // 内部 Render + RenderDrawData
        
        // ③ 渲染线程独立提交（如果有）
        // 但 ImGui 的 RenderDrawData 通常已经在 End 内同步完成
        
        // ④ swap chain
        m_Window->SwapBuffers();
    }
}
```

### 关键约束

- 所有 `ImGui::XXX` 调用在主线程。
- 输入回调要么直接在主线程触发（GLFW PollEvents），要么通过无锁队列汇集。
- 渲染线程**只**消费 `ImDrawData`——不调任何 ImGui API。

### 优点

- 简单——遵守 ImGui 的单线程模型，没有任何 race。
- 调试容易——所有交互都在一个线程的调用栈里。
- 性能足够——99% 的 UI 工作量被主线程消化得过。

### 何时不够

- 主线程**真的**忙到 fps 受限（罕见，UI 通常 <5 ms）。
- 主线程要做大量异步任务（资源加载、网络）——但这些应该 offload 到 worker 线程。

## 6.2.2 方案 2：UI 主线程 + 渲染线程消费 DrawData

**模型 B 引擎下的最佳实践**——主线程构建 UI，渲染线程提交 GPU 命令。

### 关键问题：ImDrawData 跨线程传递

```cpp
ImGui::Render();
ImDrawData* dd = ImGui::GetDrawData();
// 把 dd 传给渲染线程？

// ❌ 错误：dd 指向 viewport->DrawDataP
//    主线程下一帧 NewFrame 会让 dd->Valid = false 并清空内容
//    渲染线程读到无效数据
```

### 解法 1：双缓冲

```cpp
class ImGuiDataPool {
    ImDrawData* m_Buffers[2];   // 双缓冲
    int m_FrontIdx = 0;
    std::mutex m_Mutex;
public:
    void SubmitFromUI(ImDrawData* src) {
        std::lock_guard<std::mutex> lock(m_Mutex);
        // 克隆 ImDrawData 到 m_Buffers[m_FrontIdx ^ 1]
        CloneDrawData(src, m_Buffers[m_FrontIdx ^ 1]);
        m_FrontIdx ^= 1;
    }
    
    ImDrawData* GetForRendering() {
        std::lock_guard<std::mutex> lock(m_Mutex);
        return m_Buffers[m_FrontIdx];
    }
};

void CloneDrawData(ImDrawData* src, ImDrawData* dst) {
    dst->Valid = src->Valid;
    dst->CmdListsCount = src->CmdListsCount;
    dst->TotalIdxCount = src->TotalIdxCount;
    dst->TotalVtxCount = src->TotalVtxCount;
    dst->DisplayPos = src->DisplayPos;
    dst->DisplaySize = src->DisplaySize;
    dst->FramebufferScale = src->FramebufferScale;
    
    // 克隆每个 ImDrawList
    for (ImDrawList* old : dst->CmdLists) IM_DELETE(old);
    dst->CmdLists.resize(0);
    
    for (ImDrawList* dl : src->CmdLists) {
        ImDrawList* clone = dl->CloneOutput();   // ImGui 提供的 API
        dst->CmdLists.push_back(clone);
    }
}
```

主线程：

```cpp
ImGui::Render();
ImDrawData* dd = ImGui::GetDrawData();
g_ImGuiDataPool.SubmitFromUI(dd);
```

渲染线程：

```cpp
ImDrawData* dd_to_render = g_ImGuiDataPool.GetForRendering();
ImGuiBackend::RendererRenderDrawData(dd_to_render);
```

**双缓冲的妙处**：主线程在写 `m_Buffers[1]` 时，渲染线程读 `m_Buffers[0]`——互不冲突。

### 解法 2：ping-pong 同步（无双缓冲，单 buffer 但加同步）

```cpp
std::condition_variable cv;
std::mutex mtx;
bool ready = false;
ImDrawData* shared_dd = nullptr;

// 主线程：
ImGui::Render();
{
    std::lock_guard<std::mutex> lock(mtx);
    shared_dd = ImGui::GetDrawData();   // 注意这只是指针，不是 clone
    ready = true;
}
cv.notify_one();

{
    std::unique_lock<std::mutex> lock(mtx);
    cv.wait(lock, [&]() { return !ready; });   // 等待渲染线程消费完
}
ImGui::NewFrame();   // 现在可以下一帧

// 渲染线程：
{
    std::unique_lock<std::mutex> lock(mtx);
    cv.wait(lock, [&]() { return ready; });
}
ImGuiBackend::RendererRenderDrawData(shared_dd);
{
    std::lock_guard<std::mutex> lock(mtx);
    ready = false;
}
cv.notify_one();
```

**问题**：主线程必须等渲染线程完成——**没有真正并行**——和单线程一样慢。

**结论**：双缓冲是真正的并行。ping-pong 只是为了避免克隆。

### 性能比较

```
单线程：              主线程时间 = UI 构建 + RenderDrawData = 5ms + 2ms = 7ms

双缓冲（理想）：       主线程时间 = UI 构建 + Clone DrawData = 5ms + 0.5ms = 5.5ms
                     渲染线程时间 = RenderDrawData = 2ms
                     总并行 fps = max(5.5, 2) → 主线程瓶颈
                     
ping-pong：          相当于单线程
```

——双缓冲省 1.5 ms，对追求高帧率的应用有价值。但 Clone 也要 0.5ms。**只有当 UI 构建 + Render 加起来 > 16.6ms（60fps）时**才需要这个优化。

## 6.2.3 方案 3：N Context（多线程并行）

**最高级**——每个线程有自己的 Context，独立工作。适用：

- 自动化测试（`imgui_test_engine`）。
- 多窗口编辑器（每个窗口独立 ImGui 状态）。
- 远程协作工具（每个客户端独立 UI）。

### 代码骨架

```cpp
// imconfig.h
extern thread_local ImGuiContext* MyImGuiTLS;
#define GImGui MyImGuiTLS

// MyImGuiTLS.cpp
thread_local ImGuiContext* MyImGuiTLS = nullptr;
```

```cpp
void WorkerThread(int thread_id) {
    // 每个线程创建自己的 Context
    ImGuiContext* ctx = ImGui::CreateContext();
    ImGui::SetCurrentContext(ctx);   // 设置 thread_local
    
    // 共享字体图集（节省内存）
    if (g_shared_atlas)
        ctx->IO.Fonts = g_shared_atlas;
    
    // 该线程的工作循环
    while (running) {
        ImGui::NewFrame();
        // ... 该线程的 UI 工作 ...
        ImGui::Render();
        ImDrawData* dd = ImGui::GetDrawData();
        // ... 该线程独立渲染或汇集 ...
    }
    
    ImGui::DestroyContext(ctx);
}
```

### 字体共享

```cpp
ImFontAtlas* g_shared_atlas = nullptr;

void Initialize() {
    g_shared_atlas = new ImFontAtlas();
    g_shared_atlas->AddFontDefault();
    g_shared_atlas->Build();
}

void WorkerThread(int id) {
    ImGuiContext* ctx = ImGui::CreateContext(g_shared_atlas);   // 注意传 shared atlas
    // ...
}
```

——多个 Context 共享同一个 ImFontAtlas，节省 1-4 MB 内存（每个 atlas）。

### 注意事项

- **字体加载在主线程**：`g_shared_atlas->Build()` 必须在所有 worker Context 创建**之前**完成。1.92 的动态字体在 worker 内调用会破坏 race。
- **多 Context 不共享 ImGuiStorage / ImGuiWindow**——每个 Context 完全独立。
- **DLL 边界**：每个 DLL 的 thread_local 独立——加载 DLL 时每个线程进入 DLL 域要重新 SetCurrentContext。

## 6.2.4 资源线程的接入：异步加载贴图

实战场景：用户拖一张大贴图到 Asset Browser → 想立刻在 Inspector 看缩略图。

### 朴素同步加载（错的）

```cpp
// 主线程在 OnImGuiRender 内部：
if (need_load) {
    Texture2D* tex = Texture2D::LoadFromFile("big_image.png");   // ❌ 阻塞主线程几百毫秒
    ImGui::Image(tex->GetID(), ...);
}
```

——加载几百毫秒主线程冻结，用户体验差。

### 异步加载方案

```cpp
class AssetManager {
    struct PendingLoad {
        std::string path;
        std::function<void(Ref<Texture2D>)> on_loaded;
    };
    moodycamel::ConcurrentQueue<PendingLoad> m_PendingQueue;
    moodycamel::ConcurrentQueue<std::function<void()>> m_MainThreadCallbacks;
    
public:
    void AsyncLoad(const std::string& path, std::function<void(Ref<Texture2D>)> on_loaded) {
        m_PendingQueue.enqueue({path, on_loaded});
    }
    
    void OnMainThreadTick() {
        // 在主线程被调用，完成所有待处理的回调
        std::function<void()> cb;
        while (m_MainThreadCallbacks.try_dequeue(cb)) {
            cb();
        }
    }
    
    // 后台线程函数
    void WorkerLoop() {
        while (m_Running) {
            PendingLoad load;
            if (!m_PendingQueue.try_dequeue(load)) {
                std::this_thread::sleep_for(std::chrono::milliseconds(10));
                continue;
            }
            
            // 1. 加载文件 + 解码图像（CPU 密集，在 worker 线程）
            int w, h, ch;
            uint8_t* pixels = stbi_load(load.path.c_str(), &w, &h, &ch, 4);
            
            // 2. 把"创建 GPU 纹理"作为回调推到主线程
            //    （GPU 操作通常需要在 GL Context 所在的线程）
            m_MainThreadCallbacks.enqueue([=]() {
                Ref<Texture2D> tex = Texture2D::Create(w, h);
                tex->SetData(pixels, w * h * 4);
                stbi_image_free(pixels);
                load.on_loaded(tex);
            });
        }
    }
};
```

主线程：

```cpp
void EditorLayer::OnImGuiRender() {
    g_AssetManager.OnMainThreadTick();   // 处理 worker 完成的回调
    
    if (ImGui::Button("Load Image")) {
        g_AssetManager.AsyncLoad("big.png", [this](Ref<Texture2D> tex) {
            m_LoadedTexture = tex;   // 在主线程被调用
        });
    }
    
    if (m_LoadedTexture) {
        ImGui::Image(m_LoadedTexture->GetID(), ImVec2(256, 256));
    }
}
```

**关键**：加载在 worker 线程，但**创建 GPU 纹理 + 给 ImGui 用**在主线程——避免跨线程 GL Context / Vulkan 资源问题。

## 6.2.5 双缓冲资源（避免主线程等渲染线程）

**模型 B**（双线程引擎）下，渲染线程可能滞后主线程一帧——这意味着主线程改资源（例如改纹理像素）时，渲染线程**还在用上一帧的版本**。

```cpp
// 主线程：
m_Texture->SetData(new_pixels);   // 改纹理
// 渲染线程可能还在 glDrawElements 用旧纹理
```

GPU 资源（纹理 / buffer / shader）通常需要：

- 双缓冲（GPU 端 ping-pong）。
- 或者 staging buffer（先 upload 到 staging，下一帧 swap）。
- 或者 fence 同步（等渲染线程用完旧版本再 update）。

ImGui 自带的字体图集已经处理（`ImTextureStatus_WantUpdates` 机制——backend 在适当时机 update）。但**用户的纹理**需要你自己处理。

### 简单方案：让 ImGui 帮忙

让所有动态纹理走 ImGui 的 `ImTextureData` 系统：

```cpp
// 不直接用 GLuint
// 而是创建 ImTextureData：
ImTextureData* tex = IM_NEW(ImTextureData)();
tex->Status = ImTextureStatus_WantCreate;
tex->TexWidth = w;
tex->TexHeight = h;
tex->Pixels = new uint8_t[w*h*4];
memcpy(tex->Pixels, src, w*h*4);
ImGui::GetPlatformIO().Textures->push_back(tex);

// ImGui 内部 + backend 协同处理生命周期
ImGui::Image(ImTextureRef(tex), size);
```

**但这只适合 ImGui 显示用的纹理**——你的游戏渲染纹理仍然要自己管理。

## 6.2.6 常见死锁与陷阱清单

### 陷阱 1：在 OnImGuiRender 里持有渲染锁

```cpp
void EditorLayer::OnImGuiRender() {
    std::lock_guard<std::mutex> lock(m_Renderer->Mutex);   // ❌
    auto& meshes = m_Renderer->GetMeshes();
    
    for (auto& m : meshes) ImGui::Text("%s", m->Name.c_str());
}

// 渲染线程：
void RenderThread() {
    std::lock_guard<std::mutex> lock(m_Renderer->Mutex);   // 等主线程释放
    m_Renderer->Render();
}
```

主线程在 ImGui 内调用其他东西时也用了同一锁 → 死锁。**永远不要在 OnImGuiRender 内持有跨线程锁**。

修复：把数据**复制**到本地 vector，再渲染：

```cpp
void EditorLayer::OnUpdate(Timestep ts) {
    // 在 Update 里取数据快照
    {
        std::lock_guard<std::mutex> lock(m_Renderer->Mutex);
        m_MeshSnapshot = m_Renderer->GetMeshes();   // copy
    }
}

void EditorLayer::OnImGuiRender() {
    // 用快照渲染——不持锁
    for (auto& m : m_MeshSnapshot) ImGui::Text(...);
}
```

### 陷阱 2：在工作线程调 ImGui

```cpp
std::thread([]() {
    ImGui::Begin("Worker");   // ❌ 工作线程调 ImGui
}).detach();
```

——除非你设了 `thread_local GImGui` 并 `SetCurrentContext`，否则崩。

### 陷阱 3：跨帧持有 ImGuiWindow*

```cpp
ImGuiWindow* m_Cached = nullptr;

void Foo() {
    if (!m_Cached) m_Cached = ImGui::FindWindowByName("X");
    if (m_Cached->Active) { ... }   // ❌ 可能已被销毁
}
```

修复：每次重新查找，或用 ImGui 的 ID 加判断。

### 陷阱 4：RenderDrawData 与 EndFrame 同时执行

```cpp
// 渲染线程：
ImGuiBackend::RendererRenderDrawData(dd);   // 读 ImDrawList 的 IB/VB

// 主线程同时：
ImGui::EndFrame();   // 重置某些 DrawList 的内部 Splitter
```

**双缓冲的关键**：主线程必须**先**完成 `Render()` + 把 DrawData 克隆给渲染线程**才能** NewFrame 下一帧。否则主线程下一帧的 NewFrame 会改 DrawList 内容。

```cpp
// 错误：
ImGui::Render();
g_RenderQueue.Submit(ImGui::GetDrawData());   // 渲染线程异步处理
ImGui::NewFrame();   // ❌ 渲染线程还在用 DrawData

// 正确：
ImGui::Render();
ImDrawData* clone = CloneDrawData(ImGui::GetDrawData());   // 同步克隆
g_RenderQueue.Submit(clone);
ImGui::NewFrame();   // OK，clone 是独立副本
```

### 陷阱 5：Hot Reload 时悬挂 hook

DLL 卸载前未清除 ImGui hook → 下一帧 NewFrame 时调用悬挂函数 → 崩。详见第 2.3 章。

### 陷阱 6：Multi-Viewport 跨 GL Context

Multi-Viewport 给每个副 viewport 创建独立的 GL Context。callback 在副 viewport 渲染时被触发——此时**当前 GL Context 是该 viewport 的**，你的资源（shader / VBO 等）可能不可用。

修复：要么所有副 viewport 共享主 GL Context（`shared_ctx` 参数），要么每个 GL Context 独立创建资源。

### 陷阱 7：字体烘焙在错的线程

```cpp
// 主线程：
io.Fonts->Build();   // 烘焙原子操作

// 工作线程同时：
io.Fonts->AddFontFromFile(...);   // ❌ 修改 atlas
```

修复：所有字体加载 + Build **必须在主线程，且必须在 `NewFrame` 之前完成**。

### 陷阱 8：信号量 / 事件未配对

模型 B 中常用信号量同步主 / 渲染线程。如果某种异常路径（用户中途按 Esc 退出）让信号量未配对释放，会导致一方永远 wait。

修复：用 RAII 包装信号量，确保异常路径也释放。

### 陷阱 9：递归互斥量

```cpp
std::mutex mtx;

void A() {
    std::lock_guard lock(mtx);
    B();   // B 内部也想锁 mtx → 死锁（std::mutex 不支持递归）
}
void B() {
    std::lock_guard lock(mtx);
    // ...
}
```

修复：用 `std::recursive_mutex` 或重构代码避免递归锁。

### 陷阱 10：DropTarget 跨线程

```cpp
// 主线程的 ImGui::AcceptDragDropPayload 调用：
const ImGuiPayload* p = ImGui::AcceptDragDropPayload("FILE");
if (p) {
    // ❌ 直接在工作线程开 LoadFile
    std::thread([data = p->Data]() { LoadFile(data); }).detach();
    // p->Data 在 ImGui 帧结束时失效——工作线程可能读到悬挂数据
}
```

修复：复制 payload 数据到独立 buffer，再交给工作线程：

```cpp
if (p) {
    std::vector<char> safe_data((char*)p->Data, (char*)p->Data + p->DataSize);
    std::thread([data = std::move(safe_data)]() { LoadFromMemory(data); }).detach();
}
```

## 6.2.7 实战：Hazel 引擎升级到双线程

假设 Hazel 当前是单线程，想升级到模型 B（游戏 / 渲染分线程）：

### Step 1：分离 RenderCommand 与执行

把 `Hazel::RenderCommand::DrawIndexed` 等不是直接调 GL，而是**录制命令**到一个 buffer：

```cpp
class CommandBuffer {
    std::vector<RenderCommand> m_Commands;
public:
    void Record(RenderCommand cmd) { m_Commands.push_back(cmd); }
    void Execute() { for (auto& c : m_Commands) c.Apply(); }
};
```

### Step 2：双缓冲命令队列

```cpp
CommandBuffer m_CommandBuffers[2];
std::atomic<int> m_FrontIdx{0};

// 主线程提交：
m_CommandBuffers[m_FrontIdx ^ 1].Record(...);

// 渲染线程执行：
m_CommandBuffers[m_FrontIdx].Execute();

// 帧切换：
m_FrontIdx = m_FrontIdx ^ 1;
```

### Step 3：ImGui 配合

ImGui 的 `RenderDrawData` 也作为 RenderCommand 录制：

```cpp
// ImGuiLayer::End() 改为：
ImGui::Render();
ImDrawData* dd = ImGui::GetDrawData();
ImDrawData* clone = CloneDrawData(dd);
m_CommandBuffer->Record(RenderCommand::ImGuiRenderDrawData(clone));
```

——主线程**不**直接调 RenderDrawData，而是录制成命令。渲染线程从 buffer 取出 + 执行。

### Step 4：同步点

```cpp
void Application::Run() {
    while (m_Running) {
        // 等待渲染线程完成上一帧
        m_RenderThread->WaitForPreviousFrame();
        
        // 主线程：游戏逻辑 + ImGui + 录制命令到 m_FrontBuffer
        m_Window->OnUpdate();
        for (auto* l : m_LayerStack) l->OnUpdate(ts);
        m_ImGuiLayer->Begin();
        for (auto* l : m_LayerStack) l->OnImGuiRender();
        m_ImGuiLayer->End();   // 录制 ImGui 命令
        
        // 提交给渲染线程
        m_RenderThread->SubmitFrame(m_FrontBuffer);
        std::swap(m_FrontBuffer, m_BackBuffer);
    }
    m_RenderThread->Stop();
}

void RenderThread::Loop() {
    while (m_Running) {
        CommandBuffer* buf = WaitForFrame();
        buf->Execute();   // 全部命令执行 + RenderDrawData
        m_Window->SwapBuffers();
        SignalFrameDone();
    }
}
```

——主线程构建一帧 → 渲染线程消费这一帧 → 主线程同时构建下一帧。**真正并行**。

## 6.2.8 性能数据

|---|---|---|---|

| 提升 | | | +29% fps |

——双线程能让游戏密集场景多压一些 fps。但对桌面编辑器（不卡 60fps）不明显。

## 6.2.9 决策树：你应该选哪个方案？

```
你的引擎是？
   │
   ├── 单线程（Hazel 默认）
   │      → 方案 1 (UI 主线程)
   │
   ├── 双线程（游戏/渲染分离）
   │      └── 帧时间已经超 16ms？
   │             ├── 是 → 方案 2 (双缓冲 ImDrawData)
   │             └── 否 → 方案 1（足够）
   │
   ├── Job System (N 线程)
   │      └── 是否需要多 ImGui 实例？
   │             ├── 是 → 方案 3 (N Context + thread_local)
   │             └── 否 → 方案 1（仍只用主线程跑 ImGui）
   │
   └── 自动化测试 / 多窗口编辑器
          → 方案 3 (N Context)
```

**99% 情况选方案 1**。除非有具体性能需求或架构限制。

## 6.2.10 检查清单

升级到多线程 ImGui 之前的 checklist：

- [ ] 你的所有 `ImGui::XXX` 调用都在同一线程？
- [ ] 输入事件通过 PollEvents 同步分发，不跨线程？
- [ ] 没有跨帧持有 `ImGuiWindow*` / `ImDrawList*`？
- [ ] 没有跨线程持有 `ImGuiPayload*`？
- [ ] 字体加载 + Build 在主线程 NewFrame 之前完成？
- [ ] 用 `thread_local GImGui`（如果方案 3）？
- [ ] 每个 DLL 加载时 SetCurrentContext + SetAllocatorFunctions？
- [ ] 每条新线程 SetCurrentContext？
- [ ] 双缓冲 / Clone DrawData 而不是直接传 ImGui 内部指针？
- [ ] OnImGuiRender 内不持有跨线程锁？
- [ ] 用 TSan 跑过完整测试？
