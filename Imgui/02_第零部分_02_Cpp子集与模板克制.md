# 第 0.2 章 · ImGui 的 C++ 子集：反 STL、无异常、模板克制

> **本章目标**：让你看到 ImGui 源码中那些"看起来不太现代 C++"的写法时，能立刻明白**为什么**这样写——而不是误以为是项目陈旧。
>
> **本章对应源码**：`imgui.h:30~110`、`imgui.cpp:1276`（exit-time-destructors pragma）、`imgui_internal.h:106-110`（GCC/Clang 警告关闭）、`imgui_internal.h:506-512`（模板助手）、`imgui_internal.h:3674-3679`（Widget Behavior 模板）、`imconfig.h` 全文。

## 0.2.0 一段开场白：ImGui 是 "C with classes"，不是 "Modern C++"

ImGui 是一个 2014 年开始的项目（在 2014 年 C++11 才刚刚普及），核心作者 **Omar Cornut** 来自游戏行业。游戏行业对 C++ 的态度有两条工业惯例：

1. **代码必须能在所有合理目标上编译**：包括关闭异常的工程、关闭 RTTI 的工程、关闭 STL 的嵌入式平台、不支持完整 C++11 的旧编译器。
2. **代码的可调试性 / 可控性 > 表达力**：宁可手写一个 `for` 循环也不写 `std::transform`，宁可一个全局指针也不写复杂的依赖注入。

这不是"老派"或"跟不上时代"。这是**让代码能在 1000 个不同项目里活下去**的工程取舍。理解这一点，下面所有怪异写法都会变得自然。

## 0.2.1 反 STL：ImGui 几乎不依赖 C++ 标准库

打开 `imgui.h`，搜索所有 `#include`。你会发现：

```
#include <float.h>      // FLT_MIN, FLT_MAX
#include <stdarg.h>     // va_list, va_start, va_end
#include <stddef.h>     // ptrdiff_t, NULL
#include <string.h>     // memset, memcpy, memcmp, strlen, strchr, strcmp, strncmp
```

——全是 C 标准库头。**没有** `<vector>`、`<string>`、`<map>`、`<algorithm>`、`<memory>`、`<functional>`、`<thread>`。

`imgui.cpp` 里多了一些（`<stdio.h>` / `<stdlib.h>` / `<math.h>` 等），但仍然**不**依赖 STL。

### 为什么不用 STL？

`imgui.h` 中 `ImVector` 的注释解释了一部分原因：

```cpp
// imgui.h:2196-2204
// ImVector<>
// Lightweight std::vector<>-like class to avoid dragging dependencies (also,
// some implementations of STL with debug enabled are absurdly slow, we bypass
// it so our code runs fast in debug).
//
// - You generally do NOT need to care or use this ever. But we need to make it
//   available in imgui.h because some of our public structures are relying on it.
// - We use std-like naming convention here, which is a little unusual for this codebase.
// - Important: clear() frees memory, resize(0) keep the allocated buffer. We use
//   resize(0) a lot to intentionally recycle allocated buffers across frames and
//   amortize our costs.
// - Important: our implementation does NOT call C++ constructors/destructors,
//   we treat everything as raw data!
```

把这段话翻译成"实际原因列表"，至少有四条：

**(1) 减少依赖广度**

如果 `imgui.h` `#include <vector>`，那么所有用 ImGui 的工程都被迫拉进 `<vector>`。`<vector>` 又会拖进 `<memory>`、`<algorithm>`、`<initializer_list>` 等等。在大型游戏工程里，**编译时间和符号膨胀都是成本**。

**(2) Debug 构建性能**

MSVC 在 Debug 配置下，`std::vector::operator[]` 会做边界检查（`_ITERATOR_DEBUG_LEVEL=2`）。`std::sort` 会做迭代器有效性检查。在每帧都要扫描数千个顶点的场景下，这能让 Debug 帧率从 60fps 掉到 10fps。`ImVector` 在 Release 和 Debug 下表现一致。

**(3) ABI 跨编译器稳定**

`std::string` / `std::vector` 在 MSVC 和 Clang 之间二进制不兼容。如果 ImGui 公开 API 用了 `std::vector`，那么"用 MSVC 编译的 imgui.dll" 不能被 "用 Clang 编译的 app.exe" 使用。`ImVector` 是 POD 风格的简单结构体（`int Size; int Capacity; T* Data;`），ABI 跨编译器跨标准库一致。

**(4) 主动控制内存分配**

ImGui 全部内存分配走 `IM_ALLOC` / `IM_FREE` 两个宏（`imgui.h:2189-2190`），最终调到 `ImGui::MemAlloc/MemFree`，进而调用用户注册的全局函数指针。这意味着**用户可以一行代码替换 ImGui 的内存分配器**——例如接到游戏引擎的内存池上。如果用 STL，`std::vector` 默认走 `std::allocator`，要替换得给每个容器单独传 allocator 模板参数，写起来非常啰嗦。

### 自带的"STL 替代品"清单

ImGui 实质上自己实现了一套小型容器和工具：

| ImGui 的实现 | STL 对应 | 关键差异 |
|---|---|---|
| `ImVector<T>` | `std::vector<T>` | 不调用构造/析构、用 `memcpy` 拷贝、`grow` 1.5×、ABI 稳定 |
| `ImSpan<T>` | `std::span<T>`（C++20） | 仅 ptr+size 视图，不持有 |
| `ImPool<T>` | 没有直接对应（类似 `std::vector` + `std::unordered_map<ImGuiID, idx>`） | 槽位复用、ID 索引、保证调用析构 |
| `ImChunkStream<T>` | 没有对应（类似 arena） | 变长记录顺序流，4 字节对齐 |
| `ImStableVector<T, B>` | 类似 `std::deque<T>` 但更简单 | 块状分配，对象指针不会失效 |
| `ImBitArray<N>` / `ImBitVector` | `std::bitset<N>` / `std::vector<bool>` | 静态/动态位图，无任何 vtable |
| `ImGuiStorage` | `std::unordered_map<ImGuiID, T>`（变种） | 有序数组 + 二分查找，cache 友好 |
| `ImGuiTextBuffer` | `std::string` | 自带 `appendf` 的 `ImVector<char>` |

第二部分（Ch 2.1 / 2.2）会逐个剖析它们的实现。这里只需建立一个印象：**ImGui 用一套足够简陋但极致务实的容器，覆盖了它需要的全部场景**。

## 0.2.2 无异常、无 RTTI：错误处理用 IM_ASSERT 兜底

### 无异常

**ImGui 全代码不使用 `try/catch/throw`**。事实上，它能在 `-fno-exceptions` 编译选项下完整通过。

这有两个具体的代码体现：

**体现 1：自定义 placement new 绕开 `<new>`**

```cpp
// imgui.h:2186-2194
struct ImNewWrapper {};
inline void* operator new(size_t, ImNewWrapper, void* ptr) { return ptr; }
inline void  operator delete(void*, ImNewWrapper, void*)   {}

#define IM_ALLOC(_SIZE)         ImGui::MemAlloc(_SIZE)
#define IM_FREE(_PTR)           ImGui::MemFree(_PTR)
#define IM_PLACEMENT_NEW(_PTR)  new(ImNewWrapper(), _PTR)
#define IM_NEW(_TYPE)           new(ImNewWrapper(), ImGui::MemAlloc(sizeof(_TYPE))) _TYPE
template<typename T> void IM_DELETE(T* p)   { if (p) { p->~T(); ImGui::MemFree(p); } }
```

**为什么不直接用标准 placement new `new(ptr) T`**？

标准 placement new 在 `<new>` 头里。在某些禁用了异常的项目（特别是某些游戏控制台 SDK），`<new>` 会拉进异常类型 `std::bad_alloc`，导致编译错误。ImGui 通过自定义一个一参 `ImNewWrapper` 标签类，**完全不 include `<new>`** 就实现了 placement new。

详见 `imgui.h:2181-2184` 的注释原文：

> `// Defining a custom placement new() with a custom parameter allows us to bypass including <new> which on some platforms complains when user has disabled exceptions.`

**体现 2：所有"内存分配失败"都假装它不会失败**

```cpp
// imgui.h:2251 (ImVector::reserve)
inline void reserve(int new_capacity) {
    if (new_capacity <= Capacity) return;
    T* new_data = (T*)IM_ALLOC((size_t)new_capacity * sizeof(T));
    if (Data) {
        memcpy(new_data, Data, (size_t)Size * sizeof(T));
        IM_FREE(Data);
    }
    Data = new_data;
    Capacity = new_capacity;
}
```

`IM_ALLOC` 的默认实现 `MallocWrapper` 调用 `malloc`，**返回 NULL 时这里不会检测**。如果 `malloc` 失败，`memcpy(new_data=NULL, ...)` 会段错误。

这看起来很危险，但游戏引擎的现实是：**桌面/主机平台上，malloc 失败时进程已经处于"无法继续"状态**——剩余内存已经少到连错误处理都跑不下去。**与其检查 malloc 返回值并优雅退出，不如让它崩溃**，由 OS 的崩溃报告系统来抓 dump。

如果你在嵌入式平台需要严格处理内存失败，方案是：

1. 重写 `ImGui::MemAlloc` 让它在内存不足时主动 `IM_ASSERT(0)`，立刻把崩溃定位在分配点而不是后续 `memcpy` 处。
2. 或者让 `MemAlloc` 返回一个"哨兵地址"指向受保护的页，**任何**写入立刻触发段错误。

### 无 RTTI

**ImGui 不使用 `dynamic_cast` 和 `typeid`**。它能在 `-fno-rtti` 下编译。

这意味着 ImGui **没有继承体系**——你不会看到 `class Button : public Widget` 这种代码。它的"多态"通过其他方式实现：

- **函数指针**：`ImDrawCallback`、`ImGuiInputTextCallback`、`ImGuiSizeCallback` 等所有需要"用户挂钩子"的地方，都是 `void(*)(...)` 而不是 `std::function`。
- **`enum` + `if/switch`**：例如 Widget Behavior 通过 `ImGuiDataType` 枚举决定如何插值（int / uint / float / double）。
- **模板**：例如 `SliderBehaviorT<T, SIGNED_T, FLOAT_T>` 实例化出 4 个版本，没有运行时多态。

这种风格的好处是**没有 vtable 开销、没有间接跳转、所有调用都可被编译器内联或预测**。代价是**无法用"对象语义"组织代码**——但 ImGui 是 immediate mode，本来就不依赖对象。

### IM_ASSERT 哲学

ImGui 用 **assert** 替代异常和错误码。

```cpp
// imgui.h:94-96
#ifndef IM_ASSERT
#include <assert.h>
#define IM_ASSERT(_EXPR)            assert(_EXPR)
#endif
```

```cpp
// imconfig.h:17-21（注释里的示例）
//---- Define assertion handler. Defaults to calling assert().
// - If your macro uses multiple statements, make sure is enclosed in a 'do { .. } while (0)' block so it can be used as a single statement.
// - Compiling with NDEBUG will usually strip out assert() to nothing, which is NOT recommended because we use asserts to notify of programmer mistakes.
//#define IM_ASSERT(_EXPR)  MyAssert(_EXPR)
//#define IM_ASSERT(_EXPR)  ((void)(_EXPR))     // Disable asserts
```

**关键的工程态度**：

`imconfig.h` 里官方明确说"**用 NDEBUG 关掉 assert 不推荐**"。换句话说：

- ImGui 把 IM_ASSERT 当作**部分契约**，不是**纯调试**辅助。
- 即使在 Release 构建里，IM_ASSERT 失败也意味着"代码逻辑错了"，应该让进程崩溃而不是默默继续。

**典型 IM_ASSERT 用法**（你会在源码里反复看到）：

```cpp
// imgui.h:2234-2235
inline T&  operator[](int i)        { IM_ASSERT(i >= 0 && i < Size); return Data[i]; }

// imgui.h:2241-2242
inline T&  front()                  { IM_ASSERT(Size > 0); return Data[0]; }

// imgui.h:2258
inline T*  erase(const T* it)       { IM_ASSERT(it >= Data && it < Data + Size); ... }
```

这是 "fail fast" 哲学：**前置条件不满足，立刻崩，不要传播脏数据**。

**对你的引擎集成的启示**：

- **不要**在自家 `IM_ASSERT` 实现里"吞掉"失败再继续。这等于把契约违规变成神秘的运行时错误。
- **可以**重写 IM_ASSERT 让它做更多事——记日志、调起调试器、上报错误统计——但**最终必须 break/abort**。

**自定义 IM_ASSERT 的标准姿势**（写在 `imconfig.h`）：

```cpp
// imconfig.h 自定义示例
#include "Hazel/Core/Assert.h"

#define IM_ASSERT(EXPR)  do {                           \
        if (!(EXPR)) {                                   \
            HZ_CORE_ERROR("ImGui: " #EXPR);              \
            HZ_DEBUGBREAK();                             \
        }                                                \
    } while (0)
```

注意 `do { ... } while (0)` 包裹——`imconfig.h:18` 也强调了这一点，因为 IM_ASSERT 经常作为单语句出现在 `if` 分支里：`if (cond) IM_ASSERT(x);`。

### "软错误"与状态恢复

ImGui 还有一套更温和的错误机制——**Error Recovery**。某些用户错误（例如 `Begin` 没配对的 `End`）即使触发 IM_ASSERT 也很难"原地修复"，所以 ImGui 在 1.89+ 引入了：

```cpp
// imgui.cpp:[SECTION] ERROR CHECKING, STATE RECOVERY (约 10768 行)
// ErrorRecoveryTryToRecoverState
// ErrorLog / ErrorCheckEndFrameSanityChecks
```

它在 `EndFrame` 时检测各种栈不平衡（ID 栈、Style 栈、Window 栈），尝试**自动 Pop 到正确深度**，并通过 Debug Log 报告。

这对**热重载**（Hot Reload）特别重要——重新加载 DLL 后，前一帧的状态可能不一致，Error Recovery 能避免完全崩溃。

第 4 章会回到这个主题。

## 0.2.3 模板克制策略：ImGui 用模板，但用得很谨慎

ImGui **使用模板**，但把模板限制在三个明确场景里：

### 场景 1：泛型助手函数

```cpp
// imgui_internal.h:506-512
template<typename T> T ImMin(T lhs, T rhs)                              { return lhs < rhs ? lhs : rhs; }
template<typename T> T ImMax(T lhs, T rhs)                              { return lhs >= rhs ? lhs : rhs; }
template<typename T> T ImClamp(T v, T mn, T mx)                         { return (v < mn) ? mn : (v > mx) ? mx : v; }
template<typename T> T ImLerp(T a, T b, float t)                        { return (T)(a + (b - a) * t); }
template<typename T> void ImSwap(T& a, T& b)                            { T tmp = a; a = b; b = tmp; }
template<typename T> T ImAddClampOverflow(T a, T b, T mn, T mx)         { if (b < 0 && (a < mn - b)) return mn; if (b > 0 && (a > mx - b)) return mx; return a + b; }
template<typename T> T ImSubClampOverflow(T a, T b, T mn, T mx)         { if (b > 0 && (a < mn + b)) return mn; if (b < 0 && (a > mx + b)) return mx; return a - b; }
```

来自 `imgui_internal.h:504-505` 的注释里的关键一句：

> `// ImMin/ImMax/ImClamp/ImLerp/ImSwap are used by widgets which support variety of types: signed/unsigned int/long long float/double`
> `// (Exceptionally using templates here but we could also redefine them for those types)`

**注意 "Exceptionally using templates here" 这句**——官方明确表态："这里**例外**用了模板，本来也可以为每个类型重定义一遍"。这就是 ImGui 对模板的态度："能不用就不用，用了就为了避免重复代码"。

紧接着的几行是为 `ImVec2` / `ImVec4` 做的非模板特化：

```cpp
// imgui_internal.h:514-519
inline ImVec2 ImMin(const ImVec2& lhs, const ImVec2& rhs)               { return ImVec2(lhs.x < rhs.x ? lhs.x : rhs.x, lhs.y < rhs.y ? lhs.y : rhs.y); }
inline ImVec2 ImMax(const ImVec2& lhs, const ImVec2& rhs)               { return ImVec2(lhs.x >= rhs.x ? lhs.x : rhs.x, lhs.y >= rhs.y ? lhs.y : rhs.y); }
// ...
inline ImVec2 ImLerp(const ImVec2& a, const ImVec2& b, float t)         { return ImVec2(a.x + (b.x - a.x) * t, a.y + (b.y - a.y) * t); }
```

这里没用模板特化，而是直接重载——因为 `ImVec2` 不能用 `<`、`>` 比较，泛型版本不适用。

### 场景 2：泛型容器

```cpp
// imgui.h:2207
template<typename T>
struct ImVector { /* ... */ };

// imgui_internal.h:643
template<int BITCOUNT, int OFFSET = 0>
struct ImBitArray { /* ... */ };

// imgui_internal.h:702
template<int CHUNKS>
struct ImSpanAllocator { /* ... */ };

// imgui_internal.h:725
template<typename T, int BLOCKSIZE>
struct ImStableVector { /* ... */ };

// imgui_internal.h:758
template<typename T>
struct ImPool { /* ... */ };

// imgui_internal.h:792
template<typename T>
struct ImChunkStream { /* ... */ };
```

**模板参数都是简单的**：要么是 `typename T`（元素类型），要么是 `int N`（编译期常量大小）。**没有**：
- 多个模板参数互相约束的关系
- 模板模板参数（template-template parameter）
- 可变参模板（variadic template）
- 默认模板参数依赖前置参数

这就是工程实用主义：模板只是为了**避免重复 N 个 `ImVector_int` / `ImVector_char` / `ImVector_float`** 的样板代码。

### 场景 3：Widget Behavior 的"算法多态"

这是 ImGui 模板用得最深的地方，也是值得重点拆解的：

```cpp
// imgui_internal.h:3674-3679
template<typename T, typename SIGNED_T, typename FLOAT_T>   IMGUI_API float ScaleRatioFromValueT(ImGuiDataType data_type, T v, T v_min, T v_max, float logarithmic_zero_epsilon, float zero_deadzone_size);
template<typename T, typename SIGNED_T, typename FLOAT_T>   IMGUI_API T     ScaleValueFromRatioT(ImGuiDataType data_type, float t, T v_min, T v_max, float logarithmic_zero_epsilon, float zero_deadzone_size);
template<typename T, typename SIGNED_T, typename FLOAT_T>   IMGUI_API bool  DragBehaviorT(ImGuiDataType data_type, T* v, float v_speed, T v_min, T v_max, const char* format, ImGuiSliderFlags flags);
template<typename T, typename SIGNED_T, typename FLOAT_T>   IMGUI_API bool  SliderBehaviorT(const ImRect& bb, ImGuiID id, ImGuiDataType data_type, T* v, T v_min, T v_max, const char* format, ImGuiSliderFlags flags, ImRect* out_grab_bb);
template<typename T>                                        IMGUI_API T     RoundScalarWithFormatT(const char* format, ImGuiDataType data_type, T v);
template<typename T>                                        IMGUI_API bool  CheckboxFlagsT(const char* label, T* flags, T flags_value);
```

**注意 3 个模板参数**：`T` / `SIGNED_T` / `FLOAT_T`。

#### 为什么需要 3 个？

考虑 `SliderInt(int* v, int v_min, int v_max)` 的实现需求：

1. **存储参数**：`v`、`v_min`、`v_max` 都是 `int` → 这是 `T = int`。
2. **范围计算**：`v_max - v_min`。如果 `T = unsigned int` 且 `v_min > v_max`（虽然语义上不允许，但代码要鲁棒），无符号减法会环绕。所以需要一个**有符号版本**的 `T` → `SIGNED_T = int`（对 unsigned int 来说就是 int）。
3. **插值计算**：`v_min + (v_max - v_min) * t`，其中 `t` 是 `[0,1]` 浮点比例。为了精度，乘法必须在浮点域完成 → `FLOAT_T = float`（对 int/uint 来说）或 `double`（对 long long / double 来说）。

实例化时，`imgui_widgets.cpp` 会生成所有有效组合：

```cpp
// imgui_widgets.cpp 文末附近会有显式实例化
// (大致是这样，具体看 imgui_widgets.cpp 的 SliderBehavior 和 DragBehavior 区域)
template IMGUI_API bool SliderBehaviorT<ImS8,    ImS8,    float >(...);
template IMGUI_API bool SliderBehaviorT<ImU8,    ImS8,    float >(...);
template IMGUI_API bool SliderBehaviorT<ImS16,   ImS16,   float >(...);
template IMGUI_API bool SliderBehaviorT<ImU16,   ImS16,   float >(...);
template IMGUI_API bool SliderBehaviorT<ImS32,   ImS32,   float >(...);
template IMGUI_API bool SliderBehaviorT<ImU32,   ImS32,   float >(...);
template IMGUI_API bool SliderBehaviorT<ImS64,   ImS64,   double>(...);
template IMGUI_API bool SliderBehaviorT<ImU64,   ImS64,   double>(...);
template IMGUI_API bool SliderBehaviorT<float,   float,   float >(...);
template IMGUI_API bool SliderBehaviorT<double,  double,  double>(...);
```

10 种数据类型，每种独立实例化。这就是 ImGui 实现 `SliderInt8` / `SliderUint8` / `SliderInt16` / ... / `SliderDouble` 全家桶的方式：**一份代码，10 个实例**。

#### 与运行时多态的对比

如果用 OO 风格，你会写：

```cpp
// 反面教材：不要在 ImGui 里这样写
class SliderBehaviorBase {
    virtual bool Compute(...) = 0;
};
class SliderBehaviorInt : public SliderBehaviorBase { ... };
class SliderBehaviorFloat : public SliderBehaviorBase { ... };
```

代价：

- 引入虚函数表，每次 Slider 调用多一次间接跳转。
- 必须 `new` 派生类对象——分配内存。
- 代码膨胀更严重（每个类都有自己的 vtable）。
- 不能内联——编译器看不穿虚函数。

ImGui 的模板方案：

- 每个实例化都是普通函数，**编译器完全能内联**。
- 没有任何 vtable / 间接跳转。
- 数据类型分发由 `ImGuiDataType` 枚举 + `switch` 在**外层**完成（编译器友好）：

```cpp
// imgui_widgets.cpp 中典型的 switch 分发模式（伪代码）
bool ImGui::SliderScalar(const char* label, ImGuiDataType data_type, void* v, ...) {
    switch (data_type) {
        case ImGuiDataType_S8:     return SliderBehaviorT<ImS8,   ImS8,   float >(...);
        case ImGuiDataType_U8:     return SliderBehaviorT<ImU8,   ImS8,   float >(...);
        case ImGuiDataType_S16:    return SliderBehaviorT<ImS16,  ImS16,  float >(...);
        // ...
        case ImGuiDataType_Float:  return SliderBehaviorT<float,  float,  float >(...);
        case ImGuiDataType_Double: return SliderBehaviorT<double, double, double>(...);
    }
}
```

`switch` 跳转表通常会被编译器优化成跳转表（jump table）+ 紧接其后的内联代码块，性能比虚函数好得多。

**这是泛型编程的"纯算法"用法**：模板用来**生成一组无关联的实例**，而不是用来**做编译期推导**。

## 0.2.4 ImGui 不使用的现代 C++ 特性

下面这些特性在 ImGui 源码里**几乎找不到**，理解原因比记住列表更重要：

### SFINAE / `std::enable_if`

ImGui 没有"根据类型条件选择重载"的模板代码。原因：

- 这种模式通常是为"库代码要适配未知用户类型"准备的。但 ImGui 的 `ImVector<T>` 等容器只服务于 ImGui **内部**已知类型集合，不需要"如果 T 有 swap 成员就用，否则用 std::swap"这种通用性。
- SFINAE 编译错误信息是出名的灾难。ImGui 选择"少几行通用性，换调试体验"。

### Concepts（C++20）

虽然 Concepts 比 SFINAE 干净，但 ImGui 至今支持 C++11 编译，不会引入 C++20 特性。它的 trade-off 是**最大兼容性**。

### Fold expressions / Variadic templates

ImGui 的 "可变参函数" 用 C 风格 `va_list`：

```cpp
// imgui.h 里的 ImGuiTextBuffer
IMGUI_API void  appendf(const char* fmt, ...) IM_FMTARGS(2);
IMGUI_API void  appendfv(const char* fmt, va_list args) IM_FMTLIST(2);
```

注意 `IM_FMTARGS(2)` 这个宏——它是 GCC/Clang 的 `__attribute__((format(printf, 1, 2)))` 包装，让编译器**像检查 printf 一样**检查 fmt 字符串和后续参数。这比 C++ 可变参模板更接近 C printf 的传统语义，对**调试器和静态分析工具**也更友好。

### `std::function`

需要回调时，ImGui 用裸函数指针 + `void* user_data`：

```cpp
// imgui.h:3166
typedef void (*ImDrawCallback)(const ImDrawList* parent_list, const ImDrawCmd* cmd);
```

```cpp
// imgui.h: ImGuiInputTextCallback
typedef int (*ImGuiInputTextCallback)(ImGuiInputTextCallbackData* data);
```

`std::function` 的问题：
- 内部可能要堆分配（小对象优化不保证）。
- ABI 不稳定（不同 STL 实现尺寸/布局不同）。
- 调用开销大（间接调用 + 可能的虚函数）。

裸函数指针 + `user_data` 是 C 的经典做法，没有上述问题。代价是用户写起来稍啰嗦，但对**库**来说是合适的取舍。

### `std::shared_ptr` / `std::unique_ptr`

ImGui 的对象生命周期非常清晰：

- `ImGuiContext` 由 `CreateContext` 创建、`DestroyContext` 销毁，**用户管理**。
- `ImGuiWindow` / `ImGuiTable` / `ImGuiTabBar` 等"长寿"对象由 `ImPool` 管理，**ImGui 内部管理**。
- `ImDrawList` 由 Context 管理，跨帧持久（资源池化）。

这些都不需要智能指针。**裸指针在 ImGui 的语境下是清晰的**——所有权关系一目了然。

### `if constexpr`

C++17 特性。ImGui 偶尔用 `#ifdef`（预处理器条件编译）做编译期分支：

```cpp
// imgui.h:3151-3156
// ImDrawIdx: vertex index. [Compile-time configurable type]
#ifndef ImDrawIdx
typedef unsigned short ImDrawIdx;
#endif
```

这不是 `if constexpr` 的精确替代，但对 ImGui 的需求够用了。

## 0.2.5 静态/全局变量哲学：ImGui 主动接受静态对象

```cpp
// imgui.cpp:1276
#pragma clang diagnostic ignored "-Wexit-time-destructors"
// warning: declaration requires an exit-time destructor
// exit-time destruction order is undefined. if MemFree() leads to users code
// that has been disabled before exit it might cause problems.
// ImGui coding style welcomes static/globals.
```

**最后一句关键**：`ImGui coding style welcomes static/globals.`

这是对"现代 C++ 反静态对象"主流态度的**反向选择**。让我们看看具体在哪些地方用：

### 全局：`GImGui`

```cpp
// imgui.cpp:1437-1439
#ifndef GImGui
ImGuiContext*   GImGui = NULL;
#endif
```

整个 ImGui 库**只有一个**当前 Context 指针。所有 `ImGui::XXX` 函数读写它。这是有意为之——把"上下文参数"从所有 API 里抽走，让函数签名极简：

```cpp
// 你写的：
ImGui::Begin("MyWindow");
ImGui::Button("Click");

// 而不是：
ImGui::Begin(ctx, "MyWindow");
ImGui::Button(ctx, "Click");
```

这种风格的代价是**线程不安全**（这正是第 6 章会展开的主题），但对 99% 的用例（单线程 UI 构建）非常方便。

### 静态：分配器函数指针

```cpp
// imgui.cpp:1451-1453
static ImGuiMemAllocFunc    GImAllocatorAllocFunc = MallocWrapper;
static ImGuiMemFreeFunc     GImAllocatorFreeFunc = FreeWrapper;
static void*                GImAllocatorUserData = NULL;
```

整个进程只有一组分配器。`SetAllocatorFunctions` 改这三个静态变量。

代价：**多 DLL 模式下每个 DLL 都有自己的 ImGui 静态变量**——必须手动同步。这是 `imgui.cpp:1417-1422` 的 DLL 警告所讲的内容：

```cpp
// imgui.cpp:1417-1422 (摘录)
// DLL users:
// - Heaps and globals are not shared across DLL boundaries!
// - You will need to call SetCurrentContext() + SetAllocatorFunctions() for each static/DLL boundary you are calling from.
// - Same applies for hot-reloading mechanisms that are reliant on reloading DLL (note that many hot-reloading mechanisms work without DLL).
// - Using Dear ImGui via a shared library is not recommended, because of function call overhead and because we don't guarantee backward nor forward ABI compatibility.
```

**结论**：ImGui **不推荐**做成 DLL/共享库。游戏引擎里把它做成静态库内嵌进可执行文件最省心。

### 大量 `static` 函数

打开 `imgui.cpp`，搜 `^static `，你会看到几十个 `static` 函数。

```cpp
// 例如 imgui.cpp:1445-1446
static void*   MallocWrapper(size_t size, void* user_data) { /* ... */ }
static void    FreeWrapper(void* ptr, void* user_data) { /* ... */ }
```

**为什么用 `static`**？

`static` 函数只在当前翻译单元（.cpp 文件）内可见，不会出现在符号表里。这样：
- **链接更快**（符号少，链接器查找更快）。
- **不会和其他库的同名符号冲突**。
- **优化更激进**（编译器知道这函数不会被外部调用，可以更自由地内联/特化）。

ImGui 把所有"不需要跨翻译单元调用"的工具函数都标 `static`，让公开符号表保持精简。

## 0.2.6 编译期开关：`imconfig.h` 的设计

`imconfig.h` 是 ImGui 的"编译期配置中心"。整个文件的功能就是定义一组宏，控制 ImGui 的编译行为。

让我们看看它最重要的几组宏（对照 `imconfig.h` 文件，约 80 行）：

### 第 1 组：定义 ABI 的宏（改动会破坏二进制兼容）

```cpp
// imconfig.h:64
//#define IMGUI_USE_BGRA_PACKED_COLOR

// imconfig.h:69-70
//#define IMGUI_USE_WCHAR32      // 32-bit ImWchar，影响 ImFontGlyph 内存布局

// imconfig.h（其他文件中相关宏）
//#define IMGUI_OVERRIDE_DRAWVERT_STRUCT_LAYOUT  // 自定义顶点布局，改 ImDrawVert 大小
//#define ImDrawIdx unsigned int                  // 32-bit 索引，影响 ImDrawList::IdxBuffer 元素大小
```

**这一组宏改了之后**：你的 app.cpp 编译出来的 `ImDrawVert` / `ImFontGlyph` 与 imgui.cpp 编译出来的不一致 → 链接成功但运行时崩溃。

防御机制是 `IMGUI_CHECKVERSION`：

```cpp
// imgui.h:104
#define IMGUI_CHECKVERSION()        ImGui::DebugCheckVersionAndDataLayout(IMGUI_VERSION, sizeof(ImGuiIO), sizeof(ImGuiStyle), sizeof(ImVec2), sizeof(ImVec4), sizeof(ImDrawVert), sizeof(ImDrawIdx))
```

每个使用 ImGui 的 .cpp 都应该在初始化时调用一次 `IMGUI_CHECKVERSION()`——它会检查"编译你这个 .cpp 时看到的 sizeof"和"编译 imgui.cpp 时看到的 sizeof"是否一致。不一致就立刻 IM_ASSERT 失败。

### 第 2 组：禁用功能减少代码尺寸

```cpp
// imconfig.h:36-38
//#define IMGUI_DISABLE                 // 完全禁用 ImGui
//#define IMGUI_DISABLE_DEMO_WINDOWS    // 禁用 Demo（不要在开发期禁用！）
//#define IMGUI_DISABLE_DEBUG_TOOLS     // 禁用 Metrics/Debug Log
```

```cpp
// imconfig.h:41-53
//#define IMGUI_DISABLE_WIN32_DEFAULT_CLIPBOARD_FUNCTIONS
//#define IMGUI_DISABLE_DEFAULT_FORMAT_FUNCTIONS
//#define IMGUI_DISABLE_DEFAULT_MATH_FUNCTIONS
//#define IMGUI_DISABLE_FILE_FUNCTIONS
//#define IMGUI_DISABLE_DEFAULT_ALLOCATORS    // 让你必须 SetAllocatorFunctions
//#define IMGUI_DISABLE_DEFAULT_FONT
//#define IMGUI_DISABLE_SSE
```

**对引擎集成的实战建议**：

- 开发期**绝不**关 Demo 和 Debug Tools。它们对调试无价。
- Release 构建可以用 `IMGUI_DISABLE_DEBUG_TOOLS` 减小体积（约 100KB+）。
- `IMGUI_DISABLE_DEFAULT_ALLOCATORS` 强制让你接管内存分配——如果你的引擎有内存池，建议开。
- `IMGUI_DISABLE_DEFAULT_FONT` 在你已经加载自家字体的情况下能省 ~23KB。

### 第 3 组：行为开关

```cpp
// imconfig.h:31-32
//#define IMGUI_DISABLE_OBSOLETE_FUNCTIONS  // 禁用废弃 API（推荐定期开一下清理代码）

// imconfig.h:66-67
//#define IMGUI_USE_LEGACY_CRC32_ADLER      // 兼容 1.91.6 之前的 .ini 文件
```

`IMGUI_DISABLE_OBSOLETE_FUNCTIONS` 值得**定期开一次**——它会把所有 ImGui 标记为 obsolete 的 API 从编译里去掉。如果你的代码报错，说明你用了将来会被删的 API，及时改掉。

### 第 4 组：用户钩子

```cpp
// imconfig.h:60-61
//#define IMGUI_INCLUDE_IMGUI_USER_H
//#define IMGUI_USER_H_FILENAME         "my_folder/my_imgui_user.h"
```

如果定义 `IMGUI_INCLUDE_IMGUI_USER_H`，`imgui.h` 末尾会 `#include` 你指定的头文件。你可以在那里**追加自定义的 ImGui:: 命名空间函数声明**。配合 `imgui_user.cpp` 的实现，相当于"无侵入扩展 ImGui 公共 API"。

这是给你的**第一个魔改入口**：在不修改 ImGui 源码本身的前提下，添加自家的 `ImGui::MyEditorFooBar(...)` 函数。

### `imconfig.h` 的工程纪律

```cpp
// imconfig.h:9-13
// You need to make sure that configuration settings are defined consistently
// _everywhere_ Dear ImGui is used, which include the imgui*.cpp files but also
// _any_ of your code that uses Dear ImGui. This is because some compile-time
// options have an affect on data structures.
// Defining those options in imconfig.h will ensure every compilation unit gets
// to see the same data structure layouts.
// Call IMGUI_CHECKVERSION() from your .cpp file to verify that the data structures
// your files are using are matching the ones imgui.cpp is using.
```

**最重要的实操守则**：所有 `IMGUI_XXX` 宏要么**全在** `imconfig.h` 里定义，要么用 `IMGUI_USER_CONFIG` 指向你自己的配置文件。**绝对不要**在某个 `.cpp` 里 `#define IMGUI_USE_WCHAR32` 然后 `#include "imgui.h"`——这会让那个 .cpp 看到的 `ImWchar` 是 32-bit，其他 .cpp 看到的是 16-bit，整个工程链接成功但运行时炸。

正确做法：

```cpp
// 你的引擎 PCH 或者全局配置头
#define IMGUI_USER_CONFIG "Hazel/Imgui/HazelImguiConfig.h"
```

然后在 `HazelImguiConfig.h` 里写所有 `IMGUI_XXX` 宏。CMake/MSBuild 把 `IMGUI_USER_CONFIG` 作为编译宏全局传给所有翻译单元。

## 0.2.7 命名约定与代码风格

读 ImGui 源码之前，记住这几个约定能省你 50% 的"这是啥意思"时间：

### 前缀

- `Im*`：**通用**工具类，不依赖 ImGui Context。例如 `ImVec2`、`ImVector`、`ImRect`、`ImBezierCubicCalc`。
- `ImGui*`：**ImGui 业务**类，依赖 Context。例如 `ImGuiContext`、`ImGuiWindow`、`ImGuiStyle`。
- `ImDraw*`：**绘制相关**。例如 `ImDrawList`、`ImDrawCmd`、`ImDrawData`、`ImDrawVert`。
- `ImFont*`：**字体相关**。例如 `ImFont`、`ImFontAtlas`、`ImFontGlyph`。

### 后缀

- `_`：**枚举值后缀**。比如 `ImGuiCol_Text`、`ImGuiKey_A`。注意是单下划线。
- `Flags_`：**标志位枚举集合**。比如 `ImGuiWindowFlags_NoTitleBar`。
- `*Private*` / `Internal*`：**仅 internal 用**的字段或函数（你能看到，但不能信赖稳定）。
- `_*`（前导下划线字段）：**ImGui 内部使用**，应用代码不要碰。比如 `ImDrawList::_CmdHeader` / `ImDrawList::_Path`。

### 函数命名

- `ImGui::Begin*` / `ImGui::End*`：**栈式 API**，必须配对。例如 `BeginChild` / `EndChild`、`PushID` / `PopID`。
- `ImGui::Get*`：**快速读取**，通常 O(1)，可频繁调用。
- `ImGui::Find*`：**搜索**，可能 O(N)。
- `ImGui::Add*Event`：**事件入队**（输入路由 API）。
- 动词原形（`Begin`、`Render`、`Submit`）vs 现在分词（`Rendering`、`Submitting`）—— ImGui 用动词原形，简洁。

### 全局变量

- `g`：在函数内部，`ImGuiContext& g = *GImGui;` 是固定开头。后续代码全部用 `g.XXX` 访问字段。这是 ImGui 风格的标志，几乎每个非平凡函数都这样开头。

```cpp
// 典型的 ImGui 函数开头（imgui.cpp 中无数处）
void ImGui::SomeFunction() {
    ImGuiContext& g = *GImGui;
    ImGuiWindow* window = g.CurrentWindow;
    if (window->SkipItems) return;
    // ...
}
```

### 注释体例

ImGui 注释里有一些约定俗成的标记：

- `// FIXME-XXX: ...` 表示某个**主题领域**的待办（FIXME-MULTITHREADING / FIXME-NAV / FIXME-DPI / FIXME-OPT）。这些是宝藏：你可以搜 `FIXME-OPT` 找到所有"这里其实可以更快"的地方。
- `// (Read above ... section for context)` 出现在某个函数里，提示你回到 SECTION 头注释看背景。
- `// e.g.` 后面跟实例代码片段，通常对你 copy-paste 友好。
- `// Important:` 是真的很重要的注意事项——一定要读。

## 0.2.8 你写魔改代码时应该遵守什么风格？

如果你在**ImGui 仓库内**修改源码（贡献 PR / 维护私有分支），应该**严格遵守 ImGui 风格**：

- 用 `ImVector` 不用 `std::vector`。
- 用 `IM_ASSERT` 不用 `assert`。
- 用 `IM_ALLOC` / `IM_FREE` 不用 `malloc` / `free`。
- 不引入 `<vector>` / `<string>` / `<algorithm>` 等 STL 头。
- 函数开头 `ImGuiContext& g = *GImGui;`。
- 4 空格缩进、左花括号同行（`if (cond) {`）。

如果你在**自己的引擎里**用 ImGui，但有自己的扩展层（例如 `Hazel::ImGuiHelpers`），那么有两个合理选择：

**选择 A：完全用 ImGui 风格**

适用于：扩展函数会大量调用 ImGui internal API，与 ImGui 代码贴在一起读。

```cpp
namespace ImGui {
    void HazelInputFloat3(const char* label, float v[3]) {
        ImGuiContext& g = *GImGui;
        ImGuiWindow* window = g.CurrentWindow;
        if (window->SkipItems) return;
        // ... 用 ImVector / IM_ASSERT / IM_ALLOC ...
    }
}
```

**选择 B：用引擎风格**

适用于：扩展函数主要做"组合 ImGui 公开 API"，不深入 internal。

```cpp
namespace Hazel::UI {
    void DrawVec3Control(const std::string& label, glm::vec3& values) {
        // 引擎风格代码：用 std::string、HZ_ASSERT、用 PascalCase 等
        ImGui::PushID(label.c_str());
        // ... 用 ImGui 公开 API ...
        ImGui::PopID();
    }
}
```

**不要混用**：在一个文件里既有 `ImVector` 又有 `std::vector`，既有 `IM_ASSERT` 又有 `HZ_ASSERT`，会非常分裂。**按文件级别划分**：哪个文件深入 internal 用 ImGui 风格，哪个文件做"上层组合"用引擎风格。

## 0.2.9 警告关闭：ImGui 主动关掉了哪些编译警告

`imgui_internal.h:99-110` 有一段为 Clang/GCC/MSVC 关闭警告的 pragma：

```cpp
// imgui_internal.h:106-109 (GCC)
#pragma GCC diagnostic ignored "-Wpragmas"
#pragma GCC diagnostic ignored "-Wfloat-equal"
#pragma GCC diagnostic ignored "-Wclass-memaccess"
#pragma GCC diagnostic ignored "-Wdeprecated-enum-enum-conversion"
#pragma GCC diagnostic ignored "-Wsign-conversion"
```

```cpp
// imgui_internal.h:99-103 (Clang)
#pragma clang diagnostic ignored "-Wdeprecated-enum-enum-conversion"
#pragma clang diagnostic ignored "-Wunsafe-buffer-usage"
#pragma clang diagnostic ignored "-Wnontrivial-memaccess"
```

**每条都讲一个故事**：

### `-Wclass-memaccess` / `-Wnontrivial-memaccess`

GCC 8+ 和 Clang 都会警告"`memset` / `memcpy` 一个非平凡可拷贝（non-trivially-copyable）的类型"。但 ImGui **故意**这么做：

```cpp
// imgui.h:2255 (ImVector::push_back)
inline void push_back(const T& v) {
    if (Size == Capacity) reserve(_grow_capacity(Size + 1));
    memcpy(&Data[Size], &v, sizeof(v));        // ← 这里
    Size++;
}
```

`T` 可能是 `ImGuiTabItem`、`ImGuiTableColumn` 等带构造函数的类型。编译器认为 `memcpy` 它们不安全。但 ImGui 设计这些类型时**就是按"可以 memcpy"的标准**——也即**Trivially Relocatable**（第 0.3 章会展开）。

关闭警告的代价是：**如果你不小心把一个真的不能 memcpy 的类型（带 RAII 句柄、含 `std::shared_ptr`）放进 `ImVector`**，编译器不会警告你，运行时会神秘崩溃。

### `-Wfloat-equal`

GCC 警告"用 `==` 比较浮点"。ImGui 里有大量 `if (alpha == 1.0f)` / `if (size.x == 0.0f)` 这种比较——是有意的"精确等于"语义（不是"约等于"）。

### `-Wsign-conversion`

GCC 警告"有符号 / 无符号互转"。ImGui 里有大量 `int` 和 `unsigned int` / `size_t` 互转，按设计都是安全的（值域不会超过 `INT_MAX`）。

### `-Wexit-time-destructors`

```cpp
// imgui.cpp:1276
#pragma clang diagnostic ignored "-Wexit-time-destructors"
```

Clang 警告"程序退出时调用析构函数顺序未定义"。ImGui 接受这个风险，因为它的全局对象（如某些静态字符串表）析构顺序问题在实践中不会触发——程序退出时整个进程都没了，析构跑不跑都行。

**对你的启示**：

- 当你把 ImGui 集成进引擎的 PCH（预编译头）时，可能要复制这些 pragma，否则你的代码会被 ImGui 的写法"传染"出一堆警告。
- 当你魔改 ImGui internal 时，如果遇到这些警告，**不要**把它当成"错误信号"——这是 ImGui 风格的一部分。

## 0.2.10 本章小结

让我们把全部 7 条"ImGui 风格规则"列出来：

1. **不依赖 STL**：自带 `ImVector`、`ImString` 替代品、`ImChunkStream` 等容器。
2. **不用异常**：所有错误用 `IM_ASSERT` 兜底，分配失败假装不会发生。
3. **不用 RTTI**：不存在 `dynamic_cast` / `typeid`，多态用函数指针 + enum 实现。
4. **模板克制**：仅用于"避免重复"（容器 / 助手函数 / Widget Behavior），不用 SFINAE / Concepts / Variadic。
5. **拥抱 static / global**：`GImGui` 全局上下文、static 函数、static 分配器函数指针。
6. **`memcpy` 一切**：所有容器假设元素 trivially relocatable，主动关闭 `-Wclass-memaccess` 警告。
7. **编译期配置**：所有 ABI 影响型开关在 `imconfig.h`，必须全工程一致，靠 `IMGUI_CHECKVERSION` 检查。

**这 7 条规则的共同主题**：**牺牲一点表达力，换取最大化的可移植性、可调试性和可控性**。

如果你想"用 modern C++ 的方式重写 ImGui"——很多人尝试过，做出来的库要么没人用，要么被吞并到大型框架里失去独立性。**ImGui 的工程取舍是它能成为事实标准的核心原因之一**。
