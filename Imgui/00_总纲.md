#### 第 0.2 章 · ImGui 的 C++ 子集：反 STL、无异常、模板克制
**文件名**：`02_第零部分_02_Cpp子集与模板克制.md`

> 这是理解 ImGui "为什么这样写代码"的钥匙，关系到你看到 `memcpy` 拷对象、看到 `IM_ASSERT` 替代异常、看到模板只在窄场景出现时的反应。

- **ImGui 用了 C++ 的哪个子集**：
  - 不依赖 STL（`imgui.h` 不 `#include <vector>`，自带 `ImVector`）
  - 不用异常（`-fno-exceptions` 友好；用 `IM_ASSERT` 兜底）
  - 不用 RTTI（`-fno-rtti` 友好；用枚举 + 函数表替代 vtable 类型识别）
  - 不用 `std::string`、不用 `std::shared_ptr`、不用 `std::function`（公开 API 一律 `void(*)(...)`）
- **模板使用边界与 ImGui 的"克制策略"**：
  - 简单泛型容器：`ImVector<T>` / `ImSpan<T>` / `ImPool<T>` / `ImChunkStream<T>` / `ImBitArray<BITCOUNT, OFFSET>` / `ImStableVector<T, BLOCKSIZE>`
  - 简单泛型函数：`ImMin/ImMax/ImClamp/ImLerp/ImSwap/ImAddClampOverflow/ImSubClampOverflow`（`imgui_internal.h:506-512`）
  - 算法模板：Widget Behavior 层的 3-模板参数函数 `ScaleRatioFromValueT<T, SIGNED_T, FLOAT_T>` / `DragBehaviorT` / `SliderBehaviorT`（`imgui_internal.h:3674-3679`）——为什么需要 3 个模板参数？因为 int/uint/float 的"中间运算"类型不同。
  - **不用的部分**：SFINAE / 概念（concepts）/ 折叠表达式 / 变参完美转发 / `if constexpr` 几乎不用。
- **错误处理范式**：`IM_ASSERT` 哲学、`IM_ASSERT_USER_ERROR` 与"软错误"、`ErrorRecoveryTryToRecoverState` 状态恢复机制。
- **静态/全局变量哲学**：`#pragma clang -Wexit-time-destructors` 关闭警告（`imgui.cpp:1276`）—— ImGui 主动接受静态对象，与"现代 C++ 反静态"的态度做了取舍。
- **写魔改代码的风格守则**：你的扩展代码应该遵守 ImGui 的代码风格还是引擎自己的？
- **对应源码**：`imgui.h` 顶部宏定义段、`imgui.cpp:[SECTION] FORWARD DECLARATIONS`、`imgui_internal.h:[SECTION] Generic helpers`、`imgui_internal.h:[SECTION] Widgets support: flags, enums, data structures` 中的 BehaviorT 函数族。

#### 第 0.3 章 · 内存模型 101：从栈堆对齐到 Trivially Relocatable
**文件名**：`03_第零部分_03_内存模型101.md`

> 这一章是 Ch 2 全部内容的**前置必读**。如果你看到 `memcpy(&dst, &src, sizeof(T))` 拷一个有非默认构造函数的对象会感到不安，就需要这一章。

- **栈 vs 堆 vs 数据段 vs 常量段**：每段的生命周期、可寻址范围、权限位。
- **对齐（alignment）与填充（padding）**：
  - `alignof(T)` / `alignas(N)` 的语义；`ImVec2` / `ImDrawVert` 为什么是 8 字节对齐而不是 16。
  - 结构体内"自然填充"的规则；`#pragma pack` 的代价。
  - GPU 顶点布局对齐与 CPU 端 `ImDrawVert` 的契约。
- **POD / Trivially Copyable / Trivially Relocatable** 三层概念辨析：
  - 标准定义、`std::is_trivially_copyable` / `std::is_standard_layout` 测试。
  - "Trivially Relocatable" 是 P1144 的概念，标准未正式纳入，但 ImGui **隐式假设它存储的所有 `ImVector<T>` 元素都是 trivially relocatable**——这就是为什么 `ImVector::resize()` 用 `memcpy` 而不是 `std::move`。
  - 哪些类型**违反**这个假设（含自指针、含 RAII 句柄）就不能放进 `ImVector`。
- **`malloc / realloc / free` 的契约与陷阱**：
  - `realloc` 何时原地扩展、何时 memcpy + free，与 `ImVector::reserve` 的协作。
  - 对齐分配（`_aligned_malloc` / `posix_memalign` / `std::aligned_alloc`）—— ImGui 不用，为什么？
- **placement new 与显式析构**：`IM_PLACEMENT_NEW(p) new(p)` 和 `p->~T()` 的语义；`ImPool` 如何用它实现"对象槽位复用"。
- **对象生命周期与 lifetime 规则**：C++17 之后访问"被 memcpy 过来"的对象算不算 UB，ImGui 的实践如何在标准灰区生存。
- **debug 内存分析钩子**：`g.DebugMemAllocCount` / `g.DebugMemFreeCount`（`imgui.cpp:692`），如何用它在你的引擎里做 ImGui 内存泄漏检测。
- **对应源码**：`imgui.h` 中 `IM_ALLOC` / `IM_FREE` / `IM_NEW` / `IM_DELETE` / `IM_PLACEMENT_NEW` 宏（约 `imgui.h:2193`）、`imgui.cpp:[SECTION] CONTEXT AND MEMORY ALLOCATORS`、`#pragma GCC -Wclass-memaccess`（`imgui_internal.h:107`）。

#### 第 0.4 章 · GPU 渲染管线 101：从 IB/VB 到屏幕，ImGui 在管线中的位置
**文件名**：`04_第零部分_04_GPU管线101.md`

> 这一章是 Ch 3 全部内容的**前置必读**。如果你对"PSO / Pipeline State / 命令缓冲 / 描述符" 等概念尚不清晰，先读这一章。

- **三大现代图形 API 的统一抽象**：OpenGL / Vulkan / DirectX 11/12 / Metal 在 ImGui 视角下的最小公倍数。
- **顶点输入装配（IA）阶段**：
  - 顶点缓冲（VB）/ 索引缓冲（IB）的物理意义。
  - 顶点格式（Input Layout / Vertex Attribute）：`ImDrawVert` 的 `pos(vec2) + uv(vec2) + col(uint32)` 三字段如何映射到三种 API。
  - `Index Type` 的 16-bit / 32-bit 选择与 `ImDrawListFlags_AllowVtxOffset` 的关系。
- **顶点着色器 → 光栅化 → 像素着色器**：每阶段读到什么、写到什么。
- **管线状态对象（PSO / Pipeline）**：
  - DX12/Vulkan 的"PSO 不可变"模型与 GL/DX11 的"状态机"模型差异。
  - ImGui 后端代码里"绑定 shader / 绑定混合状态 / 绑定深度模板状态"那几行的实质。
- **混合（Blending）状态**：ImGui 强制 `SrcAlpha, OneMinusSrcAlpha` 半透明混合，关闭深度测试，关闭面剔除——这些状态需要由你的后端保证。
- **纹理与采样器**：
  - `ImTextureID` 的本质：64-bit 不透明句柄（`uint64_t` / `void*`），引擎可以用作"GL handle"、"DX SRV pointer"、"Vulkan descriptor index"。
  - 1.92 引入的 `ImTextureRef` / `ImTextureData` / `ImGuiBackendFlags_RendererHasTextures`：动态纹理上传由谁负责。
  - 字体图集（Atlas）作为一张特殊纹理。
- **裁剪矩形（Scissor / ClipRect）**：`ImDrawCmd::ClipRect` 在屏幕空间的语义、Y 轴翻转问题、HiDPI 与 framebuffer 缩放。
- **命令缓冲（Command Buffer）模型**：DX11 即时模式 vs Vulkan 录制 + 提交 vs DX12 ExecuteCommandLists；ImGui 的 `RenderDrawData` 必须在哪个时机被调用。
- **多视口（Multi-Viewport）渲染**：ImGui 跨多个 OS 窗口时各自独立的 swap chain / framebuffer / cmd queue。
- **剖析样板**：把 `backends/imgui_impl_opengl3.cpp::ImGui_ImplOpenGL3_RenderDrawData` 与 `backends/imgui_impl_vulkan.cpp::ImGui_ImplVulkan_RenderDrawData` 并排对比，标出"哪些行是状态绑定 / 哪些行是数据上传 / 哪些行是 draw call"。
- **对应源码**：`backends/imgui_impl_opengl3.cpp` 全文、`backends/imgui_impl_vulkan.cpp` 中的 `RenderDrawData`、`imgui.h` 中 `ImDrawCmd` / `ImDrawVert` / `ImDrawData` / `ImTextureRef` 定义。

## 第六部分 · 多线程模型与引擎接缝设计 ⭐ 新增

> **本部分目标**：ImGui 是**显式单线程库**（仓库内有至少 5 处 `not thread-safe` / `FIXME-MULTITHREADING` 注释），但你的引擎大概率是多线程的。这一部分专门讲清两个问题——
> - **多线程基础**：内存模型 / data race / `thread_local` / 原子操作 / 内存序，是读懂 ImGui 注释的前置。
> - **接缝设计**：在 Hazel-style 多线程引擎里，ImGui 的调用应该被"夹"在哪两条线之间。

#### 第 6.1 章 · 多线程基础与 ImGui 单线程契约的源码证据
**文件名**：`23_第六部分_01_多线程契约源码证据.md`

- **C++ 多线程基础速通（最小够用集）**：
  - 数据竞争（data race）的定义与"未定义行为"后果；为什么"读 + 写无同步"= UB。
  - 内存序（`memory_order_relaxed/acquire/release/acq_rel/seq_cst`）：什么时候你需要更弱的序，什么时候必须 seq_cst。
  - `std::atomic<T>` 与无锁读写的边界。
  - `thread_local` / TLS（Thread Local Storage）的实现机制（fs/gs 段、`__declspec(thread)` 与 `_Thread_local`）。
  - 互斥量（`std::mutex` / `SRWLock` / `pthread_mutex`）与读写锁；spinlock 的代价。
  - 内存屏障（`std::atomic_thread_fence`）与 GPU 命令缓冲的"伪并发"。
- **ImGui 的单线程契约**——逐句剖析仓库注释：
  - `imgui.cpp:1427` "Dear ImGui functions are not thread-safe because of this pointer."
  - `imgui.cpp:1428-1433` 官方提供的 `thread_local GImGui` 定制方案（`#define GImGui MyImGuiTLS`），实测踩坑：DLL 边界、初始化顺序。
  - `imgui.cpp:10546` "FIXME-MULTITHREADING: io.AddKeyEvent() etc. calls are mostly thread-safe apart from the fact they push to this..."——为什么"几乎线程安全"还是不够。
  - `imgui.cpp:5145 / 5158` 多线程并行 Context 的实验性接口（issue #8069 / #6293 / #5856）。
  - `imgui.cpp:503-504` 字体子系统因为动态字形加载而**不再**线程安全。
- **`GImGui` 的物理本质**：默认是 `static ImGuiContext* GImGui = NULL;`（`imgui.cpp:1438`），单进程单上下文。
- **多 DLL / 多模块下的全局指针陷阱**：每个 DLL 都有自己的 `GImGui` 副本，必须用 `SetCurrentContext` 同步，或定义 `IMGUI_SET_CURRENT_CONTEXT_FUNC`（`imgui.cpp:4075`）。
- **Test Engine 与 Headless 模式下的多上下文模式**：N 线程 N Context 的官方推荐做法。
- **对应源码**：`imgui.cpp:[SECTION] CONTEXT AND MEMORY ALLOCATORS`、`imgui.cpp:[SECTION] INITIALIZATION, SHUTDOWN`、所有 `FIXME-MULTITHREADING` 与 `thread-safe` 注释。

#### 第 6.2 章 · 引擎多线程接缝：游戏线程 / 渲染线程 / 资源线程下的 ImGui 落位
**文件名**：`24_第六部分_02_引擎多线程接缝设计.md`

- **典型引擎线程模型回顾**：
  - 单线程（Hazel 当前默认） vs 双线程（Game/Render） vs N 线程（Job System）。
  - "命令缓冲 + 双缓冲"模型如何让渲染线程滞后游戏线程一帧。
- **ImGui 的强制约束**：
  - `NewFrame / EndFrame / Render` 必须在**同一线程**完成（且持有同一 Context）。
  - 中间所有 `Begin/End/Button/...` 也必须在同一线程。
  - **`RenderDrawData` 是唯一可以挪到别的线程的环节**——因为它只读 `ImDrawData`。
- **设计方案 A：UI 完全在主线程**（推荐起点）
  - 主线程既跑游戏逻辑、又跑 ImGui，渲染线程只消费 `ImDrawData`。
  - 双缓冲 `ImDrawData`：让渲染线程读"上一帧"的 DrawData，主线程写"当前帧"。
- **设计方案 B：UI 在专用 UI 线程**
  - 适用于编辑器主导的场景；UI 线程独立 Context，与游戏线程通过消息队列通信。
  - 输入事件的多生产者模型：所有输入源（OS 消息泵、Editor 自己的虚拟输入）必须串行化到 UI 线程。
- **设计方案 C：N 个独立 Context**（高级）
  - 编辑器主窗口 / Inspector 子工具 / 远程调试 web 端各自独立 Context。
  - `SetCurrentContext` 在每条线程启动时设置一次。
- **资源线程的接入**：纹理 / 字体异步加载完成后，如何把 `ImTextureID` 安全地交回 UI 线程使用（生产者-消费者队列）。
- **Hazel 集成实战**：在 `Application::Run()` 主循环里，给 `m_ImGuiLayer->Begin() / OnImGuiRender() / End()` 找正确的位置；如果将来引入渲染线程，diff 在哪里。
- **常见死锁与数据竞争清单**：
  - 在 `OnImGuiRender` 里持有渲染锁 → 绝对禁止
  - 在工作线程调用 `ImGui::Text` → UB
  - 跨帧持有 `ImGuiWindow*` → 跨帧期间窗口可能已被回收
  - `RenderDrawData` 与 `EndFrame` 同时执行 → 因为 `ImDrawData` 内部数组被复用
