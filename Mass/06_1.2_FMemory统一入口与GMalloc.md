# §1.2 FMemory 的统一入口 — Malloc / Realloc / Free 的转发表

> **本节地图**:模块一第 1 章第 2 节。§1.1 把"平台抽象"的骨架讲完,这一节落到**最基础的内存接口** — 整个 UE 引擎(包括所有容器、所有 UObject、所有 Mass Fragment)分配内存的唯一入口:`FMemory::Malloc / Realloc / Free`。
>
> 我们这一节要回答几个问题:
> - 为什么 UE 不让你直接用 `new` / `malloc`?
> - `FMemory::Malloc(100)` 到底跑了哪些代码?
> - 全局变量 `GMalloc` 是什么?它什么时候被创建?
> - `FMalloc` 抽象基类下面挂了多少种分配器?(具体每种的算法在 §1.4 详讲)
> - `FMemory::Memcpy` 比标准 `memcpy` 多做了什么?
>
> **预备知识**:§0.1 模块系统、§1.1 平台抽象层。
>
> **读完之后你能做到**:
> - 看到 `FMemory::Malloc(...)` 的调用,从源码层面知道它经过了哪几层转发、哪几个钩子
> - 知道 GMalloc 的类型、声明位置、初始化时机
> - 理解为什么 `class FMalloc : public FUseSystemMallocForNew` —— 这是个有趣的"鸡生蛋"解
> - 写自己的 `FMalloc` 子类(虽然你 99% 用不到,但理解后改 Engine 内存层不再害怕)
> - 知道 5.6+ 起 `GMalloc` 的"deprecated 写法"是什么意思,新代码该怎么写

## 1.2.1 浅入:为什么 UE 不让你随便 `new` / `malloc`

普通 C++ 教程里,你这么写:

```cpp
int32* P = new int32[1000];
delete[] P;

void* Buf = std::malloc(1024);
std::free(Buf);
```

这些**能跑**,但在 UE 工程代码里你**几乎看不到**。Epic Coding Standard 也明确写:**"Use FMemory::Malloc / Free instead of malloc / free, and TArray / TUniquePtr instead of new / delete."**

为什么?三个层面的理由:

### 1.2.1.1 性能层

操作系统的 `malloc` 是个**通用分配器**,要兼顾任意线程数、任意分配大小、任意分配频率,通常带一把全局锁(或多线程下分桶但仍有锁竞争)。

UE 自家分配器(`MallocBinned2 / MallocBinned3` —— §1.4 详讲)针对游戏的分配模式做了大量特化:
- 大量"几十字节"的 short-lived 小对象 → 走 SmallPool,几条指令出结果
- TLS 线程本地缓存 → 多数 alloc/free 不锁
- 大块内存(KB 级别)直接走 OS,不污染 SmallPool
- 内置内存分配 trace、LLM tag、leak detector 钩子

你直接 `malloc`,这些**全部失效**。Mass 数万 entity 的分配/释放压力下,差距能到几个数量级。

### 1.2.1.2 工具层

UE 的内存调试工具(LLM、Memory Insights、`stat memory`、`memreport`)**全部**靠 hook FMemory 入口。你绕过 FMemory 直接 malloc,这些工具看不到你的内存,你后期排查泄漏就只能裸奔。

### 1.2.1.3 一致性层

UE 自己的对象(UObject、TArray、TMap、FString)**全部**走 FMemory。如果你项目代码混用 `new` 和 `FMemory`,那么:
- 你 `new` 出来的指针不能交给 UE 容器接管
- 跨模块对象生命周期管理变乱
- AutoRTFM 之类的高级特性失效

**纪律**:RTS 项目代码 100% 用 `FMemory` / `TArray` / `TUniquePtr` / `MakeShared`。`new` / `malloc` 仅在调用第三方 C 库不得已时使用,**且必须用 `FMemory::SystemMalloc` 而不是 `std::malloc`**(§1.2.6 详讲)。

## 1.2.2 `FMemory` 是什么 —— 它是个零成本的转发器

打开 `Engine/Source/Runtime/Core/Public/HAL/UnrealMemory.h`,你会看到 `FMemory` 是一个**纯静态函数家族**:

```cpp
// HAL/UnrealMemory.h:93
struct FMemory
{
    enum AllocationHints { None = -1, Default, Temporary, SmallPool, Max };

    // 内存操作(全部 inline 转发到 FPlatformMemory)
    static UE_FORCEINLINE_HINT void* Memmove(void* Dest, const void* Src, SIZE_T Count) { return FPlatformMemory::Memmove(Dest, Src, Count); }
    static UE_FORCEINLINE_HINT int32 Memcmp (const void* B1,  const void* B2,  SIZE_T Count) { return FPlatformMemory::Memcmp (B1, B2, Count); }
    static UE_FORCEINLINE_HINT void* Memset (void* Dest, uint8 C, SIZE_T Count) { return FPlatformMemory::Memset(Dest, C, Count); }
    static UE_FORCEINLINE_HINT void* Memzero(void* Dest, SIZE_T Count) { return FPlatformMemory::Memzero(Dest, Count); }
    static UE_FORCEINLINE_HINT void* Memcpy (void* Dest, const void* Src, SIZE_T Count) { return FPlatformMemory::Memcpy(Dest, Src, Count); }
    static UE_FORCEINLINE_HINT void* BigBlockMemcpy(void* Dest, const void* Src, SIZE_T Count);
    static UE_FORCEINLINE_HINT void* StreamingMemcpy(void* Dest, const void* Src, SIZE_T Count);
    static UE_FORCEINLINE_HINT void* ParallelMemcpy(void* Dest, const void* Src, SIZE_T Count, EMemcpyCachePolicy Policy = EMemcpyCachePolicy::StoreCached);
    static UE_FORCEINLINE_HINT void  Memswap(void* Ptr1, void* Ptr2, SIZE_T Size);

    // C 风格分配器(系统 malloc,绕过 GMalloc)
    UE_ALLOCATION_FUNCTION(1) static inline void* SystemMalloc(SIZE_T Size);
    static inline void SystemFree(void* Ptr);

    // 主分配接口(转发到 GMalloc)
    UE_ALLOCATION_FUNCTION(1, 2) static FORCENOINLINE CORE_API void* Malloc      (SIZE_T Count, uint32 Alignment = DEFAULT_ALIGNMENT);
    UE_ALLOCATION_FUNCTION(2, 3) static FORCENOINLINE CORE_API void* Realloc     (void* Original, SIZE_T Count, uint32 Alignment = DEFAULT_ALIGNMENT);
    static FORCENOINLINE CORE_API void   Free        (void* Original);
    UE_ALLOCATION_FUNCTION(1, 2) static FORCENOINLINE CORE_API void* MallocZeroed(SIZE_T Count, uint32 Alignment = DEFAULT_ALIGNMENT);
    static FORCENOINLINE CORE_API SIZE_T GetAllocSize(void* Original);
    static FORCENOINLINE CORE_API SIZE_T QuantizeSize(SIZE_T Count, uint32 Alignment = DEFAULT_ALIGNMENT);

    // TLS 缓存生命周期(§1.5 详讲)
    static CORE_API void Trim(bool bTrimThreadCaches = true);
    static CORE_API void SetupTLSCachesOnCurrentThread();
    static CORE_API void ClearAndDisableTLSCachesOnCurrentThread();
    static CORE_API void MarkTLSCachesAsUsedOnCurrentThread();
    static CORE_API void MarkTLSCachesAsUnusedOnCurrentThread();

    // 显式初始化 GMalloc(§1.3)
    static CORE_API void ExplicitInit(FMalloc& Allocator);

    // 启动期 fallback(GMalloc 还没建好时用)
    static CORE_API void* MallocExternal(SIZE_T Count, uint32 Alignment = DEFAULT_ALIGNMENT);
    static CORE_API void* ReallocExternal(void* Original, SIZE_T Count, uint32 Alignment = DEFAULT_ALIGNMENT);
    static CORE_API void  FreeExternal  (void* Original);

private:
    static CORE_API void GCreateMalloc();    // 创建 GMalloc 的私有入口
};
```

**两类成员函数,要分清**:

1. **`Memcpy / Memset / ...` 这些**:`UE_FORCEINLINE_HINT` 修饰,直接转发到 `FPlatformMemory::*`。**编译期内联,零运行时开销**。它们不分配内存,只操作已有的内存块。

2. **`Malloc / Realloc / Free / MallocZeroed`**:`FORCENOINLINE CORE_API`,这意味着它们**不内联**(故意的),并且作为 Core 模块的导出符号。它们是 GMalloc 的转发器。

为什么 Malloc 系列要 `FORCENOINLINE`?为了**减少代码膨胀**。整个引擎里 Malloc 调用点有几十万个,如果全部内联会让 .text 段爆炸。FORCENOINLINE 让它退化成普通函数调用,但内部的真正工作(`GMalloc->Malloc`)仍然是个虚函数调用,所以这层调用开销可以忽略。

## 1.2.3 `FMemory::Malloc` 实际跑了哪些代码

### Step 1 — 用户调 `FMemory::Malloc`

```cpp
void* Ptr = FMemory::Malloc(1024, 16);
```

跳到 `Engine/Source/Runtime/Core/Private/HAL/UnrealMemory.cpp:675`:

```cpp
// UnrealMemory.cpp:675
void* FMemory::Malloc(SIZE_T Count, uint32 Alignment)
{
    return FMemory_MallocInline(Count, Alignment);
}
```

非常简短。继续追 `FMemory_MallocInline`。

### Step 2 — `FMemory_MallocInline`

定义在 `Engine/Source/Runtime/Core/Public/HAL/FMemory.inl:17`(注意是 `.inl` 文件,作为 inline 实现给 `UnrealMemory.cpp` 包含使用):

```cpp
// HAL/FMemory.inl:17
FORCEINLINE void* FMemory_MallocInline(SIZE_T Count, uint32 Alignment)
{
    void* Ptr = AutoRTFM::Open([Count, Alignment]
    {
        void* Alloc = nullptr;
        if (UNLIKELY(!FMEMORY_INLINE_GMalloc))
        {
            // 启动期 fallback(GMalloc 还没创建)
            Alloc = FMemory::MallocExternal(Count, Alignment);
        }
        else
        {
            DoGamethreadHook(0);                        // (a)
            FScopedMallocTimer Timer(0);                // (b)
            Alloc = FMEMORY_INLINE_GMalloc->Malloc(Count, Alignment);   // (c) 真正的分配
        }
        // (d) LLM 内存追踪
        LLM_IF_ENABLED(FLowLevelMemTracker::Get().OnLowLevelAlloc(
            ELLMTracker::Default, Alloc, Count, ELLMTag::Untagged, ELLMAllocType::FMalloc));
        return Alloc;
    });

    // AutoRTFM 事务回滚的延迟 free
    AutoRTFM::OnAbort([Ptr] { FMemory::Free(Ptr); });

    return AutoRTFM::DidAllocate(Ptr, Count);
}
```

把这一段拆开:

**(a) `DoGamethreadHook(0)`** — Stat 钩子。如果 `STATS` 开启,会调用 `DoGamethreadHook` 累加分配计数到 stat 系统(`stat memory` 显示的就是这些)。Shipping 通常关掉,内联消失。

**(b) `FScopedMallocTimer Timer(0)`** — 计时钩子。如果 `TIME_MALLOC` 开启(默认 0,只在调试期手动开),会用 `FPlatformTime::Cycles64()` 测这次分配的耗时。Shipping 0 开销。

**(c) `FMEMORY_INLINE_GMalloc->Malloc(Count, Alignment)`** — 真正的分配。
   - `FMEMORY_INLINE_GMalloc` 是个宏,在 `UnrealMemory.cpp` 编译时被定义为 `GMalloc`(具体在 `UnrealMemory.cpp` 顶部 `#define FMEMORY_INLINE_GMalloc UE::Private::GMalloc`)。
   - 这是一个**虚函数调用**(因为 `GMalloc` 是 `FMalloc*`,而 `FMalloc::Malloc` 是 pure virtual)。
   - 实际分配工作在具体分配器(MallocBinned2/3/TBB 等)里完成。

**(d) LLM 追踪** — `LLM_IF_ENABLED` 是宏,启动加 `-llm` 才生效。生效时记录这块内存属于哪个 LLM tag(供 `stat llm` 显示)。

**(e) AutoRTFM** — 5.x 新增的"事务内存"框架(`Engine/Source/Runtime/Core/Public/AutoRTFM.h`)。如果当前在事务里(`AutoRTFM::IsClosed()`):
   - 分配在 "Open" 闭包里执行(分配器内部状态不被纳入事务)
   - `OnAbort` 注册一个回调:如果事务回滚,把这块新分配的内存释放掉
   - `DidAllocate` 通知 AutoRTFM "这块内存归本事务所有"

**对你 RTS 的实际影响**:99% 的 game 代码不在 AutoRTFM 事务里,这一段代码会全部 inline 优化为零开销。AutoRTFM 是为某些特殊系统(如 multiplayer rollback)预留的,你可以不深究 — 但要知道它存在,以防你看 .asm 输出时疑惑"这堆 lambda 哪儿来的"。

### Step 3 — `GMalloc->Malloc` 的真实身份

`GMalloc` 在 `Engine/Source/Runtime/Core/Public/HAL/MemoryBase.h:36-39` 声明:

```cpp
// HAL/MemoryBase.h:36
namespace UE::Private
{
    CORE_API extern TSAN_ATOMIC(class FMalloc*) GMalloc;
}

// HAL/MemoryBase.h:46(deprecated 别名)
UE_DEPRECATED(5.6, "Consider using FMemory::Malloc instead of accessing GMalloc directly.")
CORE_API extern class FMalloc* const& GMalloc;
```

读这段:
- **真正的 `GMalloc` 在 `UE::Private` 命名空间**,类型是 `TSAN_ATOMIC(FMalloc*)`(在普通构建下退化为 `FMalloc*`,在 TSan 构建下变成 `std::atomic<FMalloc*>` 防止数据竞争误报)。
- **全局命名空间的 `GMalloc`** 是个**引用别名**,指向 `UE::Private::GMalloc`。**5.6 起官方建议不要再直接用它**,改用 `FMemory::Malloc`。

为什么 5.6 要做这个 deprecation?因为直接 `GMalloc->Malloc(...)` 绕过 LLM 追踪、AutoRTFM 集成、stat 钩子等。`FMemory::Malloc` 是带这些"周边设施"的入口,`GMalloc->Malloc` 是裸入口。

**对你 RTS 项目**:**绝不**直接 `GMalloc->Malloc`。永远 `FMemory::Malloc`。看到老代码用 `GMalloc->Malloc` 就是技术债标记。

### Step 4 — `FMalloc` 抽象基类

`Engine/Source/Runtime/Core/Public/HAL/MemoryBase.h:96`:

```cpp
class FMalloc :
    public FUseSystemMallocForNew,
    public FExec
{
public:
    virtual void* Malloc(SIZE_T Count, uint32 Alignment = DEFAULT_ALIGNMENT) = 0;
    CORE_API virtual void* TryMalloc(SIZE_T Count, uint32 Alignment = DEFAULT_ALIGNMENT);
    virtual void* Realloc(void* Original, SIZE_T Count, uint32 Alignment = DEFAULT_ALIGNMENT) = 0;
    virtual void  Free(void* Original) = 0;
    virtual bool  GetAllocationSize(void* Original, SIZE_T& SizeOut) { return false; }
    virtual SIZE_T QuantizeSize(SIZE_T Count, uint32 Alignment) { return Count; }
    virtual bool  ValidateHeap() { return true; }
    virtual void  Trim(bool bTrimThreadCaches) {}
    virtual void  SetupTLSCachesOnCurrentThread() {}
    virtual void  GetAllocatorStats(FGenericMemoryStats& out_Stats) {}
    virtual void  DumpAllocatorStats(class FOutputDevice& Ar) {}
    virtual const TCHAR* GetDescriptiveName() = 0;
    // ... 等等 ...
};
```

注意几点:

1. **`Malloc / Realloc / Free` 是纯虚**。每个子类必须实现。
2. **`TryMalloc` 不是纯虚**。基类有默认实现:调 `Malloc`,如果失败再处理。
3. **`SetupTLSCachesOnCurrentThread` 是空的虚函数**。`MallocBinned2/3` 会重写它(`§1.5` 讲)。
4. **`GetAllocationSize` 默认返回 false**。意味着不是所有分配器都能告诉你"这块内存当初要了多少"。MallocBinned 系列能,MallocAnsi 不能。

打开 `Engine/Source/Runtime/Core/Public/HAL/`:

每个文件里都有一个 `class FMallocXxx : public FMalloc { ... };`。它们的算法、性能、用途差异很大,§1.4 会逐一拆。本节只需要知道:

- 主分配器(实际跑 game 时 GMalloc 指向的对象)由 `FPlatformMemory::BaseAllocator()` 选择。Win64 默认 `FMallocBinned2` 或 `FMallocBinned3`(取决于编译标志)。
- **Proxy 类**(MallocPoisonProxy / MallocStomp / MallocCallstackHandler / MallocLeakDetection)不是真正的分配器,而是"装饰器" — 包一层在主分配器外面,给每次 alloc/free 加额外检查。命令行 `-stompmalloc` / `-poisonmalloc` 之类启用。

## 1.2.4 `FUseSystemMallocForNew` —— 解开"鸡生蛋"

`FMalloc` 类**自己**继承了 `FUseSystemMallocForNew`(`MemoryBase.h:96`)。看下 `FUseSystemMallocForNew`(`MemoryBase.h:61`):

```cpp
class FUseSystemMallocForNew
{
public:
    CORE_API void* operator new   (size_t Size);
    CORE_API void  operator delete(void* Ptr);
    void* operator new[]  (size_t Size);
    void  operator delete[](void* Ptr);
};
```

实现在 `UnrealMemory.cpp`:

```cpp
// UnrealMemory.cpp:660-672(简化)
void  FUseSystemMallocForNew::operator delete  (void* Ptr) { FMemory::SystemFree(Ptr); }
void* FUseSystemMallocForNew::operator new   [](size_t Size){ return FMemory::SystemMalloc(Size); }
void  FUseSystemMallocForNew::operator delete[](void* Ptr) { FMemory::SystemFree(Ptr); }
```

`FMemory::SystemMalloc / SystemFree` 直接调 `::malloc / ::free`(C 运行时):

```cpp
// UnrealMemory.h:195
UE_ALLOCATION_FUNCTION(1) static inline void* SystemMalloc(SIZE_T Size)
{
    void* Ptr = ::malloc(Size);
    MemoryTrace_Alloc(uint64(Ptr), Size, 0, EMemoryTraceRootHeap::SystemMemory);
    return Ptr;
}

static inline void SystemFree(void* Ptr)
{
    MemoryTrace_Free(uint64(Ptr), EMemoryTraceRootHeap::SystemMemory);
    ::free(Ptr);
}
```

**为什么要这么设计?** 这是个经典的"鸡生蛋"问题:

1. UE 想让所有分配走 `GMalloc`(我们刚才看到的 `FMemory::Malloc` 转发链)。
2. 但 `GMalloc` 本身是个 `FMalloc*`,**它指向的对象也是要分配出来的**。
3. 如果用 `new FMallocBinned2()` 分配 `FMallocBinned2` 自己,这个 `new` 又会回到 `FMemory::Malloc` → `GMalloc->Malloc` —— `GMalloc` 还没创建,炸。

解法:让 `FMalloc` 这个**抽象基类自身的 new/delete** 走系统 `malloc / free`,绕过 GMalloc。所以所有 `FMalloc` 子类(`FMallocBinned2 / FMallocAnsi / ...`)的对象都用系统 malloc 分配,跟 GMalloc 没关系。

**实战时你什么时候要继承 `FUseSystemMallocForNew`**?
- 你写自定义 `FMalloc` 的代理类
- 你的对象需要在 GMalloc 还未就绪的极早期被构造(LoadingPhase = EarliestPossible 的某些场景)
- 你的对象与 GMalloc 之间存在依赖循环

99% 的项目代码用不到。但看到 Engine 代码里某个类继承 `FUseSystemMallocForNew`,你要立刻知道"哦它是底层基础设施,生命周期早于 GMalloc"。

## 1.2.5 `MallocExternal` —— 启动期 fallback

回到 `FMemory_MallocInline`,有这段:

```cpp
if (UNLIKELY(!FMEMORY_INLINE_GMalloc))
{
    Alloc = FMemory::MallocExternal(Count, Alignment);
}
```

**含义**:GMalloc 还没创建时(进程刚启动,`FEngineLoop::PreInit` 还没跑到分配器初始化那一步),走 `MallocExternal`。

`MallocExternal` 实现在 `UnrealMemory.cpp`,大致:

```cpp
void* FMemory::MallocExternal(SIZE_T Count, uint32 Alignment)
{
    if (!UE::Private::GMalloc)
    {
        GCreateMalloc();        // 触发 GMalloc 的延迟创建
    }
    return UE::Private::GMalloc->Malloc(Count, Alignment);
}
```

**`GCreateMalloc()`** 是 `FMemory` 的 `private` 静态方法(`UnrealMemory.h:284`)。它是**唯一**会创建 `GMalloc` 的地方,内部调用 `FPlatformMemory::BaseAllocator()` 决定具体类型,然后构造之。**这是 §1.3 的主题**,这里只占位。

**结论**:进程一启动,任何代码(甚至**比 main 还早**的全局静态变量构造里)用 `FMemory::Malloc` 都安全。第一次调用会通过 `MallocExternal → GCreateMalloc` 把 GMalloc 现场建好,后续分配走主路径。

这就是为什么 UE 容器(TArray、FString)能在 `static FString GFoo = TEXT("hello");` 这种全局静态变量里安全初始化 —— `FString` 的构造函数里会调 `FMemory::Malloc`,即使此时 main 还没开始,fallback 路径也能工作。

## 1.2.6 `FMemory::SystemMalloc` 与 `std::malloc` 的区别

`FMemory::SystemMalloc(Size)` 看起来就是包了一层 `::malloc`,有什么意义?三件事:

1. **MemoryTrace 集成**:加一行 `MemoryTrace_Alloc(...)`,让 Insights Memory 面板能看到这块内存(走 `SystemMemory` root heap,与 `GMalloc` 分开统计)。
2. **跨平台一致性**:某些平台 `::malloc` 不存在或行为不同(主机平台),`FMemory::SystemMalloc` 帮你抹平。
3. **未来切换灵活性**:如果某天 Epic 想替换底层"系统级分配"路径(比如换成 mimalloc 直接接 OS),改一处即可。

**纪律**:你绕过 GMalloc 用系统 malloc 时(典型场景:第三方 C 库要求你提供 malloc/free 回调),**用 `FMemory::SystemMalloc / SystemFree`**,不要直接 `::malloc / ::free`。

## 1.2.7 `FMemory::Memcpy / Memset / Memzero` 的 SIMD 路径

这些函数定义在 `UnrealMemory.h:109-190`:

```cpp

{
    return FPlatformMemory::Memcpy(Dest, Src, Count);
}

static UE_FORCEINLINE_HINT void* BigBlockMemcpy(void* Dest, const void* Src, SIZE_T Count)
{
    return FPlatformMemory::BigBlockMemcpy(Dest, Src, Count);
}

static UE_FORCEINLINE_HINT void* StreamingMemcpy(void* Dest, const void* Src, SIZE_T Count)
{
    return FPlatformMemory::StreamingMemcpy(Dest, Src, Count);
}

static UE_FORCEINLINE_HINT void* ParallelMemcpy(void* Dest, const void* Src, SIZE_T Count, EMemcpyCachePolicy Policy = EMemcpyCachePolicy::StoreCached)
{
    return FPlatformMemory::ParallelMemcpy(Dest, Src, Count, Policy);
}
```

四个变体的用途:

| 函数 | 适用场景 |
|---|---|
| `Memcpy` | 默认。短到中等大小,延迟敏感。 |
| `BigBlockMemcpy` | 大块(MB 级),跨页读写。Win64 实现里走非临时存储指令 / `_mm_stream_si128`,避免污染缓存。 |
| `StreamingMemcpy` | 类似 BigBlock,但更激进地走 streaming store。 |
| `ParallelMemcpy` | 把大块切成多份,多线程并行 copy。**Mass / 渲染上传 buffer 时常用**。 |

每个变体的实际 SIMD 实现在 `Windows/WindowsPlatformMemory.cpp` 等平台特化里。Windows 平台 `Memcpy` 通常调用 MSVC 内置的 `__movsb` / `memcpy` —— 后者已经被编译器特化为 SSE4.1 / AVX 路径(取决于 `/arch` 设置)。

### 1.2.7.1 模板版本(类型安全)

```cpp
// UnrealMemory.h:165
template<class T>
static inline void Memcpy(T& Dest, const T& Src)
{
    static_assert(!TIsPointer<T>::Value, "For pointers use the three parameters function");
    Memcpy(&Dest, &Src, sizeof(T));
}
```

可以这样用:

```cpp
FVector A, B;
FMemory::Memcpy(A, B);    // 等价 FMemory::Memcpy(&A, &B, sizeof(FVector))
```

`static_assert` 防止你把指针误传(`int* P, *Q; FMemory::Memcpy(P, Q);` 大概率是 bug —— 你想 copy 指针指向的内容,而不是指针本身)。

### 1.2.7.2 `Memzero` 的特殊性

`Memzero(Dest, Count)` 等价于 `Memset(Dest, 0, Count)`,但**为什么单独写一个**?

两个理由:

1. **API 表达力**:`Memzero(Buf, sizeof(Buf))` 比 `Memset(Buf, 0, sizeof(Buf))` 意图更清晰。
2. **平台优化空间**:某些平台 `Memzero` 可以走专用的"清零"指令(`stosb` 之类),比通用 `Memset` 略快。当前 Windows 实现里两者基本一样,但接口预留了空间。

### 1.2.7.3 `MemIsZero` —— 检测全零(常用)

```cpp
// UnrealMemory.h:137
static inline bool MemIsZero(const void* Ptr, SIZE_T Count)
{
    uint8* Start = (uint8*)Ptr;
    uint8* End = Start + Count;
    while (Start < End)
    {
        if ((*Start++) != 0) return false;
    }
    return true;
}
```

**当前实现是字节级 scalar**(注释还写着 "first pass implementation")。在 Mass Fragment 的 zero-init 检查上,**如果你**调用频繁,自己写个 SIMD 版本会更快。但调用频率不高时(每次 spawn 才检查一次),scalar 完全够用。

### 1.2.7.4 RTS 视角下的 Memcpy 选择

| 场景 | 用什么 |
|---|---|
| Fragment 拷贝(数十字节) | `Memcpy`(默认) |
| Archetype 间 entity 迁移(KB 级 chunk 切片) | `Memcpy` |
| 上传 ISMC 实例 buffer 到 GPU(MB 级,几千个矩阵) | `ParallelMemcpy` 或自己手写 SIMD |
| Replay 系统的录制大块数据(MB 级,一次性,绝不重读) | `StreamingMemcpy`(避免污染 L3 缓存) |
| 网络发包前序列化大 buffer | `Memcpy`(数据小) |

## 1.2.8 `FMemory::QuantizeSize` —— 容器扩容的省内存技巧

```cpp
// UnrealMemory.cpp:700
SIZE_T FMemory::QuantizeSize(SIZE_T Count, uint32 Alignment)
{
    return FMemory_QuantizeSizeInline(Count, Alignment);
}
```

这个不太起眼的函数,**对容器至关重要**。

意思:**"如果我请求 Count 字节,分配器实际会给我多少?"**(不是承诺多少,是真给多少)

举例:`MallocBinned2` 的 SmallPool 把分配按 BinSize 表对齐(32 / 48 / 64 / 80 / 96 / 112 / 128 / ...)。你请求 33 字节,实际拿到 48 字节那个 bin。`QuantizeSize(33, 0)` 返回 48。

**TArray 利用这个做扩容**:

```cpp
// 伪代码:TArray 扩容时
SIZE_T Wanted = NumElements + Growth;
SIZE_T BytesWanted = Wanted * sizeof(T);
SIZE_T BytesActual = FMemory::QuantizeSize(BytesWanted, alignof(T));
// 既然分配器反正给我 BytesActual 字节,我就用足
Capacity = BytesActual / sizeof(T);
```

这避免了"申请 100 字节实际拿 128 字节,但容器只用 100" 的浪费。Mass chunk 计算容量时也用类似机制,后面 §17 会再讲。

**对你**:写自定义容器时,扩容代码里加 `QuantizeSize` 一行,免费拿到这个优化。

## 1.2.9 `UE_ALLOCATION_FUNCTION` —— 编译器属性提示

注意 `Malloc / Realloc / MallocZeroed` 都被 `UE_ALLOCATION_FUNCTION(...)` 修饰:

```cpp
UE_ALLOCATION_FUNCTION(1, 2) static FORCENOINLINE CORE_API void* Malloc(SIZE_T Count, uint32 Alignment = DEFAULT_ALIGNMENT);
```

这是个宏,展开后给编译器加上 GCC `__attribute__((alloc_size(1, 2)))` 之类的属性,告诉编译器:
- 这个函数返回一个新分配的内存指针(可用于 alias 分析)
- 第 1 参数(Count)和第 2 参数(Alignment)决定分配大小

好处:
- AddressSanitizer / UBSan 能更精确地检测越界
- 编译器优化器知道返回的指针不与已有对象 alias
- 内存调试工具(Valgrind)能更精准报告

你**不需要**直接用这个宏,但理解它的存在能解释一些反汇编里多出来的"奇怪"行为。

## 1.2.10 `ExplicitInit` —— 显式注入分配器(高级)

```cpp
// UnrealMemory.h:273
static CORE_API void ExplicitInit(FMalloc& Allocator);
```

这个 API 让你**手动指定** GMalloc 是哪个 `FMalloc` 实例,不走默认的 `FPlatformMemory::BaseAllocator()` 选择路径。

**用途**(罕见):
- 你写了一个自定义的 `FMalloc` 子类(比如对接你公司的内存追踪系统),想替换默认的
- 你做内存测试,想强制用 `MallocAnsi` 或 `MallocStomp`
- 你做工具程序(commandlet),想用最简单的分配器减小复杂度

**纪律**:必须在**最早期**调用,且只能一次。一旦 GMalloc 有过一次 alloc 操作,再切换会泄漏全部已分配内存。配合命令行参数 `-no-lazy-alloc` 和适当宏才能保证安全。

**对你 RTS 项目**:99.99% 用不到。但你想把"内存泄漏检测"或"自定义 LLM 标签"做到极致时,ExplicitInit 是个口子。

## 1.2.11 一个完整的"分配-使用-释放"反汇编预期

把上面所有内容串起来。当你写:

```cpp
void* P = FMemory::Malloc(1024, 16);
FMemory::Memzero(P, 1024);
FMemory::Free(P);
```

在 Development 构建下,这段 C++ 实际执行:

```
FMemory::Malloc(1024, 16)
  → call FMemory::Malloc                       ; FORCENOINLINE,真函数调用
    → FMemory_MallocInline 内联展开:
      check FMEMORY_INLINE_GMalloc != nullptr  ; 通常 true
      DoGamethreadHook(0)                       ; STATS 关时空函数
      FScopedMallocTimer ctor                   ; TIME_MALLOC=0 时空对象
      call GMalloc->Malloc(1024, 16)            ; 虚函数调用 FMallocBinned2::Malloc
        → MallocBinned2 内部:
          - SmallPool 路径(<=32KB):
            - TLS cache 命中? 直接返回(无锁)
            - TLS miss → 全局 free list → 分配
          - LargePool 路径(>32KB,本例 1024 不走这里):
            - VirtualAlloc / mmap
      LLM_IF_ENABLED                            ; -llm 关时 0 开销
      AutoRTFM::OnAbort 注册                    ; 非事务模式 0 开销
    return P
  ret

FMemory::Memzero(P, 1024)
  → 全 inline 展开为 FPlatformMemory::Memzero(P, 1024)
    → Windows: __stosq + cleanup loop
       (或在 SSE2 路径下走 _mm_storeu_si128 循环)

FMemory::Free(P)
  → call FMemory::Free
    → FMemory_FreeInline 内联展开:
      if (!P) return
      AutoRTFM::OnCommit lambda:
        LLM_IF_ENABLED
        DoGamethreadHook(2)
        call GMalloc->Free(P)                   ; 虚函数 FMallocBinned2::Free
          → SmallPool 路径:推回 TLS cache(无锁)
  ret
```

**关键观察**:
- 主路径只有**一次虚函数调用**(GMalloc->Malloc)
- 大量"钩子"(stat、timer、LLM、AutoRTFM)在 Shipping / Test 下编译期消失
- TLS cache 命中时**完全无锁**,这就是 Mass 数十万 entity 频繁分配仍能保持高吞吐的根基

**Shipping 构建下,FMemory::Malloc 的实际开销 ≈ 一次虚函数调用 + 一次 TLS 查表 + 几条 ALU 指令**。这是非常便宜的。

## 1.2.12 RTS 实战:你需要直接用 FMemory 的场景

99% 的代码你**不会**直接 `FMemory::Malloc`。你用 `TArray` / `TMap` / `FString` / `MakeShared`,它们内部都走 FMemory。

**你会直接用 FMemory 的少数场景**:

### 场景 1 — 跨模块 buffer 传递

C 风格 API,buffer 由调用者分配:

```cpp
// 接收方:把分配出来的 buffer 交回去
void* Buf = FMemory::Malloc(SerializedSize);
SerializeIntoBuffer(Buf, SerializedSize);
return Buf;          // 调用方负责 FMemory::Free
```

### 场景 2 — 你自己写容器 / 内存池

```cpp
// 简化示意
class FMassChunkAllocator
{
    void* Allocate(SIZE_T Size, SIZE_T Align)
    {
        return FMemory::Malloc(Size, Align);
    }
    void Deallocate(void* Ptr) { FMemory::Free(Ptr); }
};
```

这种自定义池往往再封装一层 TLS / SLAB 等优化,但底层一定走 FMemory。

### 场景 3 — placement new + Memzero

Mass 创建 entity 时,需要在已分配的 chunk 内存上**就地构造** Fragment:

```cpp
void* FragmentPtr = ChunkData + FragmentOffset;
FMemory::Memzero(FragmentPtr, sizeof(FMyFragment));    // 先清零
new (FragmentPtr) FMyFragment();                        // placement new
```

这是 §17 讲 Mass chunk 数据初始化时的姿势。

### 场景 4 — Memcpy 大块数据

```cpp
FMemory::Memcpy(GPUUploadBuffer, Transforms.GetData(), Transforms.Num() * sizeof(FMatrix));
```

ISMC 上传、网络发包、replay 录制时常见。

## 1.2.13 与 Mass 重构的对照思考

### (1)Mass chunk 走 FMemory

`FMassArchetypeChunk` 的内存(默认 ~128KB / chunk)用 `FMemory::Malloc(ChunkSize, ALIGN)` 分配。不是 OS 直接 mmap,**也不是**自定义池。这意味着:
- 所有 LLM / Memory Insights 工具能看到 Mass 内存
- 走主分配器(MallocBinned3),拥有 TLS cache 加速
- 跟其它系统共享分配器统计

**对你的影响**:RTS 项目"加 Mass 内存"和"加 UObject 内存"在 Insights 里**不区分**,默认全混在一起。要分开统计,你需要自己加 LLM tag(后面讲)。

### (2)Fragment 是平凡数据,但分配走 FMemory

Mass Fragment 是 `USTRUCT`(其实是 `USTRUCT` + 反射 + POD-like)。每个 entity 创建时,fragment 数据**就地构造**在 chunk 里,不单独 malloc。但是:
- chunk 本身是 FMemory::Malloc 出来的
- chunk 容量满了,创建新 chunk 又是一次 FMemory::Malloc
- 销毁 archetype 时 chunk 释放走 FMemory::Free

所以 Fragment 频繁创建 / 销毁,FMemory 压力来自 **chunk 级**(数量级 O(数千 chunk))而不是 **entity 级**(O(数十万 entity))。这是 SoA + chunked 内存的精髓。

### (3)避免 TArray 在 Mass 数据循环里频繁 reallocate

如果你 Processor 内部有一个 `TArray<int32> TempBuffer;`,每个 chunk 都 `TempBuffer.Reset(); TempBuffer.Reserve(N);`,这里的 Reset / Reserve 仍是 FMemory 调用。

**纪律**:
- 把 TempBuffer 作为 Processor 的成员变量,跨帧复用,只 `Reset` 不 `Empty`(`Reset` 不 dealloc,`Empty` 缩回 0)。
- 或用 `TInlineAllocator<N>` 让小数组栈分配(§1.6 讲)。

### (4)RTS 的内存可观测性

我建议**第一周**就加上:

```cpp
// 在 RTS 主模块启动时
LLM(LLM::RegisterTag("RTS/Mass", ...));
LLM(LLM::RegisterTag("RTS/Net", ...));
LLM(LLM::RegisterTag("RTS/Render", ...));

// Processor 入口
LLM_SCOPE_BYNAME("RTS/Mass");
```

这样 `stat llm` 立刻能看到 RTS 各部分各占多少。**这个习惯越早建立越好** — 等到上线前 30 天才发现"Mass 占 800MB 内存,但不知道哪个 fragment 大",代价就很高。
