# §3.2 GUObjectArray 的 chunked 内存布局

> **本节地图**:模块一第 3 章第 2 节。§3.1 已经看到 `UObjectBase` 里有个 `int32 InternalIndex` 字段。这一节展开:**这个 index 指向哪里?那个数组长什么样?为什么 GC 算法重度依赖它的内存布局?**
>
> `GUObjectArray` 是 UE 整个 UObject 系统的"户口簿":每个活着的 UObject 都在里面有一个 `FUObjectItem` 入口,记录它的指针、状态、序列号、所属 cluster。
>
> **不理解 GUObjectArray 的内存布局,你就读不懂 §4 的 GC 算法**。GC 不是去逐个 deref UObject 指针扫,而是**密集扫这张数组的 flag 字段** —— 因为它紧凑、cache friendly。
>
> **预备知识**:§3.1(InternalIndex 字段)、§1.5(原子操作 + cache line)。
>
> **读完之后你能做到**:

> - 看 `FUObjectItem` 的位段设计,知道 5.x 怎么把 64 位指针塞进 32 位
> - 理解 `TWeakObjectPtr` 怎么用 SerialNumber 检测对象悬空
> - 解释为什么 GC 标记阶段扫数组而不扫指针(cache locality)
> - 知道 `obj list` 实际是遍历这张表
> - 在 RTS 视角下评估"加了多少 UObject"对启动 / GC 的影响

## 3.2.1 浅入:`InternalIndex` 是去哪里查的索引?

§3.1 我们看到:

```cpp
// UObjectBase.h
int32 InternalIndex;       // Index into GObjectArray
```

每个 UObject 实例都有这个 4 字节的整数。这个数字是**全局对象表 `GUObjectArray` 里的下标**。

为什么不直接用指针?为什么要"用一个 index 间接"?三个理由:

### 3.2.1.1 GC 扫描的 cache locality

GC 标记阶段需要遍历**所有 UObject** 检查 reachability。如果 GC 用一个 `TArray<UObject*>` 直接持指针,扫描时:
- 每访问一个 UObject 的 flag 都要 `*ptr` —— **不同对象在堆上散落各处**,cache miss 严重
- 50 万 UObject × 一次 cache miss(~100 ns)= 50 ms,纯纯浪费

GUObjectArray 的设计:**把每个对象的 flag / 状态紧凑放在一起**,GC 只扫这个紧凑数组,不需要 deref 对象本体。50 万 × 一次顺序内存读 ≈ 一两毫秒,**改善一两个量级**。

### 3.2.1.2 弱引用检测悬空(SerialNumber)

`TWeakObjectPtr<T>` 不持有 GC 引用 —— 对象被回收时,弱指针应该自动失效。如果弱指针只存裸 `T*`,对象释放后这个指针就**悬空了**,deref 是 UB。

UE 的解法:弱指针存 `(InternalIndex, SerialNumber)` 这个二元组。每次解析时:
1. 用 InternalIndex 查 GUObjectArray
2. 比较 GUObjectArray[Index].SerialNumber 和弱指针存的 SerialNumber
3. 不匹配 → 对象已被销毁(原 index 已被新对象复用),返回 nullptr

详见 §3.2.5。

### 3.2.1.3 远程对象 / 序列化

5.x 引入 `UE_WITH_REMOTE_OBJECT_HANDLE` 实验特性:对象可以被部署到不同进程 / 节点。Index 系统让"远程对象引用"可序列化,而裸指针则不行。

## 3.2.2 `FUObjectArray` 的双层结构

`Engine/Source/Runtime/CoreUObject/Public/UObject/UObjectArray.h:939`:

```cpp
class FUObjectArray
{
public:
    enum ESerialNumberConstants
    {
        START_SERIAL_NUMBER = 1000,
    };
    // ...

private:
    FChunkedFixedUObjectArray ObjObjects;     // ★ 主存储
```

核心字段:**`ObjObjects` —— 一个 `FChunkedFixedUObjectArray` 类型的对象数组**。

### 3.2.2.1 `FChunkedFixedUObjectArray` 的内部布局

`UObjectArray.h:715`:

```cpp
class FChunkedFixedUObjectArray
{
    enum
    {
        NumElementsPerChunk = 64 * 1024,        // ★ 每 chunk 64K 个 FUObjectItem
    };

    FUObjectItem**             Objects;            // 主表(指向 chunk 数组的指针数组)
    FUObjectItem*              PreAllocatedObjects;// 可选:预分配整段连续内存
    TSAN_ATOMIC(int32)         MaxElements;        // 当前总容量
    TSAN_ATOMIC(int32)         NumElements;        // 当前已用元素数
    int32                       MaxChunks;          // 主表容量
    TSAN_ATOMIC(int32)         NumChunks;          // 主表已用
    // ...
};
```

**双层指针索引**:
1. 第一层:`Objects` 是个**指针数组**,每项指向一个 chunk
2. 第二层:每个 chunk 是 `FUObjectItem` 的连续数组(64K 个,fixed-size)

```
Objects(主指针表)         Chunk 0(64K FUObjectItem)
   │                       ┌──────────────┐
   ├──→ Chunk 0 ──→ ──→    │ Item[0]      │
   ├──→ Chunk 1 ──→ ──→    │ Item[1]      │
   ├──→ Chunk 2 ──→ ──→    │ Item[2]      │
   ├──→ ...                │ ...          │
   └──→ ...                │ Item[65535]  │
                            └──────────────┘
                            
                            Chunk 1(64K FUObjectItem)
                            ┌──────────────┐
                            │ Item[65536]  │
                            │ ...          │
                            └──────────────┘
```

按 InternalIndex 查 FUObjectItem:
```cpp
FUObjectItem& Item = ObjObjects[Index];
// 等价于
FUObjectItem& Item = Objects[Index / NumElementsPerChunk][Index % NumElementsPerChunk];
```

### 3.2.2.2 为什么 chunked 而不是单一大数组?

如果用 `TArray<FUObjectItem>` 单一大数组:
- 数量增长触发 realloc,**所有指向 FUObjectItem 的指针失效**
- GC、监听器、debug tools 都得重新解析
- realloc 大块内存(几十 MB)会卡

Chunked 解法:
- 数量增长**只新增一个 chunk**(64K item × ~32 字节 = ~2 MB),不影响已有 chunk
- **`FUObjectItem*` 指针在对象生命周期内永久稳定**(item 在 chunk 里位置不变)
- 内存增长幅度可控(每 chunk 才 2MB)

`MaxChunks` 在启动时确定(看 `PreAllocate(InMaxElements, ...)` 路径,line 800-)。一般 `MaxChunks` 设到能容纳几百万对象的级别。

### 3.2.2.3 启动期预分配

`PreAllocateObjects` 是个可选优化(看 line 725 / 797 等):
- **未开启** → 每个 chunk 单独 `new FUObjectItem[64K]`,chunks 分散在堆
- **开启** → 一次性 `new FUObjectItem[MaxElements]`,所有 chunks 共享一段连续内存

主机平台 / Shipping 默认开启(连续内存的 cache locality 更好)。Editor / Development 一般不开。

## 3.2.3 `FUObjectItem` 的内存布局

打开 `UObjectArray.h:49`,这是 GC / 弱指针 / 监听器都依赖的核心结构:

```cpp
// UObjectArray.h:49
struct FUObjectItem
{
private:
    union
    {
        int64 FlagsAndRefCount;     // 高 32 bits = flags(可能含指针高位),低 32 bits = ref count
#if !UE_WITH_REMOTE_OBJECT_HANDLE
        uint8 RemoteId;              // natvis 用
#endif
    };

#if UE_ENABLE_FUOBJECT_ITEM_PACKING
    union
    {
        uint32 ObjectPtrLow = 0;     // ★ 5.x 优化:对象指针的低 32 位(已右移 3 位)
        uint32 Object;               // natvis 用
    };
#else
    union
    {
        UE_DEPRECATED(5.6, "...")
        class UObjectBase* Object;   // 旧版:64 位指针
        uint32 ObjectPtrLow;
    };
#endif

public:
    int32 SerialNumber;              // ★ 弱指针检测悬空用(§3.2.5)
    int32 ClusterRootIndex;          // ★ GC 集群优化用(§4)

#if UE_WITH_REMOTE_OBJECT_HANDLE
    FRemoteObjectId RemoteId;
#endif

#if STATS || ENABLE_STATNAMEDEVENTS_UOBJECT
    mutable TStatId StatID;
#endif
};
```

字段总结:

| 字段 | 大小 | 作用 |
|---|---|---|
| `FlagsAndRefCount` | 8 字节 | union:int64,高 32 位 flags(`EInternalObjectFlags` + 指针高位),低 32 位 RefCount |
| `ObjectPtrLow` / `Object` | 4 / 8 字节 | UObject 实例指针(packed 模式 4 字节,旧版 8 字节) |
| `SerialNumber` | 4 字节 | 弱指针校验序号 |
| `ClusterRootIndex` | 4 字节 | GC 集群根节点 index(§4) |
| `StatID`(可选) | 取决于 STATS 配置 | 性能统计 ID |

无 STATS:总大小 **~24 字节**(packed)或 **~32 字节**(unpacked)。

### 3.2.3.1 5.x 的指针位段打包

**老版**(`UE_ENABLE_FUOBJECT_ITEM_PACKING = 0`):

```
[ FlagsAndRefCount:8 字节 ][ Object*:8 字节 ][ SerialNumber:4 ][ ClusterRoot:4 ]
                                                                     总 = 24 字节
```

**新版**(`UE_ENABLE_FUOBJECT_ITEM_PACKING = 1`):

```
FlagsAndRefCount(8 字节):
   ┌────────────────────────────────────────┐
   │ Flags(高 32 bits):EInternalObjectFlags │
   │   - 19 bits 真正的 flag 位               │
   │   - 13 bits 存指针的高 13 位(48-49 位中)│
   │ RefCount(低 32 bits)                    │
   └────────────────────────────────────────┘

ObjectPtrLow(4 字节):
   存指针的低 32 位(已右移 3 位)

总 = 16 字节(SerialNumber + ClusterRoot 各 4 字节)
```

### 3.2.3.2 解析过程(`GetObject` 实现)

`UObjectArray.h:146`:

```cpp
inline class UObjectBase* GetObject() const
{
#if UE_ENABLE_FUOBJECT_ITEM_PACKING
    const uintptr_t Obj = 
        (uintptr_t((FlagsAndRefCount >> 32) & PtrMask) << (32 + UObjectPtrTrailingZeroes)) | 
        (uintptr_t(ObjectPtrLow) << UObjectPtrTrailingZeroes);
    return (class UObjectBase*)Obj;
#else
    return Object;
#endif
}
```

打包逻辑:
- 假设对象 8 字节对齐(UObject 都是),指针**低 3 位永远是 0**,可以丢弃
- 64 位地址空间用户态实际只用 48 位(高 16 位都是 0),所以"高位"也只需 13 位(48 - 32 - 3)
- 这样 32(低位) + 13(高位) = 45 位足够编码 48 位指针(去掉低 3 位 trailing zeros 后)
- 节省 13 位塞到 Flags 高位

**节省 4 字节 / item × 50 万 item = 2 MB**。+ 提升 cache locality(`FUObjectItem` 从 24 → 16 字节,L1 cache line 能多放 2 倍)。

### 3.2.3.3 `FlagsAndRefCount` 的精妙设计

注意这一个 8 字节字段同时承载:
- Flags(对象状态,GC 用)
- RefCount(强引用计数,`AddRef` / `ReleaseRef`)
- 部分指针位

**为什么要叠在一起**?

注释里说(line 56-58):
> "The Flags are now stored on high 32-bit so that we can use InterlockedInc/InterlockedDec directly for RefCount which is stored on the low 32-bit while preserving atomicity of the whole thing so RootFlags+RefCount can be evaluated in a lock-less way."

翻译:**RefCount 用 InterlockedInc / InterlockedDec(只动低 32 位),Flags 在高 32 位不被影响**。两者共享一个 64 位字,`AtomicLoad` 一次读到的是一致快照。GC 可以**无锁**地同时读 Flags 和 RefCount。

这是经典的"位段共享 + 单字原子"的并发编程技巧。

## 3.2.4 `EInternalObjectFlags` 的实际位段

§3.1.4.1 提到过 `EInternalObjectFlags`,位置在 `FUObjectItem.FlagsAndRefCount` 高 32 位中的特定区域:

```cpp
// 简化(实际枚举更多)
enum class EInternalObjectFlags : int32
{
    None                    = 0,
    LoaderImport            = 1 << 20,
    Garbage                 = 1 << 21,        // 已被标记为垃圾,GC 准备清理
    PersistentGarbage       = 1 << 22,
    ReachableInCluster      = 1 << 23,
    RootIsInCluster         = 1 << 24,
    ClusterRoot             = 1 << 25,
    Async                   = 1 << 26,
    AsyncLoading            = 1 << 27,
    Unreachable             = 1 << 28,        // ★ GC 标记结果:可回收
    PendingConstruction     = 1 << 29,
    RootSet                 = 1 << 30,        // ★ GC root,永远不回收
};
```

5.x 加了 `EInternalObjectFlags_MinFlagBitIndex` 等常量,把 flag 区间和指针位区间分开:

```cpp
// UObjectArray.h:91-96
constexpr static int32 UObjectAlignment = 8;
constexpr static int32 UObjectPtrTrailingZeroes = FMath::CountTrailingZeros(UObjectAlignment);  // 3
static_assert(int(EInternalObjectFlags_MinFlagBitIndex) >= 48 - 32 - UObjectPtrTrailingZeroes, 
    "We need at least 13 bits to pack higher bits of a UObject pointer into Flags");
constexpr static int32 FlagsMask = 0xFFFFFFFF << int(EInternalObjectFlags_MinFlagBitIndex);
constexpr static int32 PtrMask = ~FlagsMask;
```

`EInternalObjectFlags_MinFlagBitIndex` 通常 13 或 14。意思:**前 13-14 位被指针高位占用,真正的 flag 从这之后开始**。这就是为什么 `EInternalObjectFlags` 的具体值(如 `Unreachable = 1 << 28`)看起来"位置很靠后" —— 前面被指针让出去了。

## 3.2.5 `TWeakObjectPtr` —— 用 SerialNumber 防悬空

`Engine/Source/Runtime/CoreUObject/Public/UObject/WeakObjectPtr.h:48`:

```cpp
struct FWeakObjectPtr
{
    int32 ObjectIndex;          // 索引到 GUObjectArray 的 InternalIndex
    int32 ObjectSerialNumber;   // 创建弱指针时记下的 SerialNumber
};
```

**就 8 字节**,跟一个普通指针一样大,但能安全检测悬空。

### 3.2.5.1 创建弱指针(指向某 UObject)

```cpp
FWeakObjectPtr WeakPtr = SomeObject;
// 内部:
//   ObjectIndex = SomeObject->InternalIndex
//   ObjectSerialNumber = GUObjectArray.GetSerialNumber(SomeObject)
//     - 如果该 item 还没分配 SerialNumber,这里分配一个新的(从 START_SERIAL_NUMBER 起递增)
```

### 3.2.5.2 解析弱指针

```cpp
UObject* WeakPtr::Get()
{
    FUObjectItem* Item = GUObjectArray.IndexToObject(ObjectIndex);
    if (!Item) return nullptr;
    
    // ★ 关键检查:SerialNumber 必须匹配
    if (Item->SerialNumber != ObjectSerialNumber) return nullptr;
    
    // 检查对象状态(没有被标 garbage / unreachable)
    if (Item->HasAnyFlags(EInternalObjectFlags::Garbage | EInternalObjectFlags::Unreachable))
        return nullptr;
    
    return Item->GetObject();
}
```

**核心逻辑**:`SerialNumber` 在对象**销毁时**会被 reset(`FUObjectArray::ResetSerialNumber`,line 950)。这样:
- 旧弱指针记的 ObjectIndex 即使被新对象复用了
- 新对象的 SerialNumber 一定**不**等于旧弱指针记的 SerialNumber
- 解析时 mismatch → 返回 nullptr

完美防悬空。

### 3.2.5.3 SerialNumber 分配策略

`START_SERIAL_NUMBER = 1000`(`UObjectArray.h:956`)。每次需要新序号 → 全局 atomic 自增 → 不会重复(理论上 32 位 = 40 亿次,实际进程内基本不会用尽)。

**懒分配**:`SerialNumber` 字段初始为 0。**只有第一次有 weak pointer 指向该对象时,才分配序号**。绝大多数 UObject 没有 weak pointer 指向它,SerialNumber 永远是 0,省内存操作。

### 3.2.5.4 性能

`TWeakObjectPtr::Get()` 实测 ~3-10 ns:
- 一次 chunk 解析(lookup ObjectItem)
- 一次 SerialNumber 比较
- 一次 flag 检查

比裸指针(0 ns)慢一点,但相比 `TSharedPtr`(原子引用计数 + cache miss)快很多。

### 3.2.5.5 使用纪律

```cpp
// ✅ Mass Fragment 持有 UObject 引用的标准姿势之一
USTRUCT()
struct FMyFragment : public FMassFragment
{
    GENERATED_BODY()

    TWeakObjectPtr<UStaticMesh> MeshRef;     // 8 字节,可悬空,自动失效
};

// ✅ Hot path 访问要 .Get() 检查
void Process(FMyFragment& Frag)
{
    if (UStaticMesh* Mesh = Frag.MeshRef.Get())   // 3-10 ns
    {
        // ...
    }
}

// ❌ 不要在最热点频繁解析(每帧每 entity)
// 解决:外层缓存解析后的指针,再传入热循环
```

## 3.2.7 GC 为什么扫数组而不扫指针(关键)

§4 GC 算法详讲,这里先建立认知。

### 3.2.7.1 朴素思路 vs UE 思路

**朴素思路**:GC 扫所有 UObject,逐个调 `Obj->IsReachable()` 判断。

```cpp
for (UObject* Obj : AllUObjects)   // 但 AllUObjects 怎么得到?
{
    if (Obj->ReachableFlag) Mark(Obj);
}
```

问题:
- "AllUObjects" 哪来?需要单独维护数组,与对象生命周期同步
- 每个 Obj 是分散的堆指针,deref 一次 cache miss
- 多线程时 `Obj->ReachableFlag` 写入需要 atomic / 锁

**UE 思路**:GC 扫 `GUObjectArray.ObjObjects` 这个紧凑数组。

```cpp
for (int32 Index = 0; Index < GUObjectArray.GetObjectArrayNum(); ++Index)
{
    FUObjectItem& Item = GUObjectArray.IndexToObject(Index);
    if (Item.HasFlag(EInternalObjectFlags::ReachableInCluster)) MarkReachable(Item);
}
```

关键:**`FUObjectItem` 是 16-32 字节,密集排列在 chunk 内**。一个 64K item chunk = 1-2 MB 连续内存,顺序扫描走 cache prefetcher,接近内存带宽。

### 3.2.7.2 数据对照

| 对比维度 | 朴素扫指针 | UE 扫数组 |
|---|---|---|
| 单次访问 | cache miss(~100 ns) | cache hit(~1 ns) |
| 50K 对象总耗时 | ~5 ms | ~50 μs |
| 多线程友好 | 难(对象散落) | 易(分 chunk 并行) |

GC 标记阶段在 Editor 里 50 万对象只花 1-3 ms,**全靠 GUObjectArray 的紧凑布局**。

### 3.2.7.3 这一节的精髓

**`FUObjectItem` 的设计是一切围绕 GC 性能展开**:
- Flags / RefCount / 指针位段共享一个 64 位字 → atomic GC 标记
- chunk 化连续布局 → cache-friendly 扫描
- SerialNumber 让弱指针无需对象自身参与就能检测悬空 → 弱指针解析也走数组

UE 把"对象元数据"和"对象本体"**分离**(本体在堆上各处,元数据在 GUObjectArray 紧凑数组里),这是支撑 GC 性能的根本。

## 3.2.8 内存预算实测

```cpp
static FAutoConsoleCommand CmdInspectGUObjArray(TEXT("rts.InspectGUObjArray"),
    TEXT("Print GUObjectArray statistics"),
    FConsoleCommandDelegate::CreateLambda([]()
    {
        int32 Num = GUObjectArray.GetObjectArrayNum();
        int32 Max = GUObjectArray.GetObjectArrayCapacity();
        
        UE_LOG(LogTemp, Display, TEXT("GUObjectArray:"));
        UE_LOG(LogTemp, Display, TEXT("  Num     = %d"), Num);
        UE_LOG(LogTemp, Display, TEXT("  Max     = %d"), Max);
        UE_LOG(LogTemp, Display, TEXT("  sizeof(FUObjectItem) = %d"), (int32)sizeof(FUObjectItem));
        UE_LOG(LogTemp, Display, TEXT("  Total = %.2f MB"), (Max * sizeof(FUObjectItem)) / (1024.0 * 1024.0));
        
        // 按类型分布
        TMap<UClass*, int32> ClassCounts;
        for (int32 i = 0; i < Num; ++i)
        {
            FUObjectItem* Item = GUObjectArray.IndexToObject(i);
            if (Item && Item->GetObject())
            {
                UObject* Obj = (UObject*)Item->GetObject();
                ClassCounts.FindOrAdd(Obj->GetClass())++;
            }
        }
        
        // Sort by count, top 20
        ClassCounts.ValueSort([](int32 A, int32 B) { return A > B; });
        int32 Cnt = 0;

            if (Cnt++ >= 20) break;
            UE_LOG(LogTemp, Display, TEXT("  %-50s %d"), *Pair.Key->GetName(), Pair.Value);
        }
    }));
```

```
  ... (top 20)
```

通常一个 Editor 启动 100K-500K UObject。如果你的项目接近上限,启动慢、GC 慢,就需要审查"是不是无意中创建了太多 UObject"。

---

## 3.2.9 RTS / Mass 视角下的纪律

### (1)50K Mass entity ≠ 50K UObject

再次强调:**Mass entity 不进 GUObjectArray**。50K entity = 0 个新 UObject 进表。

如果不这样,50K 加入 GUObjectArray 意味着:
- 16 字节 × 50K = 800 KB 的 `FUObjectItem`(可接受)
- 但 50K UObject 实例本身(每个 40 字节起)= 2MB+ 头部 + 字段
- GC 每次扫描多 50K 项,可能多花几毫秒
- 创建 50K UObject 的 NewObject 调用一次几百 μs × 50K = 几十秒

Mass 把"实例数据"完全脱离 UObject 体系,这是它能 scale 的根本。

### (2)看你 Mass 体系实际增加了多少 UObject

启动你 RTS 项目,跑 `rts.InspectGUObjArray`,关注:
- `UMassEntitySubsystem` 1 个
- `UMyMassProcessor*` 几十个
- `UMyEntityTraitBase*` 若干 CDO + 你定义的 Trait 子类
- `UMassEntityConfigAsset*` 资产数

如果 Mass 部分给 GUObjectArray 加了 < 500 项,就是健康的。**+5000 项就有问题**(可能你不小心给每个 entity 配了一个 UObject)。

### (3)GC 扫描时间预算

GC 扫 GUObjectArray 大约 1-3 ms / 100 万对象。如果你 Editor 启动了 50 万对象,GC 单次约 0.5-1.5 ms。Game build 通常对象更少,GC < 1 ms。

**Mass 项目要保持 Editor 启动期不显著膨胀 GUObjectArray**,否则数十万 entity 跑起来,GC 摊到帧时间里就吃帧。

### (4)`TObjectPtr` 性能与 SerialNumber 无关

`TObjectPtr<T>` 是**强引用**,对象不会因为它存在被回收,但它**也不**走 SerialNumber 校验路径。它保持对象活着,直接 deref。性能 ≈ 裸指针。

**Fragment 里持有 UObject 的姿势**:
- **强引用 + GC 知晓**(对象不被销毁):`UPROPERTY() TObjectPtr<UMesh>`
- **弱引用 + 自动失效**:`TWeakObjectPtr<UMesh>`(用 SerialNumber)
- **裸指针**:**绝对不要**,Fragment 里持有的 UObject 不在 UPROPERTY 里 GC 完全不知道,可能悬空

## 3.2.10 改 Engine:加 FUObjectItem 字段(几乎不可能)

如果你想给 FUObjectItem 加字段(典型场景:全局对象 ID 服务):

- 50 万对象 × 你加几字节 = 几 MB(不大)
- 但**所有依赖 FUObjectItem 内存布局的代码**都要改 — GC、监听器、序列化、HotReload
- rebase 灾难:Epic 5.x 改 FUObjectItem 几乎每版都有

**纪律**:**绝对不改**。如果真需要"对象级元数据",用 `FUObjectAnnotation`(§3.1.9.2)。
