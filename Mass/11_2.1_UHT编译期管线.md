# §2.1 UnrealHeaderTool 编译期管线 — 反射代码生成的"内幕"

> **本节地图**:模块一第 2 章第 1 节。第 1 章把"内存"层完整讲清。这一节我们走进**反射系统** —— 它是 UObject / Blueprint / 网络复制 / GC / Mass Trait 反射所有功能的基石。

>

## 2.1.1 浅入:UHT 解决了什么"用纯 C++ 不能解决"的问题

C++ 是**强静态类型**语言,**没有原生反射**。`int Foo;` 编译完只剩一个内存偏移,没人知道它叫 "Foo" 或类型是 int。

可是 UE 需要做这些事:
- **Blueprint** 调一个 C++ 函数:运行时拿到函数名、参数列表、参数类型、返回值类型
- **网络复制**:序列化一个 UObject 的所有 `UPROPERTY()` 字段时,要遍历字段、按字段类型决定怎么序列化
- **垃圾回收**:扫描 UObject 引用图,需要知道某个类的所有 `UPROPERTY` 字段哪些是 `UObject*`、哪些是 `TArray<UObject*>`,以便正确递归
- **Editor 的 Property panel**:展示一个 UObject 时,自动列出所有 UPROPERTY 字段,允许编辑
- **资产序列化**:`.uasset` 文件存读时按属性表反序列化

这些**全部需要运行时反射**。C++ 自己没有,UE 自己造一个 —— 这就是 UHT + UClass 系统。

### 2.1.1.1 反射机制的两阶段架构

```
┌─────────────────────────────────────────────┐
│  阶段 1:编译期(UHT 处理)                  │
│  你的 .h 文件                                │
│       │                                      │
│       ↓ UHT 扫描 UCLASS / UPROPERTY 等宏     │
│       ↓                                      │
│  生成 .generated.h(给你的 .h 用)           │
│       + .gen.cpp(给你的 .cpp 用)            │
│       (展开成几百行 C++ 注册代码)           │
└─────────────────────────────────────────────┘
                  │
                  ↓ 与你的 .cpp 一起编译
┌─────────────────────────────────────────────┐
│  阶段 2:运行时(进程启动期)                │
│  C++ 全局静态构造调用 Z_Construct_UClass_X  │
│  → 构造 UClass 对象,挂到 GUObjectArray     │
│  → 注册所有 UPROPERTY 字段、UFUNCTION       │
│  → 反射数据就绪,Blueprint / GC / 网络可用  │
└─────────────────────────────────────────────┘
```

阶段 1 是 §2.1 的全部主题。阶段 2 是 §2.2 的主题。

## 2.1.2 UHT 在 5.7 里的位置 — C# 化已完成

**5.0 之前**,UHT 是一个**独立的 C++ 程序**,源码在 `Engine/Source/Programs/UnrealHeaderTool/`,产物 `UnrealHeaderTool.exe`。

**5.0+ 起**,Epic 把 UHT 用 C# 重写,合入 UBT。**5.7.3** 的状态:

为什么 C# 化?
1. **跟 UBT 整合** —— 共享配置加载、并行调度、增量编译框架
2. **更快开发** —— C# 写 parser / generator 比 C++ 快
3. **更好的并行** —— C# Task 模型在多核 build 上更顺
4. **代码量减少** —— 老 UHT 是几万行 C++,新 UHT 在 EpicGames.UHT 里 ~30000 行 C# 但更可读

### 2.1.2.1 调用入口

UBT 决定要构建一个 Module 时,如果该 Module 有反射头(任何 .h 含 UCLASS/USTRUCT/UFUNCTION/UPROPERTY/UENUM 的文件),UBT 会:

1. 扫描 Module 下所有 .h,找出含反射的
2. 把这批 .h 的列表交给 UHT(同一进程内调用,因为已经是 C# 库)
3. UHT 输出生成文件到 `Engine/Intermediate/Build/<Target>/Inc/<Module>/UHT/`
4. UBT 把这批生成文件加入 cl.exe / clang 的编译列表

整个流程**单进程**,UHT 是 UBT 的一个 mode。日志里会看到 `[UnrealHeaderTool] ...` 前缀的输出。

### 2.1.2.2 何时触发 UHT 重跑

UHT 增量缓存比较聪明:
- 你只改 `.cpp`(无反射变化)→ UHT **跳过**
- 你改 `.h` 但没动 UCLASS 等宏 → UHT 重跑该文件,可能产物未变,UBT 跳过编译生成的 .gen.cpp
- 你改 `.h` 加/删 UPROPERTY → UHT 重生成,UBT 重编 .gen.cpp,**很多依赖你头的下游也跟着重编**

所以"减少头里的反射改动"是降低增量编译时间的关键。

## 2.1.3 一个最小例子 — 从原始 .h 到生成文件

我们用一个最简单的类作样本。

### 2.1.3.1 你写的代码

```cpp
// MyHello.h
#pragma once
#include "Components/ActorComponent.h"
#include "MyHello.generated.h"

UCLASS()
class MYMOD_API UMyHelloComponent : public UActorComponent
{
    GENERATED_BODY()

public:
    UPROPERTY(EditAnywhere)
    int32 Health = 100;

    UFUNCTION(BlueprintCallable)
    void Heal(int32 Amount);

protected:
    UPROPERTY()
    FString Name;
};
```

```cpp
// MyHello.cpp
#include "MyHello.h"

void UMyHelloComponent::Heal(int32 Amount)
{
    Health += Amount;
}
```

UHT 处理后,在 `Engine/Intermediate/Build/Win64/UnrealEditor/Inc/MYMOD/UHT/` 下生成两个文件:
- `MyHello.generated.h`
- `MyHello.gen.cpp`

### 2.1.3.2 `MyHello.generated.h`(简化)

UHT 生成的 .generated.h 主要由**一组宏定义**组成。这些宏在你 `#include "MyHello.generated.h"` 后,被 `GENERATED_BODY()` 触发展开。简化形态:

```cpp
// Engine/Intermediate/Build/Win64/.../Inc/MYMOD/UHT/MyHello.generated.h(简化)
#pragma once

#include "UObject/ObjectMacros.h"
#include "UObject/ScriptMacros.h"

class UMyHelloComponent;

#ifdef MYMOD_MyHello_generated_h
#error "MyHello.generated.h already included, missing '#pragma once' in MyHello.h"
#endif
#define MYMOD_MyHello_generated_h

// ─── 反射 RPC wrappers(给 BP / Network 调用)─────
#define FID_MyMod_Source_MyMod_Public_MyHello_h_19_RPC_WRAPPERS \
    DECLARE_FUNCTION(execHeal);

// ─── INCLASS_NO_PURE_DECLS:GENERATED_BODY() 的核心 ─────
#define FID_MyMod_Source_MyMod_Public_MyHello_h_19_INCLASS_NO_PURE_DECLS \
private: \
    static void StaticRegisterNativesUMyHelloComponent(); \
    friend struct Z_Construct_UClass_UMyHelloComponent_Statics; \
public: \
    DECLARE_CLASS(UMyHelloComponent, UActorComponent, COMPILED_IN_FLAGS(0), CASTCLASS_None, TEXT("/Script/MYMOD"), MYMOD_API) \
    DECLARE_SERIALIZER(UMyHelloComponent)

// ─── ENHANCED_CONSTRUCTORS:GENERATED_BODY 也用 ─────
#define FID_MyMod_Source_MyMod_Public_MyHello_h_19_ENHANCED_CONSTRUCTORS \
    /** Standard constructor, called after all reflected properties have been initialized */ \
    NO_API UMyHelloComponent(const FObjectInitializer& ObjectInitializer = FObjectInitializer::Get()); \
    DEFINE_DEFAULT_OBJECT_INITIALIZER_CONSTRUCTOR_CALL(UMyHelloComponent) \
    DECLARE_VTABLE_PTR_HELPER_CTOR(NO_API, UMyHelloComponent); \
    DEFINE_VTABLE_PTR_HELPER_CTOR_CALLER(UMyHelloComponent); \
private: \
    /** Private move/copy constructors deleted */ \
    NO_API UMyHelloComponent(UMyHelloComponent&&); \
    NO_API UMyHelloComponent(const UMyHelloComponent&); \
public:

// ─── GENERATED_BODY() 实际展开 ─────
#define FID_MyMod_Source_MyMod_Public_MyHello_h_19_GENERATED_BODY \
PRAGMA_DISABLE_DEPRECATION_WARNINGS \
public: \
    FID_MyMod_Source_MyMod_Public_MyHello_h_19_RPC_WRAPPERS \
    FID_MyMod_Source_MyMod_Public_MyHello_h_19_INCLASS_NO_PURE_DECLS \
    FID_MyMod_Source_MyMod_Public_MyHello_h_19_ENHANCED_CONSTRUCTORS \
private: \
PRAGMA_ENABLE_DEPRECATION_WARNINGS

// ─── 文件位置定义(给宏内部用) ─────
#undef CURRENT_FILE_ID
#define CURRENT_FILE_ID FID_MyMod_Source_MyMod_Public_MyHello_h
```

读完几个观察:

**(1)文件名 + 行号编码进宏名**:`FID_MyMod_Source_MyMod_Public_MyHello_h_19_*` 里的 `19` 是 `GENERATED_BODY()` 在 .h 里的行号。这样**同一个 .h 不同行**的不同 `GENERATED_BODY()` 不会冲突(允许一个 .h 里有多个 UCLASS/USTRUCT)。

**(2)宏一层套一层**:`GENERATED_BODY` 实际是 `RPC_WRAPPERS + INCLASS_NO_PURE_DECLS + ENHANCED_CONSTRUCTORS` 三块拼起来。这种"积木"设计让 UHT 给不同的反射类型(USTRUCT / UCLASS / UINTERFACE)生成共享 + 特化两层宏。

**(3)`DECLARE_CLASS` 是 UE 反射的核心**(在 `UObject/ObjectMacros.h` 定义)。它展开后给类加上:
- `static UClass* StaticClass()` 静态查询
- `Super = UActorComponent` 的 typedef
- `ClassFlags`、`StaticClassMetaData` 等
- 一堆运行时 hook(`Serialize`、`PostInitProperties` 默认实现等)

**(4)RPC wrappers**:`DECLARE_FUNCTION(execHeal)` 给每个 `UFUNCTION` 生成一个 trampoline 函数 `execHeal`,负责从 Blueprint VM / 网络栈把参数解包,调用真正的 `Heal()`,再把结果打包回去。

**(5)关键:你的类必须 `#include "MyHello.generated.h"` 且必须**最后一个 include**。**因为 generated.h 里 `#define CURRENT_FILE_ID FID_..._MyHello_h` 这条会影响后续宏展开,必须在你写 `GENERATED_BODY()` 之前**就位**。

### 2.1.3.3 `MyHello.gen.cpp`(简化)

这是更"重量级"的产物。它**不**被你 include,而是**作为独立的 .cpp 文件**被加入编译。简化:

```cpp

#include "MyMod/Public/MyHello.h"

// ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
DEFINE_FUNCTION(UMyHelloComponent::execHeal)
{
    P_GET_PROPERTY(FIntProperty, Z_Param_Amount);
    P_FINISH;
    P_NATIVE_BEGIN;
    P_THIS->Heal(Z_Param_Amount);                       // 真正的 native 调用
    P_NATIVE_END;
}

// ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

// ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
void UMyHelloComponent::StaticRegisterNativesUMyHelloComponent()
{
    UClass* Class = UMyHelloComponent::StaticClass();
    static const FNameNativePtrPair Funcs[] = {
        { "Heal", &UMyHelloComponent::execHeal },
    };
    FNativeFunctionRegistrar::RegisterFunctions(Class, Funcs, UE_ARRAY_COUNT(Funcs));
}

// 3. UFunction 描述:Heal 函数的反射数据
// ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

    static const UECodeGen_Private::FPropertyParamsBase* const PropPointers[];
    static const UECodeGen_Private::FFunctionParams FuncParams;
};

const UECodeGen_Private::FIntPropertyParams 
Z_Construct_UFunction_UMyHelloComponent_Heal_Statics::NewProp_Amount = {
    "Amount",                                            // 参数名
    nullptr,                                             // group
    (EPropertyFlags)0x0010000000000080,                  // CPF_Parm | CPF_NativeAccessSpecifierPublic
    UECodeGen_Private::EPropertyGenFlags::Int,
    RF_Public | RF_Transient | RF_MarkAsNative,
```

读完几个观察:

**(1)`Z_Construct_UClass_*` 这一组函数是反射注册的"主菜"**。它们在 §2.2 会被详细拆 —— 它们是被全局注册表延迟调用的。

**(2)所有字段 / 函数的元数据都是 `static const` 全局对象**。一个类的反射信息可能上千行,全部展开成静态结构。这就是为什么 .gen.cpp 文件常常几千行。

**(3)`STRUCT_OFFSET(UMyHelloComponent, Health)`** 让反射系统知道 `Health` 字段在对象里的实际字节偏移。运行时 GC、复制、序列化都靠这个偏移。

**(4)`Z_CompiledInDeferFile_*` 是个全局静态对象**,构造函数在 C++ 全局静态初始化阶段(`WinMain` 之前)被调用,把"构造 UClass"的函数指针注册到全局列表 `GFirstPendingRegistrant`。引擎启动到 CoreUObject 初始化时,遍历这个列表实际构造每个 UClass。

**(5)`execHeal`** 是 Blueprint / Network 调 `Heal()` 的统一入口。它从虚拟参数栈读出参数,调真函数,把结果写回。`P_GET_PROPERTY` / `P_FINISH` / `P_NATIVE_BEGIN` 等是 `Script.h` 里的宏。

## 2.1.4 UHT 的工作流(C# 视角)

打开 `Engine/Source/Programs/Shared/EpicGames.UHT/Parsers/UhtClassParser.cs:57`,这是 UCLASS 的解析入口。简化版执行流:

```csharp
// UhtClassParser.cs:57
private static UhtParseResult ParseUClass(UhtParsingScope parentScope, ref UhtToken token)
{
    UhtClass classObj = new(parentScope.HeaderFile, parentScope.HeaderParser.GetNamespace(), 
                            parentScope.ScopeType, token.InputLine);
    
    using UhtParsingScope topScope = new(parentScope, classObj, ...);
    
    // 1. 解析 UCLASS(...) 里的 specifiers(BlueprintType / Abstract / Const ...)
    UhtSpecifierParser specifiers = UhtSpecifierParser.GetThreadInstance(...);
    specifiers.ParseSpecifiers();
    
    classObj.ClassFlags |= EClassFlags.Native;
    
    // 2. 处理注释(成 metadata 里的 ToolTip)
    topScope.AddFormattedCommentsAsTooltipMetaData();
    
    // 3. 消费 "class" 关键字,读类名 + API 宏
    topScope.TokenReader.OptionalAttributes(false);
    topScope.TokenReader.Require("class");
    topScope.TokenReader.TryOptionalAPIMacro(out UhtToken apiMacroToken);
    classObj.SourceName = topScope.TokenReader.GetIdentifier().Value.ToString();
    
    // 4. 处理类名前缀(U / A / F / E)
    UhtEngineNameParts nameParts = UhtUtilities.GetEngineNameParts(classObj.SourceName);
    classObj.EngineName = nameParts.EngineName.ToString();
    
    // 5. 解析继承("public UActorComponent" 等)
    UhtParserHelpers.ParseInheritance(parentScope.HeaderParser, ..., out UhtInheritance inheritance);
    classObj.SuperIdentifier = inheritance.SuperIdentifier;
    
    // 6. 进入类体 { ... },递归解析里面的成员
    topScope.HeaderParser.ParseStatements('{', '}', true);
    
    topScope.TokenReader.Require(';');
    
    // 7. 检查 GENERATED_BODY 是否存在
    if (classObj.GeneratedBodyLineNumber == -1)
    {
        topScope.TokenReader.LogError("Expected a GENERATED_BODY() at the start of the class");
    }
    
    return UhtParseResult.Handled;
}
```

`ParseStatements('{', '}', true)` 内部递归处理类体里的:
- 嵌套 UFUNCTION → `UhtFunctionParser`
- UPROPERTY → `UhtPropertyParser`
- GENERATED_BODY → `UhtClassParser.GENERATED_UCLASS_BODYKeyword`
- 普通 C++ 成员 → 跳过(UHT 不关心)

### 2.1.4.1 关键字注册机制(UhtKeyword)

UHT 怎么知道 `UCLASS` 这个关键字该走 `UhtClassParser`?看 `UhtClassParser.cs:20`:

```csharp
[UhtKeyword(Extends = UhtTableNames.Global)]
private static UhtParseResult UCLASSKeyword(UhtParsingScope topScope, UhtParsingScope actionScope, ref UhtToken token)
{
    return ParseUClass(topScope, ref token);
}
```

**`[UhtKeyword]` 属性**让 C# 反射在程序启动时自动把 `UCLASS` 这个 token 名字关联到 `UCLASSKeyword` 这个静态方法,挂到"全局解析关键字表"里。

类似:
- `UFUNCTION` → `UhtFunctionParser.UFUNCTIONKeyword`
- `UPROPERTY` → `UhtPropertyParser.UPROPERTYKeyword`
- `GENERATED_BODY` → `UhtClassParser.GENERATED_UCLASS_BODYKeyword`(`Extends = UhtTableNames.Class`,即只在类作用域里有效)
- `USTRUCT` → `UhtScriptStructParser.USTRUCTKeyword`
- `UENUM` → `UhtEnumParser.UENUMKeyword`

**这种"用 attribute 注册"的设计让 UHT 极易扩展** —— 你想加新的 UE 元宏(假设你 RTS 项目想加 `URTSCOMMAND`),写一个 parser 类,加 `[UhtKeyword]`,UHT 自动认。

### 2.1.4.2 Tokenizer 与 Parser 的分工

`Engine/Source/Programs/Shared/EpicGames.UHT/Tokenizer/UhtToken.cs` 等定义了**词法分析层**:
- 读 .h 字符流
- 切成 `UhtToken`(标识符 / 字符串 / 数字 / 操作符 / 注释)
- 跳过 C++ 编译指令(`#if WITH_EDITOR` 之类有特殊处理,UHT 模拟其语义)

Parser 层从 Tokenizer 拿 token 流,递归下降构造 AST(`UhtClass` / `UhtScriptStruct` / `UhtFunction` / `UhtProperty` 等都是 AST 节点类型,定义在 `EpicGames.UHT/Types/`)。

### 2.1.4.3 Specifier 解析

UCLASS 后面的 `(BlueprintType, Abstract, ...)` 是 specifier。`UhtSpecifierParser.cs` 处理。每个 specifier 在 `EpicGames.UHT/Specifiers/UhtClassSpecifiers.cs` 之类的文件里被注册:

```csharp
[UhtSpecifier(Extends = UhtTableNames.Class, ValueType = UhtSpecifierValueType.Legacy)]
private static void BlueprintTypeSpecifier(UhtSpecifierContext context)
{
    UhtClass classObj = (UhtClass)context.Scope.ScopeType;
    classObj.MetaData.Add("BlueprintType", "true");
}
```

这种插件式架构让 specifier 易于增删。新加一个 `UCLASS(MyCustomSpec)`?写一个新 specifier 函数,一行 `[UhtSpecifier]` 搞定。

## 2.1.5 代码生成阶段

解析完所有 .h 后,UHT 进入 codegen 阶段。入口在:
- `Engine/Source/Programs/Shared/EpicGames.UHT/Exporters/CodeGen/UhtCodeGenerator.cs`(572 行)
- `UhtHeaderCodeGeneratorHFile.cs` —— 生成 .generated.h
- `UhtHeaderCodeGeneratorCppFile.cs`(3452 行,大头)—— 生成 .gen.cpp

### 2.1.5.1 SingletonType — 四种"单例引用"

`UhtCodeGenerator.cs:18`:

```csharp
public enum UhtSingletonType
{
    Registered = 0,        // 完整构造好的 UClass
    Unregistered = 1,      // 部分构造的 UClass
    ConstInit = 2,         // C++20 constinit 变量
    Statics = 3,           // 含初始化数据的 struct
}
```

每个反射类型(class / struct / function)在 .gen.cpp 里都有对应这四种之一(或多种)的引用入口:

- `Z_Construct_UClass_UMyClass()` → Registered
- `Z_Construct_UClass_UMyClass_NoRegister()` → Unregistered
- `Z_Construct_UClass_UMyClass_Statics::ClassParams` → Statics

不同时机用不同入口。例如**构造 ChildClass 的反射**时,引用 `ParentClass_NoRegister` 而不是 `ParentClass_Registered`,以避免循环依赖。

### 2.1.5.2 Codegen 主流程

简化:

```
1. 收集所有 UhtPackage(本质对应一个 Module)
2. 对每个 Package:
   a. 对每个 UhtHeaderFile(对应一个 .h):
      - 生成 .generated.h(用 UhtHeaderCodeGeneratorHFile)
      - 生成 .gen.cpp(用 UhtHeaderCodeGeneratorCppFile)
   b. 生成 Package 级别的汇总文件(如果需要):
      - <Module>.init.gen.cpp:Module 启动时的批量注册
3. 写入磁盘(对比已有内容,只有真改了才写,触发增量)
```

### 2.1.5.3 增量(只在内容变了才写)

UHT 在写文件前**对比新旧内容**。如果你只是改了 .h 的注释、空格、不影响反射,生成出来的 .generated.h / .gen.cpp 内容**完全一样**,UHT **不**重写文件。这样下游编译时间戳没变,UBT 跳过编译。

**实战经验**:你只改 UFUNCTION 的实现(不改签名),UHT 也会重新解析头,但产物字节相同 → 不写文件 → 不触发整链重编。这是 UE 增量构建快的关键。

## 2.1.6 几个常用宏的真实展开

### 2.1.6.1 `UCLASS()`

**这是个空展开!**

```cpp
// ObjectMacros.h(简化)
#define UCLASS(...)  /* 空 */
```

UCLASS 宏对 C++ 编译器**不可见**(展开成空)。它的作用纯粹是 UHT 解析时的 marker。这就是为什么你在 IDE 里 F12 跳不到 UCLASS 的"实现"—— 它本来就没有实现。

### 2.1.6.2 `UPROPERTY()`

同样**空展开**:

```cpp
#define UPROPERTY(...)  /* 空 */
```

UHT 自己识别。C++ 编译器看到的是 `int32 Health = 100;`(没有 UPROPERTY 装饰)。

### 2.1.6.3 `UFUNCTION()`

同样空。

### 2.1.6.4 `GENERATED_BODY()`

**这个不是空**!它的展开是:

```cpp
// ObjectMacros.h:
#define BODY_MACRO_COMBINE(A,B,C,D) A##B##C##D
#define BODY_MACRO_COMBINE_INNER(A,B,C,D) BODY_MACRO_COMBINE(A,B,C,D)

#define GENERATED_BODY(...) \
    BODY_MACRO_COMBINE_INNER(CURRENT_FILE_ID, _, __LINE__, _GENERATED_BODY)
```

`__LINE__` 是当前行号(C 标准宏),`CURRENT_FILE_ID` 是 generated.h 里 `#define` 的标识符。所以 `GENERATED_BODY()` 在 19 行展开成:

```cpp
FID_MyMod_Source_MyMod_Public_MyHello_h_19_GENERATED_BODY
```

而这正是 generated.h 里定义的那个宏(§2.1.3.2)。最终把"反射注册的代码块"插入到类体里。

**精妙之处**:`__LINE__` 让同一个文件多个 GENERATED_BODY 互不冲突。Generated.h 里有:
- `FID_..._19_GENERATED_BODY`(class 在 19 行)
- `FID_..._52_GENERATED_BODY`(下一个 struct 在 52 行)
- ...

每个 `GENERATED_BODY()` 调用通过 `__LINE__` 自动选对自己那块。

### 2.1.6.5 模块 API 宏(`MYMOD_API`)

```cpp
class MYMOD_API UMyHelloComponent : public UActorComponent
```

`MYMOD_API` 是个由 UBT 注入的宏,展开为:
- 编译当前 Module 时:`__declspec(dllexport)`(导出)
- 别的 Module 编译时:`__declspec(dllimport)`(导入)
- Monolithic 构建时:空(没有 DLL,不需要导出/导入)

UBT 给每个 Module 自动定义这个宏(`<MODULE_NAME>_API`)。**类名前必须带这个宏才能被其它 Module 使用**(不带的话 Monolithic 工作但 dll 模式下 link 失败)。

## 2.1.9 UHT 与 Mass 的关系

### 2.1.9.1 USTRUCT —— Fragment 走的路径

Mass Fragment 是 USTRUCT(reflected struct)。UHT 处理 USTRUCT 与 UCLASS 类似但简化:

```cpp
USTRUCT()
struct FMassMovementFragment : public FMassFragment
{
    GENERATED_BODY()
    
    UPROPERTY(EditAnywhere)
    FVector Velocity = FVector::ZeroVector;
    
    UPROPERTY()
    float Speed = 0.0f;
};
```

UHT 生成的:
- `Z_Construct_UScriptStruct_FMassMovementFragment` 而不是 `Z_Construct_UClass_*`
- `UScriptStruct*` 注册到反射系统,Mass 内部能查询字段偏移
- **没有 vtable**(USTRUCT 不像 UCLASS 那样有虚函数支持)
- Fragment 的反射数据被 Mass `FMassEntityManager` 用来序列化、复制、Editor 展示

### 2.1.9.2 Mass 自己的"BitSet 类型识别"

Mass 不用 `UScriptStruct*` 当 Fragment 类型 ID(那是个 8 字节指针)。它用 `FMassFragmentBitSet`(后面 §17.6 详讲),把所有已注册 Fragment 类型映射到一个**位图**,每位代表一种 Fragment。

**为什么不用反射的指针**?因为 Mass 的 EntityQuery 需要"这个 archetype 包含 Fragment A 和 B,不含 C"这种**集合运算**。位图 `&` `|` `^` 比指针 set 快几个数量级。

但**位图的索引**仍然来自反射 —— 每个 USTRUCT 在 UHT 处理后注册到 `UScriptStruct*`,Mass 启动时遍历所有 `IsChildOf<FMassFragment>::Value` 的 UScriptStruct,每个分配一个位 index。

所以反射是 Mass 性能架构的**支撑层**,不直接出现在 hot path 上。

### 2.1.9.3 Trait —— 配置类反射

Mass `UMassEntityTraitBase` 子类是 UCLASS,UHT 全套生成(就是 §2.1.3 演示的形态)。Trait 在 Editor 里被资产化、配置化、复制粘贴 —— 全靠反射。

## 2.1.10 改 UHT(写自定义 Exporter)

这是高级用法。你**不改** UHT 现有行为,而是**加一个新的 Exporter**:

```csharp
// 在你 Build 体系里加一个 UHT plugin DLL
[UnrealHeaderTool]
public class UhtMyRTSExporter
{
    [UhtExporter("MyRTS", ExporterType.Module)]
    public static void Export(IUhtExportFactory factory)
    {
        // 遍历所有反射类型,导出你想要的格式
        foreach (UhtPackage package in factory.Session.Packages)
        {
            foreach (UhtHeaderFile header in package.Children)
            {
                foreach (UhtClass classObj in header.Children.OfType<UhtClass>())
                {
                    // 你的逻辑:导出到 JSON / 自定义二进制 / Lua binding 等
                }
            }
        }
    }
}
```

**真实用例**:
- 自动生成脚本绑定(Lua / Verse / Python)
- 导出反射元数据给外部工具(AI 数据生成、reverse engineering 工具)
- 自定义文档生成

UE 5 自带几个 exporter(Json / Stats / CodeGen),你可以参考:
