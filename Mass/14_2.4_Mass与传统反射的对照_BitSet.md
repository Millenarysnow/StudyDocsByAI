# §2.4 Mass 与传统反射的对照 — FStructTypeBitSet 的设计精妙

> **本节地图**:模块一第 2 章压轴。前面 §2.1-2.3 把传统反射讲透了。这一节看 Mass **怎么用反射,又怎么不用反射**。
>
> 中心问题:**Mass 已经有 `UScriptStruct*` 这个反射类型描述,为什么还要造 `FStructTypeBitSet`?**
>
> 答案:Mass 在 EntityQuery 阶段需要做"集合运算"(我要含 A B 不含 C 的 entity),`UScriptStruct*` 是 8 字节指针,集合运算 O(N²) 退化严重。BitSet 把"类型"压缩成 1 个位,集合运算变成 64 位整数 AND/OR/XOR,**几个数量级提速**。
>
> 这一节我们把 BitSet 的设计、性能对比、与传统反射的协作关系一次讲透,作为本章收尾,也为 §17(Mass 内存模型)埋下伏笔。
>
> **预备知识**:§2.1 / §2.2 / §2.3 反射全套。
>
> **读完之后你能做到**:
> - 看到 Mass 里 `FMassFragmentBitSet` / `FMassTagBitSet` 等类型,知道它们是**位图**而不是指针集合
> - 用 `TStructTypeBitSet` 给你自己的"类型集合"建立类似机制(罕见但偶尔有用)
> - 在 Mass Processor 设计时,知道 Query 阶段的集合运算如何被加速
> - 解释清楚 "为什么 Fragment 类型数量必须 < 几百"(BitSet 容量限制)
> - 在 Editor / 配置层 Mass 仍然用反射(Trait 是 UCLASS),区分两层语义

## 2.4.1 浅入:回到那个根本问题

我们已经知道:
- Mass Fragment 是 USTRUCT(§2.2)
- 每个 Fragment 类型在反射注册时变成一个 `UScriptStruct*`(§2.2.4.5)
- `UScriptStruct*` 是 8 字节指针,可比较,可哈希

那 Mass 直接用 `TSet<UScriptStruct*>` 来描述 archetype("我这个 archetype 含哪些 Fragment 类型")不就好了吗?

**问题来了**:Mass 最热的操作是 **EntityQuery**:

> "找出所有含 `FMovementFragment` 和 `FHealthFragment`,但不含 `FDeadTag` 的 entity。"

Query 在每个 Processor 的 Execute 里跑,**每帧调用几十到几百次**。每次需要做的集合运算:
- `Archetype.Fragments ⊇ Required` 测试包含
- `Archetype.Fragments ∩ None == ∅` 测试排除

如果用 `TSet<UScriptStruct*>`:
- 每个 archetype 含 5-30 个 Fragment 类型
- 测试 `⊇`:对每个 Required 元素,在 Archetype set 里查找(`O(NumRequired × log NumArchetypeFragments)`)
- 几百个 archetype × 几十个 Query × 每帧 = 数十万次 Set 查找

跑得动?跑得动。**够快吗**?**完全不行**。

`TSet<UScriptStruct*>` 的内存布局是 SparseArray + HashTable(§1.6.6),最佳查询都是 100ns 量级。把上面式子代入:数十万次 × 100ns = **几十毫秒**。预算外了。

### 2.4.1.1 BitSet 的对比

如果**所有 Fragment 类型在系统启动时被分配 0..N-1 的整数 index**,且 N < 256,我们可以用一个 64 字节(512 位)的位图表示"含有哪些 Fragment 类型":

```
位图 A(Archetype):  0001011010100100 ... (位 i = 1 表示含第 i 种 Fragment)
位图 R(Required):   0001000010000100 ...
位图 N(None):       0000000000010000 ...

测试 A ⊇ R:  (A & R) == R              ← 一条 AND + 一条 CMP,~1ns
测试 A ∩ N == ∅:  (A & N) == 0         ← 一条 AND + 一条 CMP,~1ns
```

**单次查询从 ~100ns 降到 ~1ns,100 倍提速**。整体 Query 时间从几十毫秒降到几十微秒。

这就是 BitSet 的根本动机。

## 2.4.2 `TStructTypeBitSet` —— 通用的"类型集合位图"

5.7 起,这套机制从 Mass 抽出来,放在 CoreUObject:

```
Engine/Source/Runtime/CoreUObject/Public/StructUtils/StructTypeBitSet.h
```

(在 5.5+ 之前可能在独立的 `StructUtils` 模块,5.7 已并入 CoreUObject。)

### 2.4.2.1 模板声明

`StructTypeBitSet.h:820`:

```cpp
template<typename TBaseStruct, typename TStructTrackerWrapper, typename TUStructType = UScriptStruct>
struct TStructTypeBitSet 
    : TTypeBitSetBase<TStructTypeBitSet<TBaseStruct, TStructTrackerWrapper, TUStructType>, 
                       TBaseStruct, TUStructType, FStructTypeBitSet::FBitSetContainer>
{
    // ... 各种集合操作 ...
};
```

参数:
- `TBaseStruct` — "我这个 BitSet 跟踪的类型,必须是 TBaseStruct 的子类"。例 `FMassFragment`。
- `TStructTrackerWrapper` — 提供静态 `FStructTracker` 实例的 wrapper。每个 BitSet 实例化各自一个 tracker(分配类型→位 index)。
- `TUStructType` — 反射元类型,默认 `UScriptStruct`(也可以是 `UClass`,如果你想跟踪 UCLASS 而不是 USTRUCT)。

### 2.4.2.2 用法宏

`StructTypeBitSet.h:801-813` 注释里给了用法:

```cpp
// 头文件
DECLARE_STRUCTTYPEBITSET_EXPORTED(MYMODULE_API, FMyBitSet, FMyBaseStruct);

// .cpp
DEFINE_TYPEBITSET(FMyBitSet);
```

宏展开后大致:
```cpp
struct FMyBitSet_TrackerWrapper { static FStructTracker StructTracker; };
using FMyBitSet = TStructTypeBitSet<FMyBaseStruct, FMyBitSet_TrackerWrapper>;
```

### 2.4.2.3 Mass 的五种 BitSet

`Engine/Source/Runtime/MassEntity/Public/MassEntityTypes.h:28-32`:

```cpp
DECLARE_STRUCTTYPEBITSET_EXPORTED(MASSENTITY_API, FMassFragmentBitSet, FMassFragment);
DECLARE_STRUCTTYPEBITSET_EXPORTED(MASSENTITY_API, FMassTagBitSet, FMassTag);
DECLARE_STRUCTTYPEBITSET_EXPORTED(MASSENTITY_API, FMassChunkFragmentBitSet, FMassChunkFragment);
DECLARE_STRUCTTYPEBITSET_EXPORTED(MASSENTITY_API, FMassSharedFragmentBitSet, FMassSharedFragment);
DECLARE_STRUCTTYPEBITSET_EXPORTED(MASSENTITY_API, FMassConstSharedFragmentBitSet, FMassConstSharedFragment);
```

五种独立 BitSet,**互不混用**:
- `FMassFragmentBitSet` 跟踪 `FMassFragment` 子类(普通数据 Fragment)
- `FMassTagBitSet` 跟踪 `FMassTag` 子类(无数据标记 Tag)
- `FMassChunkFragmentBitSet` 跟踪 `FMassChunkFragment` 子类(每 chunk 一份的共享数据)
- `FMassSharedFragmentBitSet` 跟踪 `FMassSharedFragment` 子类(跨 archetype 可写共享)
- `FMassConstSharedFragmentBitSet` 跟踪 `FMassConstSharedFragment` 子类(只读共享)

每种 BitSet 内部各有自己的 `FStructTracker`,互不干扰地分配位 index。

## 2.4.3 `FStructTracker` —— 类型 → 位 index 的注册表

`StructTypeBitSet.h` 里的核心类(简化伪代码):

```cpp
class FStructTracker
{
    // 注册过的所有类型(按位 index 排列)
    TArray<TWeakObjectPtr<const UStruct>> StructTypesList;
    
    // 类型 → 位 index 的反查
    TMap<const UStruct*, int32> StructTypeToIndexMap;
    
    int32 GetOrCreateIndex(const UStruct* StructType)
    {
        if (int32* Existing = StructTypeToIndexMap.Find(StructType))
        {
            return *Existing;
        }
        int32 NewIndex = StructTypesList.Add(StructType);
        StructTypeToIndexMap.Add(StructType, NewIndex);
        return NewIndex;
    }
};
```

**关键**:**第一次见到某 Struct 类型时,分配下一个空位 index**(0, 1, 2, 3, ...)。索引在该 BitSet 类型的整个生命周期(进程内)**永久稳定**。

### 2.4.3.1 Lazy 注册的好处

不需要"启动期一次性注册全部类型"。Plugin 动态加载时,新出现的 Fragment 类型自动获得下一个空位 index,无需特殊处理。

### 2.4.3.2 Lazy 注册的代价

不同次启动 / 不同模块加载顺序,**同一类型的 index 可能不同**!

这意味着:
- BitSet 不能跨进程序列化(发到网络 / 存盘)
- BitSet 不能 hard-code(`if (BitSet[3]) ...` 是危险的,3 这个数依赖加载顺序)

**实战影响**:Mass 的 BitSet 在网络层**不直接传输**。复制时传"Fragment 类型的 FName / 反射指针",收端再查本地 index。

## 2.4.4 BitSet 容器 —— `FBitSetContainer`

每个 TStructTypeBitSet 内部一个 `FStructTypeBitSet::FBitSetContainer StructTypesBitArray;`,这是个动态扩容的位数组(类似 `TBitArray`)。

容量随注册类型数自动扩 — 每加 64 种类型容器扩一个 uint64。不像编译期固定 64 位的常规 bitset,**动态 BitSet 的容量没有硬上限**(只受内存限制)。

但实战上 Mass 各 BitSet 的类型数应该控制:

| BitSet 类型 | 推荐上限 | 理由 |
|---|---|---|
| FragmentBitSet | < 256 | Query 越多越慢(每次 256 位 = 32 字节比较) |
| TagBitSet | < 128 | 同上 |
| ChunkFragmentBitSet | < 32 | chunk 共享内存有限 |
| SharedFragmentBitSet | < 64 | |

Mass 项目里如果 Fragment 类型超过 256,**说明你的设计有重复造轮子** — 用 SharedFragment / Tag / 组合数据结构压缩。

## 2.4.5 BitSet 的核心操作(性能数量级)

### 2.4.5.1 添加 / 删除 / 查询

```cpp
FMassFragmentBitSet S;

// Add 一个类型
S.Add(*FMassMovementFragment::StaticStruct());          // 也有模板版本 S.Add<FMassMovementFragment>()

// Remove
S.Remove<FMassMovementFragment>();

// Contains
bool b = S.Contains<FMassHealthFragment>();
```

实际操作:
- `Add` = `Tracker.GetOrCreateIndex(Type)` + 设置位
- `Remove` = 清除位
- `Contains` = 读位

每个操作几纳秒。

### 2.4.5.2 集合运算

```cpp
FMassFragmentBitSet A, B;
A += B;              // A = A ∪ B(union)
A -= B;              // A = A \ B(difference)

bool b1 = A.HasAll(B);          // A ⊇ B  ← Query Required 检查
bool b2 = A.IsEmpty();
bool b3 = (A & B).IsEmpty();    // A ∩ B == ∅  ← Query None 检查
```

操作直接在底层 `TBitArray` 上做按字 SIMD 友好的 AND/OR。**对于 256 位以内的 BitSet,所有集合运算都是几纳秒**。

### 2.4.5.3 性能对照表

| 操作 | TSet<UScriptStruct*> | FStructTypeBitSet |
|---|---|---|
| Add | ~100 ns | ~5 ns |
| Remove | ~100 ns | ~3 ns |
| Contains | ~50 ns | ~2 ns |
| 测 ⊇(子集判断) | ~100 ns × N | ~5 ns(整体) |
| 测 ∩ == ∅ | ~100 ns × N | ~5 ns(整体) |

**整体 Query 性能差 50-100 倍**。这就是 Mass 几十万 entity 还能跑得起来的核心数据结构武器。

## 2.4.6 BitSet 与传统反射的协作关系

注意:**Mass 没有抛弃反射**!它用反射做"启动期类型注册",运行时 hot path 走 BitSet。两层关系:

```
启动期(反射)
  │
  ↓ 通过 UHT 反射注册,生成 UScriptStruct*
  │
  ↓ Mass 第一次见到某类型(Spawn / Query 配置时)
  │
  ↓ FStructTracker 分配位 index
  │
  ↓ 后续:类型 ↔ index 通过 Tracker 双向映射
  │
运行时 hot path(BitSet)
  │
  ↓ Query 全部走位运算
  │
  ↓ 偶尔需要"按 BitSet 反查 UScriptStruct*"(序列化、调试)
  │   通过 Tracker.StructTypesList[Index] 查回
```

### 2.4.6.1 Query 的实际代码长什么样

简化(后面 §18 详讲):

```cpp
class UMyMassProcessor : public UMassProcessor
{
    FMassEntityQuery Query;
    
    virtual void ConfigureQueries() override
    {
        // 这一步把"需要 / 排除哪些类型"转成 BitSet
        Query.AddRequirement<FMovementFragment>(EMassFragmentAccess::ReadWrite);
        Query.AddRequirement<FHealthFragment>(EMassFragmentAccess::ReadOnly);
        Query.AddTagRequirement<FActiveTag>(EMassFragmentPresence::All);
        Query.AddTagRequirement<FDeadTag>(EMassFragmentPresence::None);
    }

    virtual void Execute(...) override
    {
        Query.ForEachEntityChunk(...);   // 内部用 BitSet 过滤匹配 archetype
    }
};
```

`AddRequirement<T>()` 内部干两件事:
1. `T::StaticStruct()` 拿反射指针
2. 把它注册到 Query 的 `RequiredFragments` BitSet

`Execute` 时,Query 拿着这些 BitSet,与每个 archetype 的 `Composition` BitSet 做 AND/OR 比较,O(1) 决定 archetype 是否匹配。

## 2.4.7 Trait 配置层 —— 这里仍然用传统反射

刚强调 Mass hot path 用 BitSet。但 Mass 的"配置层"完全是传统反射的天下。

### 2.4.7.1 Trait 是 UCLASS

```cpp
UCLASS(meta = (DisplayName = "RTS Movement Trait"))
class MYRTSMASS_API URTSMovementTrait : public UMassEntityTraitBase
{
    GENERATED_BODY()

protected:
    UPROPERTY(EditAnywhere, Category="Movement")
    float MaxSpeed = 5.0f;

    UPROPERTY(EditAnywhere, Category="Movement")
    float Acceleration = 2.0f;
    
    virtual void BuildTemplate(FMassEntityTemplateBuildContext& BuildContext, ...) const override;
};
```

`URTSMovementTrait` 是 UCLASS。Editor 里:
- 资产 EntityConfig 用 Property panel 列出 Trait 字段(`MaxSpeed` / `Acceleration`)— **靠反射**
- 序列化 Trait 资产到 .uasset — **靠反射**
- BP 节点引用 Trait — **靠反射**

这些都是低频(Editor 操作 / 配置加载),反射的 ~500ns 开销不重要。

### 2.4.7.2 Trait 在运行时的 BuildTemplate

但当 Spawner 实际**生成 entity** 时,Trait 的 `BuildTemplate` 被调:

```cpp
void URTSMovementTrait::BuildTemplate(FMassEntityTemplateBuildContext& BuildContext, ...) const
{
    // 反射的 MaxSpeed 字段,转成运行时 Fragment 数据
    BuildContext.AddFragment<FMassMovementFragment>(/* init data with MaxSpeed */);
    BuildContext.AddTag<FActiveTag>();
}
```

`AddFragment<T>` 内部走 BitSet,把 T 加进 entity template 的 Fragment composition。**Trait 是从"反射配置"到"BitSet 运行时"的桥梁**。

### 2.4.7.3 完整数据流

```
EntityConfig 资产(.uasset,用反射序列化)
   ↓
URTSMovementTrait(UCLASS,反射字段)
   ↓ BuildTemplate (将"配置"转成"运行时")
   ↓
FMassEntityTemplate(运行时数据)
   - FragmentBitSet:位图描述类型
   - InitialValues:每 Fragment 的初始值
   ↓ Spawn 时复用这个 template
   ↓
FMassEntity(实际 entity)
   - 数据存在 archetype chunk 里(SoA)
   - 类型识别全程 BitSet
```

**两层语义清晰分离**:
- 配置层(反射)— 慢但有 Editor 友好性
- 运行时(BitSet)— 快但 Editor 不可见

## 2.4.8 Mass 与 GUObjectArray 的关系

### 2.4.8.1 Mass entity **不是 UObject**

每个 entity 是 `FMassEntityHandle = (Index, SerialNumber)` 的 8 字节 ID。**不进 GUObjectArray**,**不被 GC 扫**。

50K entity 进 GUObjectArray?那 GC 单次扫描就不可接受。Mass 的整个设计动机就是绕开 UObject 的开销。

### 2.4.8.2 Mass 内部用到 UObject 的地方

但 Mass 框架自身仍然依赖大量 UObject:

| Mass 组件 | 是 UObject 吗 |
|---|---|
| `UMassEntitySubsystem` | ✓ UWorldSubsystem |
| `UMassProcessor` | ✓ UCLASS,Editor 可配 |
| `UMassEntityTraitBase` | ✓ UCLASS |
| `UMassEntityConfigAsset` | ✓ UDataAsset |
| `UScriptStruct*`(Fragment 类型描述) | ✓ |
| `FMassEntityHandle`(实际 entity ID) | ✗ |
| `FMassFragment`(数据 USTRUCT) | ✗(USTRUCT 注册到反射,但实例不是 UObject) |
| `FMassArchetypeData` | ✗ |
| `FMassArchetypeChunk` | ✗ |

**框架结构**用 UObject(Editor / 反射 / 配置),**实例数据**绝不是 UObject(性能 / 规模)。这条分界是 Mass 的设计精髓。

### 2.4.8.3 Fragment 持有 UObject 的安全姿势

```cpp
USTRUCT()
struct FMyFragment : public FMassFragment
{
    GENERATED_BODY()

    // ❌ 危险:裸 UObject 指针,不被 GC 标记
    UStaticMesh* Mesh;

    // ✅ 安全:TObjectPtr,Mass 内部知道怎么扫
    UPROPERTY()
    TObjectPtr<UStaticMesh> Mesh;
};
```

`TObjectPtr<>` 在 Fragment 里被 Mass 自动**注册到 GC 引用扫描列表**。后面 §4 详讲 GC,§17 详讲 Fragment 持有 UObject 的细节。

## 2.4.9 RTS 项目的实战纪律

### (1)Fragment 类型数量保守

数十种 Fragment + 数十种 Tag,合理。**上百种**说明你设计有问题(见 §17 的 Fragment 设计原则)。

### (2)Query 设计追求最小匹配集

写 Processor 的 Query 时,**Required 字段越多,匹配的 archetype 越少,遍历越快**:

```cpp
// 不好:Query 太宽,几乎所有 entity 都匹配
Query.AddRequirement<FTransformFragment>(...);

// 好:Query 精确,只匹配真正需要处理的
Query.AddRequirement<FTransformFragment>(...);
Query.AddRequirement<FMovementFragment>(...);
Query.AddTagRequirement<FActiveTag>(EMassFragmentPresence::All);
Query.AddTagRequirement<FFrozenTag>(EMassFragmentPresence::None);
```

这与 SQL 索引选择性原则相同。

### (3)用 Tag 表达 enum 而不是 Fragment 字段

```cpp
// ❌ 用 Fragment 内 enum 字段
USTRUCT() struct FStateFragment : public FMassFragment
{
    UPROPERTY() EUnitState State;     // Idle / Moving / Attacking / Dead
};

// ✅ 用 Tag(无数据,纯位)
USTRUCT() struct FIdleTag : public FMassTag {};
USTRUCT() struct FMovingTag : public FMassTag {};
USTRUCT() struct FAttackingTag : public FMassTag {};
USTRUCT() struct FDeadTag : public FMassTag {};
```

Tag 版本的好处:
- Query 直接 `AddTagRequirement<FIdleTag>(EMassFragmentPresence::All)`,**整 archetype 跳过**不匹配的
- 无运行时分支检查(`if (State == EUnitState::Idle)`)
- 状态转换时**重新分配 archetype**(idle → attacking 时换 archetype),memory locality 自动改善

### (4)Trait 的反射开销可以接受

Trait 是配置,Editor 用反射没问题。**但** Trait 的 `BuildTemplate` 是热点(spawn 时反复调),内部不要再 reflect 查询字段值,**直接 C++ 访问成员**。

## 2.4.10 自己用 TStructTypeBitSet —— 罕见但有趣

如果你 RTS 项目有非 Mass 的"类型集合"需求(典型:技能效果集合,如"流血 + 中毒 + 减速"),可以复用同一机制:

```cpp
// MyRTSEffects.h
USTRUCT()
struct FRTSEffectBase { GENERATED_BODY() };

USTRUCT() struct FBleedEffect : public FRTSEffectBase { GENERATED_BODY() };
USTRUCT() struct FPoisonEffect : public FRTSEffectBase { GENERATED_BODY() };
// ...

DECLARE_STRUCTTYPEBITSET_EXPORTED(MYRTS_API, FRTSEffectBitSet, FRTSEffectBase);

// MyRTSEffects.cpp
DEFINE_TYPEBITSET(FRTSEffectBitSet);
```

然后:
```cpp
FRTSEffectBitSet Effects;
Effects.Add<FBleedEffect>();
Effects.Add<FPoisonEffect>();

if (Effects.Contains<FBleedEffect>()) { /* 流血处理 */ }

// 集合运算
FRTSEffectBitSet Removable;
Removable.Add<FBleedEffect>();
Effects -= Removable;   // 移除流血
```

**性能**:与 Mass 内部 BitSet 一致 — 几纳秒级。

**适用场景**:你有"少量(< 64 个)、稳定的、需要组合判断"的类型集合。技能效果、buff、debuff、武器特性、单位天赋,都是候选。
