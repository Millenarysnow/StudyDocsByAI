# §1.3 全局 GMalloc 的初始化时机 — 从 LaunchEngineLoop 到 GCreateMalloc

> **本节地图**:模块一第 1 章第 3 节。§1.2 看清了 `FMemory::Malloc → GMalloc->Malloc` 的转发链。这一节我们追问:**`GMalloc` 是怎么"凭空冒出来"的?它什么时候、被谁、用什么算法创建的?**
>
> 你会发现答案出乎意料:**GMalloc 不是被显式初始化的**,而是**懒加载**。第一次任何代码调用 `FMemory::Malloc`(可能是 main 之前某个全局静态变量的构造里),触发延迟创建。这是个非常优雅的设计 — 我们把它一层层拆开。
>
> **预备知识**:§1.1 平台抽象、§1.2 FMemory 入口。
>
> **读完之后你能做到**:
> - 画出从 `WinMain` 到 GMalloc 第一次可用的完整时序
> - 知道 Editor / Game / Server / Shipping 在 Win64 下默认 `GMalloc` 是哪个分配器
> - 通过命令行 (`-binnedmalloc3` / `-tbbmalloc` / `-stompmalloc` ...) 切换 GMalloc 的实际类型
> - 理解 GMalloc 外面包的 **proxy 链**(MemoryTrace / Stomp2 / ThreadSafe / LeakDetection / Poison / DoubleFreeFinder / FrameProfiler)
> - 改 Engine 时知道在哪儿插入自己的 proxy

## 1.3.1 浅入:GMalloc 的"鸡生蛋"再访

UE 想让所有内存分配走 `GMalloc`。但 `GMalloc` 本身需要被构造。问题:

- 谁来构造 GMalloc?
- 在什么时候构造?
- 在它构造好之前,引擎里别的全局静态对象需要分配内存(比如 `static FString GFoo = TEXT("hello")` 在 main 之前就要构造,FString 内部要 alloc)— 怎么办?

UE 的答案是**完全不在固定位置初始化 GMalloc**。它走 **lazy initialization**:谁第一次需要内存,谁顺手把 GMalloc 建起来。

这听起来违反直觉。让我们从最早期的代码开始看。

---

## 1.3.2 进程启动的最早三步:WinMain → GuardedMain → PreMainInit

### Step 1 — `WinMain`(Windows 平台入口)

`Engine/Source/Runtime/Launch/Private/Windows/LaunchWindows.cpp` 末尾(具体 `WinMain` 实现在文件末尾的 200+ 行附近)。简化逻辑:

```cpp
// LaunchWindows.cpp(简化)
int WINAPI WinMain(HINSTANCE hInInstance, HINSTANCE, char* pCmdLine, int /*nCmdShow*/)
{
    // C 运行时基础设施
    SetupWindowsEnvironment();
    
    // 拉起命令行
    const TCHAR* CmdLine = ::GetCommandLineW();
    
    // SEH 异常包装(__try)然后调真正的入口
    int32 ErrorLevel = GuardedMainWrapper(CmdLine);
    
    return ErrorLevel;
}
```

关键观察:`WinMain` 还**没**调任何 `FMemory::Malloc`。但是:

**C++ 全局静态对象的构造发生在 `WinMain` 之前**(C 运行时启动时执行)。这意味着,UE 庞大的全局静态变量(`UE::Private::GMalloc` 本身、`GLog`、各种 `DEFINE_LOG_CATEGORY` 的对象、各种 `FAutoConsoleVariable` 注册...)在 `WinMain` 还没到的时候就都构造完了。

这些静态构造里,**有些不分配内存**(例如 `bool GFoo = false;` —— 普通 POD)。**有些会分配内存**(例如 `static FString GBar = TEXT("hello");` —— FString 构造函数 `FMemory::Malloc`)。

后者就触发了 GMalloc 的 lazy 初始化。

### Step 2 — `GuardedMainWrapper`

`LaunchWindows.cpp:113`:

```cpp
// LaunchWindows.cpp:113
LAUNCH_API int32 GuardedMainWrapper(const TCHAR* CmdLine)
{
    int32 ErrorLevel = 0;
    if (GEnableInnerException)  // 默认 true 在 Win64
    {
        __try
        {
            ErrorLevel = GuardedMain(CmdLine);
        }
        __except(...)
        {
            // 异常处理
        }
    }
    else
    {
        ErrorLevel = GuardedMain(CmdLine);
    }
    return ErrorLevel;
}
```

`GuardedMainWrapper` 只是 SEH(Windows Structured Exception Handling)的一层包装,让 crash 能被 UE 自己的 crash handler 捕获。它本身不做业务。

### Step 3 — `GuardedMain`

`Engine/Source/Runtime/Launch/Private/Launch.cpp:87`:

```cpp
// Launch.cpp:87(简化)
int32 GuardedMain(const TCHAR* CmdLine)
{
    FTrackedActivity::GetEngineActivity().Update(TEXT("Starting"), ...);

    FTaskTagScope Scope(ETaskTag::EGameThread);
    GGameThreadId = FPlatformTLS::GetCurrentThreadId();
    GIsGameThreadIdInitialized = true;
    
    // ... 等待调试器附加(-WaitForDebugger)的可选逻辑 ...
    
    BootTimingPoint("DefaultMain");

    // ★ 关键:这里第一次广播一个委托
    FCoreDelegates::GetPreMainInitDelegate().Broadcast();
    
    // ... 设置清理 guard ...
    
    // 执行真正的引擎初始化
    int32 ErrorLevel = EnginePreInit(CmdLine);    // 内部调 FEngineLoop::PreInit
    
    // ... 后续 EngineInit / Tick loop / Exit ...
}
```

`FCoreDelegates::PreMainInit` 是个广播事件。在 UE 5.x 里很多基础设施(包括引擎反射、CoreUObject 注册)挂在它上面。但在它**广播之前**,所有需要分配内存的 C++ 全局静态构造**已经跑完了**。

**所以 `GMalloc` 几乎肯定**在 `GuardedMain` 的第一行执行之前**就已经被建好了**。让我们看是怎么建的。

## 1.3.3 `GMalloc` 的 lazy 初始化路径

### 1.3.3.1 第一次 `FMemory::Malloc` 触发

回顾 §1.2.5。`FMemory::Malloc` 内部用的 `FMemory_MallocInline` 有这段:

```cpp
// HAL/FMemory.inl:28
if (UNLIKELY(!FMEMORY_INLINE_GMalloc))
{
    Alloc = FMemory::MallocExternal(Count, Alignment);
}
```

`FMEMORY_INLINE_GMalloc` 在 `UnrealMemory.cpp` 编译时定义为 `UE::Private::GMalloc`。第一次 alloc 时它是 `nullptr`,所以走 `MallocExternal`。

### 1.3.3.2 `MallocExternal` 触发 `GCreateMalloc`

`UnrealMemory.cpp:491`:

```cpp
// UnrealMemory.cpp:491
void* FMemory::MallocExternal(SIZE_T Count, uint32 Alignment)
{
    if (!UE::Private::GMalloc)
    {
        GCreateMalloc();
        CA_ASSUME(UE::Private::GMalloc != nullptr);
    }
    return UE::Private::GMalloc->Malloc(Count, Alignment);
}
```

`GCreateMalloc()` 是 `FMemory` 的私有静态方法,这是 GMalloc 唯一的创建入口。

### 1.3.3.3 `GCreateMalloc` —— 仅仅是个线程安全壳

`UnrealMemory.cpp:427`:

```cpp
// UnrealMemory.cpp:427
void FMemory::GCreateMalloc()
{
#if defined(REQUIRE_EXPLICIT_GMALLOC_INIT) && REQUIRE_EXPLICIT_GMALLOC_INIT
    checkf(false, TEXT("Allocating before ExplicitInit()"));
#else
    // On some platforms (e.g. Mac) GMalloc can be created on multiple threads at once.
    // This admittedly clumsy construct ensures both thread-safe creation and prevents multiple calls into it.
    static int ThreadSafeCreationResult = FMemory_GCreateMalloc_ThreadUnsafe();
#endif
}
```

注意 `static int ThreadSafeCreationResult = FMemory_GCreateMalloc_ThreadUnsafe();`。

**这是 C++11 起的"线程安全静态初始化"**:C++ 编译器保证 `static` 局部变量的初始化**最多只执行一次**,且**线程安全**(底层用 once flag + 双重检查锁)。

所以即使两个线程同时进入 `GCreateMalloc`,实际只有一个会执行 `FMemory_GCreateMalloc_ThreadUnsafe`,另一个会被阻塞,等待第一个完成后取已构造好的 GMalloc。

注意这里的两个标志:
- `REQUIRE_EXPLICIT_GMALLOC_INIT`:某些平台(主机)要求 GMalloc 必须**显式**初始化,不允许 lazy。这种情况下 `GCreateMalloc` 直接 fail。配合 `FMemory::ExplicitInit`(§1.2.10)使用。
- 默认情况下走 lazy 创建。

### 1.3.3.4 真正的工作:`FMemory_GCreateMalloc_ThreadUnsafe`

`UnrealMemory.cpp:344`:

```cpp
// UnrealMemory.cpp:344(完整流程)
static int FMemory_GCreateMalloc_ThreadUnsafe()
{
    // Step 1:让平台决定基础分配器
    UE::Private::GMalloc = FPlatformMemory::BaseAllocator();

#if !PLATFORM_MAC
    FPlatformMemoryStats Stats = FPlatformMemory::GetStats();
    uint64 ProgramSize = Stats.UsedPhysical;
#endif

    // Step 2:接入 malloc crash handler
    FPlatformMallocCrash::Get(UE::Private::GMalloc);

#if PLATFORM_USES_FIXED_GMalloc_CLASS
    // 主机平台:固定分配器,不允许 proxy 链
    if (!UE::Private::GMalloc->IsInternallyThreadSafe())
    {
        UE_LOG(LogMemory, Fatal, TEXT("..."));
    }
#else
    // PC 平台:在主分配器外面套一层层 proxy

    // Step 3a:Memory Trace 包一层(Insights Memory 面板要看到所有 alloc)
#if UE_MEMORY_TRACE_ENABLED
    FMalloc* TraceMalloc = MemoryTrace_Create(UE::Private::GMalloc);
    if (TraceMalloc != UE::Private::GMalloc)
    {
        UE::Private::GMalloc = TraceMalloc;
        MemoryTrace_Initialize();
    }
#endif

    // Step 3b:可选 -stomp2malloc
#if WITH_MALLOC_STOMP2
    UE::Private::GMalloc = FMallocStomp2::OverrideIfEnabled(UE::Private::GMalloc);
#endif

    // Step 3c:线程安全 proxy(分配器自己已线程安全则跳过)
    if (!UE::Private::GMalloc->IsInternallyThreadSafe())
    {
        UE::Private::GMalloc = new FMallocThreadSafeProxy(UE::Private::GMalloc);
    }

    // Step 3d:可选 -mallocverify
#if MALLOC_VERIFY
    UE::Private::GMalloc = new FMallocVerifyProxy(UE::Private::GMalloc);
#endif

    // Step 3e:可选 -mallocleakdetect
#if MALLOC_LEAKDETECTION
    UE::Private::GMalloc = new FMallocLeakDetectionProxy(UE::Private::GMalloc);
#endif

    // Step 3f:Debug / Development 默认开 poison 检测
#if UE_USE_MALLOC_FILL_BYTES
    UE::Private::GMalloc = new FMallocPoisonProxy(UE::Private::GMalloc);
#endif

#endif // !PLATFORM_USES_FIXED_GMalloc_CLASS

#if !PLATFORM_DESKTOP
    // 主机:打印一下启动期已用内存
    double SizeInMb = (double)ProgramSize / (1024.0 * 1024.0);
    FPlatformMisc::LowLevelOutputDebugStringf(TEXT("Used memory before allocating anything was %.2fMB\n"), SizeInMb);
#endif

    // Step 4:可选的 double-free 检测和 frame profiler
    UE::Private::GMalloc = FMallocDoubleFreeFinder::OverrideIfEnabled(UE::Private::GMalloc);
    UE::Private::GMalloc = FMallocFrameProfiler::OverrideIfEnabled(UE::Private::GMalloc);

    // Step 5:通知分配器"初始化完成,可以开干了"
    UE::Private::GMalloc->OnMallocInitialized();

    return 0;
}
```

把这一坨翻译成人话:

**Step 1**:平台层选一个**主分配器**(MallocBinned2 / Binned3 / TBB / Mimalloc / Ansi 之一)。这是真正干活的家伙。

**Step 2**:挂上 crash handler(进程崩溃时仍能分配 fallback 内存来打印崩溃信息)。

**Step 3a-3f**:把主分配器**层层包装**:

```
原始:        GMalloc → MallocBinned2 → OS
              ↓
+MemTrace:    GMalloc → MemoryTrace → MallocBinned2 → OS
              ↓
+Stomp2:      GMalloc → MallocStomp2 → MemoryTrace → MallocBinned2 → OS
              ↓
+ThreadSafe:  (跳过,因为 MallocBinned2 自己已线程安全)
              ↓
+Verify:      (调试期才有)
              ↓
+Leak:        (-mallocleakdetect 启用)
              ↓
+Poison:      (Development 默认有,Shipping 没有)
              ↓
+DoubleFree:  (-doublefreefinder 启用)
              ↓
+FrameProf:   (-mallocframeprofiler 启用)
```

**每一层 proxy 都是 `FMalloc` 子类**,内部持有指向"下一层"的指针,自己 Malloc 时可能做些额外动作(打 log / poison 内存 / 记录调用栈)然后转发给下一层。

最终 `GMalloc` 指向**最外层的 proxy**。每次 `FMemory::Malloc` 都先走最外层,再一路传到底层。

**Step 5**:通知主分配器"我准备好了,可以开始 setup TLS cache 等事项"。`OnMallocInitialized` 是 `FMalloc` 的虚函数,默认空实现,具体分配器可能重写(MallocBinned2/3 会在这里启动 TLS cache 子系统,§1.5 详讲)。

### 1.3.3.5 这个时序图非常重要

```
进程启动
  │
  ├─ C 运行时启动期(global static initialization)
  │     │
  │     ├─ GFoo = TEXT("hello")  ← 触发 FString 构造,需要 alloc
  │     │     ↓
  │     │   FMemory::Malloc(N)
  │     │     ↓
  │     │   FMemory_MallocInline:GMalloc 是 nullptr,走 fallback
  │     │     ↓
  │     │   FMemory::MallocExternal
  │     │     ↓
  │     │   FMemory::GCreateMalloc                   ← 仅这一次,后续都直接走 GMalloc
  │     │     ↓
  │     │   FMemory_GCreateMalloc_ThreadUnsafe()
  │     │     ↓
  │     │   FPlatformMemory::BaseAllocator()         ← 选 MallocBinned2/3/TBB/Mimalloc
  │     │   挂 proxy 链
  │     │     ↓
  │     │   GMalloc 就绪
  │     │     ↓
  │     │   GMalloc->Malloc(N)  → 返回 ptr
  │     │
  │     └─ 之后所有 FMemory::Malloc 直接走 GMalloc(快速路径)
  │
  ├─ WinMain
  │     ↓
  ├─ GuardedMain
  │     ↓
  ├─ EnginePreInit → FEngineLoop::PreInit
  │     ↓
  ├─ EngineInit
  │     ↓
  └─ Tick loop
```

**关键观察**:`GMalloc` 在 `WinMain` 之前**就已经存在**,而且是被某个完全无关的全局 FString 构造"顺手"建起来的。

## 1.3.4 `FPlatformMemory::BaseAllocator` —— 主分配器选择算法

`Engine/Source/Runtime/Core/Private/Windows/WindowsPlatformMemory.cpp:136`,这是 Windows 实现:

```cpp
// WindowsPlatformMemory.cpp:136
FMalloc* FWindowsPlatformMemory::BaseAllocator()
{
    static FMalloc* Instance = nullptr;
    if (Instance != nullptr) return Instance;

    // ...

    // ── 第一阶段:编译期 / 全局宏决定默认分配器 ──
    if (FORCE_ANSI_ALLOCATOR)
    {
        AllocatorToUse = EMemoryAllocatorToUse::Ansi;
    }
#if PLATFORM_64BITS
    else if ((WITH_EDITORONLY_DATA || IS_PROGRAM || USING_INSTRUMENTATION) && MIMALLOC_ENABLED)
    {
        // Editor / 工具程序 / instrumentation 构建 → mimalloc
        // (5.x 把 mimalloc 推为 editor 默认,理由:相比 TBB 内存占用更低)
        AllocatorToUse = EMemoryAllocatorToUse::Mimalloc;
    }

    else if ((WITH_EDITORONLY_DATA || IS_PROGRAM) && TBBMALLOC_ENABLED)
    {
        // 没有 mimalloc 时回退 TBB

#if PLATFORM_64BITS

        AllocatorToUse = EMemoryAllocatorToUse::Binned3;
    }
#endif
    else if (USE_MALLOC_BINNED2)
    {
        AllocatorToUse = EMemoryAllocatorToUse::Binned2;
    }
    else
    {
        AllocatorToUse = EMemoryAllocatorToUse::Binned;
    }

    // ── 第二阶段:命令行参数覆盖(非 Shipping)──
#if !UE_BUILD_SHIPPING

    if (FCString::Stristr(CommandLine, TEXT("-libpasmalloc"))) AllocatorToUse = EMemoryAllocatorToUse::Libpas;
    else if (FCString::Stristr(CommandLine, TEXT("-ansimalloc")))   AllocatorToUse = EMemoryAllocatorToUse::Ansi;
#if TBBMALLOC_ENABLED
    else if (FCString::Stristr(CommandLine, TEXT("-tbbmalloc")))    AllocatorToUse = EMemoryAllocatorToUse::TBB;
#endif
#if MIMALLOC_ENABLED
    else if (FCString::Stristr(CommandLine, TEXT("-mimalloc")))     AllocatorToUse = EMemoryAllocatorToUse::Mimalloc;
#endif
#if PLATFORM_64BITS
    else if (FCString::Stristr(CommandLine, TEXT("-binnedmalloc3")))AllocatorToUse = EMemoryAllocatorToUse::Binned3;
#endif
    else if (FCString::Stristr(CommandLine, TEXT("-binnedmalloc2")))AllocatorToUse = EMemoryAllocatorToUse::Binned2;
    else if (FCString::Stristr(CommandLine, TEXT("-binnedmalloc"))) AllocatorToUse = EMemoryAllocatorToUse::Binned;
#if WITH_MALLOC_STOMP
    else if (FCString::Stristr(CommandLine, TEXT("-stompmalloc")))  AllocatorToUse = EMemoryAllocatorToUse::Stomp;

#endif
    if (FCString::Stristr(CommandLine, TEXT("-doublefreefinder")))  GMallocDoubleFreeFinderEnabled = true;
#endif // !UE_BUILD_SHIPPING

    // ── 第三阶段:实际构造 ──
    switch (AllocatorToUse)
    {
    case EMemoryAllocatorToUse::Ansi:    Instance = new FMallocAnsi();    break;
#if WITH_MALLOC_STOMP
    case EMemoryAllocatorToUse::Stomp:   Instance = new FMallocStomp();   break;
#endif
#if TBBMALLOC_ENABLED
    case EMemoryAllocatorToUse::TBB:     Instance = new FMallocTBB();     break;
#endif
#if MIMALLOC_ENABLED
    case EMemoryAllocatorToUse::Mimalloc:Instance = new FMallocMimalloc();break;
#endif
#if LIBPASMALLOC_ENABLED
    case EMemoryAllocatorToUse::Libpas:  Instance = new FMallocLibpas();  break;
#endif
    case EMemoryAllocatorToUse::Binned2: Instance = new FMallocBinned2(); break;
#if PLATFORM_64BITS
    case EMemoryAllocatorToUse::Binned3: Instance = new FMallocBinned3(); break;
#endif
    default:
    case EMemoryAllocatorToUse::Binned:
        Instance = new FMallocBinned((uint32)(GetConstants().BinnedPageSize & MAX_uint32), (uint64)MAX_uint32 + 1);
        break;
    }

    return Instance;
}
```

### 1.3.4.1 默认决策矩阵(Win64,5.7.3)

| 构建类型 | 默认分配器(无命令行覆盖) |
|---|---|

## 1.3.5 Proxy 链的"装饰器模式"

`MallocVerifyProxy` / `MallocPoisonProxy` / `MallocLeakDetectionProxy` 等都是经典的**装饰器**(Decorator)。它们都是 `FMalloc` 子类,内部持有一个 `FMalloc* UsedMalloc`(或类似名字)指向"下一层":

```cpp
// 简化的 FMallocProxyXxx 长这样
class FMallocPoisonProxy : public FMalloc
{
    FMalloc* UsedMalloc;       // 指向下一层
public:
    FMallocPoisonProxy(FMalloc* InNext) : UsedMalloc(InNext) {}

    virtual void* Malloc(SIZE_T Size, uint32 Alignment) override
    {
        void* Ptr = UsedMalloc->Malloc(Size, Alignment);
        if (Ptr) FMemory::Memset(Ptr, 0xCD, Size);   // 用 0xCD 填充,容易看出未初始化
        return Ptr;
    }

    virtual void Free(void* Ptr) override
    {
        if (Ptr)
        {
            SIZE_T Size = 0;
            UsedMalloc->GetAllocationSize(Ptr, Size);
            FMemory::Memset(Ptr, 0xDD, Size);        // 用 0xDD 填充,detect use-after-free
        }
        UsedMalloc->Free(Ptr);
    }
    // ... 其它虚函数转发 ...
};
```

每个 proxy 都按"先做点事,再 forward 给下一层"的模式。这个设计的妙处:**主分配器(MallocBinned2/3)对 proxy 完全无知**。你想加一层新功能,写一个新的 proxy 类塞进 `GCreateMalloc_ThreadUnsafe` 的链条里就行。

### 1.3.5.1 RTS 项目可以加自己的 Proxy

举个真实场景:你想在内存分配里**注入 RTS 自己的 LLM tag**,统计"每个 alloc 来自哪个 RTS 子系统"。可以:

```cpp
// MyRTSCore/Private/MyRTSMallocTagProxy.h
class FMyRTSMallocTagProxy : public FMalloc
{
    FMalloc* UsedMalloc;
public:
    FMyRTSMallocTagProxy(FMalloc* InNext) : UsedMalloc(InNext) {}

    virtual void* Malloc(SIZE_T Size, uint32 Alignment) override
    {
        void* Ptr = UsedMalloc->Malloc(Size, Alignment);
        // 你的统计逻辑
        if (Ptr && IsInRTSScope())
        {
            RecordRTSAlloc(Ptr, Size, GetCurrentRTSTagFromTLS());
        }
        return Ptr;
    }
    // ...其它虚函数转发...

    virtual bool IsInternallyThreadSafe() const override
    {
        return UsedMalloc->IsInternallyThreadSafe();
    }

    virtual const TCHAR* GetDescriptiveName() override
    {
        return TEXT("MyRTSMallocTagProxy");
    }
};
```

要把它注入 GMalloc 链,有两条路:
- **改 Engine**(`UnrealMemory.cpp:344` 加一行 `UE::Private::GMalloc = new FMyRTSMallocTagProxy(UE::Private::GMalloc);`)— rebase 友好性差
- **走 ExplicitInit**(§1.2.10)— 但需要主机/特殊配置,PC 默认 lazy init 不允许

**实际推荐**:不要为这种需求改分配器。用 LLM(Low Level Memory Tracker)的 `LLM_SCOPE_BYNAME` API,它已经内置了"按作用域归属"的统计能力。后面 §28 详讲 LLM 实战。

## 1.3.6 各分配器的快速概览(算法在 §1.4 详讲)

下表只给"是什么 + 何时选"的速览,具体算法 §1.4 一节专讲。

| 分配器 | 来源 | 默认场景 | 特点 |
|---|---|---|---|
| `FMallocAnsi` | `::malloc` | 仅故障排查 / `-ansimalloc` | 性能差,但行为最简单 |
| `FMallocBinned` | UE3 时代旧分配器 | 已退役 | 仅作为 fallback |
| `FMallocBinned2` | UE4 主流 | Win64 Game(无 Binned3 时) | SmallPool + LargePool,TLS 缓存,成熟稳定 |
| `FMallocBinned3` | UE5 新版 | Win64 Game(USE_MALLOC_BINNED3=1) | 64 位地址空间预留,VMA 直接映射,更适合大内存场景 |
| `FMallocTBB` | Intel TBB | (旧 Editor 默认) | Intel 实现,多线程友好 |
| `FMallocMimalloc` | Microsoft mimalloc | **Win64 Editor 默认** | 内存占用低,大对象友好 |
| `FMallocLibpas` | Apple libpas | macOS / iOS | Apple 平台专用 |
| `FMallocStomp` | UE 自家 | 仅 `-stompmalloc` | 每个分配独立页 + guard page,极度内存消耗,但**行级精度**检测越界 |
| `FMallocJemalloc` | jemalloc | Linux / Server | Facebook 实现,服务器场景常用 |

**对你 RTS 项目的实际意味**:
- **Editor 开发期** → Mimalloc(默认),不用动
- **Server build** → Binned2/3(默认),不用动
- **Game shipping** → Binned3(若 64 位平台),不用动
- **碰到诡异内存崩溃** → 临时启动加 `-stompmalloc` 复现 / 定位

你的代码**不应该**对底层分配器做任何假设。`FMemory::Malloc / Free` 是契约,具体实现是细节。

## 1.3.7 一个真实的启动期内存活动观察实验

这个实验帮你建立"启动期 GMalloc 创建" 的直觉:

### Step 1 — 在 `FMemory::GCreateMalloc` 入口设断点

VS 里打开 `Engine/Source/Runtime/Core/Private/HAL/UnrealMemory.cpp:427`,在 `void FMemory::GCreateMalloc()` 第一行下断点。

### Step 2 — 启动 Editor

F5 调试启动 `UnrealEditor.exe MyRTS.uproject`。

### Step 3 — 观察断点命中

断点会**在 main 之前**命中(可能很早,你一启动就触发)。看调用栈,你会看到类似:

```
FMemory_GCreateMalloc_ThreadUnsafe()
FMemory::GCreateMalloc()
FMemory::MallocExternal(SIZE_T, uint32)
FMemory_MallocInline(SIZE_T, uint32)        ← inline 展开
FMemory::Malloc(SIZE_T, uint32)
某个全局 FString / FName / FAutoConsoleVariable 的构造函数
全局静态构造列表(由 C runtime 调度)
mainCRTStartup
```

**根因**:你在断点命中时**还没**进 `WinMain`,这是 C++ 全局静态对象构造期间触发的。

### Step 4 — 看 GMalloc 实际类型

`FMemory_GCreateMalloc_ThreadUnsafe` 跑完后,Watch 窗口看 `UE::Private::GMalloc->GetDescriptiveName()`。在 Editor build 上你应该看到:`"MallocPoisonProxy"`(最外层)。一层层往里看 `UsedMalloc` 字段:

```
GMalloc
└─ FMallocPoisonProxy (UE_USE_MALLOC_FILL_BYTES=1 时)
   └─ FMallocLeakDetectionProxy (MALLOC_LEAKDETECTION 启用时)
      └─ FMallocVerifyProxy (MALLOC_VERIFY 启用时)
         └─ MemoryTrace 包装层 (UE_MEMORY_TRACE_ENABLED=1)
            └─ FMallocMimalloc / FMallocBinned3 / FMallocBinned2 / ...
```

具体看到几层取决于编译宏配置,你能直观地理解 proxy 链的"洋葱"结构。

### Step 5 — 看 Game build 的差异

切换到 Game/Shipping target,重复实验。你会看到 proxy 层数显著减少 — Shipping 默认关掉 `UE_USE_MALLOC_FILL_BYTES`、`MALLOC_VERIFY`、`MALLOC_LEAKDETECTION`,链条几乎只剩主分配器和最低限度的 MemoryTrace。

## 1.3.8 RTS 视角下的纪律

### (1)永远不要假设 GMalloc 是某个特定分配器

你的代码可能在:
- Editor(Mimalloc + 一堆 proxy)
- Standalone Game(Binned3,几乎裸)
- Server(Binned2 或 Binned3)
- 玩家电脑跑 `-tbbmalloc`(可能性低但存在)
- QA 跑 `-stompmalloc`(为了排查 bug)

任何"我知道分配器内部机制因此可以这样这样"的代码都是 bug。**只用 `FMemory::Malloc` 的契约 API**。

### (2)启动期(GMalloc 还未就绪)的全局静态对象

写法上这是两个阶段:

**阶段 A**:静态构造期(C runtime 启动),GMalloc 通过 lazy init 现场建。
**阶段 B**:`WinMain` 之后,GMalloc 已就绪。

99% 你的代码都在阶段 B,不需要担心。**少数你需要担心的场景**:
- 你写一个含 `static FMyClass GFoo;` 的代码,而 `FMyClass` 构造里访问了一些**还没初始化**的子系统(LogMacros 系统、CoreDelegates、UClass 反射注册)
- 这种问题不是 GMalloc 引起的(GMalloc 总是能用),而是其它子系统时序问题

**纪律**:**不要**写"全局静态非 POD 对象"。需要 process-level 单例,用 `Get()` 静态函数:

```cpp
// 不要这样
static FMyManager GManager;     // 啥时候构造的?

// 这样
class FMyManager {
public:
    static FMyManager& Get()
    {
        static FMyManager Singleton;   // 第一次 Get() 时构造,稳定且线程安全
        return Singleton;
    }
};
```

### (3)RTS 项目改 GCreateMalloc 链条的时机

理论上你可以加自己的 proxy。**实际上**:
- Mass Fragment / Chunk 的统计需求 → 用 LLM tag,不要改分配器
- 内存泄漏排查 → 用 Memory Insights 或 `-mallocleakdetect`,不要改分配器
- 性能 profiling → 用 stat memory + Insights,不要改分配器

我建过的所有商业项目里,**只有一次**真的需要改 GCreateMalloc 链 — 客户要求"任何超过 1MB 的分配自动打印调用栈到日志,用于审计"。这种合规驱动的需求才值得改。99% 别动。

## 1.3.9 改 Engine:加自己的 proxy(参考)

如果你确实有充分理由加 proxy,流程:

### Step 1 — 在 `Engine/Source/Runtime/Core/Public/HAL/` 加新头

`MyRTSMallocAuditProxy.h`:
```cpp
#pragma once
#include "HAL/MemoryBase.h"

class FMyRTSMallocAuditProxy : public FMalloc
{
    FMalloc* UsedMalloc;
public:
    explicit FMyRTSMallocAuditProxy(FMalloc* InNext) : UsedMalloc(InNext) {}

    // 必须实现的纯虚:
    virtual void* Malloc(SIZE_T Count, uint32 Alignment) override;
    virtual void* Realloc(void* Original, SIZE_T Count, uint32 Alignment) override;
    virtual void  Free(void* Original) override;

    // 推荐实现的(转发即可)
    virtual bool   GetAllocationSize(void* Original, SIZE_T& SizeOut) override
        { return UsedMalloc->GetAllocationSize(Original, SizeOut); }
    virtual SIZE_T QuantizeSize(SIZE_T Count, uint32 Alignment) override
        { return UsedMalloc->QuantizeSize(Count, Alignment); }
    virtual bool   IsInternallyThreadSafe() const override
        { return UsedMalloc->IsInternallyThreadSafe(); }
    virtual const TCHAR* GetDescriptiveName() override { return TEXT("MyRTSMallocAuditProxy"); }
    virtual void   Trim(bool bTrimThreadCaches) override { UsedMalloc->Trim(bTrimThreadCaches); }
    virtual void   SetupTLSCachesOnCurrentThread() override { UsedMalloc->SetupTLSCachesOnCurrentThread(); }
    // 其它...
};
```

### Step 2 — 实现 .cpp

```cpp
void* FMyRTSMallocAuditProxy::Malloc(SIZE_T Count, uint32 Alignment)
{
    void* Ptr = UsedMalloc->Malloc(Count, Alignment);
    if (Ptr && Count >= 1024 * 1024)  // 大于 1MB
    {
        FString Stack = FPlatformStackWalk::StackWalkAndDump(...);
        UE_LOG(LogRTSMemory, Warning, TEXT("Large alloc %lld bytes:\n%s"), Count, *Stack);
    }
    return Ptr;
}
// Realloc / Free 类似
```

### Step 3 — 在 `UnrealMemory.cpp:344` 插入 proxy

```cpp
// 在 OnMallocInitialized 之前加一行
#if WITH_RTS_MALLOC_AUDIT
    UE::Private::GMalloc = new FMyRTSMallocAuditProxy(UE::Private::GMalloc);
#endif
    
    UE::Private::GMalloc->OnMallocInitialized();
```

`WITH_RTS_MALLOC_AUDIT` 在你 Build.cs 里 `PrivateDefinitions.Add("WITH_RTS_MALLOC_AUDIT=1");` 启用。

### Step 4 — 别忘把这个改动写进 EnginePatches/

这是修改 Engine 的标准流程(§0.2.6)。
