# §0.1 UBT / UHT / 模块系统速通

> **本节地图**:这是技术内容的第一节,全书的"工程基础设施层"。后面**每一章**都会引用 `Build.cs` 配置、`Public/Private` 路径、`WITH_EDITOR` 宏 — 这些都不是 UE 的"业务代码",而是工具链产物。不把它们厘清,你看到 `#include "Engine/World.h"` 失败时连去哪里加一行都不知道。
>

> - 知道为什么有时候明明 .h 文件存在却 `#include` 失败

## 0.1.1 从最浅的问题开始:一段 C++ 怎么变成 UnrealEditor.exe

假设你有一段最简单的 C++:

```cpp
// MyHello.h
#pragma once
void SayHello();
```

```cpp
// MyHello.cpp
#include "MyHello.h"
#include <cstdio>
void SayHello() { printf("hello\n"); }
```

在普通的 C++ 项目里,你会写一个 CMakeLists.txt 或 Makefile,然后 `cmake --build` / `make`。

UE 不用 CMake,也不直接用 MSBuild。**UE 自己写了一套构建系统,叫 UnrealBuildTool(简称 UBT)**。它做了同样的事 — 决定哪些文件要编、用什么编译选项、链接成什么 — 只是工具变了。

那,UE 项目里**对应 CMakeLists.txt 的东西**是什么?是两类文件:

1. `*.Target.cs` — 一个**最终产物**的描述。一个 Target = 一个可执行文件(`.exe`)或一个最终库。
2. `*.Build.cs` — 一个**模块**的描述。一个 Module = 一组源代码 + 它的依赖关系。

我们用一个真实的例子串起来。

### 0.1.1.1 真实例子:UnrealEditor.exe 是怎么被造出来的

打开 `Engine/Source/UnrealEditor.Target.cs`(整个文件就 17 行,先全文贴出来):

```csharp
// Engine/Source/UnrealEditor.Target.cs
public class UnrealEditorTarget : TargetRules
{
    public UnrealEditorTarget( TargetInfo Target ) : base(Target)
    {
        Type = TargetType.Editor;
        IncludeOrderVersion = EngineIncludeOrderVersion.Latest;
        BuildEnvironment = TargetBuildEnvironment.Shared;
        bBuildAllModules = true;
        ExtraModuleNames.Add("UnrealGame");
    }
}
```

这个文件描述的产物就是 `UnrealEditor.exe`。我们逐字段读:

- `Type = TargetType.Editor`
  这是个 **Editor 类型**的产物。Editor / Game / Client / Server / Program 是五种类型,后面 0.1.5 详谈。**不同 Type 决定了这个 Target 链接哪些 Module、定义哪些宏**。
  
- `IncludeOrderVersion = EngineIncludeOrderVersion.Latest`
  IWYU(Include What You Use)迁移引入的开关。简单理解:用最新的"严格头文件包含"规则。
  
- `BuildEnvironment = TargetBuildEnvironment.Shared`
  是否允许跟其他 Editor target 共享中间产物(`Intermediate/Build/`)。Shared 意味着这个 Target 必须使用引擎默认的编译环境,不能自定义全局宏。

- `bBuildAllModules = true`
  把 `Engine/Source/Runtime/`、`Engine/Source/Editor/`、`Engine/Source/Developer/` 下**所有模块**都编进去。这就是为什么 Editor 能打开任何引擎类型的资产。

- `ExtraModuleNames.Add("UnrealGame")`
  额外加一个叫 "UnrealGame" 的 Module。这是给 Editor 内置的"空游戏"用的,你启动 Editor 不带 .uproject 时,默认进的就是它。

**关键认知**:Target.cs 不写一行 C++ 代码。它只是**配置**。它告诉 UBT:"我要造一个 Editor 类型的 .exe,把所有 Module 都编进来,再加一个叫 UnrealGame 的 Module"。

那 Module 在哪?

### 0.1.1.2 一个 Module 长什么样

我们看一个最重要、最庞大的 Module:**Core**。

```
Engine/Source/Runtime/Core/
├── Core.Build.cs              ← 模块描述文件(C# 写的)
├── Core_APL.xml               ← Android 平台资源描述
├── Public/                    ← 对外 API 头文件(其它模块能 #include)
│   ├── Core.h
│   ├── CoreMinimal.h
│   ├── Containers/            ← TArray / TMap / FString 等
│   ├── Math/                  ← FVector / FQuat / FMatrix
│   ├── Misc/                  ← 各种工具
│   └── ...
├── Private/                   ← 私有实现(只有本模块自己能 #include)
│   ├── CorePrivatePCH.h
│   ├── Containers/
│   ├── Math/
│   └── ...
├── Internal/                  ← Engine 内部友模块共享但对游戏隐藏
│   └── CoreGlobalsInternal.h
└── Tests/                     ← 模块测试
```

**这个目录就是一个 Module**。规则:
- 包含一个 `<ModuleName>.Build.cs` 的目录就是一个 Module。
- Module 的名字以 `.Build.cs` 前缀为准。`Core.Build.cs` → Module 叫 `"Core"`。
- 顶层不需要"注册"—— UBT 在编译时自己扫描整个目录树找 `.Build.cs`。

打开 `Core.Build.cs` 的开头(行 1-20):

```csharp
// Engine/Source/Runtime/Core/Core.Build.cs:1-20
public class Core : ModuleRules
{
    public Core(ReadOnlyTargetRules Target) : base(Target)
    {
        NumIncludedBytesPerUnityCPPOverride = 491520;
        PrivatePCHHeaderFile = "Private/CorePrivatePCH.h";
        SharedPCHHeaderFile = "Public/CoreSharedPCH.h";

        PrivateDependencyModuleNames.Add("BuildSettings");
        // ... 平台分支 ...
        PrivateDependencyModuleNames.Add("AtomicQueue");
        PrivateDependencyModuleNames.Add("AutoRTFM");
        PrivateDependencyModuleNames.Add("BLAKE3");
        PrivateDependencyModuleNames.Add("OodleDataCompression");
        PrivateDependencyModuleNames.Add("xxhash");

        PublicDependencyModuleNames.Add("GuidelinesSupportLibrary");
        PublicDependencyModuleNames.Add("TraceLog");
        PublicDependencyModuleNames.Add("AtomicQueue");
        // ... 后面还有 200+ 行 ...
```

到这里你应该已经看出全貌:
- Target.cs 描述"产物"
- Build.cs 描述"模块"
- Module 的代码就放在它自己的 `Public/` `Private/` 文件夹里

剩下的就是把每个字段讲清楚。

## 0.1.2 Build.cs 的依赖三件套(最常用,必须烂熟)

UE 的模块依赖由 Build.cs 里几个 `*ModuleNames` 列表决定。这一节是你**每天都会修改的字段**。

```csharp
PublicDependencyModuleNames     // 公开依赖:.h 暴露 + .lib 链接
PrivateDependencyModuleNames    // 私有依赖:.h 不暴露 + .lib 链接
PublicIncludePathModuleNames    // 公开头文件路径暴露,不链接
PrivateIncludePathModuleNames   // 私有头文件路径暴露,不链接
DynamicallyLoadedModuleNames    // 运行时动态加载,不在静态依赖图里
```

下面逐个讲。

### 0.1.2.1 PublicDependencyModuleNames

> "我和这个模块的关系紧密到,**任何 #include 我的 Public 头的人,都会同时拿到那个模块的 Public 头**。"

举个具体例子。`Engine` 模块的 Build.cs 里:

```csharp
// Engine/Source/Runtime/Engine/Engine.Build.cs (大致内容)
PublicDependencyModuleNames.Add("Core");
PublicDependencyModuleNames.Add("CoreUObject");
```

这意味着**任何依赖 Engine 的模块**(假设你的游戏模块依赖 Engine),你写:
```cpp
#include "Engine/World.h"
```
之后,你**自动**就能用 `TArray<int>`、`UObject*`、`FVector` — 因为 Core / CoreUObject 跟着 Engine 一起被你拿到了。

**含义两条**:
1. 头文件层面:这些模块的 `Public/` 目录被加到你的 include 搜索路径。
2. 链接层面:它们的 `.lib` / `.so` 跟你一起链。

**何时使用**:你的 `.h` 文件里**直接出现**了对方的类型。比如:
```cpp
// 我的 .h
#include "GameFramework/Actor.h"  // 来自 Engine 模块
class UMyComponent : public UActorComponent { ... };  // UActorComponent 来自 Engine
```
此时 Engine **必须**进 PublicDependencyModuleNames,因为别人 `#include` 我的 .h 的时候,他们也得能解析 `UActorComponent`。

### 0.1.2.2 PrivateDependencyModuleNames

> "我和这个模块**关系紧密但仅限我自己**:.h 不暴露给我的下游,但 .lib 还是要链接。"

Core.Build.cs 里:

```csharp
PrivateDependencyModuleNames.Add("BLAKE3");        // 哈希算法
PrivateDependencyModuleNames.Add("OodleDataCompression");
PrivateDependencyModuleNames.Add("xxhash");
```

Core 模块自己**实现**里用了 BLAKE3 等库,但它**不希望**任何依赖 Core 的人也能直接用 BLAKE3。

**何时使用**:你的 `.cpp` 文件里出现了对方的类型,但 `.h` 文件里没有。比如:
```cpp
// 我的 .h
class UMyThing { ... };

// 我的 .cpp
#include "MyThing.h"
#include "MyOtherModule/PrivateHelper.h"  // ← 只在 .cpp 用到
void UMyThing::Foo() { FPrivateHelper::DoIt(); }
```
此时 MyOtherModule 进 **Private**DependencyModuleNames。

**实战经验**:能放 Private 就放 Private。这能极大改善 Editor 的增量编译速度 — Public 依赖会让下游全部跟着重编。

### 0.1.2.3 PublicIncludePathModuleNames / PrivateIncludePathModuleNames

> "我只想看到这个模块的**头文件**,但**不要链它的库**。"

这种情况比想象中常见。Core.Build.cs:

```csharp
// Core.Build.cs:44-53
PrivateIncludePathModuleNames.AddRange(new string[] {
    "DerivedDataCache",
    "TargetPlatform",
    "Json",
    "RSA"
});
```

为什么 Core 不直接 PrivateDependencyModuleNames 这些?因为这些模块**反过来依赖 Core**。如果 Core 链它们,就会形成循环依赖。

解法:Core 只需要**在 .cpp 里包含它们的头**(用前向声明 + 接口指针),实际实现走运行时多态。`PrivateIncludePathModuleNames` 就是这个意思:"**我只 include,不链接**"。

**何时使用**:循环依赖 + 接口模式。99% 的项目代码用不到,但读引擎代码会经常碰到。

### 0.1.2.4 DynamicallyLoadedModuleNames

```csharp
// Core.Build.cs:64-66
if (Target.bBuildEditor == true)
{
    PrivateIncludePathModuleNames.Add("DirectoryWatcher");
    DynamicallyLoadedModuleNames.Add("DirectoryWatcher");
}
```

这意味着 DirectoryWatcher **运行时**才加载。代码里这样用:

```cpp
FModuleManager::Get().LoadModule("DirectoryWatcher");  // 运行时加载
// 然后通过接口访问
IDirectoryWatcher* Watcher = FModuleManager::GetModulePtr<IDirectoryWatcher>("DirectoryWatcher");
```

UBT 看到 `DynamicallyLoadedModuleNames` 会做两件事:
1. 把目标模块**编译**(否则运行时找不到)
2. 但**不**把它静态链接进来

**何时使用**:可选模块、Editor-only 工具、按平台动态切换的实现。

### 0.1.2.5 一张速查表

| 字段 | .h 可见性 | 静态链接 | 何时用 |
|---|---|---|---|
| PublicDependencyModuleNames | 我和我的下游 | ✓ | .h 里直接用对方类型 |
| PrivateDependencyModuleNames | 仅我自己 | ✓ | 仅 .cpp 用对方类型 |
| PublicIncludePathModuleNames | 我和我的下游 | ✗ | 循环依赖 + 公开接口 |
| PrivateIncludePathModuleNames | 仅我自己 | ✗ | 循环依赖 + 私有使用 |
| DynamicallyLoadedModuleNames | (无影响,需配合 IncludePath) | ✗(动态加载) | 运行时才决定要不要 |

**给你一条死规则**:
> **能放 Private 就别放 Public,能放 IncludePath 就别放 Dependency。**

这条规则会让你的项目编译速度比"全 Public" 快 3-5 倍。引擎代码也是这么写的,你看 Core.Build.cs 大量字段都在 Private。

## 0.1.3 Public / Private / Classes / Internal — 文件夹的访问语义

### 0.1.3.1 四个文件夹的含义

每个 Module 目录里可以有:

| 文件夹 | 含义 | 谁能 #include |
|---|---|---|
| `Public/` | 对外 API 头文件 | 所有依赖(Public/Private)我的模块 |
| `Private/` | 私有实现(.h + .cpp) | 仅本模块自己 |
| `Classes/` | **历史遗物**,等同于 `Public/`,但**只**放含 UCLASS/USTRUCT 的反射头 | 同 Public |
| `Internal/` | UE 5.1+ 引入,介于 Public 和 Private 之间 | "信任名单"内的模块 |

物理目录约束的"语义",是 UBT 在算 include 路径时执行的:

- **Public 目录**:UBT 把它注册成"公开 include 搜索根"。所以 `Engine/Source/Runtime/Core/Public/Containers/Array.h` 可以被任何依赖 Core 的模块通过 `#include "Containers/Array.h"` 包含。
- **Private 目录**:UBT 只把它加到本模块自己的 include 搜索路径。其他模块**就算物理路径写对了也 include 不到**(实际是 include 失败,因为头文件不可见)。

### 0.1.3.2 Classes/ 的历史背景(读引擎代码必懂)

UE3 / UE4 早期,反射宏(UCLASS / USTRUCT)只能写在 `Classes/` 目录里。UHT 那时只扫这个目录。后来 UE4.16 开放,UCLASS 可以写在 `Public/` 任意位置,`Classes/` 就废弃了 — 但出于历史兼容,它**仍然有效**。

举例,你打开 `Engine/Source/Runtime/Engine/`:

```
Engine/
├── Engine.Build.cs
├── Public/
├── Private/
└── Classes/         ← 大量遗留 UCLASS 头文件还在这里
    ├── GameFramework/
    │   ├── Actor.h          ← AActor 的声明就在这
    │   ├── GameMode.h
    │   └── PlayerController.h
    └── ...
```

**结论**:`Classes/` 在你眼里 = `Public/`,不需要做任何区分。新代码统一用 `Public/`。引擎里看到 `Classes/` 别奇怪,那是历史。

### 0.1.3.3 Internal/ 文件夹(5.1+ 新特性)

`Internal/` 是 Epic 给"我想暴露给某些信任模块,但不想暴露给所有人"的需求开的口子。例如:
```
Engine/Source/Runtime/Core/Internal/
└── CoreGlobalsInternal.h
```

这个头**只**能被 Build.cs 里显式声明信任 Core 的 internal 接口的模块 include。一般项目代码用不到,但你读 Engine 源码会偶尔碰到。

### 0.1.3.4 IWYU 和 CoreMinimal.h(顺便讲清楚)

两年前 UE 流行的写法是:
```cpp
#include "CoreMinimal.h"
#include "GameFramework/Actor.h"
```

`CoreMinimal.h` 是 Core 模块的"必备头集合",拉一行就拿到 TArray / FString / UObject 基础设施。简单粗暴。

UE 5.x 在推 **IWYU(Include What You Use)** — 直接 include 你用到的东西,不要拉一个聚合头。Target.cs 里的 `IncludeOrderVersion = EngineIncludeOrderVersion.Latest;` 就是开启严格 IWYU 的开关。

**实战建议**:
- 项目代码用 `IncludeOrderVersion = EngineIncludeOrderVersion.Latest`,养成 IWYU 习惯。
- 老代码迁移期可以 fallback 到 `EngineIncludeOrderVersion.Unreal5_0` 之类的兼容档位。
- **不要**在新写的 .h 里 include `CoreMinimal.h`。.cpp 里 include 是可以的(快但不优雅)。

## 0.1.4 UBT 实际做了什么 — 比你想象的复杂

到这里你已经能写一个 Module。下面这一段帮你把"魔法"拆开 — UBT 不是黑盒。

### 0.1.4.1 入口与 Mode 系统

UBT 是个 C# 程序,源码全部在 `Engine/Source/Programs/UnrealBuildTool/`。它的入口是命令行,有非常多"模式"(mode):

```
Engine/Source/Programs/UnrealBuildTool/Modes/
├── BuildMode.cs                  ← 默认模式,构建一个 Target
├── CleanMode.cs                  ← Clean
├── GenerateProjectFilesMode.cs   ← 生成 .sln
├── UnrealHeaderToolMode.cs       ← 调用 UHT
├── QueryMode.cs                  ← 查询模块依赖
├── JsonExportMode.cs             ← 导出依赖图为 JSON(很有用!)
├── IWYUMode.cs                   ← IWYU 工具
└── ... 30+ 个其它模式
```

`Build.bat UnrealEditor Win64 Development` 实际上跑的是 `BuildMode.cs`。

### 0.1.4.2 BuildMode 的整体流程

简化版(忽略错误处理、增量、UBA 加速):

```
1. 解析命令行: TargetName + Platform + Configuration
2. 找 <TargetName>.Target.cs,反射加载它(C# 动态编译)
3. 实例化 TargetRules 对象,得到所有配置(Type / IncludeOrderVersion / ExtraModuleNames...)
4. 根据 Type 决定基础 Module 集合:
   - Editor → Engine + Renderer + UnrealEd + LevelEditor + ... (一大堆 Editor-only)
   - Game → Engine + Renderer (没有 Editor 模块)
   - Server → Engine + Renderer-stub (无图形)
5. 加 ExtraModuleNames + bBuildAllModules 决定的额外模块
6. 对每个 Module:
   a. 找 <ModuleName>.Build.cs
   b. 反射加载,得到 ModuleRules 对象
   c. 收集它的 PublicDependencyModuleNames / PrivateDependencyModuleNames ...
   d. 递归处理依赖
7. 计算最终的依赖 DAG,排序确定编译顺序
8. 对每个 Module:
   a. 调 UHT 处理含反射的头(生成 .generated.h / .gen.cpp)
   b. 调编译器(MSVC / Clang)编译每个 .cpp
   c. 生成 .obj / .lib
9. 链接成最终 .exe / .dll
```

### 0.1.4.3 你必须知道的几个细节

**(a)所有 *.Build.cs 都是 C# 代码,会被实时编译**

UBT 启动后,它会把 `Engine/Source` 树下所有 `*.Build.cs` 当作 C# 文件,**编译进一个动态程序集**,然后反射调用 `new Core(targetRules)` 之类的构造。

这意味着 **Build.cs 里你能写任意 C# 代码**,包括 if/else 决定依赖、读环境变量、文件存在性判断。看 Core.Build.cs 大量平台分支就是这么来的:
```csharp
if (Target.Platform == UnrealTargetPlatform.Android)
{
    PrivateDependencyModuleNames.Add("GoogleGameSDK");
    // ...
}
```

**(b)Unity Build(合并编译,不是游戏引擎那个 Unity)**

UE 默认开 Unity Build:把同一个 Module 的多个 .cpp 拼接成一个大 .cpp 编译,大幅减少编译次数。
```
Module.cpp001.cpp = #include "Foo.cpp"
                    #include "Bar.cpp"
                    #include "Baz.cpp"
                    ... (默认 ~512KB 一组)
```

副作用:同名的 static 变量、unnamed namespace 在不同 .cpp 里会冲突。
- 调试期可以临时关掉:Build.bat 加 `-DisableUnity`。
- 项目级关闭:Build.cs 里 `bUseUnity = false;`(慢但最干净)。
- 单 .cpp 退出 Unity:Build.cs 里 `MinSourceFilesForUnityBuildOverride = 99999;` 或 cpp 文件用 `// UnityBuild: false` 注释(具体语法看 5.7 实现)。

**(c)PCH(预编译头)**

```csharp
PrivatePCHHeaderFile = "Private/CorePrivatePCH.h";
SharedPCHHeaderFile = "Public/CoreSharedPCH.h";
```

私有 PCH 给本模块加速编译。Shared PCH 是给依赖你的模块共享用的(Core 的 SharedPCH 几乎被所有模块共用)。

**(d)Module 类型(运行时身份)**

```csharp
// 极少数情况下你需要改这个
Type = ModuleType.External;       // 第三方库,只链接,不编译
Type = ModuleType.CPlusPlus;      // 默认
```

External 模块的 Build.cs 通常长这样:
```csharp
public class libpng : ModuleRules
{
    public libpng(ReadOnlyTargetRules Target) : base(Target)
    {
        Type = ModuleType.External;
        PublicSystemIncludePaths.Add("$(ModuleDir)/include");
        PublicAdditionalLibraries.Add("$(ModuleDir)/lib/libpng.lib");
    }
}
```

`ThirdParty/` 目录里的库都长这样。

## 0.1.5 UHT — 反射代码生成,UBT 的"前菜"

UHT(UnrealHeaderTool)在 5.0 之前是 C++ 写的独立程序,5.0+ 已经被**重写为 C# 并合入 UBT**。在 5.7 里它的位置是:
```
Engine/Source/Programs/UnrealBuildTool/Modes/UnrealHeaderToolMode.cs
```

并且配套有一个 `EpicGames.UHT.*` 的 C# 库(`Engine/Source/Programs/Shared/EpicGames.UHT/`),负责真正的 parser / generator。

### 0.1.5.1 UHT 的工作时机

UHT 在每个 Module 编译之前被 UBT 调用:

```
对 Module M:
  1. 扫描 M 的 Public/ + Classes/ + Private/ 下所有 .h 文件
  2. 找出含有反射宏(UCLASS / USTRUCT / UENUM / UFUNCTION / UPROPERTY / UDELEGATE)的头
  3. 把这些头交给 UHT 处理
  4. UHT 输出:
     - <每个反射头>.generated.h 文件
     - <模块>.gen.cpp 文件(注册函数,集中所有 Z_Construct_UClass_*)
  5. 这些产物落到 Intermediate/Build/<Platform>/<Target>/Inc/<Module>/
  6. UBT 把 Inc 目录加到 include 搜索路径
  7. 把 .gen.cpp 加入编译列表
  8. 然后才启动真正的 cl.exe / clang
```

### 0.1.5.2 一个最简单的反射类被 UHT 处理后变成什么

源:
```cpp
// MyComponent.h
#pragma once
#include "Components/ActorComponent.h"
#include "MyComponent.generated.h"     // ← 必须放在最后

UCLASS()
class MYMOD_API UMyComponent : public UActorComponent
{
    GENERATED_BODY()
public:
    UPROPERTY()
    int32 Health = 100;

    UFUNCTION()
    void Heal(int32 Amount);
};
```

UHT 生成两个文件:

**`Intermediate/Build/.../Inc/MyMod/UHT/MyComponent.generated.h`**(简化):
```cpp
// 含义:UCLASS 宏在被 UHT 处理后,GENERATED_BODY() 被替换为
// 一大堆静态注册代码、虚函数声明、反射查表函数

#define MYMOD_MyComponent_h_GENERATED_BODY() \
    public: \
        DECLARE_CLASS(UMyComponent, UActorComponent, ...) \
        DECLARE_SERIALIZER(UMyComponent) \
        /* 其它生成的成员 */ \
    private:

#define MYMOD_MyComponent_h_RPC_WRAPPERS \
    DECLARE_FUNCTION(execHeal); \
    /* 反射调用入口 */
```

**`Intermediate/Build/.../Inc/MyMod/UHT/MyMod.gen.cpp`**(简化):
```cpp
// 全局注册表项,启动期被构造,把 UMyComponent 注册到反射系统
UClass* Z_Construct_UClass_UMyComponent()
{
    static UClass* OuterClass = nullptr;
    if (!OuterClass)
    {
        // 描述 UMyComponent 的所有 UPROPERTY / UFUNCTION
        // 把 Health 字段、Heal 函数登记到 UClass
        // ...
    }
    return OuterClass;
}

// 静态对象,构造时把上面的函数注册到 UClassRegistry
static FClassRegistrationInfo Z_Registration_Info_UClass_UMyComponent;
static FRegisterCompiledInInfo Z_CompiledInDeferFile_..._UMyComponent(
    Z_Construct_UClass_UMyComponent, ...);
```

这就是为什么:
- 你必须 `#include "XXX.generated.h"`(里面有 GENERATED_BODY 的展开)
- `.generated.h` 必须是**最后一个 include**(它依赖前面所有头)
- `MYMOD_API` 必须用模块名 + `_API` 后缀(用于 DLL 导出符号,UBT 自动 `#define MYMOD_API __declspec(dllexport)`)

### 0.1.5.3 反射注册的"魔法"在哪里发生

`.gen.cpp` 末尾那个 `static FRegisterCompiledInInfo Z_CompiledInDeferFile_...` 是关键。它是一个**全局变量**,在程序启动时(`main` 之前,C++ 静态初始化阶段)被构造,构造函数把"如何创建 UClass 描述"的函数指针**塞进一个全局列表**。

后来引擎启动时(`FEngineLoop::PreInit`),UObject 系统会遍历这个列表,**调用每个注册的 `Z_Construct_UClass_*` 函数**,真正构造出 `UClass*` 对象,挂到全局对象表里。

(这个流程在 §2.2 会用源码详细拆解,这里你先建立"原来是这样工作的"印象就够了。)

### 0.1.5.4 一个常见报错诊断

**报错:`fatal error C1083: Cannot open include file: 'MyComponent.generated.h'`**

九成是这两种原因:
1. **你忘了 GenerateProjectFiles**。UHT 还没生成 .generated.h。解法:重新跑一次 `GenerateProjectFiles.bat` 或 `Build.bat -NoUBTMakefiles`。
2. **你 .h 文件里有 UCLASS,但忘了 `#include "XXX.generated.h"`**。UHT 生成了文件,但你没引用它。

**报错:`error C2065: 'UMyComponent': undeclared identifier`**

通常是:
- 你忘了写 `GENERATED_BODY()` 在类内,或者
- `MYMOD_API` 的模块名拼错,UHT 没识别出模块归属。

**报错:`error UHT failed: ...`**

UHT 自己挂掉。打开 `Engine/Programs/UnrealBuildTool/Log.txt` 看具体原因。常见:UCLASS 写法错误、GENERATED_BODY 位置错误、UPROPERTY 标签语法错误。

## 0.1.6 编译期裁剪宏:WITH_EDITOR / WITH_EDITORONLY_DATA / 等

UE 的代码大量充斥着这些宏:

```cpp
#if WITH_EDITOR
    // 仅 Editor 构建可见
#endif

#if WITH_EDITORONLY_DATA
    UPROPERTY()
    UTexture2D* EditorPreviewIcon;
#endif

#if !UE_BUILD_SHIPPING
    // 非 Shipping 构建可见(开发期专用,如 console command)
#endif
```

### 0.1.6.1 矩阵速查

| 宏 | 何时为 1 | 用途 |
|---|---|---|
| `WITH_EDITOR` | TargetType == Editor | Editor-only 代码(资产编辑、PIE 调试) |
| `WITH_EDITORONLY_DATA` | TargetType == Editor 或 Program | Editor 才有的字段(预览图、源资产路径) |
| `WITH_SERVER_CODE` | 包含服务器逻辑(Editor / Game / Server,不含 Client) | 服务器权威代码 |
| `WITH_DEV_AUTOMATION_TESTS` | 非 Shipping | 自动化测试 |
| `UE_BUILD_DEBUG` | Configuration == Debug | 调试构建 |
| `UE_BUILD_DEVELOPMENT` | Configuration == Development | 开发构建 |
| `UE_BUILD_TEST` | Configuration == Test | 测试构建 |
| `UE_BUILD_SHIPPING` | Configuration == Shipping | 发布构建 |
| `IS_MONOLITHIC` | 静态链接整个 Target(无 DLL) | 通常 Shipping Game 走这条 |
| `IS_PROGRAM` | TargetType == Program | UnrealLightmass / ShaderCompileWorker 等 |

### 0.1.6.2 配置(Configuration)的真正含义

5 种 Configuration:

| Configuration | 优化 | 调试符号 | 检查 | 用途 |
|---|---|---|---|---|
| **Debug** | 关 | 全 | 全部 | 重度调试,极慢 |
| **DebugGame** | 关项目代码,引擎 Development | 全 | 全部 | 调试游戏代码,引擎不慢 |
| **Development** | 开 | 全 | 部分 | 日常开发(Editor 默认) |
| **Test** | 开 | 部分 | 关大部分 | 测试构建,接近 Shipping 但保留少量 stat |
| **Shipping** | 开 | 关 | 全关(包括 cvar) | 发布给玩家 |

**实战经验**:
- Editor 你 99% 都跑 Development。Debug 慢到无法忍受。
- 真要调试游戏逻辑用 **DebugGame** — 它把游戏代码用 Debug 编,引擎用 Development,最佳折中。
- Shipping 编一次往往要 30 分钟+,**不要轻易切**。

### 0.1.6.3 RTS 项目的实战裁剪

未来你写 RTS,会大量使用:

```cpp
#if WITH_EDITOR
    // 单位调试可视化、单位编辑器工具
    UFUNCTION(CallInEditor, Category="Debug")
    void DumpAllEntities();
#endif

#if !UE_BUILD_SHIPPING
    // 战斗调试 cvar、实时性能 hud
    static TAutoConsoleVariable<int32> CVarDebugUnitCount(...);
#endif

#if WITH_SERVER_CODE
    // 服务器 AI,仅服务器执行
    void TickAI();
#endif
```

**纪律**:Mass Fragment 里的字段**绝不要**用 `WITH_EDITORONLY_DATA` 包裹。Mass 内存模型对字段大小极度敏感,Editor 和运行时必须保持完全一致的 Fragment 内存布局,否则会有诡异的内存对齐 bug。

## 0.1.7 Target Type 矩阵

5 种 TargetType:

| Type | 产物 | 包含 Editor 模块 | 包含 Renderer | 包含游戏逻辑 | 例子 |
|---|---|---|---|---|---|
| **Editor** | UnrealEditor.exe | ✓ | ✓ | ✓ | UE 主界面 |
| **Game** | YourGame.exe | ✗ | ✓ | ✓ | 玩家最终游戏 |
| **Client** | YourGameClient.exe | ✗ | ✓ | ✓(仅客户端) | 多人游戏客户端 |
| **Server** | YourGameServer.exe | ✗ | stub | ✓(仅服务器) | 专用服务器(无图形) |
| **Program** | UnrealLightmass.exe 等 | 可选 | 可选 | ✗(自定义) | 工具程序 |

**对应宏**:
- Editor → `WITH_EDITOR=1`, `WITH_EDITORONLY_DATA=1`, `WITH_SERVER_CODE=1`, `UE_GAME=0`
- Game → `WITH_EDITOR=0`, `WITH_EDITORONLY_DATA=0`, `WITH_SERVER_CODE=1`, `UE_GAME=1`
- Client → `WITH_EDITOR=0`, `WITH_EDITORONLY_DATA=0`, `WITH_SERVER_CODE=0`, `UE_GAME=1`
- Server → `WITH_EDITOR=0`, `WITH_EDITORONLY_DATA=0`, `WITH_SERVER_CODE=1`, `UE_SERVER=1`

### 0.1.7.1 多 Target 的项目布局(RTS 必备)

未来你的 RTS 项目至少应该有:
```
MyRTS.uproject
Source/
├── MyRTS.Target.cs              ← Game(玩家版本)
├── MyRTSEditor.Target.cs        ← Editor(开发版本)
├── MyRTSServer.Target.cs        ← Server(专用服务器)
├── MyRTSClient.Target.cs        ← Client(多人客户端)
├── MyRTS/
│   ├── MyRTS.Build.cs           ← 主游戏模块
│   └── ... .h .cpp
├── MyRTSCore/
│   ├── MyRTSCore.Build.cs       ← 核心数据(Fragment 定义)
│   └── ...
├── MyRTSMass/
│   ├── MyRTSMass.Build.cs       ← Mass Processor
│   └── ...
├── MyRTSEditor/
│   ├── MyRTSEditor.Build.cs     ← Editor-only 工具
│   └── ...
```

为什么要拆?
- `MyRTSCore` 和 `MyRTSMass` 都是 Server 也要用的,所以放在 Game/Server/Editor Target 下都包。
- `MyRTSEditor` 模块只在 Editor Target 下编(Build.cs 里 `if (Target.bBuildEditor) ...`)。
- 核心数据单独成模块的好处:**改 Editor-only 代码不会触发核心模块重编**,你的迭代速度会快得离谱。

## 0.1.8 RTS 项目的工程组织建议(综合实战)

### 0.1.8.1 Plugin vs Game Module 的取舍

UE 项目里的 C++ 代码可以放两个地方:
1. **Game Module** — 直接放在 `Source/` 下,跟着 .uproject 走
2. **Plugin** — 放在 `Plugins/<PluginName>/Source/`,有独立的 .uplugin 描述文件

**何时用 Plugin**:
- 这块代码**可能在多个项目复用**(Mass、AI、UI 框架)
- 这块代码**可以独立开关**(可选模组)
- 这块代码**有自己的资产**(配套 Material / Mesh / Blueprint)

**何时用 Game Module**:
- 这块代码就是**这个游戏独有**的核心玩法

**RTS 推荐布局**:
```
MyRTS.uproject
Source/                              ← 项目层(游戏特定)
├── MyRTS/                              主游戏模块(GameMode / GameState)
└── MyRTSEditor/                        Editor 工具

Plugins/                             ← 插件层(可独立复用)
├── MyRTSMassCore/                      Fragment / 通用 Processor
│   └── Source/MyRTSMassCore/
├── MyRTSMassRender/                    渲染剥离(VAT / ISMC 调度)
│   └── Source/MyRTSMassRender/
├── MyRTSNetwork/                       自定义复制层
│   └── Source/MyRTSNetwork/
└── MyRTSGameplay/                      技能 / 命令 / Selection
    └── Source/MyRTSGameplay/
```

**这种布局的最大好处**:你将来想把 RTS 框架卖给别人 / 复用到下一个项目,直接拷 `Plugins/MyRTS*` 即可。

### 0.1.8.2 哪些代码必须改 Engine 源码

**99% 的需求**走 Plugin / Subclass / Subsystem 即可,**不要**改 Engine。理由:

- Engine 改动会跟 Epic 上游 rebase 冲突,每次合并都是地狱
- 改了 Engine 你团队所有人都要重编 Engine(Editor 重编一次半小时起)
- 改了 Engine 你的 Plugin 失去单独发布能力

**确实需要改 Engine 的少数场景**:
1. Mass 内部行为(`UMassEntityManager` / `FMassArchetypeData`)— 这部分不是虚函数,扩展点不够,有时候确实要改
2. 渲染管线深度集成(GPU Driven Render 的部分钩子)
3. 网络协议层(`UNetDriver` 替换、自定义 Iris 集成)

**纪律**:每次改 Engine,**集中提交到一个特定补丁目录**(例如 `Engine/Source/_RTSPatches/`),并在 commit 信息里详细标注上游基准 hash。后面 §29.1 会专讲 rebase 友好的补丁管理。

### 0.1.8.3 模块拆分的"逐渐增加"原则

**新项目刚启动**:不要先建 6 个模块。一个 `MyRTS` 模块开干,所有代码塞进去。
**当某段代码满足以下任意条件,拆出去**:
1. 改它会导致超过 200 个 .cpp 重编(说明它在你工程的"上游"位置,需要拆出)
2. 它**只**被 Editor / 只被 Server 用到(应该靠 Build.cs `if (Target.bBuildEditor)` 隔离)
3. 它有大量 third-party 依赖(如 ImGui debug ui),不该污染主模块

我见过太多新人一开始拆 8 个模块,拆完发现要不停跨模块同步。**先大模块,长出再拆**。

## 0.1.9 实操:加一个新 Module

为了把这一节落实到肌肉记忆,跟着做一遍。

### 步骤

假设你已经有 MyRTS 项目,目录:
```
MyRTS.uproject
Source/MyRTS/
Source/MyRTS.Target.cs
Source/MyRTSEditor.Target.cs
```

加一个 `MyRTSCore` 模块:

**1.** 创建目录 + 文件:
```
Source/MyRTSCore/
├── MyRTSCore.Build.cs
├── Public/
│   └── MyRTSCore.h
└── Private/
    ├── MyRTSCore.cpp
    └── MyRTSCorePrivatePCH.h
```

**2.** 写 `MyRTSCore.Build.cs`:
```csharp
using UnrealBuildTool;

public class MyRTSCore : ModuleRules
{
    public MyRTSCore(ReadOnlyTargetRules Target) : base(Target)
    {
        PCHUsage = ModuleRules.PCHUsageMode.UseExplicitOrSharedPCHs;
        IWYUSupport = IWYUSupport.Full;

        PublicDependencyModuleNames.AddRange(new string[] {
            "Core",
            "CoreUObject",
            "Engine"
        });

        PrivateDependencyModuleNames.AddRange(new string[] {
            // 后期会加 MassEntity / MassCommon
        });
    }
}
```

**3.** 写 `Public/MyRTSCore.h`(Module 接口类):
```cpp
#pragma once
#include "Modules/ModuleManager.h"

class FMyRTSCoreModule : public IModuleInterface
{
public:
    virtual void StartupModule() override;
    virtual void ShutdownModule() override;
};
```

**4.** 写 `Private/MyRTSCore.cpp`:
```cpp
#include "MyRTSCore.h"
#include "Modules/ModuleManager.h"

void FMyRTSCoreModule::StartupModule() {}
void FMyRTSCoreModule::ShutdownModule() {}

IMPLEMENT_MODULE(FMyRTSCoreModule, MyRTSCore)
//                                  ^ 必须和 Build.cs 类名一致
```

**5.** 在 `MyRTS.uproject` 里登记这个新模块(否则 Editor 启动时不会加载):
```json
{
    "Modules": [
        {
            "Name": "MyRTS",
            "Type": "Runtime",
            "LoadingPhase": "Default"
        },
        {
            "Name": "MyRTSCore",
            "Type": "Runtime",
            "LoadingPhase": "PreDefault"
        }
    ]
}
```
`LoadingPhase = PreDefault` 意味着它在 MyRTS 之前加载(适合"基础设施"模块)。

**6.** 在 `MyRTS.Build.cs` 里加依赖:
```csharp
PublicDependencyModuleNames.AddRange(new string[] {
    "Core", "CoreUObject", "Engine", "MyRTSCore"
});
```

**7.** 重新生成项目文件:
```
GenerateProjectFiles.bat
```

**8.** Build。

如果一切顺利,你会在编译输出里看到:
```
[1/8] Compile MyRTSCore.cpp
[2/8] Link UnrealEditor-MyRTSCore.dll
[3/8] Compile MyRTS.cpp (now sees MyRTSCore types)
...
```

### 常见踩坑

- **忘了在 .uproject 里加 Module**:Editor 不报错但你的 `StartupModule` 永远不被调用。
- **模块名大小写不一致**:Build.cs 类名、IMPLEMENT_MODULE 第二参数、.uproject Modules 数组里的 Name **必须完全一致**(包括大小写)。
- **加了 Build.cs 没重新 GenerateProjectFiles**:.sln 看不到新模块。

## 0.1.10 与 Mass 重构的对照思考

这一节是工程基础设施,看似离 Mass 很远,但有几条直接影响:

### (1)Fragment 模块的拆分

Mass Fragment(数据类型)和 Mass Processor(逻辑)**最好不在同一个模块**:
- Fragment 模块编译稳定(数据结构很少改)
- Processor 模块迭代频繁(算法天天改)
- 拆开能让 Processor 改动**不触发**Fragment 模块下游的全部重编

### (2)Editor Trait 的隔离

Mass Trait(`UMassEntityTraitBase` 子类)往往**配置类**用 Editor 编辑,但运行时不需要 Editor 代码。把 Trait 的"运行时部分"和"Editor UI 部分"拆开 — Trait 类放运行时模块,Trait 的 DetailsCustomization 放 Editor 模块。

### (3)上游 rebase 友好的纪律

每次合并 Epic 上游 5.7 → 5.8,你 99% 的 Plugin 代码不冲突。**Build.cs 是你最容易冲突的地方** — 因为 Epic 经常调整模块依赖。预防:
- 你的项目模块的 Build.cs 里**不要** `PrivateDependencyModuleNames.Add("EnhancedInput")` 之类临时小改动散落在各处
- 集中管理依赖列表,改一次只改一处

### (4)IS_MONOLITHIC 与 Shipping

Shipping Game 一般走 Monolithic — 整个 .exe 一个二进制,没有 .dll。
**含义**:
- 没有动态加载,`FModuleManager::LoadModule` 退化成查表
- 模块边界对**链接器**仍然有效,但对**符号导出**变成内部
- `MYMOD_API` 宏在 Monolithic 下展开为空(没有 dllexport)

如果你后期对加载时间有强需求(主机 RTS 要快速进游戏),Monolithic 是正解 — 但你的所有 `*_API` 宏行为会变化,要在 Development(非 Monolithic)和 Shipping(Monolithic)都测一遍。
