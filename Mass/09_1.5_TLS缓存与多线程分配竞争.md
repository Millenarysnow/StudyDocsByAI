# §1.5 TLS 缓存与多线程分配竞争 — Mass 性能命脉

> **本节地图**:模块一第 1 章第 5 节。前面 §1.2-1.4 反复提到"TLS cache 让 Malloc/Free 走快路径"。这一节我们正面拆开 TLS cache 的机制 —— **它是 UE Binned 分配器在多线程高吞吐场景下唯一不崩的原因**。Mass 数十万 entity + 多线程 Processor 的性能,80% 来自这一节讲的设计。
>
> 没有 TLS cache,你的 Mass Processor 在 16 worker 线程上对全局池 mutex 抢锁,每帧光分配开销就 5-10ms。
> 有 TLS cache,同样负载下分配开销 <100μs。
>
> **预备知识**:§1.4 主流分配器,§1.1 平台 TLS 接口。
>
> **读完之后你能做到**:
> - 看清楚 Binned2/3 的 `FPerThreadFreeBlockLists` 结构与生命周期
> - 理解 `FBundle` 是什么、为什么要"批量"跨线程交换内存
> - 知道 `SetupTLSCachesOnCurrentThread` / `Trim` / `MarkTLSCachesAsUnusedOnCurrentThread` 各自的语义
> - 在 Mass Processor 的 worker thread 上配置 TLS cache(99% 自动,但你要知道怎么验证)
> - 诊断"TLS cache 命中率低"的性能问题

## 1.5.1 浅入:无 TLS 的世界 vs 有 TLS 的世界

### 1.5.1.1 朴素分配器:全局锁

最朴素的多线程分配器(包括最早的 `MallocAnsi`):

```cpp
void* Malloc(size_t Size)
{
    std::lock_guard<std::mutex> Lock(GlobalMutex);
    // ... 分配逻辑 ...
}
```

每次 alloc 抢一次全局锁。**单线程**没问题(锁是空操作),**多线程**就是噩梦:

| 线程数 | 分配吞吐 |
|---|---|
| 1 | 100% |
| 2 | ~80%(锁竞争开始) |
| 4 | ~50% |
| 8 | ~25%(线程基本在等锁) |
| 16 | <15%(锁队列形成,严重退化) |

**Mass 想跑 16 个 worker 线程并行处理 entity?这种分配器下你拿不到任何并行收益。**

### 1.5.1.2 TLS Cache 的核心思想

每个线程拥有自己的"内存池缓存":
- 分配时:**先从自己 TLS cache 拿**,拿到就返回,**完全无锁**
- 释放时:**先推到自己 TLS cache**,推得进就完成,**完全无锁**
- TLS cache 满了 / 空了:才与全局池交换

这样**99% 的 alloc/free 操作完全无锁**,锁只在偶尔的"批量交换"时才发生。这才是 Binned2/3 在 16 worker 线程下还能扛住 Mass 数十万 entity 分配压力的关键。

## 1.5.2 `FPerThreadFreeBlockLists` —— 每线程的 TLS 缓存

`Engine/Source/Runtime/Core/Public/HAL/MallocBinnedCommon.h:502`:

```cpp
// MallocBinnedCommon.h:502
struct FPerThreadFreeBlockLists
{
    inline static FPerThreadFreeBlockLists* Get() TSAN_SAFE
    {
        FPerThreadFreeBlockLists* ThreadSingleton = 
            FPlatformTLS::IsValidTlsSlot(BinnedTlsSlot) 
            ? (FPerThreadFreeBlockLists*)FPlatformTLS::GetTlsValue(BinnedTlsSlot) 
            : nullptr;
        return ThreadSingleton;
    }

    template<typename AllocType>
    static FPerThreadFreeBlockLists* GetOrCreate()
    {
        FPerThreadFreeBlockLists* ThreadSingleton = ...;
        if (!ThreadSingleton)
        {
            const int64 TLSSize = Align(sizeof(FPerThreadFreeBlockLists), 
                                        AllocType::OsAllocationGranularity);
            ThreadSingleton = new (AllocType::AllocateMetaDataMemory(TLSSize)) 
                FPerThreadFreeBlockLists();
            FPlatformTLS::SetTlsValue(BinnedTlsSlot, ThreadSingleton);
        }
        return ThreadSingleton;
    }

    // 每个 BinSize 一组 free list
    FFreeBlockList FreeLists[NUM_POOL_SIZES];

    // ... TLS-specific stats ...
};
```

理解这段:

**(1)用 `FPlatformTLS` 接口存取**(§1.1.4.6 讲过)。`BinnedTlsSlot` 是个全局 `uint32`,在 GMalloc 创建时 `FPlatformTLS::AllocTlsSlot()` 申请,然后每个线程在它对应的 slot 里存自己的 `FPerThreadFreeBlockLists*`。

**(2)`Get()` 返回 `nullptr` 是合法的**。新启动的线程在第一次调用前没有 TLS 数据,直到 `SetupTLSCachesOnCurrentThread()` 显式建立。

**(3)`GetOrCreate()` 是懒加载版本**。第一次访问时:
- 用 `AllocType::AllocateMetaDataMemory(TLSSize)` 分配一块"元数据内存"(MallocBinned 自家的元数据池,不走主分配路径,避免循环)
- placement new 一个 `FPerThreadFreeBlockLists`
- 写入 TLS slot

**(4)结构核心**:`FFreeBlockList FreeLists[NUM_POOL_SIZES]`。每个 BinSize 一条独立的 free list。

### 1.5.2.1 TLS 内存哪来的?

注意这里的 `AllocType::AllocateMetaDataMemory` —— 它不是 `FMemory::Malloc`!如果 TLS cache 自己也走 GMalloc,会形成"TLS 还没建好,所以分配 TLS 自己"的递归崩溃。

UE 的解法:Binned2/3 内部有**专门的 metadata 分配池**,绕开主分配路径。这个池只服务于"分配器自己的元数据"(PoolInfo / TLS struct),容量小但永远不依赖主路径。

## 1.5.3 `FBundle` —— 批量跨线程交换的容器

### 1.5.3.1 FBundleNode

`MallocBinnedCommon.h:187`:

```cpp
struct FBundleNode
{
    uint64 NextNodeInCurrentBundle : 48;     // 链表 next 指针(48 位足够 256TB 地址空间)
    uint64 Count : 8;                          // 8 位计数(MAX 256,实际默认 64)
    uint64 Reserved : 8;                       // 给 ARM HW 的 TBI / MTE 等保留

    void SetNextNodeInCurrentBundle(FBundleNode* Next)
    {
        NextNodeInCurrentBundle = reinterpret_cast<uint64>(Next);
    }

    FBundleNode* GetNextNodeInCurrentBundle()
    {
        return (FBundleNode*)NextNodeInCurrentBundle;
    }
};
```

注意几个细节:

- **整个结构体只有 8 字节**(三个位段塞进一个 uint64)
- `NextNodeInCurrentBundle` 用 48 位:足够覆盖 64 位用户态地址空间(48 bit = 256TB,Linux/Win 都够)
- **侵入式链表**:这个 8 字节头**直接放在空闲 bin 的开头**,bin 自身充当链表节点(同 §1.4.3.3 的 FFreeBlock 思路)

### 1.5.3.2 FBundle —— 一捆 bin

`MallocBinnedCommon.h:266`:

```cpp
struct FBundle
{
    FBundleNode* Head;
    uint32       Count;

    FBundle() { Reset(); }

    inline void Reset() { Head = nullptr; Count = 0; }

    inline void PushHead(FBundleNode* Node)
    {
        Node->SetNextNodeInCurrentBundle(Head);
        Head = Node;
        Count++;
    }

    inline FBundleNode* PopHead()
    {
        FBundleNode* Result = Head;
        Count--;
        Head = Head->GetNextNodeInCurrentBundle();
        return Result;
    }
};
```

非常朴素的链表 push/pop。**Bundle 就是一组同 BinSize 空闲 bin 的链**。

### 1.5.3.3 FFreeBlockList —— 每 BinSize 的两 Bundle 状态机

`MallocBinnedCommon.h:300`:

```cpp
struct FFreeBlockList
{
    FBundle PartialBundle;      // 当前正在累积/消耗的 bundle
    FBundle FullBundle;          // 已经满的 bundle(待推到全局)

    inline bool PushToFront(void* InPtr, uint32 InPoolIndex, uint32 InBinSize)
    {
        // 如果 PartialBundle 满了
        if ((PartialBundle.Count >= GMallocBinnedBundleCount) || 
            (PartialBundle.Count * InBinSize >= GMallocBinnedBundleSize))
        {
            if (FullBundle.Head) return false;       // FullBundle 也满了 → 失败,推回全局
            FullBundle = PartialBundle;              // 把 partial 转 full
            PartialBundle.Reset();
        }
        PartialBundle.PushHead((FBundleNode*)InPtr);
        return true;
    }

    inline void* PopFromFront(uint32 InPoolIndex)
    {
        if (!PartialBundle.Head && FullBundle.Head)
        {
            // partial 空了,把 full 拿过来当 partial
            PartialBundle = FullBundle;
            FullBundle.Reset();
        }
        if (!PartialBundle.Head) return nullptr;
        return PartialBundle.PopHead();
    }
    
    // ... RecyleFull / PopBundles 跨线程交换 ...
};
```

这是**每个 BinSize 一份**的状态(`FPerThreadFreeBlockLists::FreeLists[NUM_POOL_SIZES]` 数组里每项是这个)。

### 1.5.3.4 双 Bundle 设计的精妙

为什么是 PartialBundle + FullBundle 两个,不是一个?

**目的:让线程在"刚好满"和"刚好空"两个临界点上不立即触发跨线程交换,有缓冲**。

具体想象:
- 线程稳态分配:从 PartialBundle 一直 Pop。Pop 完了,从 FullBundle 拿过来当 partial,继续 Pop。期间不与全局池交互。
- 线程稳态释放:Push 到 PartialBundle。partial 满了,转给 FullBundle,partial 重置。partial 又满了 + full 也满了 → 才推到全局。

**结果**:线程在"分配-释放对儿"对等的稳态下,**永远不与全局交互**。只有"长期产 / 长期销"的不平衡才会触发跨线程。

这对 Mass 极其重要:Mass Processor 经常在一个 chunk 上做"读 fragment → 改 → 写回"循环,临时分配多 free 多平衡。双 Bundle 缓冲让这种工作模式几乎不锁。

### 1.5.3.5 GMallocBinnedBundleCount / GMallocBinnedBundleSize

两个全局调谐参数:

```cpp
// 默认值(在 MallocBinnedCommon.cpp 里)
GMallocBinnedBundleCount = 64;     // 每 bundle 最多 64 个 bin
GMallocBinnedBundleSize  = 8192;   // 或者总字节数到 8KB
```

含义:bundle 满的判定是**"数量达到 64 个 OR 总字节达到 8KB"**,谁先到先算。

**为什么用两个条件**?
- 小 BinSize(16 字节):64 个 bin = 1KB,远小于 8KB。卡数量限。
- 大 BinSize(4KB):2 个 bin = 8KB。卡字节限。

这样不论 BinSize 大小,bundle 大小都被限制在合理范围。

**调谐建议**:不要改这两个值。它们已经是 Epic 在巨型项目上 tune 过的最优。

## 1.5.4 FGlobalRecycler —— 跨线程的 Bundle 池

每个 BinSize 在全局有一个 **GlobalRecycler**(具体名字在 Binned2/3 里略有差异,但语义一致)。它是一组**已 free 的 bundle 队列**,用 lock-free 链表或 mutex 保护(看实现)。

```
┌─────────────────────────────────────────────┐
│  Per BinSize Global Recycler (16 byte bin)  │
│  ┌──────┐ ┌──────┐ ┌──────┐                │
│  │ B 64 │→│ B 64 │→│ B 32 │ ...           │
│  └──────┘ └──────┘ └──────┘                │
│  每个 B 是一个 FBundle(64 个 bin 在里面) │
└─────────────────────────────────────────────┘
        ↑                ↓
   线程 A 推 full bundle        线程 B 取 full bundle
   (TLS 满了)              (TLS 空了)
```

线程 A 的 Free 把 full bundle 推到全局,线程 B 的 Malloc 把整个 full bundle 从全局拽出来当自己的新 partial。

**锁竞争只在"推/拿"那一瞬间发生**。一次操作摊到 64 个 bin 上,锁持有时间极短。

### 1.5.4.1 RecyleFull 与 PopBundles

`MallocBinnedCommon.h:337` 和 `:369` 有源码,简化版:

```cpp
// 把 FullBundle 推到全局,返回老的 FullBundle 链(回收用)
FBundleNode* RecyleFull(uint32 InPoolIndex, T& InGlobalRecycler);

// 一口气从全局拿一组 bundle 回来,串成链
FBundleNode* PopBundles(uint32 InPoolIndex);
```

实际的全局 recycler 实现用了 lock-free 技术(`TLockFreePointerListLIFO` 或类似),保证多线程并发推/拿的正确性。Lock-free 在这里是值得的 —— 推/拿是热点,不能锁。

## 1.5.5 Alloc / Free 完整路径(线程视角)

把所有元素串起来,这是 Binned2/3 在多线程下的 alloc/free 路径:

### 1.5.5.1 Alloc 路径(从 worker 线程视角)

```cpp
// 简化的 Malloc(线程 A 调用)
void* Malloc(SIZE_T Size, uint32 Align)
{
    if (Size > MAX_SMALL_POOL_SIZE) {
        return MallocLargePool(Size, Align);    // 大块走 OS,与 TLS 无关
    }
    
    uint32 PoolIndex = SizeToPoolIndex(Size);
    
    // ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
    // 路径 1:TLS 命中(99% 情况)
    // ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
    FPerThreadFreeBlockLists* Lists = FPerThreadFreeBlockLists::Get();
    if (Lists)
    {
        FFreeBlockList& FList = Lists->FreeLists[PoolIndex];
        void* Ptr = FList.PopFromFront(PoolIndex);
        if (Ptr) return Ptr;     // ← 完全无锁,几条指令
    }
    
    // ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
    // 路径 2:TLS 空,从全局 GlobalRecycler 拿 bundle
    // ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
    FBundleNode* RemoteBundle = PopBundlesFromGlobalRecycler(PoolIndex);
    if (RemoteBundle)
    {
        // 把整个 bundle 装进 TLS 的 PartialBundle
        FList.PartialBundle.Head = RemoteBundle;
        FList.PartialBundle.Count = RemoteBundle->Count;
        return FList.PopFromFront(PoolIndex);   // 然后 pop 一个
    }
    
    // ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
    // 路径 3:全局也没,锁池表分配新 page
    // ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
    FPoolTable& Table = SmallPoolTables[PoolIndex];
    FScopeLock Lock(&Table.Mutex);          // ← 此时才真正锁
    return AllocateNewBinFromPool(Table);
}
```

### 1.5.5.2 Free 路径

```cpp
void Free(void* Ptr)
{
    if (!Ptr) return;
    
    FPoolInfo* Pool = FindPoolForPtr(Ptr);
    
    if (IsLargePool(Pool)) {
        FreeLargePool(Ptr);   // 大块直接还 OS,无 TLS
        return;
    }
    
    uint32 PoolIndex = Pool->GetPoolIndex();
    uint32 BinSize = SmallBinSizes[PoolIndex];
    
    // ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
    // 路径 1:推到 TLS(99%)
    // ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
    FPerThreadFreeBlockLists* Lists = FPerThreadFreeBlockLists::Get();
    if (Lists)
    {
        FFreeBlockList& FList = Lists->FreeLists[PoolIndex];
        if (FList.PushToFront(Ptr, PoolIndex, BinSize))
        {
            return;     // ← 完全无锁
        }
    }
    
    // ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
    // 路径 2:TLS 满 → 把 FullBundle 推到全局
    // ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
    if (Lists)
    {
        FBundleNode* OldFull = FList.RecyleFull(PoolIndex, GlobalRecycler);
        // OldFull 推回全局成功,现在 TLS 有空位
        FList.PushToFront(Ptr, PoolIndex, BinSize);
        return;
    }
    
    // ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
    // 路径 3:线程没有 TLS(Setup 没跑过) → 直接锁全局还
    // ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
    FPoolTable& Table = SmallPoolTables[PoolIndex];
    FScopeLock Lock(&Table.Mutex);
    ReturnBinToPoolGlobal(Pool, Ptr);
}
```

### 1.5.5.3 性能对照

每路径的耗时数量级(Win64,典型 CPU):

| 路径 | 耗时 |
|---|---|
| 1: TLS 命中 | 5-15 ns |
| 2: TLS miss, 全局 bundle 命中 | 50-150 ns |
| 3: 完全 miss, 锁池分配 | 200ns - 50μs(取决于是否申请新 OS 页) |

**Mass 数十万 entity/帧的分配压力下,绝大多数 alloc 走路径 1**。这就是它能跑得起来的根因。

## 1.5.6 TLS 生命周期 API(`SetupTLSCachesOnCurrentThread` 等)

`HAL/UnrealMemory.h:235-250` 这一组 API:

```cpp
static CORE_API void Trim(bool bTrimThreadCaches = true);
static CORE_API void SetupTLSCachesOnCurrentThread();
static CORE_API void ClearAndDisableTLSCachesOnCurrentThread();
static CORE_API void MarkTLSCachesAsUsedOnCurrentThread();
static CORE_API void MarkTLSCachesAsUnusedOnCurrentThread();
```

逐个讲:

### 1.5.6.1 `SetupTLSCachesOnCurrentThread()`

**含义**:在当前线程上启用 TLS 分配缓存。

**何时调用**:**新线程刚启动时**。如果你自己 `FRunnableThread::Create` 创建一个工作线程,其 `Run()` 入口处应该调一次 `SetupTLSCachesOnCurrentThread()`。

**默认行为**:UE 自带的 TaskGraph worker 线程、RenderThread、AudioThread 等**都已经在 Run 入口调过**。你 99% 不需要手动调。

**如果不调会怎样**:这个线程上 `Get()` 返回 `nullptr`,所有 alloc/free 走"路径 3"(锁全局),性能直接退化到无 TLS 时代。

### 1.5.6.2 `ClearAndDisableTLSCachesOnCurrentThread()`

**含义**:清空当前线程的 TLS cache(把所有 partial/full bundle 推回全局),并标记此线程未来不再使用 TLS。

**何时调用**:线程**即将退出**时。FRunnableThread 的 stop / exit 路径会自动调。

### 1.5.6.3 `MarkTLSCachesAsUsedOnCurrentThread` / `MarkTLSCachesAsUnusedOnCurrentThread`

这一对是**"软关闭"**用的。语义:
- `MarkAsUnused`:这个线程暂时进入空闲(可能在 Sleep / 等待),`Trim` 时**可以**回收它的 TLS cache 内存
- `MarkAsUsed`:这个线程要恢复工作了,准备好 TLS

典型用途:线程池里某些 worker 长时间空转,让 `Trim` 安全地把它们 TLS 内存回收(不浪费),等它们再次工作时重新 setup。

### 1.5.6.4 `Trim(bool bTrimThreadCaches = true)`

**含义**:回收"不必要"的内存给 OS。

具体操作:
- 把所有标记为 `Unused` 的线程的 TLS cache 推回全局并释放
- 把全局 GlobalRecycler 中长期未用的 bundle 整理 / 释放
- 把所有 BinSize 池里**完全空闲**的 OS 页 VirtualFree 给 OS
- LargePool 缓存(CachedOSPageAllocator)里的过期页释放

**何时调用**:
- 自动:GC 后(`gc.TrimMemoryAfterGC` 默认 1)
- 手动:`memreport` 命令、`-cmd="Trim"`、Editor 切换关卡前

**对你 RTS 的意义**:服务器或长跑 Editor,你可以**主动**调 `FMemory::Trim(true)`,让进程 RSS 降到合理水位。但**不要每帧调** —— Trim 本身有锁开销。

### 1.5.7.2 自己写一个 micro-bench

```cpp
static FAutoConsoleCommand CmdMTAlloc(TEXT("rts.MTAlloc"),
    TEXT("Multi-threaded malloc benchmark"),
    FConsoleCommandDelegate::CreateLambda([]()
    {
        const int32 NumThreads = 16;
        const int32 NumIters = 1'000'000;
        std::atomic<int64> TotalNs{ 0 };

        TArray<TFuture<void>> Futures;
        for (int32 t = 0; t < NumThreads; ++t)
        {
            Futures.Add(Async(EAsyncExecution::TaskGraph, [&]()
            {
                FMemory::SetupTLSCachesOnCurrentThread();   // 显式 setup(其实 task worker 已自动)
                
                double Start = FPlatformTime::Seconds();
                TArray<void*> Local;
                Local.Reserve(NumIters);
                for (int32 i = 0; i < NumIters; ++i)
                {
                    Local.Add(FMemory::Malloc(64));
                }
                for (void* P : Local) FMemory::Free(P);
                double Elapsed = FPlatformTime::Seconds() - Start;
                
                TotalNs += int64(Elapsed * 1e9);
            }));
        }
        for (auto& F : Futures) F.Wait();
        
        UE_LOG(LogTemp, Display, 
            TEXT("MT Alloc/Free %d threads × %d ops, avg %lldns/op"),
            NumThreads, NumIters, TotalNs.load() / NumThreads / NumIters / 2);
    }));
```

跑这个命令,你应该看到平均 **5-30 ns/op**。如果你看到 **500ns+/op**,说明 TLS 没正常工作(或锁竞争严重)。

### 1.5.7.3 Insights 看

启动加 `-trace=cpu`,跑负载,Insights 里搜 `Malloc` / `FMallocBinned2::Malloc` / `FMallocBinned3::Malloc` 这些 scope。如果你看到大量时间花在`AcquireMutex` 或锁相关的栈,TLS 有问题。健康状态下这些 scope 几乎看不到(全部 inline 优化掉)。

## 1.5.8 Mass / RTS 视角下的纪律

### (1)永远不要在 Processor 里手动创建 `FRunnableThread` 用来跑分配密集任务

如果你在 Mass Processor 里 `FRunnableThread::Create(...)` 起一个新线程跑分配密集逻辑,这个线程**默认没有 TLS**,你会发现性能退化。

**正确做法**:用 TaskGraph(`UE::Tasks::Launch` / `Async(EAsyncExecution::TaskGraph, ...)`),Task Worker 线程自带 TLS。

### (2)Processor 内**频繁分配**是 anti-pattern

哪怕 TLS 再快,数十万 entity × 每 entity 数次 alloc 也是不可忽视开销。**Mass 设计时尽量避免 Processor 内堆分配**:

```cpp
// 不好:每次 entity 处理都临时分配
void Execute(FMassExecutionContext& Context)
{
    for (FMassEntity Entity : Context)
    {
        TArray<int32> TempArray;     // ← 每 entity 一次 alloc/free
        // ...
    }
}

// 更好:Processor 成员变量复用
class UMyProcessor : public UMassProcessor
{
    TArray<int32> TempArray;        // ← 整个 Processor 共用
    
    void Execute(...)
    {
        for (FMassEntity Entity : Context)
        {
            TempArray.Reset();      // 不释放,只清空
            // ...
        }
    }
};

// 最好:栈分配(没有堆 alloc)
void Execute(...)
{
    TArray<int32, TInlineAllocator<32>> TempArray;   // 32 个元素以内栈上,§1.6 详讲
    // ...
}
```

### (3)长 idle 后调 Trim

服务器 / Editor 长跑,内存可能膨胀到 10GB+。控制台或代码里:

```cpp
FMemory::Trim(true);   // 把 TLS / GlobalRecycler / 空闲页都还 OS
```

立刻把 RSS 降下来。**不要每帧调**(本身有锁开销)。

### (4)线程退出时显式清理(罕见)

99% 你不会自己起 `FRunnableThread`。**如果**真起了:

```cpp
class FMyRTSWorkerThread : public FRunnable
{
    virtual uint32 Run() override
    {
        FMemory::SetupTLSCachesOnCurrentThread();   // 入口:启用 TLS
        
        while (!bStopRequested)
        {
            // ... 工作逻辑 ...
        }
        
        FMemory::ClearAndDisableTLSCachesOnCurrentThread();  // 出口:清理
        return 0;
    }
};
```

但还是那句话:**用 TaskGraph,别自己起线程**。

## 1.5.9 改 Engine:调 TLS 参数(罕见)

如果你有强烈对比数据,可以改 `GMallocBinnedBundleCount` / `GMallocBinnedBundleSize`:

- 增大它们 → 单线程稳态吞吐更高(更少跨线程交换),但 TLS 内存占用增加
- 减小它们 → TLS 占内存少,但跨线程交换更频繁

`Engine/Source/Runtime/Core/Public/HAL/MallocBinnedCommon.h` 附近搜这两个全局变量(它们是 `extern int32 ...`,启动时可被 cvar 调整)。命令行:`-mallocbinnedbundlecount=128` 试试。

**强烈建议**:有数据再改。盲调没用。
