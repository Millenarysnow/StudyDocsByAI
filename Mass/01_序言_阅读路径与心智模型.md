# 序言：阅读路径与心智模型

> 这一份不是技术文档,是**地图**。把它读完,你后面每翻开一章都知道"我现在站在哪、为什么要在这里、读完它接到哪"。

> 后续每一节都会涉及具体的源码、行号、内存布局。但**心智模型一旦错了,源码读再细也会拼不起来**。所以我们先花一份文档建一张图。

## S.1 本指南的"破"与"立":为什么必须先把传统 OOP 框架吃透

你最终的目标是:
> 用 Mass ECS 从零搭建一款支持数万单位的 RTS,绕过 Actor / Controller 体系。

听上去 OOP 跟你最终代码几乎无关,那为什么我们要花**整整三个模块**讲传统 Gameplay 框架?

**理由一:你绕不开,你只是在"局部绕开"。**

Mass 不是一个独立引擎,它是 UE 里一个 World Subsystem。它**寄生**在 `UWorld` / `FEngineLoop` / `TaskGraph` / `UObject GC` 这套老体系上:
- `UMassEntitySubsystem` 本身是 `UWorldSubsystem`,生命周期由 `UWorld` 决定
- Mass Processor 的调度被钉在 `UWorld::Tick` 的 TickGroup 上
- Fragment 数据虽然不是 UObject,但持有的 `TObjectPtr<UStaticMesh>` 会被 GC 扫描
- 输入还是要从 `APlayerController` 进来,渲染还是要走 `UWorld::Scene` 提交给 Renderer

**你不是在 UE 之外搭一个 ECS,你是在 UE 的肚子里凿一个 ECS。**凿之前必须搞清楚肚子里的器官长什么样,否则一刀下去切到主动脉。

**理由二:OOP 框架是 ECS 的"反面教材"。**

理解 Mass 的设计动机,最好的方式不是直接读 Mass,而是先读 `AActor::Tick` / `UNetDriver::ServerReplicateActors` / `UAbilitySystemComponent::TickComponent`,然后**亲眼看到**它们在 1 万个对象面前是怎么跪下的。

- 看过 `FTickFunction` 的虚函数调度,你才会理解为什么 Mass Processor 一次跑一整个 chunk
- 看过 `FRepLayout::CompareProperties` 的逐属性比较,你才会理解为什么 Mass Iris 用 dirty flag 而不是脏 diff
- 看过 `GUObjectArray` 的 chunked 数组和 GC Token Stream,你才会理解 Mass 为什么把 Entity 退化成一个 `(Index, SerialNumber)` pair 而不是 UObject

**先看到"它为什么不行",再看到"它怎么改才行",这是最快的理解路径。**逆着读会让你产生大量"为什么 Mass 设计成这样"的孤儿问题。

**理由三:RTS 的"非单位部分"还是要老老实实写传统代码。**

数万小兵走 Mass,但是:
- 选择框、命令面板、小地图 — Slate / UMG
- 资源、人口、科技树 — `AGameState` 上的 UPROPERTY 复制
- 玩家本人(视角、阵营、解锁状态) — `APlayerController` + `APlayerState`
- 对局开始、结束、胜负判定 — `AGameMode`
- 战争迷雾的全局可见性矩阵 — World Subsystem
- 战役关卡的剧情触发器、过场 — Actor / Component / BlueprintEvent

**你的项目最终是一个混合体:5% 的"重要 Actor" + 95% 的 "Mass Entity"。**没有任何一个 RTS 项目能完全抛弃 Actor 体系,真这么做你连一个对话框都画不出来。

所以"破"的不是整个 OOP 框架,而是**Tick / Spawn / Replicate 这三条特定的瓶颈链路在大规模单位上的应用**。其余地方继续用 OOP 香得很。这一点想清楚,你后面就不会陷入"是不是哪里都该 ECS 化"的虚火。

## S.3 工具链与源码阅读姿势

这一节没有技术深度,但**配置好工具能让你后面省下 30% 的阅读时间**。

### S.3.1 IDE 与符号跳转

**Visual Studio 2022 (17.4+)** 是首选,UE5 官方支持最好。
- 装 **Visual Assist** 或 **ReSharper C++**(二选一,ReSharper C++ 对模板代码索引更强,但更慢)。
- 务必启用 IntelliSense — UE 的代码量足以让原生 IntelliSense 半死不活,工具是必需品而不是锦上添花。

**关键操作熟练度**(你后面每天都要用):

| 操作 | VA 快捷键 | 含义 |
|---|---|---|
| Find Symbol | `Alt + Shift + S` | 全工程符号搜索 |
| Find References | `Shift + Alt + F` | 找一个函数 / 变量的所有引用 |
| Goto Implementation | `Alt + G` | 从虚函数声明跳到实现(UE 大量虚函数,这个是命脉) |
| Find in Files | `Ctrl + Shift + F` | 文本搜索(找日志关键字、找 cvar 注册时这个最快) |
| 反向调用栈 | `Shift + Alt + H` | "谁调用了我",读 Tick 调度的时候必备 |

**不要靠 `Ctrl + 鼠标点击`**。UE 大量符号是宏展开的(`UCLASS()` / `IMPLEMENT_MODULE` / `DEFINE_LOG_CATEGORY`),原生跳转会跳到错的地方。务必用 VA / ReSharper 的"Find Symbol"。

### S.3.2 Unreal Insights — 你会跟它处一辈子

Insights 是 UE 自带的 trace 分析器,在 `Engine/Binaries/Win64/UnrealInsights.exe`。

你必须熟练的 Trace Channels:

| Channel | 看什么 |
|---|---|
| `cpu` | CPU scope,所有 `TRACE_CPUPROFILER_EVENT_SCOPE` |
| `frame` | 每帧时间线 |
| `bookmark` | 关键事件锚点(Spawn / Possess / NetReplicate) |
| `counter` | 自定义计数器(后期你会注册 RTS 的"在线单位数") |
| `gpu` | GPU 时间线 |
| `mass` | Mass 专属 channel(Processor 执行、Entity 创建/销毁) |
| `task` | TaskGraph 任务图(看并行 Processor 时必备) |

启动 Editor 时加参数:
```
UnrealEditor.exe MyProject.uproject -trace=cpu,frame,counter,bookmark,mass,task
```

trace 文件落到 `%localappdata%/UnrealEngine/Common/UnrealTrace/Store/` 或当前 Saved 目录(取决于 5.7 行为)。把它拖到 Insights 里,你会看到三层时间线:
- **Game Thread**:`UWorld::Tick` 里所有 TickGroup
- **Render Thread**:渲染指令 enqueue
- **TaskGraph Workers**:并行任务

**强烈建议**:在你写第一段 Mass Processor 之前就熟练 Insights。你将来 80% 的性能问题都是在 Insights 里看一眼就明白的。

### S.3.3 RenderDoc / PIX

- **RenderDoc**:抓帧分析渲染管线。后面 §25(渲染剥离)讲 ISMC / VAT 时,你会用 RenderDoc 验证"我画的是不是真的一个 DrawCall 出 1 万个单位"。
- **PIX on Windows**:微软的 D3D12 工具,能看到比 RenderDoc 更深的 GPU 时间线、shader occupancy、wave/lane 利用率。
  
配置一次,以后随手用。

### S.3.4 控制台命令速查

UE 的控制台(Editor 里 `~`,运行时也是 `~`)是源码阅读的"实时旁白"。你要熟到的命令:

| 命令 | 用途 |
|---|---|
| `stat unit` | 总览每帧 GameThread / RenderThread / GPU 时长 |
| `stat fps` | FPS |
| `stat scenerendering` | 渲染统计 |
| `stat memory` | 内存占用分类 |
| `DumpTicks` | 列出所有注册的 TickFunction(读 §8 时必备) |
| `obj list class=Actor` | 列出当前 World 所有 Actor |
| `gc.CollectGarbageEveryFrame 1` | 调试 GC 时强制每帧跑(极慢但能复现 GC bug) |
| `gc.NumRetriesBeforeForcingGC -1` | 关闭被动 GC,只能手动触发 |
| `Mass.Debug.DebugEntity 0` | Mass entity 调试可视化(后续详讲) |
| `t.MaxFPS 30` | 锁帧测试 |
| `r.ScreenPercentage 50` | 半分辨率渲染(测 GPU bound 时常用) |

不需要全背,但读到对应章节的时候请回来加深印象,熟练度直接决定你调试速度。

## S.4 一开始就内化的 RTS 性能预算

这一节是**你做架构决策的标尺**。每次想"这个设计行不行"的时候,把它对一遍预算。

### S.4.1 单位规模目标

| 指标 | 目标 | 说明 |
|---|---|---|
| 服务器在场 Entity 总数 | 50,000 | 包括兵、炮塔、投射物、采集物 |
| 单客户端可见 Entity | ~10,000 | 视野内 + LOD |
| 每帧网络下行新增/变化 entity | < 500 | 决定 Replication Bubble 设计 |

### S.4.2 帧预算(目标 60Hz,16.6 ms)

| 子系统 | 上限 | 备注 |
|---|---|---|
| Mass Tick(所有 Processor) | 4 ms | 含 Movement / AI / LOD / Repr |
| 渲染(GameThread 提交 + RenderThread) | 6 ms | ISMC 上传 + 主渲染 |
| 物理 / Overlap | 1 ms | 数万单位的物理是奢侈品,绝大多数走自定义 |
| 网络发送 / 接收 | 2 ms | |
| Slate / UMG / UI | 1 ms | |
| GC / 垃圾回收 | 摊到 < 1 ms / 帧 | 增量 GC 必开 |
| 留余 | 1.6 ms | 突发抖动缓冲 |

**这意味着:Mass Processor 每个**平均**只能用 100-200 微秒。**你后面看到任何 Processor 写得不像 SIMD-friendly,先把这条预算贴在屏幕上提醒自己。

### S.4.3 网络预算(单玩家)

| 方向 | 带宽 |
|---|---|
| 上行 | < 128 KB/s |
| 下行 | < 512 KB/s |

**这意味着:**每帧每玩家下行 ≈ 512KB/30Hz ≈ **17 KB**。要塞 1 万个单位状态,**平均每个单位 1.7 字节**。这就是为什么 Mass Replication 必须用量化(位置 16-bit、朝向 8-bit)+ 兴趣管理 + dirty flag。原生 `FRepLayout` 没救。

### S.4.4 内存预算

| 指标 | 目标 |
|---|---|
| 单 Entity 平均(所有 Fragment 合计) | < 256 字节 |
| 每 Archetype Chunk 默认大小 | 128 KB(Mass 默认) |
| 50K entities 总内存(纯 Fragment) | < 13 MB |
| 加上 Mass 元数据、ISMC 实例 | < 50 MB |

**这意味着:每个 Fragment 设计时要逐字节抠。**`FVector`(24 字节)如果你只用来存 2D 位置,那就改 `FVector2D`(8 字节)甚至量化的 `int16x2`(4 字节)— 前面 §17 讲 chunk 时会反复回到这个纪律。

### S.4.5 决策清单(贴在墙上的版本)

每当你做架构决策,过一遍:

1. 这个设计在 **50K entity** 时是 O(N) 还是 O(N²)?
2. 这个数据结构在 **Insights** 里能不能 trace 到?
3. 这个网络包在 **17 KB / 帧 / 玩家** 的预算下占多少?
4. 这条数据如果是 UObject,GC 会不会标记它?标记多少次?
5. 这段代码能不能 **SIMD 友好**(SoA、连续内存、无虚函数)?
6. 上游 Epic 改了引擎,我这个改动会不会冲突?(rebase 友好)

不需要每次都全部回答,但每次有一个"答不上来",就是你需要回来读对应章节的信号。

## S.5 体例约定(后面每章都遵守)

为了让你阅读时不至于在体例上分心,后面所有章节固定如下结构:

1. **本节地图**:这一节在大图里的位置 + 你应该带着什么问题进来。
2. **预备知识**:依赖哪些前置节(给出文件名链接)。
3. **从最浅的视角入手**:用一段最简单的代码 / 最日常的场景做钩子。
4. **源码深度剖析**:文件路径、类名、行号(基于 5.7.3)、关键代码片段引用。
5. **数据流 / 控制流图**:必要时画 ASCII 图。
6. **与 Mass 重构的对照**:这一节的知识在你将来魔改 Mass 时怎么用。
7. **实操提示**:断点位置、Insights 通道、控制台命令。
8. **下一节预告与依赖**。

每节落到独立 md 文件,命名:
```
<两位模块号>_<章号>.<节号>_<小标题>.md
```

例如:
- `00_序言_阅读路径与心智模型.md`(本文)

## S.6 给你的第一个建议

**不要囫囵吞枣读完整本指南再开工。**

正确节奏是:
1. 读完模块零(第 0 章)→ 立刻把 RTS 项目骨架搭出来(空 GameMode + 空 PlayerController)。
2. 读完 §6-8 → 在项目里写一个 `bCanEverTick = false` 的 Pawn,验证 Tick 关闭。
3. 读完 §17-18 → 立刻写 5 个 Mass Entity + 1 个 Movement Processor,把 50 个 cube 跑起来。
4. 读完 §20 Representation → 把 cube 换成 ISMC 真模型。
5. 读完 §22-25 → 把规模拉到 5,000,看 Insights 哪里红。

**理论必须立刻被代码验证,否则你读到 §29 也只是收藏家。**Mass 是一门手艺,手艺的底层逻辑是肌肉记忆 + 代码量,而不是阅读量。
