# §3.1 UObjectBase / UObjectBaseUtility / UObject 三层继承

> **本节地图**:模块一第 3 章第 1 节。前面 §2 看完了反射怎么注册到运行时,这一节走进**UObject 实例本身的内存布局**。
>
> `class UObject` 是引擎里最核心的基类,但它不是一个"扁平"的类。它拆成**三层继承**,每层职责清晰分离:
>
> - `UObjectBase` —— **核心数据成员**(几个字段),最薄
> - `UObjectBaseUtility` —— **零数据,纯接口便利方法**
> - `UObject` —— **虚函数家族 + Editor / 序列化 / 反射 hook**
>
> 这一节我们把这三层一一拆开,看每层贡献了什么、为什么这么分。
>
> **预备知识**:§2 反射全套(看到 GENERATED_BODY 知道展开后是什么)、§1.5(原子操作)。
>
> **读完之后你能做到**:
> - 看到 `sizeof(UObject)`,从内存布局**算出**每个字段占多少字节
> - 看到 `Obj->GetClass()` / `Obj->GetOuter()` / `Obj->GetFName()` 知道是字段直读还是查询
> - 理解 `EObjectFlags` 的位段意义(MarkAsNative / RootSet / Garbage 等)
> - 知道 5.x 的 `UE_WITH_CONSTINIT_UOBJECT` 实验特性是干什么的
> - 改 Engine 时知道为什么不能轻易给 UObjectBase 加字段(对象数量级太大,每字节 × 1M)

## 3.1.1 浅入:为什么不直接一个 UObject 类?

C++ 设计上,**一个类通常就是一个类**。UE 把 UObject 拆成三层,是为了什么?

读到引擎的解释(`UObjectBase.h:55-57`):

```cpp
/** 
 * Low level implementation of UObject, should not be used directly in game code 
 */
class UObjectBase
```

注释里写得清楚:**"Should not be used directly in game code"**。

为什么要藏起来?三个理由:

### 3.1.1.1 内存布局的紧凑性

`UObjectBase` 只放**核心数据成员**(几个 8 字节字段),不掺其它。这样:
- 整个 UObject 头部布局**完全可预测**
- 反射、GC、序列化等系统知道字段偏移
- 内存对齐稳定,不会因为某个 utility 函数的字段被加进来导致整个对象大小膨胀

### 3.1.1.2 关注点分离

- `UObjectBase`(数据)— 谁也不许动,GC / 反射 / 序列化的**契约层**
- `UObjectBaseUtility`(便利方法)— 提供大量 inline 接口,但**零数据**(不影响 sizeof)
- `UObject`(虚函数家族)— 可被子类重写的 hook 点

每层各管一摊,方便维护、测试、移植。

### 3.1.1.3 friend 边界

`UObjectBase.h:60-86` 一大段 `friend` 声明:

```cpp
class UObjectBase
{
    friend class UObjectBaseUtility;
    friend struct Z_Construct_UClass_UObject_Statics;
    friend class FUObjectArray;        // 访问 InternalIndex
    friend class FUObjectAllocator;    // 访问析构函数
    friend struct UE::CoreUObject::Private::FObjectHandleUtils;
    friend COREUOBJECT_API void UObjectForceRegistration(...);
    friend COREUOBJECT_API void InitializePrivateStaticClass(...);
    friend COREUOBJECT_API UObject* StaticAllocateObject(...);
    // ...
};
```

UObjectBase 把核心数据**藏在 protected/private**,只有少数"内核组件"(GC / 分配器 / 反射注册器)能直接访问。这就是为什么 `Obj->InternalIndex` 不能从 game 代码直接读 —— 必须走 `Obj->GetUniqueID()` 这种公开 getter。

## 3.1.2 第一层:`UObjectBase` 的核心字段

打开 `Engine/Source/Runtime/CoreUObject/Public/UObject/UObjectBase.h:374-407`:

```cpp
// UObjectBase.h:374
private:
    /** Flags used to track and report various object states. */
    EObjectFlags                    ObjectFlags;        // 4 字节

    /** Index into GObjectArray. */
    int32                           InternalIndex;      // 4 字节

    /** Class the object belongs to. */
    ObjectPtr_Private::TNonAccessTrackedObjectPtr<UClass>  ClassPrivate;   // 8 字节(指针)

    // 名字 + 可选哈希索引
    struct FNameAndObjectHashIndex
    {
        FName Name;                                      // 8 字节(NameIndex + Number)
#if UE_STORE_OBJECT_LIST_INTERNAL_INDEX
        int32 ObjectListInternalIndex;                   // 4 字节(可选)
#endif
        // ...
    };
    FNameAndObjectHashIndex NamePrivate;                // 8-16 字节

    /** Outer 对象 */
    ObjectPtr_Private::TNonAccessTrackedObjectPtr<UObject>  OuterPrivate;   // 8 字节
```

**5 个核心字段**(简化忽略 constinit 路径):

| 字段 | 类型 | 大小 | 用途 |
|---|---|---|---|
| `ObjectFlags` | `EObjectFlags` (uint32) | 4 字节 | 状态标志位(下面 §3.1.4 详讲) |
| `InternalIndex` | `int32` | 4 字节 | GUObjectArray 索引(§3.2 详讲) |
| `ClassPrivate` | `UClass*` 包装 | 8 字节 | 指向类型描述对象 |
| `NamePrivate.Name` | `FName` | 8 字节 | 对象名字(同名共享 NamePool) |
| `OuterPrivate` | `UObject*` 包装 | 8 字节 | 父对象(`/Game/Foo.Bar:Component0` 的层级) |

**`sizeof(UObjectBase) == 32 字节**`(64 位平台,无 constinit 扩展)。

### 3.1.2.1 这就是"UObject 头部固定开销"

任何 UObject 子类的实例至少 **32 字节**给这 5 个字段。叠加 vtable 指针 8 字节 → **40 字节**起步。

实际项目里:
- 一个最简单的 UObject 子类(空类) ≈ 40 字节
- AActor ≈ 数百字节(Tick 状态、Components 数组、Tags 等)
- UStaticMeshComponent ≈ 1KB+(Mesh 引用、Transform、material 数组等)

**对比 Mass Fragment**:典型 Fragment 几十字节。差距明显。这就是 Mass 不让数十万 entity 当 UObject 的根本物理原因。

### 3.1.2.2 `TNonAccessTrackedObjectPtr<T>` 是什么

5.x 引入。注意它**不是普通指针**,是个轻量包装类。功能:
- 实际还是 8 字节存指针
- 提供"远程对象"(remote object handle)的扩展挂钩
- 关闭"访问追踪"(`AccessTracked` 是 Editor 用来跟踪对象引用的功能,运行时关掉)

99% 你当作 `UClass*` / `UObject*` 用就行。看到这个名字别迷糊。

### 3.1.2.3 `FNameAndObjectHashIndex` 的双重身份

```cpp
struct FNameAndObjectHashIndex
{
    FName Name;
#if UE_STORE_OBJECT_LIST_INTERNAL_INDEX
    int32 ObjectListInternalIndex;
#endif
};
```

这是个**优化结构**:在 `UE_STORE_OBJECT_LIST_INTERNAL_INDEX = 1` 时,FName(8 字节)的内存对齐 padding 里塞一个 `int32` 用于"对象列表索引"。开销 0,收益是 UObjectHash 查询从哈希表退化为数组索引,**一定场景下查询更快**。

5.7 默认 `UE_STORE_OBJECT_LIST_INTERNAL_INDEX = 0`(看 UObjectBase.h:49-51 的 `#ifndef`),所以这个 padding 不被使用。

### 3.1.2.4 `UE_WITH_CONSTINIT_UOBJECT` 路径(实验性)

5.x 在试 C++20 `constinit` 让某些核心 UObject 在编译期就构造好(零运行时构造开销):

```cpp
// UObjectBase.h:96
#if UE_WITH_CONSTINIT_UOBJECT
public:
    explicit consteval UObjectBase(UE::CodeGen::ConstInit::FObjectParams InParams)
        : ObjectFlags(InParams.Flags | RF_MarkAsNative | RF_MarkAsRootSet | RF_NeedInitialization)
        , InternalIndex(INDEX_NONE)
        , ClassPrivate(ConstEval, InParams.Class)
        , UninitializedNameUTF8(InParams.NameUTF8)
        , OuterPrivate(InParams.Outer)
    {
    }
#endif
```

`consteval` 强制编译期求值。`InParams` 是编译期常量。结果:对应的全局静态 UObject **不**走"全局静态构造期 → RegisterCompiledInInfo → 运行时构造"那条慢路径,而是直接被编译器塞进 .text/.data 段。

**收益**:进程启动更快,启动期反射注册时机更稳定。

**代价**:要求 C++20 + 编译器支持,且字段必须能 constinit。`FName` 在编译期还没就绪 → 用 `UninitializedNameUTF8` 暂存 UTF-8 字符串,运行时再补成 FName。

**5.7 默认关**(`#if UE_WITH_CONSTINIT_UOBJECT` 通常不定义)。这是给未来准备的路径,你看到这一段代码不用慌。

## 3.1.3 `UObjectBase` 的关键 getter

```cpp
// UObjectBase.h:217 - GetClass
FORCEINLINE UClass* GetClass() const
{
    return ClassPrivate;     // 直接字段读,1 ns
}

// UObjectBase.h:223 - GetOuter
FORCEINLINE UObject* GetOuter() const
{
    return OuterPrivate;     // 直接字段读
}

// UObjectBase.h:233 - GetFName
FORCEINLINE FName GetFName() const
{
    return NamePrivate.Name;
}

// UObjectBase.h:211 - GetUniqueID
FORCEINLINE uint32 GetUniqueID() const
{
    return (uint32)InternalIndex;
}

// UObjectBase.h:285 - GetFlags
FORCEINLINE EObjectFlags GetFlags() const
{
    EObjectFlags Flags = (EObjectFlags)GetFlagsInternal();
    return Flags;
}
```

注意所有都是 `FORCEINLINE`,**单条机器指令出结果**。这是 hot path 友好的设计 — 你写 `Obj->GetClass()` 几乎免费。

### 3.1.3.1 `GetFlagsInternal` 的原子读

```cpp
// UObjectBase.h:360
FORCEINLINE int32 GetFlagsInternal() const
{
    int32 Result = 0;
    UE_AUTORTFM_OPEN
    {
        Result = FPlatformAtomics::AtomicRead_Relaxed((int32*)&ObjectFlags);
    };
    return Result;
}
```

**这是一次 relaxed atomic 读**(`AtomicRead_Relaxed`)。原因:`ObjectFlags` 可能被多个线程并发修改(`AtomicallySetFlags` / `AtomicallyClearFlags`),用 atomic read 保证不会读到撕裂值。

`AtomicRead_Relaxed` 在 x86 上等价于普通读(x86 自然原子),但在 ARM 上需要内存 barrier。

## 3.1.4 `EObjectFlags` 完整枚举

`Engine/Source/Runtime/CoreUObject/Public/UObject/ObjectMacros.h` 定义:

```cpp
enum EObjectFlags
{
    RF_NoFlags                          = 0x00000000,

    // 公共状态(初始化期)
    RF_Public                           = 0x00000001,
    RF_Standalone                       = 0x00000002,
    RF_MarkAsNative                     = 0x00000004,    // C++ 静态注册的对象
    RF_Transactional                    = 0x00000008,    // Editor undo/redo 跟踪
    RF_ClassDefaultObject               = 0x00000010,    // ★ 这是 CDO
    RF_ArchetypeObject                  = 0x00000020,
    RF_Transient                        = 0x00000040,    // 不存盘
    RF_MarkAsRootSet                    = 0x00000080,    // ★ GC root,不会被回收
    RF_TagGarbageTemp                   = 0x00000100,
    RF_NeedInitialization               = 0x00000200,    // 还没跑 InitProperties
    RF_NeedLoad                         = 0x00000400,    // 反序列化中
    RF_KeepForCooker                    = 0x00000800,
    RF_NeedPostLoad                     = 0x00001000,
    RF_NeedPostLoadSubobjects           = 0x00002000,
    RF_NewerVersionExists               = 0x00004000,    // 加载时版本不匹配
    RF_BeginDestroyed                   = 0x00008000,    // ★ 销毁中(Phase 1)
    RF_FinishDestroyed                  = 0x00010000,    // ★ 销毁完成(Phase 2)
    RF_BeingRegenerated                 = 0x00020000,    // BP reinstancing
    RF_DefaultSubObject                 = 0x00040000,
    RF_WasLoaded                        = 0x00080000,
    RF_TextExportTransient              = 0x00100000,
    RF_LoadCompleted                    = 0x00200000,
    RF_InheritableComponentTemplate     = 0x00400000,
    RF_DuplicateTransient               = 0x00800000,    // 复制时不带
    RF_StrongRefOnFrame                 = 0x01000000,
    RF_NonPIEDuplicateTransient         = 0x02000000,
    // ...
    RF_MirroredGarbage                  = 0x40000000,    // ★ 已被标记 garbage
    RF_AllocatedInSharedPage            = 0x80000000,
};
```

最关键的几个(**记住**):

| Flag | 含义 |
|---|---|
| `RF_ClassDefaultObject` | 这个对象是 CDO(每个 UClass 一个) |
| `RF_MarkAsNative` | 该对象由 C++ 静态注册产生(非 BP / 非加载) |
| `RF_MarkAsRootSet` | GC 根集成员,**永远不被回收** |
| `RF_Transient` | 不写入 .uasset,运行时对象 |
| `RF_NeedInitialization` | 还在 init 半成品状态 |
| `RF_NeedPostLoad` | 反序列化完成,但 PostLoad 还没跑 |
| `RF_BeginDestroyed` | 已调 BeginDestroy,准备删除 |
| `RF_FinishDestroyed` | 已调 FinishDestroy,可以释放内存 |
| `RF_MirroredGarbage` | 已被 MarkAsGarbage,GC 准备清理 |

### 3.1.4.1 `EInternalObjectFlags`(另一组 flag)

UE 还有第二组 flag 存在 GUObjectArray 里(不在 ObjectFlags),叫 `EInternalObjectFlags`。覆盖 GC 内部状态:

```cpp
enum class EInternalObjectFlags : int32
{
    None                    = 0,
    LoaderImport            = 1 << 20,
    Garbage                 = 1 << 21,        // 即将被 GC 回收
    PersistentGarbage       = 1 << 22,
    ReachableInCluster      = 1 << 23,
    RootIsInCluster         = 1 << 24,
    ClusterRoot             = 1 << 25,
    Native                  = 1 << 25,
    Async                   = 1 << 26,
    AsyncLoading            = 1 << 27,
    Unreachable             = 1 << 28,         // GC 标记结果:unreachable,可回收
    PendingConstruction     = 1 << 29,
    RootSet                 = 1 << 30,
    // ...
};
```

`EInternalObjectFlags` 不在 UObjectBase 字段里,而是在 GUObjectArray 的 `FUObjectItem`(§3.2 详讲)里。这是为什么 GC 性能好的关键 —— **GC 扫的是 GUObjectArray 数组,不需要逐个 deref UObject 指针**。

## 3.1.5 第二层:`UObjectBaseUtility` —— 零数据的便利层

`Engine/Source/Runtime/CoreUObject/Public/UObject/UObjectBaseUtility.h:44`:

```cpp
class UObjectBaseUtility : public UObjectBase
{
    static COREUOBJECT_API bool bGarbageEliminationEnabled;     // 只有这个静态(类级共享,不增加 sizeof)

public:
    UObjectBaseUtility() {}
    UObjectBaseUtility(EObjectFlags InFlags) : UObjectBase(InFlags) {}

    // 大量 inline 工具函数
    inline void SetFlags(EObjectFlags NewFlags);
    inline void ClearFlags(EObjectFlags FlagsToClear);
    inline bool HasAnyFlags(EObjectFlags FlagsToCheck) const;
    inline bool HasAllFlags(EObjectFlags FlagsToCheck) const;
    
    // 路径相关
    FString GetPathName(const UObject* StopOuter = nullptr) const;
    FString GetFullName(const UObject* StopOuter = nullptr) const;
    
    // 父类层次
    UPackage* GetPackage() const;
    UPackage* GetOutermost() const;
    
    // GC 接口
    inline void MarkAsGarbage();
    inline void ClearGarbage();
    inline bool IsRooted() const;
    inline void AddToRoot();
    inline void RemoveFromRoot();
    
    // 类型判断(转发到 UClass)
    bool IsA(const UClass* SomeBase) const;
    template<typename T> bool IsA() const;
    
    // ... 等等大量便利方法 ...
};
```

**关键**:`UObjectBaseUtility` **没有非静态字段**。所有方法都是 inline,操作的是从 UObjectBase 继承来的字段。

`sizeof(UObjectBaseUtility) == sizeof(UObjectBase) == 32 字节`。这个 utility 层完全免费。

### 3.1.5.1 为什么把这些方法分到 utility 层?

如果直接放 UObjectBase:
- UObjectBase.h 会爆炸(几千行 inline)
- 编译时间增加(每个 include UObjectBase.h 的文件都要解析这堆 inline)
- 紧凑性丢失(UObjectBase 应该专注数据)

放到 utility 层 + UObjectBase **friend** UObjectBaseUtility:
- 数据访问通过 friend 桥接
- inline 函数集中到 utility,关注点分离
- 子类(UObject)继承 utility 自然拿到所有便利

这是 C++ 大型代码库的常见组织方式。

## 3.1.6 第三层:`UObject` —— 虚函数家族 + GENERATED_BODY

`Engine/Source/Runtime/CoreUObject/Public/UObject/Object.h:93`:

```cpp
UCLASS(Abstract, MinimalAPI, Config = Engine)
class UObject : public UObjectBaseUtility
{
    GENERATED_BODY()

public:
    typedef UObject WithinClass;

    UObject();
    UObject(const FObjectInitializer& ObjectInitializer);
    UObject(EStaticConstructor, EObjectFlags InFlags);
    UObject(FVTableHelper& Helper);
    
    // ... 100+ 虚函数 ...
};
```

这一层的核心特征:

### 3.1.6.1 `UCLASS(Abstract, MinimalAPI, Config = Engine)`

UObject 自身**也是反射的**!它有 `GENERATED_BODY()`,有 `UClass*`(实际是 `UObject::StaticClass()`)。

`Abstract`:你不能 `NewObject<UObject>(...)`,因为 UObject 是抽象基类。`Config = Engine`:UObject 的 Config 配置存在 `Engine.ini`。

### 3.1.6.2 vtable 的引入

UObject 是第一层有**虚函数**的类(`UObjectBase` / `UObjectBaseUtility` 都没虚函数)。所以 UObject 实例的内存布局多一个 vtable 指针:

```
[UObject 实例 = 40 字节]
   0-7:  vtable 指针(virtual 方法表)
   8-39: UObjectBase 字段(ObjectFlags / InternalIndex / ClassPrivate / NamePrivate / OuterPrivate)
```

vtable 指针在**对象起始处**(标准 C++ 单继承 vtable 布局)。

### 3.1.6.3 重要虚函数(挑选)

```cpp
// 序列化(详讲在 §3.5)
virtual void Serialize(FArchive& Ar);
virtual void Serialize(FStructuredArchive::FRecord Record);

// 生命周期 hook
virtual void PostInitProperties();             // InitProperties 之后
virtual void PostLoad();                       // 资产加载完成后
virtual void PostLoadSubobjects(...);
virtual void PreSave(...);
virtual void PostSaveRoot(...);
virtual void BeginDestroy();                   // ★ 销毁阶段 1
virtual void FinishDestroy();                  // ★ 销毁阶段 2(更晚,§4 GC 详讲)
virtual bool IsReadyForFinishDestroy();        // 异步等待

// GC 引用收集
virtual void AddReferencedObjects(FReferenceCollector& Collector);

// Editor
virtual void PostEditChangeProperty(FPropertyChangedEvent& PropertyChangedEvent);
virtual void PreEditChange(FProperty* PropertyAboutToChange);

// 复制 / 实例化
virtual UObject* CreateArchetype();
virtual void GetSubobjectsWithStableNamesForNetworking(TArray<UObject*>& ObjList);

// 网络
virtual bool ReplicateSubobjects(class UActorChannel* Channel, ...);
virtual void GetLifetimeReplicatedProps(TArray<FLifetimeProperty>& OutLifetimeProps) const;

// 元数据
virtual UWorld* GetWorld() const;
```

每一个都是 hook 点,子类按需重写。**这就是为什么 sizeof(UMyClass) 经常远大于 sizeof(UObject)** —— 不是 UObject 本身大,是子类加了多少字段。

### 3.1.6.4 `UObject` 不能是 final

子类能继承的链非常深:
```
UObject ← UActorComponent ← UStaticMeshComponent
   ↑       (~1KB)               (1.5KB+)
   40字节
```

每层加成员变量。整个 UE 类型层级能套 5-15 层。

## 3.1.8 内存布局的实际样子

`UMyComponent : public UActorComponent : public UObject` 这种典型情况,实例内存:

```
偏移 0:    [vtable 指针] 8 字节
偏移 8:    [UObjectBase 字段块] 32 字节
            +0:  ObjectFlags
            +4:  InternalIndex
            +8:  ClassPrivate
            +16: NamePrivate.Name
            +24: OuterPrivate
偏移 40:   [UActorComponent 字段块] ~数百字节
            (Tick 状态、Owner、Tags、Activation 状态等)
偏移 N:    [UMyComponent 字段块]
            (你自定义的 UPROPERTY)
```

关键观察:

1. **UObject 头部固定 40 字节,所有子类共享这个布局**
2. **从对象指针 + offset 可以直接定位任意祖先字段**(GC / 反射依赖这个稳定性)
3. **加字段必须加在子类**(改 UObjectBase 影响整个引擎)

## 3.1.9 改 Engine 的纪律:绝不改 UObjectBase

### 3.1.9.1 改 UObjectBase 的代价

如果你想给 UObjectBase 加一个字段(典型场景:你的 RTS 想给所有 UObject 加一个 8 字节的 RTS 元数据 ID):

- **每个 UObject 实例 +8 字节**:Editor 启动期 UObject 数量约 50K-200K,每实例 +8 = 400KB-1.6MB
- **GC 扫描节奏改变**:GUObjectArray 的 cache line 行为变了,GC 性能可能退化
- **二进制兼容彻底毁掉**:所有插件、所有资产 cooked 数据格式改变
- **rebase 噩梦**:Epic 任何 5.x → 5.x+1 的 UObjectBase 改动都和你冲突

**纪律**:**永远不要**改 UObjectBase。99% 你想要的"全局 UObject 元数据"都能通过:
- 子类层加字段
- 单独的 hash map(`TMap<UObject*, FYourData>`)
- 用 ObjectAnnotation 系统(`Engine/Source/Runtime/CoreUObject/Public/UObject/UObjectAnnotation.h`)

### 3.1.9.2 ObjectAnnotation —— 安全的"挂数据"姿势

```cpp
// 定义你的元数据类型
struct FRTSObjectAnnotation
{
    int32 RTSUnitID = -1;
    bool IsDefault() const { return RTSUnitID == -1; }
};

// 全局 annotation 表
FUObjectAnnotationSparse<FRTSObjectAnnotation, true> RTSAnnotations;

// 添加 / 查询
RTSAnnotations.AddAnnotation(SomeObject, FRTSObjectAnnotation{ 42 });
FRTSObjectAnnotation Anno = RTSAnnotations.GetAnnotation(SomeObject);
```

UObjectAnnotation 不改 UObject 本身,而是用对象指针做 key 维护一个稀疏表。**对未挂注解的对象零开销**,挂了的占用稀疏存储。

实战:**任何"想给 UObject 加字段"的需求,先想 ObjectAnnotation 能不能替代**。能就用,不能再考虑改。

## 3.1.11 RTS / Mass 视角下的对照思考

### (1)Mass entity ≠ UObject

再次强调:Mass `FMassEntityHandle` 是 8 字节 ID,**不**继承 UObject,**不**进 GUObjectArray,**不**被 GC 扫。

50K entity × 40 字节(UObject 头部)= 2MB,**只是头部**,还没算字段。Mass entity 8 字节 × 50K = 400KB,**全部数据**。差距明显。

### (2)Mass 的"少数 UObject"必要部分

- `UMassEntitySubsystem`(1 个)
- `UMassProcessor`(数十个)
- `UMassEntityTraitBase` 子类(数十个,作为 CDO)
- `UMassEntityConfigAsset`(资产,几十个)

总共**几百个 UObject**,固定开销可以接受。这些 UObject 是框架结构,不是 entity 实例。

### (3)Fragment 的 ObjectFlags 不存在

Fragment 是 USTRUCT(纯数据),**没有 ObjectFlags / InternalIndex / vtable**。它就是个 POD 结构。这是 SoA 内存布局的基础 — Fragment 数据可以**密集排列**,不浪费在元数据上。

### (4)RTS 的"重要单位"vs "杂兵"分层

```
英雄单位、Boss 单位 (~10 个)
   ↓
   走 UObject 体系(继承 AActor)
   有完整反射、Editor 可配、Blueprint 可写逻辑、RPC 调用
   头部开销 40 字节 + 大量字段 = 1KB+/instance,可以接受

普通单位、投射物、采集物 (~50,000 个)
   ↓
   走 Mass entity(Fragment 数据,无 UObject 头)
   每实例 ~256 字节,无 vtable,无 ObjectFlags
   性能优先
```

这个分层是 RTS 实战的标准姿势,§22 详讲。
