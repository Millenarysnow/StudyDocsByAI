## 4.5.1 算笔账:50,000 单位走 UObject 的 GC 成本

假设你**不**用 Mass,把每个 RTS 单位实现为 `class AUnit : public AActor`。每个单位是 Actor + 几个 Component(MeshComp / MovementComp / HealthComp 等)。

### 4.5.1.1 GUObjectArray 增量

每个单位:
- 1 个 AUnit 主对象
- 5 个 ActorComponent(平均估)
- = **6 个 UObject / 单位**

50,000 单位 × 6 = **300,000 个新 UObject** 加入 GUObjectArray。

加上引擎本身的 UObject(约 50-100K),总 GUObjectArray ≈ **400,000 左右**。

### 4.5.1.2 mark 阶段的耗时

§4.3 给的"理想路径"(走 schema)每对象处理 ~5 ns,但前提是:
- TFastReferenceCollector 多线程并行
- Token Stream 已 assemble
- cache 友好

实测(Win64,8 worker thread):
- 简单 UObject(无 UPROPERTY 引用):2-5 ns / 对象
- 普通 UClass(5-10 个 UPROPERTY):20-50 ns / 对象
- AActor(几十字段 + Components 数组):100-300 ns / 对象

400,000 对象的混合,**单次 mark ≈ 5-15 ms**。

### 4.5.1.3 sweep 阶段的耗时

每帧死 1-5% 单位(战场死亡率):
- 50K × 2% = 1000 单位 / 帧死
- 每单位 = 6 UObject = 6000 销毁

每个 UObject 销毁:
- `ConditionalBeginDestroy` + `BeginDestroy` ≈ 1-5 μs
- `IsReadyForFinishDestroy` 多次轮询(渲染 fence 等)
- `FinishDestroy` + 析构 ≈ 1-5 μs

简单估算:6000 × 平均 5 μs = **30 ms** —— **直接超过单帧预算**。

### 4.5.1.4 创建侧:每帧 spawn 几百个新单位

战场新单位涌入(援军、生产):500 / 帧 × 6 UObject = 3000 NewObject。

NewObject ≈ 2-5 μs / 简单 UObject,Actor 30-100 μs(§3.3.9):
- 3000 × 50 μs(Actor 平均)= **150 ms / 帧**

**完全不能跑**。

### 4.5.1.5 总账

| 操作 | 耗时 |
|---|---|
| GC mark(每 60 秒一次) | 5-15 ms,摊到 60 秒 ≈ 0.1-0.3 ms/帧 |
| GC sweep(增量 2 ms / 帧 budget) | 单位死亡积累快时,**经常超 budget,卡顿** |
| 单位 spawn(战场涌入时) | 50-150 ms / 帧 |
| 单位移动 / AI(各 component Tick) | 估 0.5-5 ms / 单位 × 50K = **25-250 ms / 帧** |
| **合计** | **远超 16.6 ms 单帧预算** |

**结论**:50K 单位走 Actor / Component 体系**根本跑不动**。不是优化几百微秒的事,是**架构根本错误**。

## 4.5.2 Mass 的"零 UObject 增量"对比

同样 50K 单位走 Mass:

### 4.5.2.1 GUObjectArray 增量

- `UMassEntitySubsystem`:1 个
- `URTSMovementProcessor` / 各 Processor:~30 个 UCLASS + CDO
- `URTSMassConfig` 资产:几十个 UDataAsset
- `URTSMassTrait` 子类 CDO:几十个

合计 **< 200 个新 UObject**。GUObjectArray 总数 **几乎不变**。

### 4.5.2.2 GC mark 耗时

GC mark 几乎不变,因为 GUObjectArray 没增长。仍然 **~1-3 ms / 60 秒 = 0.02-0.05 ms / 帧**。

### 4.5.2.3 单位创建 / 销毁

Mass `CreateEntity`:
- 在已分配 chunk 上 placement new fragment
- 无 NewObject,无 GUObjectArray 注册
- ~500 ns / entity

500 单位 spawn × 500 ns = **0.25 ms / 帧**。

死亡 1000 单位:
- 从 chunk 移除 fragment 数据
- 复用 entity index
- ~300 ns / entity × 1000 = **0.3 ms / 帧**

**对比**:Actor 体系 spawn 150 ms vs Mass spawn 0.25 ms,**600 倍差距**。

### 4.5.2.4 50K 单位 Mass Tick

每个 Processor 一次扫描所有匹配 entity:
- Movement Processor:50K × ~50 ns/entity(SoA + SIMD-friendly)= 2.5 ms
- AI Processor:50K × ~100 ns/entity = 5 ms
- LOD Processor:50K × ~30 ns/entity = 1.5 ms
- Representation Processor:50K × ~80 ns/entity = 4 ms

合计 **~13 ms / 帧**(单线程)。开 4 个 worker 并行:**~3-4 ms / 帧**。

### 4.5.2.5 总账

| 操作 | Mass(50K) | Actor(50K) |
|---|---|---|
| GC mark / 帧均 | 0.05 ms | 5+ ms |
| GC sweep / 帧均(死亡 1000) | 0(不参与) | 1-5 ms,峰值 30 ms |
| Spawn 500 单位 | 0.25 ms | 50-150 ms |
| Tick 50K(并行) | 3-4 ms | 25-250 ms |
| **总计** | **3.3-4.3 ms** | **80-400 ms** |

Mass **远低于** 16.6 ms 单帧预算,Actor **完全超出**。

## 4.5.3 但是:Fragment 持 UObject 时 GC 仍然介入

虽然 Mass entity 不是 UObject,但 Fragment 经常需要持有 UObject:

```cpp
USTRUCT()
struct FUnitVisualFragment : public FMassFragment
{
    GENERATED_BODY()

    UPROPERTY()
    TObjectPtr<UStaticMesh> Mesh;
};
```

50K entity × 1 个 `TObjectPtr<UStaticMesh>` = 50K 引用边。

### 4.5.3.1 GC 怎么扫这些引用

Mass 内部维护一份**fragment GC schema**:每种 Fragment 类型注册"哪些字段是 UObject 引用 + 偏移"。GC mark 阶段调 Mass 的桥接函数:

```cpp
// 简化伪代码:Mass 自己实现的 GC 协作
void UMassEntitySubsystem::AddReferencedObjects(FReferenceCollector& C)
{
    // 遍历所有 archetype
    for (FMassArchetypeData* Archetype : AllArchetypes)
    {
        // 遍历每个 chunk
        for (FMassArchetypeChunk& Chunk : Archetype->Chunks)
        {
            // 对每个含 UObject 字段的 Fragment 类型
            for (FFragmentRefInfo& Info : Archetype->RefInfos)
            {
                // 扫 chunk 内所有 entity 的该字段
                for (int32 i = 0; i < Chunk.NumEntities; ++i)
                {
                    UObject** Ref = Chunk.GetFragmentField<UObject*>(Info.FragmentIdx, Info.Offset, i);
                    C.AddReferencedObject(*Ref);
                }
            }
        }
    }
}
```

`UMassEntitySubsystem` 是 UObject,它的 `AddReferencedObjects` 被 GC mark 调,**它替所有 entity 报告引用**。

### 4.5.3.2 性能估算

50K entity × 1 引用 × 每引用 ~5 ns(走 chunked 紧凑数组,cache 友好)= **250 μs / GC mark**。

每 60 秒 GC 一次,摊到帧 = **4 μs / 帧**。**完全不影响**。

但如果你滥用:50K × 10 个 UObject 引用 / Fragment = 500K 引用 = 2.5 ms / mark。仍然可接受,但开始有压力。

### 4.5.3.3 优化:用 SharedFragment 减少引用数

```cpp
// ❌ 每 entity 一个 mesh 引用
USTRUCT() struct FBadVisual : public FMassFragment {
    UPROPERTY() TObjectPtr<UStaticMesh> Mesh;     // 50K 份
};

// ✅ 每 archetype 一份 mesh 引用
USTRUCT() struct FGoodVisual : public FMassSharedFragment {
    UPROPERTY() TObjectPtr<UStaticMesh> Mesh;     // 几十份(archetype 数量)
};
```

SharedFragment 在每 archetype 共享一份。GC 只扫几十次,而不是 50K 次。

## 4.5.4 RTS 混合架构的 GC 预算

实战 RTS 项目几乎都是 **混合架构**:

```
重要单位(英雄、Boss、采集物大型):       走 AActor  ~50 个
普通单位(兵、投射物、效果):             走 Mass    50,000 个
UI 元素:                                 走 UMG     ~100 个
全局管理:                                 走 Subsystem ~10 个
资产:                                     UDataAsset ~500 个
```

### 4.5.4.1 GUObjectArray 估算

- 引擎自带:50K
- 重要 actor + components:50 × 8 = 400
- UI:100 × 平均 3 = 300
- Subsystem / Manager:10
- 资产:500
- Mass(Subsystem / Trait CDO / Processor):200

合计 **~ 51,000 UObject**。Editor 加 Editor-specific 对象到 100-200K。Game 几乎纯 50K。

### 4.5.4.2 GC 性能预算

| 操作 | 时间 |
|---|---|
| GC mark(每 60 秒一次,Game) | ~2 ms |
| GC sweep(增量 2 ms / 帧 budget) | 平均 < 1 ms / 帧 |
| Mass 引用扫(并入 mark) | 几百 μs |
| Spawn / Despawn 重要 actor | 偶尔几十 ms 峰值 |
| Mass entity 创建 / 销毁 | < 1 ms / 帧 |

**总 GC 影响 < 1 ms / 帧均值**。完全在预算内。

## 4.5.5 RTS 的 GC 调谐建议

### 4.5.5.1 启动期

- **不**给 Mass entity 加 UObject 头。任何"想给 entity 反射 / GC / Editor 编辑"的提议,先想能不能用 Fragment 数据 + Trait 配置替代。
- 控制 Subsystem 数量 < 10。每个职责清晰。
- 资产不要建几千个。500-2000 个 DataAsset 够用,数据多用单文件多条目。

### 4.5.5.2 运行期 cvar

```ini
[ConsoleVariables]
gc.AllowIncrementalReachability=1               ; 启用增量 mark
gc.IncrementalReachabilityTimeLimit=0.001       ; 1ms / 帧 mark 预算
gc.AllowParallelGC=1                            ; 并行
gc.TimeBetweenPurgingPendingKillObjects=60      ; 60 秒一次 GC,Game 默认
```

### 4.5.5.3 关键时机主动 GC

```cpp
// 关卡切换前
UEngine::ForceGarbageCollection(/*bFullPurge*/ true);

// 战斗结束、回大厅
UEngine::ForceGarbageCollection(/*bFullPurge*/ false);

// 大量 spawn 单位之前预热
// (不需要主动 GC,Mass 创建本就轻量)
```

### 4.5.5.4 监控指标

每帧记一个 trace counter:

```cpp
TRACE_COUNTER_SET(GUObjectCount, GUObjectArray.GetObjectArrayNum());
TRACE_COUNTER_SET(MassEntityCount, EntitySubsystem->GetNumEntities());
```

Insights 时序图能立刻看出"UObject 数量是不是异常增长"。

## 4.5.6 设计决策检查清单

每次 RTS 项目里要"加新东西",过这个清单:

```
[ ] 这个东西的实例数量级是多少?
    < 100  → AActor / UObject 没问题
    100-1000 → 谨慎,优先 UObject 也可以
    > 1000 → 必须 Mass entity

[ ] 这个东西需要 Editor 配置吗?
    需要 → 它是 Trait / DataAsset / BP 类(配置层走 UObject)
    实例数据不需要 Editor 编辑 → Fragment

[ ] 这个东西需要被 BP 调用吗?
    是 → UObject(BP 只能调 UFUNCTION)
    否 → Fragment 或 C++ class

[ ] 这个东西生命周期是?
    短(秒级)且数量大 → Mass entity 必须
    长且数量少 → Actor / Subsystem
    全程 → Subsystem(AddToRoot)

[ ] 它持有 UObject 引用吗?
    用 UPROPERTY + TObjectPtr<>(Fragment 也支持)
    弱引用用 TWeakObjectPtr
```

99% 的 RTS 中"具体单位"满足"实例多 + 不需 Editor 单独编辑 + 生命周期变化 + 持有几个共享资产引用",**全部走 Mass**。

- [x] **静态注册**:`Z_CompiledInDeferFile_*` 全局静态构造链,5.0 起 UProperty → FProperty 拆分
- [x] **运行时反射**:`Cast<>` 快/慢路径,`FindPropertyByName` O(N),`ProcessEvent` ~500ns,**hot path 缓存指针**

- [x] **UObject 内存**:三层继承,`sizeof(UObject) = 40 字节`,5 个核心字段

- [x] **NewObject**:几微秒级 / 一次,Actor 几十微秒,**Mass 必须绕开**
- [x] **CDO / Archetype / Instance**:三态对象,delta 序列化基于 archetype 不同的字段
- [x] **FArchive 序列化**:`<<` 双向,`FCustomVersion` 跨版本兼容
- [x] **GC 引用图**:5+ 种引用姿势,UPROPERTY + TObjectPtr 标准
- [x] **GC 调度**:`CollectGarbage` / `IncrementalPurgeGarbage`,5.x 增量 reachability
- [x] **GC 标记**:Token Stream / Reference Schema 预编译,TFastReferenceCollector 并行 + work stealing
- [x] **GC 清扫**:`MarkAsGarbage → BeginDestroy → IsReadyForFinishDestroy → FinishDestroy` 状态机,5.x Garbage Elimination
- [x] **Mass 必要性**:50K 单位走 Actor 体系不可行(GC + spawn + tick 累计 80-400 ms / 帧),Mass 3-4 ms / 帧
