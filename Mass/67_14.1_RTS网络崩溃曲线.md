## 14.1.1 三大崩溃曲线

```
1. NetGuid 爆炸:
   50K replicated actor + 5 component / actor = 250K NetGUID
   GUID 表 server / client 各一份 = 几 MB 内存
   GUID ack 状态 + dynamic GUID 创建延迟

2. ReplicationFrame O(N) 扫描:
   每帧 ServerReplicateActors 遍历所有 replicated actor
   50K × CompareProperties = 几十 ms / 帧
   每个 connection 重复一次 = 几百 ms / 帧

3. 带宽墙:
   单 connection 上行 < 128 KB/s,下行 < 512 KB/s
   每帧能复制的 actor 状态有限
   50K actor 的总状态远超带宽
```

---

## 14.1.2 NetGuid 爆炸

```
50K Actor:
   Server 的 GuidCache(NetGUID ↔ UObject) = 50K 项
   每项约 32-64 字节 = 1.6 - 3.2 MB
   
   每个 Client 收到的 GuidCache 也是 50K 项(相同) = 同样大小
   
   ACK 状态:每个 client 跟踪"已知道哪些 GUID"
   Server 端 = 50K × 10 client × 几字节 = ~5 MB
```

加上 dynamic GUID 创建延迟(两端同步要 1-2 RTT)→ 大量 actor 创建会让"前几秒看不到 actor"。

---

## 14.1.3 ReplicationFrame 扫描

```
每帧 ServerReplicateActors:
   对每个 connection:
      对每个 actor:
         relevancy 检测            ~50 ns
         priority 计算             ~50 ns
         CmpAndCopy(若 dirty)     ~1-10 μs

50K actor × 10 client × ~1 μs = 500 ms / 帧
```

**完全不可行**。即使 NetUpdateFrequency 降到 1Hz,仍然几十 ms / 帧。

---

## 14.1.4 带宽墙

### 14.1.4.1 单 connection 预算

```
理想 NetSpeed = 128 KB/s 上行(玩家命令)
              + 512 KB/s 下行(server → client)

每帧带宽预算(60 fps):
   128 / 60 = ~2 KB / 帧 上行(client → server)
   512 / 60 = ~8.5 KB / 帧 下行(server → client)
```

### 14.1.4.2 50K 单位的状态量

```
单位状态(最小):
   Position (3 × float = 12 字节)
   Rotation (1 × float = 4 字节)
   Health (1 × int16 = 2 字节)
   = ~20 字节 / 单位

50K 单位 × 20 字节 = 1 MB

每秒同步 1 次:1 MB/s 远超 512 KB/s
即使 1 Hz 同步:仍超
```

**完全不可行**。必须**量化 + 兴趣管理 + delta**。

---

## 14.1.5 兴趣管理(Interest Management)

不是所有 50K 单位都要给所有 client 看。**玩家只关心**:
- 自己的单位(数百)
- 玩家可见区域内的敌人单位(数千)
- 视野外不需要(战争迷雾)

```
50K 单位 × 5% 玩家可见 × 10 client = 25K 复制项 / 帧 = ~500 KB / 帧
```

仍然超带宽。需要**进一步压缩**。

---

## 14.1.6 量化(Quantization)

```
传统复制:
   FVector Pos = (123.456, 78.9, 0.0)   12 字节

量化复制:
   int16 X = (int16)(Pos.X * 100);       2 字节
   int16 Y = (int16)(Pos.Y * 100);       2 字节
   int8 Z = (int8)(Pos.Z * 10);          1 字节
   = 5 字节(精度 1cm 内)
   
   节省 60%
```

朝向同样可量化(8 位 yaw 表示 360 度,精度 1.4 度)。

---

## 14.1.7 Delta encoding(增量)

```
不发完整状态,只发"与上一帧不同的部分":

帧 N:Pos = (100, 200, 0), Health = 100
帧 N+1:Pos = (101, 200, 0), Health = 99

发送:
   Pos.X = +1
   Pos.Y = 0
   Pos.Z = 0
   Health = -1
   
进一步用 bit field 表达"哪些字段变了":
   FieldsChanged = 0b1001 (Pos.X, Health)
   Pos.X = +1
   Health = -1
```

50K 单位每帧只有 ~5% 在动 → 只发 ~2.5K 个变化。

---

## 14.1.8 综合优化估算

```
50K Mass entity:
   - 兴趣管理:每 client 看 ~5K
   - 量化:每 entity 5 字节
   - Delta:实际 ~5% 变化
   
每帧实际带宽:5K × 5 byte × 5% = 1.25 KB / 帧 = 75 KB/s
每个 connection 容易处理。
   
内存:
   - 不分配 NetGUID(Mass entity 不是 UObject)
   - Mass 自定义 ID(几字节)+ 紧凑 fragment 数据
   
CPU:
   - ServerReplicateActors 不扫 Mass(自定义 path)
   - Mass 自己 push dirty(类似 Iris 模型)
```

→ Mass + Iris + 量化 + 兴趣管理 = 50K 单位 + 10 client 完全可行。
