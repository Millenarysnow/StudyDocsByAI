## 5.5.1 Mass 调度的总览

`UMassEntitySubsystem` + Processor 一组一起跑的"调度循环"概念:

```
World Tick(GameThread)
   │
   ↓
UMassSimulationSubsystem::Tick (GameThread)
   │
   ↓
ExecutionPhase: PrePhysics
   │
   ├─ ProcessorA(并行 chunks)
   │     ↓
   ├─ ProcessorB(等 A,并行 chunks)
   │     ↓
   ├─ ProcessorC(等 A,与 B 并发)
   │     ↓
   └─ Sync(barrier)
   │
   ↓
ExecutionPhase: DuringPhysics ...
ExecutionPhase: PostPhysics ...
ExecutionPhase: FrameEnd ...
   │
   ↓
World Tick 结束
```

涉及四类并发挑战:

1. **Processor 之间的依赖图**:谁先跑、谁能并发
2. **单个 Processor 内部 chunks 的并行**:一个 Processor 要扫几百个 chunk,怎么分给 worker
3. **跨 Processor 的命令缓冲**:某 Processor 要"延迟修改" entity composition,要排队
4. **跨阶段的同步**:PrePhysics 全部跑完才进 DuringPhysics

每一项 Mass 都用了前面讲过的设施。下面逐项拆。

---

## 5.5.2 挑战 1:Processor 间依赖图 → TaskGraph / UE::Tasks

每个 `UMassProcessor` 声明自己的依赖(`ExecuteAfter / ExecuteBefore` specifier)。Mass 启动期把这些依赖**编译成 DAG**:

```cpp
// 简化伪代码
class UMassMovementProcessor : public UMassProcessor {
    UMassMovementProcessor() {
        ExecutionOrder.ExecuteAfter.Add(UMassInputProcessor::StaticClass()->GetFName());
    }
};

// Mass 启动时
TArray<UMassProcessor*> Processors = ...;
for each P in Processors:
    Determine dependencies via reflection
Build DAG of (predecessor → successor)
```

**运行时**(每个 ExecutionPhase):

```cpp
// 用 UE::Tasks 提交所有 Processor 的并行任务
TArray<TTask<void>> Tasks;
for each P in TopologicallySortedProcessors:
{
    TArray<TTask<void>> Prereqs = GetPrereqTasksFor(P);
    
    Tasks.Add(UE::Tasks::Launch(UE_SOURCE_LOCATION,
        [P, Context]() {
            P->Execute(EntityManager, Context);
        },
        Prereqs    // 等所有前驱完成
    ));
}

// 阶段末等所有完成
UE::Tasks::Wait(Tasks);
```

**用了什么设施**:
- `UE::Tasks::Launch`(§5.3.2)创建任务
- `Prerequisites` 表达 DAG
- `Wait` 在阶段末同步

### 5.5.2.1 优势

- 同阶段内**多个 Processor 并发**(无 Processor 间依赖时)
- 一个 Processor 可同时**等多个**前驱(汇合点)
- 调度自动均衡到 worker pool

## 5.5.3 挑战 2:Processor 内 chunks 并行 → ParallelFor / UE::Tasks

每个 Processor 处理"匹配 query 的所有 archetype chunk"。Chunk 数量级几十到几千。

```cpp
class UMassMovementProcessor : public UMassProcessor {
    void Execute(FMassEntityManager& EntityManager, FMassExecutionContext& Context) override {
        Query.ParallelForEachEntityChunk(EntityManager, Context, [](FMassExecutionContext& Ctx) {
            // 处理一个 chunk
            const TArrayView<FMovementFragment> Movements = Ctx.GetMutableFragmentView<FMovementFragment>();
            for (FMovementFragment& M : Movements)
            {
                M.Velocity += M.Acceleration * Ctx.GetDeltaTimeSeconds();
            }
        });
    }
};
```

`ParallelForEachEntityChunk` 内部:

```cpp
// 简化
void ParallelForEachEntityChunk(EntityManager, Context, Func) {
    TArray<FArchetypeChunk*> Chunks = FindMatching(Query);
    
    // 启动 N 个 task,每个处理 1+ chunk
    TArray<TTask<void>> Tasks;
    for each Chunk in Chunks:
    {
        Tasks.Add(UE::Tasks::Launch(UE_SOURCE_LOCATION, [Chunk, &Func, &Ctx] {
            FMassExecutionContext LocalCtx = MakeChunkContext(Ctx, Chunk);
            Func(LocalCtx);
        }));
    }
    
    UE::Tasks::Wait(Tasks);
}
```

**用了什么设施**:
- 同样 `UE::Tasks::Launch`
- 每 chunk 一个独立 task,worker pool 自动并行
- Chunk 是连续内存(§17),cache 友好

### 5.5.3.1 50K entity 的扫描时间

50K entity / chunk 容量 ~64 entity = ~780 chunks。8 worker 每个跑 ~100 chunk。
每 chunk 几百 entity × 几十 ns/entity = 几μs/chunk × 100 = 几百 μs/worker。

**Movement Processor 单次扫描 ~1-3 ms**(并行后)。完全在帧预算内。

### 5.5.3.2 自动负载均衡

worker 用 work stealing(§5.2.7),即使 chunks 大小不一,空闲 worker 偷活,负载自动均衡。

## 5.5.4 挑战 3:跨 Processor 命令缓冲 → MPSC 队列

Processor 内部不能"立即"修改 entity 的 archetype(因为别的 worker 可能正在扫这个 chunk)。Mass 要求**延迟修改**,通过命令缓冲:

```cpp
void UMyProcessor::Execute(...) {
    Query.ParallelForEachEntityChunk(EntityManager, Context, [](FMassExecutionContext& Ctx) {
        for each entity:
            if (ShouldDie(entity))
                Ctx.Defer().DestroyEntity(EntityHandle);   // 不立即销毁,排进命令队列
            if (ShouldChangeType(entity))
                Ctx.Defer().AddTag<FNewTag>(EntityHandle);  // 延迟改 archetype
    });
}

// 当前 Processor 跑完后,Mass 主线程 flush 命令队列
EntityManager.FlushCommands();
```

`Ctx.Defer()` 返回一个**线程安全的命令缓冲**(`FMassCommandBuffer`),内部用 lock-free 队列(§5.4)收集命令。多个 worker 并发产生命令 → MPSC 队列接收 → GameThread 一次性 flush。

### 5.5.4.1 用了什么设施

- `TMpscQueue` 或类似的 lock-free 容器(§5.4.4)收集命令
- Worker 端 `Enqueue`(无锁)
- GameThread 端 `Dequeue` + `Apply`

### 5.5.4.2 为什么必须延迟

如果 worker A 在 chunk 上扫,worker B 改这 chunk 的 archetype(增加 / 删除 fragment)→ A 看到的内存被破坏。**写者必须等读者全完成**。

Mass 的解法是 RW barrier:**Processor Execute 期间禁写,Execute 末尾 flush 命令**。

## 5.5.5 挑战 4:阶段同步 → UE::Tasks::Wait + Pipe

阶段间(PrePhysics → DuringPhysics)必须 barrier:

```cpp
// 简化伪代码
UMassSimulationSubsystem::Tick(...) {
    for each Phase in [PrePhysics, DuringPhysics, PostPhysics, FrameEnd]:
    {
        TArray<TTask<void>> PhaseTasks = LaunchAllProcessorsForPhase(Phase);
        UE::Tasks::Wait(PhaseTasks);              // ★ 阶段 barrier
        
        EntityManager.FlushCommands();             // 应用所有延迟命令
    }
}
```

阶段 barrier 用 `Wait` 确保**所有 Processor 完成 + 所有命令 flush** 才进下阶段。

### 5.5.5.1 BusyWait 优化

GameThread `Wait` 期间可以帮 worker 干活:

```cpp
UE::Tasks::BusyWait(PhaseTasks);
```

GameThread 不空转,直到 PhaseTasks 全完成。

## 5.5.6 命令缓冲细节:`FMassCommandBuffer`

简化伪代码(实际更复杂,§17 / §18 详讲):

```cpp
class FMassCommandBuffer
{
    TMpscQueue<TUniquePtr<FMassCommand>> PendingCommands;
    
public:
    template<typename TCommand, typename... TArgs>
    void Push(TArgs&&... Args)
    {
        PendingCommands.Enqueue(MakeUnique<TCommand>(Forward<TArgs>(Args)...));
    }
    
    void Flush(FMassEntityManager& EM)
    {
        TUniquePtr<FMassCommand> Cmd;
        while (PendingCommands.Dequeue(Cmd))
        {
            Cmd->Execute(EM);
        }
    }
};
```

每个 worker 调 `Push` → MPSC 入队。GameThread 调 `Flush` → 顺序 apply。

**实战**:你写 Processor 时,**所有"改 entity"的操作走 `Ctx.Defer()`**,不会出错。

## 5.5.7 RTS 项目模仿 Mass 模式做并行

Mass 之外,你 RTS 可能有"非 entity 数据"也要并行处理(典型:雾战 grid、AI 全局决策)。**模仿 Mass 调度**:

```cpp
class URTSFogOfWarSubsystem : public UWorldSubsystem
{
    TArray<FFogCell> FogGrid;          // 数千 cell 的雾战网格
    TMpscQueue<FFogCommand> Commands;
    
    void Tick(float DeltaTime)
    {
        // 1. 启动并行任务,每 task 处理一段 grid
        TArray<TTask<void>> Tasks;
        const int32 NumWorkers = 8;
        const int32 CellsPerWorker = FogGrid.Num() / NumWorkers;
        
        for (int32 i = 0; i < NumWorkers; ++i)
        {
            int32 Start = i * CellsPerWorker;
            int32 End = (i == NumWorkers - 1) ? FogGrid.Num() : Start + CellsPerWorker;
            
            Tasks.Add(UE::Tasks::Launch(UE_SOURCE_LOCATION,
                [this, Start, End]() {
                    for (int32 j = Start; j < End; ++j)
                    {
                        UpdateCell(FogGrid[j]);
                    }
                    
                    // 跨 cell 的修改放命令
                    if (NeedSpawnDecal(j))
                    {
                        Commands.Enqueue({ ECmd::SpawnDecal, ... });
                    }
                }));
        }
        
        // 2. 等所有完成
        UE::Tasks::BusyWait(Tasks);
        
        // 3. flush 命令(GameThread)
        FFogCommand Cmd;
        while (Commands.Dequeue(Cmd))
        {
            ApplyCommand(Cmd);
        }
    }
};
```

完全模仿 Mass:**并行处理 + lock-free 命令缓冲 + barrier 同步 + GameThread flush**。

## 5.5.8 Mass 性能数字回顾

整合 §5.1-§5.4 的所有性能数字,Mass 一帧的开销分布(50K entity,8 worker):

| 阶段 | 开销 |
|---|---|
| Processor DAG 构建 | 启动期一次性,运行时 0 |
| Processor 任务派发 | ~10 μs / 帧(几十个 task launch) |
| Movement Processor(并行) | ~1.5 ms |
| AI Processor(并行) | ~3 ms |
| LOD Processor(并行) | ~1 ms |
| Representation Processor(并行) | ~2 ms |
| 命令缓冲 flush(GameThread) | ~100 μs |
| 阶段 barrier 同步 | < 50 μs / barrier × 4 = ~200 μs |
| **总计** | **~7-8 ms / 帧** |

**这就是 Mass + 50K 单位的总账**。剩 8-9 ms 给渲染、UI、网络。一帧 16.6 ms 内。
