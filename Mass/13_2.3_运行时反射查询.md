# §2.3 运行时反射查询 — StaticClass / FindProperty / Cast / 反射调用

> **本节地图**:模块一第 2 章第 3 节。§2.1 / §2.2 把"反射数据怎么生成 + 怎么注册到运行时"讲完了。这一节我们看这些反射数据**怎么被使用** —— Blueprint 调 C++、网络复制读字段、GC 扫引用、Editor 的 Property panel,这些场景都靠下面这些查询 API。
>
> **预备知识**:§2.2(必读)。
>
> **读完之后你能做到**:
> - 看到 `Cast<T>(Obj)` 知道编译期/运行时分别走哪条路径(快路径 vs 慢路径)
> - 用 `FindPropertyByName` / `TFieldIterator` 写运行时字段访问代码
> - 看懂 Blueprint 调 C++ 时 `UFunction::ProcessEvent` 的执行栈
> - 知道反射调用比直接调用的固定开销(几百 ns 量级)
> - 在 Mass 视角下**避免**反射调用进入 hot path
> - 改 Engine 时正确设置 ClassCastFlags 让你的类参与 Cast<> 快路径

## 2.3.1 浅入:`Cast<T>` 在不同场景下的开销天差地别

```cpp
UObject* Obj = GetSomeObject();

UStaticMeshComponent* SMC = Cast<UStaticMeshComponent>(Obj);   // ←(A)
UMyComponent*         MyC = Cast<UMyComponent>(Obj);            // ←(B)
```

(A) 和 (B) 看起来一样,**实际开销可能差 10 倍以上**。

- (A) `UStaticMeshComponent` 是引擎内置类,**有 ClassCastFlag**(`CASTCLASS_UStaticMeshComponent`),Cast 走"位运算 + 一次比较"的快路径,~5ns
- (B) `UMyComponent` 是你自定义类,**没有** ClassCastFlag,Cast 退化为 `IsA<T>()` 走继承链遍历,~20-100ns

这一节我们把这些路径全部拆开。

---

## 2.3.2 `StaticClass<T>()` —— 反射查询的入口

每个 UCLASS 都有静态成员函数 `static UClass* StaticClass()`,这是 UHT 通过 `DECLARE_CLASS` 宏(§2.1.6.4)生成的。

```cpp
// 用法
UClass* C = UMyComponent::StaticClass();      // 直接调静态成员
UClass* C = StaticClass<UMyComponent>();      // 模板版本

// 内部实现
template<typename T>
inline UClass* StaticClass() { return T::StaticClass(); }     // 通用模板

// .gen.cpp 里 UHT 给特定 UCLASS 提供的显式特化(§2.2.10):
template<> MYMOD_API UClass* StaticClass<UMyComponent>() 
{ 
    return UMyComponent::StaticClass(); 
}
```

### 2.3.2.1 `T::StaticClass()` 内部

`DECLARE_CLASS` 宏展开后的 `StaticClass()` 大致:

```cpp
static UClass* StaticClass()
{
    return GetPrivateStaticClass<UMyComponent>();
}
```

`GetPrivateStaticClass<T>` 内部用一个**模板局部静态变量**缓存 UClass*:

```cpp
template<typename T>
UClass* GetPrivateStaticClass()
{
    extern UClass* GetPrivateStaticClassBody(...);
    static UClass* PrivateStaticClass = nullptr;
    if (!PrivateStaticClass)
    {
        PrivateStaticClass = GetPrivateStaticClassBody(/* 类型信息 */);
    }
    return PrivateStaticClass;
}
```

- 第一次调用 → 触发完整反射构造(经过 §2.2 讲的 `Z_Construct_UClass_*` 链)
- 后续调用 → 直接返回缓存指针,**单次内存读**

**性能**:稳态下 `StaticClass<T>()` ≈ 1-2 ns。**几乎免费**。

### 2.3.2.2 与 `FindFirstObject<UClass>` 的对比

```cpp
UClass* C1 = UMyComponent::StaticClass();                          // ★ 编译期已知类型
UClass* C2 = FindFirstObject<UClass>(TEXT("MyComponent"));         // ☆ 字符串名查找
```

C1 是编译期就知道目标类型。C2 是只在运行时知道名字。后者要遍历 `GUObjectArray` 找匹配的 `UClass`,**O(N)** 慢得多。

**纪律**:能用 `StaticClass<T>()` 就别用 `FindFirstObject` / `FindObject` / `LoadClass`。后者只在你**真的只有名字字符串**的场景(资产 ID、配置文件名)用。

## 2.3.3 `IsA<T>` / `IsChildOf` —— 父子关系判断

### 2.3.3.1 `IsA<T>`(成员函数)

```cpp
UObject* Obj = ...;
if (Obj->IsA<UStaticMeshComponent>()) { ... }
// 等价于
if (Obj->IsA(UStaticMeshComponent::StaticClass())) { ... }
```

实现简化(`UObjectBaseUtility.h` 等):

```cpp
template<typename T>
bool UObjectBase::IsA() const
{
    return IsA(T::StaticClass());
}

bool UObjectBase::IsA(const UClass* SomeBase) const
{
    return GetClass()->IsChildOf(SomeBase);
}
```

### 2.3.3.2 `UClass::IsChildOf` —— 关键的"祖先关系"检查

`Engine/Source/Runtime/CoreUObject/Private/UObject/Class.cpp` 里 `UStruct::IsChildOf` 大致:

```cpp
bool UStruct::IsChildOf(const UStruct* SomeBase) const
{
    if (!SomeBase) return false;
    
    for (const UStruct* Struct = this; Struct; Struct = Struct->GetSuperStruct())
    {
        if (Struct == SomeBase) return true;
    }
    return false;
}
```

**这是 O(D) 的祖先链遍历**,D 是继承深度。

UE 类继承通常 5-15 层(`UMyComponent ← UActorComponent ← UObject`),所以一次 `IsA` 大约 5-15 次指针追跟 + 比较。

**性能**:稳态 ≈ 10-30 ns。比 StaticClass 慢一个数量级,但仍很快。

## 2.3.4 `Cast<T>` —— 快路径 vs 慢路径

`Engine/Source/Runtime/CoreUObject/Public/Templates/Casts.h:95`:

```cpp
template <typename To, typename From>
inline TCopyQualifiersFromTo_T<From, To>* Cast(From* Src)
{
    static_assert(sizeof(From) > 0 && sizeof(To) > 0, "Attempting to cast between incomplete types");

    if (Src)
    {
        // 路径 1:Interface → Object
        if constexpr (TIsIInterface<From>::Value) { /* 接口 cast */ }
        else
        {
            static_assert(std::is_base_of_v<UObjectBase, From>, "...");

            // 路径 2:目标类型有 ClassCastFlag(快路径)
            if constexpr (UE_USE_CAST_FLAGS && UE::CoreUObject::Private::TCastFlags_V<To> != CASTCLASS_None)
            {
                if constexpr (std::is_base_of_v<To, From>)
                {
                    return (To*)Src;     // 编译期已知 From 是 To 的子类 → 直接转
                }
                else
                {
                    if (((const UObject*)Src)->GetClass()->HasAnyCastFlag(UE::CoreUObject::Private::TCastFlags_V<To>))
                    {
                        return (To*)Src;     // ★ 一次 flag 检查 + 一次 cast
                    }
                }
            }
            else
            {
                // 路径 3:无 ClassCastFlag,退化到 IsA(慢路径)
                if constexpr (TIsIInterface<To>::Value)
                {
                    return (To*)((UObject*)Src)->GetInterfaceAddress(To::UClassType::StaticClass());
                }
                else if constexpr (std::is_base_of_v<To, From>)
                {
                    return Src;            // 编译期已知 From 是 To 子类
                }
                else
                {
                    if (((const UObject*)Src)->IsA<To>())  // ★ IsA 走继承链
                    {
                        return (To*)Src;
                    }
                }
            }
        }
    }

    return nullptr;
}
```

把它拆开:

### 2.3.4.1 路径分类

| 场景 | 路径 | 性能 |
|---|---|---|
| `Cast<U子类>(父类指针)`,U子类 有 CastFlag | 路径 2 快路径 | ~3-5 ns |
| `Cast<U子类>(父类指针)`,U子类 无 CastFlag | 路径 3 慢路径(IsA 走链) | ~20-100 ns |
| `Cast<父类>(子类指针)`,编译期已知父子 | 直接 cast,不查反射 | ~0 ns(编译期消失) |
| `Cast<U另一支>(无关类型)` | 编译期 warning,运行时返回 nullptr | 极快 |
| `Cast<UInterface>(对象)` | 走 `GetInterfaceAddress` | ~10-30 ns |

### 2.3.4.2 ClassCastFlag —— 快路径的"魔法"

每个引擎内置 UCLASS 在反射注册时**预分配一个 64 位 flag**(`CASTCLASS_*`)。`UClass::ClassCastFlags` 字段是这些 flag 的 OR 累加(自身 + 所有祖先类的 flag)。

```cpp
// ObjectMacros.h(枚举片段)
enum EClassCastFlags : uint64
{
    CASTCLASS_None = 0x0000000000000000,
    CASTCLASS_UField = 0x0000000000000001,
    CASTCLASS_FInt8Property = 0x0000000000000002,
    CASTCLASS_UEnum = 0x0000000000000004,
    CASTCLASS_UStruct = 0x0000000000000008,
    CASTCLASS_UScriptStruct = 0x0000000000000010,
    CASTCLASS_UClass = 0x0000000000000020,
    CASTCLASS_FByteProperty = 0x0000000000000040,
    // ... 60+ 个具体类型 ...
    CASTCLASS_AActor = 0x0001000000000000,
    CASTCLASS_UActorComponent = 0x0002000000000000,
    CASTCLASS_UStaticMeshComponent = 0x0004000000000000,
    // ...
};
```

注意所有 flag **总数受 64 位限制**。这就是为什么**只有引擎内置的极少数核心类有 CastFlag**,**你自定义的 UClass 没有**(没位置了)。

`HasAnyCastFlag` 检查:
```cpp
bool UClass::HasAnyCastFlag(EClassCastFlags Flag) const 
{ 
    return (ClassCastFlags & Flag) != 0; 
}
```

一次位与 + 比较,5ns 内搞定。**所以 `Cast<UStaticMeshComponent>(Actor)` 极快**,`Cast<UMyComponent>(Actor)` 慢一截。

### 2.3.4.3 实战影响

```cpp
// ★ 快(走 CastFlag)
if (auto* SMC = Cast<UStaticMeshComponent>(Component)) { ... }
if (auto* AC = Cast<AActor>(Object)) { ... }
if (auto* PC = Cast<APlayerController>(Controller)) { ... }

// ☆ 慢(走 IsA 链)
if (auto* MyC = Cast<UMyComponent>(Component)) { ... }   // 你的类
```

差距在 hot path 上累积可观。**Mass 视角**:Mass Processor 里**绝不能**用 `Cast<TYourCustomClass>` 在每 entity 上判断,代价巨大。

## 2.3.5 `CastChecked<T>` —— 不返回 nullptr 的版本

```cpp
// CastChecked:Cast 失败时 check fail(crash)
auto* SMC = CastChecked<UStaticMeshComponent>(Component);  // 你"确信"它就是 SMC
```

适用场景:**你已经从其它途径(类型 ID / 注册表)知道类型,只是要换指针类型**。`CastChecked` 比 `Cast` 略快(部分检查在 Shipping 关掉),但**错了就 crash**。

**纪律**:`CastChecked` 用于"按约定来说一定对"的场景。你不太确定就用 `Cast`,做空指针检查。

## 2.3.6 `CastField<T>` —— FProperty 体系的 Cast

5.0+ FProperty 不是 UObject(§2.2.5),不能用 `Cast<>`。用 `CastField<>`:

```cpp
FProperty* Prop = MyClass->FindPropertyByName(TEXT("Health"));
if (FIntProperty* IntProp = CastField<FIntProperty>(Prop))
{
    int32 Value = IntProp->GetSignedIntPropertyValue(...);
}
```

`CastField` 用 `FFieldClass` 体系(§2.2.5.3)的 cast flags,与 UClass 的 flags **是不同体系**但思路一样。

## 2.3.7 `FindPropertyByName` —— 按名字找字段

`Engine/Source/Runtime/CoreUObject/Private/UObject/Property.cpp:2443`:

```cpp
// Property.cpp:2443
FProperty* UStruct::FindPropertyByName(FName InName) const
{
    for (FProperty* Property = PropertyLink; Property != nullptr; Property = Property->PropertyLinkNext)
    {
        if (Property->GetFName() == InName)
        {
            return Property;
        }
    }
    return nullptr;
}
```

**O(N) 线性扫描**!不是哈希。每个 UStruct 维护一个 `PropertyLink` 单链表,从头扫到目标。

注意 `FName` 比较是 O(1)(`FName` 是 `int32 + int32`,直接整数比较,§3 详讲)。所以单次比较快,但**整体仍 O(字段数)**。

### 2.3.7.1 `PropertyLink` 链表的两个细节

`PropertyLink` 链表有几个版本:
- `PropertyLink`:**所有**字段(包括继承自父类的)
- `RefLink`:**含 UObject 引用**的字段(GC 扫描专用)
- `DestructorLink`:需要析构的字段(销毁时遍历)
- `PostConstructLink`:需要构造时初始化的字段

`FindPropertyByName` 用第一条。这就是为什么"Outer 类越深,字段越多,FindPropertyByName 越慢"。

### 2.3.7.2 性能含义

```
- 一个简单 UCLASS,5 字段        : ~5 次比较 ≈ 30 ns
- 复杂 UCLASS(继承 UActorComponent),60+ 字段 : ~60 次比较 ≈ 300 ns
```

**纪律**:`FindPropertyByName` **一次性查询**(启动期 / 偶尔触发)无所谓;**hot path 上每帧调** —— 缓存结果到 `FProperty*` 指针,后续直接用指针。

```cpp
// ❌ 慢
void TickComponent(...)
{
    FProperty* Health = GetClass()->FindPropertyByName(TEXT("Health"));   // 每帧查
    int32* Ptr = Health->ContainerPtrToValuePtr<int32>(this);
    // ...
}

// ✅ 快
class UMyComp
{
    static FProperty* CachedHealthProp;     // 一次查,缓存
    
    UMyComp::UMyComp()
    {
        if (!CachedHealthProp)
            CachedHealthProp = StaticClass()->FindPropertyByName(TEXT("Health"));
    }
    
    void TickComponent(...)
    {
        int32* Ptr = CachedHealthProp->ContainerPtrToValuePtr<int32>(this);
    }
};
```

**Mass 视角**:Fragment 字段的反射访问(典型场景:序列化、网络复制)**绝不能**走 `FindPropertyByName`。Mass 自己维护一份"Fragment 类型 → 字段偏移"的预计算缓存。

### 2.3.7.3 `FindPropertyByOffset`(罕见)

```cpp
UE_INTERNAL FProperty* FindPropertyByOffset(int32 Offset) const;
```

按字节偏移找字段。罕见,主要用于反序列化错误恢复 / 调试工具。

## 2.3.8 `TFieldIterator` —— 遍历字段 / 函数

`Engine/Source/Runtime/CoreUObject/Public/UObject/UnrealType.h:7082`:

```cpp
template<class T = FField, EFieldIterationFlags InIterationFlags = EFieldIterationFlags::Default>
class TFieldIterator
{
    // 内部维护当前 UStruct + 当前 FField 指针
    // operator++ 推进,可选跳过父类字段

struct TFieldRange

    auto end() const;
```

### 2.3.8.1 标准用法

```cpp
// 遍历类的所有 FProperty(包括继承的)
for (TFieldIterator<FProperty> It(MyClass); It; ++It)
{
    FProperty* Prop = *It;
    UE_LOG(LogTemp, Log, TEXT("%s : %s"), *Prop->GetName(), *Prop->GetCPPType());
}

// 遍历所有 UFunction
for (TFieldIterator<UFunction> It(MyClass); It; ++It)
{
    UFunction* Func = *It;
}

// 区间式(range-for)
for (FProperty* Prop : TFieldRange<FProperty>(MyClass))
{
    // ...
}
```

### 2.3.8.2 `EFieldIterationFlags` 控制行为

```cpp
enum EFieldIterationFlags : uint8
{
    None              = 0,
    IncludeSuper      = 1 << 0,    // 包含父类(默认开)
    IncludeDeprecated = 1 << 1,    // 包含已弃用字段
    IncludeInterfaces = 1 << 2,    // 包含接口字段
    Default = IncludeSuper | IncludeDeprecated | IncludeInterfaces
};
```

**纪律**:你只想遍历"本类字段不含父类"时,加 `EFieldIterationFlags::None`。

## 2.3.9 反射调用 `UFunction` —— Blueprint 调 C++

### 2.3.9.1 `UObject::ProcessEvent` —— 反射调用入口

```cpp
// UObject 的成员函数
void ProcessEvent(UFunction* Function, void* Parms);
```

调用形式:

```cpp
// 假设 BP 函数签名 void Heal(int32 Amount)
struct HealParms
{
    int32 Amount;
};

UFunction* HealFunc = MyComp->FindFunction(TEXT("Heal"));
HealParms Params;
Params.Amount = 50;
MyComp->ProcessEvent(HealFunc, &Params);
```

**这就是 Blueprint VM、Python binding、网络 RPC 调 C++ 的统一入口**。

### 2.3.9.2 `ProcessEvent` 内部做什么

简化(实际代码在 `UObject::ProcessEvent` / `UObject::CallFunction`):

```cpp
void UObject::ProcessEvent(UFunction* Function, void* Parms)
{
    // 1. 检查函数有 FUNC_Native 标志(C++ 实现)
    if (Function->FunctionFlags & FUNC_Native)
    {
        // 2. 直接调函数指针(execHeal 这种 trampoline)
        FFrame Stack(this, Function, Parms);
        Function->Func(this, Stack, /* return value */ nullptr);
    }
    else
    {
        // BP 函数(纯 BP):跑字节码
        ExecuteUbergraphFunction(...);
    }
}
```

`Function->Func` 就是 §2.1.3.3 看到的 `execHeal`(UHT 生成的 trampoline)。它的内部:

```cpp
DEFINE_FUNCTION(UMyHelloComponent::execHeal)
{
    P_GET_PROPERTY(FIntProperty, Z_Param_Amount);    // 从 Parms 解参数
    P_FINISH;
    P_NATIVE_BEGIN;
    P_THIS->Heal(Z_Param_Amount);                    // 真正调 native 函数
    P_NATIVE_END;
}
```

### 2.3.9.3 性能开销

- **直接调用** `MyComp->Heal(50)`:0 ns(纯 C++,可能 inline)
- **`ProcessEvent`**:**~500 ns - 1μs**(`FindFunction` 名字查找 + 参数打包 + trampoline 解包 + 实际调用)

**慢一千倍**!这就是为什么"Blueprint 调 C++"比"C++ 调 C++"慢得离谱。

### 2.3.9.4 缓存优化

```cpp
// 慢:每帧 FindFunction
UFunction* F = MyComp->FindFunction(TEXT("Heal"));   // ★ FName 查表
MyComp->ProcessEvent(F, &Parms);

// 快:缓存 UFunction*
static UFunction* CachedF = nullptr;
if (!CachedF) CachedF = UMyComp::StaticClass()->FindFunctionByName(TEXT("Heal"));
MyComp->ProcessEvent(CachedF, &Parms);
```

`FindFunctionByName` 比 `FindPropertyByName` 略快(`UClass` 内部有 `FuncMap` 哈希,§2.2.4.3),但反射调用本身的开销才是大头。

### 2.3.9.5 Mass 视角:**绝不**用反射调用进 hot path

数十万 entity 每帧每次调 `ProcessEvent` 是 **500ns × 10万 = 50ms**,完全不能接受。

**正确姿势**:
- Mass Processor 之间通信 → 直接 C++ 函数调用 / 共享 Subsystem 接口
- 玩家操作触发逻辑 → 玩家命令是低频(< 10次/秒/玩家),反射调用 OK
- BP 暴露的"配置调整"(SpeedMultiplier 等)→ 用 cvar / DataAsset,不要 BP 函数

## 2.3.10 Property 的实际值访问

拿到 `FProperty*` 后,怎么读写实例的字段值?

### 2.3.10.1 通用接口:`ContainerPtrToValuePtr`

```cpp
UMyComponent* Comp = ...;
FIntProperty* HealthProp = ...;

// 拿到 Comp 实例里 Health 字段的指针
int32* HealthPtr = HealthProp->ContainerPtrToValuePtr<int32>(Comp);

int32 Value = *HealthPtr;
*HealthPtr = 200;
```

实现极简:

```cpp
template<typename ValueType>
ValueType* FProperty::ContainerPtrToValuePtr(void* Container) const
{
    return (ValueType*)((uint8*)Container + Offset_Internal);
}
```

**就是 `Container + Offset` 加法**。`Offset_Internal` 是 §2.1 / §2.2 看到的 `STRUCT_OFFSET(...)` 在反射注册时存进 FProperty 的字节偏移。

**性能**:1 条加法指令,~1 ns。**这就是为什么"拿到 FProperty 指针后访问字段"很快**。

### 2.3.10.2 类型化接口

每种 FProperty 子类有自己的 typed setter/getter:

```cpp
FIntProperty::SetPropertyValue(void* Addr, int32 Value);
FIntProperty::GetPropertyValue(const void* Addr);

FStrProperty::SetPropertyValue(void* Addr, const FString& Value);

FObjectProperty::SetObjectPropertyValue(void* Addr, UObject* Value);
```

这些方法封装了"这个字段的实际类型怎么读写"的细节。

### 2.3.10.3 序列化:`FProperty::ImportText` / `ExportText`

```cpp
FString TextValue;
HealthProp->ExportText_Direct(TextValue, &Health, &Health, nullptr, PPF_None);
// TextValue == "100"

HealthProp->ImportText_Direct(*TextValue, &Health, nullptr, PPF_None);
// Health 被 parse 自字符串
```

Editor 输入框、配置 INI、JSON 序列化都靠这一组 API。

### 2.3.10.4 `Property->Serialize(Ar, Container)`

二进制序列化:

```cpp
FArchive Ar = ...;
HealthProp->SerializeBinProperty(Ar, &Health);
```

资产保存读取走这条路。这是 §3.5 序列化骨架的入口。

## 2.3.11 接口的反射

### 2.3.11.1 `UInterface` / `IInterface` 双类设计

```cpp
// MyInterface.h
UINTERFACE(BlueprintType)
class UMyInterface : public UInterface
{
    GENERATED_BODY()
};

class IMyInterface
{
    GENERATED_BODY()
public:
    virtual void DoSomething() = 0;
};
```

UE 接口由两个类组成:
- `UMyInterface`(以 U 开头) — 仅作为反射元数据载体,**没有**实际虚函数
- `IMyInterface`(以 I 开头) — 真正的 C++ 接口,含虚函数

实现:
```cpp
class UMyImpl : public UObject, public IMyInterface
{
    GENERATED_BODY()
public:
    virtual void DoSomething() override { ... }
};
```

### 2.3.11.2 接口 cast

```cpp
UObject* Obj = ...;
IMyInterface* Iface = Cast<IMyInterface>(Obj);   // 通过反射查接口表
if (Iface) Iface->DoSomething();
```

`Cast<IInterface>` 内部走 `UObject::GetInterfaceAddress(UClass*)`,在 UClass 注册的接口表里查这个对象有没有实现该接口。比普通 cast 略慢。

**Mass 视角**:接口反射在 Mass 里几乎不用 — Fragment 不参与多态接口。Subsystem 才偶尔用。

## 2.3.12 反射的元数据(Metadata)查询

UPROPERTY / UFUNCTION / UCLASS 上的 specifier(`EditAnywhere`、`Tooltip` 等)在反射注册时被记到 `FFieldMetaData` / `UClass::ClassMetaData`。运行时:

```cpp
// 查 metadata
FString Tooltip = HealthProp->GetMetaData(TEXT("ToolTip"));
FString DisplayName = MyClass->GetMetaData(TEXT("DisplayName"));

// 检查是否有某 metadata key
bool bHasMeta = HealthProp->HasMetaData(TEXT("BlueprintReadOnly"));
```

### 2.3.12.1 性能

`GetMetaData` 内部走一个 `TMap<FName, FString>` 查找。`O(log N)` 或 `O(1)`(看实现)。一次几十纳秒,Editor 用没事,运行时 hot path 别用。

**Shipping 构建**:大部分 metadata 默认会被剥离(否则字符串占空间)。不要依赖运行时 metadata 查询做核心逻辑,只用于 Editor 工具 / 调试。

## 2.3.13 一个完整示例:序列化任意 UObject

把这一节学到的东西串起来。下面这段代码"把任意 UObject 的所有反射字段 dump 成字符串":

```cpp
FString DumpObjectFields(UObject* Obj)
{
    if (!Obj) return TEXT("(null)");
    
    UClass* Class = Obj->GetClass();
    FString Result = FString::Printf(TEXT("=== %s ===\n"), *Class->GetName());
    
    for (TFieldIterator<FProperty> It(Class); It; ++It)
    {
        FProperty* Prop = *It;
        FString PropName = Prop->GetName();
        FString PropType = Prop->GetCPPType();
        
        // 拿字段值的字符串表达
        FString PropValue;
        Prop->ExportText_InContainer(0, PropValue, Obj, Obj, nullptr, PPF_None);
        
        Result += FString::Printf(TEXT("  %s : %s = %s\n"), *PropName, *PropType, *PropValue);
    }
    
    return Result;
}
```

这段代码用了:
- `Obj->GetClass()` —— 拿 UClass*
- `TFieldIterator<FProperty>` —— 遍历所有字段
- `Prop->GetName()` / `GetCPPType()` —— 反射元数据
- `Prop->ExportText_InContainer` —— 字段值字符串化

**Editor 的"Property panel"本质就是这种代码 + UI 渲染**。

## 2.3.14 性能数据感知

把这一节涉及的查询/调用操作的耗时整理出来,贴到桌面边:

| 操作 | 耗时 | 备注 |
|---|---|---|
| `T::StaticClass()` | 1-2 ns | 缓存命中 |
| `Obj->GetClass()` | 1 ns | 直接读字段 |
| `Cast<EngineBuiltin>(Obj)` | 3-5 ns | CastFlag 快路径 |
| `Cast<YourCustom>(Obj)` | 20-100 ns | IsA 链 |
| `Obj->IsA<T>()` | 10-30 ns | 同 IsChildOf |
| `Class->FindPropertyByName(N)` | 30-300 ns | O(字段数) |
| `Class->FindFunctionByName(N)` | 10-30 ns | UClass 有 FuncMap 哈希 |
| `Prop->ContainerPtrToValuePtr` | 1 ns | 一次加法 |
| `Prop->GetMetaData("Key")` | 30-100 ns | TMap 查找 |
| `Obj->ProcessEvent(F, P)` | 500-1000 ns | 反射调用,**贵** |
| `FindObject<T>(Outer, Name)` | 微秒级 | GUObjectArray 遍历 |
| `LoadObject<T>(Path)` | 毫秒级 | 资产加载,IO |

## 2.3.15 Mass / RTS 视角下的纪律

### (1)Hot path 绝不用反射调用

```
❌ 在 Processor::Execute 里:
    Obj->ProcessEvent(...)
    Obj->FindFunction(...) 然后 ProcessEvent
    GetClass()->FindPropertyByName(...)

✅ 直接 C++:
    Obj->Heal(50);                  // 直接调
    Fragment.Velocity += ...;       // 直接访问
```

### (2)反射查询结果必须缓存

```cpp
// Processor 启动 ConfigureQueries 时一次查
class UMyMassProcessor
{
    FProperty* CachedHealthProp = nullptr;
    
    virtual void ConfigureQueries() override
    {
        CachedHealthProp = FMyFragment::StaticStruct()->FindPropertyByName(TEXT("Health"));
    }
    
    virtual void Execute(...) override
    {
        for (auto& Frag : Context)
        {
            int32* HP = CachedHealthProp->ContainerPtrToValuePtr<int32>(&Frag);
            // ...
        }
    }
};
```

### (3)`Cast<>` 自定义类时知道开销

`Cast<UMyClass>(...)` 是 IsA 链遍历。Mass 里 Fragment 不是 UObject 不需要 Cast,Subsystem 是 UObject 但通常**编译期已知类型**(`UMyMassSubsystem* Sub = World->GetSubsystem<UMyMassSubsystem>();`)。99% 你**不需要** Cast 就能拿到正确类型。

如果发现自己在 Processor 里大量 `Cast<>`,**说明你设计错了** — 用类型化的 Subsystem 接口或 Fragment 本身的字段表达类型,而不是运行时 cast。

### (4)不要把"配置数据"放反射 metadata

```cpp
UPROPERTY(EditAnywhere, meta=(ClampMin="0", ClampMax="100"))
int32 Health;
```

`ClampMin` / `ClampMax` 是 Editor 限制,**不**是运行时验证。运行时 `GetMetaData("ClampMin")` 慢且 Shipping 可能没有。

需要运行时验证用代码 / 单独的 DataAsset 配置:

```cpp
UCLASS()
class URTSUnitConfig : public UDataAsset
{
    UPROPERTY(EditAnywhere)
    FInt32Range HealthRange = { 0, 100 };
};
```

## 2.3.16 改 Engine:加自定义 ClassCastFlag(罕见但有用)

如果你的 RTS 有几个**极常被 Cast 的核心基类**(典型场景:你定义了 `URTSUnitFragment` 作为所有单位 Fragment 的基类,Processor 里大量 `Cast<URTSUnitFragment>`),你可以通过给该类加一个 ClassCastFlag 让 Cast 走快路径。

### 2.3.16.1 基本姿势

`Engine/Source/Runtime/CoreUObject/Public/UObject/ObjectMacros.h` 的 `EClassCastFlags` 枚举里,几个位还没用(64 位还没满)。**保留位**:
```cpp
// 一些保留位(具体 5.7 状态以源码为准)
CASTCLASS_ReservedFlag1 = 0x...
```

加你自己的:
```cpp
// 修改 ObjectMacros.h(改 Engine,要走 EnginePatches/)
enum EClassCastFlags : uint64
{
    // ...
    CASTCLASS_URTSUnitFragment = 0x0040000000000000,  // 选一个未用位
};
```

然后在你的 UCLASS 里:
```cpp
UCLASS()
class MYRTS_API URTSUnitFragment : public UObject
{
    GENERATED_BODY()
};
```

最后让 UHT 知道这个 Cast Flag(通过修改 .gen.cpp 生成模板,这部分较复杂),或在 `Z_Construct_UClass_URTSUnitFragment_Statics` 的 ClassParams 里**手动**加上 `CASTCLASS_URTSUnitFragment` 标志。

### 2.3.16.2 现实复杂度

实际上:
- 改 `EClassCastFlags` 是改 Engine,rebase 痛
- UHT 不会自动给你的类加 cast flag,要么改 UHT(更痛),要么手写 .gen.cpp(更更痛)
- 64 位中保留位有限

**实战建议**:**别改**。Cast 慢路径在你 hot path 里出现是设计问题,不是工具问题。重新设计你的类型表达方式(用 Fragment 类型、Tag 类型、SubsystemAPI)。

## 2.3.17 实操:验证反射查询性能

```cpp
static FAutoConsoleCommand CmdBenchReflection(TEXT("rts.BenchReflection"),
    TEXT("Benchmark reflection queries"),
    FConsoleCommandDelegate::CreateLambda([]()
    {
        AActor* Actor = GWorld->SpawnActor<AStaticMeshActor>();
        const int32 N = 1000000;

        // Cast 快路径(引擎内置类)

        UE_LOG(LogTemp, Display, TEXT("Cast<AActor>:       %.2fns"), 
            (FPlatformTime::Seconds() - Start) * 1e9 / N);
        
        // IsA
        Start = FPlatformTime::Seconds();
        for (int32 i = 0; i < N; ++i) (void)Obj->IsA<AStaticMeshActor>();
        UE_LOG(LogTemp, Display, TEXT("IsA<...>:           %.2fns"),

    }));
```

## 2.3.18 实操提示与下一节预告

### 实操提示

- **看你某个类的 ClassCastFlags**:控制台输出
  ```cpp
  UE_LOG(LogTemp, Display, TEXT("CastFlags: 0x%llx"), (uint64)YourClass->ClassCastFlags);
  ```
  非零 flag 对应 §2.3.4.2 的位,你能反推这个类被哪些常用 Cast 命中。
- **诊断"反射调用占太多帧"**:Insights 看 `ProcessEvent` / `CallFunction` 之类 scope 的累计耗时。如果 > 100us / 帧,说明 BP 调 C++ 太多,考虑把热点 BP 函数改写为 native。
- **BP nativization 的反思**:UE5 移除了 BP nativization。原因之一就是反射调用在大多数情况下足够快(BP nativize 的收益不及预期),且维护成本高。Mass 项目应该**避免 BP 进 hot path**,而不是依赖 nativize 救场。
