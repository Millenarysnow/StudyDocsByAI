# §2.2 静态类型注册体系 — 从 Z_Construct_UClass_* 到 GUObjectArray

> **本节地图**:模块一第 2 章第 2 节。§2.1 看完了 UHT **如何生成代码**。这一节看**生成的代码在运行时如何把自己挂入引擎**。
>
> 这是一条经典的"全局静态构造 + 延迟注册"链:
>
> 1. C++ 运行时启动 → 全局静态对象构造(`WinMain` 之前)
> 2. `FRegisterCompiledInInfo` 的构造函数把"如何造 UClass"的函数指针塞进**待办列表**
> 3. CoreUObject 模块加载完成 → 遍历待办列表,**真正构造** `UClass` 对象
> 4. `UClass` 挂入 `GUObjectArray`,反射数据可查询
>
> **预备知识**:§1.3 GMalloc lazy init(同样的"延迟创建"思路)、§2.1 UHT 输出。
>
> **读完之后你能做到**:
> - 看清楚 .gen.cpp 末尾那行 `Z_CompiledInDeferFile_*` 是怎么"凭空"起作用的
> - 画出从程序启动到 `StaticClass()` 可用的完整时序
> - 理解 5.0 起 `UProperty → FProperty` 的拆分动机与影响
> - 知道 `UField` 与 `FField` 各自的职责
> - 解决"启动期 UClass 找不到"或"模块加载顺序导致反射失败"类问题

## 2.2.1 浅入:`Z_CompiledInDeferFile_*` 这行代码究竟在做什么

回顾 §2.1.3.3 末尾,你 .gen.cpp 文件里有这么一行:

```cpp
static FRegisterCompiledInInfo Z_CompiledInDeferFile_FID_..._Statics(
    Z_Construct_UClass_UMyHelloComponent,
    UMyHelloComponent::StaticClass,
    ...
);
```

这是个**全局静态变量**。它的关键性质:

1. **全局** —— 在文件作用域,不属于任何函数
2. **静态** —— 进程启动时(`mainCRTStartup`)由 C runtime 调用其构造函数
3. **构造时机比 main 早** —— C++ 全局静态构造发生在 `WinMain` / `main` 进入之前

构造函数(`FRegisterCompiledInInfo` 的 ctor)做什么?把**接收到的参数**(包括"构造 UClass 的函数指针"、"取 UClass 的函数指针"、"类名"、"包名" 等)**追加到一个全局延迟列表**。

这就是 UE 反射注册的"种子"。**进程启动时,你的项目所有 UCLASS / USTRUCT / UENUM 自动报到全局列表** —— 没有一行你写的代码主动调,完全靠 C++ 标准的"全局静态构造保证"。

## 2.2.2 `FRegisterCompiledInInfo` 的真实定义

`Engine/Source/Runtime/CoreUObject/Public/UObject/UObjectBase.h:640`:

```cpp
// UObjectBase.h:640
#if !UE_WITH_CONSTINIT_UOBJECT
struct FRegisterCompiledInInfo
{
    template <typename... ArgTypes>
    FRegisterCompiledInInfo(ArgTypes&&... Args)
    {
        RegisterCompiledInInfo(Forward<ArgTypes>(Args)...);
    }
};
#endif
```

**这就是个"参数转发"包装**。它的唯一作用是:让全局静态变量的构造函数把参数透传给 `RegisterCompiledInInfo()` 函数。

`UE_WITH_CONSTINIT_UOBJECT` 是 5.x 的可选编译宏,用 C++20 `constinit` 让注册更早(零运行时构造开销)。**5.7 默认关**,所以 95% 你看到的是上面这种"运行时静态构造"路径。

### 2.2.2.1 `RegisterCompiledInInfo()` 函数族

`UObjectBase.cpp:668` 起有多个重载:

```cpp
// 给 UClass 用
void RegisterCompiledInInfo(
    class UClass* (*InOuterRegister)(),                  // ← Z_Construct_UClass_X
    class UClass* (*InInnerRegister)(),                  // ← X::StaticClass
    const TCHAR* InPackageName,
    const TCHAR* InName,
    FClassRegistrationInfo& InInfo,
    const FClassReloadVersionInfo& InVersionInfo);

// 给 UScriptStruct 用
void RegisterCompiledInInfo(
    class UScriptStruct* (*InOuterRegister)(),
    const TCHAR* InPackageName,
    const TCHAR* InName,
    FStructRegistrationInfo& InInfo,
    const FStructReloadVersionInfo& InVersionInfo);

// 给 UEnum 用
// 给 UPackage 用
// ...
```

每种反射类型(class / struct / enum / package)有自己的 register 函数,但**核心行为相同**:把参数封装成 `FPendingRegistrant` 结构,挂到全局链表头。

### 2.2.2.2 `GFirstPendingRegistrant` —— 待办链表的头

`UObjectBase.cpp:105`:

```cpp
// UObjectBase.cpp:105
static FPendingRegistrant* GFirstPendingRegistrant = NULL;
```

这是个**模块内静态指针**。每次 `RegisterCompiledInInfo` 被调用,`UObjectBase.cpp:481-482` 大致这样:

```cpp
PendingRegistration->NextAutoRegister = GFirstPendingRegistrant;   // 链到链表头部
check(!GFirstPendingRegistrant || ...);                              // 检查
GFirstPendingRegistrant = PendingRegistration;
```

**注意是头部插入**,所以注册顺序是"最后注册的在最前面"。这个细节后面会影响处理顺序。

## 2.2.3 完整的时序:从全局静态构造到 UClass 就绪

我们把这段时序详细展开。这是反射系统最复杂的一段,但也是最关键的。

### 2.2.3.1 阶段 0:Compile 时(已在 §2.1 讲完)

UHT 给每个反射类型生成 `Z_Construct_UClass_*` / `Z_Construct_UScriptStruct_*` 函数 + 一个 `Z_CompiledInDeferFile_*` 全局静态变量。

### 2.2.3.2 阶段 1:进程启动 — 全局静态构造期(main 之前)

C 运行时启动器(Windows 上是 `mainCRTStartup`)在调 `WinMain` **之前**,跑完所有全局静态对象的构造函数。每个 `Z_CompiledInDeferFile_*` 触发一次 `RegisterCompiledInInfo()`:

```
进程启动
  ↓
mainCRTStartup
  ↓
[全局静态对象构造期]
  ├─ Z_CompiledInDeferFile_<ClassA>_Statics 构造 → RegisterCompiledInInfo → 加入 GFirstPendingRegistrant
  ├─ Z_CompiledInDeferFile_<ClassB>_Statics 构造 → 同上
  ├─ Z_CompiledInDeferFile_<StructA>_Statics 构造 → 同上(类似流程,挂另一个待办列表)
  ├─ ...(几千次,引擎所有 UCLASS / USTRUCT)
  ├─ Z_CompiledInDeferFile_<YourGameClassA>_Statics 构造 → 同上
  ├─ ...
  ↓
[GFirstPendingRegistrant 已含所有静态链接进来的反射类型]
  ↓
WinMain → GuardedMain → FEngineLoop::PreInit
```

**重要观察**:此时 `Z_Construct_UClass_*` 函数**还没被真正调用**!只是函数指针被记下来。`UClass` 对象还不存在。

`StaticClass<UMyClass>()` 在此阶段调用会怎样?触发 `UMyClass::StaticClass()` 内部检查:`UClass` 还没构造 → 触发**首次构造**(等价于 `Z_Construct_UClass_UMyClass()`)。但通常没人在这阶段调它(全局静态构造里乱调反射等于自找麻烦)。

### 2.2.3.3 阶段 2:CoreUObject 模块加载 — 批量构造 UClass

`FEngineLoop::PreInit` 早期会加载 CoreUObject 模块。CoreUObject 加载完成后调用 `ProcessNewlyLoadedUObjects()`(`UObjectBase.cpp:1027`):

```cpp
// UObjectBase.cpp:1027(简化)
void ProcessNewlyLoadedUObjects(FName InModuleName, bool bCanProcessNewlyLoadedObjects)
{
    SCOPED_BOOT_TIMING("ProcessNewlyLoadedUObjects");
    
    // 1. 注册当前批次所有 UClass(扫 GFirstPendingRegistrant 链表)
    UClassRegisterAllCompiledInClasses();
    
    // 2. 注册 UScriptStruct / UEnum / UFunction / UPackage
    // ... 依次处理各 deferred registry ...
    
    // 3. 让 Editor 等 listener 知道"新模块加载了"
    // ...
}
```

`UClassRegisterAllCompiledInClasses()` 在 `UObjectBase.cpp:775`:

```cpp
// UObjectBase.cpp:775
void UClassRegisterAllCompiledInClasses()
{
    SCOPED_BOOT_TIMING("UClassRegisterAllCompiledInClasses");
    LLM_SCOPE(ELLMTag::UObject);
    
    FClassDeferredRegistry& Registry = FClassDeferredRegistry::Get();
    Registry.ProcessChangedObjects();
    
    for (const FClassDeferredRegistry::FRegistrant& Registrant : Registry.GetRegistrations())
    {
        UClass* RegisteredClass = FClassDeferredRegistry::InnerRegister(Registrant);
        // ...
    }
}
```

`InnerRegister(Registrant)` 内部调用 `Registrant.OuterRegister`,也就是 UHT 生成的 `Z_Construct_UClass_X()`。**至此 `UClass` 对象才真正被创建**:

```cpp
UClass* Z_Construct_UClass_UMyClass()
{
    if (!Z_Registration_Info_UClass_UMyClass.OuterSingleton)    // 双重检查
    {
        UECodeGen_Private::ConstructUClass(
            Z_Registration_Info_UClass_UMyClass.OuterSingleton, 
            Z_Construct_UClass_UMyClass_Statics::ClassParams);
    }
    return Z_Registration_Info_UClass_UMyClass.OuterSingleton;
}
```

`ConstructUClass`(`UObjectGlobals.h:4184`)做的事:
1. 用 `NewObject<UClass>` 分配 `UClass` 对象(走 §1 的 FMemory)
2. 设置类名、Super、ClassFlags
3. 把 `ClassParams.PropPointers[]` 里描述的字段一一构造为 `FProperty` 对象,挂到 `UClass::ChildProperties` 链
4. 把函数描述构造为 `UFunction` 对象,挂到 `UClass::Children`
5. 把 `UClass` 挂到 `GUObjectArray`(全局对象表)
6. 计算 GC Token Stream(Reachability 用,§4 详讲)
7. 触发 `OnClassPostInitialize` 等 hook

**完成后**:`UMyClass::StaticClass()` 返回有效指针;`FindClass(TEXT("MyClass"))` 能查到;Blueprint VM 能调它的反射函数;GC 能扫它的引用。

### 2.2.3.4 阶段 3:`UObjectBaseInit` — 全局对象表就绪

`UObjectBase.cpp:1271`:

```cpp
void UObjectBaseInit()
{
    // 真正初始化 GUObjectArray 内部数组、TLS、GC 子系统等
    // ...
    GUObjectArray.AllocateUObjectIndex(...);   // 准备好 UObject 指针存储
    // ...
}
```

之后:
- `UObjectAllocator` 就绪 → `NewObject<T>` 可用
- `GUObjectArray` 就绪 → 索引 / SerialNumber 系统启用
- GC 就绪 → 后续创建的 UObject 都被 GC 跟踪

### 2.2.3.5 阶段 4:游戏模块加载 → 第二轮 ProcessNewlyLoadedUObjects

PreInit 后期或 Init 期,游戏 Module 被加载。每个 Module 加载完时,触发自己那批 UCLASS 的注册(再次走 `ProcessNewlyLoadedUObjects`)。

整个过程被 `FModuleManager` 协调,`OnProcessLoadedObjectsCallback` 委托(`UObjectBase.cpp:1015`)被订阅,Module 加载结束自动触发反射注册。

### 2.2.3.6 完整时序图

```
Process Start
  │
  ├─ mainCRTStartup
  │     ↓
  │ [全局静态构造]
  │   每个 Z_CompiledInDeferFile_* 构造 → RegisterCompiledInInfo
  │   → 挂入 GFirstPendingRegistrant / FClassDeferredRegistry
  │   (此时 UClass 对象**不存在**,只是函数指针记录)
  │
  ├─ WinMain → GuardedMain
  │
  ├─ FEngineLoop::PreInit (Phase: PostConfigInit)
  │     ↓
  │   加载 CoreUObject 模块
  │     ↓
  │   ProcessNewlyLoadedUObjects()
  │     ├─ UClassRegisterAllCompiledInClasses
  │     │     遍历 deferred registry
  │     │     每个 → ConstructUClass(...) 真正创建 UClass
  │     │     → 挂入 GUObjectArray
  │     ├─ UScriptStructRegisterAllCompiledInScriptStructs
  │     ├─ UEnumRegisterAllCompiledInEnums
  │     └─ ...
  │
  ├─ UObjectBaseInit
  │     GUObjectArray 完整就绪
  │
  ├─ FEngineLoop::PreInit (Phase: PreDefault, Default, ...)
  │   游戏模块依次加载
  │     ├─ MyModuleA load → ProcessNewlyLoadedUObjects(再次)
  │     │     注册 MyModuleA 的所有 UCLASS / USTRUCT
  │     ├─ MyModuleB load → 同上
  │     ...
  │
  ├─ FEngineLoop::Init
  │     World 创建、GameMode、PlayerController...
  │
  └─ Tick loop
```

## 2.2.4 关键数据结构对象树:UClass / UStruct / UFunction / UEnum / UScriptStruct

这一节我们看运行时**反射的对象表达**长什么样。打开 `Engine/Source/Runtime/CoreUObject/Public/UObject/Class.h`,关键继承图:

```
UObjectBase
  └─ UObjectBaseUtility
       └─ UObject                                                  (一切的根)
            └─ UField : public UObject     (Class.h:180)            ← 类型描述对象的基类
                 ├─ UStruct                                         ← 含字段的复合类型
                 │   ├─ UClass             ← C++ 类(UObject 子类)
                 │   ├─ UScriptStruct      ← USTRUCT(纯数据)
                 │   └─ UFunction          ← 函数(为啥是 UStruct?函数也有"参数 = 字段")
                 └─ UEnum                  ← UENUM
```

### 2.2.4.1 `UField`(`Class.h:180`)

```cpp
class UField : public UObject
{
    DECLARE_CASTED_CLASS_INTRINSIC_NO_CTOR(UField, UObject, ...)
    
    /** Next Field in the linked list */
    UField* Next;       // 同一个 UStruct 内的字段链表
    
    // ... 其它接口 ...
};
```

UField 是"反射描述对象"的基类。`Next` 让一个类的所有字段(子 UField)用单链表挂起来 —— 这是 UE 反射对象树的基本骨架。

### 2.2.4.2 `UStruct`

UStruct 有一组核心成员(简化):

```cpp
class UStruct : public UField
{
public:
    UStruct* SuperStruct;             // 父类
    UField*  Children;                 // 子 UField 链(UFunction 等)
    FField*  ChildProperties;          // 子 FField 链(FProperty,5.0+ 拆出来的)
    int32    PropertiesSize;           // 实例占多少字节
    int32    MinAlignment;             // 内存对齐
    
    // ... 反射元数据 ...
};
```

注意 **`Children` 和 `ChildProperties` 是两条链**:
- `Children` (UField 单链表) 装 UFunction 等仍然是 UObject 的子类型
- `ChildProperties` (FField 单链表) 装 FProperty(5.0+ 拆出来,**不**是 UObject)

这就是"5.0 拆分 UProperty → FProperty" 的物理体现 —— 一条链拆成两条。下一节 §2.2.5 会详细讲这个拆分。

### 2.2.4.3 `UClass`

`UClass` 在 `UStruct` 上加上"运行时对象生产能力":

```cpp
class UClass : public UStruct
{
public:
    UObject* (*ClassConstructor)(const FObjectInitializer&);   // ★ NewObject<T> 内部用
    void     (*ClassVTableHelperCtorCaller)(...);               // VTable 初始化辅助
    
    EClassFlags ClassFlags;                                      // BlueprintType / Abstract / Const ...
    EClassCastFlags ClassCastFlags;
    
    FName ClassConfigName;                                       // 配置 INI 文件名
    
    UClass* ClassWithin;                                         // Outer 必须是这个类的实例
    UPackage* ClassGeneratedBy;                                  // Editor:Blueprint 类的源 BP 资产
    
    UObject* ClassDefaultObject;                                  // ★ CDO!§2.2.6 详讲
    
    // GC token stream(§4 详讲)
    FGCReferenceTokenStream ReferenceTokens;
    
    // 反射:类的所有 UFunction 名 → UFunction 映射
    TMap<FName, UFunction*> FuncMap;
    
    // ...
};
```

**核心三件**:
1. `ClassConstructor` 是函数指针,UHT 生成的 lambda,被 `NewObject<T>` 调来 placement new 一个对象
2. `ClassDefaultObject` 是 CDO(Class Default Object),所有"未显式初始化的字段"从 CDO 拷贝
3. `ReferenceTokens` 是 GC 用的引用偏移流,§4 大讲

### 2.2.4.4 `UFunction`

```cpp
class UFunction : public UStruct
{
    EFunctionFlags FunctionFlags;          // BlueprintCallable / NetReliable / Net ...
    uint16         RepOffset;
    uint8          NumParms;
    uint16         ParmsSize;
    uint16         ReturnValueOffset;
    
    Native Func;                           // ★ 函数指针:exec<FuncName> 的地址
    
    // 参数 / 返回值 的 FProperty 链通过 UStruct::ChildProperties
};
```

`Func` 是个函数指针,指向 UHT 生成的 `execHeal` 之类的 trampoline。Blueprint VM / 网络 RPC / Python binding 都通过 `UFunction::Func` 调用 native 函数。

### 2.2.4.5 `UScriptStruct`(USTRUCT 的运行时)

```cpp
class UScriptStruct : public UStruct
{
    int32        StructFlags;          // STRUCT_Atomic / STRUCT_Immutable / STRUCT_NoExport ...
    ICppStructOps* CppStructOps;        // 自定义序列化/比较/复制接口
    
    // ...
};
```

注意 `CppStructOps` —— 它允许 USTRUCT 提供自定义序列化、`==` 比较、复制等行为。Mass Fragment 的某些类型(如 `FInstancedStruct`)就是靠这个实现"动态结构"的。

## 2.2.5 5.0 起的关键变化:`UProperty → FProperty` / `FField` vs `UField`

这是 UE 5.0 带来的一次**底层重构**,你看老代码 vs 新代码会发现差异。

### 2.2.5.1 历史:为什么需要拆?

UE 4.x 时代,`UProperty` 是 `UField` 的子类,即:
- `UProperty` 是 UObject
- 一个类有多少 UPROPERTY,GUObjectArray 里就多少 UProperty 对象

问题:
- 引擎一启动,几万个 UProperty 占用 GUObjectArray 的索引位
- GC 每次扫描都要遍历这些"不会变化"的反射对象
- 反射对象本身被当作可 GC 的 UObject,引入不必要的开销

### 2.2.5.2 5.0 的拆分

把 UProperty 从 UObject 体系拆出来,变成**独立的轻量对象** `FProperty`:

```
旧:UObject ← UField ← UProperty ← UIntProperty / UStrProperty / ...
新:UObject ← UField                                    (UFunction / UStruct 仍在)
   FField ← FProperty ← FIntProperty / FStrProperty / ...   (独立体系)
```

**拆分细节**:
- `FField`(`Engine/Source/Runtime/CoreUObject/Public/UObject/Field.h:342`)是新的"反射字段对象"基类。它**不**是 UObject。
- `FProperty` 继承 `FField`。
- `FIntProperty` / `FBoolProperty` / `FObjectProperty` / `FArrayProperty` 等都是 `FProperty` 子类,仍然多态。
- `FFieldClass`(`Field.h:65`)是 FField 体系的"元类",对应于 UClass 在 UObject 体系的地位。

### 2.2.5.3 `FFieldClass` —— FField 的元类

`Field.h:65`:

```cpp
class FFieldClass
{
    using FConstructFunction = FField*(const FFieldVariant&, const FName&, EObjectFlags);

private:
    FName Name;
    EClassFlags ClassFlags;
    uint64 Id;
    EClassCastFlags CastFlags;
    FFieldClass* SuperClass;
    FField* DefaultObject;
    FConstructFunction* ConstructFn;
    // ...
};
```

`FFieldClass` 本身**不**是 UObject。它是一个全局静态对象,描述每个 FField 子类型(`FIntProperty`、`FStrProperty` 等)的元数据。每种 FProperty 子类都对应一个 `FFieldClass` 单例。

### 2.2.5.4 拆分后的好处

| 维度 | 旧(4.x) | 新(5.0+) |
|---|---|---|
| FProperty 是 UObject | ✓ | ✗ |
| FProperty 占用 GUObjectArray 索引 | 占 | 不占 |
| FProperty 被 GC 扫描 | 是 | 否 |
| FProperty 的 Outer 是 UObject? | 是 | 否(用 `FFieldVariant`) |
| 创建 / 销毁 FProperty 成本 | 中(走 NewObject) | 低(纯堆 new) |
| 启动期 UObject 数量 | 大(几万 UProperty) | 减少 50%+ |
| 反射 query 速度 | 中 | 略快 |

### 2.2.5.5 对你代码的影响

**4.x → 5.0+ 迁移要点**:

```cpp
// ❌ 4.x 写法:UProperty 是 UObject 子类
UProperty* Prop = MyClass->FindProperty(TEXT("Health"));
if (Prop->IsA(UIntProperty::StaticClass())) { ... }     // UClass 系反射

// ✅ 5.0+ 写法:FProperty 用 FFieldClass
FProperty* Prop = MyClass->FindPropertyByName(TEXT("Health"));
if (Prop->IsA<FIntProperty>()) { ... }                  // FFieldClass 系反射
// 或
if (CastField<FIntProperty>(Prop)) { ... }
```

老代码里 `UIntProperty` / `UStrProperty` 已被改名为 `FIntProperty` / `FStrProperty`。Build 时如果你看到 `UIntProperty` 之类的引用编译失败,直接 search-replace 把 `UProperty` 前缀换成 `FProperty`,把 `U` 换成 `F`。

### 2.2.5.6 哪些**还是** UField

不是所有反射对象都拆了:
- **UFunction**:仍然是 `UField` 子类。原因是 UFunction 太复杂(有自己的字节码、调用约定、网络 RPC),拆代价大。
- **UEnum / UStruct / UClass / UScriptStruct / UPackage**:仍然是 `UField` 子类。
- **UProperty 系列**:全部拆为 FField / FProperty 体系。

所以 5.0+ 的反射树是**两套并存**:UField 树管"复合类型 / 函数",FField 树管"字段属性"。

## 2.2.6 CDO(Class Default Object)简介

`UClass::ClassDefaultObject` 是**反射注册时被一并创建的"模板对象"**。

举例:`UMyHelloComponent` 注册完成时,UE 会:
```cpp
ClassDefaultObject = NewObject<UMyHelloComponent>(...);
// CDO 是一个 UMyHelloComponent 实例,所有字段是默认初始值
//   Health = 100(UPROPERTY 默认值)
//   Name = ""
```

CDO 的用途:
- **新对象初始化**:`NewObject<UMyHelloComponent>()` 默认从 CDO 拷贝字段(然后再走构造函数)
- **Editor Property 编辑**:你修改 BP 类默认值,实际改的是 CDO
- **网络复制 baseline**:第一次复制对象时只发"与 CDO 不同的字段"
- **序列化 delta**:存盘时只存"与 CDO 不同的字段"

§3.4 会大讲 CDO,这里只先建立"反射注册时一并创建 CDO" 的认知。

## 2.2.7 `IMPLEMENT_CLASS` 等关键宏的展开

### 2.2.7.1 `DECLARE_CLASS`(放在 .h 的 GENERATED_BODY 里)

```cpp
// ObjectMacros.h(简化)
#define DECLARE_CLASS(TClass, TSuperClass, TStaticFlags, TCastFlags, TPackageName, TRequiredAPIMacro) \
private: \
    TClass& operator=(TClass&&); \
    TClass& operator=(const TClass&); \
public: \
    typedef TClass ThisClass; \
    typedef TSuperClass Super; \
    static UClass* StaticClass() \
    { \
        return GetPrivateStaticClass<TClass>(); \
    } \
    static UPackage* StaticPackage() { return FindOrConstructDynamicPackage(TPackageName); } \
    static FORCEINLINE EClassCastFlags StaticClassCastFlags() { return TCastFlags; } \
    /* ... 等等 ... */
```

**关键展开**:`StaticClass()` 静态成员函数,返回该类的 UClass*。

`GetPrivateStaticClass<TClass>` 内部第一次调用时触发 `Z_Construct_UClass_<TClass>()`,得到 UClass*,缓存。后续调用直接返回缓存。

### 2.2.7.2 `IMPLEMENT_CLASS`(放在 .gen.cpp)

```cpp
// ObjectMacros.h:2201
#define IMPLEMENT_CLASS(TClass, TClassCrc) \
    static FRegisterCompiledInInfo AutoInitialize_##TClass( \
        &Z_Construct_UClass_##TClass, \
        TClass::StaticClass, \
        TClass::StaticPackage(), \
        TEXT(#TClass), \
        Z_Registration_Info_UClass_##TClass, \
        CONSTRUCT_RELOAD_VERSION_INFO(FClassReloadVersionInfo, sizeof(TClass), TClassCrc));
```

这个就是把"如何注册"塞进延迟列表的全局变量。每个 UCLASS 都有一行这种宏被 UHT 生成进 .gen.cpp。

`TClassCrc` 是类成员的 hash —— 用来检测 hot reload 时类是否真的改了(CRC 没变就跳过)。

## 2.2.8 一个常见陷阱:跨模块循环依赖

### 2.2.8.1 问题描述

ModuleA 定义 `UClassA`,字段含 `TObjectPtr<UClassB> Ref;`,ClassB 在 ModuleB。
ModuleB 也定义某个类含 `TObjectPtr<UClassA>`。

**如果两个 Module 互相依赖**,UHT 注册时会:
- ClassA 的反射构造里需要 ClassB 的 UClass*
- ClassB 的反射构造里需要 ClassA 的 UClass*

死循环?

### 2.2.8.2 UE 的解法:`Z_Construct_UClass_*_NoRegister`

UHT 给每个反射类型生成两个入口:
- `Z_Construct_UClass_X()`(Registered)— 完整注册
- `Z_Construct_UClass_X_NoRegister()`(Unregistered)— **只**返回 UClass* 占位,不递归注册依赖

```cpp
UClass* Z_Construct_UClass_UMyClass_NoRegister()
{
    return UMyClass::StaticClass();
}
```

它直接调用 `StaticClass()`,内部会在第一次调时触发完整构造,但**当下不递归**。这样在反射依赖图里,**A 引用 B 时引用 B_NoRegister**,避免提前展开 B 的完整反射。

这就是为什么 .gen.cpp 里 `DependentSingletons` 字段里看到的常常是 `_NoRegister` 版本。

### 2.2.8.3 实战:解 cycle 的标准做法

如果你 RTS 项目里有两个 Module 互相引用反射类型,**通常 UHT 自动处理**。但如果你看到`fatal error: cyclic dependency`,试这两条:

1. **检查 Module 之间的 Build.cs 依赖**:不能形成 `A 依赖 B 且 B 依赖 A` 的硬链(A 和 B 都用 PublicDependencyModuleNames 互引)。**改用 PublicIncludePathModuleNames**(§0.1.2.3)拉对方头但不链接,反射注册期间会 lazy 解析。

2. **检查反射字段类型**:能用前向声明 + `TObjectPtr<>` 的就不要用 `UClass*` 直接 include 对方头。

## 2.2.9 `LiveCoding` / `HotReload` 重新注册

UE 5.x 推 Live Coding 替代 HotReload。两者都涉及反射重注册。

### 2.2.9.1 简要工作原理

Live Coding 编译完后:
1. 卸载旧 .obj 中的反射对象(标记 `bHasChanged`)
2. 加载新 .obj
3. 触发 `ProcessNewlyLoadedUObjects` 重新走一遍注册
4. 对**字段未变**的类,旧 UClass 保留;对**字段变了**的类,触发 reinstancing(把旧实例的字段值迁移到新实例)

### 2.2.9.2 限制(再次重申 §0.2.7.2 的纪律)

Live Coding **不能**:
- 加新 UCLASS / USTRUCT(反射注册队列已固定)
- 改 UPROPERTY 字段(对象大小变化)
- 改虚函数表

**能**:
- 改函数体(只要签名不变)

## 2.2.10 `StaticClass<T>()` 与模板特化

`StaticClass<T>()` 是模板,主特化:

```cpp
// 通用版(在 Class.h 之类的某处)
template<typename T>
UClass* StaticClass() { return T::StaticClass(); }
```

每个 UCLASS 类型对此模板有显式特化(UHT 在 .gen.cpp 里生成):

```cpp
// .gen.cpp 里
template<> MYMOD_API UClass* StaticClass<UMyHelloComponent>() 
{ 
    return UMyHelloComponent::StaticClass(); 
}
```

这让 `StaticClass<UMyHelloComponent>()` 能从外部模块调用(因为 `MYMOD_API` 导出),即使你没有 `UMyHelloComponent` 完整类型(只有前向声明)。

**实战意义**:你能在某个 .h 里写 `class UMyHelloComponent;` 前向声明 + `extern template UClass* StaticClass<UMyHelloComponent>();`,然后在 .cpp 里用 `StaticClass<UMyHelloComponent>()`,**不**需要 include UMyHelloComponent.h。这能减少头依赖链。

static FAutoConsoleCommand CmdInspectClass(TEXT("rts.InspectClass"),

    {

        UE_LOG(LogTemp, Display, TEXT("PropertiesSize: %d"), Class->GetPropertiesSize());
        UE_LOG(LogTemp, Display, TEXT("MinAlignment: %d"), Class->GetMinAlignment());

## 2.2.12 与 Mass 重构的对照思考

### (1)Mass Fragment 走 `UScriptStructRegisterAllCompiledInScriptStructs`

Fragment 是 USTRUCT,注册路径与 UCLASS 不同但等价 —— 引擎启动时 `ProcessNewlyLoadedUObjects` 会调 `UScriptStructRegisterAllCompiledInScriptStructs`(注册 UScriptStruct 的同等函数),把所有 Fragment 的 `UScriptStruct*` 挂到 GUObjectArray。

Mass 之后启动时遍历所有"`IsChildOf<FMassFragment>` 的 UScriptStruct",每个分配一个 BitSet 索引。这个步骤**晚于反射注册**,所以 Fragment 的反射数据已经就绪,Mass 可以查每个 Fragment 的 PropertiesSize / MinAlignment / 字段偏移。

### (2)`PropertiesSize` 决定 Mass Chunk 容量

Mass `FMassArchetypeChunk`(默认 128KB)分配后,要算"一个 chunk 能装多少 entity"。公式:
```
EntityCountPerChunk = ChunkSize / SumOfFragmentSize
```

`SumOfFragmentSize` 来自每个 Fragment 的 `UScriptStruct::PropertiesSize`。这就是反射数据**直接被 Mass 用作运行时计算输入**。

### (3)反射对 Mass 的"代价"

反射注册期把 Fragment 的 UScriptStruct 挂入 GUObjectArray。**每个 Fragment 类型** = 1 个 UScriptStruct 对象 +N 个 FProperty 对象(N = 字段数)。如果你的 Fragment 字段平均 4-5 个,加 1 个 UScriptStruct,大概 6 个反射对象 / Fragment。

50 种 Fragment ≈ 300 个反射对象。**这是固定开销,不论运行多少 entity 都是这点**。50 种 × 6 ≈ 几 KB 元数据,完全可以接受。

但如果你**滥用**反射(比如把每个单位类型注册成独立 Fragment 的模板特化)→ 反射对象数量爆炸。**纪律**:Fragment 类型数量保持 < 100,功能差异通过数据(SharedFragment / Tag)而不是类型差异表达。

## 2.2.13 改 Engine:加 / 改反射注册流程(罕见)

如果你 RTS 项目想做"动态生成 USTRUCT"(运行时根据数据生成 Fragment 类型),你需要绕过 UHT 静态注册:

```cpp
// 运行时构造一个新的 UScriptStruct
UScriptStruct* NewStruct = NewObject<UScriptStruct>(GetTransientPackage(), 
    *FString::Printf(TEXT("Dynamic_%d"), Counter++));
NewStruct->SetSuperStruct(FBaseFragment::StaticStruct());
// 添加字段(FProperty)
FIntProperty* IntProp = new FIntProperty(NewStruct, TEXT("MyField"), RF_Public);
IntProp->ArrayDim = 1;
IntProp->ElementSize = sizeof(int32);
NewStruct->AddCppProperty(IntProp);
NewStruct->StaticLink(true);     // 计算字段偏移,生成 GC token stream
NewStruct->Bind();
```

这种"动态反射"是 Mass 的 `FInstancedStruct` 内部用的技术。极少数情况你会自己写。

**99% 的项目**:UHT 静态注册够用,不要走动态路径。
