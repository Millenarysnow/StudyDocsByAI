## 序言：阅读路径与心智模型

- S.1 本指南的"破"与"立"：为什么必须先把传统 OOP 框架吃透才有资格魔改
- S.2 五大模块的依赖图：Core → Gameplay → Network/GAS → Mass → 实战重写
- S.3 推荐源码阅读工具链
  - Visual Studio 2022 + Visual Assist / Resharper C++（符号跳转）
  - Unreal Insights / Trace Channels（运行时管线观测）
  - RenderDoc（GPU 帧抓取，验证 ISM/VAT 路径）
  - PIX on Windows（D3D12 GPU profiling）
  - ReSharper "Find Inheritor" / 反射符号跳转技巧
- S.4 一开始就内化的 RTS 性能预算
  - 单位规模目标：服务器 50,000 / 客户端可见 10,000
  - 帧预算：16.6ms（60Hz）→ Mass Tick 上限 ~4ms / Render ~6ms / Network ~2ms / 其他 ~4ms
  - 网络预算：<128 KB/s/玩家 上行 / <512 KB/s 下行
  - 内存预算：单 Entity 平均 < 256 字节（决定 Fragment 设计纪律）

## 模块一：UE5 基石 — Core & UObject 系统源码剖析

> **目标**：理解为什么 UObject 不能扛住数万单位，但 Mass 仍依赖 UObject 子系统作为骨架。

### 第 1 章 平台抽象层与内存分配器

- 1.1 平台抽象三件套
  - `FPlatformMisc` / `FPlatformAtomics` / `FPlatformProcess` 的分层与跨平台 typedef 链
  - `Windows/WindowsPlatform.h` → `GenericPlatform/GenericPlatform.h` 的 fallthrough
- 1.2 `FMemory` 统一入口
  - `Malloc/Realloc/Free` → `GMalloc->Malloc(...)` 的转发
  - `FMemory::Memzero` / `Memcpy` 的 SIMD 内联路径
- 1.3 `GMalloc` 初始化时机
  - 从 `LaunchEngineLoop.cpp` 的 `FEngineLoop::PreInit` 反推 `FMemory::GCreateMalloc()`
  - `MALLOC_LEAKDETECTION` / `USE_MALLOC_PROFILER` 的层叠
- 1.4 主流分配器源码对比
  - `MallocBinned2`：BinSize 表 / SmallPool 链表回收 / OS Page 申请
  - `MallocBinned3`：64 位地址空间预留 + Virtual Memory Address 直接映射
  - `MallocTBB` / `MallocMimalloc` / `MallocAnsi`
  - `MallocStomp` / `MallocPoisonProxy` 的调试代理
- 1.5 TLS 缓存与多线程分配竞争（决定数十万 entity 频繁分配的吞吐）
- 1.6 容器内存模型
  - `TArray` 的 Allocator policy：`FDefaultAllocator` / `FMemStackAllocator` / `TInlineAllocator<N>` / `TFixedAllocator<N>`
  - `TMap` 的 SparseArray + HashTable 双层结构
  - `FString` 小字符串优化策略与 inline 阈值

### 第 2 章 反射系统 — UHT 的源码生成与 UClass 的运行时表达

- 2.4 与 Mass 的对照
  - 为什么 Mass 自定义 `FStructTypeBitSet` 而不直接用 `UScriptStruct*` 的指针集合？

### 第 4 章 垃圾回收（GC）算法源码深度剖析
