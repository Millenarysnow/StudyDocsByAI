## 6.2.1 PreInit 的"工作清单"

`FEngineLoop::PreInit` 的核心职责:**把"内存 / 反射 / 配置 / Stats / Trace / 模块系统"等基础设施全部摆到位**,让后续 `Init` 能创建 GEngine、加载关卡。

整理成有顺序的 12 步:

```
PreInitPreStartupScreen:
  1. 命令行解析(FCommandLine::Set)
  2. Trace 初始化(Insights / 网络 trace)
  3. LLM 初始化(Low Level Memory Tracker)
  4. Tagged Storage / Process 优先级 / Sleep 等平台特性
  5. Stat 系统启动
  6. ConfigCache 加载 INI
  7. CoreUObject 加载 → ProcessNewlyLoadedUObjects(注册 UClass)
  8. LoadingPhase=PostConfigInit 模块加载
  9. PreEarlyLoadingScreen → 启动 Splash

[Splash 显示中]

PreInitPostStartupScreen:
  10. ShaderCompiler 启动 / InitializeShaderTypes
  11. LoadingPhase=PreLoadingScreen / PreDefault / Default / PostDefault 各阶段模块
  12. AssembleReferenceTokenStreams(GC schema 编译)
```

下面逐项展开。

## 6.2.2 命令行解析:`FCommandLine`

`LaunchEngineLoop.cpp:1765`:

```cpp
if (!FCommandLine::Set(CmdLine))
{
    return -1;
}
```

`FCommandLine` 是个全局单例,持有完整命令行字符串。

### 6.2.2.1 用法

```cpp
const TCHAR* CL = FCommandLine::Get();      // 取字符串

// 检查 flag
if (FParse::Param(CL, TEXT("server")))
{
    // 启动加 -server
}

// 解析 -key=value
FString Value;
if (FParse::Value(CL, TEXT("MyParam="), Value))
{
    // 启动加 -MyParam=foo
}

// int 解析
int32 NumPlayers;
FParse::Value(CL, TEXT("NumPlayers="), NumPlayers);
```

### 6.2.2.2 命令行的作用范围

UE 命令行**全局可见**:
- C++ 代码 `FParse::Param(...)`
- BP `Get Command Line` 节点
- INI 文件用 `${CmdLineParam}` 引用

但**只读**(除了少数用 `FCommandLine::Append` 追加,很少)。

### 6.2.2.3 RTS 项目的常用 cmdline

```
MyRTS.exe -server -port=7777                    # 服务器
MyRTS.exe -log -nullrhi                         # 无图形启动(测试)
MyRTS.exe -trace=cpu,frame,mass                 # 启用 trace
MyRTS.exe MyMap?Spectator                       # 加载特定关卡 + 选项
MyRTS.exe -RTS.MaxParallelProcessors=4          # 自定义 cvar
```

### 6.2.2.4 5.x 命令行处理变化

5.x 引入 `FCommandLine::AppendArg`(更安全的拼接,不需要担心引号转义)。新代码用它。

## 6.2.4 LLM 初始化

`LaunchEngineLoop.cpp:1809`:

```cpp
LLM(FLowLevelMemTracker::Get().ProcessCommandLine(CmdLine));
```

LLM(Low Level Memory Tracker)在 §0.3.9.1 / §1.2.13 提过。它需要在**第一次大量内存分配前**初始化(否则前期分配 untracked)。所以放在 PreInit 极早期。

启动加 `-llm` 启用,无该参数则 LLM 字面上是 0 开销 inline 宏。

## 6.2.5 Stat 系统启动

```cpp
{
    SCOPED_BOOT_TIMING("InitTaggedStorage");
    FPlatformMisc::InitTaggedStorage(1024);
}
// ... Stats 启动 ...
```

Stat 系统(§0.3.3)启动后,所有 `DECLARE_CYCLE_STAT` / `SCOPE_CYCLE_COUNTER` 才能正确累加。Stat group 的注册延迟到首次使用,但**Stat 全局基础设施**(线程池、threadqueue)在 PreInit 早期建好。

## 6.2.6 ConfigCache 加载 INI

引擎在 PreInit 期加载所有 .ini 文件(`Engine/Config/*.ini` + `<Project>/Config/*.ini` + `Saved/Config/*/*.ini`),建立全局 `GConfig` 单例。

### 6.2.6.1 用法

```cpp
// 读
FString Value;
GConfig->GetString(
    TEXT("MyRTS.Settings"),    // section
    TEXT("MaxPlayerCount"),    // key
    Value,                      // out
    GGameIni                   // 哪个 INI 文件
);

int32 IntValue;
GConfig->GetInt(TEXT("MyRTS.Settings"), TEXT("StartingGold"), IntValue, GGameIni);

// 写(运行时改 INI)
GConfig->SetInt(TEXT("MyRTS.Settings"), TEXT("StartingGold"), 500, GGameIni);
GConfig->Flush(false, GGameIni);   // 写盘
```

### 6.2.6.2 常用 INI 全局变量

```cpp
GEngineIni       // Engine.ini(引擎设置)
GGameIni         // Game.ini(游戏设置)
GInputIni        // Input.ini(输入)
GEditorIni       // Editor.ini(Editor 设置)
GScalabilityIni  // Scalability.ini(画质等级)
GHardwareIni
```

### 6.2.6.3 .ini 层叠

UE INI 是**层叠**的(类似 CSS):

```
Engine/Config/BaseEngine.ini             ← 基础默认
Engine/Config/Windows/WindowsEngine.ini  ← 平台特定覆盖
<Project>/Config/DefaultEngine.ini        ← 项目覆盖
<Project>/Config/Windows/WindowsEngine.ini ← 项目 × 平台
<Project>/Saved/Config/Windows/Engine.ini  ← 用户保存
```

读取时按这个顺序合并,后面覆盖前面。

### 6.2.6.4 `UDeveloperSettings`(推荐姿势)

直接读 GConfig 是**老式**。新代码用 `UDeveloperSettings`:

```cpp
UCLASS(Config = MyRTS, DefaultConfig, meta = (DisplayName = "MyRTS Settings"))
class MYRTS_API URTSDeveloperSettings : public UDeveloperSettings
{
    GENERATED_BODY()
public:
    UPROPERTY(Config, EditAnywhere)
    int32 MaxPlayerCount = 4;
    
    UPROPERTY(Config, EditAnywhere)
    float StartingGold = 1000.0f;
};
```

Editor 自动生成 Project Settings 面板。`UPROPERTY(Config)` 字段自动**读 / 写到** `<Project>/Config/DefaultMyRTS.ini`。运行时:

```cpp
const URTSDeveloperSettings* Settings = GetDefault<URTSDeveloperSettings>();
int32 Max = Settings->MaxPlayerCount;
```

**纪律**:RTS 项目的全局配置**99% 用 UDeveloperSettings**,不直接 GConfig。

## 6.2.7 CoreUObject 加载与反射注册

`LaunchEngineLoop.cpp:3661` 附近:

```cpp
ProcessNewlyLoadedUObjects();
```

§2.2.3 详讲过。简化:
1. 加载 `CoreUObject` 模块(其它模块都依赖它)
2. 调 `ProcessNewlyLoadedUObjects` 处理已注册到延迟列表的 UClass
3. 启动 `UObjectBaseInit`(GUObjectArray 完整就绪)

之后:**任何 UCLASS::StaticClass() 都可用,NewObject 可调**。

### 6.2.7.1 这步出错的典型症状

- "Could not find class XXX" → 该模块未加载或 UCLASS 写法错误
- "Cyclic class dependency" → 模块依赖循环(§2.2.8)
- "Token Stream not assembled" → AssembleReferenceTokenStreams 还没跑

## 6.2.8 ShaderCompiler 启动

`LaunchEngineLoop.cpp:3235`:

```cpp
SCOPED_BOOT_TIMING("InitializeShaderTypes");
InitializeShaderTypes();
```

**这是个慢步骤**(几百 ms - 几秒)。它做:
- 启动 ShaderCompileWorker 进程池
- 初始化所有 shader type / parameter struct 反射
- 把着色器源码 hash + 缓存映射建好

如果你 RTS 大量自定义 shader,这步会更慢。但只在 Editor / 第一次启动时显著(后续有缓存)。

### 6.2.8.1 启动加 `-NoShaderWorker` 跳过

某些场景(纯逻辑测试)不需要 shader compile,加 `-NoShaderWorker` 跳过加速启动。**注意**:Editor 不能跳(没 shader 跑不了渲染)。

## 6.2.9 加载 PostConfigInit / PreEarlyLoadingScreen 等模块

LoadingPhase 早于 `Default` 的模块在这两个阶段加载:

```
PostConfigInit:
   - 平台底层 hook
   - Trace 扩展
   - 自定义 LLM tag

PreEarlyLoadingScreen:
   - Splash 自定义
   - chunk patching 系统
```

**RTS 项目极少在这两个阶段加载**。如果你某个模块设了这个 LoadingPhase,问问自己"为什么不放 PreDefault / Default"。

## 6.2.10 Splash Screen 显示

`PreInitPreStartupScreen` 末尾启动 Splash(平台特定逻辑)。Splash 显示一个 Logo / Loading 图,让玩家知道"在加载"。

之后进 `PreInitPostStartupScreen`(splash 仍然显示)。

## 6.2.11 PreInitPostStartupScreen:重头戏

splash 显示中,引擎做"重活":

### 6.2.11.1 LoadStartupModules

每个 LoadingPhase 一批模块:

```
PreLoadingScreen → 自定义 Loading Screen
PreDefault → 基础设施(MyRTSCore 类型)
Default → 大多数游戏模块(MyRTSMass / MyRTSGameplay)
PostDefault → Default 之后的清理 / 注册
```

每批加载完调一次 `ProcessNewlyLoadedUObjects`(§2.2.3.5)。这意味着:**每 LoadingPhase 之间** UClass 反射都已完整可用。

### 6.2.11.2 ShaderCompiler 第二阶段

某些 shader 在 Default phase 模块加载后才能编译(因为 shader 类型可能在那些模块定义)。

### 6.2.11.3 AssembleReferenceTokenStreams

§4.3.2.4 提过。所有 UClass 加载完,**最后一次性** assemble GC schema:

```cpp
// 简化伪代码,在 Default phase 模块加载后
UClass::AssembleReferenceTokenStreams();
// 现在 GC mark 阶段能用 token stream 跑得快
```

这是 PreInit 的最后大动作之一。完成后 GC 可以工作。

---

## 6.2.12 PreInit 末尾的小动作

```
- 注册 Editor / Game 主菜单回调
- 准备 GameInstance(对 Game build)
- FCoreDelegates::OnPostEngineInit 准备发(实际触发在 Init 后)
- 各种 sanity check(Asserts in Shipping 关掉,Editor 仍开)
```

PreInit 末尾返回,GuardedMain 进 `EngineInit` 调用。

## 6.2.14 接入 PreInit 阶段的姿势

### 6.2.14.1 通过 Module 的 `StartupModule`

最常用的"启动期接入":

```cpp
// MyRTSCore.Build.cs:
//   "LoadingPhase": "PreDefault"

class FMyRTSCoreModule : public IModuleInterface
{
    virtual void StartupModule() override
    {
        // PreDefault 时机被调
        // 此时 CoreUObject 已就绪,但 GEngine 还没创建
        
        // 注册自定义 cvar / log category
        // 准备 RTS 全局数据
        
        FCoreDelegates::OnPostEngineInit.AddRaw(this, &ThisClass::OnPostEngineInit);
    }
};
```

### 6.2.14.2 通过 Subsystem

```cpp
class URTSEngineSubsystem : public UEngineSubsystem
{
public:
    virtual void Initialize(FSubsystemCollectionBase& Collection) override
    {
        // GEngine 创建后被调,但在第一帧之前
        // 适合"进程级"全局初始化
    }
};
```

`UEngineSubsystem::Initialize` 在 `GEngine->Init()` 内部被调,时机比 LoadingPhase=PostEngineInit 模块还略晚一点点。

### 6.2.14.3 全局 `FCoreDelegates`

```cpp
FCoreDelegates::OnInit.AddLambda([]() { /* PreInit 末尾 */ });
FCoreDelegates::OnPostEngineInit.AddLambda([]() { /* GEngine 初始化完 */ });
FCoreDelegates::OnFEngineLoopInitComplete.AddLambda([]() { /* Init 全部完成 */ });
```

适合**没有 UObject 类**(纯 C++ 工具)却想接入引擎启动期的场景。

## 6.2.15 自定义 INI 文件

如果你想把 RTS 配置放在自己的 INI:

### 6.2.15.1 通过 UDeveloperSettings(自动)

```cpp
UCLASS(Config = MyRTS)        // ← 配置文件名 = DefaultMyRTS.ini
class URTSSettings : public UDeveloperSettings { ... };
```

UE 自动:
- 读 `Engine/Config/BaseMyRTS.ini`(如果存在)+ `<Project>/Config/DefaultMyRTS.ini`
- 把读到的值赋给 UPROPERTY(Config) 字段

### 6.2.15.2 手动 GConfig

```cpp
// 你的 INI 文件名(不带扩展)
const FString MyIniName = TEXT("MyRTS");

// 写
GConfig->SetString(TEXT("Section"), TEXT("Key"), TEXT("Value"), MyIniName);
GConfig->Flush(false, MyIniName);

// 读
FString V;
GConfig->GetString(TEXT("Section"), TEXT("Key"), V, MyIniName);
```

UE 找文件路径:`<Project>/Config/Default<MyIniName>.ini`。

## 6.2.16 RTS / Mass 视角下的启动期纪律

### (1)Fragment / Tag 类型注册时机

`MyRTSCore` 模块 LoadingPhase = `PreDefault`,所有 Fragment USTRUCT 在这个阶段被反射注册。后续 `MyRTSMass` 加载时(`Default`)能拿到完整 Fragment 类型清单。

### (2)Mass Subsystem 初始化在 Init 之后

`UMassEntitySubsystem` 是 World Subsystem,**World 创建时**初始化(在 Init 末尾 LoadDefaultMap 后)。所以 PreInit / Init 期间 Mass 还**不存在**。如果你需要"启动期就启动 Mass",你做不到 — Mass 与 World 绑定。

### (3)UDeveloperSettings 的"启动期可读"

```cpp
// PostConfigInit 之后 GConfig 可用
const URTSSettings* S = GetDefault<URTSSettings>();
// PostConfigInit 阶段 S 还没创建(UClass 反射未完)→ 不安全
// PreDefault 之后稳妥
```

**纪律**:**等 PreDefault 之后**再访问 UDeveloperSettings。Module StartupModule 通常 OK(那时 LoadingPhase >= 自己设的值)。

### (4)RTS 命令行调试

启动加 `-RTSDebug` 自定义 flag,代码里检测:

```cpp
if (FParse::Param(FCommandLine::Get(), TEXT("RTSDebug")))
{
    // 启用调试可视化、verbose log 等
}
```

实战:CI 跑 RTS 自动化测试,启动加 `-RTSAutoBattle=true -RTSAutoExitAfter=60` 之类参数,代码读取 + 自动化。
