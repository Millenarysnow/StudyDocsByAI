# §4.1 UObject 引用图全景 — UPROPERTY / TObjectPtr / TStrongObjectPtr / FGCObject

> **本节地图**:模块一第 4 章第 1 节。这一章是整本指南的**关键转折点** —— 我们要拆 GC,而拆 GC 之前必须先把"引用图"画清。GC 的核心问题就一句话:**"哪些 UObject 当前还被引用?"** 这取决于代码里有多少种"持有 UObject"的方式。
>
> UE 里持有 UObject 的方式有 **5+ 种**:
>
> - `UPROPERTY()` 标记的字段(自动 GC)
> - `TObjectPtr<T>`(强引用 + access tracking)
> - `TStrongObjectPtr<T>`(RAII 引用计数,非 UObject 持有者用)
> - `TWeakObjectPtr<T>`(弱引用,§3.2 讲过)
> - `FGCObject` 接口(让非 UObject 类参与 GC 引用图)
> - 裸 `UObject*`(**危险!**GC 不知道,可能悬空)
>
> 每种姿势的开销、安全性、适用场景天差地别。**这一节是 RTS 项目设计 Fragment / Subsystem / Manager 时必须吃透的纪律**。
>
> **预备知识**:§3.1(UObject 头部),§3.2(GUObjectArray),§3.4(CDO)。
>
> **读完之后你能做到**:
> - 看到任何 UObject 引用,5 秒说出它属于哪种姿势,GC 是否知道
> - 在 Mass Fragment 里**正确**持有 UStaticMesh / UTexture 等资源
> - 在 RTS 单例 Subsystem 里持有 UObject 池
> - 知道 `FGCObject` 是给谁用的(C++ 编辑器工具、外部库桥接)
> - 调试 "对象被意外 GC 了" / "对象一直不被 GC" 的悬空 / 泄漏问题

## 4.1.1 浅入:GC 怎么知道谁还活着

GC 算法的核心问题是 **reachability(可达性)**:

> "从一组**根**(root)出发,沿着引用边走,能走到的 UObject 还活着;走不到的可以回收。"

这是图遍历问题。但**边在哪里**?

C++ 没原生反射,GC 不能像 Java 那样"扫每个对象的所有指针"。UE 必须**显式登记每条 UObject 引用边**才能让 GC 看见。登记方式有几种,每种都有自己的"语法"和"代价"。

这一节就是逐一拆这些登记姿势。

---

## 4.1.2 GC Root —— 引用图的"起点"

GC 从 root 出发遍历。Root 包含:

| Root 类型 | 来源 |
|---|---|
| `RF_RootSet` 标记的 UObject | `AddToRoot()` / `RF_MarkAsRootSet`(永久根) |
| `RF_ClassDefaultObject` (CDO) | 反射注册时自动 root |
| GC Cluster Root | §4.3 讲的集群根 |
| 注册的 `FGCObject` 子类对象 | 通过 `UGCObjectReferencer` 桥接 |
| `TStrongObjectPtr` 持有的对象 | 通过 ref count 强引用 |

GC 启动时把所有 root 标记为 reachable,然后递归扩展。

### 4.1.2.1 `AddToRoot()` / `RemoveFromRoot()`

```cpp
UMyManager* M = NewObject<UMyManager>();
M->AddToRoot();          // ★ 永远不被 GC
// ... 使用 ...
M->RemoveFromRoot();     // 之后可以 GC
```

实现就是设 / 清 `RF_RootSet` flag。**用法纪律**:
- ✅ Subsystem / 单例 / 全局 manager 在创建时 AddToRoot
- ✅ 长寿命对象,你确认它要活到进程结束
- ❌ 临时对象(几秒生命),别 AddToRoot 后忘记 RemoveFromRoot
- ❌ 数量级大的对象集合(几千个 actor),逐个 AddToRoot 累计成本不小,**而且容易忘 Remove 导致泄漏**

**RTS 实战**:你的 `URTSGameSubsystem` / `URTSMassController` 等单例,Init 时 AddToRoot,Deinit 时 RemoveFromRoot。

### 4.1.2.2 World 是默认 root

在 World 里 SpawnActor 的 actor、ActorComponent 的子 component 通过"Outer 链"间接被 World 持有。World 自己被 `UWorld` Subsystem / GameInstance 持有,这条链最终连到 root。

所以游戏对象**通常不需要手动 AddToRoot** —— 它们的 Outer 是 World 或 Actor,自然连到 root。Subsystem 是少数需要手动管的。

## 4.1.3 引用姿势 1:`UPROPERTY()` —— 反射驱动,自动 GC

最常见的姿势:

```cpp
UCLASS()
class UMyComp : public UObject
{
    UPROPERTY()
    TObjectPtr<UStaticMesh> Mesh;

    UPROPERTY()
    TArray<TObjectPtr<UMaterial>> Materials;
};
```

UHT 在反射注册时,把每个 `UPROPERTY` 字段记到 UClass 的 `ChildProperties` 链(§2.2.4.2),并标记字段类型(`FObjectProperty` 等)。GC 扫描时:

```cpp
// 简化伪代码
for (FProperty* P = Class->RefLink; P; P = P->NextRef)
{
    void* FieldPtr = (uint8*)Object + P->Offset;
    
    if (P->IsA<FObjectProperty>())
    {
        UObject* Referenced = *(UObject**)FieldPtr;
        Collector.AddReferencedObject(Referenced);     // 标记为 reachable
    }
    else if (P->IsA<FArrayProperty>())
    {
        // 数组:递归遍历每个元素
        TArray<void*>* Arr = (TArray<void*>*)FieldPtr;
        for (...) Collector.AddReferencedObject(...);
    }
    // ... 其它类型 ...
}
```

**自动**!你写 `UPROPERTY()`,GC 自动知道。这是**优雅的姿势**。

### 4.1.3.1 GC 只扫 RefLink,不扫 PropertyLink

§2.3.7.1 提到 UStruct 维护多个属性链表:
- `PropertyLink` — 所有字段
- `RefLink` — **仅含 UObject 引用的字段**(GC 用)
- `DestructorLink` / `PostConstructLink` 等

GC 走 `RefLink`,跳过纯数据字段(int / float)。这让 GC 标记阶段**显著加速** —— Mass Fragment(纯数据)即使加 UPROPERTY 反射,也几乎不影响 GC。

### 4.1.3.2 Token Stream —— UPROPERTY 的真正秘密武器

§4.3 详讲。简化:UClass 在反射注册末尾,把"所有 UObject 引用字段的字节偏移"编译成一段紧凑字节码("token stream"),GC 标记阶段直接执行这段字节码而不是反射查询。比走 RefLink 更快几倍。

这是 UE GC 性能的核心 —— 反射数据被预处理成"GC 字节码"。

### 4.1.3.3 `UPROPERTY()` 的成本

- **添加成本**:UHT 处理 + UClass 反射注册 + Token Stream 字节
- **运行时成本**:GC 标记阶段每次扫这字段一次(几纳秒)
- **存储成本**:与无 UPROPERTY 字段一样(`UPROPERTY` 不改对象内存布局)

50 个 UPROPERTY 字段 / class × 10K 实例 × 一次 GC = 50 万次字段扫描 ≈ 几毫秒。**完全可接受**。

### 4.1.3.4 实战纪律

```cpp
// ✅ 标准姿势
UPROPERTY()
TObjectPtr<UStaticMesh> Mesh;

// ✅ 数组也可以
UPROPERTY()
TArray<TObjectPtr<AMyActor>> Children;

// ✅ Map 也可以
UPROPERTY()
TMap<FName, TObjectPtr<UTexture2D>> TextureLibrary;

// ❌ 裸指针 + UPROPERTY:5.0+ 已过时,改用 TObjectPtr
UPROPERTY()
UStaticMesh* Mesh;   // 仍然能 GC,但 access tracking 失效
```

5.0+ 起,**新代码统一用 `TObjectPtr<T>` 而不是 `T*`**。下面 §4.1.4 详讲。

## 4.1.4 引用姿势 2:`TObjectPtr<T>` —— 5.0+ 的现代写法

`Engine/Source/Runtime/CoreUObject/Public/UObject/ObjectPtr.h`。

### 4.1.4.1 与裸指针对比

```cpp
TObjectPtr<UStaticMesh> Mesh;     // 5.0+ 推荐
UStaticMesh* RawPtr;              // 老式
```

行为上**几乎等价**:
- `Mesh.Get()` 返回 `UStaticMesh*`
- 自动从 `UStaticMesh*` 隐式构造
- 自动转换为 `UStaticMesh*`(运算符重载)
- `sizeof(TObjectPtr<T>) == sizeof(T*) == 8 字节`

**新加的功能**:
1. **Access tracking**:Editor 模式下,每次 deref 都被记录,用于"懒加载资产"机制(`FObjectHandle`)
2. **类型安全**:模板类型,避免 `Mesh = SomeOther*` 误赋(虽然 UE 会自动 C-style cast)
3. **未来扩展**:Epic 可能在 TObjectPtr 里加更多功能(如 RemoteObject 集成)

### 4.1.4.2 Access tracking —— Editor 的"懒加载"

```cpp
TObjectPtr<UStaticMesh> Mesh;
// 资产加载时,Mesh 字段是个"未解析"句柄
// 第一次 Mesh->RenderData 时(deref),Editor 检测并加载真正的 Mesh 资产
```

这让 Editor 在打开"含大量资产引用的关卡"时,能延迟加载部分资产,**显著缩短 Editor 加载时间**。

**Game build**(Cooked package)关掉 access tracking,`TObjectPtr` 退化为裸指针,零开销。

### 4.1.4.3 隐式转换的"魔法"

```cpp
TObjectPtr<UStaticMesh> Mesh = ...;

// 这些都合法:
UStaticMesh* Raw = Mesh;              // implicit operator UStaticMesh*
if (Mesh) { ... }                     // implicit operator bool
Mesh->RenderData;                     // operator->
*Mesh;                                 // operator*

// 与 nullptr 比
if (Mesh == nullptr) { ... }
```

代码上你**几乎察觉不到** TObjectPtr 与裸指针的差异。**但是** GC 标记 / Access tracking 在背后默默工作。

### 4.1.4.4 常见错误:`TObjectPtr` 不带 UPROPERTY

```cpp
class UMyComp : public UObject
{
    TObjectPtr<UStaticMesh> Mesh;     // ❌ 没 UPROPERTY,GC 不知道!悬空风险
};
```

**致命**:`TObjectPtr` 自身**不**让 GC 知道。它是"语法糖 + access tracking",不是"GC root"。**必须 + UPROPERTY** 才让 GC 看到:

```cpp
class UMyComp : public UObject
{
    UPROPERTY()
    TObjectPtr<UStaticMesh> Mesh;     // ✅ 标准姿势
};
```

### 4.1.4.5 何时用裸指针(`T*`)

仅一种合法场景:**纯函数参数 / 局部变量,生命周期短到 GC 不可能介入**:

```cpp
void DoSomething(UStaticMesh* Mesh)         // ✅ 短生命参数
{
    UStaticMesh* Local = Mesh;              // ✅ 局部变量
    Local->Foo();
}
```

**字段**永远用 `TObjectPtr<T>` + `UPROPERTY()`。

## 4.1.5 引用姿势 3:`TStrongObjectPtr<T>` —— RAII 强引用(非 UObject 持有者用)

`Engine/Source/Runtime/Core/Public/UObject/StrongObjectPtrTemplates.h:25`(配合 `Engine/Source/Runtime/CoreUObject/Private/UObject/StrongObjectPtr.cpp`):

```cpp
template<typename T>
class TStrongObjectPtr
{
    T* RawPtr;
public:
    TStrongObjectPtr(T* In)
    {
        RawPtr = In;
        if (RawPtr) RawPtr->AddRef();   // ★ UObject 引用计数 +1
    }
    ~TStrongObjectPtr()
    {
        if (RawPtr) RawPtr->ReleaseRef();
    }
    T* Get() const { return RawPtr; }
    // ...
};
```

底层调用 `UObject::AddRef()` / `UObject::ReleaseRef()`(§3.1.2 提到的字段 RefCount,在 `FUObjectItem.FlagsAndRefCount` 低 32 位)。

### 4.1.5.1 何时用 TStrongObjectPtr

**当持有者本身不是 UObject** 但想强引用一个 UObject 让它不被 GC:

```cpp
// 一个 C++ 工具类,不继承 UObject
class FMyTool
{
    TStrongObjectPtr<UStaticMesh> Mesh;     // 持有 mesh 不被 GC
public:
    FMyTool(UStaticMesh* M) : Mesh(M) {}
};
```

如果 `FMyTool` 改成 `class UMyTool : public UObject`,直接用 `UPROPERTY() TObjectPtr<UStaticMesh> Mesh` 即可,无需 TStrongObjectPtr。

### 4.1.5.2 性能对比

| 姿势 | 持有者类型 | 开销 |
|---|---|---|
| UPROPERTY + TObjectPtr | UObject | 零额外(GC 自动) |
| TStrongObjectPtr | 任意 | RAII(create/destroy 调 atomic 引用计数) |
| FGCObject(下面 §4.1.6) | 任意非 UObject | RegisterGCObject + 你的 AddReferencedObjects 函数 |

`TStrongObjectPtr` 创建/销毁有 atomic 操作(几十纳秒),hot path 注意。

### 4.1.5.3 与 `TWeakObjectPtr::Pin` 的关系

```cpp
TWeakObjectPtr<UMesh> Weak = ...;

// Pin 把弱引用临时升级为强引用(RAII)
TStrongObjectPtr<UMesh> Strong = Weak.Pin();
if (Strong)
{
    // 在 Strong 析构前,对象不会被 GC,即使没人引用
}
// Strong 析构 → ReleaseRef → 对象可能在下次 GC 被回收
```

5.x 引入 `Pin` 模式(`Engine/Source/Runtime/CoreUObject/Public/UObject/WeakObjectPtr.h:234+`),让你能**临时**持有强引用做关键操作。

## 4.1.6 引用姿势 4:`FGCObject` —— 让非 UObject 类参与 GC 图

`Engine/Source/Runtime/CoreUObject/Public/UObject/GCObject.h:127`:

```cpp
class FGCObject
{
public:
    FGCObject() { RegisterGCObject(); }
    virtual ~FGCObject() { UnregisterGCObject(); }
    
    // 必须重写
    virtual void AddReferencedObjects(FReferenceCollector& Collector) = 0;
    virtual FString GetReferencerName() const = 0;
    
    static UGCObjectReferencer* GGCObjectReferencer;     // 全局桥接 UObject
};
```

**机制**:进程内有一个全局 `UGCObjectReferencer`(本身是 UObject,在 root set),它持有所有注册的 `FGCObject*`。GC 标记阶段:

```
GC root → GGCObjectReferencer (UObject)
  ↓
  GGCObjectReferencer::AddReferencedObjects(Collector)
  ↓ 遍历所有注册的 FGCObject*
  ↓
  每个 FGCObject::AddReferencedObjects(Collector)
  ↓
  Collector 收到这些对象 → 标记为 reachable
```

### 4.1.6.1 用法

```cpp
// 我是个 C++ 工具类,持有几个 UObject 引用
class FMyAssetEditor : public FGCObject
{
    UStaticMesh* CurrentMesh = nullptr;   // 注意是裸指针!
    TArray<UMaterial*> CurrentMaterials;
    
public:
    virtual void AddReferencedObjects(FReferenceCollector& Collector) override
    {
        Collector.AddReferencedObject(CurrentMesh);
        Collector.AddReferencedObjects(CurrentMaterials);
    }
    virtual FString GetReferencerName() const override
    {
        return TEXT("FMyAssetEditor");
    }
};
```

**注意**:在 `AddReferencedObjects` 内部用裸指针 OK —— 这一刻 GC 已经在询问引用,你直接告诉它即可。**字段本身**用裸指针因为 FGCObject 这套机制就是给"非 UObject 类型"用的,UPROPERTY 用不了。

### 4.1.6.2 何时用 FGCObject

**典型场景**:
- C++ Editor 工具类(资产编辑器、自定义工具栏)持有引用
- 桥接外部库(Lua / Python binding)的对象池
- 临时缓存(Editor 的 undo / redo 堆栈中的对象)

**RTS 项目**:几乎不用。你大多数对象是 Subsystem(UObject)或 Mass entity(完全不是 UObject)。FGCObject 是 Editor 工具开发的专属姿势。

### 4.1.6.3 `EFlags::AddStableNativeReferencesOnly`(5.x 新增)

`GCObject.h:171`:

```cpp
enum class EFlags : uint32
{
    None = 0,
    RegisterLater = 1 << 0,
    AddStableNativeReferencesOnly = 1 << 1,   // 5.x 新
};
```

`AddStableNativeReferencesOnly` 标志:声明 `AddReferencedObjects` 只用 `Collector.AddStableReference*` 接口(不变的 native 引用)。让 GC 能在 reachability analysis **开始前**就收集这些根集,稍微提速。

**99% 用不到**。新代码默认 `EFlags::None`。

### 4.1.6.4 危险的 FGCObject 用法

GCObject.h 注释里(line 120-126)有警告:

```cpp
/**
 * For example, this won't work:
 * class FMyClass : public FGCObject {};
 * struct FSomeStruct {
 *     TArray<FMyClass> Instances; // Storing anything here might crash GC at 
 *                                 // reachability analysis
 * };
 */
```

**FGCObject 注册的是"对象指针"到全局列表**。如果你把 FGCObject 子类**值拷贝**(`TArray<FMyClass>` 把对象一个个值拷),每次拷贝构造都注册一次,但析构时全注销。GC 中途可能拿到悬空的 FGCObject*,崩溃。

**纪律**:`FGCObject` 子类**只能放堆上**(`new` 分配)或栈上(局部变量,有限作用域)。**不能放容器值类型**。如果想放容器,用 `TUniquePtr<FMyClass>` 或 `TSharedPtr<FMyClass>`。

## 4.1.7 引用姿势 5:裸 `UObject*`(危险!)

```cpp
class UMyComp : public UObject
{
    UStaticMesh* Mesh;     // 没 UPROPERTY,没 TObjectPtr,纯裸指针
};
```

**GC 完全不知道**!后果:
- GC 不标记 Mesh 为 reachable
- Mesh 可能被回收
- 你的 `Mesh` 字段悬空,deref 崩溃

实际项目中这种**几乎都是 bug**。原因可能是:
- 新人没学过 GC
- 老代码漏改(5.0 前用裸指针 + UPROPERTY,5.0 后没改成 TObjectPtr)
- 故意"避开"GC(理由几乎都站不住)

**唯一合法场景**:
- 函数参数 / 局部变量(短生命)
- 性能极敏感的 hot path 缓存(临时变量,确认 GC 不会介入)

## 4.1.8 一张总结表

| 姿势 | 持有者类型 | GC 知晓 | 性能 | 用途 |
|---|---|---|---|---|
| `UPROPERTY() TObjectPtr<T>` | UObject | ✓ 自动 | 零额外(GC 标记时 ns/字段) | 标准 |
| `UPROPERTY() T*`(老式) | UObject | ✓ 自动 | 同上 | 5.0 前代码,新代码改 TObjectPtr |
| `TObjectPtr<T>`(无 UPROPERTY) | 任意 | ✗ | 危险 | 几乎不要这样写 |
| `TStrongObjectPtr<T>` | 任意 | ✓(RefCount) | 创建/销毁 atomic | 非 UObject 持有 UObject |
| `TWeakObjectPtr<T>` | 任意 | ✗(弱) | Get() 几 ns | 不阻止 GC,自动失效 |
| `FGCObject::AddReferencedObjects` | 非 UObject | ✓ | 注册/反注册成本中 | Editor 工具、外部桥接 |
| 裸 `UObject*` | 任意 | ✗ | 0 | 仅短期局部 |
| `AddToRoot()` | UObject | ✓ 永久 root | flag 操作 | 单例 / Subsystem |

## 4.1.9 `FReferenceCollector` —— GC 的"扫描访问者"

每次 GC 询问 "你引用了哪些对象",通过 `FReferenceCollector` 接口收集:

```cpp
class FReferenceCollector
{
public:
    virtual void HandleObjectReference(UObject*& InObject, ...) = 0;
    
    // 便利方法
    void AddReferencedObject(UObject*& Object);
    void AddReferencedObject(TObjectPtr<UObject>& Object);
    template<typename T>
    void AddReferencedObjects(TArray<TObjectPtr<T>>& ObjectArray);
    void AddReferencedObjects(TSet<TObjectPtr<UObject>>& ObjectSet);
    // ... 等等 ...
    
    // 5.x 新:Stable Reference(reachability 之前就稳定的引用)
    void AddStableReference(UObject** Object);
    template<typename T>
    void AddStableReferenceArray(TArray<T*>* Objects);
};
```

GC 实现的具体 collector(`FCollectorTraversal` 之类的内部实现)继承这个接口,拿到引用后:
1. 标记对象为 reachable
2. 把对象推到 BFS 队列等待递归扫描

`AddReferencedObject` 是用户面 API,GC 内部细节不用关心。**你只需要在 `AddReferencedObjects` / Token Stream 里把所有引用告诉 collector**。

---

## 4.1.10 `UObject::AddReferencedObjects`(虚函数,可重写)

```cpp
class UObject
{
public:
    static void AddReferencedObjects(UObject* InThis, FReferenceCollector& Collector);
};
```

注意:**这是个静态函数**,签名特殊。每个 UObject 子类**可以**重写它(通过反射注册的 lambda 桥接):

```cpp
UCLASS()
class UMyComp : public UObject
{
public:
    int32 NonReflectedField;
    UStaticMesh* CustomMesh;     // 不想用 UPROPERTY 的特殊场景
    
    static void AddReferencedObjects(UObject* InThis, FReferenceCollector& Collector)
    {
        UMyComp* This = CastChecked<UMyComp>(InThis);
        Collector.AddReferencedObject(This->CustomMesh);
        Super::AddReferencedObjects(InThis, Collector);   // 调父类
    }
};
```

99% 项目代码不需要重写。Token Stream 自动处理 UPROPERTY 字段。**仅在**你有"非 UPROPERTY 但仍要 GC 知晓"的字段时重写。

## 4.1.11 RTS / Mass 视角下的纪律

### (1)Mass Fragment 持有 UObject 的标准姿势

Fragment 是 USTRUCT(POD)。它**不是 UObject,无虚函数,但反射注册**。Mass 的 Fragment 内若想持有 UObject 引用让 GC 知晓:

```cpp
USTRUCT()
struct FMassUnitFragment : public FMassFragment
{
    GENERATED_BODY()

    // ✅ 标准姿势:UPROPERTY + TObjectPtr,Mass 系统自动注册到 GC
    UPROPERTY()
    TObjectPtr<UStaticMesh> Mesh;
    
    // ❌ 裸指针:GC 不知,可能悬空
    // UStaticMesh* Mesh;
    
    // ❌ FGCObject:Fragment 是 USTRUCT 不是 class,继承不上
    
    // ✅ 弱引用:不阻止 GC,但需要 .Get() 检查
    TWeakObjectPtr<UTexture2D> WeakIcon;
};
```

**Mass 内部**对 USTRUCT 有特殊处理:它扫所有 Fragment 的 UPROPERTY 字段,把 UObject 引用挂到 GC 引用图上。具体细节在 `FMassEntityManager` 内部,§17 详讲。

### (2)Fragment 大量持有同一个 UObject 是低效的

50K entity × 每个 Fragment 持 1 个 UStaticMesh 引用 → GC 标记阶段每帧扫 50K 次"已 reachable"。即使快路径,也累积。

**优化**:用 SharedFragment(每 archetype 一份共享数据)持有引用,而不是每 entity Fragment:

```cpp
// 不好:每 entity 一份引用
USTRUCT()
struct FUnitVisualFragment : public FMassFragment
{
    UPROPERTY()
    TObjectPtr<UStaticMesh> Mesh;     // 50K 份引用
};

// 更好:每 archetype 一份(SharedFragment)
USTRUCT()
struct FUnitVisualSharedFragment : public FMassSharedFragment
{
    UPROPERTY()
    TObjectPtr<UStaticMesh> Mesh;     // archetype 数量级份引用(几十)
};
```

### (3)RTS Subsystem / Manager 持有大对象池

```cpp
UCLASS()
class URTSObjectPool : public UWorldSubsystem
{
public:
    UPROPERTY()
    TArray<TObjectPtr<AHero>> AvailableHeroes;
    
    UPROPERTY()
    TMap<FName, TObjectPtr<UDataAsset>> ConfigCache;
};
```

Subsystem 是 UObject,字段用 `UPROPERTY() TObjectPtr<>`,GC 自动跟踪。Subsystem 自身在 World 生命周期内 root,所以池里对象都活着。

## 4.1.12 调试:看一个 UObject 的所有引用者

```cpp
static FAutoConsoleCommand CmdInspectRefs(TEXT("rts.InspectRefs"),
    TEXT("rts.InspectRefs <ObjName>"),
    FConsoleCommandWithArgsDelegate::CreateLambda([](const TArray<FString>& Args)
    {
        if (Args.Num() == 0) return;
        UObject* Target = FindFirstObject<UObject>(*Args[0]);
        if (!Target) { UE_LOG(LogTemp, Warning, TEXT("Not found")); return; }
        
        // 用 UE 自带工具找谁引用了 Target
        FReferencerInformationList Refs;
        bool bIsReferenced = IsReferenced(Target, GARBAGE_COLLECTION_KEEPFLAGS, 
            EInternalObjectFlags::GarbageCollectionKeepFlags, true, &Refs);
        
        UE_LOG(LogTemp, Display, TEXT("%s referenced: %s"), 
            *Target->GetName(), bIsReferenced ? TEXT("yes") : TEXT("no"));
        
        for (const FReferencerInformation& Ref : Refs.ExternalReferences)
        {
            UE_LOG(LogTemp, Display, TEXT("  By: %s"), *Ref.Referencer->GetFullName());
            for (const FProperty* P : Ref.ReferencingProperties)
            {
                UE_LOG(LogTemp, Display, TEXT("    via field: %s"), *P->GetName());
            }
        }
    }));
```

`IsReferenced` 是 UE 自带的内置函数,会扫整个 UObject 图找谁引用了 target。**慢但准**,debug 必备。

## 4.1.13 实操提示与下一节预告

### 实操提示

- **诊断"对象意外被 GC"**:对象引用应该是 `UPROPERTY() TObjectPtr<>` 或 `TStrongObjectPtr<>`。检查是不是漏写 UPROPERTY。
- **诊断"对象一直不被 GC"**:可能是循环引用(对象 A 持 B,B 持 A,但都不在 root)。UE GC 是 mark-sweep 不是 ref count,**循环引用一般能正确回收**(只要循环外没有 root 持有)。如果你看到"该死的不死",检查是不是某处悄悄 AddToRoot 了。
- **看你某 UObject 引用图**:`IsReferenced` 配合 console command,能列出所有 referencer。
- **不确定时用 `TWeakObjectPtr`**:你不确定对象生命周期时,弱引用最安全。Hot path 上 `.Get()` 检查 nullptr。
