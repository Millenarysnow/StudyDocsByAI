# §1.1 平台抽象层 — FPlatformMisc / FPlatformAtomics / FPlatformProcess

> **本节地图**:模块一第 1 章第 1 节。这是真正的"源码深度"起点。
>
> 我们要回答一个看似简单的问题:**"UE 是怎么屏蔽 Windows / Linux / Mac / 主机平台的差异?"** 答案不仅仅是 "用 `#ifdef`",而是一整套精心设计的**模板继承 + typedef 别名 + 包含转发**机制。理解这一节后,你看到 `FPlatformAtomics::InterlockedIncrement` 的时候**立刻**知道它在你的 Win64 上展开成什么、怎么找到那个实现。
>
> **预备知识**:§0.1(模块系统)。本节不假设你懂 UE 任何运行时知识。
>
> **读完之后你能做到**:
> - 看懂 `Engine/Source/Runtime/Core/Public/{HAL, GenericPlatform, Windows}` 这三个文件夹的角色分工
> - 任意 `FPlatformXxx::Yyy()` 调用,你都能五秒内定位到 Windows / Linux 各自的实现文件
> - 写跨平台代码时不再用 `#ifdef _WIN32`,而是走 UE 风格的 `FPlatformXxx`
> - 知道为什么 5.x 的 `FGenericPlatformAtomics` 注释里写着 "DEPRECATED! Use std::atomic<T>" —— 以及对 RTS 项目意味着什么

## 1.1.1 从最浅的问题开始:UE 写跨平台代码,不用 `#ifdef`

普通 C++ 项目里,跨平台代码长这样:

```cpp
// 普通 C++ 风格
#ifdef _WIN32
    LARGE_INTEGER Freq, Counter;
    QueryPerformanceFrequency(&Freq);
    QueryPerformanceCounter(&Counter);
    double Seconds = (double)Counter.QuadPart / Freq.QuadPart;
#elif defined(__linux__)
    struct timespec Ts;
    clock_gettime(CLOCK_MONOTONIC, &Ts);
    double Seconds = Ts.tv_sec + Ts.tv_nsec * 1e-9;
#endif
```

这种写法在 UE 源码里**几乎看不到**。UE 的写法是:

```cpp
// UE 风格
double Seconds = FPlatformTime::Seconds();
```

`FPlatformTime` 是什么?它**不是**一个平台无关的实现,也**不是**虚函数运行时分发。它是**当前编译目标平台的时间 API 静态类**的别名。在 Win64 上,`FPlatformTime` = `FWindowsPlatformTime`;在 Linux 上,`FPlatformTime` = `FLinuxPlatformTime`。**编译期决定**,**零运行时开销**。

那这套别名机制具体怎么搭起来的?这就是 §1.1 要拆开的"魔法"。

## 1.1.2 三个文件夹各自的角色

打开 `Engine/Source/Runtime/Core/Public`,你会看到三个相邻文件夹:

```
Engine/Source/Runtime/Core/Public/
├── HAL/                       ← "用户面"。游戏代码 #include 的就是这里。
│   ├── Platform.h
│   ├── PlatformMisc.h
│   ├── PlatformAtomics.h
│   ├── PlatformProcess.h
│   ├── PlatformTime.h
│   ├── PlatformTLS.h
│   └── PlatformMemory.h
│
├── GenericPlatform/           ← "通用基类"。每个平台特化的父类。
│   ├── GenericPlatform.h           (FGenericPlatformTypes)
│   ├── GenericPlatformMisc.h       (FGenericPlatformMisc)
│   ├── GenericPlatformAtomics.h    (FGenericPlatformAtomics)
│   ├── GenericPlatformProcess.h
│   ├── GenericPlatformTime.h
│   └── ...
│
└── Windows/                   ← "Windows 特化"。继承自 Generic 并重写。
    ├── WindowsPlatform.h           (FWindowsPlatformTypes)
    ├── WindowsPlatformMisc.h       (FWindowsPlatformMisc)
    ├── WindowsPlatformAtomics.h    (FWindowsPlatformAtomics)
    └── ...
```

(Linux / Mac / Android 也各有自己的文件夹,结构对称。这里只看 Windows 作为例子。)

**三层职责**:

1. **`GenericPlatform/`**:**纯虚的"接口约定"**。每个 API 都有签名声明,通常给一个最朴素的(往往低性能的)默认实现作为 fallback。
2. **`Windows/`**(或 Linux/Mac/...)**:Windows 特化实现**。**继承** Generic 那个类,重写关键函数,用 Win32 API 实现。
3. **`HAL/`**:**最终别名**。通过 `#include COMPILED_PLATFORM_HEADER(...)` 选中当前平台的特化,然后 `typedef` 成 `FPlatformXxx`。游戏代码只 include `HAL/PlatformXxx.h`。

我们把这三层用一个具体例子拆开。

## 1.1.3 完整链路 walk-through:`FPlatformAtomics::InterlockedIncrement`

跟着 **`PlatformAtomics`** 走一遍。

### Step 1 — 用户面的入口

`Engine/Source/Runtime/Core/Public/HAL/PlatformAtomics.h`(整个文件就 9 行):

```cpp
// HAL/PlatformAtomics.h:1-9
#pragma once

#include "CoreTypes.h"
#include "GenericPlatform/GenericPlatformAtomics.h"

#include COMPILED_PLATFORM_HEADER(PlatformAtomics.h) // IWYU pragma: export
```

短得不可思议。它做的事:
1. 拉进 Generic 基类(`FGenericPlatformAtomics`)
2. 通过 `COMPILED_PLATFORM_HEADER(PlatformAtomics.h)` 拉进**当前平台**的特化头文件

### Step 2 — `COMPILED_PLATFORM_HEADER` 是什么

定义在 `Engine/Source/Runtime/Core/Public/HAL/PreprocessorHelpers.h:80`:

```cpp
// HAL/PreprocessorHelpers.h:80
#define COMPILED_PLATFORM_HEADER(Suffix) \
    PREPROCESSOR_TO_STRING(PREPROCESSOR_JOIN(PLATFORM_HEADER_NAME, Suffix))
```

(还有一个变体在 :84,把 `Foo/` 前缀也加上,用于子目录嵌套布局,我们这里不展开。)

这个宏依赖一个**编译期注入**的宏 `PLATFORM_HEADER_NAME`。这个宏由 UBT 在编译命令行注入:
- 编译 Win64 → `-DPLATFORM_HEADER_NAME=Windows`
- 编译 Linux → `-DPLATFORM_HEADER_NAME=Linux`
- 编译 Mac → `-DPLATFORM_HEADER_NAME=Mac`
- 主机 → 各家厂商自己给

所以 `COMPILED_PLATFORM_HEADER(PlatformAtomics.h)` 在 Win64 编译时展开为字符串字面量 `"Windows/WindowsPlatformAtomics.h"`,这就是 `#include` 的目标。

**这是 UE 跨平台机制的"心脏"**:一个宏,把"选哪个平台"这个决策从源码里抽离到**构建系统层**(UBT 注入)。游戏代码不需要知道当前平台是什么。

### Step 3 — Generic 基类提供约定

`Engine/Source/Runtime/Core/Public/GenericPlatform/GenericPlatformAtomics.h:25` 起:

```cpp
// GenericPlatform/GenericPlatformAtomics.h:25
struct FGenericPlatformAtomics
{
#if 0   // can never use these since the actual implementation would have to be in a derived class as we are not using virtuals
        // provided here for reference
    static FORCEINLINE int32 InterlockedIncrement(volatile int32* Value)
    {
        int32 RetVal;
        do {
            RetVal = *Value;
        } while (InterlockedCompareExchange((int32*)Value, RetVal + 1, RetVal) != RetVal);
        return RetVal + 1;
    }
    // ...
#endif
};
```

注意几个细节:

1. **它是一个 `struct`,不是 class,不是模板**。所有方法都是 `static`。这是 UE Platform 抽象层的统一姿势:**"静态函数家族 + 继承 + typedef"**,不用虚函数。
2. **`#if 0` 包裹的"参考实现"**。Generic 类自己**不**直接提供能跑的版本,只是给你看"如果你要新移植一个平台,大概该这么实现"。每个平台**必须**重写这些静态方法。
3. **没有 virtual,没有运行时分发**。完全编译期决定。

最关键的注释在文件顶部第 20-21 行:

```cpp
// GenericPlatform/GenericPlatformAtomics.h:19-23
/**
* DEPRECATED! UE atomics are not maintained and potentially will be physically deprecated. 
* Use std::atomic<T> for new code
*
* Generic implementation...
*/
struct FGenericPlatformAtomics
```

**这是 5.x 的一个重要纪律变化**(后面 1.1.7 单独讲):**新代码不应再用 `FPlatformAtomics::InterlockedXxx`,改用 C++ 标准的 `std::atomic<T>`**。

### Step 4 — Windows 特化

`Engine/Source/Runtime/Core/Public/Windows/WindowsPlatformAtomics.h:26`:

```cpp
// Windows/WindowsPlatformAtomics.h:26
struct FWindowsPlatformAtomics
    : public FGenericPlatformAtomics
{
    static_assert(sizeof(int8)  == sizeof(char), "...");
    // ... 一组 static_assert 验证 ABI 一致 ...

    static FORCEINLINE int8 InterlockedIncrement(volatile int8* Value)
    {
        return (int8)::_InterlockedExchangeAdd8((char*)Value, 1) + 1;
    }
    static FORCEINLINE int16 InterlockedIncrement(volatile int16* Value)
    {
        return (int16)::_InterlockedIncrement16((short*)Value);
    }
    static FORCEINLINE int32 InterlockedIncrement(volatile int32* Value)
    {
        return (int32)::_InterlockedIncrement((long*)Value);
    }
    static FORCEINLINE int64 InterlockedIncrement(volatile int64* Value)
    {
        #if PLATFORM_64BITS
            return (int64)::_InterlockedIncrement64((long long*)Value);
        #else
            // 32 位 Win 没有 64 位原子,用 CMPXCHG8B 模拟
            for (;;) { /* ... */ }
        #endif
    }
    // ... 类似的 InterlockedDecrement / InterlockedAdd / InterlockedExchange ...
    // ... InterlockedCompareExchange / InterlockedCompareExchangePointer ...
};
```

`::_InterlockedIncrement` 是 MSVC 编译器内置(`<intrin.h>`),映射到 `lock xadd` 之类的 x86 指令。Clang / GCC 在 Windows 上有同名 builtin。

### Step 5 — typedef 别名(这一步在哪做?)

**关键问题**:`FPlatformAtomics`(用户面用的名字)在哪里被定义为 `FWindowsPlatformAtomics`?

答案:**在每个平台特化文件的末尾**。看 Windows 的:

```cpp
// Windows/WindowsPlatformAtomics.h(文件末尾,5.7.3 实际内容)
typedef FWindowsPlatformAtomics FPlatformAtomics;
```

(具体行号每节奏稍有变化,但这一行**一定**在 WindowsPlatformAtomics.h 末尾。打开看就知道。)

**所以最终的链是**:

```
游戏代码
   ↓ #include "HAL/PlatformAtomics.h"
HAL/PlatformAtomics.h(2 行 include)
   ├─→ #include "GenericPlatform/GenericPlatformAtomics.h"        ── 拉进 FGenericPlatformAtomics
   └─→ #include COMPILED_PLATFORM_HEADER(PlatformAtomics.h)
              展开为 "Windows/WindowsPlatformAtomics.h"
              ├─→ struct FWindowsPlatformAtomics : FGenericPlatformAtomics { ... }
              └─→ typedef FWindowsPlatformAtomics FPlatformAtomics;

游戏代码:
   FPlatformAtomics::InterlockedIncrement(&Counter);
        = FWindowsPlatformAtomics::InterlockedIncrement(&Counter)
        = ::_InterlockedIncrement((long*)&Counter)
        = lock xadd 指令
```

**整条链编译期完成,运行时零开销。**

## 1.1.4 同样的模式:`FPlatformTypes`、`FPlatformMisc`、`FPlatformProcess`...

理解了 Atomics,其它几个 `FPlatformXxx` 是**完全一样**的模式。我们快速过一遍,只看每个的代表 API。

### 1.1.4.1 `FPlatformTypes` — 基础整型 typedef

不用 `int32_t` / `uint64_t`,UE 用自己的 `int32` / `uint64`。这些 typedef 来自:

`GenericPlatform/GenericPlatform.h`:
```cpp
struct FGenericPlatformTypes
{
    typedef unsigned char       uint8;
    typedef unsigned short int  uint16;
    typedef unsigned int        uint32;
    typedef unsigned long long  uint64;
    typedef signed char         int8;
    typedef signed short int    int16;
    typedef signed int          int32;
    typedef signed long long    int64;
    typedef wchar_t             WIDECHAR;
    typedef char                ANSICHAR;
    typedef WIDECHAR            TCHAR;
    typedef long                DWORD;
    // ... ssize_t, size_t, etc.
};
```

`Windows/WindowsPlatform.h:34`:
```cpp
struct FWindowsPlatformTypes : public FGenericPlatformTypes
{
#ifdef _WIN64
    typedef unsigned __int64    SIZE_T;
    typedef __int64             SSIZE_T;
#else
    typedef unsigned long       SIZE_T;
    typedef long                SSIZE_T;
#endif
    // ...
};
typedef FWindowsPlatformTypes FPlatformTypes;
```

**为什么不用 `<cstdint>`**?三个理由:
1. UE 代码量超过 1000 万行,在 cstdint 普及之前就有了。改起来代价太大。
2. 跨平台 typedef 的具体宽度由 UE 自己掌控,不依赖编译器(虽然实际值通常一样)。
3. UE 想保留诸如 `TCHAR`(wchar_t 或 utf8char)这种**不在 std 里**的别名。

实战:**项目代码无脑用 UE 风格的 `int32`、`uint64`、`TCHAR`**。和引擎 API 互操作时,std 整型会让你的代码满屏 `static_cast`。

### 1.1.4.2 `FPlatformMisc` — 杂项 API 的"百宝袋"

声明骨架(`HAL/PlatformMisc.h:1-7`):
```cpp
#include "CoreTypes.h"
#include "GenericPlatform/GenericPlatformMisc.h"
#include COMPILED_PLATFORM_HEADER(PlatformMisc.h)
#include "ProfilingDebugging/CpuProfilerTrace.h"
```

API 例子(从 Generic 和 Windows 实现里挑):

```cpp
// 调试相关
FPlatformMisc::DebugBreak();                              // 触发 __debugbreak() / SIGTRAP
FPlatformMisc::IsDebuggerPresent();                       // IsDebuggerPresent()
FPlatformMisc::PromptForRemoteDebugging(...);

// 系统信息
FPlatformMisc::NumberOfCores();                           // 物理核心数
FPlatformMisc::NumberOfCoresIncludingHyperthreads();      // 含 SMT 的核心数
FPlatformMisc::NumberOfWorkerThreadsToSpawn();            // 留给 TaskGraph 启动几个 worker
FPlatformMisc::GetCPUVendor();                            // "GenuineIntel" / "AuthenticAMD" / ...
FPlatformMisc::GetCPUBrand();
FPlatformMisc::GetCPUInfo();

// 退出与崩溃
FPlatformMisc::RequestExit(bool Force);                   // 优雅退出
FPlatformMisc::RaiseException(uint32 ExceptionCode);

// 用户级 GUID / 时间戳
FPlatformMisc::CreateGuid(FGuid& Result);

// 命名事件(profiling 钩子,前面 §0.3 提到的 SCOPED_NAMED_EVENT 走这个)
FPlatformMisc::BeginNamedEvent(const FColor& Color, const TCHAR* Text);
FPlatformMisc::EndNamedEvent();

// 文件路径相关
FPlatformMisc::EngineDir();
FPlatformMisc::ProjectDir();

// 平台特定
FPlatformMisc::HasPlatformFeature(const TCHAR* FeatureName);
FPlatformMisc::SetEnvironmentVar(const TCHAR* VariableName, const TCHAR* Value);
```

**RTS 视角下你最常用的**:
- `NumberOfWorkerThreadsToSpawn` — 你需要决定 Mass Processor 并行度时
- `BeginNamedEvent` / `EndNamedEvent` — 已经被 `SCOPED_NAMED_EVENT` 包了一层,Insights 能看到
- `RequestExit` — 服务器正常退出时用
- `EngineDir` / `ProjectDir` — 加载配置 / 写日志时

### 1.1.4.3 `FPlatformProcess` — 线程、库、进程

API 例子:
```cpp
// 线程
FPlatformProcess::CreateThread(...);          // 创建本地线程
FPlatformProcess::Sleep(float Seconds);
FPlatformProcess::SleepNoStats(float Seconds);
FPlatformProcess::SleepInfinite();
FPlatformProcess::YieldThread();

// TLS(Thread Local Storage)
FPlatformProcess::AllocTlsSlot();             // 申请一个 TLS slot
FPlatformProcess::SetTlsValue(uint32 Slot, void* Value);
FPlatformProcess::GetTlsValue(uint32 Slot);
FPlatformProcess::FreeTlsSlot(uint32 Slot);

// 进程
FPlatformProcess::CreateProc(...);            // 启动子进程
FPlatformProcess::WaitForProc(FProcHandle);
FPlatformProcess::IsProcRunning(FProcHandle);
FPlatformProcess::GetCurrentProcessId();

// 动态库
FPlatformProcess::GetDllHandle(const TCHAR* Filename);
FPlatformProcess::GetDllExport(void* DllHandle, const TCHAR* ProcName);

// 同步原语(老接口)
FPlatformProcess::CreateSynchEvent(...);
FPlatformProcess::CreateRunnableThread();
```

**Mass 视角下的关键 API**:
- TLS 接口被分配器用来做 thread-local 缓存(§1.5 详讲)
- `CreateThread` 是 `FRunnableThread` 的底层(§5.1 讲并发时回到这里)
- `Sleep` / `YieldThread` 是 worker 线程让出 CPU 的姿势

### 1.1.4.4 `FPlatformTime` — 高精度计时

```cpp
double Now = FPlatformTime::Seconds();           // 高精度浮点秒,自启动累计
uint64 Cycles = FPlatformTime::Cycles64();       // 高精度计数器(QueryPerformanceCounter / rdtsc)
FPlatformTime::ToSeconds64(Cycles);
FPlatformTime::ToMilliseconds(Cycles);

FDateTime SystemTime = FPlatformTime::SystemTime();
FDateTime UtcTime = FPlatformTime::UtcTime();
```

`FPlatformTime::Seconds()` 在 Windows 上底层是 `QueryPerformanceCounter` + `QueryPerformanceFrequency`,在 Linux 是 `clock_gettime(CLOCK_MONOTONIC, ...)`。

**Stat / Trace 系统几乎所有计时都走这里**。前面 §0.3 看到的 `SCOPE_CYCLE_COUNTER` 内部就是 `FPlatformTime::Cycles64()` 的差。

### 1.1.4.5 `FPlatformMath` — SIMD 友好的数学

```cpp
FPlatformMath::Sqrt(x);           // 编译期已选 SSE / NEON 指令
FPlatformMath::InvSqrt(x);        // 反平方根
FPlatformMath::Sin(x);
FPlatformMath::Floor(x);
FPlatformMath::CountLeadingZeros(uint32 Value);  // _BitScanReverse / __builtin_clz
FPlatformMath::CeilLogTwo(uint32 Arg);
```

**Mass 视角下这非常重要**:Movement Processor、LOD 距离计算、Steering 都会大量用这些。`FPlatformMath` 在 Win64 上是 `FWindowsPlatformMath`(继承 `FGenericPlatformMath`),会优先使用 SSE2 / SSE4 / AVX intrinsics。

### 1.1.4.6 `FPlatformTLS` — TLS 的薄封装

`FPlatformProcess::*Tls*` 系列已经够用,但 5.x 还有 `FPlatformTLS`(`HAL/PlatformTLS.h`)作为更纯粹的 TLS 接口:

```cpp
uint32 Slot = FPlatformTLS::AllocTlsSlot();
FPlatformTLS::SetTlsValue(Slot, MyData);
void* Data = FPlatformTLS::GetTlsValue(Slot);
FPlatformTLS::FreeTlsSlot(Slot);
```

**Mass 与分配器都重度使用 TLS**(§1.5 详讲)。

### 1.1.4.7 `FPlatformMemory` — OS 级内存接口

注意区分:**`FPlatformMemory` 不是分配器**。它是 `FMemory`/`GMalloc` 的**底层支撑**。它提供 OS 级的页分配、内存信息查询:

```cpp
FPlatformMemoryStats Stats = FPlatformMemory::GetStats();
//   Stats.AvailablePhysical / AvailableVirtual / UsedPhysical / UsedVirtual

FPlatformMemoryConstants Const = FPlatformMemory::GetConstants();
//   Const.PageSize, Const.OsAllocationGranularity, Const.TotalPhysical

void* Mem = FPlatformMemory::BinnedAllocFromOS(Size);    // 从 OS 申请大块(VirtualAlloc / mmap)
FPlatformMemory::BinnedFreeToOS(Mem, Size);

// Malloc 系列(只在分配器内部用,游戏代码用 FMemory)
FPlatformMemory::BaseAllocator();                         // 创建当前平台默认分配器
```

`FMemory::Malloc`(§1.2 详讲)实际上是个转发器,转发到 `GMalloc->Malloc`,而 `GMalloc` 内部需要从 OS 拿大块时,调用 `FPlatformMemory::BinnedAllocFromOS`。

## 1.1.5 编译期注入的关键宏:`PLATFORM_HEADER_NAME` 与 `OVERRIDE_PLATFORM_HEADER_NAME`

`PLATFORM_HEADER_NAME` 怎么被注入?是 **UBT 在生成编译命令时给出的**。

UBT 的 `Engine/Source/Programs/UnrealBuildTool/Configuration/UEBuildPlatform.cs` 等地方,根据当前 Target 平台,在编译命令上加 `/D PLATFORM_HEADER_NAME=Windows` 之类的定义。

但 5.x 还有一个微妙的"覆盖"宏 `OVERRIDE_PLATFORM_HEADER_NAME`:

- 一些主机厂商(任天堂、索尼、微软)出于"保密命名"的原因,把自己的平台头文件放在 NDA 仓库里。它们用 `OVERRIDE_PLATFORM_HEADER_NAME` 这个间接,让 PC SDK 编译时拉对应的头文件,而厂商 SDK 编译时拉机密头文件。
- 你不会直接用到这个,但你看到 `Engine/Source/Runtime/Core/Public` 下时不时有以 NDA 平台名字命名的占位头,就是这套机制的余响。

## 1.1.6 RTS 视角下的实战姿势

### 1.1.6.1 跨平台代码的纪律

**永远不写 `#ifdef _WIN32`**(除了真正写平台特化层时)。代之以 UE 风格:

```cpp
// 正确
double T = FPlatformTime::Seconds();
uint32 Slot = FPlatformTLS::AllocTlsSlot();

// 错(项目里出现这种就退回返修)
#ifdef _WIN32
    LARGE_INTEGER Counter;
    QueryPerformanceCounter(&Counter);
    // ...
#endif
```

### 1.1.6.2 `PLATFORM_*` 宏的合法使用场景

`PLATFORM_WINDOWS` / `PLATFORM_LINUX` / `PLATFORM_64BITS` 这些**值为 0 或 1 的宏**(注意:不是 `defined`!):

```cpp
// PLATFORM_WINDOWS 总是被定义,值为 0 或 1
#if PLATFORM_WINDOWS
    // Windows 特定路径
#elif PLATFORM_LINUX
    // Linux 特定路径
#endif

// 用 PLATFORM_64BITS 选择数据宽度
#if PLATFORM_64BITS
    typedef int64 FOffset;
#else
    typedef int32 FOffset;
#endif
```

**为什么是 0/1 而不是 `#ifdef`**?因为你可以在表达式里用:

```cpp
const SIZE_T Bytes = 1 * 1024 * (PLATFORM_64BITS ? 1024 : 256);  // 一个常量表达式
```

### 1.1.6.3 RTS 项目里你会真正用到 `PLATFORM_*` 的场景

很少。99% 用 `FPlatform*` 就够了。少数需要的:

- **判断 Editor vs 主机**:`#if PLATFORM_DESKTOP` 是常用的"我有键鼠 + 大内存"场景
- **SIMD 开关**:`#if PLATFORM_ENABLE_VECTORINTRINSICS` 后才能用 `_mm_*` intrinsics
- **平台特定优化**:某个 Mass Processor 在 PS5 上可以用平台原生 API 加速,这种才平台分支

## 1.1.7 重要纪律变化:UE Atomics 已 deprecated,改用 `std::atomic<T>`

打开 `GenericPlatform/GenericPlatformAtomics.h:19-23`,顶部那段注释你必须读:

```cpp
/**
* DEPRECATED! UE atomics are not maintained and potentially will be physically deprecated. 
* Use std::atomic<T> for new code
*/
struct FGenericPlatformAtomics
```

这是 5.x 的**重大纪律变化**。原因:

1. C++11 之后,`std::atomic<T>` 已经是行业标准。
2. UE 自家 atomics 长期由 Epic 维护,跨平台正确性测试覆盖度不如 std。
3. 现代编译器对 `std::atomic` 的优化(尤其是 RMW 操作的 codegen)往往更好。

**对你 RTS 项目的影响**:

| 旧写法 | 新写法 |
|---|---|
| `FPlatformAtomics::InterlockedIncrement(&Counter)` | `++atomic`(`std::atomic<int32>`)|
| `FPlatformAtomics::InterlockedCompareExchange(&V, New, Old)` | `atomic.compare_exchange_strong(Old, New)` |
| `volatile int32 Counter` 配 `FPlatformAtomics` | `std::atomic<int32> Counter` |

**唯一例外**:你确实在改 Engine 内部代码,且周围代码全部用 `FPlatformAtomics`,保持一致即可(§0.2.6 改 Engine 的纪律 — "和周围代码风格一致"压倒一切)。

**Mass 项目代码,无脑 `std::atomic`**。

## 1.1.8 怎么阅读这些文件:实操技巧

### 技巧 1 — 一个 `FPlatformXxx::Yyy()` 的实际定义在哪?

VA / ReSharper "Goto Implementation"(`Alt+G`):
- 它会跳到 `FWindowsPlatformXxx::Yyy()` 的定义
- 不要被 `Generic` 的注释代码迷惑(那是 `#if 0` 区段)

如果 IDE 跳错了,手动:打开 `Engine/Source/Runtime/Core/Public/Windows/WindowsPlatform<Xxx>.h`,搜函数名。

### 技巧 2 — 看预处理后的真实 include 链

VS 项目里:右键 .cpp → Properties → C/C++ → Preprocessor → Generate Preprocessed File → Yes (/P)。编译会出 `.i` 文件,你能**亲眼**看到 `#include COMPILED_PLATFORM_HEADER(PlatformAtomics.h)` 在你机器上展开后是什么。

### 技巧 3 — 验证某个 PLATFORM_xxx 宏的值

在 .cpp 里加一行 `static_assert`:
```cpp
static_assert(PLATFORM_64BITS == 1, "Build is 64-bit");
static_assert(PLATFORM_WINDOWS == 1, "Building for Windows");
```
编译失败的时候你就知道宏值是什么。

### 技巧 4 — 大胆点开 Generic 实现看默认行为

新人容易忘记 Generic 类**也能跑** —— 至少能跑。某些不重要的 API,Windows / Linux 都没重写,直接用 Generic 的实现。看 Generic 的源码能让你了解"这个 API 的最低保障是什么"。

## 1.1.9 改 Engine 时的纪律(平台抽象层尤其重要)

如果你**真**需要在平台抽象层加东西(典型场景:你想给 Mass 加一个"原子 64 位 SIMD CAS"的平台特化优化),纪律:

### 1.1.9.1 必须在 Generic 类先加签名

哪怕 Generic 类的实现是空的或弱的,**先在 Generic 加签名**。这样:
- 其它平台移植时知道要实现什么
- 跨平台测试不会因为某平台少了实现而崩

```cpp
// GenericPlatform/GenericPlatformAtomics.h
struct FGenericPlatformAtomics
{
    // ...
    
    // 你加的:128 位原子 CAS
    static FORCEINLINE bool InterlockedCompareExchange128(
        volatile FInt128* Dest, FInt128 Exchange, FInt128* Comparand)
    {
        // Generic fallback(慢但能跑,最坏情况下用 CritSection)
        // ... 实现 ...
    }
};
```

### 1.1.9.2 然后在每个目标平台特化里重写

```cpp
// Windows/WindowsPlatformAtomics.h
struct FWindowsPlatformAtomics : public FGenericPlatformAtomics
{
    // 重写,用 _InterlockedCompareExchange128
    static FORCEINLINE bool InterlockedCompareExchange128(...)
    {
        return ::_InterlockedCompareExchange128(...) == 1;
    }
};
```

### 1.1.9.3 不要忘了 typedef 别名

每个平台特化文件**末尾**的 `typedef FXxxPlatformAtomics FPlatformAtomics` 不能漏。否则你新加的 API 通过 `FPlatformAtomics::Yyy()` 调不到。

### 1.1.9.4 测试矩阵

最少在 Windows + Linux 两套都测一遍。如果你团队没有 Linux 环境,至少跑一次 Linux 服务器编译(`Build.bat MyRTSServer Linux Development`),让 cross-toolchain 编译捕获你 Linux 特化里的 typo。

## 1.1.10 与 Mass 重构的对照思考

### (1)Mass 的并行调度高度依赖 TLS

Mass Processor 的并行执行(`ParallelForEachEntityChunk`)在每个 worker 线程上跑。这些 worker 线程要访问的 chunk 数据在不同 NUMA 节点。TLS 是 Mass 性能的关键支撑 — 分配器(§1.5)、Stats 系统、CPU profiling scope 都靠 TLS 避免锁。

**纪律**:RTS 项目自己写 Processor 时,**永远不要**用 `__thread` 或 `thread_local` 关键字 — 用 UE 的 `FPlatformTLS` 接口,跨平台一致,而且可以被 Insights 抓到。

### (2)`FPlatformMath` 的 SIMD 是 Movement Processor 的命脉

数万单位的 `Velocity += Acceleration * dt` 这种最热循环,如果你写成 `for (auto& V : Velocities) V.X += A.X * dt; V.Y += A.Y * dt;` 这种 scalar 形式,GCC/MSVC 通常**不会**自动向量化(因为 alias 不确定)。

正确姿势:**调 `FPlatformMath` 的批量 API**,或者**手写 SSE/NEON intrinsics**,或者**用 `VectorRegister` 抽象**(`Math/UnrealMathSSE.h` 提供跨平台 4-wide SIMD 抽象)。

后面 §17 / §20 讲到 Movement Processor 实现时会详细演示。

### (3)atomic 操作密集场景(Mass 的命令队列)

如果你的 Mass 命令队列用单生产者-多消费者 lock-free 队列,你会大量用 `std::atomic<T>` 的 `compare_exchange` / `fetch_add`。**直接用 std**,别走 `FPlatformAtomics`(已 deprecated)。

### (4)RTS 的 deterministic 模式与 `FPlatformMath`

如果 RTS 走 lockstep + determinism 路线,**必须**保证不同平台浮点结果一致。`FPlatformMath::Sqrt` 在不同平台底层 SIMD 指令不同,精度可能差 1 ULP。这一点 §26.2 详讲,这里只埋下伏笔:**determinism 与 SIMD 是天敌,别图快也别图懒**。

### 实操提示

- **打开 IDE 跟一遍**:在你项目某段代码加一行 `FPlatformAtomics::InterlockedIncrement(&X);`,F12 跳进去,VA 应该带你到 `WindowsPlatformAtomics.h`。如果跳错(到 `GenericPlatformAtomics.h` 那个 `#if 0` 块),说明 VA 索引没建好,重新 Generate Project Files。
