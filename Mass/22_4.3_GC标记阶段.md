# §4.3 标记阶段(Mark)— Token Stream 与多线程 Reachability

> **本节地图**:模块一第 4 章高潮。GC 算法的"灵魂"在标记阶段 —— **从 root 出发,走遍整个 UObject 引用图,标记所有 reachable 的对象**。这一步如果做得慢,游戏就卡;做得快,数十万对象的 GC 也只是几毫秒级的事。
>
> UE 的标记阶段有两个性能武器:
>
> 1. **Token Stream / Reference Schema** — UClass 在反射注册时,把"哪些字段是 UObject 引用、它们在对象里的字节偏移"**编译成一段紧凑字节码**。GC 标记直接执行字节码,不走反射查询。
> 2. **多线程并行 + Work Stealing** — 标记任务被切成 work block,多个 GC worker 线程并行处理,空闲 worker 偷别人的活儿。
>
> 这一节我们把这两个机制拆开。
>
> **预备知识**:§4.1 引用姿势、§4.2 GC 调度、§3.2 GUObjectArray、§1.5 TLS / 多线程。
>
> **读完之后你能做到**:
> - 解释为什么 UE GC 比"逐个 deref UObject 调虚函数"快几十倍
> - 看到 UClass 上的 `AssembleReferenceTokenStream` 知道它在生成什么
> - 理解 5.x 的 `FReferenceToken` 与老 `FGCReferenceTokenStream` 的差异
> - 调试"GC 漏标记导致对象悬空"或"GC 误标记导致泄漏"
> - 在 RTS 视角下评估 50K Mass entity 在 GC mark 阶段的零代价

## 4.3.1 浅入:朴素 mark 为什么慢

考虑最朴素的 mark 实现:

```cpp
// 朴素版
void Mark(UObject* Obj)
{
    if (Obj->IsMarked()) return;
    Obj->Mark();
    
    // 怎么知道 Obj 引用了哪些对象?反射查!
    UClass* C = Obj->GetClass();
    for (FProperty* P = C->RefLink; P; P = P->NextRef)
    {
        if (P->IsA<FObjectProperty>())
        {
            UObject* Ref = *(UObject**)((uint8*)Obj + P->Offset);
            Mark(Ref);    // 递归
        }
        // Array / Map / Set 各种特殊处理...
    }
}
```

每个对象:
- 一次反射 RTTI 检查(`IsA`)
- 一次虚函数调用(可能)
- 一次字段地址计算
- 一次 cache miss(对象数据在堆上散落)

50 万 UObject × 每对象 5 个引用 = 250 万次操作。每次 50-100 ns → **250 万 × 100 ns = 250 ms**。一帧时间 16.6 ms,光 mark 就 250 ms?**完全不能接受**。

UE 的解决方案分两步:**预编译 schema** + **并行执行**。

## 4.3.2 Token Stream / GC Schema —— 反射数据的"GC 字节码"

### 4.3.2.1 设计动机

每个 UClass 的"哪些字段是 UObject 引用、偏移在哪"是**编译期就知道**的(反射数据)。GC mark 时**没必要每次反射查** —— 一次查完,把结果**预编译成一个紧凑列表**,后续直接用。

简化思路:

```cpp
// UClass 反射注册末尾,编译 schema
UClass::AssembleReferenceTokenStream()
{
    for (FProperty* P = RefLink; P; P = P->NextRef)
    {
        if (P->IsA<FObjectProperty>())
        {
            ReferenceSchema.AddObjectRef(P->Offset);     // 记录"偏移 X 处有个 UObject*"
        }
        else if (P->IsA<FArrayProperty>())
        {
            ReferenceSchema.AddArrayOfObjects(P->Offset, ElementSize);
        }
        // ...
    }
    // 包含父类 schema(继承的 UPROPERTY 字段)
    if (SuperStruct) ReferenceSchema.Append(SuperStruct->ReferenceSchema);
}
```

GC mark 时只走 schema:

```cpp
void Mark(UObject* Obj)
{
    UClass* C = Obj->GetClass();
    for (auto& Entry : C->ReferenceSchema)
    {
        switch (Entry.Type)
        {
            case Object:
                Mark(*(UObject**)((uint8*)Obj + Entry.Offset));
                break;
            case ArrayOfObjects:
                ProcessArray(Obj, Entry.Offset, Entry.ElementSize);
                break;
            // ...
        }
    }
}
```

**反射查询消失**!每个字段处理 ~5-10 ns。

### 4.3.2.2 5.x 的实现:`FReferenceToken` + Schema

5.x 重构了 GC,引入 `FReferenceToken`(`Engine/Source/Runtime/CoreUObject/Public/UObject/ReferenceToken.h:43`):

```cpp
enum class EReferenceTokenType
{
    None,
    Object,             // 普通 UObject*
    GCObject,           // FGCObject* (§4.1.6)
    VerseCell,          // Verse 语言对象
    GCObjectInfo,
    GCVerseCellInfo,
    Barrier = 1 << 3,   // 增量 GC barrier 标记
};

struct FReferenceToken
{
    uint64 EncodedBits;     // 高 61 位:指针 / 偏移;低 3 位:类型 tag

    explicit FReferenceToken(const UObject* Object)
        : EncodedBits(BitCast<uint64>(Object) | (uint64)EReferenceTokenType::Object) {}
    
    EReferenceTokenType GetType() const;
    UObject* AsObject() const;
    FGCObject* AsGCObject() const;
    // ...
};
```

**关键观察**:`FReferenceToken` 是**指针 + 3 位类型 tag** 的 64 位 packed 表达。指针 8 字节对齐,低 3 位永远 0,被复用为类型 tag。

每个 UClass 持有一组**reference schema entries**,描述"对象内偏移 X 处有 类型 Y 的引用"。GC mark 时按 schema 遍历对象内存,把数据按 type tag 解释为 UObject*/FGCObject*/Verse cell。

### 4.3.2.3 Schema 的 entries

5.x 没用单一字节流,而是用结构化的 **schema** 描述每个 UStruct 的引用布局:

```cpp
// Class.h:4021(简化)
struct FReferenceSchema
{
    TArray<FSchemaEntry> Entries;
    // 每个 entry 描述一个引用字段:类型 + 偏移 + 元素大小(数组用)
};

class UClass : public UStruct
{
    FReferenceSchema ReferenceSchema;     // 5.x 实际字段名可能不同,语义一致
    // ...
};
```

每个 schema entry 大致表达:
- "我的 Object 在偏移 0x18,直接 UObject 引用"
- "我的 Outer 在偏移 0x10,UObject 引用"
- "我的 Children 数组在偏移 0x40,是 TArray<UObject*>,元素大小 8"
- "我的 Components 在偏移 0x80,是 TMap<FName, UActorComponent*>"
- ...

GC 走这些 entries,对每种类型用不同处理函数。**所有"反射"决策都在 AssembleReferenceTokenStream 里一次性做完**,运行时只剩"按 schema 解释 + 标记"。

### 4.3.2.4 `AssembleReferenceTokenStream` 何时被调

`Class.h:4563`:

```cpp
COREUOBJECT_API void AssembleReferenceTokenStream(bool bForce = false);
```

调用时机:
- UClass 反射注册末尾(§2.2.3.4 提到的 `ConstructUClass` 后期)
- BP 类编译完成时
- HotReload / Live Coding 重新生成 UClass 时

**一次性开销**(类的字段一定后,schema 编译完不再变)。50K UClass × 一次 ~10 μs = ~500 ms 启动开销。但**只在启动期**,游戏运行不再花。

### 4.3.2.5 Class.h:3970 `AssembleReferenceTokenStreams`(批量)

```cpp
static COREUOBJECT_API void AssembleReferenceTokenStreams();
```

引擎启动后期,所有 UClass 注册完了,**一次性**给所有 UClass 编译 schema。这是 PreInit 阶段的固定步骤。

## 4.3.3 `TFastReferenceCollector` —— 多线程 mark 引擎

`Engine/Source/Runtime/CoreUObject/Public/UObject/FastReferenceCollector.h:905`:

```cpp
template <typename ProcessorType, typename CollectorType>
class TFastReferenceCollector : public FGCInternals
{
public:
    TFastReferenceCollector(ProcessorType& InProcessor) : Processor(InProcessor) {}

    void ProcessObjectArray(FWorkerContext& Context)
    {
        Context.bDidWork = true;
        // ...
        
        // 1. 处理 root 引用(GGCObjectReferencer 等)
        Context.ReferencingObject = FGCObject::GGCObjectReferencer;
        for (UObject** InitialReference : Context.InitialNativeReferences)
        {
            Dispatcher.HandleKillableReference(*InitialReference, EMemberlessId::InitialReference, EOrigin::Other);
        }
        
        // 2. 主循环:扫初始对象 + 沿引用扩展
        TConstArrayView<UObject*> CurrentObjects = Context.InitialObjects;
        while (true)
        {
            ProcessObjects(Dispatcher, CurrentObjects);
            
            if (Processor.IsTimeLimitExceeded()) {
                /* 增量 GC:把剩余工作存起来,下帧继续 */
                return;
            }
            
            // 3. 拿下一批工作
            FWorkBlock* Block = RemainingObjects.PopFullBlock<Options>();
            if (!Block) {
                if constexpr (bIsParallel) {
                    // 4. 没活了 → 偷别人的活
                    switch (StealWork(...)) {
                        case ELoot::Block:  break;     // 偷到一整 block
                        case ELoot::Nothing: break;    // 大家都干完了
                    }
                }
            }
            CurrentObjects = Block->GetObjects();
        }
    }
};
```

### 4.3.3.1 模板参数 + EGCOptions

```cpp
template <typename ProcessorType, typename CollectorType>
```

模板特化让 mark 引擎能根据**模式**生成最优代码。`EGCOptions` 标志(简化):

```cpp
enum class EGCOptions
{
    None = 0,
    Parallel = 1 << 0,            // 并行模式
    AutogenerateSchemas = 1 << 1, // 自动生成 schema(5.x 实验)
    // ...
};
```

`bIsParallel = EnumHasAllFlags(Options, EGCOptions::Parallel)` —— **编译期常量**。`if constexpr (bIsParallel)` 在不同实例化下生成不同代码(单线程版本不带 work stealing 开销,并行版本带)。

### 4.3.3.2 `FWorkBlock` —— 工作切片

每个 GC worker 线程拿一个 `FWorkBlock`(若干个待处理对象的列表)。Block 容量固定(`FWorkBlock::ObjectCapacity`,通常几十到一百个)。

切片粒度:**block 太小 → 偷工开销大,block 太大 → 负载不均**。Epic 实测调到合适的中庸值。

### 4.3.3.3 Work Stealing(从其它线程偷活)

```cpp
case ELoot::Block:    // 偷到一整 block
case ELoot::Partial:  // 偷到部分
case ELoot::Nothing:  // 大家都没活了
```

`StealWork` 实现 **work-stealing 调度**:线程 A 干完自己的 → 检查其它 worker 队列 → 拿走半个 block / 整个 block。这让 **mark 阶段几乎完美负载均衡**,即使初始分配不均。

学术界经典算法(Cilk-style work stealing),UE 工业实现。

## 4.3.4 标记阶段的完整时序

```
CollectGarbage(KeepFlags, bFullPurge=false) (§4.2)
  ↓
GReachabilityState.CollectGarbage:
  ↓
  阶段 1:Marking
  │
  ├─ 1.1 收集 Initial References(root)
  │     - GGCObjectReferencer (FGCObject 系)
  │     - RootSet 标记的 UObject(AddToRoot 的)
  │     - CDO(每个 UClass 的 ClassDefaultObject)
  │     - TStrongObjectPtr 持有的对象(通过 RefCount > 0)
  │
  ├─ 1.2 启动多个 GC worker 线程
  │     - GC.AllowParallelGC = 1 → 并行
  │     - 默认 worker 数 = NumberOfWorkerThreads(物理核 - 1)
  │
  ├─ 1.3 每个 worker 跑 TFastReferenceCollector::ProcessObjectArray
  │     循环:
  │       - 取一个对象 Obj
  │       - 沿 Obj->Class->ReferenceSchema 走每条 entry
  │         - Object entry:Mark(*ptr) + 推到 BFS 队列
  │         - Array entry:Mark 数组每元素
  │         - GCObject entry:调 FGCObject::AddReferencedObjects
  │       - 时间到了(增量)→ 暂停,下帧继续
  │
  ├─ 1.4 Work stealing 平衡负载
  │
  └─ 1.5 所有 worker 干完 → mark 阶段结束
  
  ↓ Mark 完成,所有 reachable 对象有 EInternalObjectFlags 标记
  ↓
  阶段 2:确定 Unreachable 对象集
  │
  ├─ 扫 GUObjectArray
  ├─ 凡是没有 reachable 标记的 → 标记 EInternalObjectFlags::Unreachable
  └─ 这些对象可被 sweep 阶段清理
  
  ↓
  阶段 3:Sweep(§4.4 详讲)
```

### 4.3.4.1 `Mark` 操作的实际内容

每次给一个对象加 reachable 标记:

```cpp
void Mark(UObject* Obj)
{
    FUObjectItem& Item = GUObjectArray.ObjectToObjectItem(Obj);
    
    // 原子 CAS 设置 reachable bit(防止两个 worker 同时标记)
    if (Item.SetFlagsAndCheck(EInternalObjectFlags::ReachableInCluster, ...))
    {
        // 我是第一个标记这个对象的 → 加入待处理队列
        WorkBlock.Push(Obj);
    }
    // 其它 worker 已标 → 跳过
}
```

**关键**:**flag 写在 `FUObjectItem` 而不是 `UObject` 本身**。因为:
- FUObjectItem 紧凑(§3.2),atomic 操作的 cache line 友好
- 原子 CAS 在 FUObjectItem 的 64 位字上
- UObject 可能在堆上散落,直接写慢

回头看 §3.2 的 `FlagsAndRefCount union` 设计 —— 这就是它存在的原因。

## 4.3.5 `AddReferencedObjects` 的桥接

§4.1.10 提过 `UObject::AddReferencedObjects` 是静态虚函数,子类可重写。GC mark 时**也会调它**(除了走 schema):

```cpp
// 简化伪代码
void Mark(UObject* Obj)
{
    UClass* C = Obj->GetClass();
    
    // 1. 走 schema(快路径,99% 情况)
    for (auto& Entry : C->ReferenceSchema)
    {
        ProcessSchemaEntry(Obj, Entry);
    }
    
    // 2. 调虚函数 AddReferencedObjects(慢路径,但允许自定义)
    if (C->HasAddReferencedObjectsOverride())
    {
        C->AddReferencedObjects(Obj, Collector);
    }
}
```

`HasAddReferencedObjectsOverride` 在反射注册时检测子类是否重写了这个静态函数。如果重写了,在每次 mark 时调用。

**实战**:99% 你不需要重写 AddReferencedObjects(UPROPERTY 自动覆盖)。仅当你有非 UPROPERTY 但需 GC 知道的字段时才重写。

## 4.3.6 GC Cluster —— 减小 mark 集合的优化

某些对象群组**生命同步**(同生共死):比如一个 SkeletalMesh 资产 + 它内含的所有 LOD 数据 + 所有材质引用。

UE 引入"**GC Cluster**"(§3.2.3 提到的 `FUObjectItem.ClusterRootIndex`):

```cpp
// 创建 cluster
UMyAsset* Root = ...;
TArray<UObject*> Members = { ... };       // 这些对象与 Root 同生死
Root->AddObjectsToCluster(Members);
```

效果:
- mark 阶段**只标记 cluster root**,内部所有 members 免标
- cluster root unreachable → 整个 cluster 一次性回收
- mark 集合从"几十万对象"压缩到"几千 cluster + 少数独立对象"

**性能改善**:对象多的项目能让 mark 加速 2-5 倍。引擎默认给 SkeletalMesh、Material、Animation Sequence 等大资产创建 cluster。

### 4.3.6.1 Cluster 的代价

- Cluster 一旦建立,**内部对象不能被独立回收**(只能整 cluster 销毁)
- Cluster 之间引用要谨慎(可能导致 cluster 锁定)

**实战**:你 RTS 项目通常不需要手动建 cluster。引擎自动建的够用。

## 4.3.7 增量 mark 的"barrier"

5.x 增量 mark 把工作拆多帧。期间游戏代码可能**新建 UObject 引用**:

```
Frame N: GC mark 进行中,已标记 Obj1 reachable
Frame N: 游戏代码:Obj1->NewField = Obj2;     ← Obj2 是新引用
Frame N+1: GC mark 继续,但 Obj1 已经处理过
           ↓ Obj2 没被标记 reachable 吗?会被错误回收!
```

UE 的解法:**写屏障(write barrier)**。`TObjectPtr::operator=` / 其它赋值操作在增量 mark 期间会触发 hook:

```cpp
// 简化
TObjectPtr<T>& operator=(T* NewValue)
{
    if (GIsIncrementalReachabilityPending)
    {
        // 标记 NewValue 为 reachable(防止它被漏掉)
        if (NewValue) MarkReachable(NewValue);
    }
    Ptr = NewValue;
    return *this;
}
```

`Barrier` 是 `EReferenceTokenType::Barrier`(§4.3.2.2)枚举值之一,标记"这个引用是 mark 期间产生的,需要 barrier 处理"。

**对你的代码的实际影响**:几乎为零。`TObjectPtr` 自动处理。**但** 5.x 之前如果你大量用裸 `UObject*` 字段(且 UPROPERTY 标记),增量 mark 可能漏 — 这是 5.x 强推 `TObjectPtr` 的另一个原因。

## 4.3.9 RTS / Mass 视角下的纪律

### (1)Mass 在 mark 阶段几乎零成本

50K Mass entity = 0 个新 UObject 加入 GUObjectArray。**mark 完全不扫这 50K 数据**。

只有 Mass 内部的 UObject(几百个 Subsystem / Processor / Trait CDO / Asset)被 mark。这是 Mass 性能的根基。

### (2)Fragment 持 UObject 的 schema 影响

```cpp
USTRUCT()
struct FUnitFragment : public FMassFragment
{
    UPROPERTY()
    TObjectPtr<UStaticMesh> Mesh;        // ← UScriptStruct 也有 schema
};
```

USTRUCT 也参与 `AssembleReferenceTokenStream`。Mass 在 chunk 上扫 Fragment 时,通过 schema 知道 "哪几个字段是 UObject 引用,扫它们"。

**但**:Mass entity **不是** UObject,GC 不直接扫它。Mass 内部有自己的"扫 fragment 的 UObject 引用"路径,与 GC 协作。

### (3)避免 Subsystem 持有大量 UObject

```cpp
UCLASS()
class URTSObjectPool : public UWorldSubsystem
{
    UPROPERTY()
    TArray<TObjectPtr<AActor>> AllActors;    // ★ GC 每次 mark 都扫这数组
};
```

如果 `AllActors.Num() == 100000`,每次 mark 扫 100K 元素 ≈ 几毫秒。频繁 GC 时累计。

**解法**:
- 用 `TWeakObjectPtr` 数组(GC 不扫弱引用)
- 用 cluster(把它们打包,只扫 root)
- 用 Mass entity(完全脱离 UObject)

### (4)Subsystem 数量保持精简

每个 Subsystem 是一个 UObject。RTS 项目不要有几十个 Subsystem,5-10 个足够。每个负责清晰子领域。

## 4.3.10 改 Engine:自定义 schema entry 类型(罕见)

如果你 RTS 有"非 UObject 但 GC 要扫"的特殊数据(典型:Mass 自己的 entity reference 系统),Mass 内部已经做了一套定制 schema。

读 `Engine/Source/Runtime/MassEntity/Private/MassArchetypeData.cpp` 你能看到 Mass 怎么:
1. 给每个 Fragment 类型注册 GC 扫描函数
2. mark 阶段被 GC 调,扫 chunk 内所有 entity 的 fragment 引用
3. 把这些 reference 推给 Collector

**普通 RTS 项目不要改 GC schema 自己**。Mass 已经做了你需要的桥接。
