## 1.6.1 浅入:`TArray<int32>` 实际占多少字节?

来看一行最常见的代码:

```cpp
TArray<int32> MyArray;
```

`MyArray` 这个**对象本身**(放在栈上 / Fragment 里 / 类成员里)占多少字节?

答案不是"取决于元素数量"—— `MyArray` 这个对象的大小是**编译期确定的、固定的**。元素是动态分配在堆上的,跟 `MyArray` 对象本身的内存布局无关。

打开 `Engine/Source/Runtime/Core/Public/Containers/Array.h:668`:

```cpp
// Array.h:668
template<typename InElementType, typename InAllocatorType>
class TArray
{
public:
    using SizeType      = typename InAllocatorType::SizeType;
    using ElementType   = InElementType;
    using AllocatorType = InAllocatorType;
    
    // ... 大量方法 ...

protected:
    ElementAllocatorType AllocatorInstance;    // 持有"分配状态"的对象
    SizeType             ArrayNum;             // 当前元素数
    SizeType             ArrayMax;             // 当前容量
};
```

三个数据成员:
- `AllocatorInstance` —— 分配器**对象**(具体大小看 Allocator 类型)
- `ArrayNum` —— 当前已用的元素个数
- `ArrayMax` —— 已分配的容量

对于 `TArray<int32>`(默认用 `FDefaultAllocator`):
- `AllocatorInstance` 是 `TSizedHeapAllocator<32>::ForAnyElementType`,内部就一个 `void* Data` 指针(8 字节)
- `ArrayNum`、`ArrayMax` 是 `int32`(默认 `IndexSize=32`,SizeType=int32),各 4 字节

总计:**8 + 4 + 4 = 16 字节**(64 位平台)。

也就是说,`TArray<int32> MyArray;` 这个对象在栈上占 16 字节,不论你将来 Push 1 个还是 100 万个元素。元素本身在堆上由 AllocatorInstance 管理。

**这点对 Mass Fragment 设计极其重要** —— Fragment 内放 `TArray<int32>`,每个 entity 立刻 +16 字节。50K entity 就是 800KB。再加上每个 array 在堆上的元素分配,内存压力很快显著。

## 1.6.2 `FDefaultAllocator` —— 默认堆分配器

### 1.6.2.1 别名链

`Engine/Source/Runtime/Core/Public/Containers/ContainerAllocationPolicies.h`:

```cpp
// :830-831
template <int IndexSize>
class TSizedDefaultAllocator : public TSizedHeapAllocator<IndexSize> {
    typedef TSizedHeapAllocator<IndexSize> Typedef;
};
using FDefaultAllocator = TSizedDefaultAllocator<32>;

// :857
using FHeapAllocator = TSizedHeapAllocator<32>;
```

所以:
- `FDefaultAllocator` = `TSizedDefaultAllocator<32>` ← 继承 `TSizedHeapAllocator<32>`(空继承,等价)
- `FHeapAllocator` = `TSizedHeapAllocator<32>`

两者基本是同一个东西。**在 99% 的代码里 `FDefaultAllocator` 就是 `FHeapAllocator`**。区分主要给某些扩展场景用(如 `TSizedNonshrinkingAllocator`)。

### 1.6.2.2 `TSizedHeapAllocator` 的本质

简化版伪代码:

```cpp
template <int IndexSize, typename BaseMallocType = FMemory>
class TSizedHeapAllocator
{
public:
    using SizeType = typename TBitsToSizeType<IndexSize>::Type;   // int32 或 int64
    
    enum { NeedsElementType = false };           // 不需要元素类型(byte-blob 风格)
    enum { RequireRangeCheck = true };
    
    class ForAnyElementType
    {
        void* Data = nullptr;                    // 唯一字段:指向堆内存
        
    public:
        void* GetAllocation() const { return Data; }
        bool  HasAllocation() const { return !!Data; }
        
        void ResizeAllocation(SizeType CurrentNum, SizeType NewMax, SIZE_T BytesPerElement)
        {
            if (Data || NewMax)
            {
                Data = BaseMallocType::Realloc(Data, NewMax * BytesPerElement, ...);
            }
        }
        // 还有 CalculateSlackReserve / Grow / Shrink 等
    };
};
```

关键观察:
- **存储就是一个 `void* Data`**,8 字节(64 位)
- `ResizeAllocation` 走 `FMemory::Realloc`(走 GMalloc,§1.2 讲过)
- IndexSize=32 → SizeType=int32,IndexSize=64 → SizeType=int64

### 1.6.2.3 IndexSize 的选择(`TArray64`)

UE 还提供:

```cpp
template <typename T>
using TArray64 = TArray<T, TSizedDefaultAllocator<64>>;
```

当你 array 元素**可能超过 21 亿(int32 上限)** 时,改用 `TArray64<T>`:

```cpp
TArray<uint8>     SmallBuffer;          // 最多 ~2G 元素
TArray64<uint8>   HugeBuffer;           // 最多 ~9E 元素(64 位)
```

代价:`SizeType` 是 int64,Array 本身从 16 字节涨到 24 字节。**99% 用 32**,只有真要存 GB 级 byte buffer 时用 64。

### 1.6.2.4 容量增长策略

`TSizedHeapAllocator::CalculateSlackGrow` 等是容量增长曲线的实现。简化:

```cpp
// 当 Add 一个元素超出 ArrayMax 时,新容量 = max(NewNum, OldMax + GROW_FACTOR(OldMax))
SizeType CalculateSlackGrow(SizeType NewNum, SizeType OldMax, SIZE_T BytesPerElement)
{
    // 大致按 1.375 倍(AMD64 黄金比) + QuantizeSize 调整
    SizeType Grown = ...;
    // 走 FMemory::QuantizeSize 让分配器替我们对齐到 BinSize
    return CalcQuantizedGrowth(Grown, BytesPerElement);
}
```

**关键设计**:增长后会调 `FMemory::QuantizeSize`(§1.2.8),根据分配器实际给的 bin 大小拓展容量。这意味着:

```cpp
TArray<int32> A;
A.Add(1); A.Add(2); A.Add(3); A.Add(4);
A.Add(5);   // 此时可能 capacity 变 12,而不是 8 —— Binned 把 32 字节请求给到 48
```

不要假设增长曲线是严格 ×1.5 或 ×2。**实际容量永远 ≥ 你想要的**,且对齐到分配器最小浪费的 bin 边界。

## 1.6.3 `TInlineAllocator<N>` —— 局部 inline + 备用堆

### 1.6.3.1 设计动机

`TArray<int32>` 哪怕只放 4 个元素也得 alloc 一次堆。如果你的代码大量出现"短 array",这种小堆 alloc 累积很恐怖。

`TInlineAllocator<N>` 解决:**前 N 个元素直接放在 Array 对象自己的内存里(inline),超过 N 才 alloc 堆**。

### 1.6.3.2 用法

```cpp
// 短 buffer:32 个元素以内不堆分配
TArray<int32, TInlineAllocator<32>> ShortBuffer;
ShortBuffer.Add(1);   // 写到栈上,无 alloc
// ...
ShortBuffer.SetNum(40);   // 超过 32 → 转移到堆,对象本身的 inline 存储不再用
```

**典型场景**:函数内临时 buffer。

### 1.6.3.3 `TSizedInlineAllocator` 的内存布局

`ContainerAllocationPolicies.h:892`:

```cpp
template <uint32 NumInlineElements, int IndexSize, typename SecondaryAllocator = FDefaultAllocator>
class TSizedInlineAllocator
{
public:
    using SizeType = typename TBitsToSizeType<IndexSize>::Type;
    
    template<typename ElementType>
    class ForElementType
    {
        // 关键:
        TTypeCompatibleBytes<ElementType> InlineData[NumInlineElements];   // 栈/对象 内的 inline 存储
        SecondaryAllocator::ForElementType<ElementType> SecondaryAllocation; // 备用堆 allocator
    public:
        ElementType* GetAllocation() const
        {
            return SecondaryAllocation.HasAllocation()
                ? SecondaryAllocation.GetAllocation()
                : (ElementType*)InlineData;     // 默认返回 inline,只有溢出时返回 heap
        }
        
        void ResizeAllocation(SizeType OldNum, SizeType NewMax, SIZE_T BytesPerElement)
        {
            if (NewMax <= NumInlineElements && !SecondaryAllocation.HasAllocation())
            {
                // 全在 inline,无需 heap
                return;
            }
            // 超出 inline 容量 → 从 inline 迁移到 heap(或扩 heap)
            SecondaryAllocation.ResizeAllocation(OldNum, NewMax, BytesPerElement);
            // 第一次溢出时把 inline data 拷到 heap
            // ...
        }
    };
};

// :1073
template <uint32 NumInlineElements, typename SecondaryAllocator = FDefaultAllocator>
using TInlineAllocator = TSizedInlineAllocator<NumInlineElements, 32, SecondaryAllocator>;
```

### 1.6.3.4 内存大小算账

`TArray<int32, TInlineAllocator<32>>` 的对象大小:

| 字段 | 大小 |
|---|---|
| `InlineData[32]`(32 × `int32`) | 128 字节 |
| `SecondaryAllocation`(`void*`) | 8 字节 |
| `ArrayNum` | 4 字节 |
| `ArrayMax` | 4 字节 |
| 总计 | **144 字节** |

注意这是**对象本身**的大小。如果你把它放在 Fragment 里:

```cpp
USTRUCT()
struct FMyMassFragment
{
    UPROPERTY()
    int32 SomeData;                                        // 4 字节
    
    TArray<int32, TInlineAllocator<32>> Buffer;            // 144 字节!
};
```

50K entity × 144 字节 = **7.2 MB**,无论你的 Buffer 实际有没有用。

### 1.6.3.5 `TInlineAllocator` 的恰当用法

✅ **函数内临时 buffer**:
```cpp
void MyFunc()
{
    TArray<int32, TInlineAllocator<32>> Temp;
    Temp.Add(1);
    Temp.Add(2);
    // 函数返回时栈上 inline 数据自动析构,无堆 alloc 全程
}
```

✅ **Processor 成员变量**:
```cpp
class UMyMassProcessor : public UMassProcessor
{
    TArray<FMassEntityHandle, TInlineAllocator<256>> ProcessingBuffer;
    
    void Execute(...)
    {
        ProcessingBuffer.Reset();   // 不释放堆
        // ... 填充 ProcessingBuffer ...
    }
};
```

❌ **绝不放在 Fragment 里**:每 entity 144 字节就是 7MB 起步。改用其它方案(下面 1.6.10 详讲)。

### 1.6.3.6 NumInlineElements 怎么选

经验值:
- **绝大多数容器实际只有 0-N 个元素 → 选 N**,溢出走 heap 兜底
- 太小 → 频繁溢出,inline 起不到作用
- 太大 → 对象膨胀,栈/Fragment 不堪重负

实战做法:**先写 `TArray<...>` 不带 inline,跑 profile,看 99% 情况下实际容量是多少,再加 `TInlineAllocator<那个值>`**。

## 1.6.4 `TFixedAllocator<N>` —— 纯 inline,不允许溢出

`ContainerAllocationPolicies.h:1275`:

```cpp
template <uint32 NumInlineElements>
class TFixedAllocator
{
public:
    template<typename ElementType>
    class ForElementType
    {
        TTypeCompatibleBytes<ElementType> InlineData[NumInlineElements];
        // 注意:**没有** SecondaryAllocation
    public:
        void ResizeAllocation(SizeType CurrentNum, SizeType NewMax, SIZE_T BytesPerElement)
        {
            // 关键:超出立刻 check 失败
            check(NewMax >= 0 && NewMax <= NumInlineElements);
        }
    };
};
```

### 1.6.4.1 用法与代价

```cpp
TArray<int32, TFixedAllocator<8>> FixedArray;
FixedArray.Add(1);
// ...
FixedArray.SetNum(9);   // CHECK FAIL — 越界,游戏崩溃
```

`TFixedAllocator` 是"硬上限"。一旦超过,**`check` 失败,游戏崩溃**。

### 1.6.4.2 何时该选

✅ **能力受限的预算严格场景**:你**确定**最多 N 个元素,超过就是 bug,不应该兜底。
✅ **Fragment 里的"小数组"**:`TArray<int32, TFixedAllocator<4>>` 对象大小 = 16 字节(不带 secondary 8 字节指针),Fragment 紧凑。

### 1.6.4.3 与 TInlineAllocator 的对比

| | `TInlineAllocator<N>` | `TFixedAllocator<N>` |
|---|---|---|
| inline 容量 | N | N |
| 溢出行为 | 转 heap | check fail |
| 对象大小 | inline + secondary 指针 | 仅 inline |
| Fragment 友好 | 需评估 | ★ 友好(无指针,无堆) |

**Mass Fragment 里如果非要用数组,优先 `TFixedAllocator<N>`**(确定有上限),否则改用 `TArray` 然后挪出 Fragment(把数组放在共享 Subsystem 里,用 entity index 做 lookup)。

## 1.6.5 `FMemStackAllocator` —— Bump allocator

### 1.6.5.1 设计

`Engine/Source/Runtime/Core/Public/Containers/MemStack.h` 提供 `FMemStack`,这是个**线程局部的 bump allocator**:

- 一段连续大内存区
- `Alloc(N)` 仅推进一个指针,几乎零开销
- `Free` **不存在** —— 整段以"作用域"为单位释放(`FMemMark` 标记保留点,析构时 rewind 到那)

`FMemStackAllocator` 把这个分配器接到容器:

```cpp
TArray<int32, TMemStackAllocator<>> MyArray;
// 底层从 FMemStack::Get() 申请,作用域结束后整段释放
```

### 1.6.5.2 用法(经典)

```cpp
void ProcessFrame()
{
    FMemMark Mark(FMemStack::Get());   // 标记
    
    {
        TArray<int32, TMemStackAllocator<>> TempA;
        TArray<float, TMemStackAllocator<>> TempB;
        // ... 用 ...
    }
    
    // Mark 析构时,自动把这一段 MemStack rewind,所有上面分配的内存"瞬间释放"
}
```

### 1.6.5.3 适用场景

- 一帧内的临时数据
- 大量小分配 + 一次性释放
- 渲染线程中的命令 buffer 构造

### 1.6.5.4 不适用场景

- 跨帧持久数据(rewind 会破坏)
- 跨线程共享(MemStack 是 thread local)
- 元素需要析构(MemStack rewind 不调析构函数 —— 仅 POD 安全)

**Mass 场景下 FMemStack 用得不多**(Mass 自己管 chunk 内存)。但渲染剥离(§25)处理 ISMC 上传 buffer 时可能用到。

## 1.6.6 `TMap` / `TSet` / `TSparseArray` 的内存模型

### 1.6.6.1 `TSparseArray` —— 稀疏数组

`Engine/Source/Runtime/Core/Public/Containers/SparseArray.h`。它是 TMap / TSet 的底层。

**核心思想**:

```cpp
class TSparseArray
{
    TArray<TElementOrFreeListLink<T>> Data;       // 紧凑的元素数组
    TBitArray<>                       AllocationFlags;  // 哪些 index 是有效的
    int32                             FirstFreeIndex;   // 空洞 freelist 头
};
```

- `Data` 是**密集紧凑的**(元素 + 空洞混在一起),但 index 稳定
- `AllocationFlags` 用 1 bit 标记每个 index 是否在用
- 删除元素**不**移动其它元素,只标记位 + 串入 freelist
- 添加元素优先重用 freelist,没有 freelist 才扩容

**优势**:
- Index 永久稳定(对应 Mass `FMassEntityHandle.Index` 的设计原型)
- 删除 O(1)
- 遍历用 BitArray 跳过空洞

### 1.6.6.2 `TSet`

`Containers/Set.h`。在 SparseArray 之上加一个 hash 表:

```cpp
class TSet<T>
{
    TSparseArray<TSetElement<T>>       Elements;     // 元素存这里
    TInlineAllocator<1, FDefaultAllocator>  Hash;    // 哈希桶,每桶指向 Elements 里的一个 index
};
```

### 1.6.6.3 `TMap`

`Containers/Map.h`。**`TMap` 内部就是 `TSet<TPair<K, V>>`** + 几个语法糖。

```cpp
template <typename K, typename V>
class TMap
{
    TSet<TPair<K, V>, ...> Pairs;
};
```

### 1.6.6.4 `TMap` 的开销估算

```cpp
TMap<int32, int32> M;
M.Add(1, 100);
```

发生了什么?
1. `TSet::Add` → `TSparseArray::Add(TPair<int, int>)` 
2. SparseArray 没空 → 扩 `Data` 数组(走 FDefaultAllocator,堆 alloc)
3. 计算 `GetTypeHash(1)`,找哈希桶
4. 桶(`TInlineAllocator<1>`)第一次溢出 → 堆 alloc
5. 桶链表加节点

**初次 Add 会触发 2 次小堆 alloc**(SparseArray data + Hash bucket)。这就是为什么 `TMap` 比 `TArray` 贵得多。

### 1.6.6.5 `TMap` 在 Fragment 里?极不推荐

```cpp
// 不要这么做
USTRUCT()
struct FMyFragment
{
    TMap<int32, float> ScoreByID;       // ← 每 entity 一个独立 TMap,巨贵
};
```

50K entity × TMap 对象本身约 56 字节 + 至少 2 次堆 alloc(典型 64 + 16 = 80 字节)= **每 entity ~140 字节** + 100K 次小 alloc。Mass 立刻爆炸。

正确做法:把 ScoreByID 提到 World Subsystem,key 用 `FMassEntityHandle`。

## 1.6.7 `FString` 的真相 —— **没有 SSO**

很多人(包括我以前)以为 FString 有 SSO(Small String Optimization,小字符串放在对象本身,长字符串才 heap)。**5.7 实测:并没有**。

### 1.6.7.1 源码验证

`Engine/Source/Runtime/Core/Public/Containers/UnrealString.h.inl:54-69`:

```cpp
class UE_STRING_CLASS    // 宏展开为 FString
{
public:
    using AllocatorType = TSizedDefaultAllocator<32>;
    using ElementType   = UE_STRING_CHARTYPE;     // TCHAR

private:
    /** Array holding the character data */
    typedef TArray<ElementType, AllocatorType> DataType;
    DataType Data;                                  // ← 整个 FString 就是一个 TArray<TCHAR>
public:
    // ...
};
```

**FString 的内部就是一个 `TArray<TCHAR, FDefaultAllocator>`**。没有 inline 字符存储。任何非空字符串**必然**有一次堆 alloc(给 TArray 的 Data)。

### 1.6.7.2 内存占用

`FString` 对象本身:**16 字节**(同 `TArray<TCHAR>` 的 sizeof = `void*` 8 + `int32` 4 + `int32` 4)。

加上字符堆:
- 空 FString:16 字节(无堆)
- "hello"(5 字符):16 + heap 12-32 字节(5 TCHAR + null + 容量 round-up)≈ 28-48 字节
- 长字符串:16 + heap N

### 1.6.7.3 为什么不做 SSO?

合理猜测(Epic 没公开说过):
1. **FName 已经服务大多数"短字符串场景"**(下一章详讲),FString 主要给真的"动态长字符串"用,SSO 收益有限。
2. **TCHAR 在 Win 上是 wchar_t = 2 字节**,SSO 阈值要更宽,设计复杂。
3. **历史包袱**:FString 接口稳定 20+ 年,改内部布局风险高。

### 1.6.7.4 对你的 Mass / RTS 项目的影响

❌ **不要在 Fragment 里放 `FString`**:
```cpp
USTRUCT()
struct FMyFragment
{
    UPROPERTY()
    FString DisplayName;     // 16 + 至少 16 字节堆 = ~32 字节 / entity,且每个都是独立 alloc
};
```

50K entity × 一次堆 alloc = 50K 次小 alloc 在 Spawn 时,给 Binned 一个不必要的压力。**改用 `FName`**(下一章 §2 详讲)—— `FName` 是个 8 字节的 ID,字符串内容存在全局 NamePool,极快。

✅ **`FString` 适合**:
- 玩家输入的内容(聊天、命名、UI 文本)
- 错误信息、日志
- 动态拼接的命令行 / URL

## 1.6.8 `Empty` / `Reset` / `Shrink` / `Reserve` —— 容量语义差异

容器接口里这几个方法**很容易混淆**。Mass 性能优化时必须分清。

### 1.6.8.1 语义对照

| 方法 | ArrayNum | ArrayMax | 析构现有元素 | 释放堆 |
|---|---|---|---|---|
| `Empty()` | → 0 | → 0(默认)/ slack | ✓ | ✓(默认) |
| `Empty(slack)` | → 0 | → slack | ✓ | 视 slack 而定 |
| `Reset()` | → 0 | 不变 | ✓ | ✗(保留容量) |
| `Reset(slack)` | → 0 | ≥ slack | ✓ | 视情况 |
| `Reserve(N)` | 不变 | ≥ N | ✗ | 视情况 |
| `Shrink()` | 不变 | → ArrayNum | ✗ | ✓(若 Max>Num) |
| `SetNum(N)` | → N | ≥ N | 析构超过 N 的 / 默认构造新增 | 视情况 |

### 1.6.8.2 性能含义

```cpp
// 帧内反复使用的 buffer
TArray<int32> Buffer;

// ━━━━━━━ 慢 ━━━━━━━
for (int frame = 0; frame < N; ++frame)
{
    Buffer.Empty();          // 释放堆!下一帧重新 alloc
    Buffer.Reserve(1000);
    // ... 填充 ...
}

// ━━━━━━━ 快 ━━━━━━━
Buffer.Reserve(1000);
for (int frame = 0; frame < N; ++frame)
{
    Buffer.Reset();          // 容量保留,无 alloc
    // ... 填充 ...
}
```

**Mass Processor 内的临时 buffer 必须用 `Reset`,不要 `Empty`**。前者跨帧零分配,后者每帧一次 alloc/free。

### 1.6.8.3 `SetNum` 的两个变体

```cpp
A.SetNum(10);                              // 把 N 调到 10。如果原来 < 10,默认构造填充;> 10,析构尾部
A.SetNum(10, EAllowShrinking::No);         // 同上,但即使原来 Max > 10 也不缩容
```

`EAllowShrinking::Yes` 是默认。如果你**确定**很快又要扩,加 `EAllowShrinking::No` 避免反复扩缩。

## 1.6.9 `MoveTemp` 与移动语义

```cpp
TArray<int32> A;
A.Add(1); A.Add(2); A.Add(3);

TArray<int32> B = A;              // ← 拷贝!alloc + Memcpy
TArray<int32> C = MoveTemp(A);    // ← 移动!仅 swap 指针/字段,无 alloc
// 此时 A 处于 "valid but empty" 状态
```

`MoveTemp` 等价于 `std::move`。UE 早期用自家命名,5.x 起也支持 `std::move`(它们等价)。

**Mass 视角**:Fragment 间数据迁移、命令对象传递,**永远用 `MoveTemp`**。绝大多数 UE API 也支持移动:

```cpp
TArray<int32> Buffer = ...;
GetSubsystem()->SubmitData(MoveTemp(Buffer));   // 把 Buffer 整个交出去,无拷贝
// 之后 Buffer 是 empty TArray,你用它 Add 是合法的
```

## 1.6.10 Mass / RTS 视角下的容器选型纪律

这是本节的实战压轴。

### (1)Fragment 内**禁用**的容器

```
❌ TArray<T>                        每 entity 16 字节 + 堆 alloc
❌ TArray<T, TInlineAllocator<N>>   每 entity 大量 inline 字节
❌ TMap<K, V> / TSet<T>             每 entity 多次堆 alloc
❌ FString                          每 entity 一次堆 alloc
❌ TSharedPtr / TUniquePtr 包裹的容器  同上
```

### (2)Fragment 内**允许**的容器

```
✅ TArray<T, TFixedAllocator<N>>    无 secondary 指针,纯 inline,严格上限
✅ FName                             8 字节 ID,无堆
✅ TStaticArray<T, N>                C 数组的薄封装,纯栈
✅ POD 结构体                        所有原生类型 + UPROPERTY
```

### (3)Processor 内的临时 buffer 选型

```cpp
class UMyProcessor : public UMassProcessor
{
    // 选项 A:成员变量,跨帧复用
    TArray<int32> PerFrameBuffer;
    
    // 选项 B:成员 + InlineAllocator(典型大小已知)
    TArray<int32, TInlineAllocator<64>> SmallBuffer;
    
    void Execute(...)
    {
        PerFrameBuffer.Reset();    // 仅清零 Num,不释放
        // ...
    }
};
```

### (4)需要"按 entity index 查找"的数据,放 Subsystem

```cpp
// ❌ 不要在 Fragment 里
USTRUCT() struct FBadFragment {
    TMap<EElementType, int32> ResourceCounts;    // 每 entity 一个 map
};

// ✅ 改放在 Subsystem
class URTSResourceSubsystem : public UWorldSubsystem
{
    TSparseArray<TStaticArray<int32, EnumCount>> ResourcesByEntityIndex;
    // 用 entity.Index 作为外部 index,稳定
};
```

### (5)字符串永远用 FName

`FString DisplayName` → `FName UnitTypeName`。前者每 entity 一次堆 alloc,后者全局共享 8 字节 ID。下一章会拆 FName 的全部细节。

### 实操 2 — Bench 不同 Allocator

```cpp
static FAutoConsoleCommand CmdBenchContainers(TEXT("rts.BenchContainers"),
    TEXT("Compare container alloc strategies"),
    FConsoleCommandDelegate::CreateLambda([]()
    {
        const int32 N = 10000, IterCount = 10000;
        
        auto Bench = [&](const TCHAR* Name, auto Func)
        {
            double Start = FPlatformTime::Seconds();
            for (int32 i = 0; i < IterCount; ++i) Func();
            double Elapsed = FPlatformTime::Seconds() - Start;
            UE_LOG(LogTemp, Display, TEXT("%s: %.2fms"), Name, Elapsed * 1000.0);
        };
        
        // 每次 alloc 新 TArray
        Bench(TEXT("TArray (heap)"), [&]() {
            TArray<int32> A;
            for (int32 i = 0; i < 32; ++i) A.Add(i);
        });
        
        // TInlineAllocator,inline 容量足够
        Bench(TEXT("TArray<TInlineAllocator<32>>"), [&]() {
            TArray<int32, TInlineAllocator<32>> A;
            for (int32 i = 0; i < 32; ++i) A.Add(i);
        });
        
        // TFixedAllocator
        Bench(TEXT("TArray<TFixedAllocator<32>>"), [&]() {
            TArray<int32, TFixedAllocator<32>> A;
            for (int32 i = 0; i < 32; ++i) A.Add(i);
        });
    }));
```

跑这个命令。第二、第三个应该比第一个快**几倍到一个数量级**。建立"inline allocator 真的省 alloc"的肌肉记忆。

## 1.6.13 改 Engine:写自己的 Allocator policy(罕见)

如果你 RTS 项目里有个非常特殊的容器需求(典型:TArray 的元素来自一个**自管理的 chunk pool**),可以写自己的 Allocator policy:

```cpp
template <uint32 ChunkSize>
class TMyChunkAllocator
{
public:
    using SizeType = int32;
    enum { NeedsElementType = true };
    enum { RequireRangeCheck = true };
    
    template<typename ElementType>
    class ForElementType
    {
        ElementType* Data = nullptr;
        // ... 实现 ResizeAllocation / GetAllocation / ... 等接口 ...
    };
};

// 用法
TArray<FMyType, TMyChunkAllocator<128>> MyArr;
```

要实现的接口在 `ContainerAllocationPolicies.h:9` 注释里有清单。**99% 项目用不到**,但你看 Mass 内部有自己的 chunk allocator 时(`Engine/Source/Runtime/MassEntity/Public/MassArchetypeData.h` 等),会发现是这种思路的延伸。
