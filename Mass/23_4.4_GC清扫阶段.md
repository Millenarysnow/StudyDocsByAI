# §4.4 清扫阶段(Sweep)— 销毁的状态机

> **本节地图**:模块一第 4 章第 4 节。§4.3 标记完成后,所有不可达对象都有了 `EInternalObjectFlags::Unreachable` 标记。这一节看 GC 怎么把它们**销毁**。
>
> 销毁不是一步完成的。UE 用一个**两阶段状态机** —— `BeginDestroy` 启动异步清理(网络断开、文件关闭、GPU 资源释放),等所有异步操作就绪 (`IsReadyForFinishDestroy`),才调 `FinishDestroy` 真正释放内存。这种设计让"对象销毁"不阻塞 GC 主流程。
>
> 本节也澄清 5.x 的术语变化:**`MarkPendingKill` 已被 `MarkAsGarbage` 替代**,"Garbage Elimination" 是 5.x 的新名字。
>
> **预备知识**:§4.1 / §4.2 / §4.3。
>
> **读完之后你能做到**:
> - 画出从 `Unreachable` 标记到内存释放的完整销毁状态机
> - 区分 `MarkAsGarbage` / `BeginDestroy` / `FinishDestroy` 三个时机
> - 在自定义 UObject 子类正确重写 `BeginDestroy` / `FinishDestroy`
> - 知道 `IsReadyForFinishDestroy` 异步等待的典型用例(GPU、网络、IO)
> - 在 RTS 视角下评估单位"快速死亡"的销毁路径

---

## 4.4.1 浅入:为什么不能直接 free 内存

GC mark 完成后,假如简单粗暴一行 `FMemory::Free(Obj)` 释放就完事 —— 不行,有几个问题:

1. **对象可能持有 OS 资源**:文件句柄、socket、GPU 资源。直接 free 内存,这些资源泄漏。
2. **对象可能在异步操作中**:等 IO、等渲染线程、等网络。直接 free 会让异步回调访问已释放内存。
3. **C++ 析构函数有逻辑**:基类 / 字段析构需要按正确顺序跑。
4. **GUObjectArray 入口要清理**:`InternalIndex` 必须从 GUObjectArray 移除。

UE 的解法:**两阶段销毁**。

```
对象被标记 Unreachable
   ↓
ConditionalBeginDestroy:调 BeginDestroy 虚函数
   ↓ (子类做"启动异步清理"的事)
   │
   │ 等待...
   │
   ↓
IsReadyForFinishDestroy 返回 true(异步操作完成)
   ↓
ConditionalFinishDestroy:调 FinishDestroy 虚函数
   ↓
真正调析构函数,释放内存,从 GUObjectArray 移除
```

每个"等待"都让 GC 不阻塞,继续干别的活儿。

## 4.4.2 阶段 1:`BeginDestroy`

`Engine/Source/Runtime/CoreUObject/Public/UObject/Object.h:366`:

```cpp
COREUOBJECT_API virtual void BeginDestroy();
```

GC 通过 `ConditionalBeginDestroy`(Object.h:1183)调到它。简化:

```cpp
bool UObject::ConditionalBeginDestroy()
{
    if (HasAnyFlags(RF_BeginDestroyed)) return false;    // 已经调过了
    
    SetFlags(RF_BeginDestroyed);
    BeginDestroy();      // 你的代码在这里跑
    return true;
}
```

`RF_BeginDestroyed` flag 防止重入。

### 4.4.2.1 你应该在 BeginDestroy 里做什么

```cpp
void UMyComp::BeginDestroy()
{
    Super::BeginDestroy();
    
    // ✅ 启动异步清理(关键:不要等待完成)
    if (RenderResourceFence)
    {
        RenderResourceFence->BeginFence();   // 让渲染线程释放 GPU 资源
    }
    
    if (NetConnection)
    {
        NetConnection->Close();              // 启动网络断开
    }
    
    if (FileWriter)
    {
        FileWriter->FlushAsync();            // 启动文件刷盘
    }
    
    // ✅ 注销监听器、回调
    GetWorld()->OnTickDispatch.RemoveAll(this);
    
    // ❌ 不要释放裸内存(留给 FinishDestroy)
    // ❌ 不要 delete 子对象(GC 会处理)
    // ❌ 不要等待异步操作(用 IsReadyForFinishDestroy)
}
```

**纪律**:`BeginDestroy` 只**启动**清理流程,不等待。

### 4.4.2.2 为什么必须调 `Super::BeginDestroy()`

UObject 基类的 `BeginDestroy` 实现做关键事:
- 通知监听器(`FCoreUObjectDelegates::OnObjectPreSave` 等)
- 解除 outer 链
- 标记 internal flags

漏掉 `Super::BeginDestroy()` 会让对象处于半破不破状态。

## 4.4.3 异步等待:`IsReadyForFinishDestroy`

`Object.h:373`:

```cpp
virtual bool IsReadyForFinishDestroy() { return true; }
```

默认返回 true(立即可销毁)。子类可重写让 GC 等异步操作:

```cpp
bool UMyComp::IsReadyForFinishDestroy()
{
    // 等渲染线程的 fence 完成
    if (RenderResourceFence && !RenderResourceFence->IsFenceComplete())
    {
        return false;
    }
    
    // 等文件 IO 完成
    if (FileWriter && FileWriter->IsAsyncBusy())
    {
        return false;
    }
    
    return Super::IsReadyForFinishDestroy();
}
```

GC 会**反复调** `IsReadyForFinishDestroy()`,直到返回 true。如果你的对象**永远不返回 true**,就会卡死整个销毁链。

### 4.4.3.1 经典用例:渲染资源

`UStaticMeshComponent` 等渲染对象的销毁:

```cpp
// 简化伪代码
void UStaticMeshComponent::BeginDestroy()
{
    Super::BeginDestroy();
    
    // 通知渲染线程:停止使用我的 SceneProxy
    BeginReleaseResource(SceneProxy);
    DetachFence.BeginFence();   // 设 fence
}

bool UStaticMeshComponent::IsReadyForFinishDestroy()
{
    return Super::IsReadyForFinishDestroy() && DetachFence.IsFenceComplete();
    // 渲染线程跑过 fence 后,GameThread 这边 fence.IsFenceComplete() 返回 true
}

void UStaticMeshComponent::FinishDestroy()
{
    // 此时 GPU 资源已释放,可以安全 delete SceneProxy
    if (SceneProxy)
    {
        delete SceneProxy;
        SceneProxy = nullptr;
    }
    Super::FinishDestroy();
}
```

`BeginFence` / `IsFenceComplete` 是渲染线程同步原语。GameThread 在销毁这个 component 时,**等渲染线程读完它的 SceneProxy 数据**,才允许 FinishDestroy。

### 4.4.3.2 增量 GC 友好

GC 看到 `IsReadyForFinishDestroy() == false`,**跳过这个对象**,继续处理其它。下一帧再回来检查。这样**单帧不卡** —— 100 个对象等异步完成,GC 可以先销毁 9000 个就绪的,等下次 tick 再回来。

## 4.4.4 阶段 2:`FinishDestroy`

`Object.h:387`:

```cpp
COREUOBJECT_API virtual void FinishDestroy();
```

GC 通过 `ConditionalFinishDestroy`(Object.h:1186)调到。简化:

```cpp
bool UObject::ConditionalFinishDestroy()
{
    if (HasAnyFlags(RF_FinishDestroyed)) return false;
    
    SetFlags(RF_FinishDestroyed);
    FinishDestroy();
    return true;
}
```

### 4.4.4.1 你应该在 FinishDestroy 里做什么

```cpp
void UMyComp::FinishDestroy()
{
    // ✅ 释放 BeginDestroy 启动的资源(此时 IsReady 已 OK)
    if (SceneProxy) { delete SceneProxy; SceneProxy = nullptr; }
    
    // ✅ 释放裸 C++ 内存(non-UObject 持有的)
    if (RawCBuffer) { FMemory::Free(RawCBuffer); RawCBuffer = nullptr; }
    
    // ✅ 必须最后调 Super(警告里说的)
    Super::FinishDestroy();
}
```

**注意 Object.h:385 的注释**:

> "Because properties are destroyed here, Super::FinishDestroy() should always be called at the end of your child class's FinishDestroy() method, rather than at the beginning."

`Super::FinishDestroy()` 会析构基类字段(包括所有 UPROPERTY 字段)。**必须最后调**,否则你的代码可能访问已析构的字段。

### 4.4.4.2 之后会发生什么

`FinishDestroy()` 返回后,GC 调用 C++ 析构函数(虚析构 → 子类析构 → 父类析构),最后:

```cpp
GUObjectArray.FreeUObjectIndex(Object);     // 移除 GUObjectArray 入口
FMemory::Free(Object);                       // 真正释放内存
```

`FreeUObjectIndex` 还会**重置 `FUObjectItem.SerialNumber`**(§3.2.5),让所有指向它的 `TWeakObjectPtr` 自动失效。

## 4.4.5 完整销毁状态机

```
对象 Obj 被 GC mark 阶段确定为 Unreachable
   │
   ↓
GC 进入 IncrementalPurgeGarbage(可拆帧)
   │
   ↓ 第 1 轮:扫所有 Unreachable 对象
   │
   ├─ 调 Obj->ConditionalBeginDestroy()
   │     ↓
   │     设 RF_BeginDestroyed
   │     调 Obj->BeginDestroy()(虚函数,你的代码)
   │
   ↓ 第 2 轮:扫所有 BeginDestroyed 对象,等异步就绪
   │
   ├─ 调 Obj->IsReadyForFinishDestroy()
   │     │
   │     ├─ true → 进 FinishDestroy 阶段
   │     └─ false → 跳过,下一轮再检查
   │
   ↓ 第 3 轮:对就绪对象,调 ConditionalFinishDestroy
   │
   ├─ 调 Obj->ConditionalFinishDestroy()
   │     ↓
   │     设 RF_FinishDestroyed
   │     调 Obj->FinishDestroy()(虚函数,你的代码)
   │     ↓
   │     调 C++ 析构链(virtual ~UMyClass → ~UObject)
   │     ↓
   │     GUObjectArray.FreeUObjectIndex(Obj)
   │     ↓
   │     FMemory::Free(Obj)
   │
   ↓
对象彻底消失
```

**关键**:整个销毁是**多阶段、可拆帧、异步友好**的。增量 GC 让每帧只花 1-2 ms 处理一批对象,游戏主循环不卡。

## 4.4.6 `MarkAsGarbage` —— 显式标记销毁

不等 GC 标记,你也可以**显式**告诉 GC:"这个对象没用了,下次扫请回收它"。

`Engine/Source/Runtime/CoreUObject/Public/UObject/UObjectBaseUtility.h:182`:

```cpp
inline void MarkAsGarbage()
{
    check(!IsRooted());     // 根集对象不能被标 garbage

    AtomicallySetFlags(RF_MirroredGarbage);
    GUObjectArray.IndexToObject(InternalIndex)->SetGarbage();
    
    AtomicallyClearInternalFlags(EInternalObjectFlags::Async);
}
```

设两个 flag:
- `RF_MirroredGarbage`(在 ObjectFlags)
- `EInternalObjectFlags::Garbage`(在 GUObjectArray 的 FUObjectItem)

下一次 GC mark,该对象**直接被视为 unreachable**(即使别处还有引用,在 5.x 默认开启的 Garbage Elimination 模式下),进入销毁流程。

### 4.4.6.1 用法

```cpp
// 显式销毁:不等 GC 自然回收
UMyActor* Actor = ...;
Actor->MarkAsGarbage();
// 之后 Actor 不应再使用
```

### 4.4.6.2 `Actor::Destroy()` 与 `MarkAsGarbage`

`AActor::Destroy()` 不直接 free,而是:
1. 触发 `EndPlay` / `Destroyed` 事件
2. 通知 World 移除 actor
3. 调用 `MarkAsGarbage()`,等 GC 回收

所以你写 `Actor->Destroy()` 后,对象**不立刻消失**,要等 GC 周期。这一段时间里 `Actor` 指针仍合法但 `IsValid(Actor) == false`。

## 4.4.7 5.x 术语变化:`PendingKill` → `Garbage`

UE 4.x 时代的方法名:
- `MarkPendingKill()` → 5.x 改名 `MarkAsGarbage()`
- `IsPendingKill()` → 5.x `IsValid(Obj) == false` 或 `Obj->HasAnyFlags(RF_MirroredGarbage)`
- `RF_PendingKill` → 5.x 的 `RF_MirroredGarbage`

变化原因:
1. 术语清晰:Garbage(垃圾)比 PendingKill(待杀)更标准
2. **行为变化**:5.x 默认启用 "**Garbage Elimination**" — 当某对象被 MarkAsGarbage 后,任何指向它的 `UPROPERTY()` 引用在下次 GC mark 时**自动置为 nullptr**。这让"对象已死,但引用悬空"的状态消失。

`Engine/Source/Runtime/CoreUObject/Public/UObject/UObjectBaseUtility.h:47`:

```cpp
class UObjectBaseUtility : public UObjectBase
{
    /** If true references to objects marked as Garbage will be automatically eliminated by Garbage Collector*/
    static COREUOBJECT_API bool bGarbageEliminationEnabled;
    // ...
};
```

`bGarbageEliminationEnabled` 默认 true。控制台 `gc.GarbageEliminationEnabled` 可关。

### 4.4.7.1 Garbage Elimination 的好处

老 4.x 行为:
```cpp
ObjA->MarkPendingKill();
// ObjB 持有 UPROPERTY() ObjA*
// 此时 ObjB->ObjA 仍然指向 ObjA(虽然 ObjA->IsPendingKill() == true)
// 你必须 if (IsValid(ObjB->ObjA)) 才能安全使用
```

5.x 新行为:
```cpp
ObjA->MarkAsGarbage();
// 下次 GC mark:
//   ObjB 持有的 UPROPERTY() ObjA* 被自动置 nullptr
// ObjB->ObjA == nullptr,直接安全
// IsValid(ObjB->ObjA) == false 等价于 ObjB->ObjA == nullptr
```

**纪律**:
- ✅ 检查 nullptr 即可:`if (ObjB->ObjA)`
- ✅ 用 `IsValid(...)` 兼容:`if (IsValid(ObjB->ObjA))`
- ❌ 老式 `if (!ObjB->ObjA->IsPendingKill())`:**不再正确**,而且 `IsPendingKill` 已 deprecated

## 4.4.8 `IncrementalPurgeGarbage` —— 拆帧销毁

§4.2 提过。这是销毁阶段的"增量执行器"。`GarbageCollection.cpp:4652`:

```cpp
void IncrementalPurgeGarbage(bool bUseTimeLimit, double TimeLimit)
{
    SCOPED_NAMED_EVENT(IncrementalPurgeGarbage, FColor::Red);
    
    double StartTime = FPlatformTime::Seconds();
    
    // 阶段 A:扫所有需要 BeginDestroy 的对象
    while (HasMoreToBeginDestroy())
    {
        ProcessNextBeginDestroy();
        if (bUseTimeLimit && FPlatformTime::Seconds() - StartTime > TimeLimit)
            return;     // 超时,下帧继续
    }
    
    // 阶段 B:等异步就绪后 FinishDestroy
    while (HasMoreToFinishDestroy())
    {
        if (Obj->IsReadyForFinishDestroy())
        {
            ProcessNextFinishDestroy();
        }
        if (bUseTimeLimit && FPlatformTime::Seconds() - StartTime > TimeLimit)
            return;
    }
}
```

引擎 Tick 每帧调一次 `IncrementalPurgeGarbage(true, 0.002)`(2 ms 预算)。两阶段交错执行。

### 4.4.8.1 `bPerformFullPurge`

`CollectGarbage(KeepFlags, /*bFullPurge*/ true)` 会**一次性跑完整个销毁**:

```cpp
// FullPurge 内部
while (HasMoreToBeginDestroy()) { ProcessNextBeginDestroy(); }

// 等所有异步就绪
while (HasMoreToFinishDestroy())
{
    bool bAllReady = true;
    for (Obj : ToFinish)
    {
        if (Obj->IsReadyForFinishDestroy())
            ProcessNextFinishDestroy();
        else
            bAllReady = false;
    }
    if (!bAllReady) FPlatformProcess::Sleep(0.0001);   // 等一会儿再轮询
}
```

**FullPurge 可能阻塞数百毫秒**,因为要等渲染线程 / 文件 IO 完成。仅在关卡切换 / 进程退出时用。

## 4.4.9 销毁 hook 时序

子类完整销毁链的 virtual 调用:

```
GC 决定销毁 Obj
   ↓
Obj->ConditionalBeginDestroy()
   ↓
Obj->BeginDestroy()                  ← 你的子类重写,启动异步清理
   ↓
... 异步操作进行 ...
   ↓
Obj->IsReadyForFinishDestroy()       ← 你的子类返回 false 直到就绪
   ↓ (返回 true)
Obj->ConditionalFinishDestroy()
   ↓
Obj->FinishDestroy()                 ← 你的子类重写,释放资源 + Super 最后调
   ↓
~UMyClass()                          ← 你的析构函数
   ↓
~UMyClass 父类                        ← 自动链
   ↓
~UObject()                           ← 最终
   ↓
GUObjectArray.FreeUObjectIndex
   ↓
FMemory::Free(Memory)
```

10+ 步。每步都是 hook 点。

### 4.4.9.1 `OnDestroy` 委托(蓝图常用)

很多 UObject 子类暴露 `OnDestroy` / `Destroyed` 事件给 BP:

```cpp
// AActor 在 BeginDestroy 阶段触发
DECLARE_MULTICAST_DELEGATE(FActorDestroyedSignature);
FActorDestroyedSignature OnDestroyed;
```

BP 蓝图绑定 `Event Destroyed` 事件接收通知。这是 BP 玩家"对象死亡"逻辑的标准入口。

## 4.4.10 销毁纪律

### 4.4.10.1 在自定义 UObject 子类正确写销毁

```cpp
UCLASS()
class UMyComp : public UObject
{
public:
    int32 NonReflectedBuf[1024];     // 假设这是大量数据
    void* RawHeap = nullptr;
    FAsyncIOHandle FileHandle;
    
    virtual void BeginDestroy() override
    {
        // 启动异步操作,不等待
        if (FileHandle.IsValid())
        {
            FileHandle.BeginClose();
        }
        Super::BeginDestroy();    // 让基类处理 UPROPERTY 字段等
    }
    
    virtual bool IsReadyForFinishDestroy() override
    {
        if (FileHandle.IsValid() && FileHandle.IsAsyncBusy()) return false;
        return Super::IsReadyForFinishDestroy();
    }
    
    virtual void FinishDestroy() override
    {
        // 此时 IsReady 已 true,可以安全释放
        if (RawHeap)
        {
            FMemory::Free(RawHeap);
            RawHeap = nullptr;
        }
        FileHandle.Reset();
        
        Super::FinishDestroy();   // ★ 必须最后!基类析构 UPROPERTY
    }
};
```

### 4.4.10.2 `Actor->Destroy()` vs `Actor->MarkAsGarbage()`

```cpp
// ✅ 标准杀死 actor
SomeActor->Destroy();

// ❌ 不要直接 MarkAsGarbage(跳过 EndPlay 事件)
SomeActor->MarkAsGarbage();   // 错!Actor 系统期待你调 Destroy
```

`Destroy()` 内部会触发 EndPlay / Destroyed 事件,然后调 `MarkAsGarbage`。直接 MarkAsGarbage 跳过事件,游戏逻辑可能出错。

### 4.4.10.3 不要在析构函数里访问其它 UObject

C++ 析构跑到时,**其它 UObject 可能已经死了**(同一 GC 周期内多个对象一起销毁)。访问会崩。

```cpp
// ❌ 危险
UMyComp::~UMyComp()
{
    GetWorld()->RemoveListener(this);   // GetWorld 返回的可能已 Destroyed
}

// ✅ 在 BeginDestroy 做
void UMyComp::BeginDestroy()
{
    if (UWorld* W = GetWorld()) W->RemoveListener(this);
    Super::BeginDestroy();
}
```

`BeginDestroy` 阶段所有 UObject 还活着(`Unreachable` 已标但还没 Begin/Finish),安全访问。

## 4.4.11 RTS / Mass 视角下的销毁

### (1)Mass entity 销毁路径完全不走这套

Mass `FMassEntityManager::DestroyEntity`:
- 直接从 archetype chunk 移除 fragment 数据
- 复用 entity index
- **没有** BeginDestroy / FinishDestroy / GC 协作

50K 单位每帧死 1000:
- Mass:几 μs 完成所有销毁(批量内存移动)
- 假如是 UObject:1000 × `ConditionalBeginDestroy + IsReady + ConditionalFinishDestroy + 析构` ≈ 1000 × 几 μs = 几 ms / 帧

差**几个数量级**。这是 Mass 扛得住数万单位每秒生死的关键。

### (2)RTS "重要 actor" 死亡

英雄 / Boss 是 AActor,死亡走标准路径:

```cpp
void AHero::Die()
{
    // 1. 播放死亡动画
    PlayDeathAnim();
    
    // 2. 触发事件(BP / Subsystem 监听)
    OnDeath.Broadcast(this);
    
    // 3. 延迟销毁(让动画播放)
    GetWorldTimerManager().SetTimer(DeathTimer, this, &AHero::DestroyAfterDeath, 3.0f);
}

void AHero::DestroyAfterDeath()
{
    Destroy();   // 标记 garbage,GC 之后回收
}
```

死亡到内存释放可能 5+ 秒(动画 3 秒 + GC 周期 60 秒 / 增量销毁几帧)。这是正常的,因为单位数量少,延迟不影响性能。

### (3)Subsystem 销毁

`UWorldSubsystem` 在 World 销毁时被 GC:

```cpp
class URTSGameSubsystem : public UWorldSubsystem
{
    virtual void Deinitialize() override
    {
        // World 销毁时调用,先于 BeginDestroy
        // 释放管理的资源
    }
    
    virtual void BeginDestroy() override
    {
        Super::BeginDestroy();
        // 启动异步清理
    }
};
```

`Deinitialize()` 是 Subsystem 专用 hook,**先于** UObject 通用销毁链。这里做"World 还活着但 Subsystem 要走"的清理。

## 4.4.12 调试销毁

### 4.4.12.1 看对象当前销毁阶段

```cpp
EObjectFlags Flags = Obj->GetFlags();

bool bBeginDestroyed = !!(Flags & RF_BeginDestroyed);
bool bFinishDestroyed = !!(Flags & RF_FinishDestroyed);
bool bGarbage = !!(Flags & RF_MirroredGarbage);

UE_LOG(LogTemp, Display, TEXT("Garbage=%d BeginDestroyed=%d FinishDestroyed=%d"),
    bGarbage, bBeginDestroyed, bFinishDestroyed);
```

### 4.4.12.2 诊断"对象死亡卡住"

如果某对象 `IsReadyForFinishDestroy` 永远返回 false → 它和它的引用都不被回收,GC 列表越积越长。

诊断:
1. 检查你的 `IsReadyForFinishDestroy` 实现里所有 fence / async 操作是不是真的会完成
2. 用 `obj list class=YourClass` 看是不是某种类型的对象积累
3. `gc.DumpRefCounts` 看引用计数

### 4.4.12.3 "FinishDestroy 后还崩"

通常是:
- 析构函数里访问了其它 UObject 字段(已被基类析构)
- 漏调 `Super::FinishDestroy()`(基类清理跳过)
- 子类析构在基类前的字段(应该最后调 Super)

### 实操提示

- **看销毁过程**:启动加 `-trace=cpu,gc`,Insights 里看 `BeginDestroy` / `FinishDestroy` scope 时间分布
- **诊断"内存不释放"**:`memreport` 看分配,GC 后看是否减少。如果不减少 → 引用图漏了 / `IsReadyForFinishDestroy` 卡住
