## 1.4.2 共性框架:`TMallocBinnedCommon` 与"小池 + 大池"二分

打开 `Engine/Source/Runtime/Core/Public/HAL/MallocBinned2.h:70` 和 `MallocBinned3.h:92`,你会看到:

```cpp
// MallocBinned2.h:70
class FMallocBinned2 : public TMallocBinnedCommon<FMallocBinned2, UE_MB2_SMALL_POOL_COUNT, UE_MB2_MAX_SMALL_POOL_SIZE>

// MallocBinned3.h:92
class FMallocBinned3 : public TMallocBinnedCommon<FMallocBinned3, UE_MB3_SMALL_POOL_COUNT, UE_MB3_MAX_SMALL_POOL_SIZE>
```

两者**都继承自同一个 CRTP 基类** `TMallocBinnedCommon`(`MallocBinnedCommon.h`)。`TMallocBinnedCommon` 抽出了所有 Binned 系分配器的共性:

- TLS 缓存(thread-local cache,§1.5 详讲)
- "Bundle" 概念(分配批量打包给 TLS,减少跨线程交互)
- BinSize 索引到 PoolIndex 的快速映射表
- 统一的 fork 处理(BINNED2_FORK_SUPPORT)

**关键的二分**(所有 Binned 分配器都遵循这个心智模型):

```
你请求分配 N 字节
  │
  ├─ N <= MAX_SMALL_POOL_SIZE(通常 32KB-16 或 128KB)
  │     ↓
  │   走 SmallPool 路径:
  │     1. 查 BinSize 表,找到 ≥N 的最小 bin(例:N=33 → bin=48)
  │     2. 该 bin 对应的"池"里取一块预先切好的内存
  │     3. 池里没有? 从 OS 申请新的页/块,切片
  │     4. 多线程:先查 TLS cache,再查全局 free list
  │
  └─ N > MAX_SMALL_POOL_SIZE
        ↓
      走 LargePool 路径:
        1. 直接调 FPlatformMemory::BinnedAllocFromOS(VirtualAlloc / mmap)
        2. 在 hash 表里记录元信息(以便 Free 时找到对应分配)
```

**为什么这样设计?**
- 游戏里**绝大多数分配是小对象**(几十到几百字节,UObject 头、TArray 元素、字符串)。SmallPool 用预分配的"切好的块"快速派发,无锁路径。
- **少数大块分配**(资产数据、纹理、模型)直接走 OS,避免污染 SmallPool 的内存布局。
- 大小阈值(`MAX_SMALL_POOL_SIZE`)在 Binned2 是 32KB-16,Binned3 是 128KB。

下面分别看 Binned2 和 Binned3 的具体实现。

把这张表读懂,你就理解了 Binned2 的**核心设计哲学**:

**(1)前 13 项是固定 +16 步进**(16, 32, 48, ..., 208)。这是因为 UE 的对齐基线是 16 字节,小于 256 字节的分配密度高,精细分桶能减少内部碎片。

**(2)256 字节之后步进变大**(288, 320, 384, 448, 512, 560, 624, ...)。Epic 选这些数字不是随便选的 —— 注释 `// /256`、`// /227`、`// /204` 是"一个 64KB 页能装多少个 bin"。每个数字都让"尾部浪费"尽可能少。

例:
- `64KB / 288 = 227 个 bin`,尾部浪费 `64KB - 227*288 = 160 字节`(注释里 "/227 160b")
- `64KB / 320 = 204 个 bin`,尾部浪费 256 字节(注释里 "/204 256b")
- `64KB / 4096-16 = 16 个 bin`,几乎无浪费(注释里 "/16")
- `64KB / 32768-16 = 2 个 bin`,几乎无浪费(注释里 "/2")

**(3)`AGGRESSIVE_MEMORY_SAVING` 编译宏**:某些受限平台(老款 iOS / Android 旧机)开启,把最大 SmallPool 限制到 13104。一般 Win64 不开。

**(4)注意 `1024-16`、`2048-16` 等**:这些是为了给每个 bin 留 16 字节的元数据头(canary 等),让 bin 对齐到 4KB / 64KB 页边界后还能塞下管理信息。

### 1.4.3.2 BinSize 索引的快速查表

`Engine/Source/Runtime/Core/Public/HAL/MallocBinned2.h` 之后的源码里:

```cpp
// 索引表:从"请求字节数 / 16"快速映射到 BinSize 索引
uint8 FMallocBinned2::MemSizeToPoolIndex[SIZE_TO_POOL_INDEX_NUM];
```

构造时被初始化(`MallocBinned2.cpp:390` 附近):

```cpp
FMemory::Memcpy(SmallBinSizes, SmallBinSizesInternal);   // 拷贝表

// 然后构建 MemSizeToPoolIndex
for (uint32 i = 0; i < UE_MB2_MAX_SMALL_POOL_SIZE / 16 + 1; ++i)
{
    uint32 RequestedBytes = i * 16;
    // 在 SmallBinSizes 里二分查找第一个 ≥ RequestedBytes 的 bin
    uint32 PoolIndex = std::lower_bound(SmallBinSizes, SmallBinSizes + UE_MB2_SMALL_POOL_COUNT, RequestedBytes) - SmallBinSizes;
    MemSizeToPoolIndex[i] = (uint8)PoolIndex;
}
```

(实际代码长得不太一样,但语义就是这个。)

意义:**任何分配请求,O(1) 查表得到 PoolIndex**。例如 `Malloc(33)`:
- `33 / 16 = 2`(向上取整后 3,但实际算法可能略有不同)
- `MemSizeToPoolIndex[3]` → 索引 2 → `SmallBinSizes[2] = 48`
- 走 48 字节 bin 池

### 1.4.3.3 PoolInfo / FreeBlock 数据结构

`MallocBinned2.h:77`:

```cpp
struct FPoolInfo
{
    enum class ECanary : uint16
    {
        Unassigned = 0x3941,
        FirstFreeBlockIsOSAllocSize = 0x17ea,
        FirstFreeBlockIsPtr = 0xf317
    };

    uint16      Taken;          // 这个 pool 里已分配出去的 bin 数,降到 0 就能整池释放
    ECanary     Canary;         // 检测内存损坏的"金丝雀"
    uint32      AllocSize;
    FFreeBlock* FirstFreeBlock; // 链表头:指向第一个空闲 bin(或 OS 分配大小)
    FPoolInfo*  Next;           // 双向链表
    FPoolInfo** PtrToPrevNext;
    // ...
};
```

`FFreeBlock` 是放在**空闲 bin 内部**的链表节点(类似 freelist 经典做法):

```cpp
// 简化示意
struct FFreeBlock
{
    EBlockCanary Canary;
    uint8        BlockSizeShift;
    uint16       NumFreeBins;
    FFreeBlock*  NextFreeBlock;
    // ... 后面是真实的可用空间 ...
};
```

**精髓**:**空闲 bin 自己充当链表节点**。不需要额外申请 freelist 内存。当 bin 被分配出去,链表节点信息被覆盖;bin 被还回时,在它头部重建一个 FFreeBlock 节点链回 freelist。

这是教科书级别的"侵入式 freelist"设计,所有"binned" / "slab" 分配器都用这套思路。

### 1.4.3.4 FPoolTable —— 一个 BinSize 一个池

```cpp
struct FPoolTable
{
    FPoolList ActivePools;     // 还有空 bin 的 pool 链表
    FPoolList ExhaustedPools;  // 已经分配满的 pool 链表
    uint32 BinSize;            // 这个表负责的 BinSize
    // ...
};

FPoolTable SmallPoolTables[UE_MB2_SMALL_POOL_COUNT];   // 51 个池表
```

每个 BinSize(16 / 32 / 48 / ...)有**自己的 PoolTable**。整个分配器维护 51 个独立的池表(`UE_MB2_SMALL_POOL_COUNT = 51`)。

### 1.4.3.5 Alloc 完整路径(SmallPool)

简化 walk-through(对应 `MallocBinned2.cpp` 的核心逻辑):

```cpp
void* FMallocBinned2::Malloc(SIZE_T Size, uint32 Alignment)
{
    if (Size <= UE_MB2_MAX_SMALL_POOL_SIZE)
    {
        // 1. 快速查表:Size → PoolIndex
        uint32 PoolIndex = BoundSizeToPoolIndex(Size);
        
        // 2. 先查 TLS cache(下一节 §1.5 详讲)
        FPerThreadFreeBlockLists* Lists = FPerThreadFreeBlockLists::Get();
        if (Lists)
        {
            void* Result = Lists->Malloc(PoolIndex);
            if (Result) return Result;        // ← 大多数情况走这条快路径,无锁
        }
        
        // 3. TLS 没有,锁全局池表
        FPoolTable& Table = SmallPoolTables[PoolIndex];
        FScopeLock Lock(&Table.Mutex);
        
        // 4. 从 ActivePools 里取一个有空的 pool,从中切一个 bin
        FPoolInfo* Pool = Table.ActivePools.Head();
        if (Pool)
        {
            void* Bin = AllocateBinFromPool(Pool);
            if (Pool->IsExhausted()) Table.MoveToExhausted(Pool);
            return Bin;
        }
        
        // 5. 没有 ActivePool → 从 OS 申请新 page/block
        return AllocateNewPoolAndBin(Table);
    }
    else
    {
        // LargePool 路径(下面 §1.4.3.7)
        return MallocLargePool(Size, Alignment);
    }
}
```

**性能表象**:绝大多数 Malloc 走 Step 2 的 TLS cache,**完全无锁,几条指令出结果**。这是为什么 UE 在数百万次/秒分配压力下依然吃得消。

### 1.4.3.6 Free 路径

```cpp
void FMallocBinned2::Free(void* Ptr)
{
    if (!Ptr) return;
    
    // 1. 通过 Ptr 找到归属 PoolInfo(用地址哈希或元数据查)
    FPoolInfo* Pool = FindPoolForPtr(Ptr);
    
    if (Pool->Canary == ECanary::FirstFreeBlockIsPtr)
    {
        // SmallPool free 路径
        uint32 PoolIndex = Pool->GetPoolIndex();
        
        // 2. 先尝试推回 TLS cache
        FPerThreadFreeBlockLists* Lists = FPerThreadFreeBlockLists::Get();
        if (Lists && Lists->Free(Ptr, PoolIndex))
        {
            return;    // ← 大多数情况走这条快路径
        }
        
        // 3. TLS 满了 / 没 TLS,放回全局
        FPoolTable& Table = SmallPoolTables[PoolIndex];
        FScopeLock Lock(&Table.Mutex);
        ReturnBinToPool(Pool, Ptr);
        
        // 4. 整个 pool 空了? → 还给 OS
        if (Pool->Taken == 0) FreePoolToOS(Pool);
    }
    else
    {
        // LargePool free
        FreeLargePool(Ptr);
    }
}
```

**关键设计**:**优先把"已 free 的 bin" 推到 TLS cache**(只要这个线程的 cache 还没满)。这样下次同一线程再 Malloc 同样大小的 bin,**直接 TLS 拿,完全不锁**。

这是 Binned2 在多线程场景下高吞吐的根基。

### 1.4.3.7 LargePool 路径(>32KB 分配)

LargePool 不再分桶,**直接走 OS**:

```cpp
void* FMallocBinned2::MallocLargePool(SIZE_T Size, uint32 Alignment)
{
    // 1. 算实际要申请的 OS 页对齐大小
    SIZE_T AlignedSize = Align(Size, OSPageSize);
    
    // 2. 调 OS 申请(VirtualAlloc / mmap)
    void* Ptr = CachedOSPageAllocator::Allocate(AlignedSize, Alignment);
    
    // 3. 在 hash 表里记一笔(便于 Free 时找到 metadata)
    FPoolInfo* PoolInfo = NewPoolInfo();
    PoolInfo->AllocSize = (uint32)Size;
    PoolInfo->FirstFreeBlock = (FFreeBlock*)AlignedSize;  // 用这个字段存 OS 分配大小
    PoolInfo->Canary = ECanary::FirstFreeBlockIsOSAllocSize;  // ← 区分大小池的 marker
    HashTable.Insert(Ptr, PoolInfo);
    
    return Ptr;
}
```

`CachedOSPageAllocator` 是个**页级缓存**(`Engine/Source/Runtime/Core/Public/HAL/Allocators/CachedOSPageAllocator.h`)。它在 OS 之上又加了一层"小型 free list":释放回 OS 的页先放在缓存里,**下次有相同大小请求直接复用**,避免 VirtualAlloc 系统调用。`UE_MB2_MAX_CACHED_OS_FREES = 64`(`MallocBinned2.h:21`)是这个缓存的容量。

### 1.4.3.8 Bundle 机制 —— 跨线程批量交换

读到这里你可能想:"Free 时推回 TLS cache,但万一线程 A 分配了一堆 bin,然后线程 B 全 free 了,这些 bin 会卡在线程 B 的 TLS,A 永远拿不到?"

确实会。Binned2 的解法叫 **Bundle**:

- 每个 TLS cache 容量是固定的(N 个 bin)
- TLS cache 满了,把整个 cache 打包成一个"Bundle"(一捆 bin)
- Bundle 推到该 BinSize 对应的**全局 Bundle 池**(类似 free list of bundles)
- 其它线程 Malloc 时如果 TLS 空了,从全局 Bundle 池**整捆**拿过来

这个设计的妙处:跨线程交换是**整捆**的,不是单个 bin。一次交换摊到 N 个 bin 上,锁竞争被摊薄到 1/N。

具体实现细节我们 §1.5 讲 TLS 时再深入。

### 1.4.3.9 Binned2 的内存损坏检测

Binned2 内置三层防护:

1. **Canary**(`FPoolInfo::ECanary` 等),已分配 / 已释放区域填特定 magic number,被覆盖即知有越界。
2. **FreeBlock canary**(`EBlockCanary`),空闲 bin 自身的链表节点带 marker。
3. **`UE_USE_MALLOC_FILL_BYTES`**(默认 Development 开):Malloc 后填 0xFD,Free 后填 0xFE。这一层由 `FMallocPoisonProxy`(§1.3 proxy 链)提供。

**对你的实际意义**:Editor / Development 跑出 `MallocBinned2 Corruption Canary was 0xX, should be 0xY` 的 LogFatal,大概率是你某段代码越界写了别人的内存。配合 `-stompmalloc`(§1.4.7)能精确定位。

## 1.4.4 FMallocBinned3 — UE5 新一代

### 1.4.4.1 设计动机

Binned3 不是"Binned2 + 一些优化"。它是**完全不同的内存布局策略**。

Binned2 的痛点(在巨型项目里逐渐暴露):
- SmallPool 的 PoolInfo 用 hash 表查找(O(1) 但有 cache miss)
- 大量 BinSize 各自的池在地址空间里**交错**,大对象池碎片
- 64 位地址空间下"页缓存"未充分利用

Binned3 的新思路(`MallocBinned3.h:73-90` 的注释里写得很清楚):

> "MallocBinned3 supports two types of allocations - large and small pool allocation:
> 1. For small pool allocation MallocBinned3 reserves contiguous range of virtual memory (a Pool) for each allocation size (a Bin). These Pools can be adjacent to each other in memory if BINNED3_USE_SEPARATE_VM_PER_POOL is set to 0. By default each Pool reserves 1 GB of address space..."

翻译:
- **每个 BinSize 预先在 64 位虚拟地址空间里 reserve 一段 1GB 连续区**(`UE_MB3_MAX_MEMORY_PER_POOL_SIZE = 1GB`)
- 这一段地址**只 reserve 不 commit** —— OS 不分配实际物理内存,只占地址空间(64 位空间富裕得很)
- 当某个 BinSize 真实分配增长,**按需 commit** 这段 reserve 区里的页
- 释放时**可以 decommit** 物理页,但保留虚拟地址 reserve

### 1.4.4.2 关键数据结构

`MallocBinned3.h:134`:

```cpp
struct FPoolTable
{
    uint32 BinSize;                       // 这个池的 BinSize
    uint32 BlockSize;                     // Block 大小(几个页)
    uint32 NumMemoryPagesPerBlock;        // 一个 Block 占几页
    uint32 NumEverUsedBlocks;
    
    FBitTree BlocksAllocatedBits;         // 每个 Block 一位:1 = 已 commit
    FBitTree BlocksExhaustedBits;         // 每个 Block 一位:1 = 这个 block 已分配满
    
    FPoolInfoSmall** PoolInfos;           // 每个 Block 的元数据
    
    uint64 UnusedAreaOffsetLow;           // 高水位标记:已使用 VM 段的末尾偏移
    
    UE::FPlatformRecursiveMutex Mutex;
    // ...
};
```

理解这个结构:

- **VM Pool 的地址空间是预先 `VirtualAlloc(MEM_RESERVE)` 的 1GB**(在分配器构造时一次性 reserve,不消耗物理内存)。
- 这 1GB 被切成等大的 Block,每个 Block 包含若干 Bin。
- `BlocksAllocatedBits` 是 BitTree:第 i 位为 1 表示"第 i 个 block 已 commit 了物理页"。
- `BlocksExhaustedBits`:第 i 位为 1 表示"第 i 个 block 已经分配满,没有空闲 bin"。

**BitTree 的优势**:相比线性扫描,BitTree 用层级位图实现**O(log N) 查找**"第一个有空闲的 block"。当 1GB pool 含数千个 block 时,这个差异显著。

### 1.4.4.3 Alloc 路径

```cpp
void* FMallocBinned3::Malloc(SIZE_T Size, uint32 Alignment)
{
    if (Size <= UE_MB3_MAX_SMALL_POOL_SIZE)   // 默认 128KB
    {
        // 1. 查表得到 PoolIndex
        uint32 PoolIndex = BoundSizeToPoolIndex(Size);
        
        // 2. TLS cache 路径(同 Binned2)
        // ... 此处省略 TLS 路径,与 Binned2 几乎一样 ...
        
        // 3. 从 PoolTable 找一个有空的 Block
        FPoolTable& Table = PoolTables[PoolIndex];
        FScopeLock Lock(&Table.Mutex);
        
        // BitTree 找第一个 BlocksAllocatedBits=1 且 BlocksExhaustedBits=0 的 block
        int32 BlockIndex = FindFirstFreeBlock(&Table);
        
        if (BlockIndex == -1)
        {
            // 4. 当前没有空 Block:在 reserve 的 VM 区里 commit 一个新 Block
            BlockIndex = AllocateNewBlock(Table);
        }
        
        // 5. 从该 Block 里切一个 Bin
        return AllocateBinFromBlock(&Table, BlockIndex);
    }
    else
    {
        // LargePool 路径
        return MallocLargePool(Size, Alignment);
    }
}
```

`AllocateNewBlock` 内部调用 `FPlatformVirtualMemoryBlock::CommitPages(...)`,**仅 commit 这一段已 reserve 的地址,不 reserve 新空间**。OS 这时候给物理页,完成虚拟到物理的映射。

### 1.4.4.4 Free 路径关键差异

Binned3 的 Free 关键差异:**整个 Block 全部 bin 都 free 了之后,可以 decommit 物理页**(但 reserve 仍保留),把物理内存还给 OS。

```cpp
void FMallocBinned3::Free(void* Ptr)
{
    // ... TLS / 全局 free 路径 同 Binned2 ...
    
    // 如果一个 Block 全空了:
    if (BlockIsEmpty(BlockIndex))
    {
        // decommit 物理页,但保留虚拟地址 reserve
        FPlatformVirtualMemoryBlock::DecommitPages(...);
        BlocksAllocatedBits.ClearBit(BlockIndex);
    }
}
```

**对运行时内存的影响**:
- Binned2:整池释放后,VirtualFree 把整页还给 OS。下次 Malloc 同 BinSize 时再 VirtualAlloc。
- Binned3:reserve 永远保留(地址空间不解绑),只有物理页 commit/decommit。下次重用更快(地址映射 metadata 已存在,只需 commit)。

### 1.4.4.5 Binned3 vs Binned2 的关键差异(对比表)

| 维度 | Binned2 | Binned3 |
|---|---|---|
| 地址空间策略 | 按需 VirtualAlloc | 启动期一次性 reserve 1GB × 池数 |
| 池的相邻性 | 无序(取决于 OS 决定地址) | 每池连续(`BINNED3_USE_SEPARATE_VM_PER_POOL=1` 时) |
| Block 查找 | 链表 | BitTree O(log N) |
| Free 后归还 OS | VirtualFree(完全归还) | DecommitPages(物理释放,虚拟地址保留) |
| 重用速度 | 中(下次重新 reserve) | 快(只需 recommit) |
| 32 位平台 | 支持 | 不支持(地址空间不够) |
| MAX_SMALL_POOL_SIZE | 32KB-16 | 128KB |

### 1.4.4.6 何时该选 Binned3?

Binned3 在以下场景明显优于 Binned2:

1. **超大内存场景**:64 位平台 + 数 GB 进场内存(典型:Editor、巨型 RTS)
2. **频繁的"分配-释放-再分配同样大小"**(典型:Mass entity 频繁创建销毁)
3. **多线程高吞吐 Mass Processor**(reserved VM 减少 mmap 系统调用竞争)

Binned3 的代价:启动期就要 reserve 51 个 BinSize × 1GB = 51GB 虚拟地址空间。**32 位平台地址不够,无法启用**。64 位平台地址富裕,完全 OK。

**对你的 RTS 项目**:Game build 默认就是 Binned3(若 `USE_MALLOC_BINNED3` 编译宏开启)。**不需要手动切换**。但如果你怀疑 Binned3 引入了内存问题,可以临时 `-binnedmalloc2` 对比测试。

## 1.4.5 FMallocMimalloc — Editor 默认主力

### 1.4.5.1 它是什么

`FMallocMimalloc` 是 Microsoft Research 开发的 [mimalloc](https://github.com/microsoft/mimalloc) 的 UE 包装。源码在:
- `Engine/Source/Runtime/Core/Public/HAL/MallocMimalloc.h`
- `Engine/Source/Runtime/Core/Private/HAL/MallocMimalloc.cpp`
- 底层库在 `Engine/Source/ThirdParty/mimalloc/`

UE 自己**不维护**它的算法,只做接口适配。

### 1.4.5.2 算法骨架(高度简化)

mimalloc 的核心思路:
- 每线程一个 **heap**(轻量,仅几 KB 元数据)
- heap 内有多个 **page**,每个 page 服务一个 size class
- 每个 page 的空闲 bin 用**两条 free list**:
  - **本地 free list**(同线程 free)
  - **远程 free list**(跨线程 free,原子链表)
- Alloc 时优先本地,本地空了"批量回收"远程 free list 到本地

这个设计的最大特点:**本地 alloc/free 完全无锁**,与 Binned2 的 TLS cache 思路类似但更细粒度。

### 1.4.5.3 为什么 Editor 选 mimalloc

Epic 实测(`WindowsPlatformMemory.cpp:156` 注释):
> "Mimalloc has shown both great performance and as much as half the memory usage of TBB after heavy editor workloads."

Editor 长时间使用的场景里,mimalloc 内存占用比 TBB 少**一半**。原因:
- mimalloc 对**内存归还 OS 更激进**(decommit 阈值低),长时运行的 RSS 不会无限膨胀
- Page 复用策略针对"打开关闭多个资产编辑器"这种碎片重的场景优化

### 1.4.5.4 Game / Server 为什么不用 mimalloc

Game 进程通常生命周期相对短,内存占用比 Editor 平稳。Binned3 的"VM 预 reserve"模型在这种"进程内分配模式相对固定"的场景反而更有优势。Mass 高频小对象分配也对 Binned3 的快路径友好。

**纪律**:**别动**。Editor 用 mimalloc,Game 用 Binned3(或 Binned2),这是 Epic 用大量项目数据校准的默认值。除非你有强烈对比数据,不要切。

## 1.4.6 FMallocTBB / FMallocAnsi / FMallocJemalloc

### 1.4.6.1 FMallocTBB

Intel Threading Building Blocks 的内置分配器。算法跟 mimalloc 类似(per-thread cache + global pool),性能也接近,**但内存占用高**。被 mimalloc 取代是 5.x 的趋势。

适用场景:**几乎没有**。除非你在 Intel 平台跑 instrumentation tool 需要 TBB 整套生态,否则没必要。

### 1.4.6.2 FMallocAnsi —— 简单粗暴的 std::malloc 包装

`Engine/Source/Runtime/Core/Public/HAL/MallocAnsi.h` + `Private/HAL/MallocAnsi.cpp`:

```cpp
class FMallocAnsi : public FMalloc
{
public:
    virtual void* Malloc(SIZE_T Size, uint32 Alignment) override
    {
        return ::aligned_alloc(Alignment, Size);   // 或 _aligned_malloc on MSVC
    }
    virtual void Free(void* Ptr) override
    {
        ::aligned_free(Ptr);
    }
    // ...
};
```

适用场景:
1. **初步排查"内存损坏是不是 Binned2 自己的 bug"**(用 `-ansimalloc` 切到 std::malloc,如果问题消失,说明确实 Binned 有问题)
2. **某些受限平台**(老式嵌入式)
3. **教学** —— 帮新人理解什么是"光秃秃的分配器"

**性能**:比 Binned 慢一个量级。Mass 数万 entity 场景跑 `-ansimalloc` 会立刻看到帧率掉。

### 1.4.6.3 FMallocJemalloc

Facebook 开发的 jemalloc 包装。Linux 服务器场景常用。`MallocJemalloc.h` / `.cpp`,内部包 jemalloc 库。

特点:对长时运行的服务器进程内存碎片控制好。**Linux 服务器 build 在某些项目里默认用它**。

## 1.4.7 调试型分配器:Stomp / DoubleFreeFinder / LeakDetection

这一组**不是用来跑游戏的**,是用来**复现内存 bug 的**。

### 1.4.7.1 FMallocStomp(`-stompmalloc`)

`Engine/Source/Runtime/Core/Public/HAL/MallocStomp.h`。算法:

- **每个 Malloc 调用对应一整个 OS 页**(4KB / 16KB),不论你要多少字节
- 在该页**末尾**对齐放你的内存
- 紧接你内存末尾的下一页**保留为 guard page**(`PAGE_NOACCESS`,任何读写立即触发 access violation)
- Free 时把整页 `mprotect(PAGE_NOACCESS)`,任何 use-after-free 立刻段错误

**结果**:
- ✅ 越界写**1 个字节**就立刻段错误,栈 trace 精确到出错那一行
- ✅ Use-after-free 立刻段错误
- ❌ 内存占用爆炸(每次 alloc 至少 4KB)
- ❌ 性能掉到 1-10 fps

适用:**复现并定位**内存损坏 bug。日常开发**不开**。

### 1.4.7.2 FMallocStomp2(`-stomp2malloc`)

Stomp 的"proxy 模式"版本。不替代主分配器,而是**在主分配器外面**包一层。能与 Binned2/3 共存,部分场景下比 Stomp 更轻。`§1.3.5` 讲过它在 proxy 链里的位置。

### 1.4.7.3 FMallocDoubleFreeFinder(`-doublefreefinder`)

`Engine/Source/Runtime/Core/Public/HAL/MallocDoubleFreeFinder.h`。检测 double-free:
- 维护一个"已 free 指针"的 hash 集
- Free 时检查指针是否已在集合中,在则 fatal log + 打印两次 free 的栈

代价:每次 Malloc/Free 多一次 hash 操作。开发期排查 double-free 必备,**生产环境不开**。

### 1.4.7.4 FMallocLeakDetectionProxy(`-mallocleakdetect`)

`Engine/Source/Runtime/Core/Public/HAL/MallocLeakDetection.h`。每次 Malloc 记录调用栈,Free 时移除。`memreport` 能 dump 当前所有"分配但未释放"的栈。

代价:每次 Malloc 多一次栈采集(O(N) where N = 栈深),**慢**。但在排查"哪里漏 alloc 了"时无可替代。

### 1.4.7.5 实战:RTS 排查内存 bug 的渐进流程

```
1. 普通运行,问题难复现        → 常规 -dev,看 stat memory 时序
2. 怀疑是 leak                → 加 -mallocleakdetect,跑一段时间后 memreport
3. 怀疑是越界写               → -stomp2malloc(代价小),如果没复现再 -stompmalloc
4. 怀疑是 double-free         → -doublefreefinder
5. 怀疑是分配器自身 bug        → -ansimalloc(切到最朴素分配器,如果问题消失说明 Binned 锅)
```

后面 §28 调试稳定性章节会把这套流程做成完整 SOP。

## 1.4.9 改 Engine:增加自定义 BinSize(高级)

如果你 RTS 项目里有大量"特定大小"的对象(假设你 Mass Fragment 普遍 96 字节),你可能想:**"96 字节的 bin 在 Binned2 里走 96 bin 还是 112 bin?能不能加一个我专属的 100 byte bin 提高密度?"**

### 1.4.9.1 现实

- 96 字节请求**精确命中** 96 byte bin(看 `SmallBinSizesInternal` 表第 6 项)。无浪费。
- 100 字节请求会被分到 112 byte bin,浪费 12 字节 / entity。
- 添加 100 byte bin 需要改 `SmallBinSizesInternal`,这是**改 Engine**。

### 1.4.9.2 如果真要改

`MallocBinned2.cpp:48` 的 `SmallBinSizesInternal[]` 数组里加一行,然后:

1. 数组**必须严格递增**(有 `static_assert`)
2. 数组长度必须等于 `UE_MB2_SMALL_POOL_COUNT`(`MallocBinned2.h:35` 的宏)
3. 数组长度 ≤ 256(因为索引用 uint8)
4. 最大 bin 必须等于 `UE_MB2_MAX_SMALL_POOL_SIZE`

改完之后所有相关的 `static_assert` 必须通过,且**必须重编整个 Engine**(大量代码 inline 引用了这个表)。

### 1.4.9.3 推荐做法

**不要改 Engine 的 BinSize 表**。99% 你以为的"分配器优化空间"实际收益很小。改:
- 你的 Fragment 设计(让大小命中现有 bin)
- 用 `TArray<T, TInlineAllocator<N>>`(§1.6 讲)避开堆分配
- 自定义 SLAB 池(在你的代码里维护一个固定大小池,绕过 GMalloc)

商业 RTS 项目里我没见过谁真改 BinSize 表能跑出明显收益的。

## 1.4.10 性能数据感知

给你一些数量级感觉(Win64 Editor,典型工作站 CPU):

| 操作 | 耗时(无锁路径) |
|---|---|
| `FMemory::Malloc(64)` (TLS hit) | ~10-20ns |
| `FMemory::Malloc(64)` (TLS miss,锁全局) | ~100-200ns |
| `FMemory::Malloc(64)` (新 OS 页) | ~5-50μs |
| `FMemory::Malloc(1MB)` (LargePool,新 VirtualAlloc) | ~10-100μs |
| `FMemory::Malloc(1MB)` (LargePool,缓存命中) | ~1-2μs |
| `FMemory::Free(P)` (TLS push) | ~5-15ns |
| `FMemory::Free(P)` (整池归还 OS) | ~5-50μs |

**Mass 视角**:50K entity 每帧创建/销毁 5%(2500 个),每个 entity 的 Fragment 结构假设触发 2 次小 alloc(chunk 已预分配,这只是 O(创建数量),不是 O(总数量)),那:
- 5000 次 alloc + 5000 次 free
- TLS 命中(常见):5000 × 15ns = **75 μs / 帧**
- TLS 未命中(罕见):5000 × 200ns = **1 ms / 帧**

完全在帧预算内。这就是 Mass 数万 entity 跑得起来的原因之一。

## 1.4.11 RTS 视角下的总结纪律

### (1)分配器选择交给 Epic

不要切。Editor 用 mimalloc,Game 用 Binned3,Server 看 build 默认。99% 不需要改。

### (2)知道 BinSize 表的存在

设计 Fragment 时,**有意识地让大小落在 bin 边界**。打开 `MallocBinned2.cpp:48` 那张表,贴在桌面边。例子:
- Fragment 96 字节 ✓ 精确命中
- Fragment 100 字节 → 浪费 12 字节(分到 112)
- Fragment 130 字节 → 分到 144,浪费 14 字节
- Fragment 250 字节 → 分到 256,浪费 6 字节

Mass entity 数 5K+,这种字节级浪费乘起来就几百 KB 到 MB。

### (3)大块连续内存优先 LargePool

如果你设计自己的 chunk allocator(如 Mass chunk 默认 128KB),走 `FMemory::Malloc(128*1024)` 直接进 LargePool,**不**消耗 SmallPool。这是 Mass 的设计精髓。

### (4)调试期备好 -stompmalloc 习惯

碰到任何"诡异 crash"或"看似无解的内存损坏",**立刻**试 `-stompmalloc`。它能告诉你越界发生在哪一行,经常 30 秒定位 30 小时不知所措的 bug。

### (5)绝不在 Shipping 启用 proxy 调试器

`-stompmalloc` / `-mallocleakdetect` 等绝不能进玩家的 build。打 Shipping 包前确认命令行干净。

## 1.4.12 实操提示与下一节预告

### 实操提示

- **观察当前分配器选择**:Editor 启动后控制台 `memreport`,顶部输出 `Allocator: ...`,告诉你当前主分配器名字。
- **查看 BinSize 命中**:`memreport -full` 输出每个 BinSize 的当前使用量。能看到你的项目实际命中哪些 bin。
- **测分配器吞吐**:写一个 console command:
  ```cpp
  static FAutoConsoleCommand CmdBenchAlloc(TEXT("rts.BenchAlloc"),
      TEXT("Benchmark FMemory::Malloc throughput"),
      FConsoleCommandDelegate::CreateLambda([]()
      {
          const int32 N = 1000000;
          double Start = FPlatformTime::Seconds();
          TArray<void*> Ptrs;
          Ptrs.Reserve(N);
          for (int32 i = 0; i < N; ++i)
          {
              Ptrs.Add(FMemory::Malloc(64, 16));
          }
          for (void* P : Ptrs) FMemory::Free(P);
          double Elapsed = FPlatformTime::Seconds() - Start;
          UE_LOG(LogTemp, Display, TEXT("Alloc/Free %d times in %.2fms = %.0fns/op"),
              N, Elapsed * 1000.0, Elapsed * 1e9 / N / 2);
      }));
  ```
  跑 `rts.BenchAlloc`,在 `-binnedmalloc2 / -binnedmalloc3 / -mimalloc / -tbbmalloc / -ansimalloc` 各跑一遍对比。
- **看 BinSize 表的内存浪费**:`stat memory` 显示的 "Pool Memory Used / Pool Memory Allocated" 比例就是密度。低于 80% 说明你大量分配落在 bin 间隙。
