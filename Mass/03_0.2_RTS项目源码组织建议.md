# §0.2 一个 RTS 项目的源码组织建议

> **本节地图**:§0.1 教你怎么造一个 Module。§0.2 教你怎么把**几十个 Module + 几个 Plugin + 若干 Engine 补丁**组织成一个**能 5 年不发霉**的工程。
>
> **预备知识**:§0.1(必读)。
>
> **读完之后你能做到**:
> - 设计一个能跨 Editor / Game / Server 三套构建复用的项目骨架
> - 看懂任何 `.uplugin` 文件,知道每个字段意味着什么
> - 设计 Plugin 之间的依赖,避免循环 / 提前加载 / 加载失败
> - 选定一套 Engine 补丁管理流程,让你两年后 rebase 上游不抓狂
> - 知道 Hot Reload / Live Coding 在哪些设计下会爆炸,提前规避

---

## 0.2.1 从一个真实场景反推架构

想象一下两年后,你的 RTS 已经做了 18 个月。这时一个**典型的工作日**长这样:

- 美术新提交了一批兵种模型,你要导入并配置 Mass Trait
- 策划要求"狂战士技能多一个减速效果",你改技能 Fragment 数据
- QA 报告一个"5000 单位时帧率掉到 20"的 bug,你需要看 Insights
- 你发现一个引擎 5.7 的 ISMC 上传 bug,要打补丁
- 上游 Epic 发布了 5.7.4 hotfix,你要 rebase
- 服务器同事说"专用服务器内存涨到 8GB",你要把 Editor-only 数据从核心模块剥离

**一份好架构,这一天里你不会发狂**。一份烂架构,你光是为了"5.7.4 rebase"就要花半天调和冲突。

我们的目标:**让上面任意一项工作的影响半径都被压在最小**。

### 0.2.2.1 为什么是这种拆法

每个文件夹都对应一个**独立的迭代节奏**:

| 目录 | 改动频率 | 改动来源 | 影响半径 |
|---|---|---|---|
| `Source/MyRTS/` | 高 | 游戏程序员 | 主模块 |
| `Source/MyRTSEditor/` | 中 | TA / 工具组 | Editor 工具,与游戏运行时无关 |
| `Plugins/MyRTSCore/` | 低 | 架构师 | 基础设施,改动谨慎 |
| `Plugins/MyRTSMass/` | 高 | 战斗程序员 | Mass 逻辑迭代 |
| `Plugins/MyRTSRender/` | 中 | 渲染程序员 | 渲染表现 |
| `Plugins/MyRTSNetwork/` | 中 | 网络程序员 | 网络层 |
| `Plugins/MyRTSGameplay/` | 高 | 玩法程序员 | 命令 / 技能 |
| `EnginePatches/` | 极低 | 全员谨慎 | Engine,需 rebase |

**关键洞察**:迭代节奏不同的代码,**绝对**不能放同一个模块。把高频和低频混在一起,你高频改动会反复触发低频代码重编。

### 0.2.2.2 拆分粒度的"逐渐增加"原则(再强调)

新项目刚启动**不要**一次拆这么多。先 1 个 Module,长出来再拆。但你要**预知**长出哪些边界 — 这样后期拆分阻力最小。

**"未来要拆但现在还合并"的边界**用文件夹和 namespace 提前预留:

```
Source/MyRTS/Public/
├── Core/           ← 未来要拆成 MyRTSCore Plugin
├── Mass/           ← 未来要拆成 MyRTSMass Plugin
├── Render/         ← 未来要拆成 MyRTSRender Plugin
├── Network/        ← 未来要拆成 MyRTSNetwork Plugin
└── Gameplay/       ← 未来要拆成 MyRTSGameplay Plugin
```

**纪律**:子目录之间**不允许**互相 `#include`(除了往下游方向)。这条纪律在大模块里也强制成立,等你拆模块时,那个 `#include` 关系就直接变成 `Build.cs` 依赖。

## 0.2.3 .uplugin 文件深度解析

每个 Plugin 根目录都有一个 `<PluginName>.uplugin` 文件(JSON 格式)。你来看一个真实的:

```json
// Engine/Plugins/Runtime/MassEntity/MassEntity.uplugin (5.7.3 截图)
{
    "FileVersion": 3,
    "Version": 1,
    "VersionName": "0.4",
    "FriendlyName": "MassEntity",
    "Description": "...This plugin is now DEPRECATED. All of MassEntity code has been moved to the engine...",
    "Category": "Gameplay",
    "CreatedBy": "Epic Games, Inc.",
    "CanContainContent": true,
    "IsBetaVersion": true,
    "Installed": false,
    "EnabledByDefault": false,
    "DeprecatedEngineVersion": "5.5",
    "Modules": [],
    "Plugins": []
}
```

**关键观察**:5.5 版本起,MassEntity **从 Plugin 迁移到了 Engine 主体**。在 5.7.3 里它的真实位置是:
```
Engine/Source/Runtime/MassEntity/      ← 真实代码
Engine/Plugins/Runtime/MassEntity/     ← 仅留一个空 .uplugin 占位,提示 deprecated
```

这个迁移说明 Mass 已经被 Epic 视为"engine first-class"。我们**继续把它当作 Plugin 心智模型来理解**(Subsystem 注册、Tick 触发都没变),但 `#include` 路径要按 Runtime/MassEntity 来。

### 0.2.3.1 .uplugin 字段总览

下面是一个完整版的 .uplugin 模板,带每个字段的作用:

```json
{
    "FileVersion": 3,                    // 描述文件 schema 版本(几乎都是 3)
    "Version": 1,                        // Plugin 自身的整数版本号
    "VersionName": "1.0",                // Plugin 自身的人类可读版本号
    "FriendlyName": "My RTS Mass",       // Plugin 浏览器里显示的名字
    "Description": "...",                // Plugin 浏览器里的描述
    "Category": "RTS",                   // Plugin 浏览器里的分组
    "CreatedBy": "Your Studio",
    "CreatedByURL": "https://...",
    "DocsURL": "",

    "EnabledByDefault": true,            // 默认启用?(false 时需玩家手动开)

        {
            "Name": "MyRTSMass",
```

### 0.2.3.2 Modules 数组每个字段的语义

每个 Module 条目最重要三个字段:`Name` / `Type` / `LoadingPhase`。

**Name**:必须**精确**等于 `<Name>.Build.cs` 里 `public class <Name> : ModuleRules` 的类名,也精确等于 `IMPLEMENT_MODULE(FXxxModule, <Name>)` 第二参数。**大小写敏感**。

### 0.2.3.3 Type(EHostType)— 决定模块在哪些 Target 里加载

源码定义在 `Engine/Source/Runtime/Projects/Public/ModuleDescriptor.h`,行 82-130 附近:

```cpp
// Engine/Source/Runtime/Projects/Public/ModuleDescriptor.h:82
namespace EHostType
{
    enum Type : int
    {
        Runtime,                    // 所有 Target,除 Program
        RuntimeNoCommandlet,        // 同上,但不在 commandlet 模式加载
        RuntimeAndProgram,          // 所有 Target,包括 Program
        CookedOnly,                 // 仅 cooked 游戏(不在 Editor)
        UncookedOnly,               // 仅未 cooked(Editor / -game)
        Developer,                  // 已弃用,等同 UncookedOnly
        DeveloperTool,              // bBuildDeveloperTools 为真时
        Editor,                     // 仅 Editor 启动时
        EditorNoCommandlet,         // Editor,且非 commandlet
        EditorAndProgram,           // Editor 和 Program target
        // ...
        Max
    };
}
```

**RTS 项目里你最常用的三种**:

| Type | 用在什么模块 |
|---|---|
| `Runtime` | 默认。绝大多数游戏逻辑。 |
| `Editor` | Editor-only 模块(MyRTSEditor / MyRTSGameplayEditor) |
| `UncookedOnly` | 调试/工具代码。Editor 能用,Shipping Cooked 包裹不进。比 Editor 更宽松,因为 `-game` 模式也能用。 |
| `DeveloperTool` | 仅 Test / Development 构建,Shipping 不带(典型:debug HUD) |
| `RuntimeAndProgram` | 罕见。仅当你写 ShaderCompileWorker 之类的 program 也要用到这个模块时。 |

**实操经验**:Editor 工具模块写 `Editor` 还是 `UncookedOnly`?
- 你的工具**只在 Editor 启动时用**(资产编辑器、Slate UI 扩展)→ `Editor`
- 你的工具**还想在 `UnrealEditor.exe -game` 启动的 Standalone 测试里用**(调试可视化、cvar 注册)→ `UncookedOnly`
- 你的工具**Test / Development 构建也要带,但 Shipping 不带**(性能 HUD、回放工具)→ `DeveloperTool`

### 0.2.3.4 LoadingPhase(ELoadingPhase)— 决定模块加载顺序

源码 `ModuleDescriptor.h:24-60`:

```cpp
// Engine/Source/Runtime/Projects/Public/ModuleDescriptor.h:24
namespace ELoadingPhase
{
    enum Type
    {
        EarliestPossible,          // pak 文件加载之前都需要(压缩格式)
        PostConfigInit,            // 配置系统初始化后,引擎初始化前(极底层 hook)
        PostSplashScreen,          // 系统启动画面后第一屏
        PreEarlyLoadingScreen,     // 在 CoreUObject 之前(自定义 Loading Screen)
        PreLoadingScreen,          // 引擎初始化完成前(挂 Loading Screen 钩子)
        PreDefault,                // Default 之前
        Default,                   // 默认!引擎初始化中,游戏模块加载完之后
        PostDefault,               // Default 之后
        PostEngineInit,            // 引擎初始化完成之后
        None,                      // 不自动加载(代码里手动 LoadModule)
        Max
    };
}
```

**实战决策树**:

| 你的模块特征 | 选什么 LoadingPhase |
|---|---|
| 普通游戏逻辑 | `Default`(就是默认) |
| 基础设施(Fragment 定义、Subsystem 类) | `PreDefault` |
| 注册资产编辑器、菜单项 | `Default` 或 `PostEngineInit` |
| 必须在 CoreUObject 之前(罕见) | `PreEarlyLoadingScreen` 或更早 |
| 自定义 Loading Screen | `PreLoadingScreen` |
| 平台底层 hook(读 pak 前) | `EarliestPossible` |
| 仅运行时按需加载 | `None` + 代码 `FModuleManager::LoadModule(...)` |

**RTS 项目典型方案**:
```json
{
    "Name": "MyRTSCore",       "Type": "Runtime",      "LoadingPhase": "PreDefault"
},
{
    "Name": "MyRTSMass",       "Type": "Runtime",      "LoadingPhase": "Default"
},
{
    "Name": "MyRTSGameplay",   "Type": "Runtime",      "LoadingPhase": "Default"
},
{
    "Name": "MyRTSEditor",     "Type": "Editor",       "LoadingPhase": "PostEngineInit"
}
```

理由:
- Core 在 PreDefault,确保 Fragment 类型先注册到反射系统
- Mass / Gameplay 在 Default,跟着主模块一起
- Editor 工具在 PostEngineInit,确保所有 Editor 子系统(AssetTools 等)都已就绪

### 0.2.3.5 Plugins 数组 — Plugin 之间的依赖

`Plugins` 数组写"**这个 Plugin 启用时,这些 Plugin 也要启用**"。它和 `Modules.Type` 是两个不同维度:
- `Modules.Type` 决定**当前 Plugin 内部模块**在不同 Target 的取舍
- `Plugins` 决定**对其它 Plugin 的元依赖**

```json
"Plugins": [
    { "Name": "MyRTSCore", "Enabled": true },
    { "Name": "EnhancedInput", "Enabled": true },
    { "Name": "ModelingToolsEditorMode", "Enabled": true, "Optional": true }
]
```

**Optional**:找不到时不报错。常用于"可选集成"(例如有 ImGui 时启用某些调试)。

### 0.2.3.6 Plugin 依赖图 vs Module 依赖图(易混淆)

这是新人最常踩的坑。两套依赖图**独立**:

- **Plugin 依赖图**:写在 `.uplugin` 的 `"Plugins"` 数组,决定**哪些 Plugin 一起启用**。
- **Module 依赖图**:写在 `.Build.cs` 的 `*DependencyModuleNames`,决定**编译期 include + 链接关系**。

启用 Plugin A 不会让你**自动**能 `#include` Plugin B 的头。你必须在 Build.cs 里加 `PublicDependencyModuleNames.Add("BModule")`。

正确姿势:
1. `.uplugin` Plugins 数组:让 Plugin A 启用时,Plugin B 自动启用
2. `A 模块的 Build.cs`:加 `PublicDependencyModuleNames.Add("BModule")`,这样代码里能 include B 的头

少了任何一步都会编译失败 / 启动失败。

## 0.2.4 LoadingPhase 与子系统初始化的微妙时序

后面 §11 会细讲 Subsystem,但 LoadingPhase 影响 Subsystem 的注册时机,这里先打底。

### 0.2.4.1 引擎启动时序(简化)

```
EarliestPossible            ← 几乎没人在这层做事
        ↓
PostConfigInit              ← FConfigCacheIni 已就绪
        ↓
PostSplashScreen
        ↓
PreEarlyLoadingScreen       ← CoreUObject 还没全初始化
        ↓
[CoreUObject 初始化,UClass 反射注册全部完成]
        ↓
PreLoadingScreen            ← 可以挂 Loading Screen,可以用 UObject
        ↓
PreDefault                  ← 你的 Core 模块通常在这里
        ↓
Default                     ← 大部分游戏模块在这里
        ↓
PostDefault
        ↓
[FEngineLoop::Init 主体 — UEngineSubsystem 在这里实例化]
        ↓
PostEngineInit              ← Editor 工具模块通常在这里
        ↓
[UWorld 创建 — UWorldSubsystem 在 World 创建时实例化,与 LoadingPhase 无关]
        ↓
[BeginPlay]
```

### 0.2.4.2 你最容易踩的两个坑

**坑 1:把含 UCLASS 的代码放在 PreEarlyLoadingScreen 之前**

```cpp
// PostConfigInit phase 加载的模块里
void FMyModule::StartupModule()
{
    UClass* C = ULMyClass::StaticClass();   // ← 可能崩!
}
```

这个时候 CoreUObject 还没完全初始化,反射系统未就绪,你拿到的 UClass 可能是空指针或半残状态。**纪律**:任何用到 UCLASS / UScriptStruct / 反射的 StartupModule,LoadingPhase 不要早于 `PreLoadingScreen`,稳妥起见就用 `PreDefault` 或 `Default`。

**坑 2:Editor 模块依赖 Editor 子系统但 LoadingPhase 太早**

```cpp
void FMyEditorModule::StartupModule()
{
    auto& AssetTools = FModuleManager::LoadModuleChecked<FAssetToolsModule>("AssetTools");
    AssetTools.Get().RegisterAssetTypeActions(...);   // ← 太早会崩或没效果
}
```

Editor 工具的注册要确保 AssetTools / LevelEditor 等系统已就绪。**纪律**:Editor 工具模块 LoadingPhase 永远写 `PostEngineInit`(Slate / Editor 子系统都已起来)。

## 0.2.5 Build.cs 的高级技巧(项目级常用)

§0.1 讲了 Build.cs 的依赖三件套。这里补充项目里高频用到的进阶写法。

### 0.2.5.1 按 Target Type 条件依赖

```csharp
public class MyRTSGameplay : ModuleRules
{
    public MyRTSGameplay(ReadOnlyTargetRules Target) : base(Target)
    {
        PublicDependencyModuleNames.AddRange(new string[] {
            "Core", "CoreUObject", "Engine"
        });

        // 仅 Editor 才需要的依赖
        if (Target.bBuildEditor)
        {
            PrivateDependencyModuleNames.AddRange(new string[] {
                "UnrealEd",        // FAssetEditorManager 等
                "AssetTools",
                "PropertyEditor"
            });
        }

        // 仅服务器需要的依赖(假设你有自研验证模块)
        if (Target.Type == TargetType.Server)
        {
            PrivateDependencyModuleNames.Add("MyRTSAntiCheat");
        }

        // Shipping 关掉某些调试依赖
        if (Target.Configuration != UnrealTargetConfiguration.Shipping)
        {
            PrivateDependencyModuleNames.Add("MyRTSDebugUI");
        }
    }
}
```

### 0.2.5.2 按平台分支

```csharp
if (Target.Platform == UnrealTargetPlatform.Win64)
{
    PublicSystemLibraries.Add("d3d12.lib");
    PublicSystemIncludePaths.Add(Path.Combine(Target.WindowsPlatform.WindowsSdkDir, "Include", "10.0.22000.0", "um"));
}
else if (Target.Platform.IsInGroup(UnrealPlatformGroup.Linux))
{
    PublicAdditionalLibraries.Add("/usr/lib/x86_64-linux-gnu/libsomething.so");
}
```

### 0.2.5.3 自定义全局宏

```csharp
PublicDefinitions.Add("MYRTS_USE_FAST_PATH=1");
PrivateDefinitions.Add("INTERNAL_DEBUG_HOOK=1");
```

`PublicDefinitions` 会传递给所有依赖此模块的下游;`PrivateDefinitions` 仅本模块编译用。

### 0.2.5.4 第三方库(External Module)

```csharp
public class MyImGui : ModuleRules
{
    public MyImGui(ReadOnlyTargetRules Target) : base(Target)
    {
        Type = ModuleType.External;          // ← 关键:不编译,只暴露
        PublicSystemIncludePaths.Add(
            Path.Combine(ModuleDirectory, "include"));
        PublicAdditionalLibraries.Add(
            Path.Combine(ModuleDirectory, "lib", "imgui.lib"));
    }
}
```

`ThirdParty/` 下的库基本都是这种写法。

### 0.2.5.5 关闭 Unity / 调单文件 PCH

调试期某个 .cpp 编译报错很乱(Unity 把多个 .cpp 拼了)?:

```csharp
// 全模块关闭 Unity
bUseUnity = false;

// 或者调高阈值,等价于关闭
MinSourceFilesForUnityBuildOverride = 999;

// 关闭单元最小数量(通常 8)
MinFilesUsingPrecompiledHeaderOverride = 1;
```

### 0.2.5.6 IWYUSupport

```csharp
IWYUSupport = IWYUSupport.Full;   // 强制 IWYU,不暴露不必要的 include
// IWYUSupport.None;             // 老式聚合 include
// IWYUSupport.KeepAsIs;         // 保留现有,不审查
```

新模块**强烈建议** Full。

## 0.2.6 Engine 补丁管理(rebase 友好的核心)

这一节是这一章的"压轴"。**90% 的项目两年后冲突地狱都是因为这一节没做好**。

### 0.2.6.1 永远先想"能不能不改 Engine"

依次尝试:

1. **写一个 Subclass**:`UMyMassProcessor : public UMassProcessor`,重写虚函数。
2. **注册一个 Subsystem**:`UMyWorldSubsystem` 替代你想加在 `UWorld` 里的功能。
3. **Hook 委托**:UE 大量公共委托(`FGameDelegates::Get().OnPostSpawnActor` 等)能让你"在不动 Engine 的前提下"插入逻辑。
4. **代理模式**:写一个外部代理类,在游戏代码里调用 Engine API 完成你想要的事,而不是改 Engine。
5. **CDO 修改**:很多 Engine 类的默认行为可以通过修改 CDO(在 GameInstance 启动时)调整。
6. **Console Variable**:Engine 有几千个 cvar,你想要的"配置型修改"很可能已经被 cvar 覆盖了。
7. **如果以上都不行,才改 Engine。**

### 0.2.6.2 改 Engine 的几条铁律

**(1)改动必须**集中**到独立的补丁文件,不能直接 commit 到 Engine 目录混着改**。

正确做法:在项目根有一个 `EnginePatches/` 目录:

```
EnginePatches/
├── README.md                                    
├── 0001-mass-batch-create-perf-fix.patch        (来自 git format-patch)
├── 0002-ismc-instance-buffer-upload.patch
├── 0003-add-rts-network-hook.patch
└── BASE_HASH.txt                                上游 Epic 的 base commit hash
```

每次 rebase 上游 Epic 的新版本,流程是:
1. `git checkout <new-epic-tag>`
2. 重新 apply 所有 .patch 文件
3. 处理冲突
4. 重新 `git format-patch` 导出,更新 EnginePatches/

**(2)每个补丁文件要回答三个问题**:
- 为什么改?(业务背景)
- 上游什么时候可能 fix(等 Epic 修了就可以删)
- 影响哪些代码(哪些其它系统会被这个改动影响)

写在 commit message 里,导出 patch 时自然就带上。

**(3)改动要尽量"加",少"改",更少"删"**:
- ✅ 加新虚函数(`virtual void OnXxx()`)
- ✅ 加新成员变量
- ✅ 加新公开 API
- ❌ 改现有函数签名
- ❌ 删现有代码
- ❌ 改现有数据结构内存布局

理由:加东西在 rebase 时几乎不冲突,改/删的内容在 Epic 也修同一段时**必然**冲突。

**(4)用编译宏隔离改动**:

```cpp
// Engine/Source/Runtime/MassEntity/Public/MassEntityManager.h
class FMassEntityManager
{
    // ... Epic 原有代码 ...

#if MYRTS_MASS_PATCHES
    // 你加的内容,集中在一块,清晰可见
    void BatchCreateEntitiesFast(...);
#endif
};
```

`MYRTS_MASS_PATCHES` 在你的 Build.cs 里定义。这样:
- 如果将来想"暂时关掉所有 RTS 补丁"测一下原版行为,定义一改就行
- rebase 时"我加的"和"Epic 原有的"一眼区分

**(5)BASE_HASH.txt 必须明确**:

```
EnginePatches/BASE_HASH.txt:
Upstream base: tag 5.7.3 (commit 0b917fe1ab67)
Last rebase: 2026-05-14 by yixiao.liu
Next planned rebase: 5.8 (when stable)
```

下次 rebase 时一眼知道"我们在哪个版本上"。

### 0.2.6.3 git 工作流的两种主流方案

**方案 A:fork 引擎仓库,补丁直接 commit 进去**

适合:大团队、引擎改动多。
做法:从 Epic 的 release 分支拉出自己的 release-myrts 分支,直接 commit。每次同步用 `git rebase` 上游。
缺点:rebase 上游时整个分支历史要重写,冲突非常痛。

**方案 B:补丁外置,引擎仓库不改**(推荐小团队)

适合:小团队、引擎改动少。
做法:Engine/ 保持纯净,所有改动放 `EnginePatches/`。每次同步:
1. `git checkout <upstream-tag> -- Engine/`(强制覆盖)
2. `for p in EnginePatches/*.patch; do git apply $p; done`
3. 解决冲突,format-patch 导出新 patch

缺点:不能 git blame 到具体改动(blame 会指向 apply patch 的那次 commit)。

**当前这个仓库**(看 `git log` 的痕迹)看上去是**方案 A**,因为 commit 历史里有大量 Epic 之外的项目改动。这是大团队的经典姿势,但需要严格的 commit message 纪律。

### 0.2.6.4 一个真实场景模拟

假设你今天发现 `FMassEntityManager::BatchCreateEntities` 在 50K 单位时性能不够,想加一个快速路径。

**方案 A 的做法**:
```bash
# 在引擎仓库里
git checkout -b feature/mass-batch-fast-path
# 改 Engine/Source/Runtime/MassEntity/Private/MassEntityManager.cpp
# 加新方法
git add ...
git commit -m "[MyRTS] Add fast path for BatchCreateEntities

Why: profiling shows 5ms/frame at 50K entities in vanilla path
Affected: MassEntityManager.h/cpp
Upstream tracking: filed UE-XXXXX, may be fixed in 5.8
"
```

**方案 B 的做法**:
```bash
# 在 git 里改 Engine 文件
git diff > EnginePatches/0007-mass-batch-fast-path.patch
git checkout -- Engine/   # 把工作区清回去
# 然后在项目仓库 commit 这个 .patch 文件
```

两种方案都需要把"为什么改"用 commit message 或 README 写清楚。

### 0.2.6.5 改 Engine 时的"红线"

绝对不要做的事:
1. 改公开数据结构的内存布局(`UClass`、`UObject`、`FMassArchetypeData` 等)— ABI 一变,你二进制资产全部失效
2. 改虚函数表的顺序 — 同上,ABI 灾难
3. 删除 / 重命名现有公开 API — 会让其它 Plugin 编译失败
4. 改静态全局变量的初始化时机 — 会让启动期出现奇怪的 crash
5. 删除现有的反射类 / 函数 — 会让旧资产无法加载

如果你**确实**需要做 1-5 任意一条,先想清楚:**这是不是说明你应该完全自定义一个新类型,而不是改 Engine 现有的?** 99% 答案是 yes。

## 0.2.7 Live Coding / Hot Reload 与模块设计

### 0.2.7.1 两套机制的区别

| | Hot Reload(老) | Live Coding(新,推荐) |
|---|---|---|
| 触发 | Editor 里点"Compile" | VS 里 Ctrl+Alt+F11 |
| 范围 | 重编整个 Module | 重编单 .cpp 的改动 |
| 实现 | 替换整个 .dll | patch .obj,运行时打热补丁 |
| 速度 | 中等(秒到十几秒) | 极快(亚秒到秒) |
| 侵入性 | 大(替换 UObject,可能丢数据) | 小(不替换 UObject) |

**5.x 里 Live Coding 是默认推荐方式**,Hot Reload 已经被官方建议禁用(Editor 设置里 "Enable Live Coding" 默认开,"Enable Hot Reload" 默认关)。

### 0.2.7.2 Live Coding 不能做什么

Live Coding 用 Visual Studio 的 EditAndContinue + 自研补丁器实现,本质是"在已加载的 .obj 上 patch 函数代码"。所以:

❌ **加新 UCLASS / USTRUCT** — 反射类型已经注册,加新类型需要重启
❌ **改 UCLASS / USTRUCT 的字段**(加 / 删 UPROPERTY)— 同上,反射结构变了
❌ **改虚函数表**(新虚函数、虚继承变化)
❌ **改类的内存布局**

✅ **改函数体**(任意函数,包括虚函数、内联函数)
✅ **加非反射的成员变量、函数**(只要不改类对象大小)
✅ **改 cvar 默认值**

**纪律**:开发期对 UCLASS / USTRUCT 的字段改动会触发 Live Coding 失败 — 每次失败你只能重启 Editor,**很**疼。所以 Mass Fragment 设计期尽量一次到位,后期只改逻辑不改字段。

### 0.2.7.3 跨模块依赖与 Live Coding

如果模块 A 依赖 B,改了 B 的非 inline 函数 → 只重编 B → A 不重编也能用。
但如果改了 B 的 inline 函数(大量 Mass 模板代码就是 inline)→ A 也得跟着重编 → Live Coding 触发整链重编 → 可能失败。

**纪律**:Mass Processor 的核心逻辑**避免**写在 inline 函数里。把热点逻辑写在 .cpp 里,头文件只暴露最小接口。

## 0.2.8 一个 RTS 项目骨架的最小落地清单

如果你今天就要开干,跟着做:

### 步骤 1:GenerateProjectFiles

确保你的 UE5.7.3 引擎已 build 成功,`UnrealEditor.exe` 能跑。

### 步骤 2:创建空白 C++ 项目

Editor 里 File → New Project → C++ Empty → MyRTS。
得到:

```
MyRTS.uproject
```

### 步骤 3:加 Server / Client Target

`Source/MyRTSServer.Target.cs`:
```csharp
using UnrealBuildTool;
```

### 步骤 4:加第一个 Plugin(MyRTSCore)

`MyRTSCore.uplugin`:
```json
{
    "FileVersion": 3,
```

`Build.cs`、`Public/MyRTSCore.h`、`Private/MyRTSCore.cpp` 按 §0.1.9 的步骤 2-4 写。

```json

    "EngineAssociation": "5.7",

        { "Name": "MyRTSCore", "Enabled": true },
```

`Source/MyRTS/MyRTS.Build.cs`:
```csharp
PublicDependencyModuleNames.AddRange(new string[] {
    "Core", "CoreUObject", "Engine", "InputCore",

});
```

```

```

跑起来打开 Editor,确认无报错。

### 步骤 8:加 EnginePatches/ 目录(即使现在是空的)

```
EnginePatches/
├── README.md
└── BASE_HASH.txt    (写 "Upstream: 5.7.3 / commit 0b917fe1ab67")
```

**预先**建好这个目录的好处:第一次想改 Engine 时不会"为图一时方便"直接 commit 到 Engine 里,而是去 EnginePatches/ 写 patch。**习惯比工具重要**。

## 0.2.9 与 Mass 重构的对照思考

这一节工程组织看似离 Mass 还很远。但有几条直接决定你后续能不能"优雅地重构":

### (1)Fragment 模块必须独立

`MyRTSCore` 应该**只**含 Fragment 类型定义、Tag 类型定义、共享 Subsystem 接口。**不**含任何 Processor 实现、AI 逻辑、网络代码。

**理由**:Fragment 的内存布局是整个 RTS 的"基石数据",一旦稳定就**几乎**不再改。你战斗代码改 1000 次,Core 应该不变。这样:
- Live Coding 改 Processor 时,Core 不用重编
- Core 当作"通用 RTS 框架"可以复用到下一个项目

### (2)Editor Trait 与 Runtime Trait 分模块

`UMassEntityTraitBase` 子类:
- 类**本身**(数据结构)放运行时模块(MyRTSMass)
- DetailsCustomization、PropertyCustomization 放 Editor 模块(MyRTSMassEditor)
- 配置资产(`UDataAsset` 子类)放 Core

理由:Trait 数据 cooked 包要带,DetailsCustomization 不带。混在一起会让 Shipping 包变臃肿且引入不必要的 Editor-only 头依赖。

### (3)Processor 模块的依赖纪律

Mass Processor 经常需要访问:
- 自定义 Fragment(在 Core)
- Subsystem(在 Core 或 Gameplay)
- 渲染相关(在 Render)

但 **Render 模块不应反过来依赖 Mass 模块**(单向依赖)。这点违反会立刻形成循环依赖,UBT 会拒绝编译,逼你解开。

### (4)上游 rebase 的"安全距离"

每次 5.x → 5.x+1 升级,Mass 都可能有破坏性改动(从 5.4 → 5.5 整个 Plugin 都被搬到 Engine 了)。你的项目代码层结构越独立,越能扛住这种动荡。

**纪律**:你的 RTS 代码**不要**`#include` Mass 内部 Private 头(`Engine/Source/Runtime/MassEntity/Private/...`)。只用 Public 接口。Private 头改了你不冲突,Public API 改了 Epic 一般会发 deprecation warning 提前一两个版本警告。
