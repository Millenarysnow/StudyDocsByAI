## 4.2.1 浅入:GC 不是"自动神奇" — 它有明确节奏

很多新手以为 GC 是引擎"在某一刻偷偷跑完",其实不是。**GC 由游戏代码**或**引擎 Tick**显式触发,有完整的状态机和时序:

```
游戏运行
  ↓
某帧 Tick:
  ↓
  WorldTickStart →
    World->Tick() {
      // 各子系统 tick
      // ...
      // 在某个 TickGroup 末尾或专门的 GC tick:
      if (ShouldRunGC()) {
        CollectGarbage(RF_Standalone, /*bFullPurge*/ false);
        // 可能要花几 ms,卡这一帧
      }
    }
  ↓
WorldTickEnd
```

`ShouldRunGC()` 内部检查:
- 距上次 GC 时间 ≥ `gc.TimeBetweenPurgingPendingKillObjects`(默认 60 秒)
- 累计内存增长超阈值
- 显式标记 `GEngine->ForceGarbageCollection()`
- AutoRTFM 不在事务里

满足条件 → CollectGarbage。

## 4.2.2 完整 GC 入口:`CollectGarbage`

`Engine/Source/Runtime/CoreUObject/Private/UObject/GarbageCollection.cpp:6203`:

```cpp
void CollectGarbage(EObjectFlags KeepFlags, bool bPerformFullPurge)
{
    if (GIsInitialLoad)
    {
        UE_LOG(LogGarbage, Log, TEXT("Skipping CollectGarbage() call during initial load. It's not safe."));
        return;
    }

    AcquireGCLock();
    UE::GC::CollectGarbageInternal(KeepFlags, bPerformFullPurge);
}
```

参数:
- `KeepFlags`:不被 GC 的对象 flag 集合。常用 `RF_Standalone`(独立资产,Editor 模式)或 `RF_NoFlags`(Game 模式,无额外保留)。
- `bPerformFullPurge`:是否走"完整 GC"(默认 false,走增量;true 时阻塞直到全部清理完)。

### 4.2.2.1 `GARBAGE_COLLECTION_KEEPFLAGS`

`GarbageCollection.h:28`:

```cpp
#define GARBAGE_COLLECTION_KEEPFLAGS  (GIsEditor ? RF_Standalone : RF_NoFlags)
```

游戏代码常用调法:

```cpp
CollectGarbage(GARBAGE_COLLECTION_KEEPFLAGS);                        // 默认增量,KeepFlags 自适应
CollectGarbage(RF_NoFlags, /*bPerformFullPurge*/ true);               // 完整 GC,阻塞
```

### 4.2.2.2 `TryCollectGarbage`(非阻塞版本)

`GarbageCollection.cpp:6221`:

```cpp
bool TryCollectGarbage(EObjectFlags KeepFlags, bool bPerformFullPurge)
{
    if (GIsInitialLoad) return false;
    
    if (AutoRTFM::IsTransactional()) return false;       // 事务里不 GC
    
    if (UE::GC::GIsIncrementalReachabilityPending) {
        AcquireGCLock();    // 已经在 GC 中,必须阻塞
    } else if (!FGCCSyncObject::Get().TryGCLock()) {
        return false;       // 别的线程在用 UObject,无法获锁,放弃
    }
    
    UE::GC::CollectGarbageInternal(KeepFlags, bPerformFullPurge);
    return true;
}
```

`TryCollectGarbage` 比 `CollectGarbage` 更宽容:**拿不到锁就放弃**,不阻塞。适合"我想 GC,但卡住游戏不行"的场景。

### 4.2.2.3 不能 GC 的 4 个时机

`CollectGarbage` 内部检查这些条件,任一为真就跳过:

1. **`GIsInitialLoad`** —— 引擎启动期(GUObjectArray 还在装填,GC token stream 可能未就绪)
2. **`AutoRTFM::IsTransactional()`** —— 5.x 事务运行中,GC 释放对象会让事务无法回滚
3. **GC lock 已被其它线程持有** —— `FGCCSyncObject::Get().TryGCLock()` 失败
4. **重入** —— GC 内部调到 GC,直接退出

实战:`CollectGarbage` 总是从 GameThread 调,确保不冲突。

## 4.2.3 增量 vs 完整 — 两种 GC 模式

### 4.2.3.1 什么是增量

GC 标记阶段(reachability analysis)需要遍历整个 GUObjectArray + 所有引用边。50 万 UObject 的 World,标记可能要 5-15 ms。**这一帧就丢了**。

5.x 引入"**增量 reachability**":把 reachability analysis 拆成多帧执行,每帧花 1-2 ms,几帧后才完成 mark。这样**单帧 hitch 显著减少**。

清理阶段(sweep)同样可拆:`IncrementalPurgeGarbage`。

### 4.2.3.2 完整 GC(`bPerformFullPurge = true`)

```cpp
CollectGarbage(RF_NoFlags, /*FullPurge*/ true);
```

行为:
- 阻塞 GameThread 直到**所有标记 + 所有清理**完成
- 单帧时间可能 50-200ms(World 大)
- 适合"已知会卡的时机":关卡加载 / 玩家退出 / 切换战役

### 4.2.3.3 增量 GC(默认)

```cpp
CollectGarbage(RF_NoFlags, /*FullPurge*/ false);     // 默认
```

或者引擎自动调度:World->Tick 中检测时机自动触发,默认增量。

行为:
- Mark 阶段拆若干帧
- Sweep 阶段拆若干帧
- 每帧阻塞 1-2 ms(可调)
- 适合"游戏运行中"

### 4.2.3.4 `IncrementalPurgeGarbage`

`GarbageCollection.cpp:4652`:

```cpp
void IncrementalPurgeGarbage(bool bUseTimeLimit, double TimeLimit)
{
    SCOPED_NAMED_EVENT(IncrementalPurgeGarbage, FColor::Red);
    
    // 拆开 BeginDestroy / FinishDestroy 阶段(§4.4)
    // 每次只处理一定数量对象(看 TimeLimit)
    // ...
}
```

`bUseTimeLimit = true` + `TimeLimit = 0.002`(2 ms)是典型参数。引擎 Tick 每帧调一次,阻塞最多 2 ms。

## 4.2.4 关键 cvar(GC 调谐)

下面这些 cvar 是 GC 行为的旋钮。**记下来,RTS 上线前做对比测试**:

### 4.2.4.1 触发节奏

| cvar | 默认 | 含义 |
|---|---|---|
| `gc.TimeBetweenPurgingPendingKillObjects` | 60 (秒) | 两次完整 GC 的最小间隔 |
| `gc.LowMemory.TimeBetweenPurgingPendingKillObjects` | 30 | 低内存模式下的 GC 间隔 |
| `gc.LowMemory.MemoryThresholdMB` | 10240 | 触发"低内存模式"的阈值 |
| `gc.NumRetriesBeforeForcingGC` | 5 | NewObject 失败时,触发 GC 的重试次数 |
| `gc.AllowParallelGC` | 1 | 启用并行标记 |
| `gc.MaxObjectsInGameWorld` | 0 (未限) | 对象数上限触发 GC |
| `gc.MaxObjectsInEditor` | 25M | Editor 上限 |

### 4.2.4.2 增量行为

| cvar | 默认 | 含义 |
|---|---|---|
| `gc.IncrementalGCTimePerFrame` | 0.002 | 增量 GC 每帧时间预算(秒) |
| `gc.IncrementalReachabilityTimeLimit` | 0.002 | 增量 reachability 每帧 |
| `gc.AllowIncrementalReachability` | 1 | 5.x 启用 |

### 4.2.4.3 调试

| cvar | 默认 | 含义 |
|---|---|---|
| `gc.CollectGarbageEveryFrame` | 0 | 强制每帧跑(极慢,debug 用) |
| `gc.VerifyGCObjectNames` | 0 | 验证 GC 对象名一致性 |
| `gc.VerifyAssumptions` | 0 | 启用各种 GC 内部断言 |
| `gc.DumpAllReferencers` | 0 | 输出每个对象的引用链 |

### 4.2.4.4 实战调谐示例

```
# Editor 长时间使用,内存压力大
[ConsoleVariables]
gc.TimeBetweenPurgingPendingKillObjects=30        ; 30 秒一次 GC
gc.LowMemory.MemoryThresholdMB=4096               ; 内存超 4GB 触发更激进

# RTS Game build,优化帧率
gc.AllowIncrementalReachability=1
gc.IncrementalReachabilityTimeLimit=0.001         ; 每帧只用 1ms 做 mark
gc.AllowParallelGC=1                              ; 并行标记
```

## 4.2.5 GC 触发的几种实际场景

### 4.2.5.1 引擎 Tick 自动触发

`UEngine::ConditionalCollectGarbage`(WorldTickStart 附近被调):

```cpp
// 简化伪代码
void UEngine::ConditionalCollectGarbage()
{
    if (TimeSinceLastGC > gc.TimeBetweenPurgingPendingKillObjects ||
        IsLowMemory() ||
        bForceGC)
    {
        bool bFullPurge = bForceGC || /* ... 其它条件 ... */;
        CollectGarbage(GARBAGE_COLLECTION_KEEPFLAGS, bFullPurge);
        TimeSinceLastGC = 0;
        bForceGC = false;
    }
}
```

每帧检查,满足条件就启动。

### 4.2.5.2 显式触发:`GEngine->ForceGarbageCollection`

```cpp
// 关键时机手动触发
GEngine->ForceGarbageCollection(/*bFullPurge*/ true);
```

设 `bForceGC = true`,下一次 ConditionalCollectGarbage 跑完整 GC。

**实战时机**:
- 关卡切换前 / 后
- 战役章节切换
- 战斗结束(回大厅时清理战斗对象)
- 玩家退出 PIE
- Editor 切换关卡

### 4.2.5.3 NewObject 内存压力触发

如果 GUObjectArray 接近 `gc.MaxObjectsInEditor` 上限,NewObject 会触发 `CollectGarbage` 释放空间,然后重试。`gc.NumRetriesBeforeForcingGC` 控制重试次数。

### 4.2.5.4 World 切换的 GC

```cpp
// LoadLevel / OpenLevel 内部:
UEngine::LoadMap(...)
{
    // ... 卸载旧 World ...
    CollectGarbage(GARBAGE_COLLECTION_KEEPFLAGS, /*bFullPurge*/ true);
    // 强制完整 GC,清空旧关卡所有对象
    // ... 加载新 World ...
}
```

这是为什么"切关卡时卡一下" —— 一次性 50-200 ms 的 stop-the-world GC。

## 4.2.6 5.x 增量 reachability —— 不再是 stop-the-world

5.0 之前 GC mark 阶段必须**完整跑完**才能进 sweep。期间 GameThread 阻塞。

5.x 起 `gc.AllowIncrementalReachability = 1`(默认)启用增量 mark:

```
完整 mark(老 5.0):
  Frame N:  ┌────── 12 ms mark ──────┐ + 渲染 → 帧时间 28 ms,卡!

增量 mark(新):
  Frame N:    ┌─2ms─┐ render        → 帧时间 18 ms
  Frame N+1:  ┌─2ms─┐ render        → 帧时间 18 ms
  Frame N+2:  ┌─2ms─┐ render        → 帧时间 18 ms
  ...(直到 mark 完成)
  Frame N+M:  完整 mark 完成,触发 sweep
```

代价:GC 总时间略长(增量切换有开销),但**单帧 hitch 消失**。RTS / 多人游戏体验显著提升。

**前提**:增量 mark 需要"barrier"机制 —— 在 mark 期间,任何**新创建的 UObject 引用**必须额外通知 GC(否则可能漏标记)。这是 5.x GC 系统重写的核心。

### 4.2.6.1 `GIsIncrementalReachabilityPending`

```cpp
extern bool GIsIncrementalReachabilityPending;     // 是否有正在进行的增量 mark
```

`TryCollectGarbage` 看到这个为 true,知道"上次 GC 还没完",必须阻塞等。

## 4.2.7 `stat gc` 输出读图

游戏运行时控制台输入 `stat gc`,屏幕显示:

```
GC Stats:
  Mark Time         : 12.3 ms (avg)
  Sweep Time        : 8.5 ms
  Total Time        : 22.4 ms
  Objects (total)   : 158234
  Objects (purged)  : 5210
  Objects (clusters): 8
```

关注:
- **Mark Time** 是标记阶段
- **Sweep Time** 是清理阶段
- **Objects (total)** 是 GUObjectArray 总数(§3.2)
- **Objects (purged)** 是本次回收的数量

健康指标:
- Editor:总耗时 < 50 ms,可接受
- Game:总耗时 < 5 ms / 帧(增量后),否则要调谐

### 4.2.7.1 Insights 看 GC 时间线

启动加 `-trace=cpu,gc`,Insights 里搜:
- `CollectGarbage` scope
- `IncrementalPurgeGarbage`
- `MarkObjectsAsUnreachable`
- `ConditionalBeginDestroy`

每个都标着具体耗时。增量 GC 时,你会看到这些 scope **跨多帧分布**。

## 4.2.8 Editor / Game / Server 的 GC 节奏差异

| 场景 | 默认 GC 间隔 | 触发激进度 |
|---|---|---|
| **Editor** | 60s | 中等(Editor 内存压力大,但用户操作不能卡) |
| **Game(玩家)** | 60s | 低(尽量不卡) |
| **Server**(专用) | 30s | 高(服务器内存珍贵,优先回收) |
| **PIE** | 60s | 同 Editor |

服务器 build 的 `gc.TimeBetweenPurgingPendingKillObjects` 默认更小(更频繁 GC),因为:
- 服务器进程跑数小时数天,内存累积明显
- 服务器无图形,玩家看不到 GC 卡顿

## 4.2.9 `EObjectFlags` 与 KeepFlags

`CollectGarbage(KeepFlags, ...)` 的 KeepFlags 决定"哪些对象不被 GC"(强制 root)。

**Editor 模式**(`GIsEditor = true`):用 `RF_Standalone`。所有"独立资产"(Mesh、Material 这些被引用的资产)被 keep。**结果**:Editor GC 不删资产,只删玩家创建的临时对象。

**Game 模式**:`RF_NoFlags`(空)。所有对象按引用图判断,无关资产可被回收。**结果**:更彻底的 GC,适合游戏运行时。

实战:`CollectGarbage(GARBAGE_COLLECTION_KEEPFLAGS)` 自动适配。

## 4.2.10 `gc.MaxObjectsInGameWorld` —— 对象上限保险

```
gc.MaxObjectsInGameWorld 0       # 默认 0 = 不限
gc.MaxObjectsInEditor 25000000   # Editor 默认 2500 万
```

含义:`GUObjectArray.Num` 接近这个值时,触发激进 GC。如果 GC 后仍超过,**进程 fatal**。

实战:
- Game build 默认 0 = 无限,GUObjectArray 真满了才崩(几百万对象级)。这个上限通常不用调。
- Editor 默认 2500 万,但实际 Editor 一般 < 100 万。设这么大就是为了"几乎不可能撞上"。

## 4.2.11 RTS 项目的 GC 触发策略

### (1)关卡切换时强制完整 GC

```cpp
void URTSGameInstance::SwitchMap(FString MapName)
{
    UGameplayStatics::OpenLevel(this, *MapName);
    // OpenLevel 内部已经会触发 GC,但如果想确保更彻底:
    GEngine->ForceGarbageCollection(/*bFullPurge*/ true);
}
```

### (2)战斗结束时主动 GC

```cpp
void URTSBattleSubsystem::EndBattle()
{
    DestroyAllUnits();         // Destroy actor + Mass entity 销毁
    
    // 主动触发 GC,清理战斗中累积的临时对象
    GEngine->ForceGarbageCollection(/*bFullPurge*/ false);   // 增量
}
```

`bFullPurge = false` 增量模式,不卡 GameThread。下一帧可能开始大厅 UI,GC 在后台进行。

### (3)Mass Spawner / Despawner 不直接触发 GC

**Mass entity 不是 UObject**,创建 / 销毁 entity **不**给 GUObjectArray 加压力。所以你大批量 spawn / despawn 单位**不需要**手动触发 GC。

### (4)避免 GC 卡顿的最重要纪律

让 Editor / Game 的 GC 不卡,关键是 **GUObjectArray 总数控制**:

```
✅ Mass entity:0 个 UObject 增加
✅ ISM 实例:UISMC 一个 UObject,实例数据在 GPU
✅ Particle:Niagara 共享 UObject,粒子数据在 GPU
❌ AStaticMeshActor 数千个:每个一个 Actor + 一个 Component = 几千 UObject
```

一个 RTS 项目正常 GUObjectArray 约 50K-200K(Editor 高,Game 低)。如果你看到 500K+,优化方向是**把"一类东西"从 Actor 换成 Mass / ISM**。

## 4.2.12 实操:测 GC 耗时

```cpp
static FAutoConsoleCommand CmdMeasureGC(TEXT("rts.MeasureGC"),
    TEXT("Measure GC time"),
    FConsoleCommandDelegate::CreateLambda([]()
    {
        double Start = FPlatformTime::Seconds();
        CollectGarbage(GARBAGE_COLLECTION_KEEPFLAGS, /*bFullPurge*/ true);
        double Elapsed = FPlatformTime::Seconds() - Start;
        
        UE_LOG(LogTemp, Display, TEXT("Full GC took %.2f ms"), Elapsed * 1000.0);
        UE_LOG(LogTemp, Display, TEXT("GUObjectArray: %d / %d"), 
            GUObjectArray.GetObjectArrayNum(), GUObjectArray.GetObjectArrayCapacity());
    }));
```

跑 `rts.MeasureGC`,看你项目当前完整 GC 多久。一个干净 Game build 通常 < 5 ms,Editor 加载完几个关卡可能 30-100 ms。

## 4.2.13 实操提示与下一节预告

### 实操提示

- **看 GC 频率**:启动加 `-trace=gc,frame`,Insights 时间线上 GC scope 清晰可见,频率一目了然
- **诊断"GC 太频繁"**:可能是 GUObjectArray 增长太快。检查是否有循环创建 UObject 的代码
- **诊断"GC 太慢"**:可能是 GUObjectArray 太大。看每类 UObject 数量,优化最多的那种
- **临时关 GC**:debug 时 `gc.NumRetriesBeforeForcingGC -1` + `gc.MaxObjectsInGameWorld 100000000`,基本不再触发 GC,排查问题完后改回
