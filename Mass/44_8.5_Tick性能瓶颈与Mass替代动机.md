## 8.5.1 Actor Tick 的开销组成

每个 Actor::Tick 调用,**单次开销**包含:

```
1. 调度开销(从 TickTaskManager 队列取出)        ~20-50 ns
2. 虚函数派发(多态调对正确的 Tick 实现)         ~10-20 ns
3. 你的 Tick 代码(可短可长)                       依业务
4. Stat 累加(`SCOPE_CYCLE_COUNTER`)               ~50-100 ns(开 STATS 时)
5. 屏障同步(等其它 prerequisite 完成)             ~0-1 μs
```

**最少**也是几百纳秒 / Actor。复杂 Actor(动画、AI 决策、动力学)单次 Tick 几十 μs - 几百 μs。

50K Actor × 1 μs / Tick = **50 ms / 帧** —— 帧预算 16.6 ms,**直接卡死 3 倍**。

---

## 8.5.2 Component Tick 的进一步开销

每个 Actor 通常带 5-10 Component(Mesh / Movement / Capsule / SkeletalMesh / 自定义 logic 等)。每 Component 的 PrimaryComponentTick 也是 TickFunction:

```
Actor 50K × 5 Component = 250K TickFunction
   ↓ 每 TickFunction 平均 500 ns
250K × 500 ns = 125 ms / 帧
```

**完全不可行**。

实战 RTS 项目里,**单兵种 actor 通常 3-5 component**:Mesh / Movement / Capsule + 1-2 自定义 logic。50K × 4 = 200K,250 ms 量级。

---

## 8.5.3 Tick 的"虚函数 + cache miss" 双重代价

每个 Actor::Tick 是虚函数调用:
- 派发到正确的 `AMyActor::Tick` 实现
- 必须从 vtable 间接跳

每个 Actor / Component **在堆上的不同位置**:
- 50K Actor 散落在堆,每次 Tick 一次 cache miss
- 数据访问也 cache miss

**Cache 不友好** + **虚函数** = 单次 Tick 实际 ~ 1-3 μs(典型),不是理论值 200 ns。

Mass 通过:
- **SoA 内存布局**:同类型 entity 的 Fragment 紧密排列,顺序访问
- **批量循环**:一个 Processor 一次扫几百到几千个 entity,vtable 调用摊到批次
- **SIMD 友好**:连续 float / int 数组,编译器自动向量化(`Velocity += Acceleration * dt`)

50K entity 单 Processor 扫描:**几纳秒 / entity** × 50K = **几百 μs**。比 Actor Tick 快 **100 倍**。

## 8.5.4 数字对照

```
RTS 50K 单位场景:

Actor + Component 体系:
   - SpawnActor 50K × 200 μs = 10 秒(开局卡死)
   - GC mark / 帧 = 5-15 ms
   - Tick / 帧:
     ├─ Actor Tick × 50K          = 50-100 ms
     ├─ Component Tick × 200K     = 100-200 ms
     ├─ 渲染 SceneProxy × 50K     = 30-60 ms
     ├─ 物理 Body × 50K           = 20-50 ms
     ├─ ServerReplicateActors      = 50-200 ms
     ├─ NewlySpawned 重跑          = 几十 ms
   - 总帧时间                      = 数百 ms - 1 秒
   ❌ 完全不可行

Mass entity 体系:
   - CreateEntity 50K × 500 ns = 25 ms(可分摊)
   - GC 不变(50K entity 不增 GUObjectArray)
   - Tick / 帧:
     ├─ Mass PrePhysics Processors  = 3-5 ms
     ├─ Mass DuringPhysics(并行)    = 1-2 ms
     ├─ Mass PostPhysics             = 0.5-1 ms
     ├─ Mass FrameEnd(LOD/Repr)     = 1-2 ms
     ├─ ISMC 渲染                     = 3-6 ms
     ├─ Mass 网络复制                 = 1-2 ms
   - 总 Mass 相关                   = 10-15 ms
   ✅ 可行
```

**两个体系差 1-2 个数量级**。这就是 Mass 必要性的硬证据。

## 8.5.5 性能优化的"边际效益递减"

如果你尝试**优化 Actor 体系**让它扛 50K 单位:

```
✘ 关闭 Component 不必要 tick → 省 30%
✘ 用 ISMC 替代 SkeletalMesh → 省 50% 渲染开销
✘ 简化 Tick body → 省 20%
✘ 异步 Tick(AnyThread)→ 节省 GameThread 但全总量没变
✘ NetUpdateFrequency 调低 → 省 50% 网络

总优化 ~70-80%
50 ms × 0.2-0.3 = 10-15 ms / 帧
```

**仍然不够**。Actor 体系的固定开销(虚函数、TickFunction 注册、Component 注册、SceneProxy)即使优化也吃掉大部分预算。

Mass 不是"优化的 Actor",是**完全不同的内存模型**:
- 无虚函数派发
- 无 vtable 引用
- SoA + cache friendly + SIMD

这是为什么 Mass 不只是"快一点",而是"快两个数量级"。

## 8.5.6 RTS 项目的"混合架构"标准方案

```cpp
// 重要 Actor(数量 < 100,行为复杂,BP 可写,网络复制)
✅ AHero        : public ACharacter      // 玩家英雄
✅ ABoss        : public ACharacter      // Boss
✅ AMainBase    : public AActor          // 主基地建筑
✅ APlayerHQ    : public AActor          // 玩家主城

// Mass entity(数量 >> 1000,行为简单,无 BP,自定义复制)
✅ Soldier      : Mass Fragment 组       // 兵
✅ Worker       : Mass Fragment 组       // 工人
✅ Projectile   : Mass Fragment 组       // 投射物
✅ Resource     : Mass Fragment 组       // 资源点
✅ Effect       : Niagara 系统            // 特效不是 Mass / Actor

// Subsystem(数量 < 10,管理类)
✅ URTSCombatSubsystem
✅ URTSCommandSubsystem
✅ URTSFogOfWarSubsystem
```

**经验法则**:某种东西"数量 > 100 + 行为相似" → Mass。"数量 < 100 + 个性化" → Actor。

## 8.5.7 Tick 优化纪律(给 Actor 部分)

即使 RTS 重要 actor 数量不大,Tick 仍要纪律:

### 8.5.7.1 默认关 Tick

```cpp
class AMyRTSBuilding : public AActor
{
public:
    AMyRTSBuilding()
    {
        PrimaryActorTick.bCanEverTick = false;     // ★ 默认关
        // 仅在动画 / 状态机需要时手动开
    }
};
```

### 8.5.7.2 Component Tick 总开关

```cpp
UMyComp::UMyComp()
{
    PrimaryComponentTick.bCanEverTick = false;   // 默认关
}
```

UE 内置 component(`UStaticMeshComponent` 等)默认已关,你的子类不要随手开。

### 8.5.7.3 限频 + 跳帧

低频任务:

```cpp
PrimaryActorTick.TickInterval = 0.5f;   // 0.5 秒一次
```

或 Tick 内手动跳帧:

```cpp
void Tick(float DT) override
{
    if (FrameCounter++ % 4 != 0) return;   // 每 4 帧一次
    // ...
}
```

### 8.5.7.4 Tick 内**不要** SpawnActor

```cpp
// ❌ NewlySpawned 重跑触发,本帧多干活
void Tick(float DT) override
{
    if (ShouldSpawn) {
        GetWorld()->SpawnActor<...>(...);
        ShouldSpawn = false;
    }
}

// ✅ Defer 到下一帧 / 用 Mass
GetWorld()->GetTimerManager().SetTimerForNextTick([]() { /* SpawnActor */ });
// 或直接 Mass CreateEntity
```

## 8.5.8 渐进式从 Actor 迁移到 Mass

如果你 RTS 项目最初用 Actor,后期发现性能问题需要切 Mass:

### Phase 1:量化现状

- `stat unit` / `stat game` / Insights → 找出瓶颈
- 哪种 Actor 数量最多?
- 哪个 TickGroup 最慢?

### Phase 2:Mass 化最痛的部分

- 数量最多的兵种类型先切(Soldier/Worker)
- 保留 Hero / Boss / Building 不动
- 测试性能改善

### Phase 3:Mass Trait 配置

- 旧 Actor 类的字段 → 拆成 Fragment
- 旧 ActorComponent → 拆成 Fragment / Tag
- BP 逻辑 → 改写为 Mass Processor

### Phase 4:网络层

- 旧 RepLayout → Mass Replication / Iris
- 详 §13 / §21

### Phase 5:渲染剥离

- 旧 USkeletalMeshComponent → ISMC + VAT
- 详 §25

每 Phase 之间**保持游戏可玩**,渐进。

## 8.5.9 常见误区

### 误区 1:"我用 Actor 也能 50K 单位,只是要优化"

不行。固定开销吃掉预算。即使你写出全世界最快的 Tick body,Actor / Component / TickFunction 的注册 + 调度开销就 ~ 30 μs / Actor。50K × 30 μs = 1.5 秒 / 帧。

### 误区 2:"Mass 学习曲线高,先用 Actor"

短期对,长期错。RTS 一旦上线发现性能问题,**重写**比"一开始就用 Mass"贵 5-10 倍。建议:**新 RTS 项目第一天就用 Mass**。

### 误区 3:"Mass 是新东西,不稳定"

5.x Mass 已经成熟(Epic 自家 City Sample / Matrix Awakens 都用)。生产可用。Trait / Processor / Spawner 接口稳定。

### 误区 4:"我可以混用,Hero 用 Mass / 工兵用 Actor"

反了。**重要的少数用 Actor,大量的 simple 用 Mass**。Hero 可能要 BP 写技能、要复杂动画 / 网络 / 存档,Actor 适合。Worker 数百个,行为简单(找资源、回基地、采集),Mass 适合。
