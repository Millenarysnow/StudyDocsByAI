# §5.4 Lock-Free 容器 — TQueue / TMpscQueue / TSpscQueue / TLockFreePointerListLIFO

> **本节地图**:模块一第 5 章第 4 节。多线程数据交换是并发系统的"血管"。锁太昂贵 → UE 提供一组 lock-free 容器,用 atomic CAS 实现无锁数据交换。这些容器是 Mass 命令队列、TaskGraph worker pool、网络发送队列的底层。
>
> **预备知识**:§5.1 / §5.2 / §5.3,§1.1.7(`std::atomic` 替代 `FPlatformAtomics`)。
>

> - 区分 MPSC / SPSC / MPMC 各自的 ABA / sequencing 假设

> - 知道 5.x 推荐 `std::atomic` + `TMpscQueue` / `TSpscQueue` 而非老 `TLockFreePointerListLIFO`

## 5.4.1 浅入:为什么需要 lock-free

```cpp
// 朴素:用 mutex 保护一个队列
TArray<FCommand> CommandQueue;
FCriticalSection Lock;

// 玩家线程
{
    FScopeLock S(&Lock);
    CommandQueue.Add(Cmd);
}

// 消费线程
TArray<FCommand> Local;
{
    FScopeLock S(&Lock);
    Local = MoveTemp(CommandQueue);
}
ProcessCommands(Local);
```

问题:**锁竞争**。玩家发命令时,消费线程拿走;两者频繁 enqueue/dequeue 时,争抢这把锁。

Lock-free 容器用 **atomic CAS**(Compare-And-Swap)替代锁:

```cpp
TQueue<FCommand> CommandQueue;     // SPSC 默认

// 玩家线程
CommandQueue.Enqueue(Cmd);          // 内部 atomic CAS,无锁

// 消费线程
FCommand Out;
while (CommandQueue.Dequeue(Out)) { ProcessOne(Out); }
```

**性能差距**:稳态下 lock-free 比 mutex 快 **2-10 倍**。竞争激烈时差距更大。

---

## 5.4.2 容器选型:看你有几个生产者 / 消费者

UE 容器按"**几个线程读 / 几个线程写**"分类:

| 场景 | 容器 | 头文件 |
|---|---|---|
| 1 P + 1 C(单生产单消费) | `TSpscQueue` | `Containers/SpscQueue.h` |
| 多 P + 1 C(多生产单消费) | `TMpscQueue` | `Containers/MpscQueue.h` |
| 通用 | `TQueue<T, EQueueMode>` | `Containers/Queue.h` |
| LIFO 栈(多生产多消费) | `TLockFreePointerListLIFO` | `Containers/LockFreeList.h` |
| 固定容量循环(单生产单消费) | `TCircularQueue` | `Containers/CircularQueue.h` |

**纪律**:能用更窄的就别用更宽的。SPSC 比 MPSC 快,MPSC 比 MPMC 快。

## 5.4.3 `TQueue<T, EQueueMode>` —— 通用 SPSC / MPSC

`Engine/Source/Runtime/Core/Public/Containers/Queue.h:46`:

```cpp
enum class EQueueMode
{
    Mpsc,             // Multiple Producers, Single Consumer
    Spsc,             // Single Producer, Single Consumer
    SingleThreaded,
};

template<typename T, EQueueMode Mode = EQueueMode::Spsc>
class TQueue
{
public:
    void Enqueue(T&& Item);             // 多生产 OK(Mpsc 模式)
    bool Dequeue(T& OutItem);           // 仅消费线程
    bool Peek(T& OutItem) const;        // 看队头不弹
    bool IsEmpty() const;
    void Empty();
};
```

`Queue.h:32-40` 注释:

> "This template implements an unbounded non-intrusive queue using a lock-free linked list that stores copies of the queued items."

**本质**:一个用 atomic 维护的单链表队列。

### 5.4.3.1 SPSC 用法

```cpp
TQueue<FCommand, EQueueMode::Spsc> Queue;     // 默认 SPSC

// 生产线程(只有 1 个)
Queue.Enqueue(Cmd1);
Queue.Enqueue(Cmd2);

// 消费线程(只有 1 个)
FCommand Out;
while (Queue.Dequeue(Out)) {
    Process(Out);
}
```

**约束**:
- **只能** 1 个线程调 Enqueue
- **只能** 1 个线程调 Dequeue
- 两者可以是不同线程,但各自只能 1 个

最快路径,因为不需要处理"多个生产者 enqueue 时打架"。

### 5.4.3.2 MPSC 用法

```cpp
TQueue<FCommand, EQueueMode::Mpsc> Queue;

// 任意多个生产线程
ParallelFor(NumProducers, [&Queue](int32 i) {
    Queue.Enqueue(MakeCmd(i));        // 安全
});

// 仍然只有 1 个消费线程
FCommand Out;
while (Queue.Dequeue(Out)) { Process(Out); }
```

Enqueue 用 atomic CAS 处理多生产者打架。Dequeue 仍要求单线程。

### 5.4.3.3 RTS 用例

- **玩家命令队列**:UI / 网络多线程产生命令,Mass Processor(GameThread)消费 → MPSC
- **战斗事件**:多 Processor 产生伤害事件,主线程汇总 → MPSC

## 5.4.4 `TMpscQueue` —— 5.x 新一代 MPSC

`Containers/MpscQueue.h:17`:

```cpp
template<typename T>
class TMpscQueue final
{
public:
    void Enqueue(T&& Item);             // 任意多个线程
    bool Dequeue(T& OutItem);           // 单消费线程
    // ...
};
```

5.x 引入,**比 `TQueue<T, Mpsc>` 性能更好**(用更激进的 lock-free 算法,通常基于 Vyukov MPSC queue)。新代码倾向用 `TMpscQueue` 而非 `TQueue<T, Mpsc>`。

### 5.4.4.1 与 `TQueue<T, Mpsc>` 的差异

| 特性 | TQueue<T, Mpsc> | TMpscQueue<T> |
|---|---|---|
| 算法 | 节点链表 + atomic CAS | Vyukov 风格,更紧凑 |
| 性能 | 中 | 更好(尤其 high contention) |
| 内存 | 每入队 new 节点 | 类似但更高效 |
| 推荐 | 老代码兼容 | 新代码 |

## 5.4.6 `TLockFreePointerListLIFO<T>` —— 多生产多消费 LIFO 栈

`Containers/LockFreeList.h:897`:

```cpp
template<typename T>
class TLockFreePointerListLIFO : public TLockFreePointerListLIFOPad<T, 0>
{
    // LIFO(后进先出),多 P 多 C 都安全
    // T 必须是指针类型
};
```

**注意**:它是 LIFO **栈**,不是 FIFO 队列!且 `T` 必须是指针(`T*`)。

### 5.4.6.1 用法

```cpp
TLockFreePointerListLIFO<FNode> Stack;

// 多个生产线程都安全 push
Stack.Push(NewNode);

// 多个消费线程都安全 pop
FNode* Top = Stack.Pop();
```

LIFO 适合"重用对象池"场景:

```cpp
// 对象池
TLockFreePointerListLIFO<FCommand> CommandPool;

// 取
FCommand* GetFreeCommand()
{
    FCommand* C = CommandPool.Pop();
    return C ? C : new FCommand();
}

// 还
void ReleaseCommand(FCommand* C)
{
    C->Reset();
    CommandPool.Push(C);
}
```

LIFO 比 FIFO 简单(只一个原子端),性能更高。**只在你不在乎顺序**(对象池、自由列表)时用。

### 5.4.6.2 ABA 问题与缓解

经典 lock-free 栈有 ABA 问题:线程 A pop 看到 X,正要 CAS,线程 B pop X push 它再 push Y 让 X 变栈顶 — A 的 CAS 假装看到的还是原状态,但实际栈已变。

UE 的实现用 **counter 标记**(每个 pointer 配一个 counter,CAS 同时比较 pointer + counter)缓解。但仍要谨慎用 — 高并发栈极容易出 bug。

## 5.4.7 `TCircularQueue<T>` —— 固定容量 SPSC

`Containers/CircularQueue.h`:

```cpp
template<typename T>
class TCircularQueue
{
public:
    TCircularQueue(uint32 InCapacity);   // 启动时定容量
    
    bool Enqueue(const T& Item);          // 满了返回 false
    bool Dequeue(T& OutItem);
    // ...
};
```

特点:
- **固定容量**,不动态增长
- SPSC,**比 unbounded TQueue 更快**(不 alloc 节点)
- 元素类型不必是指针

适合:已知最大队列长度的场景(如音频 ring buffer、网络包预 alloc 缓冲)。

## 5.4.8 内存释放:`TLockFreePointerListLIFOPad`(避免 false sharing)

`LockFreeList.h:840`:

```cpp
template<typename T, int TPaddingForCacheContention>
class TLockFreePointerListLIFOPad : private FLockFreePointerListLIFOBase<T, TPaddingForCacheContention>
```

`TLockFreePointerListLIFO` = `TLockFreePointerListLIFOPad<T, 0>`(无 padding)。

**Padding 的目的**:防止 **false sharing**。如果两个 atomic 变量在同一个 cache line(64 字节),不同线程改它们会**互相冲刷 cache**,变慢。Padding 让它们隔在不同 cache line。

`TLockFreePointerListLIFO` 默认无 padding。某些性能极敏感场景可用带 padding 版本。

## 5.4.9 5.x 推荐:`std::atomic` + 你自己的小型 lock-free

UE 老式 `FPlatformAtomics` 已 deprecated(§1.1.7),`std::atomic` 是新方向。简单 lock-free 直接写:

```cpp
// 一个简单的"flag + 数据"模式
std::atomic<bool> Ready{ false };
int32 Data;

// 生产
Data = 42;
Ready.store(true, std::memory_order_release);

// 消费
if (Ready.load(std::memory_order_acquire))
{
    int32 V = Data;       // 安全(被 release-acquire 同步)
    Process(V);
}
```

`std::memory_order_release` / `acquire` 配对使用,保证 Data = 42 的写**先于** Ready = true 被其它线程看到(release ordering)。

**这是最基本的 lock-free 模式**。比写自己的 queue 简单得多,适合"flag 通知"。

## 5.4.10 RTS / Mass 视角下的纪律

### (1)RTS 命令队列用 `TMpscQueue`

```cpp
class URTSCommandSubsystem : public UWorldSubsystem
{
    TMpscQueue<FRTSCommand> CommandQueue;
    
public:
    // 任何线程都能 enqueue(玩家输入、AI、网络包处理)
    void EnqueueCommand(FRTSCommand Cmd)
    {
        CommandQueue.Enqueue(MoveTemp(Cmd));
    }
    
    // GameThread / Mass Processor 消费
    void ProcessCommandsOnGameThread()
    {
        FRTSCommand Cmd;
        while (CommandQueue.Dequeue(Cmd))
        {
            ApplyCommand(Cmd);
        }
    }
};
```

或用 `FPipe`(§5.3.5)替代,更灵活。但 `TMpscQueue` 更直接。

### (2)Mass 内部命令也用 lock-free

`FMassCommand` / `FMassCommandBuffer` 内部用 lock-free 队列,Processor worker 并发产生命令时无锁。详 §17 / §18。

### (3)对象池用 `TLockFreePointerListLIFO`

如果你的 RTS 大量 spawn / despawn 同种 actor:

```cpp
TLockFreePointerListLIFO<AHero> HeroPool;

// 多个 worker 都能拿
AHero* H = HeroPool.Pop();
if (!H) H = SpawnNew();

// 还回
HeroPool.Push(H);
```

LIFO 不保证顺序,但池化场景不需要顺序。

### (4)**绝不**自己写 lock-free 容器

```cpp
// ❌ 极危险
class FMyAwesomeQueue
{
    std::atomic<TNode*> Head;
    void Push(TNode* N) {
        // 自己写 CAS 链表,容易出 ABA / order bug
    }
};
```

Lock-free 算法**对错** atomically 取决于内存序的精细控制。任何一处 `memory_order` 写错就是难复现的 bug。**永远用 UE 自带或 std 标准库的**。

## 5.4.11 性能对比(实测数量级)

| 容器 | Enqueue + Dequeue 一对 | 备注 |
|---|---|---|
| `FCriticalSection` 保护的 TArray | 50-200 ns | 有竞争时退化到 μs |
| `TQueue<T, Spsc>` | 20-50 ns | 单 P + 单 C |
| `TSpscQueue<T>` | 15-40 ns | 5.x 新版,稍快 |
| `TQueue<T, Mpsc>` | 50-100 ns | 多 P + 单 C |
| `TMpscQueue<T>` | 30-80 ns | 5.x 新版 |
| `TLockFreePointerListLIFO` | 20-50 ns | 仅 push/pop 指针 |

(竞争少时数据,极高竞争差距收窄)

## 5.4.13 实操提示与下一节预告

### 实操提示

- **DEBUG 时关 lock-free 用 mutex 版本**:lock-free bug 难定位,**有时**先用 mutex + TArray 验证逻辑,再换 lock-free
- **不要把 lock-free 容器嵌套**:把 `TQueue<TQueue<int>>` 之类。两层 lock-free 难以推理
- **看竞争**:Insights 里看 atomic CAS 的失败重试次数(若有 trace),竞争激烈时 lock-free 反而慢
