## 第 0 部分：通用基石

> 在踏入任何模块之前必须建立的世界观。这一部分不重，但跳过会让后面所有源码读起来像天书。

### 0.1 Minecraft 世界的坐标系与单位

- **方块坐标 BlockPos**：整数三元组，单位为 1m 立方体格子。Y 轴向上。
- **区块坐标 ChunkPos**：`(blockX >> 4, blockZ >> 4)`，每 16×16 列。
- **段坐标 SectionPos**：在 ChunkPos 基础上加 Y 维度，每段 16³，主世界 Y∈[-64, 320] 共 24 段。
- **区域坐标 RegionPos**：`(chunkX >> 5, chunkZ >> 5)`，每 32×32 区块构成一个 `.mca` 文件。
- **实体坐标 Vec3**：双精度浮点。
- 三种坐标互转的位运算技巧（`& 15`、`>> 4` 等）以及为什么 Java 的算术右移在负坐标依然正确。

### 0.2 Tick 模型与时间轴

- 服务端固定 20 TPS（每 tick 50 ms）。
- 主循环顺序：`MinecraftServer.tickServer()` → 各 `ServerLevel.tick()` → blockTicks/fluidTicks/entityTick/blockEvents。
- 客户端帧 vs 服务端 tick 的差异（客户端按真实帧率，渲染时插值）。
- "tick"、"game tick"、"random tick" 三个易混名词。

### 0.3 客户端 / 服务端 / 集成服务端架构

- 单机本质是 **集成服务端**（`IntegratedServer`）+ 客户端跑在同一进程，通过 in-memory channel 通讯。
- 联机：独立 `DedicatedServer` + 远端客户端，通过 TCP/Netty。
- `Dist.CLIENT` / `@OnlyIn` 注解的实际作用与运行期含义。
- 为什么这套架构对 C++ 移植至关重要：你必须从一开始就把"权威世界状态"和"客户端表象"分离。

### 0.4 Registry 与 ResourceLocation 命名系统

- `ResourceLocation` = `namespace:path`（如 `minecraft:oak_log`）。
- `Registry<T>` / `BuiltInRegistries` / `RegistryAccess`：所有可枚举资源（方块、物品、生物群系、地物、维度类型...）都通过注册表访问。
- 数据驱动注册（datapack JSON）vs 硬编码注册的区别。
- C++ 移植：`TMap<FName, T*>` 还是手写 ID 桶？

### 0.5 数据驱动设计哲学

- 1.18+ 后世界生成几乎完全 datapack 化：`worldgen/biome/*.json`、`worldgen/density_function/*.json`、`worldgen/noise_settings/*.json` 等。
- Codec 框架：DataFixerUpper 的 `Codec<T>` 是 JSON ↔ Java 对象的双向序列化器。
- 为什么 Mojang 选择把硬代码 DSL 抽到 JSON：modder 友好 + 测试友好。

### 0.6 反编译源码导读约定

- `p_NNNNNN_` 参数名的来源（Mojang 不发布的运行时混淆名），如何通过上下文推参数语义。
- 异常变量是类型小写名（`ioexception`）的阅读技巧。
- `LOGGER` / `@Nullable` / `@OnlyIn` 在 1.21 的统一约定。
- `mcp/client/Start.java` 是 MCP 工程的客户端入口包装，不是 Minecraft 真正的 `Main`。

## 第 1 部分：方块、状态、Chunk —— 世界数据结构基石

> 关键词：`net.minecraft.world.level.block.*`、`net.minecraft.world.level.chunk.*`、`StateHolder`、`Palette`。

### 1.1 Block 与 BlockState：到底什么是一格"方块"

- **`Block`**：方块**类型**（singleton），如 `Blocks.OAK_LOG`。
- **`BlockState`**：方块**实例状态**（属性组合），如"oak_log[axis=y]"。
- 一个 `Block` 拥有有限的 `StateDefinition`，所有 `BlockState` 在启动时一次性枚举完毕、共享 immutable 实例。
- `Property<T>`：枚举型/整数型/布尔型属性（`facing`、`waterlogged`、`age`...）。
- 为什么这套设计能把方块寻址压成 16-bit ID。

### 1.2 Palette 与 PalettedContainer：紧凑存储

- 朴素方案：每个方块 4 字节 ID = 16³×4 = 16 KB / section = 384 KB / chunk，吃不消。
- Palette：每段独立维护"调色盘"，只存调色盘下标 + 可变 bit 宽（1/2/4/.../15 bit/global）。
- `PalettedContainer<T>`、`HashMapPalette`、`LinearPalette`、`SingleValuePalette`、`GlobalPalette` 五种实现的切换策略。
- 与 C++ 的 RLE/字典编码方案对比。

### 1.3 ChunkSection（16×16×16 子区块）

- 数据成员：`PalettedContainer<BlockState>` + `PalettedContainer<Holder<Biome>>`（注意 1.18+ 后生物群系也按 4×4×4 体素粒度存）+ 非空方块计数。
- 为什么生物群系要 3D 存储（与 1.18 之前的 2D 区别）。

### 1.4 ChunkAccess 层次结构

- `ChunkAccess`（接口）→ `ProtoChunk`（生成中）→ `ImposterProtoChunk`（包装层）→ `LevelChunk`（已加载到世界）→ `EmptyLevelChunk`。
- 为什么生成阶段用 `ProtoChunk`：它允许写入但不参与 tick / 邻居更新。

### 1.5 Heightmap：高度图与遮挡查询

- 6 种 heightmap 类型：`WORLD_SURFACE`、`WORLD_SURFACE_WG`、`OCEAN_FLOOR`、`OCEAN_FLOOR_WG`、`MOTION_BLOCKING`、`MOTION_BLOCKING_NO_LEAVES`。
- WG 后缀：world-gen 阶段使用，与运行时维护的版本分离。
- 用途：阳光计算、生物刷怪 Y 选取、雪降落、闪电等。
- 数据结构：`SimpleBitStorage` packed long array。

### 1.6 BlockEntity（方块实体）vs Entity

- 方块实体 = 需要存储额外状态的方块（箱子、熔炉、信标...）。
- 与方块本体的双向引用，与 chunk 的 `Map<BlockPos, BlockEntity>` 关联。
- ticking 调度（`TickingBlockEntity` + `LevelChunkTicks`）。

### 1.7 寻址：BlockPos / SectionPos / ChunkPos

- 三者的 long 编码方案与位段布局。
- `BlockPos.MutableBlockPos` 模式：避免 GC 的可变指针。
- 在 C++ 中应该用 `glm::ivec3` 还是 `int64_t` 编码：取舍。

### 1.8 C++ 移植讨论

- SoA vs AoS：`BlockState` 应该按 ECS 列存还是行存？
- `PalettedContainer` 的 SIMD 友好实现思路。
- 为什么不要照搬 `LevelChunk` 的"运行时持有 BlockEntity 指针"的设计 —— UE5 的 GC 模型不一样。

## 第 2 部分：NBT 与存档存储格式

> 关键词：`net.minecraft.nbt.*`、`net.minecraft.world.level.chunk.storage.*`、`SerializableChunkData`、`RegionFile`。

### 2.1 NBT 格式规范

- "Named Binary Tag" 由 Notch 在 alpha 时期发明，big-endian、自描述、紧凑。
- 12 种 Tag：End / Byte / Short / Int / Long / Float / Double / ByteArray / String / List / Compound / IntArray / LongArray。
- 二进制布局：`[tagId:u8][nameLen:u16][name:UTF8][payload]`。
- 顶级标签必须是 Compound 且必须有名（即使是空字符串）。

### 2.2 Tag 类型族系（源码导读）

- `Tag` 接口、`TagType<T>`、`TagTypes` 注册表。
- 各 `*Tag` 的 `read/write/visit/copy` 实现要点。
- `CompoundTag` 的内部 map（`Map<String, Tag>`）与序列化顺序（无序）。
- `NbtAccounter`：防止 NBT 炸弹的递归深度 + 字节预算限制。

### 2.3 NbtIo 与 NbtUtils

- `NbtIo.read/write`：流式读写。
- 三种磁盘形态：raw、gzip 压缩（`.dat` 单文件）、zlib（区块文件中）。
- `NbtUtils.snbtToStructure` / SNBT 文本格式（命令行 `/data` 用的）。
- `NbtOps`：把 NBT 接入 DataFixerUpper Codec 体系。

### 2.4 Region 文件 (.mca) 的扇区分配

- 一个 `.mca` 文件 = 32×32 区块（最多 1024 个区块）。
- 文件头 8 KiB：4 KiB 偏移表（每条 4 字节，前 3 字节为扇区下标，第 4 字节为占用扇区数）+ 4 KiB 时间戳表。
- 数据区按 4 KiB 扇区为单位；每个区块开头 5 字节（4 字节长度 + 1 字节压缩类型 + payload）。
- `RegionBitmap` 维护已用扇区位图。

### 2.5 RegionFileVersion 压缩家族

- 1: GZIP、2: ZLIB、3: 不压缩、4: LZ4（1.21 新增）、127: 外部文件指针（区块单条 > 1 MiB 时）。
- 为什么外部文件指针存在：单 entry 不能跨多扇区无限增长。

### 2.6 SerializableChunkData：1.21 新版区块序列化

- 1.21 把"区块 → NBT"的逻辑从 `ChunkSerializer` 重构成数据载体类 `SerializableChunkData`。
- 核心字段：sections、blockEntities、heightmaps、structureStarts、blockTicks、fluidTicks、postProcessing、carvingMasks 等。
- 与旧版 `ChunkSerializer` 的差异（更易测试、更易做 datafix）。

### 2.7 IOWorker：异步 IO

- chunk save / load 是阻塞调用？不，`IOWorker` 用一个独立线程批处理。
- 写合并、读穿透、状态机（pending write → on-disk）。
- 与主线程的同步点（flush 时机）。

### 2.8 DataFixerUpper 简介

- Mojang 自己的"模式版本迁移"框架（早期独立发布，后内嵌）。
- `DataVersion` / `Schema` / `TypeReference` / `DSL`。
- 1.21 的 DataVersion 范围与跨版本兼容策略。
- 何时触发 fix：load chunk、load player、load level.dat。

### 2.9 C++ 移植讨论

- 用 `flatbuffers` / `cap'n'proto` 替代 NBT 的取舍（性能 vs 兼容性）。
- 自实现 NBT 的关键陷阱（big-endian、UTF-8 长度前缀类型）。
- Region 文件应该照搬还是用现代格式（mmap + LSM）。

## 第 3 部分：地形生成 —— 主菜（最详细模块）

> 关键词：`net.minecraft.world.level.levelgen.*`、`net.minecraft.world.level.biome.*`、`net.minecraft.world.level.chunk.status.*`。这是整个教程篇幅最大、最值钱的部分。

### 3.0 顶层视野

#### 3.0.1 ChunkGenerator 抽象与三大实现
- `ChunkGenerator`（抽象基类）。
- `NoiseBasedChunkGenerator`：噪声驱动的主世界 / 下界 / 末地共用实现。
- `FlatLevelSource`：超平坦。
- `DebugLevelSource`：调试模式（每个方块 ID 占一格）。

#### 3.0.2 NoiseBasedChunkGenerator 主线
- 持有 `BiomeSource` + `Holder<NoiseGeneratorSettings>` + `RandomState`。
- `applyCarvers` / `buildSurface` / `applyBiomeDecoration` / `fillFromNoise` / `getBaseHeight` 五个核心方法。

#### 3.0.3 一个区块从无到有的"流水线"鸟瞰图

```
EMPTY ─→ STRUCTURE_STARTS ─→ STRUCTURE_REFERENCES ─→ BIOMES
                                                          │
                                                          v
                            NOISE  ←──── 调用 NoiseChunk + NoiseRouter
                              │
                              v
                            SURFACE  ←─ SurfaceRules
                              │
                              v
                            CARVERS  ←─ WorldCarver
                              │
                              v
                            FEATURES ←─ ConfiguredFeature × 10 step
                              │
                              v
                            INITIALIZE_LIGHT → LIGHT
                              │
                              v
                            SPAWN（首次刷怪）
                              │
                              v
                            FULL（升级为 LevelChunk，可被玩家 tick）
```

### 3.1 概念释义（专有名词科普）

#### 3.1.1 Biome：到底是什么？视觉上决定什么？
- 它**不是地形几何**，而是一组**视觉与行为参数**：草色、水色、雾色、空气粒子、雨/雪/无雨、刷怪表、地表方块覆盖配方、可生成地物列表。
- 同一坐标的地形几何由噪声决定，"是不是沙漠"由生物群系决定。
- `Biome.ClimateSettings` / `Biome.SpecialEffects` / `MobSpawnSettings` / `BiomeGenerationSettings`。

#### 3.1.2 五大气候参数（最重要！）
| 参数 | 范围 | 视觉 / 概念含义 |
|------|------|------------------|
| Temperature 温度 | -1..1 | 越高越像沙漠/丛林，越低越像雪原。决定下雪 vs 下雨。 |
| Humidity 湿度 | -1..1 | 越高植被越密（丛林、沼泽），越低越干（沙漠、稀树草原）。 |
| Continentalness 大陆性 | -1.2..1 | **决定海陆分布**：负值 = 深海，0 附近 = 海岸/海滩，正值 = 内陆。这是 1.18+ 大世界感的灵魂。 |
| Erosion 侵蚀度 | -1..1 | **决定地表平滑度**：高 = 平原/高原顶平地，低 = 山峰/陡崖。 |
| Weirdness / PV (Peaks & Valleys) | -1..1 | **决定山脊形态**：通过对 weirdness 取绝对值再分段映射，得到"山谷-山坡-山顶"的剖面。 |

加上 **Depth 深度**（不是采样的，是从 Y 坐标推导出来的"距地表多远"）共六个维度。

#### 3.1.3 海平面 / Min Y / Max Y / 世界高度
- 主世界：`min_y = -64`，`height = 384`（即 Y ∈ [-64, 320)）。
- 海平面：63（NoiseSettings 中的 `seaLevel`）。
- 下界：高度 256，但有 128 的"虚拟天花板"。
- 末地：高度 256。

#### 3.1.4 Aquifer 含水层
- 1.18+ 引入的"地下水位"系统：地下不再默认是石头，而是按局部水位规则填水或熔岩。
- 这就是为什么现在洞穴里会出现"地下湖"。

#### 3.1.5 Surface 表面层 vs Stone Bed 基岩层
- 噪声只决定"哪里是固体哪里是空气/液体"。
- "固体表层用什么方块"（草方块、沙、雪）由 `SurfaceRules` 决定。
- 二者解耦后才能用同一套噪声生成沙漠和草原。

#### 3.1.6 Cave Carver（雕刻洞）vs Noise Cave（噪声洞）
- 雕刻洞：1.16- 时代经典圆管洞。`net.minecraft.world.level.levelgen.carver.*`。
- 噪声洞：1.18+ 引入，由密度函数中的 caves 子项直接挖出，形成 cheese cave / spaghetti cave / noodle cave 三种形态。
- 二者**叠加**而非互斥。

#### 3.1.7 Feature / ConfiguredFeature / PlacedFeature
- `Feature<C>`：生成算法（"长一棵树"）。
- `ConfiguredFeature<C, F>`：算法 + 配置（"长一棵橡树，最大 6 高，叶子半径 2"）。
- `PlacedFeature`：配置好的算法 + 放置规则（"在草方块上、Y 位于地表、每 chunk 4 次随机尝试"）。

#### 3.1.8 Structure / StructureSet / StructureTemplate
- `Structure`：村庄、要塞、远古城市等"大型多区块建筑"。
- `StructureSet`：一组结构 + 放置策略（间距、separation、salt）。
- `StructureTemplate`：以 NBT 形式存储的方块阵列（`.nbt` 文件，加载自 `data/<ns>/structure/`）。

#### 3.1.9 ProtoChunk vs LevelChunk
- 生成期间：`ProtoChunk`，可多线程并行写入。
- 生成完毕进入 `FULL` 状态：升级成 `LevelChunk`，进入 ticking 主循环。
- "PROTO" = 原型 / pre-thaw。

### 3.2 Chunk 生命周期：ChunkStatus 流水线

#### 3.2.1 1.21 的 ChunkStep / ChunkPyramid 重构（**重要**）
- **1.20 之前**：`ChunkStatus` 是一个枚举式驱动器，`generate(...)` 直接挂在每个状态上。
- **1.21 重构**：拆分为 `ChunkStatus`（数据状态标签）+ `ChunkStep`（执行单元）+ `ChunkPyramid`（依赖图）+ `ChunkStatusTasks`（任务体）。
  - `ChunkPyramid` 像金字塔：底层（早阶段）依赖周围更多区块。
  - `ChunkStep` 描述"为了进入这个 status 需要哪些邻居 chunk 处于哪个 status"。
  - `ChunkStatusTasks` 是无状态的纯函数集合，方便测试和数据驱动。
- 这套重构对 C++ 异步流水线移植非常友好，是教程的重点。

#### 3.2.2 12 个生命周期阶段逐一拆解
| 阶段 | 职责 | 关键源码 |
|------|------|----------|
| EMPTY | 占位 | — |
| STRUCTURE_STARTS | 决定本 chunk 是否是某结构的"起点"（区块对齐） | `ChunkGenerator.createStructures` |
| STRUCTURE_REFERENCES | 把附近 chunk 的 structure starts 引用到本 chunk | `ChunkGenerator.createReferences` |
| BIOMES | 用 BiomeSource 给每个 4×4×4 体素分配 biome | `ChunkGenerator.createBiomes` |
| NOISE | 用 NoiseChunk 求解每格的"是固体/空气/液体" | `NoiseBasedChunkGenerator.fillFromNoise` |
| SURFACE | 应用 SurfaceRules，铺草、沙、雪 | `ChunkGenerator.buildSurface` |
| CARVERS | 雕刻洞穴/峡谷 | `ChunkGenerator.applyCarvers` |
| FEATURES | 跑 10 步 GenerationStep（树木、矿物、湖泊...） | `ChunkGenerator.applyBiomeDecoration` |
| INITIALIZE_LIGHT | 初始化光照引擎 | `LightEngine.retainData` |
| LIGHT | 计算天光 / 方块光 | `ThreadedLevelLightEngine.lightChunk` |
| SPAWN | 首次自然刷怪 | `NaturalSpawner.spawnMobsForChunkGeneration` |
| FULL | ProtoChunk → LevelChunk | `ChunkStatusTasks.generateFull` |

#### 3.2.3 区块依赖半径与"加载半径"
- 为什么生成单个 chunk 实际上要触发 8×8 区块进入早期阶段：FEATURES 阶段会跨 chunk 边界写入。
- 视距 (`view-distance`) vs 模拟距离 (`simulation-distance`) vs 生成半径的关系。

#### 3.2.4 ProtoChunk → LevelChunk 升级时机与原子性
- 升级在主线程完成，避免半完成状态被 tick 看到。

#### 3.2.5 ChunkStatusTasks 任务体源码导读
- 每个任务的输入 / 输出 / 副作用。
- 哪些任务是 CPU-bound（NOISE、FEATURES），哪些是 IO-bound（依赖邻居加载）。

#### 3.2.6 C++ 异步流水线移植
- 用 task graph（类似 UE5 `FGraphEvent`）映射 ChunkPyramid 依赖。
- 优先级队列：靠近玩家的 chunk 先升级。

### 3.3 随机源系统

#### 3.3.1 RandomSource 接口家族
- `RandomSource` 接口：`nextInt`、`nextFloat`、`nextDouble`、`nextGaussian`、`fork()`、`forkPositional()`。

#### 3.3.2 LegacyRandomSource（java.util.Random 兼容）
- 用于跨版本可重复性（旧地图）。
- `MarsagliaPolarGaussian` 用于 Box-Muller 高斯采样的旧实现。

#### 3.3.3 XoroshiroRandomSource / Xoroshiro128PlusPlus
- 1.18+ 默认随机源。`RandomSupport` 提供混合函数。
- 对比 java.util.Random：周期更长（2^128 vs 2^48）、性能更好、统计性能更好。

#### 3.3.4 PositionalRandomFactory
- 关键概念：**坐标确定性随机**。给定 `(seed, blockPos)` 总能复现同一序列。
- 这是 MC 世界生成可重玩性的灵魂：同一种子 + 同一位置 = 同一棵树。

#### 3.3.5 WorldgenRandom
- 包装层，把多种随机源 + ChunkPos 派生封装好。
- `setDecorationSeed` / `setFeatureSeed`：每个 feature 独立种子，避免互相干扰。

#### 3.3.6 种子派生层级
- World seed → biome seed / noise seed / aquifer seed / ore seed / structure seed ...
- Mojang 用 `RandomSupport.seedSlimeChunk` 等命名约定的混合函数派生。

### 3.4 噪声系统数学基础

#### 3.4.1 一维噪声、值噪声、梯度噪声概念
- 值噪声（Value Noise）：在格点定义随机值，插值。
- 梯度噪声（Gradient Noise / Perlin）：在格点定义随机**方向向量**，与偏移点点积，再插值。

#### 3.4.2 Improved Perlin（Mojang 实现）
- `ImprovedNoise` 类剖析：256 元素 permutation table、`grad(...)` 函数、`fade(t) = 6t^5 - 15t^4 + 10t^3` 五次平滑。
- 输出范围与归一化系数。

#### 3.4.3 Simplex Noise
- `SimplexNoise` 类剖析：与 Perlin 的差异（六边形网格、O(n²) → O(n) 在高维）。
- 1.21 中哪些场景用 Simplex（如某些 2D 噪声）。

#### 3.4.4 Octaves 八度叠加 / fBm
- `PerlinNoise`（多 octave 包装）+ `NormalNoise`（fBm 后归一化）。
- amplitude / frequency 序列，`firstOctave` 索引含义。
- 数学上的 fractional Brownian motion 模型。

#### 3.4.5 NormalNoise / PerlinNoise 类剖析
- 数据成员、构造时的种子派生。
- `getValue(x, y, z)` 主入口的优化技巧（缓存、SIMD 思路）。

#### 3.4.6 Noises.java 注册表
- 全部内置噪声键（temperature、humidity、continentalness、erosion、ridge、cave_layer、cave_cheese...）。
- 每个噪声的 amplitudes、firstOctave 配置。

#### 3.4.7 C++ 实现：与 stb_perlin / FastNoiseLite 对比
- 是否需要 1:1 复刻 Mojang 的 permutation 才能保证种子一致？答：是。
- 提供完整 C++ 翻译模板。

### 3.5 Density Function DSL（核心创新）

#### 3.5.1 为什么用"密度函数"建模地形
- 1.18 之前：硬编码 `if biome == DESERT then noise * 0.5 else ...`，每加一种地形都要改 Java。
- 1.18 之后：用 datapack JSON 描述任意噪声组合树，运行时编译为函数对象。
- 这是 Mojang 工程上的最大胜利之一。**也是教程要重点剖析的部分**。

#### 3.5.2 DensityFunction 接口
- 核心方法：`compute(FunctionContext)`、`fillArray(double[], ContextProvider)`、`mapAll(Visitor)`。
- 为什么有 `fillArray`：批处理 1024 个点比单点调用快得多。

#### 3.5.3 内置函数族（约 30 种）
| 类别 | 代表 | 作用 |
|------|------|------|
| 常量 | `Constant` | 返回固定值 |
| 噪声 | `Noise`、`ShiftedNoise`、`ShiftA/B` | 包装 NormalNoise |
| 算术 | `Add`、`Mul`、`Min`、`Max`、`Abs`、`Square`、`Cube`、`HalfNegative`、`QuarterNegative`、`Squeeze` | 一元 / 二元算子 |
| 形状 | `Spline` | 控制点样条插值，是大陆性 → 高度的关键 |
| 控制 | `Clamp`、`RangeChoice`（区间分支）、`Slide`、`YClampedGradient` | 条件 / 分段 |
| 缓存 | `Cache2D`、`FlatCache`、`OnceCache`、`CacheAllInCell`、`Interpolated` | 性能优化 |
| 引用 | `HolderHolder` | 延迟绑定到 Holder<DensityFunction> |
| 混合 | `BlendDensity`、`BlendAlpha`、`BlendOffset` | 与旧地图的边界融合 |
| 端魔 | `EndIslands` | 末地大岛硬编码 |

#### 3.5.4 DensityFunctions.java 工厂
- 静态方法 `add`、`mul`、`spline`、`yClampedGradient` 等：在 Java 里组装树。
- `MarkerOrMarked` 标记机制（让 Cache 之类节点参与 visit）。

#### 3.5.5 NoiseRouter 路由器结构
- 不是单一密度函数，而是 **8 条命名输出通道** 的捆绑：
  - `barrierNoise` / `fluidLevelFloodednessNoise` / `fluidLevelSpreadNoise` / `lavaNoise`
  - `temperature` / `vegetation` / `continents` / `erosion` / `depth` / `ridges`（生物群系采样用）
  - `initialDensityWithoutJaggedness` / `finalDensity`（地形高度判断用）
  - `veinToggle` / `veinRidged` / `veinGap`（矿脉用）
- 教程会画一张完整的 NoiseRouter 数据流图。

#### 3.5.6 NoiseRouterData 主世界配方
- 这是**整个主世界长什么样的核心配方文件**。逐 spline 拆解：
  - `OFFSET` spline：大陆性 → 基础高度。
  - `FACTOR` spline：高度乘数。
  - `JAGGEDNESS` spline：山顶锯齿强度。
- 阅读时配合官方 wiki 的 spline 可视化图。

#### 3.5.7 三维噪声体积的查询模式
- 实际不是每个 BlockPos 都查一次。改为按 `cell_width × cell_height` 单元格查，再三线性插值。
- 默认 `cell_width = 4`（XZ）、`cell_height = 8`（Y）→ 一个 chunk 实际密度采样点 4×4×40 = 640 次而不是 16×16×384。

#### 3.5.8 性能优化
- `Interpolated`：在 cell 角点采样，cell 内部插值。
- `Cache2D`：XZ-only 噪声只算 1 次。
- `FlatCache`：bilinearly upsample 后整层缓存。
- `CacheAllInCell`：cell 内复用。

#### 3.5.9 数据包视角
- 拆解 `data/minecraft/worldgen/density_function/overworld/*.json` 几个关键文件。

#### 3.5.10 C++ 移植方案
- 方案 A：组合算子树（虚函数调用）。
- 方案 B：JIT 编译为 SPIR-V 风格 IR，跑在 GPU compute。
- 方案 C：表达式模板（C++ template metaprogramming）。
- 三种方案的取舍与推荐。

### 3.6 NoiseChunk：地形数值化的核心

#### 3.6.1 NoiseChunk 的职责
- 一次实例化对应一个 chunk 的"密度采样工作集"。
- 内部维护当前 cell、当前 column 的插值缓存。

#### 3.6.2 单元格分块
- `CellWidth` / `CellHeight` / `CellCountX,Y,Z` 的来源（`NoiseSettings`）。

#### 3.6.3 三线性插值还原细节
- 8 个角点 → 单元格内任意点。
- 配合 `Interpolated` 节点的双重缓存机制。

#### 3.6.4 与 NoiseSettings 的连接
- `NoiseSettings.create` 中 `minY`、`height`、`size_horizontal`、`size_vertical` 决定 cell 划分。

#### 3.6.5 Beardifier（结构对地形的反向"剃须"）
- 当 chunk 里要生成村庄时，需要把房屋下方"刮平"。
- `Beardifier` 在 `finalDensity` 之外注入一个修正项。
- 数学上是一个加性 bell-shaped 函数。

### 3.7 Climate / 多噪声生物群系采样器

#### 3.7.1 Climate.ParameterPoint：六维参数空间
- 每个 biome 在 (T, H, C, E, D, W) 六维空间中占据一个超长方体。
- `Climate.Parameter` = `[min, max]` 区间，`Climate.ParameterPoint` 是 6 维超长方体。

#### 3.7.2 Climate.RTree：空间最近邻查询
- KD-tree 风格 R-tree，用 SAH-like 启发式划分。
- 查询：给定六维点 → 返回距离最近的 ParameterPoint → 对应 biome。
- 为什么不用直接 6D 网格：稀疏。

#### 3.7.3 OverworldBiomeBuilder：主世界配方
- ~5000 行的"硬编码表"，列出每个 biome 在六维空间的占位。
- 教程把它分成 8 张表（陆地内陆 / 海岸 / 浅海 / 深海 / 山区 / 冰原 / 沙漠 / 河流）逐一讲解。

#### 3.7.4 BiomeManager：模糊化与位置抖动
- 简单查询会让 biome 边界呈完美直线。
- BiomeManager 用 `Mth.smoothstep` 风格的位移在边界 ±2 格抖动，得到自然边界。

#### 3.7.5 BiomeSource 三大实现
- `MultiNoiseBiomeSource`：主世界 + 下界都用。
- `FixedBiomeSource`：单 biome（buffet / 调试）。
- `CheckerboardColumnBiomeSource`：调试棋盘模式。

#### 3.7.6 The End / The Nether 特殊采样器
- `TheEndBiomeSource`：根据距离原点的距离 + 噪声决定 small island vs main island。
- 下界用 4 维参数空间（不需要 C/W）。

#### 3.7.7 视觉映射：参数 → 玩家眼中地貌
- 对照表："T=0.5, H=0.0, C=0.5, E=-0.5, W=0.0" 长什么样。
- 这是新手最缺的可视化直觉，必须配图。

### 3.8 SurfaceRules：地表材料覆盖系统

#### 3.8.1 为什么需要"地表规则"层
- 噪声决定形状，地表规则决定"皮肤"。

#### 3.8.2 SurfaceRules.RuleSource DSL
- `Sequence`、`Condition`、`Block`、`Bandlands`（恶地特殊）。
- `ConditionSource`：`Above/BelowPreliminarySurface`、`StoneDepth`、`YAbove`、`Water`、`Temperature`、`Steep`、`Hole`、`Biome`、`NoiseThreshold`、`VerticalGradient` 等。

#### 3.8.3 条件 vs 材料解耦
- 二者通过 `ConditionedRuleSource` 组合。
- 求值是惰性的（短路）。

#### 3.8.4 SurfaceSystem 执行机制
- 一次执行一整个 chunk。
- 列循环：从顶到底扫描，第一次命中规则停下。

#### 3.8.5 主世界规则配方导读
- `SurfaceRuleData` ：分阶段（badlands special → grass surface → sand → underwater → bedrock）。

#### 3.8.6 案例
- 沙滩：海岸 + Y 接近海平面 + 大陆性中等 → sand。
- 雪线：温度 < 0.15 + Y > heightmap → snow。
- 沼泽：biome = swamp + 浅水底 → grass。

### 3.9 Aquifer 含水层系统

#### 3.9.1 1.18+ 含水层革命
- 之前：地下默认是石头，洞穴里默认空气；水仅来自地表湖泊。
- 之后：地下随机出现"局部水位"，洞穴可能从洞顶到这个水位都被水填满。

#### 3.9.2 Aquifer.NoiseBasedAquifer 实现
- 16×12×16 grid 上每格独立采样一个"流体粒子"（水位 Y + barrier 强度）。
- 三粒子加权决定一个具体位置的流体属性。

#### 3.9.3 流体粒子 (FluidStatus) 概念
- `(fluidLevel, fluidType)` —— 这个位置以下到底是水还是熔岩，水位线在哪。
- 运行时插值：处于"barrier" 区域的位置依然是石头。

#### 3.9.4 与 NoiseChunk 的耦合
- Aquifer 在 NoiseChunk 的 `updateForY` 中被回调。
- 输出会改写"是空气"为"是水"。

### 3.10 Carvers 洞穴雕刻

#### 3.10.1 Carver 与 WorldCarver
- `WorldCarver<C>`：抽象基类，子类 `CaveWorldCarver`、`CanyonWorldCarver`、`NetherWorldCarver`。

#### 3.10.2 房间、隧道、峡谷三种形态
- 隧道：分支递归 + 椭圆截面。
- 峡谷：长条 + 起伏 Y。
- 房间：球体。

#### 3.10.3 噪声洞 vs 雕刻洞协同
- 噪声洞由 `finalDensity` 自然产生。
- 雕刻洞在 `applyCarvers` 阶段额外打孔。
- 二者都受 Aquifer 影响（洞里可能有水）。

### 3.11 Features 地物装饰

#### 3.11.1 Feature 抽象与 PlaceContext
- `Feature.place(FeaturePlaceContext<C>)`：返回 boolean 表示是否成功。
- `FeaturePlaceContext` 携带 level、generator、random、origin、config。

#### 3.11.2 三层嵌套：ConfiguredFeature / PlacedFeature / Modifier
- ConfiguredFeature：算法 + 参数。
- PlacedFeature：ConfiguredFeature + `List<PlacementModifier>`。
- PlacementModifier 例：`CountPlacement(N)`、`InSquarePlacement`、`HeightRangePlacement`、`BiomeFilter`、`RarityFilter`、`HeightmapPlacement`。

#### 3.11.3 GenerationStep.Decoration 的 10 个步骤
| 步骤 | 用途 |
|------|------|
| RAW_GENERATION | 罕见低级地物 |
| LAKES | 老式湖泊 |
| LOCAL_MODIFICATIONS | 巨型水晶簇等 |
| UNDERGROUND_STRUCTURES | 地下结构（怪物房） |
| SURFACE_STRUCTURES | 地表结构 |
| STRONGHOLDS | 要塞 |
| UNDERGROUND_ORES | 矿物 |
| UNDERGROUND_DECORATION | 矿洞装饰 |
| FLUID_SPRINGS | 喷泉 |
| VEGETAL_DECORATION | 植被 |
| TOP_LAYER_MODIFICATION | 雪、冰最后一层 |

10 个步骤按固定顺序执行，每个 biome 在每步贡献一个 PlacedFeature 列表。

#### 3.11.4 树（TreeFeature 体系）
- `TreeFeature` + `TreeConfiguration`。
- `TrunkPlacer`（树干）：StraightTrunkPlacer、ForkingTrunkPlacer、GiantTrunkPlacer、CherryTrunkPlacer 等。
- `FoliagePlacer`（树叶）：BlobFoliagePlacer、SpruceFoliagePlacer、AcaciaFoliagePlacer 等。
- `RootPlacer`（树根，1.19+）。
- `TreeDecorator`：藤蔓、蜂巢等附加。

#### 3.11.5 矿物（OreFeature & ScatteredOreFeature）
- `OreFeature`：椭球簇 + 内部随机替换。
- `ScatteredOreFeature`：稀疏散布。
- `OreConfiguration.TargetBlockState`：在不同基岩中替换为不同矿石（深板岩矿 vs 普通矿）。

#### 3.11.6 OreVeinifier：1.18+ 矿脉系统
- 不在 FEATURES 阶段，而是在 NOISE 阶段就介入！
- 用 `veinToggle` / `veinRidged` / `veinGap` 三个噪声决定是否替换基岩为铜/铁矿脉。
- 这是为什么深板岩区有"长条矿脉"。

#### 3.11.7 RandomPatch / VegetationPatch / Disk
- `RandomPatchFeature`：随机散点（草、花）。
- `VegetationPatchFeature`：苔藓块簇。
- `DiskFeature`：圆盘形（沙、砾石）。

#### 3.11.8 特殊地物
- `GeodeFeature`：紫水晶簇（多层壳 + 内部水晶）。
- `LargeDripstoneFeature`、`PointedDripstoneFeature`、`DripstoneClusterFeature`：钟乳石。
- `SculkPatchFeature`：幽匿。
- `IcebergFeature`：冰山。
- `EndIslandFeature` / `EndPodiumFeature`：末地。

#### 3.11.9 Feature 排序与去重（FeatureSorter）
- 不同 biome 在同一步贡献的 feature 集合需要做拓扑排序，保证全局一致顺序。
- `FeatureSorter` 用 Tarjan 强连通 + 拓扑序。

### 3.12 Structures 结构生成

#### 3.12.1 Structure / StructureSet / StructurePlacement
- `Structure` 是抽象（村庄、要塞、远古城市...）。
- `StructureSet` 决定多个结构如何**互斥放置**（spacing、separation、salt）。
- `StructurePlacement.RandomSpread` vs `ConcentricRings`（要塞用）。

#### 3.12.2 StructureStart 与 StructurePiece
- StructureStart：一个结构实例的根节点（区块对齐）。
- StructurePiece：构成该实例的房间/走廊。
- 子类：`PoolElementStructurePiece`（jigsaw）、`TemplateStructurePiece`（直接 NBT 模板）等。

#### 3.12.3 模板加载（StructureTemplate / StructureManager）
- `.nbt` 文件 = `StructureTemplate` 序列化形式。
- `StructureManager.get(ResourceLocation)` 按需加载。

#### 3.12.4 Jigsaw 拼图系统（村庄、要塞、海底神殿）
- `StructureTemplatePool`：池子，可随机抽取元素。
- `JigsawJunction`：拼图衔接点。
- 递归装配：从起点池抽 → 按 jigsaw 方块连接下一段 → 限深度。

#### 3.12.5 结构对地形的影响（Beardifier）
- 已在 3.6.5 提及，这里对应到具体结构（村庄房屋是怎么把地刮平的）。

#### 3.12.6 StructureCheck 缓存
- 防止反复扫描"这个 chunk 是不是某个结构起点"。
- 持久化到 `level.dat` 同级。

### 3.13 实体与生物的初始填充

#### 3.13.1 Spawn ChunkStatus 阶段
- `NaturalSpawner.spawnMobsForChunkGeneration`。

#### 3.13.2 MobSpawnSettings
- 每个 biome 定义可刷怪种类 + 权重 + 群落大小。

#### 3.13.3 PhantomSpawner / PatrolSpawner
- 这是**运行时**周期性额外刷怪器（每 tick 跑一次），不是生成期的。

### 3.14 末地与下界（差异点）

#### 3.14.1 The Nether 配方
- NoiseRouterData 中 nether 分支。

#### 3.14.2 The End 配方

### 3.15 跨区块写入与生成边界处理（**移植关键**）

> 用户提问：一棵树长在区块边界上，邻居区块尚未生成，怎么保证那棵树最终是完整的而不是半截？
>
> 这一节系统回答这个问题，并把它推广到矿脉、结构、湖泊、雪盖等所有"会越界"的生成行为。

#### 3.15.1 问题陈述
- 一棵 5×5 树冠的橡树，树心放在 (15, Y, 15) ——它的叶子会写到 +X 邻居和 +Z 邻居。
- 一条 ~20 格长的铜矿脉，可能横跨 2-3 个区块。
- 一座村庄、一座要塞，跨 10+ 区块。
- 共同点：「拥有者 chunk」决定生成内容，但物理写入跨多个 chunk。

#### 3.15.2 三层机制总览

```
  静态契约：       ChunkStep.blockStateWriteRadius
  生成期视图：     WorldGenRegion + StaticCache2D<GenerationChunkHolder>
  延迟补救：       ProtoChunk.postProcessing[] / markPosForPostprocessing
```

#### 3.15.3 第一层：`ChunkStep.blockStateWriteRadius`（静态合约）
- `record ChunkStep(ChunkStatus targetStatus, ChunkDependencies directDependencies, ChunkDependencies accumulatedDependencies, int blockStateWriteRadius, ChunkStatusTask task)` —— 1.21 把"写入半径"做成了 status 流水线的**一等公民**。
- 每个 status 显式声明：「我执行时可能向半径多远的邻居 chunk 写方块」。
  - NOISE / SURFACE / CARVERS：通常 0（只写本 chunk）。
  - FEATURES：1（树、矿脉、湖泊）。
  - 涉及大型结构时，由 `StructureStarts` 在更早阶段把跨度预登记。
- 同时通过 `directDependenciesByRadius[]` 数组规定：「我要执行，那么我中心的 (2r+1)² 邻居都必须至少处于某个 prerequisite status」。
- **不变量**：当你成功调用 FEATURES 时，半径 1 内的邻居都至少已经走完 CARVERS。换言之，邻居已经"准备好接受写入"。

#### 3.15.4 第二层：`WorldGenRegion`（生成期写入面）
- 不是一个 chunk 的视图，而是「以中心 chunk 为中心、按当前 step 的 write radius 展开的 (2r+1)² 方阵」的视图。
- 数据成员：
  - `StaticCache2D<GenerationChunkHolder> cache`：方阵内每个 chunk 的句柄。
  - `ChunkAccess center`：本步真正在"生成"的 chunk。
  - `ChunkStep generatingStep`：决定能写多远。
- `setBlock(BlockPos, BlockState, flags)` 内部：定位 BlockPos 落在哪个 chunk → 从 cache 取 ProtoChunk → 写入。**对 Feature 代码完全透明：它感觉自己在操作一个无限世界。**
- 越界保护：如果 Feature 试图写到 cache 之外（`r+1` 之外），会触发 `LOGGER.error` 并丢弃，因为目标 chunk 此刻可能正在被另一个线程生成。这是 1.21 的并行生成安全网。

#### 3.15.5 第三层：`ProtoChunk.postProcessing`（延迟补救）
- `int packed = packOffsetCoordinates(blockPos); chunk.getOrCreateOffsetList(this.postProcessing, sectionIndex).add(packed);`
- 用途：当 Feature 放置一个**需要在邻居加载完才能验证**的方块时（典型：藤蔓/苔藓/可掉落沙的依附性方块），把它的本地坐标登记到一个待办列表。
- 时机：当本 chunk 升级到 FULL 时，调用 `LevelChunk.upgrade()` 扫描 postProcessing 列表，对每个登记的方块重做一次"自检"（typically 调用其 `updateShape` / 检查支撑方块），不通过则掉落。
- 作用：解决"我放置时邻居尚不可读，于是我无法验证支撑"的鸡生蛋问题。

#### 3.15.6 实战追踪：一棵橡树的跨区块过程
1. 区块 C₀ 在 FEATURES 阶段执行 VEGETAL_DECORATION step。
2. 取出"橡树"PlacedFeature，骰子决定放在 C₀ 的本地 (15, _, 15)。
3. `TreeFeature.place` 计算高度 → 调用 WorldGenRegion.setBlock 放树干。
4. 放叶子时计算到 (16, _, 16) —— 落在 +X+Z 邻居 C₁。WorldGenRegion 看到 ChunkPos 不是 center，定位到 cache 中的 C₁。
5. 此时 C₁ 必然处于 ≥ CARVERS 状态（由 ChunkStep 合约保证），但还没轮到自己跑 FEATURES。
6. 写入 C₁.ProtoChunk —— 那些叶子方块就**永久存在**于 C₁ 的数据中。
7. 后来 C₁ 自己跑 FEATURES：它根据**自己的 biome 和种子**决定要长哪些树，**完全不知道也不在乎** C₀ 的那棵树已经溢出过来。两套写入互相覆盖（按时间顺序），但因为坐标确定性 + 同一 biome 配方，结果稳定可复现。

**关键洞察**：没有"半棵树"问题，是因为**树的整体写入发生在 C₀ 的 FEATURES 步骤里的同一个原子调用**，那一刻 C₀ 和 C₁ 同时被 WorldGenRegion 持有。不是"C₀ 先写一半 → C₁ 以后再补另一半"。

#### 3.15.7 矿脉跨区块（更细微的例子）
- `OreVeinifier` 不在 FEATURES 阶段，而是嵌入在 NOISE 阶段的密度函数计算里！
- 这意味着每个 chunk 在 NOISE 时都对**自己内部**的每一格独立判断"是否换成铜/铁矿"。
- 矿脉跨区块自然成立：是因为产生矿脉的噪声场是全局连续的，邻居 chunk 在自己跑 NOISE 时，对边界另一侧采样到同一矿脉的同一段，结果一致。
- **这是另一种解决方案**：根本不需要跨 chunk 写入，让噪声的连续性直接保证物理连续性。

#### 3.15.8 结构跨多区块（更宏观的例子）
- 村庄、要塞可能横跨 5×5 区块。
- 解决：在 `STRUCTURE_STARTS` 阶段（流水线最前端），由结构起点 chunk 计算出整个结构的 BoundingBox + StructurePieces 列表。
- `STRUCTURE_REFERENCES` 阶段：每个被 BoundingBox 触及的 chunk 把"我属于这个结构"的引用登记下来。
- 当某个 chunk 跑 FEATURES 时，先看自己 references 列表，把所有跨 chunk 涉及自己的结构 piece 在自己范围内的部分生成（结构 piece 自带"裁剪到当前 chunk"逻辑）。
- 这是**结构专属机制**，与 Feature 的 WorldGenRegion 直接写入是两条不同的路径。

#### 3.15.9 边界 case 汇总
| 场景 | 处理 |
|------|------|
| 玩家走到生成半径边缘 | `ChunkMap` 触发"生成更多 chunk 到必要 prerequisite status" |
| Feature 想写 r+2 的越界 chunk | `WorldGenRegion` 拒绝 + LOGGER 报错（这是 datapack bug） |
| C₀ 已 FULL，C₁ 才 FEATURES，C₁ 的树想写到 C₀ | 不会发生：FULL chunk 周围必有 buffer，C₁ 在 FEATURES 时 C₀ 已经经过 FEATURES 自己一遍 |
| 玩家在结构生成途中关服 | StructureStarts 已持久化到 NBT，重新打开时恢复继续生成 |
| 树叶飘到一个**永远不会被加载**的远方 chunk | 不会发生：写入半径受 ChunkStep 限制，不可能写到 cache 之外 |

#### 3.15.10 C++ 移植要点
- 必须把 `blockStateWriteRadius` 作为流水线 step 的一等数据携带。
- 设计 `WorldGenRegion` 的 C++ 等价物：以 chunk-local 坐标为输入，根据当前 step 的半径展开一个 `StaticCache2D`-like view。
- 选择并行粒度：1.21 的 ChunkPyramid 允许同 status 的不同 chunk 并行，但同 chunk 的相邻 status 串行。
- 千万不要为了"性能"在 Feature 内部直接访问邻居 chunk 的内部数组 —— 走 view 层，等于免费拿到了越界保护。
- postProcessing 列表必须随 chunk 一起持久化（在 SerializableChunkData 中已支持），重启后还能补救。

## 第 4 部分：方块更新机制

> 关键词：`net.minecraft.world.level.Level`、`ServerLevel.tick`、`LevelChunkTicks`、`NeighborUpdater`。

### 4.1 三类 tick：scheduled / random / neighbor / event
- **Scheduled tick**：按"延迟 + 优先级"排队（红石中继器、流体扩散）。
- **Random tick**：每 chunk section 每 tick 抽 N 格随机（树叶腐烂、作物生长、火蔓延）。
- **Neighbor update**：方块变化触发 6 邻居 `neighborChanged` 调用。
- **Block event**：跨 tick 异步事件（活塞推动、唱片机播放）。

### 4.2 BlockState.tick 与 BlockState.randomTick
- `Block.tick(state, level, pos, random)`：scheduled 触发。
- `Block.randomTick(state, level, pos, random)`：random 触发。
- 两者实现的常见模式（先验证条件、再生成下一状态、再 schedule next）。

### 4.3 ServerLevel.blockTicks / fluidTicks 数据结构
- `LevelTicks<T>`：含 chunk-local + level-global 的延迟队列。
- 优先级 + 延迟 + 子tick顺序的排序键。

### 4.4 NeighborUpdater 与 CollectingNeighborUpdater
- `InstantNeighborUpdater`：递归式，立即调用，可能爆栈。
- `CollectingNeighborUpdater`：广度优先 + 队列，1.21 默认。
- 1.21 体验性红石可选 `Orientation` 化版本。

### 4.5 BlockEvent 异步事件
- `LevelChunk.addBlockEvent` → 下一 tick 派发。

### 4.6 BlockPhysics 状态变更
- `Level.setBlock` 的 flag 位（NOTIFY_NEIGHBORS、UPDATE_CLIENTS、INVISIBLE、NO_NEIGHBOR_DROPS、IS_MOVING、UPDATE_KNOWN_SHAPE）。
- 这些 flag 决定是否触发邻居更新、是否同步给客户端、是否触发掉落。

### 4.7 Client / Server 不同处理
- 客户端只为渲染维护 `ClientLevel`，**不跑** scheduled tick。
- 客户端的"假更新"（粒子、声音）走另一套路径。

### 4.8 性能上限与 tick 旁路
- `ServerLevel.MAX_BLOCK_TICKS_PER_TICK = 65536`，超出会 warn。
- 1.21 实验性 `tickrate` 命令。

### 4.9 C++ 移植讨论
- 用 ECS 替代 OOP 多态。
- Job System 并行 random tick。

### 5.1 红石作为信号传播图

### 5.2 信号源、传输、负载三类组件

- 传输：红石线、中继器、比较器、观察者。
- 负载：活塞、门、TNT、漏斗、发射器...

### 5.3 RedstoneWire 经典扁平传播（DefaultRedstoneWireEvaluator）
- 以"线段团"为单位的 DFS 传播算法。
- 与"准连接性 (Quasi-Connectivity, QC)"的关系。
- "BUD" 现象的代码层解释。

### 5.4 1.21 实验性红石：ExperimentalRedstoneWireEvaluator
- 1.21 引入的"局部传播"实验性算法（命令行 `experimental_redstone`）。
- 用 `Orientation` 携带方向信息，避免循环依赖。

### 5.5 Orientation：朝向感知更新
- `Orientation` 类 = "更新进入方向" + "侧面"。
- 为什么这能让红石更"自然"。

### 5.6 强信号 vs 弱信号
- `getSignal` vs `getDirectSignal`。
- "强供电方块"概念。

### 5.7 比较器、中继器、活塞
- ComparatorBlock：测量信号或读取容器。
- RepeaterBlock：放大 + 延迟 + 锁存。

### 5.8 更新顺序与时序
- 神秘的 NSWE-DUP 顺序：邻居更新顺序由 `Direction.values()` 决定。

### 5.9 InstantNeighborUpdater 解析
- 何时仍使用 instant（结构生成期）。

### 5.10 C++ 实现：图算法 vs ECS 事件

## 第 6 部分：流体动力学

> 关键词：`net.minecraft.world.level.material.*`、`FlowingFluid`。

### 6.1 流体作为 BlockState 的特殊化
- 流体本身有 `FluidState`（独立于 BlockState），但在世界中存储为 BlockState（水方块、熔岩方块）。
- waterloggable 方块：BlockState 中有一个 boolean `waterlogged` 让"同一格既有方块又有水"。

### 6.2 FlowingFluid 算法
- `FlowingFluid.spreadTo` / `getSpread` / `tick`。
- 8-邻居扩散，向下优先。

### 6.3 水流扩散 8-neighbor 距离场
- `getSlopeDistance`：找最近"可下落点"的距离。
- 水最大流距 = 7。

### 6.4 LavaFluid 差异
- 主世界流速更慢、流距更短（4），下界全速。
- 与水接触：水 → 黑曜石 / 圆石；熔岩 → 石头。

### 6.5 Source / Falling / Level 状态
- `level` ∈ [1..8]，8 = source，1 = 最远。
- `falling` flag = 垂直下落水柱。

### 6.6 与 Aquifer 区别（生成 vs 运行时）
- Aquifer = 生成期一次性铺水。
- FlowingFluid = 运行时每 tick 流动。

### 6.7 与方块的交互
- 水推方块（红色 / 蓝色 / 黑曜石）。
- 海绵吸水。
- 灵魂土上水柱效果（虚拟流体）。

### 6.8 性能与 tick 限额
- `MAX_FLUID_TICKS_PER_TICK`。
- 卡顿源：长水流 + 大范围水位重算。

### 6.9 C++ 移植：FluidSim ECS 系统
- 用单独的 fluid 体素层替代 BlockState 嵌入式存储（性能更好，但破坏 waterlogged 语义）。
- 推荐折中：waterlogged 保留 BlockState flag，纯水/纯熔岩走单独 layer。

## 第 7 部分：网络协议

> 关键词：`net.minecraft.network.*`、`net.minecraft.server.network.*`、`net.minecraft.client.multiplayer.*`。

### 7.1 整体架构：Netty pipeline
- `Connection` (Netty `Channel`)。
- 解码栈：`Splitter` (length-prefix) → `Decompressor` (zlib，可选) → `Decryptor` (AES-CFB8，可选) → `PacketDecoder`。
- 编码栈对称。

### 7.2 连接状态机：5 阶段
```
HANDSHAKE ──→ STATUS（服务器列表 ping）
            └→ LOGIN（鉴权 + 加密握手）
                └→ CONFIGURATION（资源包、注册同步）
                    └→ PLAY（游戏中）
```
1.20.2 之后引入 CONFIGURATION 阶段，是 1.21 网络层的关键变化之一。

### 7.3 PacketFlow 方向
- `CLIENTBOUND` / `SERVERBOUND`。
- 同名包在两个方向上是不同类型。

### 7.4 Packet 序列化（StreamCodec）
- 1.20.5+ 引入 `StreamCodec<B, T>`：组合式编解码 DSL。
- 替代旧的手写 `read(FriendlyByteBuf)`。

### 7.5 包压缩与加密
- 阈值压缩（默认 256 字节以上）。
- AES-CFB8 + 共享密钥（RSA 握手交换）。
- 离线模式 vs 在线模式。

### 7.6 关键包速览
| 类别 | 包 |
|------|----|
| 玩家移动 | ServerboundMovePlayerPacket / ClientboundPlayerPositionPacket |
| 区块同步 | ClientboundLevelChunkWithLightPacket |
| 单格更新 | ClientboundBlockUpdatePacket |
| 段批量更新 | ClientboundSectionBlocksUpdatePacket |
| 实体增量 | ClientboundMoveEntityPacket（用 VecDeltaCodec 压缩 delta） |
| 玩家信息 | ClientboundPlayerInfoUpdatePacket |
| 砍树/挖方块 | ServerboundPlayerActionPacket |

### 7.7 Bundle Packet 概念
- `BundlePacket<P>` + `ClientboundBundleDelimiterPacket`：把多个独立包打包让客户端在同一 frame 应用，避免视觉 desync。

### 7.8 同步模型：权威服务端 + 预测客户端
- 客户端做"乐观预测"（自己移动、自己挖方块），服务端校验 + 回滚。
- "回滚条" / rubber-banding 现象的代码出处。

### 7.9 Chunk 流式发送策略
- `ChunkMap` + `ChunkHolder` 维护"哪个玩家看哪个 chunk"。
- "tracking distance" 与 view-distance 的区别。

### 7.10 C++ 移植讨论
- 与 UE5 网络层（NetDriver / Replication）对比。
- 如何用 enet / yojimbo / quic 替代 Netty。
- 字节序、varint、uuid 表示的兼容点。
