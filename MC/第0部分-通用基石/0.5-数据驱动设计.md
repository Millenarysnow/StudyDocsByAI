# 0.5 数据驱动设计：Codec、DataFixerUpper 与 Datapack

## 0.5.0 你将在本节学到什么

读完这一节你应当能闭着眼睛回答：

1. "Datapack" 到底是什么？是 mod 吗？玩家用得上吗？为什么 Mojang 自己也用？
2. 我打开一个 datapack，里面 `data/minecraft/worldgen/biome/plains.json` 长什么样？谁在解析它？
3. `Codec<T>` 这个类在 Mojang 代码里到处出现，它到底是序列化器还是反序列化器？
4. 同一份 `Codec<T>` 怎么能既写 JSON 又写 NBT 又写网络包？`DynamicOps` 是怎么抽象掉数据格式差异的？
5. `DataFixerUpper` 是什么？它和 Codec 是同一个东西吗？1.18 的存档怎么读到 1.21？
6. 我在 C++ 引擎里要复现这套数据驱动机制，最小设计是什么？

## 0.5.1 一切的起点：Mojang 的工程哲学转向

2014-2017 年的 Minecraft 是一个"硬代码地狱"。每加一种 biome 都要改 Java、重编译、发版本。modder 痛苦，Mojang 自己的内部迭代也痛苦。

2018 年起 Mojang 启动 "data-driven" 改造：把所有可枚举的"配方"——recipe / loot table / advancement / structure / biome / dimension / worldgen ——从 Java 代码里搬到 JSON 文件，运行时读取。

到 1.18，"地形生成"这个最大、最难、最敏感的子系统也被搬进 JSON：noise settings / density functions / surface rules / placed features / structure pools 全部 JSON 化。整个 worldgen 现在只剩**几个不可数据驱动的硬编码核心算法**（如噪声函数本身），其余都是 datapack。

到 1.21，Mojang 自己加新内容（trial chambers、breeze、wind charge）的工作流是：**先在 datapack 里 prototype，跑测试，再把"通用算法"提到 Java**。Datapack 不是 mod 玩具，是 Mojang 自己的开发主战场。

## 0.5.2 Datapack 是什么：物理形态

Datapack = 一组按约定目录结构组织的 JSON 文件，外加一个 `pack.mcmeta` 元数据。

物理形态可以是：

1. **存档里的 datapack 文件夹**：`<saves>/<world>/datapacks/<packname>/`。
2. **存档里的 datapack zip**：同上路径下放 .zip。
3. **内置 datapack**：`net.minecraft.server` 的 jar 内置一个名叫 `vanilla` 的 datapack，包含 Mojang 所有的 vanilla 配方。
4. **mod jar 内置**：Forge / Fabric 的 mod 也可以内置 datapack。

**目录约定**：

```
<packname>/
├── pack.mcmeta                # 元数据（版本兼容性等）
├── data/                      # 所有数据文件根
│   ├── <namespace>/
│   │   ├── advancement/       # 成就
│   │   ├── recipe/            # 合成配方
│   │   ├── loot_table/        # 战利品
│   │   ├── tags/              # tag 文件
│   │   │   ├── block/
│   │   │   ├── item/
│   │   │   └── worldgen/biome/
│   │   ├── worldgen/          # 世界生成
│   │   │   ├── biome/
│   │   │   ├── density_function/
│   │   │   ├── noise/
│   │   │   ├── noise_settings/
│   │   │   ├── configured_feature/
│   │   │   ├── placed_feature/
│   │   │   ├── structure/
│   │   │   ├── structure_set/
│   │   │   └── ...
│   │   ├── dimension/         # 维度配置
│   │   ├── dimension_type/
│   │   └── ...
│   └── minecraft/             # vanilla 命名空间（覆盖默认）
└── pack.png                   # 缩略图（可选）
```

**目录就是 ResourceLocation**——`data/minecraft/worldgen/biome/plains.json` 就是 `ResourceKey<Biome>`，registry = `worldgen/biome`、entry = `minecraft:plains`。

**多个 datapack 同时启用**：按优先级排序，**后者覆盖前者**（同一个 ResourceLocation 后定义胜）。这就是 mod 兼容性的来源。

打开本仓库 `setup` 后会有一个抽出来的 vanilla datapack 在 `run/` 目录附近，你可以照着上面这个结构对照浏览。

## 0.5.4 Codec：双向可逆的序列化器

谁负责把上面那份 JSON 解析成 `Biome` 对象？答案是 **Codec**。

`Codec<T>` 是 Mojang 自家库 **DataFixerUpper**（DFU）里的核心抽象。它是一个 **双向**、**可组合**、**与具体数据格式无关**的序列化器。

**双向**：一个 `Codec<T>` 同时知道：
- 怎么把 T 编码（encode）成某个数据格式。
- 怎么从某个数据格式解码（decode）成 T。

```java
public interface Codec<A> extends Encoder<A>, Decoder<A> { ... }
```

**可组合**：复杂类型的 codec 由简单类型的 codec **组合** 出来：

```java
// 简化的 Biome codec 写法
public static final Codec<Biome> CODEC = RecordCodecBuilder.create(builder -> builder.group(
    Codec.BOOL.fieldOf("has_precipitation").forGetter(Biome::hasPrecipitation),
    Codec.FLOAT.fieldOf("temperature").forGetter(Biome::getTemperature),
    Codec.FLOAT.fieldOf("downfall").forGetter(Biome::getDownfall),
    BiomeSpecialEffects.CODEC.fieldOf("effects").forGetter(Biome::getSpecialEffects),
    MobSpawnSettings.CODEC.fieldOf("spawners").forGetter(Biome::getMobSettings),
    BiomeGenerationSettings.CODEC.fieldOf("...").forGetter(...)
).apply(builder, Biome::new));
```

读这种代码的诀窍：

- `Codec.BOOL` / `Codec.FLOAT` / `Codec.STRING` ⋯⋯ 是基础 codec。
- `.fieldOf("name")` 把它变成 "JSON 中名为 name 的字段"。
- `.forGetter(Biome::getTemperature)` 告诉 codec 怎么从 `Biome` 实例读出这个字段（用于编码）。
- `.apply(builder, Biome::new)` 告诉 codec 怎么从所有字段构造 `Biome`（用于解码）。
- `RecordCodecBuilder.create` 把上面这些拼成一个完整的 `Codec<Biome>`。

**这就是 Mojang 几乎所有 datapack-loadable 类型的写法**。当你在源码里看到一个 `public static final Codec<X> CODEC = RecordCodecBuilder.create(...)`，就是一份"X 的 JSON schema 定义"。

**与具体数据格式无关**：`Codec<T>` 不关心目标是 JSON / NBT / network buffer，由 `DynamicOps<U>` 抽象。下一小节解释。

## 0.5.5 DynamicOps：抽象数据格式

`DynamicOps<U>` 描述"通用树形数据结构 U 的基本操作"——怎么创建一个数字、怎么创建一个字符串、怎么创建一个 map、怎么遍历一个 list。

实现：
- **`JsonOps.INSTANCE`**：U = `JsonElement`（来自 Gson）。把 codec 操作映射到 JSON 解析 / 输出。
- **`NbtOps.INSTANCE`**：U = `Tag`（NBT）。把 codec 操作映射到 NBT 读写。
- **`ByteBufOps`** 与 **`StreamCodec`**：网络字节流（这个 1.20.5 后改为独立的 `StreamCodec`，但思路一致）。

**关键点**：同一个 `Codec<Biome>` 配合不同的 `DynamicOps`，可以：

```java
// 编码到 JSON
JsonElement json = Biome.CODEC.encodeStart(JsonOps.INSTANCE, biome).getOrThrow();

// 编码到 NBT
Tag nbt = Biome.CODEC.encodeStart(NbtOps.INSTANCE, biome).getOrThrow();

// 解码从 JSON
Biome b = Biome.CODEC.parse(JsonOps.INSTANCE, json).getOrThrow();

// 解码从 NBT
Biome b2 = Biome.CODEC.parse(NbtOps.INSTANCE, nbt).getOrThrow();
```

**写一次 codec，三处复用**——JSON datapack、NBT 存档、网络包（虽然 1.20.5+ 网络包改成 StreamCodec，但概念延续）。这是 DataFixerUpper 真正威力的地方。

## 0.5.6 一个 codec 的最小完整例子

写一份「自定义点」的 codec，演示完整流程：

```java
public record Point3D(int x, int y, int z) {
    public static final Codec<Point3D> CODEC = RecordCodecBuilder.create(b -> b.group(
        Codec.INT.fieldOf("x").forGetter(Point3D::x),
        Codec.INT.fieldOf("y").forGetter(Point3D::y),
        Codec.INT.fieldOf("z").forGetter(Point3D::z)
    ).apply(b, Point3D::new));
}
```

对应的 JSON：

```json
{ "x": 10, "y": 64, "z": -3 }
```

对应的 NBT（SNBT 表示）：

```
{ x: 10, y: 64, z: -3 }
```

**编码 / 解码代码示例**：

```java
Point3D p = new Point3D(10, 64, -3);

JsonElement json = Point3D.CODEC.encodeStart(JsonOps.INSTANCE, p).getOrThrow();
String s = json.toString();   // {"x":10,"y":64,"z":-3}

Point3D p2 = Point3D.CODEC.parse(JsonOps.INSTANCE, json).getOrThrow();
assert p2.equals(p);
```

**进阶：可选字段、默认值**：

```java
public record Wave(float amplitude, float frequency, float phase) {
    public static final Codec<Wave> CODEC = RecordCodecBuilder.create(b -> b.group(
        Codec.FLOAT.fieldOf("amplitude").forGetter(Wave::amplitude),
        Codec.FLOAT.fieldOf("frequency").forGetter(Wave::frequency),
        Codec.FLOAT.optionalFieldOf("phase", 0.0f).forGetter(Wave::phase)
    ).apply(b, Wave::new));
}
```

`optionalFieldOf("phase", 0.0f)` 表示 JSON 里 `phase` 字段缺省时默认取 0。

**进阶：和或类型（sum type）**——dispatch codec：

```java
public sealed interface Shape permits Circle, Box {
    Codec<Shape> CODEC = ResourceLocation.CODEC.dispatch(Shape::typeId, Shape::codecForType);
    ResourceLocation typeId();
    Codec<? extends Shape> codecForType();
}
```

JSON：

```json
{ "type": "minecraft:circle", "radius": 3.0 }
{ "type": "minecraft:box", "width": 2, "height": 1, "depth": 5 }
```

DataFixerUpper 用 `dispatch` 把"先读一个 type 字段，再按 type 选不同子 codec"封装好了。后面 Module 3 的 DensityFunction DSL 就是用这个机制实现的。

## 0.5.7 RegistryDataLoader：把 JSON 装进 Registry

谁把磁盘上的 JSON 一个个读出来，调 codec 解码，塞到 Registry 里？

答：`net.minecraft.resources.RegistryDataLoader`。

它的工作流（极简化）：

```java
for (RegistryKey registry : registriesToLoad) {                  // 比如 BIOME / DENSITY_FUNCTION 等
    Codec<T> codec = codecOf(registry);
    for (ResourceLocation file : datapack.listFiles(registry)) { // 比如 minecraft:plains
        JsonElement json = parseJson(datapack.read(file));
        T value = codec.parse(JsonOps.INSTANCE, json).getOrThrow();
        targetRegistry.register(file, value);
    }
}
```

实际代码更复杂——要处理 mod 加载顺序、处理跨 registry 的 reference（如一个 Biome 引用一个 PlacedFeature，需要先加载 PlacedFeature；DFU 提供"延迟绑定"机制处理这个），处理覆盖优先级。但骨架就是这样。

加载发生在 **世界打开之前**。一个世界开起来之后，所有动态注册表已经填好了。后面 worldgen / tick 都从这里读。

## 0.5.8 DataFixerUpper：跨版本兼容性

最后一个名词。`DataFixerUpper`（**DFU**）是 Mojang 单独开源的一个库（github.com/Mojang/DataFixerUpper），后来内嵌到游戏。

它的目标：**把旧版本的存档 / datapack 自动转换为新版本的格式**。

举例：1.13 之前方块用整数 ID（`stone = 1`），1.13 之后用字符串 ID（`stone = "minecraft:stone"`）。一个 1.12 存档要在 1.21 里打开，需要把所有 chunk palette 里的整数 ID 转成对应的字符串 ID。这种"格式迁移"叫 **fix**（修补）。

**DFU 的核心抽象**：

- **Schema**：描述某个版本时刻所有 NBT 字段的类型。每发布一个新格式版本（DataVersion）就生成一个新 Schema。
- **Type**：基础类型 / 记录 / 求和 / 列表 / map ⋯⋯
- **Rule**：一个 fix 规则。比如「把 `tile` 字段重命名为 `Block`」「把整数 0..255 映射到对应的字符串 ID」⋯⋯

**`DataVersion`** 是一个单调递增的整数（1.21.4 大约是 4189），每个 NBT 文件 / 存档都记录自己保存时的 DataVersion。加载时 DFU 把它从旧 DataVersion 一步步 fix 到当前 DataVersion，应用所有中间规则。

**Codec 与 DFU 的关系**：

- `Codec<T>` 描述**当前版本**的格式。
- `DataFixerUpper` 描述**所有版本之间的迁移规则**。
- 加载流程：先 DFU 把旧 JSON / NBT 升级到当前格式，再 Codec 解码到 Java 对象。

**对我们移植的意义**：

- 你的 C++ 引擎可以**先不实现 DFU**——只支持当前版本的存档格式即可。
- 但要**预留 DataVersion 字段**，否则未来想兼容旧版很痛苦。
- 真要实现 DFU，是另一篇大文章——DFU 用了不少 monad / 范畴论的概念（`Type`、`TypeFamily`、`Pointer`），不是周末项目。

## 0.5.9 实际代码片段对比

最后看一段真实的 Codec 代码，把上面所有抽象落实下来。

`net.minecraft.world.level.biome.Biome` 内部的 codec 拼装（简化版）：

```java
// Biome.java (示意)
public static final Codec<Biome> DIRECT_CODEC = RecordCodecBuilder.create(b -> b.group(
    ClimateSettings.CODEC.forGetter(Biome::getClimateSettings),
    BiomeSpecialEffects.CODEC.fieldOf("effects").forGetter(Biome::getSpecialEffects),
    BiomeGenerationSettings.CODEC.forGetter(Biome::getGenerationSettings),
    MobSpawnSettings.CODEC.forGetter(Biome::getMobSettings)
).apply(b, Biome::new));

public static final Codec<Holder<Biome>> CODEC =
    RegistryFileCodec.create(Registries.BIOME, DIRECT_CODEC);
public static final Codec<HolderSet<Biome>> LIST_CODEC =
    RegistryCodecs.homogeneousList(Registries.BIOME, DIRECT_CODEC);
```

**两个 codec 同时存在**：

- `DIRECT_CODEC`：把整个 Biome **内联** 解析（写在父 JSON 里）。
- `CODEC`（`Holder<Biome>` 版）：当父 JSON 只写 `"minecraft:plains"` 这种引用 ID 字符串时使用——Codec 自动去 Registry 查找。

`RegistryFileCodec` 是专门处理"文件中的字符串 = registry 引用"这一模式的工厂。它在底层尝试两种解析：

1. JSON 里是字符串 → 当 ResourceLocation 用，去 Registry 找。
2. JSON 里是对象 → 用 `DIRECT_CODEC` 直接解码并构造一个 `Holder.Direct`。

这个二选一让 datapack 既能用 `"minecraft:plains"` 引用现成 biome，也能就地内联一个新 biome。

## 0.5.10 C++ 移植：codec 的最小可行实现

C++ 没有 DFU 这么强的库，但概念可以照搬。最简洁的做法是用 `nlohmann::json` + 手写模板：

```cpp
template<typename T>
struct Codec {
    using Encode = std::function<nlohmann::json(const T&)>;
    using Decode = std::function<T(const nlohmann::json&)>;
    Encode enc;
    Decode dec;
};

// 基础
extern Codec<int> CODEC_INT;
extern Codec<float> CODEC_FLOAT;
extern Codec<std::string> CODEC_STRING;

// 组合
template<typename T>
class CodecBuilder { ... };  // 类似 RecordCodecBuilder

// 例子
struct Point3D { int x, y, z; };
inline const Codec<Point3D> POINT_CODEC = makeCodec<Point3D>()
    .field("x", &Point3D::x, CODEC_INT)
    .field("y", &Point3D::y, CODEC_INT)
    .field("z", &Point3D::z, CODEC_INT)
    .build();
```

**进阶**：抽象 `DynamicOps<U>`：

```cpp
template<typename U>
struct DynamicOps {
    virtual U createInt(int v) = 0;
    virtual U createString(const std::string& s) = 0;
    virtual U createMap(std::map<U, U> map) = 0;
    virtual std::optional<int> getInt(const U& v) = 0;
    // ...
};

class JsonOps : public DynamicOps<nlohmann::json> { ... };
class NbtOps  : public DynamicOps<NbtTag> { ... };
class StreamOps : public DynamicOps<std::vector<std::byte>> { ... };
```

然后 codec 不绑定具体格式：

```cpp
template<typename T>
struct Codec {
    template<typename U>
    U encode(const DynamicOps<U>& ops, const T& value) const;
    template<typename U>
    T decode(const DynamicOps<U>& ops, const U& value) const;
};
```

**实现路径建议**：

1. **第一步**：先用 `nlohmann::json` 写个简单版本，把 datapack 加载跑通。
2. **第二步**：等需要把同一对象写进 NBT 时，把 codec 抽象到 `DynamicOps`。
3. **第三步**：网络包再加 StreamOps。

不要一开始就追求 1:1 复刻 DFU——它的复杂性在 C++ 里反而是负担。

---

## 0.5.11 一句话总结

Datapack 是一组按 `data/<ns>/<category>/<name>.json` 组织的资源文件，由 `RegistryDataLoader` 在世界加载时塞进 `Registry`；`Codec<T>` 是 Mojang 的双向可逆序列化器，配合 `DynamicOps<U>` 抽象掉具体格式（JSON / NBT / 字节流），让一份 codec 三处复用；`DataFixerUpper` 在 codec 之上提供跨版本格式迁移；这套机制让 Mojang 自己的 worldgen 几乎不写 Java，全靠 datapack 拼。
