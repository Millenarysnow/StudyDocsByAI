# 0.6 反编译源码导读约定

## 0.6.0 你将在本节学到什么

读完这一节你应当能闭着眼睛回答：

1. `p_122016_` 这种参数名是什么？为什么不是 `pos` `state` 这种正常名字？

## 0.6.1 `p_NNNNNN_`：反编译丢掉的参数名

打开仓库里几乎任何一个 `net.minecraft.*` 的文件，你会看到大量这种代码：

```java
public static long offset(long p_121916_, Direction p_121917_) {
    return offset(p_121916_, p_121917_.getStepX(), p_121917_.getStepY(), p_121917_.getStepZ());
}
```

`p_121916_` 不是某种密码、不是 obfuscation 的反义词、不是奇怪的协议字段。它就是 **"第 121916 号 SRG 占位参数名"** 的缩写，前缀 `p_` 是 "parameter"，末尾 `_` 是分隔。它对应的真实参数名 Mojang 不发布。

### 为什么是这样

Mojang 自己用的内部源码当然有正常参数名（`pos`、`state`、`level` 之类）。但发布给玩家的是混淆后的 jar——所有方法 / 字段 / 类的名字都被改成 `a` `b` `c` 的两字符随机组合。

社区做了两件事来还原可读性：
1. **MCP / Mojang Mappings**：把混淆名 `a` / `b` / `c` 映射回有语义的名字（类名、方法名、字段名）。1.14.4 之后 Mojang 自己开始发布 "official mappings" 解决这一层。
2. **方法参数名**：但这一层 Mojang **没有公开**。混淆后的方法签名里参数没有名字，只有类型。

所以反编译工具看到 `void method(BlockPos a, BlockState b)`，无法还原 a 和 b 到底叫什么，于是按"方法 + 参数序号"生成稳定的占位符，比如 `p_121916_`。

### 怎么读

**核心心法：把它当通配的 `_` 看待，根据上下文推语义**。

```java
public static long offset(long p_121916_, Direction p_121917_) {
    return offset(p_121916_, p_121917_.getStepX(), p_121917_.getStepY(), p_121917_.getStepZ());
}
```

读这段时心里念：

> "这是 offset 函数。第一个参数是 long 类型，下面又被传到另一个 offset 重载里且当**第一个 long**——所以它是被偏移的目标 long（packed BlockPos）。第二个参数 Direction 类型，被取 stepX/Y/Z——所以它是偏移方向。"

上下文足够了，参数名等于不存在。

**实战 idiom**：拷贝代码到 IDE 里，IntelliJ 的 "Rename" 重构能把 `p_NNNNNN_` 一键改成有意义的名字（仅本地有效）。如果你想长期阅读源码，建议在 IntelliJ 装 `MCP-Reborn` 工程时用 IDE 自带的 rename 把高频方法的参数批量改名（注意只在你 fork 的分支里改，别提交到 master）。

### 不要在 patch 里改

如果你给 Forge / Fabric 提 PR、写 mod、做 patch，**不要**把 `p_NNNNNN_` 改成 `pos`。这会让你的 patch 在下一次 mappings 更新时全文 conflict。

但本仓库是 MCP-Reborn，已经 commit 过修过的源码——你看到的反编译产物就是工程的源代码。你**可以**在 `mcp.client.*` 自己的代码里用正常名字。Mojang 包路径 `net.minecraft.*` 下的代码尽量保留 `p_NNNNNN_`，否则下次 ForgeGradle re-decompile 会冲突。

## 0.6.2 异常变量命名为类型小写名

```java
try {
    something();
} catch (IOException ioexception) {
    LOGGER.warn("...", ioexception);
} catch (NumberFormatException numberformatexception) {
    return 0;
}
```

**反编译惯例**：catch 块里捕获的异常变量名 = 类型名小写。`IOException` → `ioexception`，`NumberFormatException` → `numberformatexception`，`InterruptedException` → `interruptedexception`。

为什么？因为 Mojang 自己的源码里这些变量原本叫什么，混淆后只剩类型——反编译工具看到 `catch (X)` 没参数名，就按"类型小写"生成可读默认名。这个习惯到处都是，**习惯就好**。

读源码时心里把它当 `e` 看待即可，不要被名字长度晃住。

### 同理：局部变量

很多局部变量也是 "类型小写" 风格命名，因为反编译工具按类型分配：

```java
ServerLevel serverlevel = (ServerLevel)level;
BlockPos blockpos = entity.blockPosition();
LevelChunk levelchunk = serverlevel.getChunkAt(blockpos);
ChunkPos chunkpos = levelchunk.getPos();
```

这种 "类型小写" 的局部变量在主世界生成代码、生物群系代码里特别密集。读起来有点啰嗦，但好处是**类型直接写在变量名里**，跳读时不需要在 IDE 里 hover 看类型。

很多变量是简单的 `i`、`j`、`k`、`l` 这种数学风格命名。这是另一回事——Mojang 自己写代码就是这个风格（看 `BlockPos.asLong` 里的 `long i`、`long j`），反编译保留下来了。

## 0.6.3 `LOGGER` 字段：日志约定

仓库里几乎每个 vanilla 类都有：

```java
import com.mojang.logging.LogUtils;
import org.slf4j.Logger;
// ...
public class Foo {
    private static final Logger LOGGER = LogUtils.getLogger();
}
```

`LogUtils.getLogger()` 是 Mojang 包装的快捷函数，等价于 `LoggerFactory.getLogger(MethodHandles.lookup().lookupClass())`——按调用类自动拿到 SLF4J Logger。

底层是 **SLF4J + Logback**。

**用法**：

```java
LOGGER.trace("...");
LOGGER.debug("...");
LOGGER.info("World loaded in {} ms", elapsed);
LOGGER.warn("Can't keep up!");
LOGGER.error("Failed to save chunk {}", chunkPos, exception);
```

`{}` 是 SLF4J 占位符（不是 `%s`）。最后一个参数如果是 `Throwable` 会被 SLF4J 自动识别并打印 stacktrace。

**对照 C++ spdlog**：SLF4J 等价于 spdlog，Logback 等价于 spdlog 的 sink。`LogUtils.getLogger()` ≈ `spdlog::default_logger()`。语法风格几乎一样，迁移很自然。

**约定细节**：

- `LOGGER` 字段一律 `private static final`、命名一律全大写 `LOGGER`。
- 客户端独有的类**也**用同样的 LOGGER。
- 不要在 hot loop 里调 `LOGGER.debug(...)`——SLF4J 会构造参数 array，分配垃圾。要么用 `LOGGER.isDebugEnabled()` 守门，要么直接不打。

## 0.6.4 注解大全：每个分别管什么

源码里出现的注解可以分成几类。

### 必读类

| 注解 | 来源 | 含义 |
|------|------|------|
| `@Override` | java.lang | 标记覆盖父类方法。编译器检查。读时跳过即可。 |
| `@Deprecated` | java.lang | 不推荐使用。Mojang 用得很多，但**有时候只是 Forge 加的**——表示 mod 不应该直接调，但 vanilla 内部还在用。**不要看到 `@Deprecated` 就以为它要被删**。 |
| `@Nullable` | javax.annotation | 该值 / 参数 / 返回可能为 null。**读到这个一定要在脑子里加上 null check 意识**。 |
| `@OnlyIn(Dist.CLIENT)` | net.minecraftforge.api.distmarker | 仅客户端 jar 存在。详见 0.3 节。 |
| `@OnlyIn(Dist.DEDICATED_SERVER)` | 同上 | 仅专用服务端 jar 存在。罕见。 |

### 信息提示类（读源码时关注）

| 注解 | 含义 |
|------|------|
| `@Immutable` (来自 javax.annotation.concurrent) | 该类是不可变的。多线程安全。 |
| `@MustBeInvokedByOverriders` | Override 时必须调 super。 |
| `@VisibleForTesting` | 仅为测试公开，正式代码别调。 |
| `@SerialVersionUID` | Java 标准序列化标记。无视。 |

### Mojang 内部 / 框架类（你写代码不需要）

| 注解 | 含义 |
|------|------|
| `@SerializableField` | DFU 内部 |
| `@DontObfuscate` | 混淆器忽略 |

### 不要被吓到的类

`com.google.errorprone.annotations.*` 的一些注解（如 `@CheckReturnValue`、`@Immutable`）由 Errorprone 静态检查工具识别。Mojang 自己用的不多，但如果你看到了，含义都能从名字猜出来，无需深究。

## 0.6.5 import 排序约定

每个文件顶部会有这种排列：

```java
package net.minecraft.world.level.block;

import com.google.common.collect.ImmutableList;
import com.mojang.serialization.Codec;
import it.unimi.dsi.fastutil.ints.Int2ObjectMap;
import java.util.List;
import java.util.Optional;
import javax.annotation.Nullable;
import net.minecraft.core.BlockPos;
import net.minecraft.world.level.Level;
import org.slf4j.Logger;
```

**严格的字母序，按以下顶级前缀分组**：

1. `com.*` —— 第三方库（Google Guava、Mojang DFU、jsoup ⋯⋯）
2. `it.*` —— Italian fastutil（高性能基础容器）
3. `java.*` —— JDK 标准库
4. `javax.*` —— JDK 扩展（注解 / 注释）
5. `net.*` —— Minecraft 自身 + Forge / Fabric
6. `org.*` —— SLF4J 等开源库

**组与组之间没有空行**——这是和很多 Java 项目（Google style）不同的地方。Mojang 用紧凑排列。

**禁止 wildcard import**：没有 `import java.util.*`，必须每个类一行。

**怎么加新 import**：

- IntelliJ 配好 "Auto Import" + "Optimize Imports" + 上面的分组顺序，写代码时 IDE 自动维护。
- 手动加时找到正确字母位置插入，**不要**乱往末尾加（后面 patch 时这种风格不一致会被 lint 拒）。

## 0.6.6 K&R 大括号 + 4 空格缩进 + 长行

```java
if (something) {
    doIt();
} else {
    doOther();
}
```

K&R style 大括号（左大括号在行末），4 空格缩进，**没有 tab**。

**长行**：Mojang 的源码经常单行 120-200 字符，不强制换行。读起来横向滚动累，但反编译保留原结构通常就这样。**不要**为了"美观"主动给反编译代码换行——会破坏 patch diff。

**布尔三元表达式**经常嵌套到不可读的程度：

```java
return p_121973_ == 0 && p_121974_ == 0 && p_121975_ == 0
    ? this
    : new BlockPos(this.getX() + p_121973_, this.getY() + p_121974_, this.getZ() + p_121975_);
```

这是反编译的常见产物——原本可能是几行 if/else，反编译器折叠成三元。读熟后比 if/else 还快。

## 0.6.7 没有 javadoc / 没有注释

打开 vanilla 包里随便一个文件，你几乎找不到 javadoc 或行内注释。**不是 Mojang 没写**——是反编译丢失了 / 不完整。Mojang 内部有详尽 javadoc，但它们没进 obfuscated jar，反编译产出里全部消失。

读源码时不要指望注释帮你。**所有理解都要靠**：
1. 类名 / 方法名 / 字段名（mapping 还原后多数有意义）。
2. 参数 / 局部变量类型推断（即使名字是 `p_NNNNNN_`，类型也能告诉你很多）。
3. 调用关系（IDE 的 "Find Usages" 是你最好的朋友）。
4. 外部资料：Minecraft Wiki（minecraft.wiki / minecraft.fandom.com）、Fabric Wiki、Cubitect 的 cubiomes 项目、Misode 的 Worldgen Visualizer。
5. 这个教程。

**写自己的代码时**则相反：好好写注释 / 文档。本仓库 `mcp.client.*` 自己的代码可以用正常风格。

## 0.6.8 异常处理风格：吞 vs throws

Mojang 风格的异常处理有几个特征：

```java
// 风格 1：try / catch + LOGGER.error，吞掉
try {
    do_io();
} catch (IOException ioexception) {
    LOGGER.error("Failed to ...", ioexception);
}

// 风格 2：throws 一路传到顶层
public void process() throws IOException { ... }

// 风格 3：把已知异常包成 Util.pauseInIde
try {
    something();
} catch (Exception exception) {
    if (SharedConstants.IS_RUNNING_IN_IDE) {
        Util.pauseInIde(exception);   // IDE 里直接抛出来 break debugger
    }
    LOGGER.error("...", exception);
}
```

**第三种**特别值得注意：`Util.pauseInIde(exception)` 是 Mojang 自己的"开发期诊断"——只在 IDE 模式下抛出异常断到 debugger，正式打包时静默吞掉。这种"开发模式 vs 发布模式行为不同"的代码很多，认得即可。

## 0.6.9 文件组织约定

### 单文件多类

Mojang 喜欢把"接口 + 多个内部实现 / 子类"塞进同一个 `.java` 文件。例子：

- `Climate.java` 包含 `Climate.Parameter`、`Climate.ParameterPoint`、`Climate.RTree`、`Climate.Sampler`、⋯⋯
- `DensityFunction.java` 是 interface，但 `DensityFunctions.java` 是另一个文件，里面装了所有具体实现 record。
- `Holder.java` 同时定义 `Holder` 接口和 `Holder.Direct`、`Holder.Reference`、`Holder.Kind` 等子类型。

**为什么**：作用域局部、避免文件爆炸、modifier 关系自然（内部类自动 `static`）。

读源码的 IDE 提示：**总是用 "Navigate → Symbol" 找类名**，而不是按文件名找。一个名字可能藏在意想不到的文件里。

### 包级 helper 类

很多地方有 `Xxxs`（复数）类作为 `Xxx` 类型的"实例工厂 + 注册集合"：

| 类 | 作用 |
|----|------|
| `Blocks` | `Block` 类型的所有静态实例（`Blocks.OAK_LOG`、`Blocks.STONE` ⋯⋯） |
| `Items` | `Item` 实例 |
| `Biomes` | `Biome` 实例（实际是 `ResourceKey<Biome>`） |
| `Fluids` | `Fluid` 实例 |
| `Features` | `Feature<?>` 实例 |
| `DensityFunctions` | `DensityFunction` 工厂方法 |
| `Noises` | 所有 noise key |
| `BiomeTags` | 所有 biome tag |
| `BlockTags` | 所有 block tag |

**约定**：`Xxxs` 静态字段 / 工厂集合，`Xxx` 是基础抽象。看到一个名字 `Xxxs` 就知道里面装了一堆同类静态成员。

## 0.6.10 一段示范代码逐行读

把上面所有约定串起来，读一段真实代码（取自 `BlockPos.java` 行 122-127）：

```java
public static long asLong(int p_121883_, int p_121884_, int p_121885_) {
    long i = 0L;
    i |= ((long)p_121883_ & PACKED_X_MASK) << X_OFFSET;
    i |= ((long)p_121884_ & PACKED_Y_MASK) << 0;
    return i | ((long)p_121885_ & PACKED_Z_MASK) << Z_OFFSET;
}
```

读时心里串：

> "static 方法 asLong，三个 int → long。三个参数没语义名，但函数名 asLong 暗示是把"BlockPos 三轴坐标 → packed long"。第一个 `p_121883_` 上来就和 PACKED_X_MASK 与运算后左移 X_OFFSET → 是 X。第二个和 PACKED_Y_MASK 共用 → 是 Y。第三个 PACKED_Z_MASK 共用 → 是 Z。
>
> 局部变量 `long i = 0L` 是累加器，标准的 packed-long 构造模式。
>
> 三个 mask 都是各位段的低位 mask（如 `(1L << 26) - 1`），目的是把负数高位 1 截掉只留位段长度。
>
> 三个左移 OFFSET 把各位段移到正确位置：`X_OFFSET = 38`、`Z_OFFSET = 12`、`Y_OFFSET = 0`。
>
> Y 那行的 `<< 0` 是反编译器保留的 no-op 移位——它不会优化掉，因为编译器看不到 `Y_OFFSET` 是常量 0。"

15 秒读完。

## 0.6.11 速查表

| 看到 | 含义 / 怎么处理 |
|------|----------------|
| `p_122016_` | 反编译占位参数名，按上下文推 |
| `catch (IOException ioexception)` | "类型小写" 异常名，相当于 `e` |

| 长行 200 字符 | 不要主动换行 |
| 没有注释 | 反编译丢失，读类名 / 方法名 / 类型 |
| 单文件多类 | 用 IDE 的 "Find Symbol" 而非 "Find File" |

## 0.6.12 一句话总结

`p_NNNNNN_` 是反编译丢失的参数占位符，`ioexception` 是反编译生成的异常默认名，`LOGGER` 是 SLF4J 日志字段——这些都是噪声，看几次就习惯；`@Nullable` / `@OnlyIn` 等注解承载真实语义，必须留意；import 严格分组按 `com / it / java / javax / net / org`；vanilla 包路径下基本无注释，读懂靠类名 + 类型 + 调用图 + 外部资料；写自己的代码（`mcp.*` 包）用正常风格，但**不要**改 vanilla 路径下的 `p_NNNNNN_`，否则未来 patch 冲突。
