# 0.1 坐标系与单位

## 0.1.0 你将在本节学到什么

读完这一节，你应当能闭着眼睛回答：

1. 我说「`BlockPos(100, 64, 200)`」时，那是世界里哪一个具体的格子？（朝哪边算 +X、+Y、+Z？）
2. 这个格子属于哪一个 chunk？哪一个 section？哪一个 region？
3. 我用一个 64-bit 的 `long` 把它打包，每一位代表什么？反过来 unpack 是哪几个位运算？
4. 如果 X 是 -1，`-1 >> 4` 在 Java 里等于多少？在 C++ 里等于多少？为什么这件事对一个体素引擎来说性命攸关？
5. 实体（玩家、怪物、扔出去的物品）的坐标和方块的坐标是同一种类型吗？如果不是，怎么互转？

如果你完全没玩过 Minecraft，先读 0.1.1。如果你玩过几小时，可以从 0.1.2 开始。

## 0.1.1 世界长什么样：体素与方块

打开 Minecraft 进入一个世界，环顾四周，你会看到草地、石头、橡木原木、水、岩浆、沙子、各种花草和怪物。把镜头拉得足够近你会发现一件事：**所有这些「环境」都是一个个对齐到网格的 1 米立方体**。每一个立方体只有一种「身份」——这一格要么是草方块，要么是橡木原木，要么是空气，没有「半格沙子半格水」这种状态（先不管 waterlogged，后面 1.1 会专门讲）。

这种「世界由密集排列的小立方体单元构成」的建模方式，在图形学里叫**体素（voxel）**。Minecraft 的世界就是一个巨大的三维体素阵列。

每一个体素单元，在 Minecraft 的代码与玩家社区里都叫**方块（Block）**。所以记住第一对术语对照：

| 通用术语 | Minecraft 术语 |
|----------|----------------|
| voxel    | block          |
| voxel grid | the world / level |

不要被「方块」这个名字误导。一个「方块」既可以指代「方块这个**类型**」（比如「这是一个橡木原木方块」），也可以指代「世界里某一个具体位置的那一格」（比如「(100, 64, 200) 这个方块」）。这两层含义在代码里被严格区分，分别是 `Block` 类型与「位置 + BlockState」的组合，1.1 节会讲。

每个方块的**边长是 1 米**。这是 Mojang 早期定下的设定，几乎所有距离与速度都按这个尺度展开（玩家身高 1.8 米=1.8 格、走路速度约 4.3 米/秒、跳跃高度约 1.25 米）。

## 0.1.2 三轴朝向：Y up，+X 是东，+Z 是南

接下来你需要知道这个游戏的坐标轴朝向。这一段对从 UE5 / Unity 转过来的人特别重要，因为约定不一样。

**Minecraft 的轴向**：
- **+Y** 朝**上**（对天）。这一点和 UE5 的 +Z up 不同。
- **+X** 朝**东**。
- **+Z** 朝**南**。

也就是说在水平方向上，**北 = -Z、南 = +Z、东 = +X、西 = -X**。这是绝对约定，所有方向相关的字段（比如 `Direction` 枚举）都遵守。

请特别注意 **+Z 是南** 这一点。在不少图形学教材里 +Z 习惯朝向"屏幕外"或"前方"，但 Minecraft 里 +Z 是世界南方。如果你照搬 UE5 的本能记忆，会在 1.5 节读到 heightmap 翻转、3.7 节读到 biome 横向分布时陷入怪异的「为什么我画出来是镜像的」。

**Y 的范围（1.21）**：
- 主世界（Overworld）：`Y ∈ [-64, 320)`，总高度 384 格。
- 下界（The Nether）：`Y ∈ [0, 256)`，但游戏里默认的可活动空间是顶部基岩之下、坐标 0 到 128 之间。
- 末地（The End）：`Y ∈ [0, 256)`。

你会在源码里反复看到 `minBuildHeight` / `maxBuildHeight` / `minSectionY` / `getMinY()` 等访问器。它们都是动态值，由维度（dimension）决定。**永远不要硬编码 Y=0 是底**——那是 1.18 之前的约定，1.21 里不成立了。

**海平面**默认在 `Y=63`。早期版本是 64，1.18 改成了 63（因为地形顶端会更尖锐）。它由 `NoiseGeneratorSettings.seaLevel` 字段决定，跟随维度。

## 0.1.3 BlockPos：定位一个具体方块

世界里要表达「(100, 64, 200) 这一格」这件事，代码里用的类是 `BlockPos`。

**核心要点**：

```java
public class BlockPos extends Vec3i {
    public BlockPos(int x, int y, int z) { ... }
}
```

它继承自 `Vec3i`（整型三维向量），三轴都是 32 位有符号整数。

**为什么是整数？** 因为方块严格对齐到格子。世界里没有「(100.5, 64, 200) 这一格」这种说法。整数三元组就是方块在世界中的「身份证号」。

**坐标范围**：

水平方向 X / Z 的极限不是 `Integer.MAX_VALUE`，而是受 Mojang 主动限制：

```java
// BlockPos.java 行 52-60（本仓库 1.21.4）
public static final int PACKED_HORIZONTAL_LENGTH =
    1 + Mth.log2(Mth.smallestEncompassingPowerOfTwo(30000000));
public static final int PACKED_Y_LENGTH = 64 - 2 * PACKED_HORIZONTAL_LENGTH;
public static final int MAX_HORIZONTAL_COORDINATE =
    (1 << PACKED_HORIZONTAL_LENGTH) / 2 - 1;
```

把这段算清楚：
- `30_000_000` 是 Mojang 文档里说的「世界水平边界」数值（被称为"远古边界 / Far Lands border"，老玩家都熟）。
- `smallestEncompassingPowerOfTwo(30_000_000)` 取最小的 2 的幂能装下它，结果是 `2^25 = 33_554_432`。
- `log2(2^25) = 25`，所以 `PACKED_HORIZONTAL_LENGTH = 26`。
- `PACKED_Y_LENGTH = 64 - 2 * 26 = 12`。
- `MAX_HORIZONTAL_COORDINATE = (1<<26)/2 - 1 = 33_554_431`。

也就是说，**X / Z 实际可达 ±33,554,431**（约 ±3.3×10^7），但游戏会在 ±30,000,000 处放一道隐形墙拦住玩家。这是 26-bit 有符号整数的天然容纳范围。

**Y 用 12 位**，可表达的有符号范围是 `[-2048, 2047]`，远超主世界的 `[-64, 320)`，留了余量给自定义维度。

**为什么这些数字这么挑剔？** 因为 `BlockPos` 必须能够**无损打包到一个 64-bit 的 `long`**——`26 + 12 + 26 = 64`。后面 0.1.8 详讲。

**你可以从 BlockPos 上做什么操作**（节选）：

```java
// 偏移
BlockPos p2 = p.offset(1, 0, 0);    // +X
BlockPos p3 = p.above();             // +Y
BlockPos p4 = p.below(3);            // -Y by 3
BlockPos p5 = p.relative(Direction.NORTH); // -Z

// 与 long 互转
long packed = p.asLong();
BlockPos p6 = BlockPos.of(packed);

// 与浮点点互转
Vec3 center = p.getCenter();         // (x+0.5, y+0.5, z+0.5)
BlockPos contains = BlockPos.containing(3.7, 64.2, -1.1); // floor

// 求两点 min/max
BlockPos lo = BlockPos.min(a, b);
BlockPos hi = BlockPos.max(a, b);
```

**关键陷阱：BlockPos 是不可变（`@Immutable`）的**。`p.offset(1, 0, 0)` 不会改 `p`，会返回**新实例**。这是 Java 里的常见模式，但对来自 C++ 的人是「明明只想 +1，为啥每次都 new 对象，GC 怎么办？」的疑问源。

Mojang 的解法是 `BlockPos.MutableBlockPos`：

```java
BlockPos.MutableBlockPos cursor = new BlockPos.MutableBlockPos();
for (int dx = -1; dx <= 1; dx++) {
    for (int dy = -1; dy <= 1; dy++) {
        for (int dz = -1; dz <= 1; dz++) {
            cursor.set(x + dx, y + dy, z + dz);
            level.getBlockState(cursor); // 复用同一个对象
        }
    }
}
```

`MutableBlockPos` 继承 `BlockPos`，但暴露 `set(...)`。**所有需要在紧循环中按 BlockPos 查询世界的代码（区块生成、光照传播、AI 寻路）都用它**。读源码看到 `MutableBlockPos` 不要疑惑，记住它就是 GC 友好版的 BlockPos。

**C++ 移植映射**：在 C++ 里这个问题不存在——`BlockPos` 直接用栈上 `glm::ivec3` 即可。但要注意把 Java 里那些通过 `new BlockPos(...)` 把临时坐标传出函数的 API 一律改成传值或 `const&`，不要照抄出 `BlockPos*` 这种。

## 0.1.4 ChunkPos：把世界横向切成 16×16 的"列"

如果整个世界是一个连续的大体素阵列，加载 / 存储 / 网络同步会非常痛苦——你不可能把所有方块都装进内存，也不可能为单个方块的更改单独发一个网络包。

Minecraft 选择把世界横向切成 **16×16 一组的"列"**。每一列（在水平方向 16×16，在竖直方向贯穿整个世界高度 384 格）叫做一个 **chunk**（区块）。

```
        Z
        ↑
        │     +-------+-------+-------+
        │     │ chunk │ chunk │ chunk │
        │     │(0,1)  │(1,1)  │(2,1)  │
        │     │       │       │       │
        │     +-------+-------+-------+
        │     │ chunk │ chunk │ chunk │
        │     │(0,0)  │(1,0)  │(2,0)  │
        │     │       │       │       │
        │     +-------+-------+-------+
        │
        └──────────────────────────→ X
        
        每个格子代表 16×16 个 BlockPos（俯视）
```

横向 16 这个数字是 Notch 在 alpha 时期定下的，现在已经成为 Minecraft 协议的硬约定。它**不会变**，所以把 16 写死在代码里没问题。

**单位换算**：从一个 BlockPos 找到它所在的 ChunkPos，只需要把 X 和 Z **算术右移 4 位**（除以 16 的位运算版本）：

```java
int chunkX = blockX >> 4;
int chunkZ = blockZ >> 4;
```

反过来，从 ChunkPos 找到它在世界中的最小角 BlockPos：

```java
int minBlockX = chunkX << 4;     // = chunkX * 16
int minBlockZ = chunkZ << 4;
```

**`>> 4` 在负数下的行为非常关键**。Java 的 `>>` 是**算术右移**，它会把符号位复制下来。也就是 `-1 >> 4 == -1`（不是 0）、`-16 >> 4 == -1`、`-17 >> 4 == -2`。这正是我们想要的——块 X=-1 的方块属于 chunk X=-1，块 X=-17 的方块属于 chunk X=-2。

**陷阱**：在 C 与 C++ 里，对**有符号**整数右移**实现定义**的（implementation-defined）。GCC、Clang、MSVC 都按算术右移实现，但**标准并不保证**。如果你的 C++ 代码里直接 `int chunkX = blockX >> 4`，多数情况下能跑，但理论上是 UB（C++17 之前）/ implementation-defined（C++20 改为算术右移强制）。**安全做法**：

```cpp
// C++ 里推荐
inline int blockToChunk(int blockCoord) {
    // floor(blockCoord / 16) for any sign
    return (blockCoord >> 4);  // C++20 起为算术右移
    // 或显式：
    // return blockCoord >= 0 ? blockCoord / 16
    //                        : -((-blockCoord + 15) / 16);
}
```

**`& 15` 是另一个常用位运算**，它从 BlockPos 提取出 chunk 内的本地 X / Z（0..15）：

```java
int localX = blockX & 15;  // 等价于 ((blockX % 16) + 16) % 16
int localZ = blockZ & 15;
```

注意 `blockX % 16` 在 Java 和 C++ 里对负数都会返回负值（`-1 % 16 == -1`），所以**绝对不要**用 `%` 提取 chunk 内本地坐标，永远用 `& 15`。

**`ChunkPos` 数据结构**（本仓库 `ChunkPos.java`）：

```java
public class ChunkPos {
    public final int x;
    public final int z;
    
    public ChunkPos(int x, int z) { this.x = x; this.z = z; }
    public ChunkPos(BlockPos pos) {
        this.x = SectionPos.blockToSectionCoord(pos.getX());
        this.z = SectionPos.blockToSectionCoord(pos.getZ());
    }
    public ChunkPos(long packed) {
        this.x = (int)packed;
        this.z = (int)(packed >> 32);
    }
}
```

只有两个 int 字段，朴素得不能再朴素。**没有 Y**——chunk 是「列」，纵向贯通整个世界。要在 Y 上定位再切一刀的事情交给下面的 `SectionPos`。

`ChunkPos.asLong()` 也是简单的 32+32 拼接：

```java
public static long asLong(int x, int z) {
    return (long)x & 0xFFFFFFFFL | ((long)z & 0xFFFFFFFFL) << 32;
}
```

低 32 位放 X、高 32 位放 Z。这个布局和 `BlockPos.asLong()` **完全不同**——别混淆。

## 0.1.5 SectionPos：把每个 chunk 进一步切成 24 段

一个 chunk 在 1.21 里高 384 格，宽长各 16 格，体积 16×384×16 = 98,304 个方块。这对很多操作（光照传播、网络压缩、内存分配）来说颗粒度还是太大。

所以 chunk 内部又被竖直方向切成 **16×16×16 的小立方体**，叫做 **section**（段 / 子区块）。一个 chunk 在 1.21 主世界由 24 个 section 堆成（384 / 16 = 24）。

```
   +-------+   ← Y = 320 (top)
   │ sec23 │
   +-------+
   │ sec22 │
   +-------+
       ⋮
   +-------+
   │ sec 0 │
   +-------+   ← Y = -64 (bottom)
```

**SectionPos 的索引方式**：和 ChunkPos 一样靠 `>> 4`，只不过这次 Y 也参与：

```java
// SectionPos.java 行 76-78
public static int blockToSectionCoord(int blockCoord) {
    return blockCoord >> 4;
}
```

那么对于 BlockPos `(x, y, z)`：

```
sectionX = x >> 4   (= ChunkPos.x)
sectionY = y >> 4
sectionZ = z >> 4   (= ChunkPos.z)
```

**注意 sectionY 是负的**（对主世界 Y=-64 的最底段，sectionY = -4）。所以 1.21 里看到 `Y ∈ [-4, 19]` 这种 sectionY 范围不要慌——是负 Y 切出来的。

**段内本地坐标**用 `& 15`：

```java
// SectionPos.java 行 84-86
public static int sectionRelative(int blockCoord) {
    return blockCoord & 15;
}
```

**段内位置打包到 short**：因为段是 16³，本地 X / Y / Z 各占 4 位，加起来 12 位，正好能塞进一个 16-bit 的 `short`：

```java
// SectionPos.java 行 88-93
public static short sectionRelativePos(BlockPos pos) {
    int i = sectionRelative(pos.getX());
    int j = sectionRelative(pos.getY());
    int k = sectionRelative(pos.getZ());
    return (short)(i << 8 | k << 4 | j);
}
```

注意位段顺序是 **X 在最高 4 位、Z 在中间、Y 在最低 4 位**。这个顺序在网络包 `ClientboundSectionBlocksUpdatePacket`（段内批量方块更新）中复用，所以不能任意改。

**`SectionPos` 的 long 打包**（行 19-30）：

```
PACKED_X_LENGTH = 22
PACKED_Y_LENGTH = 20
PACKED_Z_LENGTH = 22
布局：高位到低位 → [22位X][22位Z][20位Y]   合计 64 位
```

注意它的**位数和 BlockPos 不同**！BlockPos 是 26+12+26，SectionPos 是 22+22+20。原因：因为 SectionPos 已经"除以 16"，它需要表达的范围只有 BlockPos 的 1/16，所以位数可以缩减；而 Y 维度反而稍宽（20 位有符号 = ±524288 段 = ±8M 格），给极端自定义维度留余地。

`SectionPos.x(long)` 用了一个看似魔法的位运算（行 131-141）：

```java
public static int x(long packed) { return (int)(packed << 0  >> 42); }
public static int y(long packed) { return (int)(packed << 44 >> 44); }
public static int z(long packed) { return (int)(packed << 22 >> 42); }
```

这是 **「先左移把目标位段顶到最高位，再算术右移让符号位扩展」** 的标准技巧。以 `x` 为例：
1. `packed << 0`：X 段已经在 long 的最高 22 位，左移 0 不动。
2. `>> 42`：把它整体算术右移 42 位（= 64 - 22），**符号位被复制到上面**，于是得到一个正确的有符号 22 位整数（提升为 64 位再 cast 成 int）。

`y` 同理：Y 段在最低 20 位，先左移 44 位顶到最高 20 位，再算术右移 44 位回来。

**这个技巧值得专门记住**——你会在 `BlockPos.getX/Y/Z`、`Heightmap`、`PalettedContainer` 等多处看到一模一样的模式。它的意义是：用纯位运算就能对任意位宽的有符号整数做正确的 sign extension，而不需要 if/else 分支或 branch-on-sign。

**C++ 移植时**：C++20 之后保证算术右移，可以照抄这个技巧。C++17 想稳妥，就用 `std::bit_cast` 或自己写：

```cpp
inline int signExtend(uint64_t value, int bits) {
    int64_t shifted = (int64_t)value << (64 - bits);
    return (int)(shifted >> (64 - bits));
}
```

## 0.1.6 RegionPos：32×32 个 chunk 一组

最后一个层级是 **region**（区域）。32×32 个 chunk = 1024 个 chunk = 一个 region。

这个层级**只在磁盘存档里出现**，运行时游戏逻辑几乎不直接接触。它对应硬盘上的 `r.<x>.<z>.mca` 文件（"mca" = "minecraft anvil"，是存储格式名）。

从 ChunkPos 推 RegionPos：

```java
int regionX = chunkX >> 5;   // /32 的位运算版本
int regionZ = chunkZ >> 5;
```

`ChunkPos.java` 中的对应字段：

```java
// ChunkPos.java 行 42-45
private static final int REGION_BITS = 5;
public  static final int REGION_SIZE = 32;
private static final int REGION_MASK = 31;
public  static final int REGION_MAX_INDEX = 31;
```

第 2 部分讨论存档格式时会再回到这里。本节你只需要记住：**region 是磁盘概念，不是逻辑概念**。

## 0.1.7 Vec3：实体的浮点坐标

到这里为止我们说的所有坐标都是整数——它们指向「某一格」。但游戏里还有不与方块对齐的东西：玩家的脚不一定刚好踩在格子边上、扔出去的箭可以处于格子之间、生物的眼睛在 Y 方向上比脚高 1.62 米。这些位置是浮点的。

存浮点位置的类是 `Vec3`（在 `net.minecraft.world.phys.Vec3`）：

```java
public class Vec3 {
    public final double x, y, z;
    ...
}
```

注意是 **double**，不是 float。Minecraft 整体走 double 精度，因为世界跨度可达 ±3×10^7 米，float 在远处会失去格点级精度。

**实体坐标的语义**：玩家、生物、扔出去的物品（统称 entity，**实体**）的位置是它**碰撞盒底面中心**的位置。也就是说一个站在 (10, 64, 10) 这一格上的玩家，它的 Vec3 大约是 (10.5, 64.0, 10.5)。Y 是脚的高度（不是腰、不是头），X / Z 是水平中心。

`Vec3` 与 `BlockPos` 互转：

```java
// Vec3 → BlockPos：向下取整
BlockPos p = BlockPos.containing(vec.x, vec.y, vec.z);

// BlockPos → Vec3：取格子中心
Vec3 center = pos.getCenter();          // (x+0.5, y+0.5, z+0.5)
Vec3 bottom = pos.getBottomCenter();    // (x+0.5, y,   z+0.5)
```

`getBottomCenter()` 在很多 spawn / 飞溅水花 / 粒子定位代码里出现，**它的 Y 是格子底面**，因为这些地方需要的是「方块上表面所在的 Y」（一个格子的"上表面"在 `y+1`，而下表面在 `y`）。注意区分 `getCenter` 与 `getBottomCenter`，混用会让粒子飘到方块半身高那种诡异位置。

**碰撞盒（AABB / `AABB.java`）** 是另一个浮点几何类型：玩家的碰撞盒大约 `0.6 × 1.8 × 0.6`，其中 0.6 是 X / Z 厚度，1.8 是高。它存储为 `(minX, minY, minZ, maxX, maxY, maxZ)` 六个 double。

## 0.1.8 long 打包：把三个整数塞进 64 位

前面在每个坐标系里都顺便提过它的 long 打包方案。这里集中比较一次，因为这是 Minecraft 性能与网络协议的关键设计点。

| 坐标 | X 位 | Y 位 | Z 位 | X 范围 | Y 范围 | Z 范围 |
|------|------|------|------|--------|--------|--------|
| `BlockPos`   | 26 | 12 | 26 | ±33,554,431 | ±2,047 | ±33,554,431 |
| `SectionPos` | 22 | 20 | 22 | ±2,097,151 | ±524,287 | ±2,097,151 |
| `ChunkPos`   | 32 | —  | 32 | ±2,147,483,647 | — | ±2,147,483,647 |

**为什么要打包？**

1. **`HashMap<Long, T>` 比 `HashMap<BlockPos, T>` 快得多**。Long 是值类型（auto-boxing 到 cache），BlockPos 是对象，需要算 hashCode + equals。Mojang 的所有大规模坐标 → 数据映射（光照、tick 队列、chunk 加载状态）都用 `Long2ObjectMap`（来自 fastutil）。
2. **网络传输紧凑**。一个 BlockPos 走线路 8 字节而不是 12 字节。
3. **`equals` 简单**：long 比较是单条 CPU 指令。

**`BlockPos.asLong` 的位段布局**（行 57-59 / 122-127）：

```
位 63 ............................................ 位 0
[ X(26位) ] [ Z(26位) ] [ Y(12位) ]
   高位                          低位
```

**特别注意**：是「X 在最高位、Z 在中间、Y 在最低位」。**Y 在最低**这一点反直觉（人类思维里 Y 最特殊），但工程上有原因——很多算法只关心水平位置（同一列内的方块共享 Y 上下），把 X / Z 放高位、Y 放低位的话，「同一列」的方块在 long 数值上接近，对 `Long2ObjectMap` 的 hash 局部性有利。

`BlockPos.asLong` 实现（行 122-127）：

```java
public static long asLong(int x, int y, int z) {
    long i = 0L;
    i |= ((long)x & PACKED_X_MASK) << X_OFFSET;   // X_OFFSET = 38
    i |= ((long)y & PACKED_Y_MASK) << 0;          // Y_OFFSET = 0
    return i | ((long)z & PACKED_Z_MASK) << Z_OFFSET; // Z_OFFSET = 12
}
```

`PACKED_X_MASK = (1L << 26) - 1` 这个 mask 的作用是把负数的高位 1 截掉，只留 26 位。这样负数 X 也能正确塞进位段而不污染 Y / Z。

**反过来 `BlockPos.getX(long)`**（行 78-80）：

```java
public static int getX(long packed) {
    return (int)(packed << 64 - X_OFFSET - PACKED_HORIZONTAL_LENGTH
                       >> 64 - PACKED_HORIZONTAL_LENGTH);
}
```

代入数：`X_OFFSET = 38`、`PACKED_HORIZONTAL_LENGTH = 26`，所以是 `packed << 0 >> 38`。
逻辑：左移把 X 段的最高位顶到 long 的位 63，然后算术右移 38 位（= 64-26）让符号位扩展到 32 位。最后 cast 为 int。

——这就是 0.1.5 提到的同一个 sign-extension 技巧，到处都是。**记住这个 idiom**。

**ChunkPos 的 long** 是平凡的拼接（无 Y）：低 32 位 X、高 32 位 Z。

**SectionPos 的 long** 22+22+20 布局，X 在最高位、Z 中间、Y 最低（与 BlockPos 同序）。

**C++ 移植**：直接照抄位运算即可。但请把这些 `asLong / getX / getY / getZ` 写成 `constexpr` 函数甚至 `consteval` —— 这是热路径，越早常量折叠越好。

## 0.1.9 完整换算速查表

```
BlockPos (x, y, z)
   │
   │  >>4 / >>4
   ▼
ChunkPos (x>>4, z>>4)              ←─── (x & 15, z & 15) 是 chunk 内本地 X/Z
   │
   │  >>5 / >>5
   ▼
RegionPos (x>>5, z>>5)             ←─── 仅磁盘相关

BlockPos (x, y, z)
   │
   │  >>4 / >>4 / >>4
   ▼
SectionPos (x>>4, y>>4, z>>4)      ←─── (x & 15, y & 15, z & 15) 是段内本地 X/Y/Z

Vec3 (dx, dy, dz)  ─── floor ───→  BlockPos
BlockPos (x, y, z) ─── +0.5 ───→  Vec3 (中心) 或 Vec3 (底面中心，Y 不+0.5)
```

**口诀**：
- 算坐标系层级：`>>4`（chunk / section）、`>>5`（region）。
- 算本地偏移：`& 15`（chunk / section 都是 16 一段），`& 31`（region）。
- **永远不要**用 `%` 算本地偏移——负数会给你错误结果。

## 0.1.10 Java 与 C++ 在右移与负数取模上的差异（重要）

这个小节单独拎出来强调。任何体素引擎在 C++ 里复刻时都必然撞上它。

**Java 的算术右移 `>>`**：
- 对有符号整数复制符号位。
- `-1 >> 4 == -1`。
- 行为是规范保证的。

**Java 的逻辑右移 `>>>`**：
- 不复制符号位，高位补 0。
- `-1 >>> 4 == 0x0FFFFFFF`。

**C++ 的右移 `>>`**：
- 对无符号整数总是逻辑右移（高位补 0）。
- 对有符号整数：
  - **C++17 之前**：implementation-defined（标准上 UB 边缘）。GCC / Clang / MSVC 都按算术右移实现，但理论上你不能假设。
  - **C++20 起**：标准明确为算术右移。

**Java 的取模 `%`**：
- `-1 % 16 == -1`。负数取模符号跟随被除数。

**C++ 的取模 `%`**：
- C++11 起也定义为符号跟随被除数：`-1 % 16 == -1`。

**结论**：在 C++20 项目里你可以放心 `>>`，行为与 Java 相同。但**绝对不要**用 `%` 提取「mod 16」之类的本地坐标——`& 15` 不仅快，还和 Java 一致。

写一段 C++ 模板把这些封装好，整个引擎就不用再担心：

```cpp
namespace mc::coord {

inline constexpr int blockToChunk(int v) noexcept {
    return v >> 4;            // C++20: arithmetic shift
}
inline constexpr int blockToSection(int v) noexcept {
    return v >> 4;
}
inline constexpr int chunkLocal(int v) noexcept {
    return v & 15;
}
inline constexpr int sectionLocal(int v) noexcept {
    return v & 15;
}
inline constexpr int chunkToRegion(int v) noexcept {
    return v >> 5;
}
inline constexpr int regionLocal(int v) noexcept {
    return v & 31;
}

inline constexpr int64_t packBlockPos(int x, int y, int z) noexcept {
    constexpr int64_t XMASK = (1LL << 26) - 1;
    constexpr int64_t YMASK = (1LL << 12) - 1;
    constexpr int64_t ZMASK = (1LL << 26) - 1;
    int64_t r = 0;
    r |= (int64_t(x) & XMASK) << 38;
    r |= (int64_t(z) & ZMASK) << 12;
    r |= (int64_t(y) & YMASK);
    return r;
}

inline constexpr int unpackBlockPosX(int64_t p) noexcept {
    return int(p << 0 >> 38);          // sign-extend 26-bit
}
inline constexpr int unpackBlockPosY(int64_t p) noexcept {
    return int(p << 52 >> 52);          // sign-extend 12-bit
}
inline constexpr int unpackBlockPosZ(int64_t p) noexcept {
    return int(p << 26 >> 38);          // sign-extend 26-bit
}

} // namespace mc::coord
```

把这个头文件作为你 C++ 移植的第一块砖。所有后续模块都会用到它。

## 0.1.12 一句话总结
