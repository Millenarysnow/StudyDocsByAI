# 0.4 Registry 与 ResourceLocation 命名系统

## 0.4.0 你将在本节学到什么

读完这一节你应当能闭着眼睛回答：

1. `minecraft:oak_log` 这种格式叫什么？为什么 Mojang 用字符串而不是 enum 索引？
2. `Block`、`Item`、`Biome`、`EntityType`、`Feature` 这些"全局唯一可枚举资源"在代码里怎么注册、怎么查询？
3. 为什么我看到一个字段是 `Holder<Biome>` 而不是 `Biome` 直接？`Holder` 多了一层间接，价值在哪？
4. `ResourceKey<Biome>` 和 `ResourceLocation` 看起来都是"全局唯一字符串"，区别在哪？
5. 联机时客户端如何知道服务器自定义的 biome / item / 维度的 ID？这套 Registry 机制在网络层是怎么同步的？
6. 我在 C++ 里要复现"动态注册 + 字符串 ID + 数据驱动"这一切，最简洁的设计是什么？

## 0.4.1 一切的起点：为什么不能用 enum

如果你来自 UE5 / 自研引擎，可能会本能想到这种设计：

```cpp
enum class BlockType : uint16_t {
    AIR = 0, STONE = 1, GRASS_BLOCK = 2, ...
};
```

但 Minecraft **不能这么做**，原因有三：

1. **Mod 与 datapack 注册新方块**：Forge mod 可以加 `mymod:fancy_log`、datapack 可以加 `examplepack:my_biome`。enum 的成员必须编译期确定，无法支持。
2. **跨版本兼容**：1.21 删掉了 1.20 的某个方块、加了新的方块——如果 ID 用 enum 整数，旧存档加载到新版会错位。
3. **网络协议**：客户端连服务端时，服务端可能装了 mod / datapack 客户端没有，或者反过来。整数 ID 表里两边对不上号。

Mojang 的解法：**所有"全局唯一可枚举资源"都用字符串作为身份标识，运行时再动态分配整数 ID 用于压缩存储和网络传输**。

字符串身份这一对（namespace + path）就叫 `ResourceLocation`。装这种字符串到资源对象的映射的容器叫 `Registry`。这就是这一节的全部内容。

## 0.4.2 ResourceLocation：`namespace:path`

打开 `net.minecraft.resources.ResourceLocation`，第 25-43 行：

```java
public final class ResourceLocation implements Comparable<ResourceLocation> {
    public static final char NAMESPACE_SEPARATOR = ':';
    public static final String DEFAULT_NAMESPACE = "minecraft";
    public static final String REALMS_NAMESPACE = "realms";

    private final String namespace;
    private final String path;

    private ResourceLocation(String namespace, String path) { ... }
}
```

**两段字符串**，用冒号分隔。

- **namespace**：资源所属的"命名空间"。Mojang 自己的全部用 `minecraft`；mod / datapack 用自己的 ID（`forge`、`examplemod`、`gregtech`）。
- **path**：在该命名空间内的路径。可以含 `/`（视为目录层级，对应 datapack 的子目录）。

**典型例子**：

| ResourceLocation | 指向什么 |
|------------------|---------|
| `minecraft:oak_log` | 橡木原木方块（Mojang 自带） |
| `minecraft:overworld` | 主世界维度 |
| `minecraft:plains` | 平原 biome |
| `minecraft:village/plains/town_centers/plains_fountain_01` | datapack 里的一个结构模板 |
| `examplemod:fancy_log` | 某个 mod 的方块 |
| `realms:test_pack` | Realms 服务器内置资源包 |

**字符规则**（行 25-200 之间分布）：

- namespace：仅小写字母 / 数字 / `_` / `-` / `.`。
- path：仅小写字母 / 数字 / `_` / `-` / `.` / `/`。
- 长度有上限（通常 32767 字符以下）。

**关键 API**：

```java
ResourceLocation.parse("minecraft:oak_log");                       // 标准
ResourceLocation.parse("oak_log");                                  // 等价于 minecraft:oak_log
ResourceLocation.withDefaultNamespace("oak_log");                   // 显式说"用 minecraft"
ResourceLocation.fromNamespaceAndPath("examplemod", "fancy_log");   // 显式指定
ResourceLocation.tryParse(input);                                   // 失败返回 null（不抛）
ResourceLocation.tryBuild(ns, path);                                // 失败返回 null
```

**省略 namespace 默认是 `minecraft`** —— 你看到任何一段代码用 `ResourceLocation.withDefaultNamespace("xxx")` 或者 `ResourceLocation.parse("yyy")`（没有冒号），它们都自动套上 `minecraft:`。

**`equals` / `hashCode` 由 namespace + path 一起决定**。两个同名同路径的 `ResourceLocation` 是相等的（即使是不同对象）。

**Codec 已经内置**（行 26-28）：

```java
public static final Codec<ResourceLocation> CODEC = ...;
public static final StreamCodec<ByteBuf, ResourceLocation> STREAM_CODEC = ...;
```

也就是 `ResourceLocation` 本身已经知道怎么把自己写进 NBT / JSON / 网络包，不用你手动序列化。

## 0.4.3 Registry：字符串到对象的双向映射

`Registry` 是装 `ResourceLocation → T` 的双向 map（同时还能拿到整数 ID）。

打开 `net.minecraft.core.Registry`：

```java
public interface Registry<T> extends Keyable, HolderLookup.RegistryLookup<T>, IdMap<T> {
    @Override
    ResourceKey<? extends Registry<T>> key();

    @Nullable ResourceLocation getKey(T value);
    Optional<T> getOptional(ResourceLocation name);
    Optional<Holder.Reference<T>> get(ResourceLocation name);
    int getId(T value);
    @Nullable T byId(int id);
    Set<ResourceLocation> keySet();
    // ...
}
```

它同时支持三种 lookup：

1. **按 ResourceLocation 查**：稳定的字符串 ID。
2. **按整数 ID 查**：高性能（数组下标）。
3. **按值反查 ResourceLocation / 整数 ID**：序列化时用。

整数 ID 是注册时**按顺序分配**的——所以**不要假设它跨进程稳定**。Mojang 的 vanilla 注册顺序在每个版本里固定，但加一个 mod / datapack 就可能让所有 ID 偏移。整数 ID 仅用于：

- 当前进程内部的紧凑存储（chunk palette 内是 int，不是字符串）。
- 当前 session 的网络传输（连接建立时同步一份 ID 表）。

**永远不要**把整数 ID 写入存档磁盘或硬编码到代码里——存档里写的永远是 `ResourceLocation` 字符串，加载时重新分配 ID。

## 0.4.4 BuiltInRegistries：看一眼内置注册表清单

`net.minecraft.core.registries.BuiltInRegistries` 持有所有 vanilla 注册表的全局静态引用。打开它（第 80-150 行）你会看到一长串：

```java
public static final Registry<Block> BLOCK = ...;
public static final Registry<Item> ITEM = ...;
public static final Registry<Fluid> FLUID = ...;
public static final Registry<EntityType<?>> ENTITY_TYPE = ...;
public static final Registry<BlockEntityType<?>> BLOCK_ENTITY_TYPE = ...;
public static final Registry<Feature<?>> FEATURE = ...;
public static final Registry<DensityFunctionType<?>> DENSITY_FUNCTION_TYPE = ...;
public static final Registry<SoundEvent> SOUND_EVENT = ...;
public static final Registry<MobEffect> MOB_EFFECT = ...;
public static final Registry<Potion> POTION = ...;
public static final Registry<Enchantment> ENCHANTMENT = ...;
public static final Registry<ParticleType<?>> PARTICLE_TYPE = ...;
public static final Registry<MenuType<?>> MENU = ...;
public static final Registry<RecipeType<?>> RECIPE_TYPE = ...;
public static final Registry<RecipeSerializer<?>> RECIPE_SERIALIZER = ...;
public static final Registry<VillagerProfession> VILLAGER_PROFESSION = ...;
// ... 共约 80 个
```

这是**世界上所有"可被 ResourceLocation 引用的资源类型"的清单**。每个都是一个 `Registry<T>`，里面装该类型的所有 ResourceLocation → T 映射。

**两类注册表**：

| 类别 | 注册时机 | 数据来源 |
|------|---------|---------|
| **静态注册** | 启动时一次性注册，运行时不变 | hard-coded 在 Java 中（如 `Blocks` 类的静态字段） |
| **动态注册** | 运行时从 datapack 加载 | JSON 文件，每次世界打开重新加载 |

**静态注册** 例子：`Block`、`Item`、`EntityType`、`Feature`、`DensityFunctionType` 等。这些是"代码模板"，不能在运行时增删（mod 例外，mod 在加载时阶段也算"启动时"）。

**动态注册** 例子：`Biome`、`DimensionType`、`ConfiguredFeature`、`PlacedFeature`、`Structure`、`StructureSet`、`NoiseGeneratorSettings`、`DensityFunction`（注意是具体函数实例，不是 type）。这些是"配方"，可以纯靠 datapack 配置出来，不用写一行 Java。

**重要的一点**：1.18 之后 worldgen 的几乎所有概念都是动态注册——你完全可以在不写 Java 的前提下，用一个 datapack 把整个 worldgen 改成另一个游戏（"Lost Cities" 那种)。后面 Module 3 会大量利用这一点。

## 0.4.5 ResourceKey：带类型的 ResourceLocation

`ResourceLocation` 是纯字符串身份，但它**不知道自己指向哪个 Registry**。`minecraft:plains` 既可以是一个 biome，也可以是一个 advancement，也可以是一个 datapack-defined recipe。光凭字符串无法区分。

`ResourceKey<T>` 解决这个问题：

```java
// 简化
public final class ResourceKey<T> {
    private final ResourceLocation registryName;  // 哪个 registry，比如 "minecraft:worldgen/biome"
    private final ResourceLocation location;      // 在该 registry 内的 id，比如 "minecraft:plains"
}
```

它由两个 ResourceLocation 组成：一个指向 registry 自己，一个指向 registry 内的某项。

**典型用法**：

```java
ResourceKey<Biome> PLAINS_KEY = ResourceKey.create(
    Registries.BIOME,                          // 这是个 ResourceKey<Registry<Biome>>
    ResourceLocation.withDefaultNamespace("plains")
);

// 然后在 datapack 里用
biomeRegistry.getOrThrow(PLAINS_KEY);
```

`Registries`（`net.minecraft.core.registries.Registries`）持有所有 **registry 的 key**（即所有"哪些 registry 存在"）。`BuiltInRegistries` 持有所有 **registry 的实例**（即"那些 registry 的具体内容"）。

Mojang 的命名约定：**`Registries.BIOME` = `ResourceKey<Registry<Biome>>`**（"什么 registry" 的 key），**`BuiltInRegistries.BLOCK` = `Registry<Block>`**（registry 的实例）。

**为什么需要 ResourceKey 而不是直接用 ResourceLocation？** 因为 Mojang 的 Codec 系统（0.5 节）需要"类型化的引用"。`Codec<ResourceKey<Biome>>` 知道该序列化成什么样、加载时去哪个 registry 找；`Codec<ResourceLocation>` 不知道。

## 0.4.6 Holder：到注册项的"间接引用"

到这里你应该问：既然有了 `Registry.get(key)`，为什么源码里到处是 `Holder<Biome>` 而不是直接 `Biome`？

打开 `net.minecraft.core.Holder`：

```java
public interface Holder<T> {
    T value();
    boolean isBound();
    boolean is(ResourceLocation rl);
    boolean is(ResourceKey<T> key);
    boolean is(Predicate<ResourceKey<T>> p);
    boolean is(TagKey<T> tag);
    Stream<TagKey<T>> tags();
    Either<ResourceKey<T>, T> unwrap();
    Optional<ResourceKey<T>> unwrapKey();
    Holder.Kind kind();
    // ...
}
```

`Holder<T>` 是"对一个**有可能注册过、也可能没注册的** T 实例的引用"。它是**对象 + 元数据**的包装：

- 知道自己**值**是什么（`value()`）。
- 知道自己**身份 key**是什么（`unwrapKey()`）—— 如果是动态注册的话。
- 知道自己**属于哪些 tag**（`tags()`、`is(TagKey)`）—— 这是 Minecraft 的 tag 系统，下面 0.4.7 讲。

**两种实现 (`Holder.Kind`)**：

1. **`Holder.Direct<T>`** —— 直接持有一个 T 实例，**没有** registry key。给临时构造、不需要持久化的对象用。
2. **`Holder.Reference<T>`** —— 持有 `(ResourceKey<T>, T)`，是对 registry 内某项的引用。

为什么不直接 `T`？三个理由：

1. **延迟绑定**：在加载 datapack 时，可能先看到 "我引用 minecraft:plains" 这个声明，但 `plains` 自己还没加载完。`Holder.Reference` 可以先创建一个 unbound（`isBound() == false`）的 reference，等 plains 加载好后再 bind 上。这是 datapack 自洽校验的关键。
2. **元数据查询**：你拿到一个 `Holder<Biome>`，可以直接 `holder.is(BiomeTags.IS_FOREST)` 判断是不是森林系生物群系，而不需要先解 ResourceKey 再去 tag 注册表里查。
3. **零拷贝同步**：Holder 在 NoiseChunk / SectionStorage / ChunkSerializer 里非常常见——它让代码可以**操作引用而不是值副本**，减少分配。

**对应规则**：

- 写代码时，**永远不要**接受 `Biome biome` 参数；**总是** `Holder<Biome> biome`。这是 Mojang 1.18+ 的强制约定。
- 解出值用 `holder.value()`。
- 解出身份用 `holder.unwrapKey().orElse(null)`（可能是 null，因为 Direct holder 没有 key）。

## 0.4.7 TagKey：一组对象的标签

最后一个名字：`TagKey<T>`。

很多场景需要"一类东西"而不是"一个东西"。比如生物群系要分组（"森林系"、"沙漠系"），物品要分组（"原木"、"羊毛"），方块要分组（"基岩矿替代物"、"村庄路径方块"）。

`TagKey<T>` 就是这种"组"的身份：

```java
TagKey<Biome> IS_FOREST = TagKey.create(
    Registries.BIOME,
    ResourceLocation.withDefaultNamespace("is_forest")
);
```

它和 `ResourceKey<T>` 长得几乎一样（都是 registry id + path），但语义不同：

- `ResourceKey<Biome>` 指向 **一个具体的** biome 实例。
- `TagKey<Biome>` 指向 **一组** biome 实例的集合。

具体哪些 biome 属于这个 tag，由 datapack 文件决定：`data/<ns>/tags/worldgen/biome/<tag>.json`：

```json
{
    "values": [
        "minecraft:forest",
        "minecraft:birch_forest",
        "minecraft:dark_forest",
        "#minecraft:is_taiga"     // # 前缀 = 包含另一个 tag
    ]
}
```

**用 tag 比用具体 ResourceKey 列表的优势**：mod / datapack 可以**追加**到 tag 里（`"replace": false`）。比如某个 mod 加了一种新森林 biome，把自己加到 `#minecraft:is_forest` 里，所有"对森林系起作用"的代码（比如树木生成、生物刷怪）自动接纳它，**不需要改原代码**。

**调用方式**：

```java
Holder<Biome> biome = ...;
if (biome.is(BiomeTags.IS_FOREST)) {
    // ...
}

// 或在循环里枚举 tag 的所有项
HolderSet<Biome> forests = registry.getOrThrow(BiomeTags.IS_FOREST);
for (Holder<Biome> b : forests) { ... }
```

`HolderSet<T>` 就是 `Set<Holder<T>>` 的语义包装。源码里它经常以 `HolderSet.Named` 子类出现，那是 tag 解析后的延迟实例。

## 0.4.8 RegistryAccess 与维度对应的 registry 实例

`Registry` 实例并不全是"全局唯一"的——动态注册表是**每个世界各一份**。一个存档里你定义了一个自定义 biome，另一个存档可能没有。

所以 1.18+ 引入了 `RegistryAccess`：

```java
public interface RegistryAccess extends HolderLookup.Provider {
    <T> Optional<Registry<T>> registry(ResourceKey<? extends Registry<T>> key);
    <T> Registry<T> registryOrThrow(ResourceKey<? extends Registry<T>> key);
    // ...
}
```

每个 `Level`（每个维度）持有一个 `RegistryAccess` 引用。要访问 biome：

```java
Registry<Biome> biomeRegistry = level.registryAccess().registryOrThrow(Registries.BIOME);
Holder.Reference<Biome> plains = biomeRegistry.getHolderOrThrow(Biomes.PLAINS);
```

这看起来啰嗦，但它保证了**世界隔离**：A 世界的 datapack 不会污染 B 世界。

`BuiltInRegistries.X` 用于**静态注册**，永远全局唯一；`level.registryAccess().registryOrThrow(Registries.X)` 用于**动态注册**，每世界一份。

## 0.4.9 网络层：客户端怎么得知服务端的 registry 内容

当客户端连服务端，两边可能装了不同的 mod / datapack。整数 ID 表必须协商一致，否则方块、实体、物品都会错位。

**1.20.2 之前的做法**：握手时服务端发一份完整的"id 表"，客户端按服务端的顺序覆盖自己的本地表。

**1.20.2+ 的做法**（CONFIGURATION 阶段引入）：握手分两阶段——LOGIN 阶段做鉴权和加密，**CONFIGURATION** 阶段做"配置同步"，包括：

1. 服务端发 `ClientboundRegistryDataPacket` 把自己所有动态注册表（biome / dimension / damage_type 等）发给客户端。
2. 服务端发 `ClientboundUpdateTagsPacket` 把所有 tag 内容发给客户端。
3. 服务端发 `ClientboundFinishConfigurationPacket` → 进入 PLAY 阶段。

到 PLAY 阶段时，客户端的 `RegistryAccess` 已经被服务端的版本覆盖了。这就是为什么单机和联机都能用同一套 worldgen 代码——客户端在加载世界时也是从这套同步过来的 registry 读 biome 配方。

后面 Module 7 会展开网络细节。这里先建立这个"同步是握手时一次性完成的"概念。

## 0.4.10 一个完整生命周期：一个方块从注册到被玩家手持

```
启动期（一次性）：
1. Bootstrap.bootStrap() 调用 Blocks.<clinit>，
   依次创建 OAK_LOG = Registry.register(BLOCK, "oak_log", new RotatedPillarBlock(...))
2. Registry 内部分配整数 ID（按注册顺序）
3. Block.OAK_LOG 现在可全局访问

世界加载期（每次）：
4. RegistryAccess 加载动态注册表（biome / dimension 等），从 datapack JSON 解析
5. 每个 BlockState 的 Holder<Block> 重新解析（如果需要）

玩家放置一个橡木原木：
6. ItemStack 内部记的是 Item.OAK_LOG 引用 + 数据组件
7. 客户端发 ServerboundUseItemOnPacket
8. 服务端 setBlock(pos, BLOCKS.OAK_LOG.defaultBlockState().with(AXIS, Direction.Y))
9. 这个 BlockState 在 ChunkSection palette 里被分配一个 chunk-local 整数 ID
10. ChunkSerializer 写存档时，palette 用 ResourceLocation "minecraft:oak_log" 存盘
11. 网络包同步时，用全局动态分配的整数 ID（连接 session 内有效）
```

注意第 10 / 11 步分别用了**两套不同的整数 ID**：

- **palette local id**：chunk section 内部的"调色盘下标"，仅本 section 有效。
- **global session id**：当前 session 内的"全局方块 ID"，握手时同步。

存档里**两者都不写**，写的永远是 ResourceLocation 字符串。这保证了存档的版本和实例兼容性。

## 0.4.11 C++ 移植设计

把以上拿到 C++ 引擎里。最小可行设计：

```cpp
// 字符串 ID
struct ResourceLocation {
    std::string ns;
    std::string path;
    bool operator==(...) const;
    auto hash() const { return std::hash<std::string>{}(ns + ":" + path); }
    static ResourceLocation parse(std::string_view s);
};

// 类型化 key
template<typename T>
struct ResourceKey {
    ResourceLocation registryId;   // 哪个 registry
    ResourceLocation entryId;      // 该 registry 内的项
};

// Registry：动态分配 int id
template<typename T>
class Registry {
public:
    int register_(ResourceLocation id, std::unique_ptr<T> obj) {
        int newId = int(byId_.size());
        T* ptr = obj.get();
        byId_.push_back(std::move(obj));
        byName_[id] = newId;
        ids_[ptr] = newId;
        return newId;
    }
    T* get(ResourceLocation id) const;
    T* byId(int id) const;
    int idOf(T* obj) const;
private:
    std::vector<std::unique_ptr<T>> byId_;
    std::unordered_map<ResourceLocation, int> byName_;
    std::unordered_map<T*, int> ids_;
};

// Holder：引用 + 元数据
template<typename T>
class Holder {
public:
    T* value() const;
    std::optional<ResourceKey<T>> key() const;
    bool isInTag(const TagKey<T>& tag) const;
private:
    enum class Kind { Direct, Reference };
    Kind kind_;
    T* ptr_;
    ResourceKey<T> key_;            // 仅 Reference 有效
    std::vector<TagKey<T>> tags_;   // 仅 Reference 有效
};

// 全局静态注册表入口
namespace BuiltInRegistries {
    extern Registry<Block> BLOCK;
    extern Registry<Item> ITEM;
    extern Registry<Biome> BIOME;
    // ...
}

// 每世界一份动态注册表
class RegistryAccess {
public:
    template<typename T> Registry<T>* registry(const ResourceKey<Registry<T>>& key);
};
```

**实现要点**：

1. `ResourceLocation` 用 `std::string` 还是用 interned `int`？**用 interned**（全局 string pool 返回 `int`），所有 hash / equals 比较都退化为整数比较，性能立刻 5-10×。Mojang 在 Java 用 `String.intern()` 也是这个目的。
2. 整数 ID 分配的顺序必须**确定**——所有客户端 / 服务端要保持完全一致的注册顺序，否则握手后还是错位。最简单的做法：让所有 register 调用从一个 lambda 列表里按顺序执行。
3. 网络握手时同步整个 ID 表 = 直接 dump `byName_` map 到包里。客户端收到后清掉自己的、按服务端顺序重建。

后面 Module 1 会用这个 `Registry<Block>` + `BlockState` 配合 `PalettedContainer`，那时这些类型就具体化了。

## 0.4.12 一句话总结

每一个"全局可枚举资源"都有一个 `ResourceLocation`（"minecraft:oak_log"）作为字符串身份；这些资源装在 `Registry<T>` 里同时支持字符串 / 整数 ID 双向查询；`Holder<T>` 是对 registry 项的"延迟绑定 + 携元数据"引用，源码里几乎一切对资源的字段都是 `Holder<T>` 而非裸 `T`；`ResourceKey<T>` 是类型化的字符串 key（registry-id + entry-id），`TagKey<T>` 是一组项的标签 key——这两套搭配起来支持 datapack 完全数据驱动地拼装 worldgen 而不写一行 Java。
