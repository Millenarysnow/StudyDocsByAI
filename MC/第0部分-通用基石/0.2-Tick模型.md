## 0.2.1 最关键的一对常量：20 TPS / 50 ms

打开 `SharedConstants.java`，第 129-130 行：

```java
// SharedConstants.java
public static final int TICKS_PER_SECOND = 20;
public static final int MILLIS_PER_TICK = 50;
```

这是 Minecraft **整个游戏世界的时间基准**。一秒钟 20 个 tick，一个 tick 50 毫秒。所有时间长度（魔药持续 60 秒 = 1200 tick、白天 10 分钟 = 12000 tick、铁傀儡冷却 30 秒 = 600 tick）都按这个基准换算。这两个常量被硬编码到协议、存档、命令系统的几乎所有地方，**实质上不可改动**——你看到任何 mod 想做"60 TPS"都是在改感官速度，不是真改这个常量。

需要纳秒精度时用 `TimeUtil.java`：

```java
// TimeUtil.java 第 7-9 行
public static final long NANOSECONDS_PER_SECOND       = TimeUnit.SECONDS.toNanos(1L);       // 1_000_000_000
public static final long NANOSECONDS_PER_MILLISECOND  = TimeUnit.MILLISECONDS.toNanos(1L);  // 1_000_000
public static final long MILLISECONDS_PER_SECOND      = TimeUnit.SECONDS.toMillis(1L);      // 1_000
```

还有一个常用的辅助方法（行 13-15）：

```java
public static UniformInt rangeOfSeconds(int min, int max) {
    return UniformInt.of(min * 20, max * 20);
}
```

这是给 datapack 写「3-7 秒后再触发」用的——它把秒乘 20 再返回 tick 区间。**记住"乘 20 = 秒转 tick"是 MC 代码里满天飞的隐式转换**。

## 0.2.2 主循环长什么样：MinecraftServer.runServer

服务端启动后会创建一个名为「Server thread」的 Java Thread（见 `MinecraftServer.java` 第 278 行的 `new Thread(... , "Server thread")`），这个线程的生命就是不停跑下面这个循环。我们简化成核心骨架：

```java
// MinecraftServer.java 第 672-730 行（极简化）
protected void runServer() {
    this.nextTickTimeNanos = Util.getNanos();
    while (this.running) {
        long perTick;
        if (this.tickRateManager.isSprinting()) {
            // /tick sprint 模式：一刻不停连续 tick，用于命令调试
            perTick = 0;
            this.nextTickTimeNanos = Util.getNanos();
        } else {
            perTick = this.tickRateManager.nanosecondsPerTick();   // 默认 = 50_000_000
            long lag = Util.getNanos() - this.nextTickTimeNanos;
            if (lag > OVERLOADED_THRESHOLD_NANOS + 20L * perTick) {
                long skip = lag / perTick;
                LOGGER.warn("Can't keep up! ...");
                this.nextTickTimeNanos += skip * perTick;
            }
        }

        this.nextTickTimeNanos += perTick;
        this.tickServer(this::haveTime);

        long sleep = this.nextTickTimeNanos - Util.getNanos();
        if (sleep > 0) {
            LockSupport.parkNanos(sleep);   // 睡到下一个 tick 边界
        }
    }
}
```

**关键点**：
1. `nextTickTimeNanos` 是「**下一个 tick 应该开始的绝对纳秒时间**」（线程主时钟）。
2. 每跑完一个 tick，`nextTickTimeNanos += 50_000_000`（50 ms）。
3. 如果一个 tick 超时（实际开销 > 50 ms），下一个 tick 不会延迟、而是**立刻**开始；超过 `OVERLOADED_THRESHOLD_NANOS`（默认 20 秒）会打印著名的 "Can't keep up! Is the server overloaded?" 警告并跳过 N 个 tick 让时基重新对齐。
4. `parkNanos` 是 Java 的精确睡眠，对应 OS 的 nanosleep。

**这是一个「软实时」循环**：理想情况 50 ms 一拍，但允许丢帧。它和 Unity / UE5 的固定时间步（fixed timestep）哲学一致，但具体实现选择了"绝对时间表"（next tick is at T+50ms）而不是"相对累计"（accumulate dt > 50ms）。绝对时间表的好处：长跑下来不会漂移。

## 0.2.3 tickServer：tick 一次到底干了什么

`runServer` 每 50 ms 调一次 `tickServer`。`tickServer`（`MinecraftServer.java` 第 923 行起）是真正的「这一拍要做的所有事」：

```java
// 极简化骨架
public void tickServer(BooleanSupplier haveTime) {
    this.tickRateManager.tick();          // 自身节奏调控
    this.tickChildren(haveTime);          // 推进所有 ServerLevel
    this.connection.tick();                // 处理网络收发（Netty 不是这里 IO，但事件分发在这）
    this.playerList.tick();
    this.functionManager.tick();           // datapack /function 队列
    // ... GameTestServer / scheduledFunctions / ...
}
```

`tickChildren` 内部依次为每一个加载的 `ServerLevel`（每个维度一个）调用 `serverlevel.tick(haveTime)`。

## 0.2.4 ServerLevel.tick：单个维度的一拍

打开 `ServerLevel.java` 第 318 行起。这是真正"游戏世界推进 50 ms"的地方。骨架（按代码顺序）：

```java
public void tick(BooleanSupplier haveTime) {
    boolean normal = tickRateManager.runsNormally();

    if (normal) {
        this.getWorldBorder().tick();      // 1. 世界边界缓动
        this.advanceWeatherCycle();        // 2. 雷雨/降雪计时器
    }

    handlePlayerSleeping();                 // 3. 全员睡觉？跳过夜晚

    this.updateSkyBrightness();             // 4. 天光重算
    if (normal) tickTime();                 // 5. gametime / daytime ++

    if (!isDebug() && normal) {             // 6. 计划 tick
        this.blockTicks.tick(gameTime, 65536, this::tickBlock);
        this.fluidTicks.tick(gameTime, 65536, this::tickFluid);
    }

    if (normal) this.raids.tick();          // 7. 袭击事件

    this.getChunkSource().tick(...);        // 8. 区块加载/卸载/random tick
    if (normal) this.runBlockEvents();      // 9. 方块事件队列（活塞推动等）

    /* 玩家或强制加载 chunk 不为空才推进实体 */
    if (haveActiveContent()) {
        if (this.dragonFight != null && normal) this.dragonFight.tick();
        for (Entity e : this.entityTickList) {
            if (alive && inRange) this.guardEntityTick(this::tickNonPassenger, e);
        }
        this.tickBlockEntities();           // 10. 方块实体 tick
    }

    this.entityManager.tick();              // 11. 加载/卸载实体到/从 chunk
}
```

**这个顺序非常重要**，1.21 的源码里就是这个顺序，每一项之间不能换。后面 Module 4 / 5 / 6 都会回头引用这一段，标注它们各自挂在哪一步上。先大致记住：

- **scheduled tick（计划 tick）** 在第 6 步执行：`this.blockTicks.tick(...)` 和 `this.fluidTicks.tick(...)`。
- **random tick（随机 tick）** 隐藏在第 8 步 `chunkSource.tick(...)` 内部，每个被加载的区块每 tick 都被遍历一遍。
- **block event（方块事件）** 在第 9 步处理：活塞、唱片机这种"延迟一 tick 再生效"的副作用。
- **neighbor update（邻居更新）** 不在 `ServerLevel.tick` 主循环里，它是 **同步触发**——任何 `level.setBlock(...)` 调用立刻引发邻居 6 个方块的 `neighborChanged`，回栈到当前调用者继续执行。

## 0.2.5 第 6 步详解：scheduled tick

`blockTicks` 是一个 `ServerTickList<Block>` 类型的字段，里面装的是一堆 `(BlockPos, Block, triggerTick, priority)` 四元组。游戏运行过程中，方块自身或外部代码会调用：

```java
level.scheduleTick(pos, block, delayInTicks);
level.scheduleTick(pos, block, delayInTicks, TickPriority.NORMAL);
```

把"我希望在 N tick 后再处理这个方块"登记进去。典型用例：
- 中继器 / 比较器：信号变化触发后延迟 1-4 tick 才更新输出。
- 流体：每次扩散后排下一次扩散的 tick。
- 火：每次燃烧后排下一次燃烧的 tick。

到了真正的当前 tick，`this.blockTicks.tick(gameTime, 65536, this::tickBlock)` 会把所有 `triggerTick <= gameTime` 的项弹出来执行。第二个参数 `65536` 是**单 tick 处理上限**——超过就推到下一 tick。

**为什么有上限**：水流爆炸、TNT 大堆爆炸时一个 tick 内可能产生上百万个 scheduled tick，没有上限的话会卡爆。Mojang 早期版本没限上限，导致著名的"水位炸弹"卡服。

**fluidTicks** 是另一个独立的同类型表，专门处理 `Fluid` 类型，逻辑等价。

## 0.2.6 第 8 步详解：random tick

打开 `ServerLevel.java` 第 451 行 `tickChunk`：

```java
public void tickChunk(LevelChunk chunk, int randomTickSpeed) {
    // ...
    if (randomTickSpeed > 0) {
        for (LevelChunkSection section : chunk.getSections()) {
            if (section.isRandomlyTicking()) {
                int sx = section.bottomBlockX();
                int sy = section.bottomBlockY();
                int sz = section.bottomBlockZ();
                profilerfiller.push("randomTick");
                for (int i = 0; i < randomTickSpeed; i++) {
                    BlockPos randPos = this.getBlockRandomPos(sx, sy, sz, 15);
                    BlockState bs = section.getBlockState(
                        randPos.getX() - sx, randPos.getY() - sy, randPos.getZ() - sz);
                    if (bs.isRandomlyTicking()) {
                        bs.randomTick(this, randPos, this.random);
                    }
                    FluidState fs = bs.getFluidState();
                    if (fs.isRandomlyTicking()) {
                        fs.randomTick(this, randPos, this.random);
                    }
                }
                profilerfiller.pop();
            }
        }
    }
}
```

**关键事实**：

1. **每个加载的 chunk** 每 tick 跑一次 `tickChunk`。
2. 对每个 **被标记为可 random-tick** 的 16³ section，**抽 N 次**——N 等于游戏规则 `randomTickSpeed`，主世界默认 **3**。
3. 每次"抽"是均匀地从 16³ = 4096 个位置中选一个，看落到的方块是不是"愿意接受 random tick"，是的话就让它 `randomTick(...)`。

也就是说，每个 16³ section 平均每 tick 只有 3 个方块被随机选中、可能被 tick 到。这个随机性是 Minecraft 许多"慢系统"的根源：作物生长、树叶腐烂、火势蔓延、雪化、冰冻、苦力怕燃烧、黑曜石形成 ⋯⋯ 全靠它。

**random tick 不能跨 tick 持久化**——它是真随机抽的，错过就错过，不会"补"。所以作物长不出来通常是因为玩家离开了那块区域 chunk 卸载后。`/gamerule randomTickSpeed 1000` 调高这个值，作物会瞬间疯长。

## 0.2.7 第 9 步详解：block event

`runBlockEvents()` 把队列里所有 `BlockEventData` 派发出去。一个典型 BlockEventData = `(pos, block, eventId, eventParam)`。

谁排队？常见的是活塞：

```java
// 活塞被红石信号激活
level.blockEvent(pos, this, EVENT_PUSH, direction.ordinal());
```

不会立刻推动，而是排到队列里下一 tick 的第 9 步统一处理。这种**显式延迟一 tick** 的设计是为了：

1. 避免在 `setBlock` 内部递归处理推动逻辑（活塞推动会触发更多 setBlock，会爆栈）。
2. 让所有"复杂副作用"在固定时机触发，便于打印调试和回放。

**BlockEvent 是 Minecraft 里少数几个"游戏可见的双 tick 延迟"现象之一**——你激活活塞后需要一 tick 它才动。这是历史包袱也是设计选择。

## 0.2.8 不在 tick 主循环里的 neighbor update

最后这件事必须澄清：**邻居更新（neighbor update）不是计划 tick**，它是**同步**的。

任何 `level.setBlock(pos, newState, flags)` 调用，只要 `flags` 包含 `Block.UPDATE_NEIGHBORS`（2），就会**立刻**触发周围 6 邻居的 `neighborChanged(...)` 回调。这些回调会同步执行，可能再触发 `setBlock`，如此递归下去。

1.21 之前，这个递归是真递归（`InstantNeighborUpdater`），层数深了会爆栈。1.21 引入了 `CollectingNeighborUpdater` 作为默认：

```java
// CollectingNeighborUpdater
// 入口：把待更新放进队列，不立刻递归
// 出口：在 setBlock 调用栈最外层弹完队列，每条出队再触发邻居
```

它把递归展开成 **BFS**，避免了爆栈，且能保证更新顺序与递归版一致（这是 1.21 红石新机制的前置）。

不管哪种，**它们都不进 ServerLevel.tick 的任何一个步骤**。它们随当前正在执行的代码同步发生。后面 Module 4 会专门展开。

## 0.2.9 客户端帧率 vs 服务端 tick

到这里都是服务端的故事。客户端是另一回事。

客户端运行在 **`net.minecraft.client.Minecraft`**，主线程叫 "Render thread"。它**按照玩家显卡能跑出的帧率刷新**——可能是 60、144、244 FPS，也可能是 30 FPS 卡顿。

但客户端要显示一个**和服务端 tick 同步推进**的世界，怎么办？

**答案：客户端有两个独立的时间基准**：

1. **客户端 tick**：客户端自己也按 50 ms / 20 Hz 跑一个轻量级 tick（在 `Minecraft.runTick()` 里），处理客户端独有的逻辑（粒子、动画状态机推进、客户端预测）。它和服务端 tick **大致**对齐，但允许小漂移。
2. **客户端帧（render）**：每帧渲染时，根据「上一次 tick 到现在过了多少毫秒」算出 **`partialTick`**（0..1 之间的浮点数），用它对所有实体位置、动画状态做**插值**。

举例：玩家在服务端 tick T 处于 X=10.0，tick T+1 处于 X=10.5。服务端只发了这两个离散位置。客户端在两 tick 之间渲染了 3 帧，每帧用 partialTick = 0.0、0.33、0.67 算插值，画出 X=10.0、10.165、10.335 三个中间帧，看起来就丝滑了。

这套机制叫 **客户端插值（client-side interpolation）**。所有实体、爆炸、粒子、摄像机都靠它渲染。

**partialTick 在源码里到处出现**：

```java
public void renderEntity(Entity entity, double cx, double cy, double cz, float partialTick, ...);
public Vec3 getPosition(float partialTick);
```

看到带 `float partialTick` 参数的方法，就是渲染期间用 0..1 之间的小数算插值。

## 0.2.10 ServerTickRateManager：1.20.4 的 /tick 命令

1.20.4 引入了 `/tick` 命令，让你可以：

- `/tick rate <hz>`：把 TPS 从 20 改到任意值（不会改协议时基，只改 server-side perception）。
- `/tick freeze` / `/tick unfreeze`：冻结时间。
- `/tick step <N>`：单步 N 个 tick。
- `/tick sprint <N>`：一口气跑 N 个 tick（用来加速调试，不睡眠）。

实现是 `ServerTickRateManager` 类（在 `MinecraftServer.java` 第 266 行）。它替代了原本写死的 `50_000_000`（纳秒/tick）：

```java
perTick = this.tickRateManager.nanosecondsPerTick();
```

这是 1.21 时基系统**唯一可改动的部分**。常量 `MILLIS_PER_TICK = 50` 仍然不可改（协议固化），但运行时主循环节奏可以加速 / 减慢 / 暂停。

## 0.2.12 客户端 tick 的简化版

为了让你建立完整对照，客户端的等价图（高度简化）：

```
                  +-------------------+
                  |  GLFW frame loop  |   ← 60-244Hz，完全跟显卡走
                  +--------+----------+
                           │
            renderFrame(partialTick)
                           │
                ┌──────────┴──────────┐
                ▼                     ▼
            ClientTick                Render
           （20Hz 限频）              （任意帧率）
                │                      │
        ┌───────┴────────┐             ▼
        ▼                ▼          画面

                       tick
                         │
                  particles, animations,
                  client prediction,
                  network.recv (Netty 异步收, 主线程消费)
```

注意：
- 客户端没有 `randomTick` / `scheduled tick` / `blockTicks`。这些都是**服务端权威**，客户端只是渲染服务端发来的状态。
- 客户端 `ClientLevel.tick` 主要做粒子、动画、声音衰减这些"反正服务端不管"的视觉工作。
- 客户端的 tick 频率和服务端**逻辑上独立**——没人保证它们以微秒级精确对齐，靠的是网络包驱动的 sync。

## 0.2.13 C++ 移植的最小可行设计

以下是给 C++ 引擎用的骨架。**绝对时间表 + 软实时 + 跳帧追赶**：

```cpp
class ServerClock {
public:
    using Nanos = std::chrono::nanoseconds;
    static constexpr Nanos NANOS_PER_TICK{50'000'000};
    static constexpr Nanos OVERLOAD_THRESHOLD{2'000'000'000};   // 2s
    static constexpr int  MAX_SKIP_PER_OVERLOAD = 20;

    void run() {
        nextTickTime_ = std::chrono::steady_clock::now();
        while (running_) {
            auto now = std::chrono::steady_clock::now();
            auto lag = now - nextTickTime_;
            if (lag > OVERLOAD_THRESHOLD) {
                int skip = std::min<int>(int(lag / NANOS_PER_TICK), MAX_SKIP_PER_OVERLOAD);
                LOG_WARN("Can't keep up, skipping {} ticks", skip);
                nextTickTime_ += skip * NANOS_PER_TICK;
            }

            nextTickTime_ += NANOS_PER_TICK;
            tickOnce_();

            now = std::chrono::steady_clock::now();
            if (nextTickTime_ > now) {
                std::this_thread::sleep_until(nextTickTime_);
            }
        }
    }

private:
    std::chrono::steady_clock::time_point nextTickTime_;
    void tickOnce_() {
        // 1-12 步...
    }
};
```

**ECS 友好的 tickOnce_ 拆解**：

```cpp
void World::tick() {
    worldBorder_.tick();
    weather_.tick();
    handlePlayerSleeping_();
    skyLight_.update();
    timeSystem_.advance();

    blockTickQueue_.processUpTo(currentGameTick_, /*budget=*/65536);
    fluidTickQueue_.processUpTo(currentGameTick_, /*budget=*/65536);

    raids_.tick();

    chunkManager_.tick();          // 内部跑 randomTick
    blockEventQueue_.flush();      // 活塞等

    for (auto& entity : entityTickList_) {
        if (!entity.removed && entity.inActiveRange) {
            entity.tick();
        }
    }
    blockEntityManager_.tick();
    entityStreamManager_.tick();   // 加载/卸载 entity 到 chunk
}
```

**客户端**：单独一个线程 / 单独的 `ClientWorld`，按显卡帧率渲染。每帧需要：

1. 收 server 发来的状态包 → 写进 `ClientWorld`。
2. 计算 `partialTick = (now - lastClientTick) / NANOS_PER_TICK`，clamp 到 [0, 1]。
3. 用 partialTick 对所有实体位置插值后再渲染。
4. 每 50 ms 调用 `ClientWorld::tick()` 推进客户端独有逻辑（粒子、动画状态机）。

---

## 0.2.14 一句话总结

20 TPS / 50 ms 的固定时基由 `SharedConstants` 写死；服务端主循环 `runServer → tickServer → ServerLevel.tick` 12 步走完，是所有方块、流体、实体、网络逻辑的唯一节拍器；客户端不跑 tick，按显卡帧率渲染并用 `partialTick` 在两个服务端状态之间插值；scheduled / random / block-event / neighbor 是**四种性质完全不同**的"更新"，挂在主循环的不同点，下一节起每次提起都要先想清楚是哪一种。
