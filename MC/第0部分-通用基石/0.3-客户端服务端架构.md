# 0.3 客户端 / 服务端 / 集成服务端架构

## 0.3.0 你将在本节学到什么

读完这一节你应当能闭着眼睛回答：

1. 单机 Minecraft 一启动，到底有几个进程、几个线程、几个 World 对象在内存里？
2. 联机版（你连别人服务器）和单机版的差别是什么？为什么"单机也跑了一个服务端"？
3. `@OnlyIn(Dist.CLIENT)` 这个注解在源码里到处出现，它在编译期 / 运行期分别意味着什么？我能直接调一个标了 `@OnlyIn(Dist.CLIENT)` 的方法吗？
4. 玩家按下 W 键到角色真正移动一格，这个事件在客户端 / 服务端来回跑了几趟？
5. `mcp.client.Start` 这个仓库里唯一手写的 Java 文件，它到底是什么，和 `net.minecraft.client.main.Main` 什么关系？
6. 我在 C++ 引擎里要复现这套客户端 / 服务端架构，最简洁的设计是什么？

## 0.3.1 同一份"游戏"，三种部署形态

Minecraft 1.21 的代码同时支持三种部署模式：

| 模式 | 客户端在哪 | 服务端在哪 | 通讯 | 入口类 |
|------|-----------|-----------|------|--------|
| **单机** | 玩家自己进程 | **同一个进程** 的另一组对象 | 内存 channel | `net.minecraft.client.main.Main` |
| **联机（玩家自架专用服）** | 玩家进程 | 另一台机器另一个进程 | TCP / Netty | 客户端：`Main`；服务端：`net.minecraft.server.Main` |
| **多人开放服（Realms / Aternos / 自有服务器）** | 玩家进程 | 远程进程 | TCP / Netty | 同上 |

**关键事实**：从游戏逻辑看，**永远存在客户端 + 服务端两侧**。单机模式不是"少了服务端"，而是"服务端跑在玩家进程内"。

这个设计的好处：

- 单机和联机的代码路径**完全统一**——一段方块更新代码不需要写两份「客户端版」「服务端版」。
- 玩家暂停游戏 = 服务端 `tickServer` 不调用，世界冻结。
- 玩家给单机存档开 LAN 让朋友连进来 = 启动一个 socket 监听器，接受外部连接复用同一个服务端。

代价：单机也要付出"序列化 + 反序列化"的开销（你的角色动作要经过完整的网络包路径，只不过是经过内存 channel 而不是 socket）。Mojang 觉得值得，因为代码统一性极高。

## 0.3.2 三个关键的 Main 入口

`MCP-Reborn-1.21` 仓库里和"启动"有关的入口：

### `net.minecraft.client.main.Main`
**真正的客户端入口**。被 `./gradlew runclient` 调用。它解析命令行参数（`--username`、`--uuid`、`--accessToken`、`--version`、`--assetsDir`、`--assetIndex`），构造 `Minecraft` 单例，启动渲染循环。

### `net.minecraft.server.Main`
**专用服务端入口**。被 `./gradlew runserver` 调用。它构造 `DedicatedServer`，开始监听端口（默认 25565），等待客户端连接。这是你下载 `server.jar` 双击启动时跑的代码。

### `mcp.client.Start`
**MCP 工程独有的客户端包装器**，本仓库唯一的手写文件之一。它的作用是给 IntelliJ 的 Run Configuration 提供一个能直接点"运行"按钮的入口——它在调用真正的 `Main.main(args)` 之前，先把 `--version`、`--assetsDir`、`--assetIndex 16`、`--accessToken 0` 这些参数注入进去：

```java
// mcp/client/Start.java（伪代码）
public static void main(String[] args) {
    List<String> defaults = Arrays.asList(
        "--version", "1.21.4",
        "--assetsDir", "run/assets",
        "--assetIndex", "16",
        "--accessToken", "0"
    );
    String[] full = concat(defaults, args);
    net.minecraft.client.main.Main.main(full);
}
```

它**不是**游戏代码，**不是** Mojang 的产物，是 MCP 工程为方便开发准备的脚手架。看到它知道是这么个东西就行，跳过不读。

## 0.3.3 单机模式下的进程内拓扑

按下"创建新世界"或"加载世界"，单机 Minecraft 会构造下面这张图：

```
                   Java JVM 进程
   ┌──────────────────────────────────────────────────────────────┐
   │                                                              │
   │    Render Thread                  Server Thread              │
   │   (Minecraft.run)               (IntegratedServer.run)       │
   │                                                              │
   │   ┌───────────────┐              ┌────────────────────┐      │
   │   │   Minecraft   │              │ IntegratedServer   │      │
   │   │  (singleton)  │              │ extends            │      │
   │   │               │              │ MinecraftServer    │      │
   │   │ ClientLevel   │              │                    │      │
   │   │  (镜像)       │              │ ServerLevel ×N     │      │
   │   │               │              │  (权威世界)        │      │
   │   │ LocalPlayer   │              │                    │      │
   │   │               │              │ ServerPlayer ×N    │      │
   │   └──────┬────────┘              └─────────┬──────────┘      │
   │          │                                 │                 │
   │          │           内存 channel          │                 │
   │          ▼                                 ▼                 │
   │   ┌─────────────┐  ←──────────────→  ┌─────────────┐        │
   │   │  Connection │   LocalChannel     │  Connection │        │
   │   │  (client    │   (DefaultEvent    │  (server    │        │
   │   │   side)     │    LoopGroup)      │   side)     │        │
   │   └─────────────┘                    └─────────────┘        │
   │                                                              │
   └──────────────────────────────────────────────────────────────┘
```

具体说：

- **Render Thread** 跑客户端的渲染循环。它持有 `Minecraft` 单例、`ClientLevel`（世界的客户端镜像）、`LocalPlayer`（玩家在客户端的副本）。
- **Server Thread** 跑服务端的 tick 循环（0.2 节那张图）。它持有 `IntegratedServer`（继承 `MinecraftServer`）、各 `ServerLevel`（权威世界状态）、各 `ServerPlayer`（玩家在服务端的副本）。
- 两侧之间靠 **Netty 的 `LocalChannel`** 通讯——Netty 提供的纯内存管道，零拷贝，但走完整的编解码流水线（`PacketEncoder` / `PacketDecoder`），所以**协议层和远程网络完全一致**。
- 玩家放置一个方块：客户端发 `ServerboundUseItemOnPacket` → 进 LocalChannel → 服务端 `ServerGamePacketListenerImpl.handleUseItemOn` 处理 → 改 `ServerLevel` → 广播 `ClientboundBlockUpdatePacket` → 客户端 `ClientPacketListener` 接收 → 改 `ClientLevel` → 渲染线程下一帧画出来。

**这个流程在单机和联机里一模一样**。区别只是 LocalChannel 换成 Socket。

## 0.3.4 IntegratedServer vs DedicatedServer

`MinecraftServer` 是抽象基类，两个子类：

### `net.minecraft.client.server.IntegratedServer`
单机模式下用的服务端实现。特点：
- 跑在客户端 JVM 内的 "Server thread" 上。
- 不监听 socket（除非玩家点了"开放局域网"）。
- 进度条更新会回调到客户端（用 `connection.send` 走 LocalChannel）。
- 玩家断开 = 暂停游戏。
- 不能被 Bukkit / Spigot 替换（它和客户端绑死）。

### `net.minecraft.server.dedicated.DedicatedServer`
专用服务端实现。特点：
- 自己一个进程，从 `net.minecraft.server.Main` 启动。
- 读 `server.properties` 决定监听端口、白名单、view-distance 等。
- 接受任意数量客户端连接，无客户端时也能继续跑（后台运行）。
- 是 Bukkit / Paper / Forge / Fabric 的 mixin 注入目标。
- 没有玩家在线时空 tick 几百次后会进入"没人就少 tick"的省电模式（参考 `ServerLevel.emptyTime`）。

**对开发者来说重要的一点**：你写一段服务端逻辑，要确保它在 IntegratedServer 和 DedicatedServer 上都能跑。区别极少，但有：DedicatedServer 没有 `Minecraft.getInstance()` 可以调，所以**绝对不要在服务端代码里访问任何客户端单例**。

## 0.3.5 `@OnlyIn(Dist.CLIENT)` 在干嘛

打开本仓库 `src/main/java/net/minecraft/client/Minecraft.java`，看第 246-252 行：

```java
import net.minecraftforge.api.distmarker.Dist;
import net.minecraftforge.api.distmarker.OnlyIn;
// ...
@OnlyIn(Dist.CLIENT)
public class Minecraft extends ReentrantBlockableEventLoop<Runnable> implements ... {
```

**这是 Forge 注入的注解**（包名 `net.minecraftforge.api.distmarker`）。在 Vanilla Mojang 源码里没有它，是 ForgeGradle 在反编译过程中根据"哪些字段在 server jar 里被剥离"自动加上的。

它的语义：**这个类 / 字段 / 方法只在客户端 jar 里存在，服务端 jar 里被剥离**。

实际意义：

1. **编译期**：标注 `@OnlyIn(Dist.CLIENT)` 的代码引用了客户端独有的类（`Minecraft`、`LevelRenderer`、`SoundEngine` ...）。如果你在一段服务端代码里调用它们，发布服务端 jar 时这些代码会被剥离，导致 NoClassDefFoundError。
2. **运行期**：服务端 jar 启动时，类加载器看到 `@OnlyIn(Dist.CLIENT)` 的方法被调用 = 抛 `IllegalSideException`。
3. **代码组织提示**：你应该把客户端逻辑和服务端逻辑分开放，不要混。

**对照表**：

| 注解 | 含义 | 例子 |
|------|------|------|
| `@OnlyIn(Dist.CLIENT)` | 仅客户端 jar | `Minecraft`、`ClientLevel`、`SoundEngine` |
| `@OnlyIn(Dist.DEDICATED_SERVER)` | 仅服务端 jar（罕见） | 几个专门的 GUI 命令 |
| 无注解 | 共享，两边都有 | `BlockState`、`ServerLevel`、`Block` |

**MCP-Reborn 工程是合一的**——两边的代码都在 `src/main/java/`，`build` 出来一个 jar 同时含两边。所以从工程层面你不会真的撞上 `IllegalSideException`，但**注解的语义提示**仍然重要：看到 `@OnlyIn(Dist.CLIENT)` 就知道"这是客户端专属，不可能在服务端线程上跑"。

## 0.3.6 关键划分：哪些类在哪边

| 类前缀 / 包 | 跑在 | 说明 |
|------------|------|------|
| `net.minecraft.client.*` | 仅客户端 | 渲染、输入、UI、声音、客户端预测 |
| `net.minecraft.server.*` | 仅服务端 | dedicated server 启动器、网络监听 |
| `net.minecraft.server.level.*` | 服务端线程（含集成服务端） | `ServerLevel`、`ServerChunkCache`、`ServerPlayer`、`ChunkMap` |
| `net.minecraft.world.level.*` | **共享** | `Level`、`LevelChunk`、`Block`、`BlockState`、`Biome` ⋯⋯ |
| `net.minecraft.world.entity.*` | **共享** | `Entity`、各生物、玩家基类 `Player` |
| `net.minecraft.network.*` | **共享** | 协议、Connection、Packet 类型 |
| `net.minecraft.nbt.*` | **共享** | NBT |
| `net.minecraft.world.level.levelgen.*` | 主要服务端，但 chunk 数据要发客户端 | 世界生成（Module 3） |

**最关键的一对**：

- `Level`（基类）：客户端 / 服务端共有的世界基础实现，提供查询方块、查询光照等共享 API。
- `ClientLevel`（客户端子类）：负责接收网络包、做客户端预测。
- `ServerLevel`（服务端子类）：跑权威 tick、做实体管理、生成新区块。

90% 的"游戏世界"代码（方块更新、流体、redstone、carver、feature）都写在共享的 `Level` 或 `LevelChunk` 上。**所以这些代码两边都跑**。区别在于：服务端的 tick 真正驱动了状态变化，客户端的 tick 主要是渲染辅助。

## 0.3.7 客户端预测 vs 服务端权威

最容易混淆的一点：**为什么我移动时画面是流畅的，但我做了非法操作（比如挖一个保护方块）会被"弹回去"**？

答：**客户端预测 + 服务端权威**。

1. 玩家按下 W：客户端立刻更新 `LocalPlayer` 位置（=客户端预测），同时发 `ServerboundMovePlayerPacket(newX, newY, newZ, ...)`。
2. 服务端收到包：检查合法性（速度上限、不能穿墙、有没有冰冻 debuff）。
3. **合法**：服务端更新 `ServerPlayer` 位置，广播给其他客户端。本玩家**收不到回包**（节省带宽，假设客户端预测正确）。
4. **不合法**：服务端把 `ServerPlayer` 位置回滚到上次合法位置，发 `ClientboundPlayerPositionPacket(legalX, legalY, legalZ)` 强制纠正。客户端收到这个包后**强制把 LocalPlayer 拉回去**——视觉上就是著名的"橡皮筋"效果。

这套机制扩展到所有客户端可主动发起的操作：挖方块、放方块、攻击实体、丢物品、聊天、进出容器。**全部都是「客户端先模拟，服务端后审核，不合法就回滚」**。

**对引擎移植的启示**：你的 C++ 引擎也必须这么做，否则联机会有 200ms 移动延迟，体感无法接受。具体做法在第 7 部分网络协议里展开。

## 0.3.8 玩家放置一格泥土的完整时序

把上面所有要素串起来，一个具体例子：

```
玩家在 (10, 64, 10) 这一格手握泥土，按下右键。

[客户端 Render Thread]
1. MouseHandler.onMouseAction → useItem
2. 客户端预测：LocalPlayer.getInventory() 减 1 个泥土；ClientLevel 不直接 setBlock（要等服务端确认）
3. 发包：connection.send(new ServerboundUseItemOnPacket(InteractionHand.MAIN, BlockHitResult, sequenceId))

[网络层 LocalChannel / Socket]
4. 包通过 LocalChannel（单机）或 Socket（联机）传到服务端
   编解码：PacketEncoder → bytes → PacketDecoder → ServerboundUseItemOnPacket

[服务端 Server Thread]
5. ServerGamePacketListenerImpl.handleUseItemOn:
   - 检查 player 距离目标方块 ≤ 6 格
   - 检查 player 持有的物品确实是泥土
   - 检查目标位置允许放方块（不是基岩、不被实体占据）
6. 通过：ServerLevel.setBlock(pos, dirt.defaultBlockState(), Block.UPDATE_ALL)
   - 此时触发同步邻居更新（Module 4）
7. ChunkMap 把 BlockUpdate 排进发送队列
8. 周围所有玩家（包括本玩家）收到 ClientboundBlockUpdatePacket
9. 给本玩家发 ServerboundUseItemOnPacket 的 ack（含相同 sequenceId）

[本玩家客户端 Render Thread]
10. ClientPacketListener.handleBlockUpdate → ClientLevel.setBlock(pos, dirt, ...)
11. ClientPacketListener.handleBlockChangedAck：sequenceId 一致 → 客户端预测被服务端确认，不需要回滚
12. 下一帧渲染：ChunkRenderDispatcher 看到 chunk dirty，重编译该 chunk 的 mesh
13. 玩家看到泥土出现
```

**注意第 11 步的 `ClientboundBlockChangedAckPacket`**——1.19+ 引入的"回执机制"。客户端在第 2 步会乐观地把方块**也**预测放上去（不只是减库存），然后等待 ack；如果服务端拒绝，会发"撤销"包让客户端回滚预测。这是 Minecraft 的客户端预测从"只预测移动"升级到"也预测方块交互"的关键改进。

## 0.3.9 C++ 移植的最小可行架构

C++ 引擎里，给上面这套机制最简洁的映射：

```cpp
// 共享（client + server 都用）
class World;
class Chunk;
struct BlockState;

// 服务端独有
class ServerWorld : public World { ... };
class ServerPlayer : public Player { ... };
class ServerHost {
    void run();   // tick loop, 0.2 节
};

// 客户端独有
class ClientWorld : public World { ... };
class LocalPlayer : public Player { ... };
class GameClient {
    void runFrame();  // render frame, partialTick
};

// 单机：
class IntegratedHost {
    ServerHost server;
    GameClient client;
    InMemoryConnection connClient2Server;
    InMemoryConnection connServer2Client;
    // server 在另一个 std::thread 上跑，与 client 共享内存通讯
};
```

**关键守则**：

1. `ClientWorld` 和 `ServerWorld` 都继承 `World`，95% 的方块查询逻辑写在 `World` 上。
2. **网络包通讯永远走 `Connection`**——单机也用 `InMemoryConnection`（基于 `std::queue<Packet>` + `std::condition_variable`）。这样切到联机模式只需要换实现，不改逻辑。
3. **客户端不许直接调用 `ServerWorld::setBlock`** ——哪怕在单机进程内、哪怕能拿到指针。永远走包。
4. **客户端预测**：`ClientWorld::predictBlockChange(pos, expected, sequenceId)` 立刻改 chunk + 标记 dirty render；收到 ack 再 commit。

这套架构很像 UE5 的 `NetDriver` + `Replicated` 字段，但比它简单——MC 的网络模型完全是自己 hand-roll 的，没有自动同步。

## 0.3.10 一句话总结

无论单机联机，**永远存在客户端 + 服务端两侧** —— 单机只是把它们装在同一进程里、用内存 channel 通讯；服务端权威推进世界状态，客户端做预测和插值；`@OnlyIn(Dist.CLIENT)` 是 Forge 标注的"该代码仅客户端 jar 有"的提示；几乎所有"世界逻辑"代码都写在共享层（`Level` / `LevelChunk`），但实际驱动它们 tick 的只有服务端线程。
