## 4.8.1 主要性能预算与限额

汇总 Module 4 涉及的所有限额：

| 限额 | 默认值 | 来源 | 含义 |
|------|--------|------|------|
| `tickRate` | 20 Hz / 50 ms per tick | SharedConstants.MILLIS_PER_TICK | 服务端 tick 频率 |
| `OVERLOADED_THRESHOLD_NANOS` | 20 秒 | MinecraftServer | tick 超时多久触发 "Can't keep up" 警告 |
| `MAX_BLOCK_TICKS_PER_TICK` | 65536 | ServerLevel | scheduled block tick 单 tick 上限 |
| `MAX_FLUID_TICKS_PER_TICK` | 65536 | ServerLevel | scheduled fluid tick 单 tick 上限 |
| `randomTickSpeed` | 3 | GameRule | random tick 每 section 每 tick 抽样数 |
| `maxChainedNeighborUpdates` | 1000000 | NeighborUpdater | 单 setBlock 链触发邻居更新上限 |
| `maxEntityRadius` | 50.0 | ServerLevel | 实体 tick 范围（与玩家距离）|
| `MOB_CATEGORY_LIMITS` | varies | NaturalSpawner | 每类 mob 的世界总数上限 |

下面逐一展开。

## 4.8.2 MAX_BLOCK_TICKS_PER_TICK = 65536

回顾 4.3.9：

```java
// ServerLevel.tick 行 353
this.blockTicks.tick(gameTime, 65536, this::tickBlock);
this.fluidTicks.tick(gameTime, 65536, this::tickFluid);
```

`LevelTicks.tick(gameTime, budget, ticker)`：

```java
public void tick(long gameTime, int budget, BiConsumer<BlockPos, T> ticker) {
    this.collectTicksToRun(gameTime);
    int processed = 0;
    while (processed < budget) {
        ScheduledTick<T> tick = this.toRunThisTick.poll();
        if (tick == null) break;
        ticker.accept(tick.pos(), tick.type());
        processed++;
    }
    // 未处理完的 ticks 推到下一 tick
}
```

**含义**：

- 单 tick 内最多处理 65536 个 scheduled block tick + 65536 个 fluid tick。
- 超出 → 剩余推到下一 tick。
- **不丢失** —— 只是延迟。

**为什么 65536**：经验值。1.13 之前没有限额（早期"水位炸弹"卡服 → 加 budget）。65536 在常见硬件上 50 ms 内处理完 + 留余地给 entity / network。

## 4.8.3 水位炸弹与流体卡服

经典 1.7 时代攻击：玩家在 chunk 边缘放 1000 个水源——水流向四面八方，每格水都要 schedule fluid tick。

**1.7-1.12**：每 tick 处理所有 scheduled fluid tick，无 budget。

→ 单 tick 处理 ~50 万次 → 服务端冻僵 ~30 秒。

**1.13+**：fluid budget = 65536。爆炸不会让服务端冻僵，但会**积压** —— 多个 tick 持续超 budget → 大量"等待中" fluid tick 推到下一 tick → 服务端持续慢。

**实际现象**：玩家 break 大量水源 → 服务端 TPS 短暂掉到 5-10 → 几十秒后恢复。

## 4.8.4 randomTickSpeed GameRule

```java
// GameRules
public static final GameRules.Key<GameRules.IntegerValue> RULE_RANDOMTICKING = ...;
```

默认 3。`/gamerule randomTickSpeed N` 改值。

**线性 vs 总开销**：

```
开销 ∝ randomTickSpeed × ticking_section_count

主世界视距 32 chunk² ≈ 1024 chunk × 24 section = 24576 sections
其中 ticking section ≈ 30%（geometry 决定）= ~7000 sections

randomTickSpeed = 3：每 tick 抽样 21000 次 → ~1-3 ms / tick
randomTickSpeed = 100：抽样 700000 次 → ~30-100 ms / tick（接近 tick budget 上限）
randomTickSpeed = 1000：抽样 700万次 → 几乎肯定超时
```

**实际用途**：

- `/gamerule randomTickSpeed 0` —— 关闭所有 random tick（作物 / 雪化全停）。
- `/gamerule randomTickSpeed 1000` —— 作物瞬间长大（农场 cheat）。
- `/gamerule randomTickSpeed 3` —— vanilla 默认。

`/gamerule randomTickSpeed` 是**最常被改的 game rule** —— 给玩家更多控制。

## 4.8.5 Can't keep up 警告

回顾 0.2.2：

```java
// MinecraftServer.runServer
long lag = Util.getNanos() - this.nextTickTimeNanos;
if (lag > OVERLOADED_THRESHOLD_NANOS + 20L * perTick) {
    long skip = lag / perTick;
    LOGGER.warn("Can't keep up! Is the server overloaded? Running {}ms or {} ticks behind", skip * perTick / 1_000_000, skip);
    this.nextTickTimeNanos += skip * perTick;
}
```

**`OVERLOADED_THRESHOLD_NANOS = 20 * 1_000_000_000` = 20 秒**。

**触发条件**：服务端连续 ≥ 20 秒没有跟上 50 ms / tick 的节拍。

**触发后的行为**：

1. 打印警告。
2. **跳过**滞后的 tick —— 直接把 `nextTickTimeNanos` 设到当前时间附近。
3. 下次 tick 立刻开始。

**结果**：服务端不会"无限累积滞后"——超过 20 秒就放弃追赶。**游戏内时间会变慢**（比如本来 5 分钟天黑，现在 6 分钟才天黑）。

**这不是数据不一致**——只是 game time 和 wall time 的比例失调。所有 scheduled tick 仍按 game time 处理，对玩家"内部"逻辑 OK。

## 4.8.6 ServerTickRateManager

1.20.4 引入的 `/tick` 命令族——可以调节 server tick 节奏。

```java
public class ServerTickRateManager extends TickRateManager {
    // ⋯
    public boolean stepGameIfPaused(int steps) { ... }
    public boolean stopStepping() { ... }
    public boolean sprintTick() { ... }
    public boolean stepTicks(int steps) { ... }
    public void requestSprint(float ticks) { ... }
    public void stopSprinting() { ... }
}
```

**`/tick` 子命令**：

| 命令 | 效果 |
|------|------|
| `/tick rate <hz>` | 改变 tick 频率（1-10000 Hz）|
| `/tick freeze` | 冻结时间 —— 不 tick |
| `/tick unfreeze` | 解冻 |
| `/tick step` / `/tick step <n>` | 单步 tick |
| `/tick sprint <n>` | 一口气跑 N tick（无 sleep）|
| `/tick query` | 查询当前 tick rate |

**`tick rate` 改频率**的实现：

```java
public long nanosecondsPerTick() {
    return (long)(NANOS_PER_SECOND / this.tickrate);
}
```

`MinecraftServer.runServer` 用这个值替代默认 50 ms。

**`/tick sprint`**：

```java
if (this.tickRateManager.isSprinting() && this.tickRateManager.checkShouldSprintThisTick()) {
    perTick = 0;     // 不 sleep
    this.nextTickTimeNanos = Util.getNanos();
}
```

**忽略 sleep**——CPU 100% 跑 tick 直到 sprint 结束。给"快进游戏内时间"用。

**`/tick freeze`**：

```java
public boolean isFrozen() { return this.frozenTicksToRun.get() <= 0 && !this.runsNormally; }

// ServerLevel.tick 内
public void tick(BooleanSupplier haveTime) {
    boolean normal = tickRateManager.runsNormally();
    if (normal) {
        // 正常 tick
    } else {
        // frozen 时仍跑某些代码（如 entity 状态机推进）
    }
}
```

**冻结时**仍跑：

- entity 动画状态。
- 客户端 tick（粒子、动画）。
- 网络层。

**冻结时不跑**：

- scheduled block tick / fluid tick。
- random tick。
- weather cycle / time progression。
- mob AI tick.
- runBlockEvents.

视觉效果：世界完全静止，但玩家仍能移动 / 探索。

## 4.8.7 NaturalSpawner 刷怪封顶

NaturalSpawner 不是"无限刷"——有按 MobCategory 的世界总数上限：

```java
public enum MobCategory {
    MONSTER(70, false, false, 128),
    CREATURE(10, true, true, 128),
    AMBIENT(15, true, false, 128),
    AXOLOTLS(5, true, false, 128),
    UNDERGROUND_WATER_CREATURE(5, true, false, 128),
    WATER_CREATURE(5, true, false, 128),
    WATER_AMBIENT(20, true, false, 128),
    MISC(-1, true, false, 128);
    
    private final int max;
    private final boolean isFriendly;
    private final boolean isPersistent;
    private final int despawnDistance;
}
```

**MONSTER cap = 70**：玩家附近**不能同时存在超过 70 只 hostile mob**。这是 mob cap。

**实现**（NaturalSpawner.spawnForChunk 内）：

```java
public static void spawnForChunk(...) {
    for (MobCategory category : MobCategory.values()) {
        int spawnable = category.getMax() - existingCountInRange;
        if (spawnable <= 0) continue;
        // ⋯
    }
}
```

每 tick 服务端扫所有 chunk 内的实体，按 category 计数。已经 ≥ cap 的 category 不再刷新。

**这是为什么大型怪物农场玩家要"远离"** —— 远离后近处玩家附近的 cap 就只算自己（减少其他 mob 占用），农场效率最大化。

## 4.8.8 Distance Manager

`DistanceManager` 维护"哪些 chunk 在 ticking 范围"：

```java
public class DistanceManager {
    public static final int ENTITY_TICKING_RANGE_LEAVES = 32;     // 实体 tick 范围
    public static final int BLOCK_TICKING_RANGE_LEAVES = 33;       // 方块 tick 范围
    
    public boolean inEntityTickingRange(long chunkPos) { ... }
    public boolean inBlockTickingRange(long chunkPos) { ... }
}
```

**两层 ticking 范围**：

- **block ticking**（默认 simulation distance 10 chunks）：本范围内的 chunk 跑 random tick / scheduled tick。
- **entity ticking**（block ticking 内一圈较小）：本范围内的 entity 才 tick。

**超出**则 chunk 加载但**不 tick** —— 玩家看到"静止冻结"的 chunk。这是"卸载 vs ticking 距离"的差别。

## 4.8.9 一些其他限额

| 限额 | 默认 | 含义 |
|------|------|------|
| `Block.UPDATE_LIMIT` | 512 | setBlock 递归 shape update 深度 |
| `Level.MAX_BRIGHTNESS` | 15 | 光照值上限 |
| `view-distance` | 8-32 | 客户端 / 服务端可见 chunk 半径 |
| `simulation-distance` | 4-32 | 服务端 ticking chunk 半径 |
| `serverProperties.maxPlayers` | 20 | 单服上限 |

**注意**：`view-distance` 和 `simulation-distance` 在 1.18+ 是分开的——之前合并成一个。让玩家看到远但不 tick 远（性能优化）。

## 4.8.10 单 tick 超时的影响

如果某 tick 真的需要 100 ms（超过 50 ms budget）：

1. `runServer` 检测到 lag > 0：
   - lag < 20 秒：忽略，下次 tick 立刻开始（追赶）。
   - lag ≥ 20 秒：跳过 N 个 tick + 警告。
2. `nextTickTimeNanos` 已经过期：直接进下一 tick，不 sleep。
3. 客户端：因为 ChunkUpdatePacket 等包延迟到达，**视觉上玩家会感觉卡顿** ~50-100 ms。
4. TPS 跌破 20。

**TPS 可观测性**：

- `/forge tps` (Forge mod)、`/spark tps` (Spark mod) 等命令显示。
- vanilla 1.21 没有内置 TPS 命令——但 `/debug start` / `/debug stop` 可以记录详细 profile。

## 4.8.11 优化策略

### 1. 减少 random tick 抽样

`randomTickSpeed` 调小（1-2）—— 农作物变慢但服务端轻松。

### 2. 调小 simulation-distance

`server.properties` 的 simulation-distance 从 10 → 6 → ticking chunk 数量减半。

### 3. 限制 mob cap

`/gamerule maxNumberOfPlayersInTheGameStraightAfterRespawn` 等不存在——但 mod 经常 hack mob cap。

### 4. 不让玩家集中

mob 集群 / 实体扫描 / 邻居更新等都是 N² 复杂度。让玩家分散到不同 chunk 减少 hot chunk。

### 5. 避免大型水流

破坏大量水源 / 创造水流不要在 ticking range 边界（避免反复 tick 进出范围 schedule）。

## 4.8.13 C++ 移植

```cpp
namespace mc::server {

struct TickBudget {
    static constexpr int MAX_BLOCK_TICKS = 65536;
    static constexpr int MAX_FLUID_TICKS = 65536;
    static constexpr int MAX_CHAINED_NEIGHBOR_UPDATES = 1000000;
    static constexpr std::chrono::seconds OVERLOADED_THRESHOLD{20};
};

class TickRateManager {
public:
    int64_t nanosecondsPerTick() const {
        if (sprinting_) return 0;
        return int64_t(1e9 / tickrate_);
    }
    
    bool isFrozen() const { return frozen_; }
    bool runsNormally() const { return !frozen_; }
    
    void setTickRate(float hz) { tickrate_ = std::clamp(hz, 1.0f, 10000.0f); }
    void freeze() { frozen_ = true; }
    void unfreeze() { frozen_ = false; }
    void sprint(int ticks) { sprinting_ = true; sprintRemaining_ = ticks; }

private:
    float tickrate_ = 20.0f;
    bool frozen_ = false;
    bool sprinting_ = false;
    int sprintRemaining_ = 0;
};

class ServerLevel : public Level {
public:
    void tick(std::function<bool()> haveTime) {
        bool normal = tickRateManager_->runsNormally();
        
        // ... 12 步 ...
        
        if (normal) {
            blockTicks_.tick(gameTime_, TickBudget::MAX_BLOCK_TICKS, [this](BlockPos pos, Block* block) {
                tickBlock(pos, block);
            });
            fluidTicks_.tick(gameTime_, TickBudget::MAX_FLUID_TICKS, [this](BlockPos pos, Fluid* fluid) {
                tickFluid(pos, fluid);
            });
        }
        
        // ... 8. random tick (chunkSource.tick) ...
    }
};

}
```

## 4.8.14 一句话总结

服务端 tick 性能上限通过多层限额防护：单 tick `MAX_BLOCK_TICKS_PER_TICK = 65536` + `MAX_FLUID_TICKS_PER_TICK = 65536` 让水位炸弹不冻僵服务端（仅积压）；`maxChainedNeighborUpdates = 1M` 让超大红石机器报错跳过；`OVERLOADED_THRESHOLD_NANOS = 20s` 触发 "Can't keep up" 警告并放弃追赶；`randomTickSpeed = 3` 控制 random tick 密度（玩家可改）；NaturalSpawner mob cap（MONSTER 70 / CREATURE 10）限制刷怪密度；`simulation-distance` vs `view-distance` 分离（1.18+）让远 chunk 可见但不 tick；`/tick rate` / `/tick freeze` / `/tick step` / `/tick sprint` 命令给运维 / 调试控制 tick 节奏；vanilla `Profiler` 提供详细 tick profile 用于定位瓶颈。
