# 4.7 客户端 vs 服务端 Tick

## 4.7.0 你将在本节学到什么

读完这一节你应当能闭着眼睛回答：

1. 客户端 `ClientLevel` 和服务端 `ServerLevel` 的 tick 内容差别是什么？
2. 客户端跑 scheduled tick 吗？跑 random tick 吗？跑 BlockEvent 吗？
3. 客户端的"假更新"——那些粒子、声音、动画是哪里发起的？
4. 客户端 60-244 FPS 帧率与服务端 20 TPS tick 怎么协调？
5. 玩家挖方块的"挖掘进度"在客户端 / 服务端各自怎么计算？

---

## 4.7.1 总览

回顾 0.3 节的进程拓扑：单机 = Render Thread（Minecraft）+ Server Thread（IntegratedServer）。两个线程各自有自己的 tick 逻辑：

```
                 Render Thread                    Server Thread
                 ─────────────                    ─────────────
                 Minecraft.runTick()              MinecraftServer.tickServer()
                       │                                │
                       ▼                                ▼
                 ClientLevel.tickEntities         ServerLevel.tick()
                 ClientLevel.animateTick           ├── 1. worldBorder
                       │                            ├── 2. weather
                       ▼                            ├── 3. sleeping
                 渲染（任意帧率）                    ├── 4. skyBrightness
                                                    ├── 5. tickTime
                                                    ├── 6. blockTicks ★
                                                    ├── 7. raids
                                                    ├── 8. random tick ★
                                                    ├── 9. runBlockEvents ★
                                                    ├── 10. entityTickList ★
                                                    ├── 11. blockEntities ★
                                                    └── 12. entityManager
```

**核心差异**：

- **`scheduled tick` / `random tick` / `runBlockEvents` / 实体 AI** **只在服务端跑**。
- 客户端只做**渲染相关**：粒子、动画、声音、客户端预测。

---

## 4.7.2 客户端不跑 scheduled tick

打开 `net.minecraft.client.multiplayer.ClientLevel`：

```java
public class ClientLevel extends Level {
    @Override
    public TickContainerAccess<Block> getBlockTicks() {
        return BlackholeTickAccess.emptyContainer();
    }
    
    @Override
    public TickContainerAccess<Fluid> getFluidTicks() {
        return BlackholeTickAccess.emptyContainer();
    }
    
    @Override
    public LevelTickAccess<Block> getBlockTicks() {
        return BlackholeTickAccess.emptyLevelList();
    }
}
```

**`BlackholeTickAccess`**：

```java
public class BlackholeTickAccess {
    private static final TickContainerAccess<Object> CONTAINER = new TickContainerAccess<Object>() {
        public void schedule(ScheduledTick<Object> tick) { /* ignore */ }
        public boolean hasScheduledTick(BlockPos pos, Object type) { return false; }
    };
    
    public static <T> TickContainerAccess<T> emptyContainer() {
        return (TickContainerAccess<T>) CONTAINER;
    }
}
```

**所有 `level.scheduleTick(...)` 在客户端是 noop**——存进黑洞，永远不执行。

**为什么？** 因为：

1. **服务端权威**：游戏逻辑是服务端推进。客户端跑 scheduled tick 会与服务端不一致——客户端的中继器输出 vs 服务端的中继器输出可能差异。
2. **网络同步**：服务端的 tick 结果通过 `ClientboundBlockUpdatePacket` 发给客户端。客户端只需要应用更新 BlockState。
3. **避免重复计算**：客户端跑 scheduled tick 是浪费 CPU。

## 4.7.3 客户端不跑 random tick

类似地，`ClientLevel.tickChunk`（如果有的话）**不**调用 random tick：

```java
// 没有 ClientLevel.tickChunk —— 客户端没有 random tick 入口
```

**结果**：客户端的世界**不会自然演进**——作物不会长，树叶不会腐烂，雪不会化。

**客户端看到的"作物长高"**：

- 服务端 random tick 让作物长高 → setBlock(pos, state.cycle(AGE)) → 触发 ClientboundBlockUpdatePacket。
- 客户端收到包 → ClientLevel.setBlock 改 BlockState → chunk dirty render。
- **客户端看到的是结果，不是过程**。

## 4.7.4 客户端不跑 BlockEvent runBlockEvents

```java
// ClientLevel.tick 没有 runBlockEvents
// 客户端的 blockEvent 是收到包后立刻 triggerEvent
```

回顾 4.5.6：

```java
public void handleBlockEvent(ClientboundBlockEventPacket packet) {
    this.level.blockEvent(packet.getPos(), packet.getBlock(), packet.getParamA(), packet.getParamB());
}

// ClientLevel.blockEvent
@Override
public void blockEvent(BlockPos pos, Block block, int paramA, int paramB) {
    this.getBlockState(pos).triggerEvent(this, pos, paramA, paramB);
    // ★ 立刻执行——不进队列
}
```

**客户端 blockEvent 不延迟**——服务端发来的包立刻触发动画。

## 4.7.5 客户端 ClientLevel.tick：跑什么？

简化版客户端 tick：

```java
public class ClientLevel extends Level {
    public void tickEntities() {
        for (Entity entity : this.entitiesForRendering()) {
            if (!entity.isPassenger() && !entity.tickCount % chunkSize == 0) {
                this.tickNonPassenger(entity);
            }
        }
    }
    
    public void animateTick(int x, int y, int z) {
        // 在玩家附近的随机位置生成"环境粒子"——熔岩冒泡、火飞溅、空气粒子等
        int randomTickRadius = 16;
        int spotsPerTick = 667;
        for (int i = 0; i < spotsPerTick; i++) {
            int rx = x + this.random.nextInt(randomTickRadius * 2 + 1) - randomTickRadius;
            int ry = y + this.random.nextInt(randomTickRadius * 2 + 1) - randomTickRadius;
            int rz = z + this.random.nextInt(randomTickRadius * 2 + 1) - randomTickRadius;
            BlockState state = this.getBlockState(new BlockPos(rx, ry, rz));
            state.getBlock().animateTick(state, this, new BlockPos(rx, ry, rz), this.random);
        }
    }
    
    public void tickRainSplashing() { ... }
}
```

**客户端 tick 内容**：

- **`tickEntities`**：实体动画状态机推进（不是 AI——AI 在服务端）。
- **`animateTick`**：在玩家附近随机 667 个位置抽样，调用方块的 `animateTick` 方法生成环境粒子（如熔岩冒泡、灵魂沙的灵魂粒子、孢子绽放）。
- **`tickRainSplashing`**：下雨时随机产生雨溅粒子。
- **粒子系统**：`ParticleEngine.tick()`——已有粒子推进生命周期。
- **声音系统**：`SoundManager.tick()`——衰减、3D 定位等。
- **网络包消费**：从 Connection 队列拿包并应用。

## 4.7.6 Block.animateTick：客户端粒子专用钩子

这是个**仅客户端**的方法：

```java
// BlockBehaviour
@OnlyIn(Dist.CLIENT)
public void animateTick(BlockState state, Level level, BlockPos pos, RandomSource random) {
}
```

**重写示例**：

```java
public class LavaBlock extends LiquidBlock {
    @OnlyIn(Dist.CLIENT)
    @Override
    public void animateTick(BlockState state, Level level, BlockPos pos, RandomSource random) {
        if (random.nextInt(100) == 0) {
            // 1% 概率：在熔岩表面冒泡
            level.addParticle(ParticleTypes.LAVA, pos.getX() + random.nextDouble(), pos.getY() + 1.0, pos.getZ() + random.nextDouble(), 0, 0, 0);
            level.playLocalSound(...);
        }
    }
}
```

**这就是熔岩"冒泡 + 飞溅"的来源**——服务端不参与，纯客户端粒子。

类似的：

- `SoulSandBlock` / `SoulSoilBlock`：灵魂粒子。
- `ConduitBlock` / `BeaconBlock`：beam 光柱。
- `RedstoneTorchBlock` / `TorchBlock`：火焰粒子。

**注意**：`animateTick` 不依赖 `randomTickSpeed`——它独立的客户端调度，每帧抽 667 个位置。

## 4.7.7 客户端预测

回顾 0.3.7：客户端**预测**自己玩家的动作（移动、挖方块、放方块），等服务端确认或回滚。

**关键代码点**：

```java
// 客户端：玩家挖到方块的"破坏完成"瞬间
ServerboundPlayerActionPacket actionPacket = new ServerboundPlayerActionPacket(...);
connection.send(actionPacket);
this.level.setBlockAndUpdate(pos, AIR);     // ★ 立刻预测把方块变 air
```

客户端**不等服务端**就改 BlockState。等服务端 `ClientboundBlockChangedAckPacket` 来：

- 一致 → 客户端预测正确，确认。
- 不一致（玩家挖了禁挖方块、距离过远） → 服务端发"反向"包让客户端回滚。

## 4.7.8 partialTick 与帧间插值

客户端帧率 60-244 FPS，服务端 20 TPS。两者中间靠 **`partialTick`**（0..1 浮点）插值。

```java
// 客户端渲染期
float partialTick = (float)(System.nanoTime() - lastTickTime) / 50_000_000f;
partialTick = Mth.clamp(partialTick, 0, 1);

// 渲染实体时
double renderX = entity.lastTickX + (entity.posX - entity.lastTickX) * partialTick;
double renderY = entity.lastTickY + (entity.posY - entity.lastTickY) * partialTick;
double renderZ = entity.lastTickZ + (entity.posZ - entity.lastTickZ) * partialTick;
```

**插值字段**：每个实体有"上 tick 位置"和"当前 tick 位置"两套。渲染时按 partialTick 算中间值。

**结果**：实体看起来**丝滑**移动（即使服务端只 20 次/秒更新位置）。

## 4.7.9 客户端 chunk 加载

客户端不生成 chunk——它**接收**服务端的 chunk：

```java
// ClientPacketListener.handleLevelChunkWithLight
public void handleLevelChunkWithLight(ClientboundLevelChunkWithLightPacket packet) {
    int chunkX = packet.getX();
    int chunkZ = packet.getZ();
    LevelChunk chunk = level.getChunkSource().replaceWithPacketData(chunkX, chunkZ, packet.getChunkData(), packet.getLightData(), ...);
    if (chunk != null) {
        level.onChunkLoaded(new ChunkPos(chunkX, chunkZ));
    }
}
```

**包内容**：

- `ClientboundLevelChunkPacketData`：含整 chunk 的 BlockState palette + BitStorage（详见 Module 7）。
- `ClientboundLightUpdatePacketData`：含 sky light + block light 数据。
- BlockEntity NBT 列表。

**客户端 chunk 没有**：

- StructureStarts / StructureReferences（客户端不需要重新生成结构）。
- Tick queues（客户端不跑 tick）。
- Heightmaps（部分发送：WORLD_SURFACE 和 MOTION_BLOCKING）。

详见 Module 7。

## 4.7.10 客户端的 tick 控制

客户端的 ClientLevel 也有自己的 tick 计数：

```java
// Minecraft.runTick
public void runTick() {
    if (this.tickRateManager().isFrozen()) return;
    
    this.level.tick();         // ClientLevel.tick
    this.gui.tick();
    this.inputHandler.tick();
    this.particleEngine.tick();
    this.soundManager.tick();
    // ⋯
}
```

**`tickRateManager`** 也存在于客户端（与服务端独立）。`/tick freeze` 命令冻结服务端的 ServerLevel——但客户端不知道，会继续跑 ClientLevel.tick。**结果**：服务端冻住时客户端粒子继续动、动画继续播。

**特例**：`/tick rate <hz>` 改变服务端 tick 速度——客户端不改。客户端按 20 Hz 解释包到达。

## 4.7.11 客户端 vs 服务端的 Block 差异

某些方块的逻辑**只在服务端运行**：

```java
// CropBlock
@Override
public void randomTick(BlockState state, ServerLevel level, BlockPos pos, RandomSource random) {
    // ★ 注意 ServerLevel —— 不是 Level
    // 客户端永远不会进入这里
}
```

**`ServerLevel`** 而不是 `Level` 作参数 —— 编译期保证只在服务端用。

**反之** `animateTick(BlockState, Level, ...)` 用 `Level` —— 客户端 / 服务端理论都能调，但 `@OnlyIn(Dist.CLIENT)` 注解保证只客户端调（服务端启动时这部分代码被剥离）。

## 4.7.12 一段实战：玩家挖方块的双端时序

```
[Client tick T - render thread]
玩家鼠标按住 → ClientPlayerInteractionManager.continueDestroyBlock
  ↓ 累积破坏进度
玩家持续按 ~10 tick 后破坏完成
  ↓
1. 客户端预测：level.setBlockAndUpdate(pos, AIR)
   ClientLevel 立刻把那格变 air → 视觉上方块已消失
   触发碎块粒子（animateTick 之外的特殊粒子）
   触发破碎声音
2. 客户端发包：ServerboundPlayerActionPacket(STOP_DESTROY_BLOCK, pos, ...)

[Server tick T+0 ~ T+1 - server thread]
服务端 ServerGamePacketListener.handlePlayerAction(STOP_DESTROY_BLOCK)
  ↓
gameMode.destroyAndAck(pos, sequenceId)
  ↓
ServerLevel.setBlock(pos, AIR, UPDATE_ALL | UPDATE_INVISIBLE)
  ↓
触发 onRemove + neighborChanged + 掉落物品（如果不 SUPPRESS_DROPS）
广播 ClientboundBlockChangedAckPacket(sequenceId) 给本玩家
广播 ClientboundBlockUpdatePacket(pos, AIR) 给其他玩家

[Client tick T+1+网络延迟 - render thread]
本玩家收到 ClientboundBlockChangedAckPacket
  ↓
sequenceId 匹配 → 客户端预测被服务端确认 → 不 rollback
其他玩家收到 ClientboundBlockUpdatePacket
  ↓
ClientLevel.setBlock(pos, AIR, UPDATE_ALL) → 看到方块消失
  ↓ 触发碎块粒子（animateTick 之外）+ 声音
```

**关键点**：

- 本玩家**立刻**看到结果（客户端预测）。
- 其他玩家**延迟 ~50-100 ms** 看到结果（网络 + 1 tick）。
- 服务端**最终判定**——错误时回滚本玩家。

## 4.7.13 性能

```
客户端 ClientLevel.tick：~3-5 ms / tick
   - 实体动画：~1 ms
   - animateTick 粒子抽样：~1-2 ms
   - 粒子推进：~1 ms

服务端 ServerLevel.tick：~10-30 ms / tick（视玩家活动）
   - 内容多：方块 / 流体 / 实体 / 网络 / 调度
```

**客户端 tick 比服务端快 ~5-10 倍**——因为客户端不跑游戏逻辑。

## 4.7.14 C++ 移植

```cpp
namespace mc::client {

class ClientLevel : public Level {
public:
    // 覆盖 scheduled / fluid tick 入口为黑洞
    TickContainerAccess<Block>& getBlockTicks() override { return BlackholeTickAccess::CONTAINER; }
    TickContainerAccess<Fluid>& getFluidTicks() override { return BlackholeTickAccess::CONTAINER; }
    
    void tick() {
        tickEntities();
        animateTickRandomSpots();
        tickRainSplashing();
        // 不调 blockTicks.tick / chunkSource.tickChunk(random) / runBlockEvents
    }
    
    void animateTickRandomSpots() {
        BlockPos playerPos = getCenterPos();
        constexpr int radius = 16;
        constexpr int spots = 667;
        for (int i = 0; i < spots; i++) {
            int dx = random_.nextInt(radius * 2 + 1) - radius;
            int dy = random_.nextInt(radius * 2 + 1) - radius;
            int dz = random_.nextInt(radius * 2 + 1) - radius;
            BlockPos pos = playerPos.offset(dx, dy, dz);
            const BlockState* state = getBlockState(pos);
            state->getBlock()->animateTick(*state, *this, pos, random_);
        }
    }
    
    void blockEvent(BlockPos pos, Block* block, int paramA, int paramB) override {
        // 立刻 trigger，不进队列
        getBlockState(pos)->triggerEvent(*this, pos, paramA, paramB);
    }

private:
    XoroshiroRandomSource random_;
};

class ServerLevel : public Level {
public:
    void tick(std::function<bool()> haveTime) {
        // 12 步主循环
        // 详见 Module 4 / 0.2 节
    }
};

}
```

## 4.7.15 一句话总结

ClientLevel 与 ServerLevel 共享同一套 BlockState + Chunk 数据结构（第 1 部分），但 tick 逻辑完全不同——客户端不跑 scheduled tick / random tick / runBlockEvents（这些路径是 BlackholeTickAccess noop），只跑实体动画 / animateTick 粒子（每帧 667 个位置抽样）/ 客户端预测 / 网络包消费；服务端跑完整的 12 步 tick 主循环；客户端 tick ~3-5 ms（远快于服务端）；玩家行为通过客户端预测立刻看到结果，等服务端确认或回滚；partialTick (0..1) 让 60-244 FPS 客户端在 20 TPS 服务端的离散位置之间丝滑插值；客户端的 BlockEvent 是收到包后立即执行，不延迟。
