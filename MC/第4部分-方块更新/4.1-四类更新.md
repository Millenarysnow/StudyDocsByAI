# 4.1 四类更新机制

## 4.1.0 你将在本节学到什么

读完这一节你应当能闭着眼睛回答：

1. Minecraft 运行期"世界自身在动"由几种**性质完全不同**的更新机制驱动？
2. 把它们摆一起对比：触发源 / 处理时机 / 性能特性 / 持久化与否，每一项都说得清。
3. 看到一段代码（中继器更新 / 作物长高 / 活塞推动 / 玩家挖方块）能立刻判断"它是哪类更新"。
4. 这些更新和 0.2 节讲过的 `ServerLevel.tick` 12 步主循环各自挂在哪一步。

---

## 4.1.1 总览：4 类更新

| 类别 | 例子 | 触发 | 处理时机 | 持久化 |
|------|------|------|---------|--------|
| **Scheduled tick** | 中继器延迟、作物未来生长、火 / TNT 计时 | 代码主动 `level.scheduleTick(pos, ..., delay)` | `ServerLevel.tick` 第 6 步 `blockTicks.tick(...)` | 是（写 NBT） |
| **Random tick** | 作物自然生长、树叶腐烂、雪化、冰冻 | `randomTickSpeed` 自动抽 | `ServerLevel.tick` 第 8 步 `chunkSource.tick → tickChunk` | 否 |
| **Neighbor update** | 活塞被红石信号触发、连接性方块（栅栏）形状更新、传感器响应 | `setBlock` 同步触发（包含 `UPDATE_NEIGHBORS` flag） | **同步**——`setBlock` 调用栈内立即处理 | 否（瞬时） |
| **Block event** | 活塞推动动画、唱片机播放、信标 beam 启动 | 代码主动 `level.blockEvent(pos, block, eventId, param)` | `ServerLevel.tick` 第 9 步 `runBlockEvents` | 是（缓存到下一 tick） |

**4 类性质完全不同**——下面逐一拆开。

---

## 4.1.2 Scheduled tick：按时间排队

**核心 idea**："我希望在 N tick 之后再做某事"。

代码示例（`RepeaterBlock`）：

```java
@Override
public void neighborChanged(BlockState state, Level level, BlockPos pos, Block neighborBlock, BlockPos neighborPos, boolean movedByPiston) {
    if (state.canSurvive(level, pos)) {
        // 信号变了，但中继器要延迟才输出
        boolean isPowered = state.getValue(POWERED);
        boolean shouldPower = this.shouldTurnOn(level, pos, state);
        if (isPowered != shouldPower && !level.getBlockTicks().willTickThisTick(pos, this)) {
            int delay = state.getValue(DELAY);     // 1-4 tick
            level.scheduleTick(pos, this, delay);
        }
    }
}

@Override
public void tick(BlockState state, ServerLevel level, BlockPos pos, RandomSource random) {
    // 延迟到了，正式更新输出
    boolean isPowered = state.getValue(POWERED);
    boolean shouldPower = this.shouldTurnOn(level, pos, state);
    if (isPowered != shouldPower) {
        level.setBlock(pos, state.cycle(POWERED), Block.UPDATE_ALL);
    }
}
```

**两个钩子**：

- `neighborChanged`：信号变化时**调度**（schedule）一次延迟 tick。
- `tick`（也叫 scheduled tick）：到时间后**真正**更新输出。

**为什么需要这套延迟**？

1. 中继器物理上就是"延迟器"——玩家看到的视觉一致性。
2. 防止信号循环——A→B→A 的红石电路如果 instant 更新会无限递归。
3. 让单 tick 内逻辑确定——一 tick 内的多次信号变化在 N tick 后**最终**结果稳定。

**典型用例**：

| 方块 | 用途 | 延迟 |
|------|------|------|
| `RepeaterBlock` | 信号延迟 | 1-4 tick（玩家配置）|
| `ComparatorBlock` | 信号比较 | 2 tick（固定） |
| `RedstoneTorchBlock` | 火把开关 | 2 tick（防抖动） |
| `TntBlock` | 引爆 | 80 tick = 4 秒 |
| `FireBlock` | 火势蔓延 | 30-40 tick 随机 |
| `CropBlock` | 不直接用 scheduled，用 random tick | — |
| `LiquidBlock` (water/lava) | 流体扩散 | 5/30 tick |

**持久化**：scheduled tick 写入 chunk NBT 的 `block_ticks` / `fluid_ticks` 列表。chunk 卸载再加载后**继续等待剩余延迟**。

## 4.1.3 Random tick：随机抽样

**核心 idea**："每 tick 在每个 chunk section 内**随机抽 N 格**，看抽到的方块是不是想 tick"。

回顾 0.2.6：

```java
// ServerLevel.tickChunk
for (LevelChunkSection section : chunk.getSections()) {
    if (section.isRandomlyTicking()) {
        for (int i = 0; i < randomTickSpeed; i++) {
            BlockPos pos = this.getBlockRandomPos(secX, secY, secZ, 15);
            BlockState state = section.getBlockState(...);
            if (state.isRandomlyTicking()) {
                state.randomTick(this, pos, this.random);
            }
            FluidState fs = state.getFluidState();
            if (fs.isRandomlyTicking()) {
                fs.randomTick(this, pos, this.random);
            }
        }
    }
}
```

**关键参数**：

- **`randomTickSpeed`** 默认 **3**（GameRule 可改）。意味着每 16³=4096 格的 section 每 tick 只抽 3 格——抽中概率 0.073%。
- **`section.isRandomlyTicking()`** 是 1.4.3 节看过的 short 计数器优化——空 section / 全石头 section 直接跳过。

**典型用例**：

| 方块 | random tick 行为 |
|------|------------------|
| `CropBlock`（小麦、胡萝卜、土豆） | age 增加 1 |
| `LeavesBlock`（树叶） | 距离树干太远 → 腐烂 |
| `SaplingBlock`（树苗） | 长成树 |
| `IceBlock` | 高温下融化为水 |
| `SnowLayerBlock` | 高温下融化 / 低温下加层 |
| `GrassBlock` / `MyceliumBlock` | 蔓延到旁边 dirt |
| `DirtBlock`（暴露的） | 草方块蔓延过来 → 变草 |
| `FireBlock` | 蔓延到旁边可燃方块 |
| `LiquidBlock` | 蒸发（沙漠水）/ 缓慢扩散 |

**特点**：

- **不持久化**——random tick 是真随机，错过就错过。chunk 卸载期间 random tick 不发生，所以离玩家远的作物不会长。
- **概率低**——平均一个作物方块每秒被 tick 0.07 × 20 = 1.4 次。一阶作物长大约 5-30 秒。
- **依赖 `randomTickSpeed`**——`/gamerule randomTickSpeed 1000` 让作物瞬间长大。

**这就是为什么作物长得"慢"+ 玩家离开后回来发现作物没长**。

## 4.1.4 Neighbor update：同步级联

**核心 idea**：方块 A 变了 → 立刻通知周围 6 邻居"我变了，你看着办"。

代码触发点：`level.setBlock(pos, newState, flags)` 内部，如果 `flags & UPDATE_NEIGHBORS != 0`：

```java
// Level.setBlock 内部（简化）
if ((flags & 1) != 0) {
    level.updateNeighborsAt(pos, newState.getBlock());
}

// updateNeighborsAt:
public void updateNeighborsAt(BlockPos pos, Block sourceBlock) {
    this.neighborUpdater.updateNeighborsAtExceptFromFacing(pos, sourceBlock, null, null);
}

// 底层调
for (Direction dir : NeighborUpdater.UPDATE_ORDER) {
    BlockPos neighborPos = pos.relative(dir);
    BlockState neighborState = level.getBlockState(neighborPos);
    neighborState.handleNeighborChanged(level, neighborPos, sourceBlock, null, false);
    // 内部最终调到目标 block 的 neighborChanged 钩子
}
```

**`UPDATE_ORDER`**（neighbor 顺序）：

```java
Direction[] UPDATE_ORDER = new Direction[]{WEST, EAST, DOWN, UP, NORTH, SOUTH};
```

**这个顺序很重要**——红石电路的某些"BUD（block update detector）"行为依赖这个固定顺序。Mojang 至今没改。

**典型用例**：

- 红石线：邻居信号变化 → 重新评估自己强度。
- 活塞：邻居方块改变 → 检查周围 redstone power → 决定推 / 缩。
- 栅栏 / 玻璃板：邻居方块改变 → 重新连接形状。
- 沙 / 砾石：邻居（下方）方块变 → 检查支撑 → 掉落。
- 草方块 → 暴露后被打成 dirt：邻居（上方）变 air → 立刻变 dirt（如果光照足够）。这其实由后续的 random tick 处理；这里指的是"shape update"。

**特点**：

- **同步**——发生在 `setBlock` 调用栈内，不进任何队列。
- **递归**——一次 setBlock 可能触发多次 setBlock 触发多次 neighbor update。1.21 的 `CollectingNeighborUpdater` 改 BFS 防爆栈（4.4 节展开）。
- **不持久化**——是"瞬时事件"。

## 4.1.5 Block event：异步副作用

**核心 idea**：某些方块需要执行"复杂副作用但不能立刻执行"——延迟到下一 tick 的第 9 步。

代码触发：

```java
// 玩家给活塞红石信号
level.blockEvent(pos, this, EVENT_PUSH, direction.ordinal());

// blockEvent 实际上是把 BlockEventData 加进队列
public void blockEvent(BlockPos pos, Block block, int eventId, int eventParam) {
    BlockEventData data = new BlockEventData(pos, block, eventId, eventParam);
    this.pendingBlockEvents.add(data);
}
```

下一 tick 的第 9 步：

```java
// ServerLevel.tick 第 9 步
if (flag) this.runBlockEvents();

// runBlockEvents:
private void runBlockEvents() {
    BlockEventData event;
    while ((event = this.pendingBlockEvents.poll()) != null) {
        BlockState state = this.getBlockState(event.pos());
        if (state.is(event.block())) {
            state.handleBlockEvent(this, event.pos(), event.eventId(), event.eventParam());
        }
    }
}
```

**典型用例**：

- **活塞推动**（最经典）：当活塞 receive 信号 → 不能立刻推（推动会触发其他 setBlock 触发更多 neighbor update 触发递归 setBlock 爆栈）。改为发 BlockEvent → 下一 tick 第 9 步统一处理。
- **唱片机播放**：放唱片 → 发 BlockEvent → 客户端听到音乐启动。
- **信标启动 beam**：高度变化 → 发 BlockEvent → 客户端渲染光柱。
- **音符盒**：被红石激活 → 发 BlockEvent → 玩家听到音符。

**特点**：

- **延迟一 tick**——明显可见（玩家激活活塞后会感觉"卡一下"）。
- **持久化**——`pendingBlockEvents` 写入 NBT。

## 4.1.6 4 类的对比

```
┌─────────────────┬─────────────────┬────────────────┬─────────────────┐
│                 │ Scheduled tick  │ Random tick    │ Neighbor update │ Block event
├─────────────────┼─────────────────┼────────────────┼─────────────────┼──────────
│ 触发            │ 主动 schedule   │ 自动随机抽样   │ setBlock 同步触发│ 主动 fire
│ 处理时机        │ tick 第 6 步    │ tick 第 8 步    │ 调用栈内立即     │ tick 第 9 步
│ 持久化          │ 是              │ 否             │ 否              │ 是
│ 延迟            │ 配置（1-N tick）│ 概率（不确定）  │ 0 tick          │ ≥ 1 tick
│ 受 chunk 卸载  │ 暂停（恢复继续）│ 不发生         │ 不发生          │ 暂停
│ 受 randomTickSpeed │ 否           │ ★ 是            │ 否              │ 否
│ 受 tickRate    │ 是              │ 是             │ 否（同步）       │ 是
└─────────────────┴─────────────────┴────────────────┴─────────────────┴──────────
```

## 4.1.7 一个方块多种机制并用：以 RedstoneTorchBlock 为例

**红石火把**这个看似简单的方块实际上 4 类机制都用：

```java
public class RedstoneTorchBlock extends BaseTorchBlock {
    @Override
    public boolean isSignalSource(BlockState state) { return true; }
    
    @Override
    public int getSignal(BlockState state, BlockGetter level, BlockPos pos, Direction dir) {
        return state.getValue(LIT) && Direction.UP != dir ? 15 : 0;
    }
    
    @Override
    public void neighborChanged(BlockState state, Level level, BlockPos pos, ...) {
        // 1. NEIGHBOR：周围方块变了 → 自己可能要改
        if (state.getValue(LIT) == this.hasNeighborSignal(level, pos, state)) {
            // 输入 != 输出（火把应该灭 / 亮）
            if (!level.getBlockTicks().willTickThisTick(pos, this)) {
                // 2. SCHEDULED：延迟 2 tick 检查
                level.scheduleTick(pos, this, 2);
            }
        }
    }
    
    @Override
    public void tick(BlockState state, ServerLevel level, BlockPos pos, RandomSource random) {
        // 2. SCHEDULED 触发：实际改变 LIT 状态
        if (state.getValue(LIT) == this.hasNeighborSignal(level, pos, state)) {
            if (isToggleable(level, pos, this)) {
                // 防过快开关（防红石钟过快）→ 烧毁
                level.removeBlock(pos, false);
                // ...
            } else {
                level.setBlock(pos, state.cycle(LIT), Block.UPDATE_ALL);
                // 3. setBlock 触发同步 NEIGHBOR UPDATE 给周围
            }
        }
    }
    
    @Override
    public void onPlace(BlockState state, Level level, BlockPos pos, BlockState oldState, boolean isMoving) {
        // 玩家放置时也触发 neighbor update
        for (Direction dir : Direction.values()) {
            level.updateNeighborsAt(pos.relative(dir), this);
        }
    }
}
```

**没有 random tick / block event**——红石火把不需要这两类。

## 4.1.8 处理顺序回顾

`ServerLevel.tick` 的 12 步（0.2.4 节）：

```
1. worldBorder.tick                               ─┐
2. advanceWeatherCycle                            │
3. handlePlayerSleeping                           ├ 不涉及 4 类更新
4. updateSkyBrightness                            │
5. tickTime（gameTime++）                          ─┘

6. ★ blockTicks.tick(...) / fluidTicks.tick(...)    ← Scheduled tick
7. raids.tick

8. ★ chunkSource.tick → tickChunk → randomTick      ← Random tick

9. ★ runBlockEvents                                 ← Block event

10. entityTickList                                  ← entity tick (Module 4 不展开)
11. tickBlockEntities                               ← BlockEntity tick
12. entityManager.tick
```

**Neighbor update 不在主循环里**——它在 setBlock 调用栈内即时发生。可能在第 6 步的某个 scheduled tick 触发；可能在第 9 步的某个 block event 触发；甚至可能在第 10 步实体 tick 内（玩家挖方块）触发。**它是横切的**。

## 4.1.9 Tick 优先级（priority）

`scheduledTick` 有一个额外字段 `TickPriority`：

```java
public enum TickPriority {
    EXTREMELY_HIGH(-3), VERY_HIGH(-2), HIGH(-1), NORMAL(0), LOW(1), VERY_LOW(2), EXTREMELY_LOW(3);
    
    public final int value;
}
```

调用：

```java
level.scheduleTick(pos, block, delay, TickPriority.HIGH);
```

**用途**：同一 tick 触发的多个 scheduled tick 按 priority 排序。例：红石火把烧毁优先于普通火把切换。

**默认 NORMAL**。Mojang 用得不多——大部分 scheduledTick 不指定 priority。

## 4.1.10 一个易混淆点：subtick

`scheduleTick` 的内部实现里还有一个 **`subTickCount`**：

```java
// LevelTicks.scheduleTick
public void schedule(ScheduledTick<T> tick) {
    ScheduledTick<T> withSubtick = new ScheduledTick<>(
        tick.type(), tick.pos(), tick.triggerTick(), tick.priority(), this.tickCount.getAndIncrement()
    );
    // ...
}
```

**`subTickCount`** 是个全局原子计数器——每个 scheduled tick 取一个独一无二的"子 tick 序号"。同 (triggerTick, priority) 下，subTickCount 小的先执行。

**作用**：保证完全确定的执行顺序——即使两个 scheduled tick 完全同 triggerTick + priority，仍按"先 schedule 的先执行"。这对**红石电路的可重现性**至关重要。

---

## 4.1.11 一句话总结

Minecraft 运行期"世界自身在动"由 4 类性质完全不同的机制驱动：**Scheduled tick**（按时间排队，处理时机 ServerLevel.tick 第 6 步，持久化）—— 红石中继器、TNT 计时、流体扩散；**Random tick**（自动随机抽样，第 8 步，不持久化，受 randomTickSpeed 控制）—— 作物生长、树叶腐烂、雪化；**Neighbor update**（setBlock 调用栈内同步触发，递归式扩散，1.21 改用 BFS 防爆栈）—— 红石信号传播、栅栏连接形状；**Block event**（主动 fire 后下一 tick 第 9 步执行，持久化）—— 活塞推动、唱片机播放。同一个方块（如红石火把）可能同时用其中 3 类。
