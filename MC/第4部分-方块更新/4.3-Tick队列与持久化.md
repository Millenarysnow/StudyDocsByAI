## 4.3.1 ScheduledTick：record 5 字段

打开 `net.minecraft.world.ticks.ScheduledTick`：

```java
public record ScheduledTick<T>(
    T type,                  // Block 或 Fluid 实例（不是 BlockState！）
    BlockPos pos,
    long triggerTick,        // 该 tick 应被处理的绝对 game time
    TickPriority priority,   // -3..3
    long subTickOrder        // 全局递增计数器，保证 tie-break 确定性
) {
    public static final Comparator<ScheduledTick<?>> DRAIN_ORDER = (a, b) -> {
        int t = Long.compare(a.triggerTick, b.triggerTick);
        if (t != 0) return t;
        int p = a.priority.compareTo(b.priority);
        return p != 0 ? p : Long.compare(a.subTickOrder, b.subTickOrder);
    };
    
    public static final Strategy<ScheduledTick<?>> UNIQUE_TICK_HASH = ...;
}
```

**5 个字段**：

- **`type`**：要 tick 的 Block 或 Fluid（singleton）。`BlockTicks<Block>` 用 Block，`FluidTicks<Fluid>` 用 Fluid。
- **`pos`**：BlockPos。注意 record 构造时调 `pos.immutable()` 转为 immutable BlockPos——避免后续被修改。
- **`triggerTick`**：绝对 game time（不是 delta）。"我希望在 game time = T 时被处理"。
- **`priority`**：tie-break 用，TickPriority enum。默认 NORMAL（0）。
- **`subTickOrder`**：全局原子递增——同 (triggerTick, priority) 时按 subTickOrder 升序处理。**确保完全确定的执行顺序**。

### DRAIN_ORDER：排序键

```java
Comparator: (triggerTick, priority, subTickOrder)  → 字典序升序
```

PriorityQueue 用这个 comparator——队头是"应当下一个处理的 tick"。

### UNIQUE_TICK_HASH

```java
hashCode = pos.hashCode() * 31 + type.hashCode()
equals   = (a.type == b.type) && a.pos.equals(b.pos)
```

**用于去重**：同一 (pos, type) 的多次 schedule 只保留**第一次**。例如玩家快速点几次按钮，按钮的方块 schedule 多次，最终只一次 tick。

## 4.3.2 LevelChunkTicks：单 chunk tick 队列

打开 `net.minecraft.world.ticks.LevelChunkTicks`（行 20-30）：

```java
public class LevelChunkTicks<T> implements SerializableTickContainer<T>, TickContainerAccess<T> {
    private final Queue<ScheduledTick<T>> tickQueue = new PriorityQueue<>(ScheduledTick.DRAIN_ORDER);
    @Nullable private List<SavedTick<T>> pendingTicks;
    private final Set<ScheduledTick<?>> ticksPerPosition = new ObjectOpenCustomHashSet<>(ScheduledTick.UNIQUE_TICK_HASH);
    @Nullable private BiConsumer<LevelChunkTicks<T>, ScheduledTick<T>> onTickAdded;
}
```

**3 个核心字段**：

- **`tickQueue`** ：`PriorityQueue` 按 DRAIN_ORDER 排序。**队头是应当下一个处理的 tick**。
- **`ticksPerPosition`**：`HashSet` 按 UNIQUE_TICK_HASH 去重。**任何 (pos, type) 同时只一个 tick 在队列中**。
- **`pendingTicks`**：从 NBT 加载但未"绑定"到 game time 的 ticks（下面 4.3.4 解释）。

**核心 API**：

```java
public void schedule(ScheduledTick<T> tick) {
    if (this.ticksPerPosition.add(tick)) {     // 去重：已有则丢弃
        this.tickQueue.add(tick);
        if (this.onTickAdded != null) onTickAdded.accept(this, tick);
    }
}

public ScheduledTick<T> poll() {
    ScheduledTick<T> tick = this.tickQueue.poll();
    if (tick != null) this.ticksPerPosition.remove(tick);
    return tick;
}

public boolean hasScheduledTick(BlockPos pos, T type) {
    return this.ticksPerPosition.contains(ScheduledTick.probe(type, pos));
}
```

**`onTickAdded`** 是回调——`LevelTicks`（外层）注册它，让自己的全局优先索引同步更新。

**为什么去重**？因为 redstone / fluid 等子系统经常在同一 tick 内多次 `scheduleTick(samePos, ...)`——只保留一次。

## 4.3.3 LevelTicks：world 级聚合

`net.minecraft.world.ticks.LevelTicks` 是 `ServerLevel` 持有的"全 world tick 调度器"：

```java
public class LevelTicks<T> implements LevelTickAccess<T> {
    private final LongPredicate tickCheck;
    private final Supplier<ProfilerFiller> profiler;
    private final Long2ObjectMap<LevelChunkTicks<T>> allContainers = new Long2ObjectOpenHashMap<>();
    private final Long2LongMap nextTickForContainer = ...;       // 每 chunk 下一次 tick 时间
    private final PriorityQueue<LevelTicks.ContainerProvider<T>> containersToTick = new PriorityQueue<>(...);
    private final Queue<ScheduledTick<T>> toRunThisTick = new ArrayDeque<>();
    private final List<ScheduledTick<T>> alreadyRunThisTick = ...;
    private final Set<ScheduledTick<?>> toRunThisTickSet = ...;
    private final BiConsumer<LevelChunkTicks<T>, ScheduledTick<T>> chunkScheduleUpdater = ...;
    
    public LevelTicks(LongPredicate tickCheck, Supplier<ProfilerFiller> profiler) {
        this.tickCheck = tickCheck;
        this.profiler = profiler;
    }
    
    public void addContainer(ChunkPos pos, LevelChunkTicks<T> ticks) {
        long longPos = pos.toLong();
        this.allContainers.put(longPos, ticks);
        ticks.setOnTickAdded(this.chunkScheduleUpdater);
        this.updateContainerScheduling(longPos);
    }
    
    public void tick(long gameTime, int budget, BiConsumer<BlockPos, T> ticker) {
        // 1. 从所有 chunk 收集"现在该 tick 的"
        // 2. 按 DRAIN_ORDER 排序
        // 3. 限制 budget 内 dispatch
    }
}
```

**核心数据结构**：

- **`allContainers`** : 所有 chunk 的 LevelChunkTicks 集合（按 ChunkPos.long key）。
- **`nextTickForContainer`** : 每 chunk 下一次最早 triggerTick 缓存——避免每 tick 扫所有 chunk。
- **`containersToTick`** : 按"下一次 trigger 时间"排序的 PQ，让每 tick 只查最早的几 chunk。
- **`tickCheck`** : `LongPredicate`，判断"这个 chunk 是否在 ticking 范围内"——超出 simulation distance 的 chunk 不 tick。
- **`toRunThisTickSet`** : 当前 tick 已经收集但未执行的 ticks，**用于支持新 schedule 时检查"我已经被本 tick 处理过吗"**。

### tick 主入口

```java
public void tick(long gameTime, int budget, BiConsumer<BlockPos, T> ticker) {
    // 1. 收集本 tick 应处理的 ticks
    this.collectTicksToRun(gameTime);
    
    // 2. 按确定顺序处理
    this.runCollectedTicks(budget, ticker);
}

private void collectTicksToRun(long gameTime) {
    while (!containersToTick.isEmpty()) {
        ContainerProvider<T> top = containersToTick.peek();
        if (top.minScheduledTick > gameTime) break;     // 还没到时间
        
        // 从该 container 取出 ≤ gameTime 的 ticks
        LevelChunkTicks<T> chunk = top.ticks;
        ScheduledTick<T> tick;
        while ((tick = chunk.peek()) != null && tick.triggerTick() <= gameTime) {
            if (this.tickCheck.test(top.chunkPos)) {     // 在 ticking 范围内
                chunk.poll();
                this.toRunThisTick.add(tick);
                this.toRunThisTickSet.add(tick);
            } else {
                break;     // 跳过 distant chunk
            }
        }
        
        containersToTick.poll();
        // 重新计算 minScheduledTick 入队
        if (chunk.peek() != null) {
            top.minScheduledTick = chunk.peek().triggerTick();
            containersToTick.add(top);
        }
    }
}

private void runCollectedTicks(int budget, BiConsumer<BlockPos, T> ticker) {
    int processed = 0;
    while (processed < budget) {
        ScheduledTick<T> tick = this.toRunThisTick.poll();
        if (tick == null) break;
        this.toRunThisTickSet.remove(tick);
        ticker.accept(tick.pos(), tick.type());     // ★ 真正执行
        this.alreadyRunThisTick.add(tick);
        processed++;
    }
    
    // 未处理完的 → 下次再处理（或者按 budget 直接丢弃，详见 4.8）
    
    // 清理"本 tick 已运行"集合，给下次准备
    this.alreadyRunThisTick.clear();
}
```

**关键点**：

1. **`budget = 65536`**——`ServerLevel.tick` 第 6 步传入。单 tick 处理上限。
2. **未处理完的 ticks 推到下一 tick**——不丢失。
3. **chunk 范围检查**：超出 simulation distance 的 chunk 跳过，但不丢弃 tick——chunk 进入范围后继续处理。

## 4.3.4 SavedTick：持久化形式

打开 `net.minecraft.world.ticks.SavedTick`：

```java
public record SavedTick<T>(T type, BlockPos pos, int delay, TickPriority priority) {
    private static final String TAG_ID = "i";
    private static final String TAG_X = "x";
    private static final String TAG_Y = "y";
    private static final String TAG_Z = "z";
    private static final String TAG_DELAY = "t";
    private static final String TAG_PRIORITY = "p";
    
    public static final Hash.Strategy<SavedTick<?>> UNIQUE_TICK_HASH = ...;
    
    public static <T> Codec<SavedTick<T>> codec(Codec<T> typeCodec) { ... }
    
    public ScheduledTick<T> unpack(long gameTime, long subTickOrder) {
        return new ScheduledTick<>(this.type, this.pos, gameTime + (long)this.delay, this.priority, subTickOrder);
    }
}
```

**SavedTick 是 ScheduledTick 的"磁盘版本"**：

- 没有 `subTickOrder`（重启后重新分配）。
- 用 **`delay`** 而不是 `triggerTick`（绝对时间）——因为存档与游戏时间绑定，迁移到新世界时需要相对时间。

**字段对应**：

```
ScheduledTick {type, pos, triggerTick, priority, subTickOrder}
       │
       │ ScheduledTick.toSavedTick(currentGameTime)
       ▼
SavedTick {type, pos, delay = triggerTick - currentGameTime, priority}
       │
       │ SavedTick.unpack(currentGameTime, newSubTickOrder)
       ▼
ScheduledTick {type, pos, triggerTick = currentGameTime + delay, priority, subTickOrder}
```

**Codec**：

```java
public static <T> Codec<SavedTick<T>> codec(Codec<T> typeCodec) {
    return RecordCodecBuilder.create(b -> b.group(
        typeCodec.fieldOf("i").forGetter(SavedTick::type),
        Codec.INT.fieldOf("x").forGetter(t -> t.pos.getX()),
        Codec.INT.fieldOf("y").forGetter(t -> t.pos.getY()),
        Codec.INT.fieldOf("z").forGetter(t -> t.pos.getZ()),
        Codec.INT.fieldOf("t").forGetter(SavedTick::delay),
        TickPriority.CODEC.fieldOf("p").forGetter(SavedTick::priority)
    ).apply(b, ...));
}
```

**NBT 形式**：

```json
{
    "i": "minecraft:repeater",
    "x": 100, "y": 64, "z": 100,
    "t": 3,                        // delay tick
    "p": 0                          // priority
}
```

每个 chunk 的 `block_ticks` / `fluid_ticks` 字段是一个 ListTag<CompoundTag> 含若干 SavedTick。

## 4.3.5 chunk 加载时的"pendingTicks → 队列绑定"

回顾 LevelChunkTicks 构造：

```java
public LevelChunkTicks(List<SavedTick<T>> savedTicks) {
    this.pendingTicks = savedTicks;
    for (SavedTick<T> saved : savedTicks) {
        this.ticksPerPosition.add(ScheduledTick.probe(saved.type(), saved.pos()));
    }
}
```

**chunk 从 NBT 加载时**：

1. 读出 `List<SavedTick<T>>` 放入 `pendingTicks`。
2. 注册占位到 `ticksPerPosition`（让 hasScheduledTick 立刻能查）。
3. **不立刻塞 PriorityQueue**——因为还没绑定到 game time。

`LevelTicks.addContainer` 时绑定：

```java
public void addContainer(ChunkPos pos, LevelChunkTicks<T> ticks) {
    if (ticks.pendingTicks != null) {
        // 绑定 pendingTicks 到当前 game time
        for (SavedTick<T> saved : ticks.pendingTicks) {
            ScheduledTick<T> realTick = saved.unpack(this.gameTime, this.nextSubTickOrder.getAndIncrement());
            ticks.scheduleUnchecked(realTick);
        }
        ticks.pendingTicks = null;
    }
    this.allContainers.put(pos.toLong(), ticks);
    // ⋯
}
```

**这是为什么 SavedTick 用 delay 而不是 triggerTick**——重启后 game time 起始可能不同，不能简单复用旧 triggerTick。

## 4.3.6 ProtoChunkTicks：worldgen 期的简化版

worldgen 期的 chunk 也可能 schedule tick——但它们还不能立刻执行，因为 chunk 不在 ticking 主循环。

`ProtoChunkTicks<T>`（在 `net.minecraft.world.ticks` 包）：

```java
public class ProtoChunkTicks<T> implements TickContainerAccess<T>, SerializableTickContainer<T> {
    private final List<SavedTick<T>> ticks = new ArrayList<>();
    private final Set<SavedTick<?>> ticksPerPosition = new HashSet<>(SavedTick.UNIQUE_TICK_HASH);
    
    @Override
    public void schedule(ScheduledTick<T> tick) {
        SavedTick<T> saved = tick.toSavedTick(0L);     // delay 直接用 triggerTick（worldgen 期为 0）
        if (this.ticksPerPosition.add(saved)) {
            this.ticks.add(saved);
        }
    }
    
    @Override
    public boolean hasScheduledTick(BlockPos pos, T type) {
        return this.ticksPerPosition.contains(...);
    }
}
```

**简单的 List**——不需要 PriorityQueue。chunk 升级到 LevelChunk 时，所有 ticks 转移到 LevelChunkTicks 里：

```java
// LevelChunk 升级构造（1.5.6）
this.blockTicks = new LevelChunkTicks<>(protoChunk.getBlockTicks().scheduledTicks());
```

## 4.3.7 完整生命周期

```
[Worldgen 期]
ProtoChunk.blockTicks = ProtoChunkTicks<Block>     ← 简单 List
  ↓ chunk 升级到 FULL
LevelChunk.blockTicks = LevelChunkTicks<Block>(savedTicks)
  ↓ 加入 ServerLevel
ServerLevel.blockTicks.addContainer(chunkPos, levelChunkTicks)
  ↓ pendingTicks 绑定到 game time
LevelChunkTicks.tickQueue 填满

[运行期]
某段代码 level.scheduleTick(pos, block, delay)
  ↓
LevelChunk.blockTicks.schedule(new ScheduledTick(...))
  ↓
LevelChunkTicks.tickQueue 加入 + ticksPerPosition 加入
  ↓
LevelTicks.containersToTick 重新排序

[每 tick]
ServerLevel.tick 第 6 步 blockTicks.tick(gameTime, 65536, this::tickBlock)
  ↓
collectTicksToRun(gameTime)：扫所有 chunk 找 ≤ gameTime 的
  ↓
runCollectedTicks(budget)：dispatch 到 BlockState.tick(...)
  ↓
具体 Block.tick 执行（可能 setBlock / scheduleTick / blockEvent）

[chunk 卸载]
ServerLevel.blockTicks.removeContainer(chunkPos)
LevelChunkTicks 内部的 tickQueue 转回 List<SavedTick>
通过 ScheduledTick.toSavedTick(gameTime) 转换 delay 形式
SerializableChunkData.packedTicks 持久化
ChunkSerializer.write 写到 NBT
```

## 4.3.9 性能与限额

**`LevelTicks.tick(gameTime, 65536, ...)`**：

- **65536 = 2^16**：单 tick 处理上限。`ServerLevel` 写死的常量（行 353）。
- 超出 65536 → 剩余 ticks 推到下一 tick。**不丢弃**。
- 如果连续 60+ tick 总有 ≥ 65536 个 ticks → 警告 "Ticks loss" → 慢慢累积积压。

**这就是著名的"水位炸弹"卡服**——超大水流 / 流体爆破短时间产生百万 scheduled tick。**1.13 之前没有 budget**，导致 chunk 卸载到内存后还在跑 → 服务端冻僵。1.13 引入 budget 后只是"卡，但不死"。

**实际负载**：

- 普通服务端：每 tick 几百到几千 scheduled tick。65536 budget 富裕。
- 大型 redstone 机器 / TNT 工坊：可能短时间触发 10K+。
- 极端场景（爆炸 + 大量水流）：超过 budget 是常态。

## 4.3.10 内存预算

```
单 chunk LevelChunkTicks:
- 空 chunk：~50 字节（空 PriorityQueue + 空 HashSet）
- 含 100 ticks：~6 KB（PQ entry + HashSet entry + ScheduledTick records）

视距 1024 chunks ≈ 平均 50 ticks/chunk → ~3 MB total

LevelTicks:
- allContainers map: ~30 KB
- containersToTick PQ: ~30 KB
- toRunThisTick / alreadyRunThisTick: ~10 KB peak
```

总内存可控（< 10 MB）。

## 4.3.11 C++ 移植

```cpp
namespace mc::ticks {

template<typename T>
struct ScheduledTick {
    T* type;
    BlockPos pos;
    int64_t triggerTick;
    TickPriority priority;
    int64_t subTickOrder;
    
    bool operator<(const ScheduledTick& other) const {
        if (triggerTick != other.triggerTick) return triggerTick < other.triggerTick;
        if (priority != other.priority) return priority < other.priority;
        return subTickOrder < other.subTickOrder;
    }
};

template<typename T>
struct SavedTick {
    T* type;
    BlockPos pos;
    int delay;
    TickPriority priority;
    
    ScheduledTick<T> unpack(int64_t gameTime, int64_t subTickOrder) const {
        return {type, pos, gameTime + delay, priority, subTickOrder};
    }
};

template<typename T>
class LevelChunkTicks {
public:
    void schedule(ScheduledTick<T> tick) {
        auto key = std::make_pair(tick.pos, tick.type);
        if (ticksPerPosition_.insert(key).second) {
            tickQueue_.push(tick);
            if (onTickAdded_) onTickAdded_(*this, tick);
        }
    }
    
    std::optional<ScheduledTick<T>> peek() const {
        if (tickQueue_.empty()) return std::nullopt;
        return tickQueue_.top();
    }
    
    std::optional<ScheduledTick<T>> poll() {
        if (tickQueue_.empty()) return std::nullopt;
        ScheduledTick<T> tick = tickQueue_.top();
        tickQueue_.pop();
        ticksPerPosition_.erase(std::make_pair(tick.pos, tick.type));
        return tick;
    }
    
    bool hasScheduledTick(BlockPos pos, T* type) const {
        return ticksPerPosition_.contains(std::make_pair(pos, type));
    }
    
    void setOnTickAdded(std::function<void(LevelChunkTicks&, const ScheduledTick<T>&)> cb) {
        onTickAdded_ = std::move(cb);
    }
    
    // NBT 序列化 / 反序列化

private:
    std::priority_queue<ScheduledTick<T>, std::vector<ScheduledTick<T>>, std::greater<>> tickQueue_;
    std::unordered_set<std::pair<BlockPos, T*>, PairHash> ticksPerPosition_;
    std::function<void(LevelChunkTicks&, const ScheduledTick<T>&)> onTickAdded_;
};

template<typename T>
class LevelTicks {
public:
    void tick(int64_t gameTime, int budget, std::function<void(BlockPos, T*)> ticker) {
        collectTicksToRun(gameTime);
        runCollectedTicks(budget, ticker);
    }
    
    void addContainer(ChunkPos pos, std::shared_ptr<LevelChunkTicks<T>> ticks);
    void removeContainer(ChunkPos pos);
    void schedule(BlockPos pos, T* type, int delay, TickPriority priority = TickPriority::NORMAL);

private:
    std::function<bool(int64_t)> tickCheck_;
    std::unordered_map<int64_t, std::shared_ptr<LevelChunkTicks<T>>> allContainers_;
    std::priority_queue<ContainerProvider<T>> containersToTick_;
    std::deque<ScheduledTick<T>> toRunThisTick_;
    std::unordered_set<...> toRunThisTickSet_;
    std::atomic<int64_t> nextSubTickOrder_{0};
};

}
```

**关键工程选择**：

1. **`std::priority_queue` + `std::greater<>`** 是 min-heap：top 最小。
2. **`std::unordered_set<std::pair<BlockPos, T*>>`** 替代 fastutil hash set：需要 hash 自定义。
3. **`subTickOrder` 用 `std::atomic<int64_t>`**：保证多线程下唯一性。
4. **`onTickAdded` 回调**：用 std::function 灵活注入。

## 4.3.12 一句话总结

`ScheduledTick<T>` 5 字段（type / pos / triggerTick / priority / subTickOrder）+ DRAIN_ORDER 字典序排序保证完全确定执行顺序；`LevelChunkTicks` 是单 chunk 的 PriorityQueue + HashSet 双结构（PQ 排序 + Set 去重）；`LevelTicks` 是 world 级聚合，用 minScheduledTick 缓存避免每 tick 扫所有 chunk；`ProtoChunkTicks` 是 worldgen 期简化 List 版，chunk 升级时转 LevelChunkTicks；`SavedTick` 是 NBT 持久化形式（用 delay 而非 triggerTick，跨 session 可迁移）；`ServerLevel.scheduleTick(pos, type, delay, priority)` 是入口；单 tick budget 65536，超出推到下 tick。
