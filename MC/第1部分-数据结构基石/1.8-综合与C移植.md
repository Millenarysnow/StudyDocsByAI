## 1.8.1 完整内存图：从 World 到 long[]

把第 1 部分 1.1 - 1.7 所有概念串起来：

## 1.8.2 内存预算汇总

按一个"普通地表 chunk"（多种 biome 边界、地表带树和草、地下有洞穴）估算：

| 组件 | 数量 | 单位 | 小计 |
|------|------|------|------|
| LevelChunk 对象本体（除字段） | 1 | ~200 字节 | 200 |
| sections[] 数组头 | 1 | ~50 字节 | 50 |
| LevelChunkSection 实例 | 24 | ~2500 字节 | 60 KB |
| Heightmap 实例 | 4 (运行时保留) | ~360 字节 | 1.5 KB |
| postProcessing[] | 24 | ~16 字节空 list | ~400 字节 |
| structureStarts / refs | 1 set + 1 set | ~1 KB | 1 KB |
| blockEntities map | ~5 entry | ~300 字节 / entry | 1.5 KB |
| pendingBlockEntities map | 0 | — | 0 |
| tickersInLevel map | ~3 entry | ~100 字节 / entry | 300 字节 |
| LevelChunkTicks (block + fluid) | 2 | ~2 KB / each | 4 KB |
| gameEventListeners | ~24 | ~100 字节 / entry | 2.5 KB |

**总计 ~75 KB / chunk**。

视距 12 chunk² × 14 chunk² = 168 chunk × 75 KB ≈ **13 MB**——一个客户端 chunk 内存量级。

视距 32 chunk² × 32 chunk² × server-side = 1024 chunk × 100 KB（含 BE 数据）= **~100 MB**——一个 vanilla 服务端 chunk 内存量级。

实际生产的 server 通常 chunk 数据占总进程内存的 50-70%。

## 1.8.3 关键设计决策的回顾

第 1 部分一路下来，Mojang 做了几个对**性能 / 内存 / 可移植性都至关重要的决策**：

### 决策 1：Block ↔ BlockState 分离

**好处**：
- 1100 个 Block × 平均 20 个 state ≈ 22000 个 BlockState 实例 + ~6 MB 总内存。
- chunk 里每格存"state 引用"而非"完整状态"——共享 immutable 让 == 比较合法。

**代价**：
- 启动时穷举所有 state 略慢（vanilla ~200 ms）。
- 状态空间过大时强制走 BlockEntity（额外层）。

### 决策 2：PalettedContainer 4 种 palette + BitStorage 紧凑打包

**好处**：
- 空 section 只 ~80 字节（vs 朴素 16 KB，省 200×）。
- 普通 section ~2.5 KB（vs 16 KB，省 6×）。
- 整体 chunk 内存省 80%。

**代价**：
- bit 操作常数比朴素 int 数组慢（约 2-3×），但 cache miss 减少 5-10× 抵消。
- 升级 palette 是 O(4096) 重打包，但发生概率低。

### 决策 3：ProtoChunk vs LevelChunk 分离

**好处**：
- 类型系统强制保证未生成完的 chunk 不能进 ticking 主循环。
- 生成期可并行写入，运行期单线程独占。
- 升级是 by-reference O(1) 搬迁，零拷贝代价。

**代价**：
- 多了一类 `ImposterProtoChunk` 处理"邻居已 FULL 但当前在 worldgen FEATURES" 的边界情况。

### 决策 4：Heightmap 增量 update + 6 种类型

**好处**：
- random tick / 寻路 / 阳光投射 / worldgen 都能 O(1) 查"列地表"。
- 6 种类型让"是否包括树叶 / 是否包括水"等需求各取所需。

**代价**：
- 6 个 heightmap × 每次 setBlock 都要 update。但每个 update 平均 O(1)，可接受。

### 决策 5：BlockEntity 独立于 BlockState

**好处**：
- 复杂状态不污染 BlockState 穷举。
- 大多数 chunk 数据（普通方块）受益于 BlockState 极简共享。

**代价**：
- 同步 BE.blockState 与 chunk section 内 BlockState 需要小心。
- 跨进程 / 跨版本时 BE 是序列化最复杂的部分（多版本 schema 升级）。

## 1.8.4 C++ 移植的取舍：直接照搬 vs ECS 改造

下面把第 1 部分所有结构按"是否值得改造"分类。

### 应该直接照搬的（OOP，与 Java 同构）

| 结构 | 理由 |
|------|------|
| `Block` 类型层次 | singleton，`const Block*` 共享，无需 ECS 化 |
| `BlockState` immutable 穷举 | 设计本身就最优，照搬即可 |
| `Property` / `StateDefinition` | 启动期一次性构造，运行时只读 |
| `PalettedContainer` 四 palette + BitStorage | 经过 10 年优化，照搬最稳 |
| `LevelChunkSection` 的双 PalettedContainer + 计数器 | 紧凑且热路径已最优 |
| `Heightmap` 6 种 + 增量 update | 增量算法极优，无可改进 |

**这些都是 Mojang 经过多年迭代的成熟设计**。在 C++ 里照搬 1:1，并享受到 C++ 的常数优势（zero-overhead generic、SIMD friendly、no GC pause）。

### 可考虑 ECS 改造的（SoA 受益）

| 结构 | 改造方向 |
|------|---------|
| Entity 系统（玩家、怪物、物品） | **强烈建议 ECS**——entities × ~10K 个、SoA 让 movement / collision 大幅加速 |
| `tickersInLevel` 全局表 | 可改为 ECS 的 ticker 系统组件 |
| `gameEventListenerRegistrySections` | 同上 |
| `blockTicks` / `fluidTicks` 的优先队列 | 用 lock-free MPMC 队列 + sorted bucket 替代 |

**这些 Mojang 的实现并非性能最优**——Java 的 HashMap / PriorityQueue 在 100K 元素时性能下降明显。C++ 引擎可以用更专门的数据结构。

### 不需要照搬的

| 结构 | 替代方案 |
|------|---------|
| `BlockBehaviour` 巨型行为基类 | C++ 里直接组合 `BlockProperties` 配置项，不需要这层 |
| `StateHolder` 抽象 | 直接 `BlockState` 类即可，`<O, S>` 泛型在 C++ 没必要 |
| `ChunkAccess` 接口 + 多子类 | C++ 里可以合并 `ProtoChunk`/`LevelChunk` 用 enum 区分阶段，省一层虚函数 |
| `ImposterProtoChunk` 透明转发 | 设计技巧 + 视图类即可（C++ 没有 sealed interface 的限制） |
| `Holder<T>` 间接引用 | C++ 直接用 `T*` 或 `std::reference_wrapper<T>`，不需要 enum 包装 |
| `DataFixerUpper` 跨版本迁移 | 第一版可以不实现，只支持当前版本格式 |

## 1.8.5 C++ 工程蓝图（最小可行）

namespace mc::chunk {
    template<typename T>
    class Palette {
    public:
        virtual ~Palette() = default;
        virtual int32_t idFor(const T& value) = 0;
        virtual const T& valueFor(int32_t id) const = 0;
        virtual int size() const = 0;
    };
    
    class BitStorage {
    public:
        virtual ~BitStorage() = default;
        virtual int get(int idx) const = 0;
        virtual void set(int idx, int value) = 0;
        virtual int getAndSet(int idx, int value) = 0;
        virtual int bits() const = 0;
        virtual int size() const = 0;
    };
    
    class SimpleBitStorage : public BitStorage { /* magic-number divide */ };
    class ZeroBitStorage : public BitStorage { /* always 0 */ };
    
    template<typename T> class SingleValuePalette : public Palette<T> { ... };
    template<typename T> class LinearPalette : public Palette<T> { ... };
    template<typename T> class HashMapPalette : public Palette<T> { ... };

    template<typename T>
    class PalettedContainer {
    public:

            // 配置：bits → palette factory

            }
            std::unique_ptr<Palette<T>> makePalette(int bits, const IdMap<T>* idMap) const;
        };
        
        static const Strategy SECTION_STATES;
        static const Strategy SECTION_BIOMES;

        void writeNetwork(ByteBuf& buf) const;

        Strategy strategy_;
        std::unique_ptr<Palette<T>> palette_;

    };

## 1.8.7 性能 targets

把 1:1 复刻的 C++ 实现和 vanilla Java 比较，应该能达到：

| 指标 | Java（vanilla） | C++（理想） | 说明 |
|------|---------------|-----------|------|
| `setBlockState` | ~50 ns | ~20 ns | 主要省 GC + JIT inline |
| `getBlockState` | ~10 ns | ~3 ns | 少一层 virtual call |
| chunk 全局序列化 | ~5 ms | ~1 ms | SIMD pack + 并发 |
| chunk 反序列化 | ~3 ms | ~0.8 ms | 同上 |
| 1000 chunk 全 random tick | ~20 ms | ~3-5 ms | 关键热点 |
| 内存占用 / chunk | ~100 KB | ~40-50 KB | 没有对象头开销，flat_map 替代 HashMap |

如果你的实现达到这些 target，已经超越 Mojang 了。如果没达到，多半是有些地方还在用虚函数 / shared_ptr / unordered_map 时不够紧凑。

1. **如果你想"先把世界存起来再说"**：去第 2 部分。容易、自包含、给你一个看得见摸得着的产出（能导出 .mca 文件）。
2. **如果你想"先看看 worldgen 怎么把世界凭空造出来"**：去第 3 部分。最有趣，也是 Mojang 最复杂的子系统，但你需要最长的耐心。
3. **如果你想"先让世界活起来"**：去第 4 部分。讲方块更新机制，能给你一个 vanilla 风格的"放置 → tick → 状态变化"完整故事。

无论你去哪，回头查阅本部分都很方便：每节末尾的一句话总结涵盖了关键概念。

## 1.8.10 一句话总结

第 1 部分把"chunk 在内存里到底长什么样"完整拆开：1.1-1.2 的 Block + BlockState 给出"方块类型 vs 方块状态"分离；1.3 的 PalettedContainer 用 4 种 palette + BitStorage 把 chunk 内存压到原本 1/6；1.4 的 LevelChunkSection 把 BlockState + Biome 双 PalettedContainer + 三个计数器组合成最小可 tick 单位；1.5 的 ChunkAccess 层次让 worldgen 期与运行期类型分离；1.6 的 6 种 Heightmap 提供 O(1) 列地表查询；1.7 的 BlockEntity 把"复杂状态"从 BlockState 穷举里独立出来；1.8 给出完整 C++ 工程蓝图与移植路线。所有后续模块（NBT 存档、地形生成、方块更新、红石、流体、网络）都建立在这套数据结构之上。
