# 1.3 Palette 编码与压缩存储

## 1.3.0 你将在本节学到什么

读完这一节你应当能闭着眼睛回答：

1. 一个 16×16×16 的 chunk section 有 4096 个格子。如果每格存一个 `BlockState` 引用要 4 字节 = 16 KB / section。Mojang 用什么机制把它压到平均 ~512 字节？
2. SingleValue / Linear / HashMap / Global 这四种 Palette 各自的内存模型是什么？什么时候自动从一种切到另一种？
3. `PalettedContainer.Strategy.SECTION_STATES` 和 `SECTION_BIOMES` 的差别是什么？为什么 biome 用 4³ = 64 而不是 16³ = 4096？
4. `BitStorage` 把 4096 个 `int` 索引压到一个 `long[]` 里，每格用动态 bit width。这种 packed bit array 的位运算是什么？为什么 `SimpleBitStorage` 里有一张 192 个常量的 MAGIC 表？
5. 一份 chunk section 在网络包 / NBT / 内存中的三种格式有什么差别？为什么不能直接 mmap 内存当存档？
6. 我在 C++ 里要复现 PalettedContainer，最小可行设计 + SIMD 加速思路是什么？

## 1.3.1 问题：朴素方案的成本

回顾上一节的结论：

- 全 vanilla 共有约 26000 个 BlockState。
- 每个 BlockState 在 `BLOCK_STATE_REGISTRY` 里有一个全局整数 ID。

最朴素的"chunk section 内每格存一个 BlockState"实现：

```cpp
// 朴素方案 A：每格存指针
const BlockState* states[16][16][16];   // 4096 × 8B = 32 KB / section

// 朴素方案 B：每格存全局 ID（int）
int32_t states[16][16][16];             // 4096 × 4B = 16 KB / section
```

按主世界 24 个 section / chunk × 视距 32×32 chunk ≈ 1000 chunk = **24000 个 section**：

| 方案 | 每 section | 总内存 |
|------|-----------|--------|
| A 指针 | 32 KB | **750 MB** |
| B 全局 ID | 16 KB | **375 MB** |

吃不消。

**关键观察**：一个普通 section 里 BlockState 的**多样性极低**——

- 海里某一段：可能 100% 都是 water。**1 种**。
- 地下深处某一段：可能 99% stone + 一点点煤矿铁矿。**5-10 种**。
- 地表某一段：可能 dirt / grass / oak_log / oak_leaves / dandelion / tall_grass / air / water 等。**10-30 种**。
- 极复杂如村庄某一段：可能 50-100 种不同 BlockState。

**4096 个格子里实际只有 1-100 种不同 BlockState 出现**。这意味着：每格不需要 16 bits（一万多种）也不需要 32 bits（全局）—— 用一个 **section-local 的小调色盘**配 **3-7 bit 的下标**就够了。

这就是 Palette 编码的核心思想：

```
section-local palette:  [oak_log, stone, dirt, grass_block, air]
                          0       1      2      3            4
indices: [4, 4, 4, 4, 1, 1, 1, 1, 2, 2, 3, 3, ...]   ← 每格 3 bit (因为 5 种 < 2^3 = 8)
```

**5 种** BlockState 用 **3 bit / 格** = 4096 × 3 / 8 = **1536 字节 / section**，10× 压缩。

## 1.3.2 PalettedContainer 的总结构

`PalettedContainer<T>` 的核心字段（行 29-35）：

```java
public class PalettedContainer<T> implements PaletteResize<T>, PalettedContainerRO<T> {
    private final IdMap<T> registry;                    // T 的全局 ID 映射（IdMap）
    private volatile PalettedContainer.Data<T> data;   // 实际数据
    private final PalettedContainer.Strategy strategy;  // SECTION_STATES 或 SECTION_BIOMES
    private final ThreadingDetector threadingDetector;
}

static final class Data<T> {
    final Configuration<T> configuration;   // 当前的 palette 类型 + bit 宽
    final BitStorage storage;               // 所有 4096 个下标的 packed long[]
    final Palette<T> palette;                // 实际的 palette 实例
}
```

**三个核心组件**：

1. **`Palette<T>`**：调色盘，"local id ↔ T" 的双向映射（小尺寸时 4 种实现切换）。
2. **`BitStorage`**：4096 个 local id 的紧凑数组。
3. **`Strategy`**：定义"section 体积是多少格"以及"local id 量在不同区间用哪种 palette"。

PalettedContainer 是 BlockState **和** Biome 共用的同一份代码——`<T>` 参数让它泛型化。section 内：

- `PalettedContainer<BlockState> states`（4096 格）。
- `PalettedContainerRO<Holder<Biome>> biomes`（64 格 = 4×4×4 体素）。

## 1.3.3 Strategy：定义体积与 palette 切换阈值

`PalettedContainer.Strategy` 是个 sealed 抽象类，只有两个实例（行 352-372）：

```java
public static final PalettedContainer.Strategy SECTION_STATES = new PalettedContainer.Strategy(4) {
    @Override
    public <A> PalettedContainer.Configuration<A> getConfiguration(IdMap<A> idMap, int bits) {
        return switch (bits) {
            case 0       -> new Configuration(SINGLE_VALUE_PALETTE_FACTORY, bits);
            case 1, 2, 3, 4 -> new Configuration(LINEAR_PALETTE_FACTORY, 4);   // 永远 4 bits
            case 5, 6, 7, 8 -> new Configuration(HASHMAP_PALETTE_FACTORY, bits);
            default     -> new Configuration(GLOBAL_PALETTE_FACTORY, Mth.ceillog2(idMap.size()));
        };
    }
};

public static final PalettedContainer.Strategy SECTION_BIOMES = new PalettedContainer.Strategy(2) {
    @Override
    public <A> PalettedContainer.Configuration<A> getConfiguration(IdMap<A> idMap, int bits) {
        return switch (bits) {
            case 0    -> new Configuration(SINGLE_VALUE_PALETTE_FACTORY, bits);
            case 1, 2, 3 -> new Configuration(LINEAR_PALETTE_FACTORY, bits);
            default -> new Configuration(GLOBAL_PALETTE_FACTORY, Mth.ceillog2(idMap.size()));
        };
    }
};
```

**Strategy 的两个职责**：

### 1. 定义体积（`sizeBits`）

```java
private final int sizeBits;
public int size() { return 1 << this.sizeBits * 3; }
```

- `SECTION_STATES`：sizeBits=4，size = 1 << 12 = **4096**（16×16×16）。
- `SECTION_BIOMES`：sizeBits=2，size = 1 << 6 = **64**（4×4×4）。

为什么 biome 是 4×4×4 = 64？因为玩家只能感知 ~10m 尺度的气候差异，1m 精度对 biome 是浪费。每 4³ block 共享同一 biome 即可。

### 2. 定义 bit 宽 → palette 类型映射

`getConfiguration(idMap, bits)` 是这套机制最微妙的部分。`bits` = 当前需要的下标 bit 宽度（决定能装多少种）。

**SECTION_STATES**：

| 当前需要 bits | 用哪个 Palette | 实际 BitStorage 用 bits | 能存几种 |
|--------------|---------------|------------------------|---------|
| 0 | SingleValuePalette | 0 | 1 种 |
| 1 / 2 / 3 / 4 | LinearPalette | **永远 4** | 1-16 种 |
| 5 / 6 / 7 / 8 | HashMapPalette | 当前 bits | 17-256 种 |
| 9+ | GlobalPalette | ~15 (log2(BlockState 总数)) | 全部 BlockState |

**注意 `case 1, 2, 3, 4 → 4`** —— 1-4 bit 的需求都映射到固定 4 bit。**这是协议规定**：服务端发给客户端的 chunk 数据按这个固定阶梯，避免每次 BitStorage 重新分配。最小有效大小是 4 bit（也意味着 1 种以内退化到 SingleValuePalette）。

**bits 的来源**：当 palette 里项数从 N 变成 N+1，需要的 bits = `Mth.ceillog2(N+1)`。一个空 section 上来 0 bits（只有 air）；放第二种方块 → 1 bit（其实存为 4 bit）→ 沿用 LinearPalette；继续放到 17 种 → 5 bits → 触发"resize"切换到 HashMapPalette；继续超出 256 种 → 切到 GlobalPalette。

**SECTION_BIOMES** 的阶梯更短（biome 比 BlockState 少得多）：

| 当前需要 bits | 用哪个 Palette | bits | 能存几种 |
|--------------|---------------|------|---------|
| 0 | SingleValuePalette | 0 | 1 种 |
| 1 / 2 / 3 | LinearPalette | 当前 bits | 2-8 种 |
| 4+ | GlobalPalette | ~7 | 全部 biome |

## 1.3.4 SingleValuePalette：1 种 BlockState 的极致情形

打开 `net.minecraft.world.level.chunk.SingleValuePalette`：

```java
public class SingleValuePalette<T> implements Palette<T> {
    private final IdMap<T> registry;
    @Nullable private T value;          // 唯一的那个值（可能未初始化）
    private final PaletteResize<T> resizeHandler;
    
    @Override
    public int idFor(T value) {
        if (this.value == null || this.value == value) {
            this.value = value;
            return 0;
        } else {
            return this.resizeHandler.onResize(1, value); // 自动升级
        }
    }
    
    @Override
    public T valueFor(int id) {
        if (id != 0 || this.value == null) throw ...;
        return this.value;
    }
}
```

**只持有 1 个值**。所有 4096 个格子都是那个值。

**BitStorage 不需要任何 bit**——配套用的是 `ZeroBitStorage`：

```java
public class ZeroBitStorage implements BitStorage {
    public int get(int index) { return 0; }
    public void set(int index, int v) { /* 啥也不做 */ }
    public int getAndSet(int index, int v) { return 0; }
    public int size();
    public int getBits() { return 0; }
    public long[] getRaw() { return new long[0]; }
}
```

**完整的 SingleValuePalette + ZeroBitStorage 组合内存开销：~80 字节**（一个对象头 + 一个引用）。

**典型场景**：海洋深处（全 water）、虚空之上（全 air）、大型矿洞内（全 air 或 cave_air）。

写入第二种方块时触发 `onResize(1, newValue)` → PalettedContainer 看到 → 创建一个 LinearPalette 替代。

## 1.3.5 LinearPalette：≤ 16 种的"小数组"实现

打开 `net.minecraft.world.level.chunk.LinearPalette`：

```java
public class LinearPalette<T> implements Palette<T> {
    private final IdMap<T> registry;
    private final T[] values;          // 长度 = 1 << bits
    private final PaletteResize<T> resizeHandler;
    private final int bits;
    private int size;
    
    @Override
    public int idFor(T value) {
        for (int i = 0; i < this.size; i++) {
            if (this.values[i] == value) {                  // ★ == 比较，因为 BlockState 共享
                return i;
            }
        }
        // 没找到，加进去
        int newId = this.size;
        if (newId < this.values.length) {
            this.values[newId] = value;
            this.size++;
            return newId;
        } else {
            return this.resizeHandler.onResize(this.bits + 1, value); // 升级到 HashMap
        }
    }
    
    @Override
    public T valueFor(int id) {
        if (id < 0 || id >= this.size) throw ...;
        return this.values[id];
    }
}
```

**`values[]` 长度永远是 `1 << bits`**——SECTION_STATES 时 bits 永远 4，所以数组永远 16 大。

**`idFor` 是 O(N) 线性扫描**。但 N ≤ 16，且 `==` 比较是单条指令，比 hashmap 快很多。

**典型场景**：地表正常 chunk section（10-15 种 BlockState）、矿洞掺杂（5-12 种）。这是**最常用的 Palette 类型**，覆盖 vanilla 80% 以上的 chunk section。

**`==` 比较合法的关键**：因为 BlockState 是 immutable 共享实例（1.2 节）。如果你尝试自己 new 一个属性相同但不同实例的 BlockState 塞进来，会导致 palette 把它当不同 entry，浪费下标。**永远不要 new BlockState**。

## 1.3.6 HashMapPalette：17-256 种的中等情形

打开 `net.minecraft.world.level.chunk.HashMapPalette`：

```java
public class HashMapPalette<T> implements Palette<T> {
    private final IdMap<T> registry;
    private final CrudeIncrementalIntIdentityHashBiMap<T> values;   // ★
    private final PaletteResize<T> resizeHandler;
    private final int bits;
    
    @Override
    public int idFor(T value) {
        int i = this.values.getId(value);
        if (i == -1) {
            i = this.values.add(value);
            if (i >= 1 << this.bits) {
                i = this.resizeHandler.onResize(this.bits + 1, value);
            }
        }
        return i;
    }
}
```

**`CrudeIncrementalIntIdentityHashBiMap`** 是 Mojang 自家的 "对象 ↔ int ID" 双向 hashmap，专门优化 add-only / 不删除场景：
- `getId(T)` 用 IdentityHashMap 风格的 `==` 比较查找。
- `add(T)` 自增分配 int ID。
- `byId(int)` 返回数组 `[]` 元素。

**典型场景**：村庄复杂区域、jigsaw 结构边界、mod 大量替换 vanilla 方块。bits = 5 (32 entries) 到 8 (256 entries)。

**bits 越大 BitStorage 也越宽**：5 bit / 格 → 4096 格 × 5 bit / 8 = **2560 字节 / section**。

## 1.3.7 GlobalPalette：> 256 种的兜底

打开 `net.minecraft.world.level.chunk.GlobalPalette`：

```java
public class GlobalPalette<T> implements Palette<T> {
    private final IdMap<T> registry;
    
    @Override
    public int idFor(T value) {
        int i = this.registry.getId(value);
        return i == -1 ? 0 : i;
    }
    
    @Override
    public T valueFor(int id) {
        T t = this.registry.byId(id);
        if (t == null) throw ...;
        return t;
    }
}
```

**没有 local palette 字段**——直接用全局 `BLOCK_STATE_REGISTRY` 的 ID 当 BitStorage 索引。

**bits 固定为** `Mth.ceillog2(BLOCK_STATE_REGISTRY.size())` ≈ **15 bits**（vanilla 26000 ≤ 2^15 = 32768）。

**典型场景**：异常 chunk 含多种 mod block / 测试场景 / debug 模式。**vanilla 几乎用不到**。

**bits = 15 → 4096 × 15 / 8 = 7680 字节 / section**——比 SingleValue 大 96 倍。

## 1.3.8 升级链：自动从轻到重切换

`PalettedContainer.onResize`（行 109-116）：

```java
@Override
public int onResize(int newBits, T value) {
    PalettedContainer.Data<T> data = this.data;
    PalettedContainer.Data<T> data1 = this.createOrReuseData(data, newBits);
    data1.copyFrom(data.palette, data.storage);     // ★ 重新打包数据
    this.data = data;
    return data1.palette.idFor(value);
}
```

升级流程：

```
1. 当前 palette 满了（如 LinearPalette 4 bit 满 16 种）。
2. idFor 调 resizeHandler.onResize(newBits, value)。
3. PalettedContainer.onResize 创建一个新 Data：
   - 新 Configuration（如 5 bits → HashMapPalette）。
   - 新 BitStorage（5 bits / 格）。
   - 新 Palette。
4. data1.copyFrom：把旧的 palette + storage 解包，按新 palette 的 idFor 重新打包到新 storage。
5. 把新 value 加进新 palette，返回它的 newId。
6. 替换 this.data。
```

**这是个 O(4096 + |oldPalette|) 操作**，相对昂贵。但发生频率很低（一个 section 通常生命周期内只升级 0-2 次）。

**注意 PalettedContainer 没有"降级"机制**——如果你把 17 种 BlockState 减到 5 种，palette 不会自动从 HashMapPalette 退回 LinearPalette。**只有重新存档加载时**才会从最紧凑表示重启动（pack/unpack 流程）。

## 1.3.9 BitStorage：把 N×bits 个 int 塞进 long[]

`Palette` 解决了"把 4096 个 BlockState 引用变成 4096 个小 int 索引"。`BitStorage` 解决"把 4096 个小 int 紧密打包到 long[]"。

接口（`net.minecraft.util.BitStorage`）：

```java
public interface BitStorage {
    int getAndSet(int index, int value);
    void set(int index, int value);
    int get(int index);
    long[] getRaw();
    int getSize();
    int getBits();
    void getAll(IntConsumer consumer);
    void unpack(int[] out);
    BitStorage copy();
}
```

主要实现：

- **`SimpleBitStorage`**：通用实现。本节主菜。
- **`ZeroBitStorage`**：0 bits 时用，所有 get 返回 0。
- **`PalettedContainer.Data`** 内置的 storage 类型由 Configuration 决定。

### SimpleBitStorage 的内存布局

```
size = 4096, bits = 5

每个 long 64 位：可装 ⌊64 / 5⌋ = 12 个值，剩余 4 bit 浪费（不跨 long 边界，**对齐**）。
共需 ⌈4096 / 12⌉ = 342 个 long = 2736 字节。

values per long = 64 / bits  (向下取整)
total longs    = ceil(size / valuesPerLong)

每个值占用 long 内的位段：
long[k]:  ┌──── 64 bit ──────┐
          [v0][v1][v2]...[v11][padding 4 bit]
           5   5   5         5
```

**为什么对齐而不跨 long 边界？** 跨边界要做"先读两个 long 再拼"的逻辑，慢且不友好 SIMD。Mojang 选择牺牲少量空间（每个 long 浪费 0-3 bit），换取每个 get/set 永远只碰一个 long。

### get/set 的实现

```java
@Override
public int get(int index) {
    long[] raw = this.raw;
    long longIdx = (long)index * (long)this.divideMul + (long)this.divideAdd;
    int j = (int)(longIdx >> 32 >> this.divideShift);    // 第几个 long
    int k = (index - j * this.valuesPerLong) * this.bits;
    return (int)(raw[j] >> k & this.mask);
}
```

**`j = index / valuesPerLong`** 应该用整数除法，但**整数除法慢**（10+ 周期）。Mojang 用 **divide-by-multiplication**：把除法转换成"乘以一个常数 + 移位"。这就是 SimpleBitStorage 顶部那个 192 个常量的 MAGIC 表的来历：

```java
private static final int[] MAGIC = new int[]{
    -1, -1, 0,
    Integer.MIN_VALUE, 0, 0,
    1431655765, 1431655765, 0,        // bits=2: divisor=32, magic=1431655765=0x55555555
    Integer.MIN_VALUE, 0, 1,
    858993459, 858993459, 0,           // bits=4: divisor=16, magic=858993459=0x33333333
    715827882, 715827882, 0,
    613566756, 613566756, 0,
    Integer.MIN_VALUE, 0, 2,
    ...
};
```

每 3 个 int 一组：`MAGIC[3*divisor + 0/1/2]` 是 (mul, add, shift)。给定 `divisor = 16`（即 bits=4，每 long 16 个值 ❌ 实际是 12+4 padding，bits=5 时是 12 等），`get` 通过 `index * mul + add >> 32 >> shift` 计算"对应第几个 long"。

这是一种叫 **Hacker's Delight unsigned division by constant** 的技巧。除法由编译期已知的 magic number 转换为乘法 + 移位。**对热路径是大幅加速**。

C++ 标准库 `<numeric>` 没有内置这个，但 GCC / Clang 在 `divisor` 是常量时会自动应用。Mojang 的 Java 编译器不做这个优化，所以手动表化。

### set 的实现

```java
@Override
public void set(int index, int value) {
    int j = this.cellIndex(index);                      // 与 get 同样的 magic 除法
    long current = this.raw[j];
    int k = (index - j * this.valuesPerLong) * this.bits;
    this.raw[j] = current & ~(this.mask << k) | ((long)value & this.mask) << k;
}
```

读出旧 long → 用 mask 把目标位段清零 → 把 value 按 bit 位移入 → 写回。

整段 set 是 **5-10 个 ALU 指令**，无分支、无除法、无内存额外访问。**这是 chunk write 性能的核心**。

## 1.3.10 BitStorage 的实际尺寸表

固定 4096 entries 时：

| bits | 每 long 装几个 | 需要几个 long | 字节数 | 用法 |
|------|---------------|--------------|--------|------|
| 0 | ∞ | 0 | 0 | ZeroBitStorage（SingleValuePalette） |
| 4 | 16 | 256 | 2048 | LinearPalette（最常见） |
| 5 | 12 | 342 | 2736 | HashMapPalette 起步 |
| 6 | 10 | 410 | 3280 | HashMapPalette |
| 7 | 9 | 456 | 3648 | HashMapPalette |
| 8 | 8 | 512 | 4096 | HashMapPalette 极限 |
| 15 | 4 | 1024 | 8192 | GlobalPalette（含 padding） |

**vanilla 平均一个 section ≈ 2400 字节**（含 palette 对象本身）—— 比朴素的 16 KB **省 6.7×**。

视距 32 chunk² × 24 section / chunk × 2.4 KB = **~60 MB** 替代了原本的 ~400 MB。

## 1.3.11 索引计算：3D 坐标 → 1D index

`Strategy.getIndex`（行 383-385）：

```java
public int getIndex(int x, int y, int z) {
    return (y << this.sizeBits | z) << this.sizeBits | x;
}
```

代入 SECTION_STATES（sizeBits = 4）：

```
index = (y << 4 | z) << 4 | x
      = y * 256 + z * 16 + x
```

**布局是 Y-major、Z-mid、X-minor**。也就是说同一 X 行的格子在 BitStorage 里**相邻**。

**为什么这个顺序？** 几个工程理由：

1. **垂直访问 Y 跨度大**：相邻 Y 索引差 256（跨 ~16 个 long）。这对"扫描某一列"不友好。
2. **水平访问 X / Z 局部性好**：扫一整行 X 只跨一个 long（Linear/Hash palette 时 4-8 bit/格，16 格 / long）。
3. **匹配 chunk 渲染遍历**：天空光从顶向下扫扫描线，水平片段批处理。

**网络协议、NBT 存档、ProtoChunk → LevelChunk 转换都用同一个 Y-Z-X 顺序**。**这是协议层硬约定**，不能换。

C++ 移植时**不要**自作聪明用 X-major：协议层的 BitStorage 字节序就是 Y-Z-X，你乱了就解析不动 vanilla 存档。

## 1.3.12 序列化：网络 / NBT / 内存三种格式

PalettedContainer 同时要支持：

1. **运行时**：尽量快、尽量紧凑。当前实现就是上面讲的 Strategy 自动切换。
2. **网络**：发给客户端时，需要客户端能立刻 deserialize。**协议固定**：1 字节 bits + palette VarInt 列表 + LongArray BitStorage。
3. **NBT 存档**：写盘格式。**版本兼容**：用 BlockState 的 namespace string 而不是任何 int ID。

### 网络格式（`PalettedContainer.write` 行 188-197）

```java
@Override
public void write(FriendlyByteBuf buf) {
    this.acquire();
    try {
        this.data.write(buf);  // 写 1 byte bits + palette + long[] storage
    } finally {
        this.release();
    }
}
```

`Data.write`（实际方法位于 PalettedContainer 内部 Data 类）：

```java
buf.writeByte(this.storage.getBits());     // 1 byte: bit 宽
this.palette.write(buf);                    // VarInt count + count × VarInt entries
buf.writeLongArray(this.storage.getRaw());  // VarInt longCount + longCount × i64
```

**一个 SECTION_STATES + LinearPalette(5 entries, 4 bits)** 的 section 网络包大小：

```
1 byte  bits=4
1 byte  palette VarInt count = 5
5×~1 byte palette entries (BlockState IDs 通常 < 128)  ≈ 5 bytes
1 byte  longArray VarInt count = 256
256×8   long array                                   = 2048 bytes
                                                      ─────
                                                       ~2060 bytes
```

平均一整个 chunk = 24 section × 2 KB ≈ 48 KB。视距 8 chunk × 32 chunk × 32 chunk = 1024 chunk → 50 MB 网络流量。这是 Mojang 的 chunk packet 实际带宽量级。

### NBT 格式（`pack` 行 236-262）

```java
@Override
public PalettedContainerRO.PackedData<T> pack(IdMap<T> idMap, Strategy strategy) {
    HashMapPalette<T> hashmap = new HashMapPalette<>(idMap, this.data.storage.getBits(), this.dummyPaletteResize);
    int size = strategy.size();
    int[] expanded = new int[size];
    this.data.storage.unpack(expanded);

    // 把 storage 中的 local id 重映射到一个新的、紧凑的 hashmap palette
    swapPalette(expanded, idx -> hashmap.idFor(this.data.palette.valueFor(idx)));

    int newBits = strategy.calculateBitsForSerialization(idMap, hashmap.getSize());
    Optional<LongStream> longs;
    if (newBits != 0) {
        SimpleBitStorage rebuilt = new SimpleBitStorage(newBits, size, expanded);
        longs = Optional.of(Arrays.stream(rebuilt.getRaw()));
    } else {
        longs = Optional.empty();
    }

    return new PalettedContainerRO.PackedData<>(hashmap.getEntries(), longs);
}
```

**NBT 格式总是先重打包到一个紧凑的 HashMapPalette**——不管运行时是哪种 palette。这保证存档总是最紧凑的形式。

NBT 内的 chunk section（节选）：

```
{
    Y: 5b,
    block_states: {
        palette: [
            { Name: "minecraft:air" },
            { Name: "minecraft:stone" },
            { Name: "minecraft:oak_log", Properties: { axis: "y" } }
        ],
        data: [L; <1024 个 long>]
    },
    biomes: {
        palette: [ "minecraft:plains", "minecraft:forest" ],
        data: [L; <2 个 long>]
    },
    BlockLight: <2048 字节 ByteArray>,
    SkyLight: <2048 字节 ByteArray>
}
```

注意 NBT 里 palette 项不是字符串而是**完整的 BlockState 描述**（namespace + Properties）。每加载一次都要 deserialize 回 BlockState 实例。

后面 Module 2 会展开 NBT 格式的细节。

## 1.3.13 线程安全

`PalettedContainer` 用 `ThreadingDetector` 而不是 `synchronized`：

```java
private final ThreadingDetector threadingDetector = new ThreadingDetector("PalettedContainer");

public void acquire() { this.threadingDetector.checkAndLock(); }
public void release() { this.threadingDetector.checkAndUnlock(); }
```

`ThreadingDetector` 是个**断言式的并发检测器**：调用 `acquire` 时记录线程，下次调用 `release` 验证是同一线程。开发模式（IS_RUNNING_IN_IDE）下违反断言抛异常；正式模式下 noop。

**这是因为 Mojang 设计上 PalettedContainer 不应被多线程并发访问**——chunk 由单一线程拥有（生成时是 worldgen 线程，运行时是服务端 server thread，客户端是客户端 chunk 队列）。如果你看到并发崩溃，多半是有人没遵守 chunk 线程归属。

`acquire / release` 像极了"动态 single-threaded 验证"。

## 1.3.14 一个完整时序：从 air 起步、放方块、升级 palette

模拟一个新生成的 chunk section 演化：

```
状态 0：刚 new LevelChunkSection
  states = SingleValuePalette(AIR), ZeroBitStorage(4096 = all 0)
  内存：~80 字节

执行 setBlockState(0, 0, 0, STONE):
  1. SingleValuePalette.idFor(STONE)
     - 当前 value 是 AIR ≠ STONE
     - 调 onResize(1, STONE)
  2. PalettedContainer.onResize:
     - 新 Configuration: bits=1 → 但 SECTION_STATES 1-4 都映射到 LinearPalette(4 bit)
     - 新 BitStorage: SimpleBitStorage(4 bit, 4096) = 256 long = 2048 字节
     - copyFrom: 把所有 4096 格的 AIR 用新 LinearPalette 重打包（AIR 在新 palette 里 id=0）
     - 把 STONE 加入 LinearPalette → id=1
  3. 数据写入 storage[0] = 1
  内存：~2300 字节

继续放 15 种不同 BlockState:
  LinearPalette 还没满（16 容量），每次 idFor 线性扫描，O(15)。
  内存不变（仍 4 bit 阶梯）。

放第 17 种 BlockState：
  1. LinearPalette.idFor 扫完没找到，size = 16 == values.length = 16
  2. 调 onResize(5, newValue)
  3. PalettedContainer.onResize:
     - 新 Configuration: bits=5 → HashMapPalette(5 bit)
     - 新 BitStorage: SimpleBitStorage(5 bit, 4096) = 342 long = 2736 字节
     - copyFrom: 4096 格全部从 4-bit 索引重打包成 5-bit 索引
  4. HashMapPalette 加入第 17 种值 → id=16
  内存：~3000 字节

继续到 257 种：
  HashMapPalette idFor 满，调 onResize(9, ...)
  实际不会到 9—— SECTION_STATES 的 case 9+ 直接跳到 GLOBAL_PALETTE
  新 BitStorage: SimpleBitStorage(15 bit, 4096) = 1024 long = 8192 字节
  GlobalPalette 不存任何 entry，直接走全局 BLOCK_STATE_REGISTRY
  内存：~8200 字节
```

整个升级链是**单调向上**的——一旦升级到大 palette，不会自动降回。这就是为什么 Mojang 在每次写 NBT 时都重新打包成最紧凑形式。

## 1.3.16 C++ 移植设计

```cpp
// === 接口定义 ===

template<typename T>
class IdMap {
public:
    virtual int32_t getId(const T& value) const = 0;
    virtual const T* byId(int32_t id) const = 0;
    virtual int size() const = 0;
};

template<typename T>
class Palette {
public:
    virtual ~Palette() = default;
    virtual int32_t idFor(const T& value) = 0;          // 返回 local id（满了触发 resize）
    virtual const T& valueFor(int32_t id) const = 0;
    virtual int size() const = 0;
    virtual std::unique_ptr<Palette<T>> copy() const = 0;
};

class BitStorage {
public:
    virtual ~BitStorage() = default;
    virtual int get(int index) const = 0;
    virtual void set(int index, int value) = 0;
    virtual int getAndSet(int index, int value) = 0;
    virtual int bits() const = 0;
    virtual int size() const = 0;
};

// === 4 种 Palette 实现 ===

template<typename T>
class SingleValuePalette : public Palette<T> {
    std::optional<T> value_;
    std::function<int32_t(int newBits, T)> onResize_;
};

template<typename T>
class LinearPalette : public Palette<T> {
    std::array<T, 16> values_;     // 永远 16
    int size_ = 0;
};

template<typename T>
class HashMapPalette : public Palette<T> {
    boost::container::flat_map<const T*, int32_t> idByPtr_;
    std::vector<T> byId_;
    int bits_;
};

template<typename T>
class GlobalPalette : public Palette<T> {
    const IdMap<T>* registry_;
};

// === SimpleBitStorage：紧凑 long[] ===

class SimpleBitStorage : public BitStorage {
public:
    SimpleBitStorage(int bits, int size, std::vector<uint64_t> raw = {});
    int get(int index) const override;
    void set(int index, int value) override;
    int getAndSet(int index, int value) override;
private:
    std::vector<uint64_t> raw_;
    int bits_;
    int size_;
    uint64_t mask_;            // (1 << bits) - 1
    int valuesPerLong_;        // 64 / bits
    // Magic numbers for divide-by-multiplication
    uint32_t divideMul_;
    uint32_t divideAdd_;
    int divideShift_;
};

// === 主容器 ===

template<typename T>
class PalettedContainer {
public:
    PalettedContainer(const IdMap<T>* idMap, Strategy strategy, T defaultValue);
    
    const T& get(int x, int y, int z) const {
        int idx = strategy_.getIndex(x, y, z);
        int32_t localId = data_.storage->get(idx);
        return data_.palette->valueFor(localId);
    }
    
    void set(int x, int y, int z, const T& value) {
        int idx = strategy_.getIndex(x, y, z);
        int32_t localId = data_.palette->idFor(value);
        data_.storage->set(idx, localId);
    }
    
    int32_t onResize(int newBits, const T& trigger);
    
private:
    struct Data {
        std::unique_ptr<Palette<T>> palette;
        std::unique_ptr<BitStorage> storage;
        Configuration configuration;
    };
    
    const IdMap<T>* idMap_;
    Strategy strategy_;
    Data data_;
};

// === Strategy ===

class Strategy {
public:
    static Strategy SECTION_STATES;
    static Strategy SECTION_BIOMES;
    
    int sizeBits;
    int size() const { return 1 << (sizeBits * 3); }
    
    int getIndex(int x, int y, int z) const {
        return ((y << sizeBits) | z) << sizeBits | x;
    }
    
    Configuration getConfiguration(const IdMap<auto>& idMap, int bits) const;
};
```

**关键工程选择**：

1. **`Palette<T>` 用虚函数还是 `std::variant<...>`？**
   - 虚函数：清晰，符合 OOP，分支通过 vtable。
   - variant：编译期已知所有 case，无 vtable，可被 inline，快 2-3 倍。
   - 推荐 **variant** —— 4 种 palette 是封闭集合，不会扩展。

2. **`SimpleBitStorage` 的 magic number**：用 `<cstdint>` + 构造函数计算，不要硬表。GCC `__udiv` builtins 也可以。

3. **`LinearPalette` 的 `idFor`**：用 SIMD 比较 16 个指针。AVX2 `_mm256_cmpeq_epi64` 一次比较 4 个，4 次循环搞定 16 槽线性扫描。

4. **`PalettedContainer.set` 不要每次走 idFor**：在批量初始化时（如 chunk 加载），先一次性把所有不同的 BlockState 加入 palette，再写 storage。这比 4096 次 set 快 5 倍。

5. **不要用 `std::unique_ptr<Palette<T>>` 包装**：考虑用 in-place storage（fixed buffer + placement new）避免堆分配。一个 chunk 24 section × 4 个 palette 实例 = 96 个堆分配，会成为热点。

## 1.3.17 实战：手算一个 section 的内存

打开本仓库 `LevelChunkSection.java` 行 41-44：

```java
public LevelChunkSection(Registry<Biome> biomes) {
    this.states = new PalettedContainer<>(
        Block.BLOCK_STATE_REGISTRY,
        Blocks.AIR.defaultBlockState(),
        PalettedContainer.Strategy.SECTION_STATES
    );
    this.biomes = new PalettedContainer<>(
        biomes.asHolderIdMap(),
        biomes.getOrThrow(Biomes.PLAINS),
        PalettedContainer.Strategy.SECTION_BIOMES
    );
}
```

新创建一个 section 时：

- `states`：SingleValuePalette(AIR) + ZeroBitStorage(4096) ≈ **80 字节**。
- `biomes`：SingleValuePalette(PLAINS) + ZeroBitStorage(64) ≈ **80 字节**。
- 两个 short 计数器：6 字节。
- 对象头 + 字段：~50 字节。

**新 section 总占用：~220 字节**。

放第一个 STONE：states 升级到 LinearPalette + SimpleBitStorage(4 bit, 4096) ≈ 2 KB。biomes 不动（仍 80 B）。

**这就是为什么"虚空之上一片 air 的 chunk"几乎不吃内存**——空 section 只有 ~200 字节。

## 1.3.18 一句话总结

`PalettedContainer<T>` = `Palette<T>`（local id ↔ T 映射）+ `BitStorage`（packed long[] 索引数组）+ `Strategy`（体积 + bit 阶梯）；BlockState 用 SECTION_STATES (16³)、Biome 用 SECTION_BIOMES (4³)；palette 4 种实现按 bit 宽度自动切换 SingleValue → Linear(永远 4 bit) → HashMap(5-8 bit) → Global(15 bit)，向下不降级；`SimpleBitStorage` 用 magic number 把整除转化为乘法 + 移位提速；3D 索引 `(y << 4 | z) << 4 | x` 是 Y-Z-X major 协议硬约定；序列化时永远重新打包成 HashMapPalette 紧凑形式；空 section 仅占 ~220 字节，整套机制比朴素 int[4096] 省 ~80% 内存。
