## 1.6.1 直觉：什么是 heightmap

想象你在主世界俯视一个 16×16 的 chunk。从天空往下看，每一列你最先看到的是什么？

- 一列长着一棵橡树：最先看到的是树冠（叶子）。
- 一列是开放草地：最先看到的是草方块顶面。
- 一列是水面：最先看到的是水（如果不算在内）或水底沙子（如果算把水当透明）。
- 一列被熔岩覆盖：最先看到的是熔岩。

**heightmap 就是把这种"每列最高某种东西的 Y 坐标"存成一张 16×16 的表**。

但"某种东西"的定义不止一种——下雪要找的"地面"和怪物刷怪要找的"地面"和阳光要照射的"地面"都不一样。所以 Minecraft 维护**6 种不同的 heightmap**，每种用不同的"什么算实心 / 不透明"判断函数。

## 1.6.2 6 种 Heightmap 类型

打开 `net.minecraft.world.level.levelgen.Heightmap` 行 141-151：

```java
public static enum Types implements StringRepresentable {
    WORLD_SURFACE_WG("WORLD_SURFACE_WG", Usage.WORLDGEN, NOT_AIR),
    WORLD_SURFACE("WORLD_SURFACE", Usage.CLIENT, NOT_AIR),
    OCEAN_FLOOR_WG("OCEAN_FLOOR_WG", Usage.WORLDGEN, MATERIAL_MOTION_BLOCKING),
    OCEAN_FLOOR("OCEAN_FLOOR", Usage.LIVE_WORLD, MATERIAL_MOTION_BLOCKING),
    MOTION_BLOCKING("MOTION_BLOCKING", Usage.CLIENT, 
        s -> s.blocksMotion() || !s.getFluidState().isEmpty()),
    MOTION_BLOCKING_NO_LEAVES("MOTION_BLOCKING_NO_LEAVES", Usage.LIVE_WORLD,
        s -> (s.blocksMotion() || !s.getFluidState().isEmpty()) && !(s.getBlock() instanceof LeavesBlock));
}
```

逐一拆开。

### WORLD_SURFACE / WORLD_SURFACE_WG

**判断函数**：`NOT_AIR` —— 只要不是空气（含树叶、水、岩浆、玻璃 ⋯⋯）就算"实心"。

**含义**："最高的非空气方块的 Y + 1"。从天空往下扫，第一个不是空气的位置。

**用途**：

- 阳光投射、月光层级。
- 渲染深色昼夜过渡。
- "下界传送门定位"等需要"地表"概念的逻辑。
- worldgen 期 Surface 阶段判断"哪是地表" → 铺草 / 铺沙。

**为什么有 _WG 版？** 见 1.6.6。

### OCEAN_FLOOR / OCEAN_FLOOR_WG

**判断函数**：`MATERIAL_MOTION_BLOCKING` —— `blockstate.blocksMotion()` 为 true 才算实心。

`blocksMotion()` 由 `BlockBehaviour` 决定，简化逻辑是：实体能站立在上面 → blocks motion。**水不 blocks motion**（水可以让实体下沉），**树叶通常 blocks motion**（实体落到树叶顶上能站）。

**含义**："最高的能站立方块的 Y + 1"。换句话说"如果有水，水底地面在哪"。

**用途**：

- worldgen Aquifer 找"地下水位线"。
- 海洋纪念碑、海底神殿生成。
- 鱼类刷怪。

### MOTION_BLOCKING

**判断函数**：`s -> s.blocksMotion() || !s.getFluidState().isEmpty()` —— 要么本身 blocksMotion，要么有流体（水或岩浆）也算。

**含义**："最高的实心或液体的 Y + 1"。换句话说"实体落下时第一个会被阻挡的位置"。

**用途**：

- 实体着陆点判断。
- 刷怪算法找平台。
- 雪降落判断。
- **客户端发送**——这是客户端最常用的 heightmap，渲染需要它。

### MOTION_BLOCKING_NO_LEAVES

**判断函数**：和 MOTION_BLOCKING 相同，**但**树叶（`LeavesBlock`）不算。

**含义**："忽略树叶层的实体落点"。树叶顶上其实能站，但很多生成 / AI 逻辑希望忽略它们（因为树是"装饰"不是"地面"）。

**用途**：

- 闪电劈击的"地面"判断（劈不到树叶）。
- 某些刷怪条件（不在树冠上刷）。
- worldgen 时找"真正的地面"。

## 1.6.3 Usage：三种使用场景

每个 heightmap type 还携带一个 `Usage` 标签：

```java
public static enum Usage {
    WORLDGEN,    // 仅 worldgen 期使用，FULL 状态后丢弃
    LIVE_WORLD,  // 运行期使用，但不发给客户端
    CLIENT;      // 发送给客户端
}
```

**完整对照表**：

| Heightmap Type | 判断函数 | Usage | 是否发客户端 |
|----------------|---------|-------|-------------|
| WORLD_SURFACE_WG | NOT_AIR | WORLDGEN | 否 |
| WORLD_SURFACE | NOT_AIR | CLIENT | **是** |
| OCEAN_FLOOR_WG | blocksMotion | WORLDGEN | 否 |
| OCEAN_FLOOR | blocksMotion | LIVE_WORLD | 否 |
| MOTION_BLOCKING | blocksMotion ∨ fluid | CLIENT | **是** |
| MOTION_BLOCKING_NO_LEAVES | blocksMotion ∨ fluid，去树叶 | LIVE_WORLD | 否 |

**只有 2 种 heightmap 发给客户端**：WORLD_SURFACE 和 MOTION_BLOCKING。这两个是渲染 / 客户端预测必需的最小集合。

`Types.sendToClient()`（行 168）就是这个判断：

```java
public boolean sendToClient() {
    return this.usage == Heightmap.Usage.CLIENT;
}
```

`Types.keepAfterWorldgen()`（行 172）：

```java
public boolean keepAfterWorldgen() {
    return this.usage != Heightmap.Usage.WORLDGEN;
}
```

WORLDGEN 类型在 ChunkStatus 推进到 FULL 时会被丢弃（节省内存）。

## 1.6.4 数据结构：BitStorage 打包 256 个高度值

```java
public class Heightmap {
    private final BitStorage data;
    private final Predicate<BlockState> isOpaque;
    private final ChunkAccess chunk;

    public Heightmap(ChunkAccess chunk, Heightmap.Types type) {
        this.isOpaque = type.isOpaque();
        this.chunk = chunk;
        int bits = Mth.ceillog2(chunk.getHeight() + 1);    // 主世界 = 9
        this.data = new SimpleBitStorage(bits, 256);       // 256 = 16×16 列
    }
}
```

**256 个高度值**，每个用 `bits` 位。

**`bits = ceil(log2(height + 1))`**：主世界 height = 384，`ceil(log2(385)) = 9`。这是因为高度值范围是 [0, height]（从最底到最顶高度，含两端），需要表达 height+1 种值。

**注意 heightmap 存的是 "** 距离最低层的偏移 **"，不是绝对 Y**！

```java
private int getFirstAvailable(int packedIdx) {
    return this.data.get(packedIdx) + this.chunk.getMinY();   // ★ 加上 minY
}

private void setHeight(int x, int z, int absoluteY) {
    this.data.set(getIndex(x, z), absoluteY - this.chunk.getMinY());   // ★ 减去 minY
}
```

**为什么用相对偏移？** 因为 1.18 之后 minY 可以是 -64（甚至维度自定义），用绝对 Y 需要 10 bit 才能表达 [-64, 320]，相对偏移只要 9 bit。**省一位**。

**总内存**：256 × 9 bit / 8 = 288 字节 + SimpleBitStorage 对象头 = ~320 字节 / heightmap。一个 chunk 6 个 heightmap = ~2 KB。

**索引函数**（行 137-139）：

```java
private static int getIndex(int x, int z) {
    return x + z * 16;
}
```

`(x, z)` ∈ [0, 16) → 索引 [0, 256)。布局是 **Z-major**（z 在高位），与 BlockPos 的 X-Z 习惯**不同**——但因为是 chunk-local 16×16，对外不暴露这个差别。

## 1.6.5 update：高效增量更新

`update(x, y, z, newState)`（行 76-103）是热路径。每次 `setBlockState` 都会触发 6 次 update（每个 heightmap 一次）。它必须**避免全列重扫**。

```java
public boolean update(int x, int y, int z, BlockState newState) {
    int firstAvailable = this.getFirstAvailable(x, z);  // 当前列的"最高 + 1"

    if (y <= firstAvailable - 2) {
        return false;     // ① 改的位置在已知地表下方很多，不影响 heightmap
    }

    if (this.isOpaque.test(newState)) {
        // ② 新方块是 opaque
        if (y >= firstAvailable) {
            this.setHeight(x, z, y + 1);   // 直接抬高 firstAvailable
            return true;
        }
        // 在已知地表下方但是 opaque：旧方块不可能更高，noop
    } else if (firstAvailable - 1 == y) {
        // ③ 新方块是 transparent，刚好删掉了"原来的地表"
        // 必须从 y-1 向下重扫找新的地表
        BlockPos.MutableBlockPos cursor = new BlockPos.MutableBlockPos();
        for (int j = y - 1; j >= this.chunk.getMinY(); j--) {
            cursor.set(x, j, z);
            if (this.isOpaque.test(this.chunk.getBlockState(cursor))) {
                this.setHeight(x, z, j + 1);
                return true;
            }
        }
        this.setHeight(x, z, this.chunk.getMinY());     // 全空，触底
        return true;
    }
    return false;
}
```

**三种情况**：

1. **改在地表深处下方**：noop。最常见，因为大部分世界改动在地表附近，但绝大多数方块更新发生在更深处（如矿洞建造）—— 更深处的更改对 heightmap 无影响。
2. **新方块是 opaque 且在地表上方或同位**：直接抬高。O(1)。
3. **新方块是 transparent 且刚好破坏了原地表**：必须向下扫直到找到新的 opaque 方块。**最坏 O(height)**，但概率低（只在你恰好挖掉地表那一格才发生）。

**这个增量算法是 heightmap 性能的灵魂**。如果每次 setBlock 都全列重扫，主世界 16×16×384 列 = 384 次方块查询，乘 6 个 heightmap = 2304 次 / setBlock —— 不可接受。增量算法平均 O(1)。

## 1.6.6 为什么 _WG 版本：worldgen 期的临时副本

回到 `WORLD_SURFACE` vs `WORLD_SURFACE_WG` 的差别。

**问题**：worldgen 流水线（Module 3）会在不同阶段反复修改 chunk 数据：

- NOISE 阶段先填基础地形。此时"地表"是 stone 顶。
- SURFACE 阶段铺草、沙、雪。此时"地表"变了。
- CARVERS 阶段挖洞穴。地表不变（不挖到地面）。
- FEATURES 阶段长树、矿。地表（含树冠）抬高。

如果整个 worldgen 用同一份 heightmap，每一步都要更新它—— Worldgen 流程上各种 feature 的"放在最高的草方块上"判断会读到中间状态。

**Mojang 的解法**：对**worldgen-only** 的查询，用 `_WG` 版（`WORLDGEN` usage）。FULL 状态时把它丢弃，运行时只保留非 _WG 版（`LIVE_WORLD` 或 `CLIENT`）。

这也是为什么 Heightmap 有 `keepAfterWorldgen()` 标志。

`ChunkStatus.FULL.heightmapsAfter()` 是个 EnumSet，只含 `LIVE_WORLD` 和 `CLIENT` 用途的 4 种 heightmap。`ChunkStatus.heightmapsAfter()` 是个常用过滤器，决定哪些 heightmap 在升级阶段保留。

## 1.6.7 primeHeightmaps：批量初始化

worldgen 的 NOISE 阶段填完一个 section 后，需要建立 heightmap 初始数据。一个 chunk 16×16 = 256 列、6 种 heightmap、每列高度搜索 384 格 → 朴素遍历 = 256 × 6 × 384 = 590336 次方块查询。

`primeHeightmaps`（行 38-74）做了高效合并：

```java
public static void primeHeightmaps(ChunkAccess chunk, Set<Heightmap.Types> typesToFill) {
    if (typesToFill.isEmpty()) return;
    
    int n = typesToFill.size();
    ObjectList<Heightmap> queue = new ObjectArrayList<>(n);
    int topY = chunk.getHighestSectionPosition() + 16;
    BlockPos.MutableBlockPos cursor = new BlockPos.MutableBlockPos();

    for (int x = 0; x < 16; x++) {
        for (int z = 0; z < 16; z++) {
            // 把所有要填的 heightmap 加入工作队列
            for (Heightmap.Types t : typesToFill) {
                queue.add(chunk.getOrCreateHeightmapUnprimed(t));
            }
            ObjectListIterator<Heightmap> iter = queue.iterator();
            
            // 从顶向下扫这一列
            for (int y = topY - 1; y >= chunk.getMinY(); y--) {
                cursor.set(x, y, z);
                BlockState state = chunk.getBlockState(cursor);
                if (!state.is(Blocks.AIR)) {
                    // 检查每个 heightmap 是否要"接受"这个方块
                    while (iter.hasNext()) {
                        Heightmap h = iter.next();
                        if (h.isOpaque.test(state)) {
                            h.setHeight(x, z, y + 1);
                            iter.remove();    // 该 heightmap 已找到地表，移出队列
                        }
                    }
                    if (queue.isEmpty()) break;     // 全部 heightmap 都已找到 → 提前终止
                    iter.back(n);                   // 重置迭代器到末尾
                }
            }
        }
    }
}
```

**关键优化**：

1. **共享列扫描**：对每个 (x, z) 列，从顶向下扫一次方块状态，所有 6 个 heightmap 同时检查。
2. **找到即移除**：一旦某个 heightmap 找到第一个 opaque 方块，从队列移出，不再参与该列剩余扫描。
3. **早停**：所有 heightmap 都找到时，跳出该列。

最坏情况仍是 O(256 × 384) = 98K 次方块查询，但因为 heightmap 通常都在地表 (y ~ 64) 附近找到，实际平均扫 ~120 格 / 列 → 256 × 120 = 30K 次查询。

## 1.6.8 序列化

`getRawData()` / `setRawData()`：

```java
public long[] getRawData() {
    return this.data.getRaw();
}

public void setRawData(ChunkAccess chunk, Heightmap.Types type, long[] raw) {
    long[] target = this.data.getRaw();
    if (target.length == raw.length) {
        System.arraycopy(raw, 0, target, 0, raw.length);
    } else {
        LOGGER.warn("Ignoring heightmap data ...");
        primeHeightmaps(chunk, EnumSet.of(type));
    }
}
```

**raw 是 long[]**——SimpleBitStorage 的内部 packed long array。一个主世界 heightmap = 256 × 9 / 64 = ⌈36⌉ × 64 bit ≈ 36 long = 288 字节。

**NBT 存档里**，每个 heightmap 用一个 LongArray 标签存：

```
{
    Heightmaps: {
        WORLD_SURFACE: [L; <36 个 long>],
        OCEAN_FLOOR:   [L; <36 个 long>],
        MOTION_BLOCKING: [L; <36 个 long>],
        MOTION_BLOCKING_NO_LEAVES: [L; <36 个 long>]
    }
}
```

WORLDGEN 用途的 _WG 版本不写盘（FULL 状态后已被丢弃）。

**网络包**（`ClientboundLevelChunkPacketData`）：只发 CLIENT usage 的 2 种（WORLD_SURFACE + MOTION_BLOCKING），共 ~600 字节。

`ChunkStatus.heightmapsAfter()` 控制升级时哪些 heightmap 被保留：

```java
// 简化
public Set<Heightmap.Types> heightmapsAfter() {
    return switch (this) {
        case BIOMES -> EnumSet.of(WORLD_SURFACE_WG, OCEAN_FLOOR_WG);
        case NOISE -> EnumSet.of(WORLD_SURFACE_WG, OCEAN_FLOOR_WG);
        case FULL -> EnumSet.of(WORLD_SURFACE, OCEAN_FLOOR, MOTION_BLOCKING, MOTION_BLOCKING_NO_LEAVES);
        // ...
    };
}
```

## 1.6.9 一段实战：玩家放方块时哪些 heightmap 被更新

场景：玩家在 (10, 64, 10) 放下一个橡木原木。原本该位置是 air，且地表在 y=63 处。

时序：

```java
ServerLevel.setBlock(pos, oakLog, UPDATE_ALL)
  → LevelChunk.setBlockState(pos, oakLog, false)
    → LevelChunkSection.setBlockState(10, 0, 10, oakLog)    // section[8] 内
      → PalettedContainer.set(10, 0, 10, oakLog)
    → 更新 6 个 heightmap:
      heightmaps[WORLD_SURFACE].update(10, 64, 10, oakLog)
      heightmaps[WORLD_SURFACE_WG].update(...)              // 已丢弃则 noop
      heightmaps[OCEAN_FLOOR].update(...)
      heightmaps[OCEAN_FLOOR_WG].update(...)                // noop
      heightmaps[MOTION_BLOCKING].update(...)
      heightmaps[MOTION_BLOCKING_NO_LEAVES].update(...)
```

实际只有 4 个 heightmap 在运行期保留（`heightmapsAfter()` 返回那 4 个）。每个 update 内部：

- WORLD_SURFACE：判断 oakLog 是 NOT_AIR → 是。新 y=64 ≥ 旧 firstAvailable=64 → setHeight(64+1=65)。✅ 更新。
- OCEAN_FLOOR：判断 oakLog blocksMotion → 是。同上 → setHeight(65)。✅
- MOTION_BLOCKING：判断 blocksMotion ∨ fluid → 是。setHeight(65)。✅
- MOTION_BLOCKING_NO_LEAVES：oakLog 不是 LeavesBlock → 走和 MOTION_BLOCKING 一样的路径 → setHeight(65)。✅

**4 次 O(1) 更新，总共 ~20 ALU 指令**。

如果换成"放橡木树叶（OAK_LEAVES）"：

- WORLD_SURFACE：NOT_AIR → 是 → 更新 65。
- OCEAN_FLOOR：blocksMotion → 是（树叶 blocks motion） → 更新 65。
- MOTION_BLOCKING：是 → 更新 65。
- MOTION_BLOCKING_NO_LEAVES：blocksMotion ∨ fluid 是，**但是 LeavesBlock**，predicate `&& !LeavesBlock` 让其返回 false → **不更新**。

注意 heightmap 的 update 函数对"非 opaque"且"不是当前地表"的情况是 noop，所以 MOTION_BLOCKING_NO_LEAVES 在该列上仍维持原 y=64 的值。

## 1.6.10 内存预算

```
Heightmap 实例:
├── 对象头                                  : 16 字节
├── BitStorage 引用                          : 8 字节
├── isOpaque (Predicate)                     : 8 字节
├── chunk (ChunkAccess 反向引用)            : 8 字节
└── SimpleBitStorage:
    ├── 对象头 + 字段                        : 32 字节
    └── raw long[36]                          : 288 字节
                                                ─────
                                              ≈ 360 字节 / heightmap

每 chunk 4 个运行期 heightmap × 360 = 1.5 KB
每 chunk + 2 个 _WG 临时 heightmap (生成期) = 2.2 KB
```

视距 1024 chunk × 1.5 KB ≈ 1.5 MB —— 微不足道。

## 1.6.11 C++ 移植

```cpp
class Heightmap {
public:
    enum class Type {
        WORLD_SURFACE_WG, WORLD_SURFACE,
        OCEAN_FLOOR_WG, OCEAN_FLOOR,
        MOTION_BLOCKING, MOTION_BLOCKING_NO_LEAVES
    };
    enum class Usage { WORLDGEN, LIVE_WORLD, CLIENT };

    struct TypeInfo {
        Type type;
        Usage usage;
        std::function<bool(const BlockState&)> isOpaque;
        const char* name;
    };
    
    static const std::array<TypeInfo, 6> ALL_TYPES;

    Heightmap(ChunkAccess* chunk, Type type)
        : chunk_(chunk), type_(type),
          bits_(intLog2Ceil(chunk->height() + 1)),
          data_(bits_, 256),
          isOpaque_(ALL_TYPES[size_t(type)].isOpaque) {}

    bool update(int localX, int absoluteY, int localZ, const BlockState& newState) {
        int firstAvail = getFirstAvailable(localX, localZ);
        if (absoluteY <= firstAvail - 2) return false;

        if (isOpaque_(newState)) {
            if (absoluteY >= firstAvail) {
                setHeight(localX, localZ, absoluteY + 1);
                return true;
            }
        } else if (firstAvail - 1 == absoluteY) {
            // 重扫
            for (int y = absoluteY - 1; y >= chunk_->minY(); y--) {
                if (isOpaque_(chunk_->getBlockState(BlockPos(localX, y, localZ)))) {
                    setHeight(localX, localZ, y + 1);
                    return true;
                }
            }
            setHeight(localX, localZ, chunk_->minY());
            return true;
        }
        return false;
    }

    int getFirstAvailable(int x, int z) const {
        return data_.get(z * 16 + x) + chunk_->minY();
    }

    void setHeight(int x, int z, int absoluteY) {
        data_.set(z * 16 + x, absoluteY - chunk_->minY());
    }

    static void primeAll(ChunkAccess& chunk, std::span<const Type> typesToFill);

    std::span<const uint64_t> rawData() const { return data_.raw(); }
    void setRawData(std::span<const uint64_t> raw);

private:
    ChunkAccess* chunk_;
    Type type_;
    int bits_;
    SimpleBitStorage data_;
    std::function<bool(const BlockState&)> isOpaque_;
};
```

**关键工程选择**：

1. **`isOpaque_` 用 `std::function` 还是 enum + switch？** 用 enum + switch 更快（避免 indirect call）。`Type` 已经是 enum，可以在判断时直接 switch：
   ```cpp
   bool isOpaque(const BlockState& s) const {
       switch (type_) {
           case Type::WORLD_SURFACE: case Type::WORLD_SURFACE_WG:
               return !s.isAir();
           case Type::OCEAN_FLOOR: case Type::OCEAN_FLOOR_WG:
               return s.blocksMotion();
           case Type::MOTION_BLOCKING:
               return s.blocksMotion() || !s.fluidState().isEmpty();
           case Type::MOTION_BLOCKING_NO_LEAVES:
               return (s.blocksMotion() || !s.fluidState().isEmpty()) && !isLeaves(s);
       }
   }
   ```
   编译器能内联，性能好 5-10×。

2. **`SimpleBitStorage` 已有**（1.3 节复用）。

3. **`chunk_` 反向引用**：用裸指针，因为 chunk 拥有 heightmap，生命周期对齐。

4. **`primeAll` 静态批量函数**：对应 Mojang 的 primeHeightmaps，是 worldgen 后期填充的入口。

5. **不要用 `std::vector<Heightmap>` 存 6 个**：用 `std::array<Heightmap, 6>` 或者把它们直接内嵌到 ChunkAccess 里（避免堆分配）。

---

## 1.6.12 一句话总结

每个 chunk 维护 6 种 heightmap（WORLD_SURFACE / OCEAN_FLOOR / MOTION_BLOCKING / MOTION_BLOCKING_NO_LEAVES + 各自的 _WG worldgen-only 版），每种用不同的"什么算实心"判断函数；存储为 16×16 = 256 个值的紧凑 BitStorage（每值 9 bit 主世界）；增量 update 平均 O(1)，仅在打掉地表那一格时重扫；2 种发给客户端（WORLD_SURFACE / MOTION_BLOCKING），4 种持久化到 NBT，2 种 _WG 版仅 worldgen 用 FULL 后丢弃；总内存约 1.5 KB / chunk，可忽略。
