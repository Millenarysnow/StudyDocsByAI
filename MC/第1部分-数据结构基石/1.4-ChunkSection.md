## 1.4.1 ChunkSection 是什么

回顾位置：

- 一个 **chunk** 是 16×16 横向、384 高的"立柱"。
- 一个 chunk 被竖直切成 24 个 16×16×16 的 **section**。
- 每个 section 是 4096 个方块格 + 64 个 biome 格 + 一些元信息。

`LevelChunkSection`（在 `net.minecraft.world.level.chunk`）就是 1 个 section 在内存里的实体。

它的职责：

1. 保存 4096 格的 BlockState（通过 1.3 节的 `PalettedContainer<BlockState>`）。
2. 保存 64 格的 biome（通过 `PalettedContainer<Holder<Biome>>`）。
3. 维护几个**计数器**（多少格非空、多少格在 random-tick），让外层快速判断"这个 section 要不要参与 tick"。
4. 提供高层 API（`getBlockState(x, y, z)` / `setBlockState(x, y, z, state)`）。
5. 支持网络包 / 存档的读写。

它**不负责**：
- 光照（在 `LevelChunk` 上）。
- BlockEntity 字典（在 `LevelChunk` 上）。
- 随机 tick 调度（在 `ServerLevel` + `LevelChunk` 上）。

`LevelChunkSection` 是个**纯数据容器**。tick 调度、光照、网络广播都在更外层。

## 1.4.3 三个 short 计数器

```java
private short nonEmptyBlockCount;   // 非空气方块数（含液体计 1 / 与空气共占的也算）
private short tickingBlockCount;    // 接受 random tick 的方块数
private short tickingFluidCount;    // 接受 random tick 的流体数
```

**为什么需要计数器？**

`ServerLevel.tickChunk`（0.2.6 节看过）每 tick 对每个加载的 chunk 跑：

```java
for (LevelChunkSection section : chunk.getSections()) {
    if (section.isRandomlyTicking()) {              // ★ 用计数器快速 short-circuit
        // ... random tick
    }
}
```

如果没有计数器，每 tick 要扫 4096 格判断"是不是有 random-ticking 方块"——那是 24 section × 4096 = **每 chunk 每 tick 9.8 万次方块查询**，乘上加载半径 1024 chunk = **每 tick 1 亿次查询**。无法承受。

有了计数器，`isRandomlyTicking()` 退化为：

```java
public boolean isRandomlyTicking() {
    return this.isRandomlyTickingBlocks() || this.isRandomlyTickingFluids();
}
public boolean isRandomlyTickingBlocks() { return this.tickingBlockCount > 0; }
public boolean isRandomlyTickingFluids() { return this.tickingFluidCount > 0; }
```

**3 条 ALU 指令**。99% 的 section（地下深处、虚空、海洋）都跳过——0 个 random-ticking 方块。

类似地：

- `hasOnlyAir() = nonEmptyBlockCount == 0` —— 让 chunk 网络序列化时跳过空 section。
- `isRandomlyTickingBlocks()` / `isRandomlyTickingFluids()` 分别判块 / 流体。

**为什么用 `short` 不用 `byte`？** section 4096 格，单个 byte（256）放不下。`short` 32767 够用，省一半空间相对 `int`。

## 1.4.4 计数器的维护：setBlockState 内部

打开 `LevelChunkSection.setBlockState`（行 66-99）。这是计数器更新的**唯一**入口（除了 `recalcBlockCounts` 全量重算）：

```java
public BlockState setBlockState(int x, int y, int z, BlockState newState, boolean acquireLock) {
    BlockState oldState;
    if (acquireLock) {
        oldState = this.states.getAndSet(x, y, z, newState);   // 走 ThreadingDetector
    } else {
        oldState = this.states.getAndSetUnchecked(x, y, z, newState);
    }

    FluidState oldFluid = oldState.getFluidState();
    FluidState newFluid = newState.getFluidState();

    // 减去旧的
    if (!oldState.isAir()) {
        this.nonEmptyBlockCount--;
        if (oldState.isRandomlyTicking()) {
            this.tickingBlockCount--;
        }
    }
    if (!oldFluid.isEmpty()) {
        this.tickingFluidCount--;
    }

    // 加上新的
    if (!newState.isAir()) {
        this.nonEmptyBlockCount++;
        if (newState.isRandomlyTicking()) {
            this.tickingBlockCount++;
        }
    }
    if (!newFluid.isEmpty()) {
        this.tickingFluidCount++;
    }

    return oldState;
}
```

**原子性**：注意整个流程是"先在 PalettedContainer 里 swap → 再更新计数器"。如果中间抛异常，会得到不一致状态。Mojang 假设 `getAndSet` 不抛异常（PalettedContainer 内部确保），所以全流程不显式 try/catch。

**注意**：

1. `oldState.isAir()` 和 `newState.isAir()` 都检查——意味着"air → air"是 noop 但不需要特判。
2. `randomlyTicking` 计数和 `nonEmpty` 计数是**独立增减**的——一个方块可以是非空但不 random-tick（如 stone），也可以是非空且 random-tick（如 leaves、ice、grass）。
3. `tickingFluidCount` 和 `tickingBlockCount` **分开维护**——因为流体随方块走（waterlogged 方块自带 water 流体），但流体的 random tick 与方块的 random tick 是两个独立事件。

## 1.4.5 全量重算：recalcBlockCounts

```java
public void recalcBlockCounts() {
    class BlockCounter implements PalettedContainer.CountConsumer<BlockState> {
        int nonEmptyBlockCount, tickingBlockCount, tickingFluidCount;
        public void accept(BlockState state, int count) {
            FluidState fluid = state.getFluidState();
            if (!state.isAir()) {
                this.nonEmptyBlockCount += count;
                if (state.isRandomlyTicking()) {
                    this.tickingBlockCount += count;
                }
            }
            if (!fluid.isEmpty()) {
                this.nonEmptyBlockCount += count;
                if (fluid.isRandomlyTicking()) {
                    this.tickingFluidCount += count;
                }
            }
        }
    }

    BlockCounter counter = new BlockCounter();
    this.states.count(counter);                          // 遍历 palette + storage
    this.nonEmptyBlockCount = (short)counter.nonEmptyBlockCount;
    this.tickingBlockCount = (short)counter.tickingBlockCount;
    this.tickingFluidCount = (short)counter.tickingFluidCount;
}
```

**触发时机**：

1. **构造 LevelChunkSection** 时（接收已有 PalettedContainer）。
2. **从存档 / 网络包 read 完之后**——网络包不传计数器（节省带宽），需要重算。

`PalettedContainer.count` 是个高效遍历：它不是逐格 4096 次，而是**用 palette + 直方图**：

1. 用一个 `int[paletteSize]` 直方图扫 4096 个 storage 格子，O(4096) 但只触碰内部数组，无虚函数调用。
2. 对 palette 的每个 entry，调用一次 `accept(state, histogram[i])`，传入"state + 出现次数"。

这意味着 `BlockCounter.accept` 只被调用 `paletteSize` 次（典型 5-15 次），而不是 4096 次。

## 1.4.6 BlockState 容器：PalettedContainer<BlockState>

`states` 字段：

```java
private final PalettedContainer<BlockState> states;
```

构造（行 41-44）：

```java
public LevelChunkSection(Registry<Biome> biomes) {
    this.states = new PalettedContainer<>(
        Block.BLOCK_STATE_REGISTRY,
        Blocks.AIR.defaultBlockState(),
        PalettedContainer.Strategy.SECTION_STATES         // sizeBits=4 → 4096 格
    );
    // ...
}
```

**初始填满 air**——`SingleValuePalette(AIR)` + `ZeroBitStorage`，~80 字节起步（详见 1.3.4）。

**之后所有改动通过 `setBlockState` 走入**——它内部调用 `states.getAndSet`，从而经过 PalettedContainer 的整套 idFor / resize / setBitStorage 流程。

**为什么是 `PalettedContainer`（可写）而不是 `PalettedContainerRO`（只读）？** 因为 BlockState 在运行时随时被 setBlock 修改。下面 biomes 是 RO 包装，原因不同。

## 1.4.7 Biome 容器：PalettedContainerRO<Holder<Biome>>

`biomes` 字段：

```java
private PalettedContainerRO<Holder<Biome>> biomes;
```

注意类型是 **`PalettedContainerRO`**（只读接口）而不是 `PalettedContainer`。但实际持有的对象是 `PalettedContainer`——只是用 RO 接口包装暴露出来。

**为什么用 RO 接口暴露？** 因为 Mojang 想表达"biome 容器整体替换、不允许逐格 set"。运行时改 biome 的合理操作是：

```java
public void fillBiomesFromNoise(BiomeResolver resolver, Climate.Sampler sampler, int qx, int qy, int qz) {
    PalettedContainer<Holder<Biome>> newContainer = this.biomes.recreate();
    // ... 重新填整个容器 ...
    this.biomes = newContainer;     // ★ 整体替换
}
```

**生产环境里 biome 是不变的**——它在 chunk 生成期被填一次，之后只读。Mojang 用 RO 接口编码这个不变量。如果你试图 cast 回 `PalettedContainer` 强行改，技术上能跑但破坏不变量，可能让 PalettedContainer 的 ThreadingDetector 抓到。

**4³ = 64 格的体素粒度**：

```java
public static final int BIOME_CONTAINER_BITS = 2;    // sizeBits=2

new PalettedContainer<>(
    biomes.asHolderIdMap(),
    biomes.getOrThrow(Biomes.PLAINS),
    PalettedContainer.Strategy.SECTION_BIOMES      // size = 1 << 2*3 = 64
);
```

**为什么 4³ 而不是 16³？**

- biome 决定的是"宏观气候"——温度、降水、植被、海陆。这些参数在小尺度下变化不应该太剧烈。
- 玩家视觉上区分 biome 边界的尺度是 ~10m。如果 biome 边界精确到 1m 级，玩家会看到锯齿。
- 4³ 体素粒度让 biome 边界自然柔和（其实还有 BiomeManager 进一步抖动，1.21.4 默认开启，会再讲）。
- **存储效率**：4³ = 64 比 16³ = 4096 省 64×。

注意 4³ biome 体素是**顶天的高度**（每 4 格 Y 共享 biome），不是只看水平方向。所以你下到地下 100m 处，那里的 biome 可能与地面 biome 不同——这就是 1.18+ 的"地下 biome"特性（dripstone caves、lush caves、deep dark）。

## 1.4.8 fillBiomesFromNoise：worldgen 期填 biome

```java
public void fillBiomesFromNoise(BiomeResolver resolver, Climate.Sampler sampler, int qx, int qy, int qz) {
    PalettedContainer<Holder<Biome>> nc = this.biomes.recreate();
    int i = 4;
    for (int j = 0; j < 4; j++) {
        for (int k = 0; k < 4; k++) {
            for (int l = 0; l < 4; l++) {
                nc.getAndSetUnchecked(j, k, l, resolver.getNoiseBiome(qx + j, qy + k, qz + l, sampler));
            }
        }
    }
    this.biomes = nc;
}
```

参数：

- `resolver`：实现 `BiomeResolver` 的对象，能根据 noise 坐标返回 biome。通常是 `MultiNoiseBiomeSource`（Module 3.7 详讲）。
- `sampler`：Climate.Sampler，能在 noise 坐标查询气候参数。
- `qx`, `qy`, `qz`：本 section 在 4³ biome 网格中的最小角的 noise 坐标（= sectionPos << 2，因为 1 section = 4 biome 格宽）。

**循环 4×4×4 = 64 次**，每次调 `resolver.getNoiseBiome(qx+j, qy+k, qz+l, sampler)` 返回一个 `Holder<Biome>`，写入新容器。

**新容器替换旧容器**——RO 接口的"原子整体替换"语义。

后面 Module 3.7 会讲清楚 `getNoiseBiome` 怎么查询气候参数返回 biome。这一节你只需要知道**biome 是在 worldgen 期一次性填好的**。

## 1.4.9 网络包读写

```java
public void read(FriendlyByteBuf buf) {
    this.nonEmptyBlockCount = buf.readShort();
    this.states.read(buf);
    PalettedContainer<Holder<Biome>> newBiomes = this.biomes.recreate();
    newBiomes.read(buf);
    this.biomes = newBiomes;
}

public void write(FriendlyByteBuf buf) {
    buf.writeShort(this.nonEmptyBlockCount);
    this.states.write(buf);
    this.biomes.write(buf);
}
```

**网络包 layout**：

```
[short: nonEmptyBlockCount]
[PalettedContainer<BlockState>: states]
[PalettedContainer<Holder<Biome>>: biomes]
```

**注意**：

1. **只传 `nonEmptyBlockCount`**——`tickingBlockCount` / `tickingFluidCount` 不传，客户端不需要它们（客户端不跑 random tick）。
2. **biomes 在网络包里也传**——客户端要画 biome 颜色（草色、树叶颜色）。
3. **PalettedContainer 的 read 是"重建"流程**：先读 1 字节 bits → 推断 palette 类型 → 读 palette entries → 读 long[] storage。

`readBiomes` 是**单独读 biome** 的入口，给"光照变化但 BlockState 没变"的局部更新场景用：

```java
public void readBiomes(FriendlyByteBuf buf) {
    PalettedContainer<Holder<Biome>> newBiomes = this.biomes.recreate();
    newBiomes.read(buf);
    this.biomes = newBiomes;
}
```

**`getSerializedSize`** 给网络层算预算：

```java
public int getSerializedSize() {
    return 2 + this.states.getSerializedSize() + this.biomes.getSerializedSize();
    //   ^ short
}
```

## 1.4.10 拷贝构造

```java
private LevelChunkSection(LevelChunkSection other) {
    this.nonEmptyBlockCount = other.nonEmptyBlockCount;
    this.tickingBlockCount = other.tickingBlockCount;
    this.tickingFluidCount = other.tickingFluidCount;
    this.states = other.states.copy();      // 深拷贝 PalettedContainer
    this.biomes = other.biomes.copy();
}

public LevelChunkSection copy() {
    return new LevelChunkSection(this);
}
```

`PalettedContainer.copy()` 是浅拷贝吗？看 `PalettedContainer.Data.copy`（行 342-344）：

```java
public PalettedContainer.Data<T> copy(PaletteResize<T> resize) {
    return new PalettedContainer.Data<>(
        this.configuration,
        this.storage.copy(),         // BitStorage 的 long[] 复制
        this.palette.copy(resize)    // Palette 的 entries 复制
    );
}
```

**深拷贝**：BitStorage 的 long[] 整体复制，Palette 的 entries 整体复制。但 entries 内部的 BlockState 实例是**共享的**——因为 BlockState 是 immutable，共享安全。

**何时使用 `copy`？**

1. ProtoChunk → LevelChunk 升级时（1.5 节讲）。
2. 客户端预测时希望保留一份"未确认状态"的快照。
3. ChunkSerializer 写 NBT 前的临时副本（避免写盘期间被改）。

复制成本主要是 BitStorage 的 long[] —— 一个典型 section 的 long[] 是 256-1024 个 long = 2-8 KB。`Arrays.copyOf` 走 `System.arraycopy`，超快。

## 1.4.11 完整内存布局（一个普通 section）

```
LevelChunkSection 实例 (~80 字节对象本体 + 字段):
├── 对象头                                   :  16 字节
├── nonEmptyBlockCount  (short)              :   2 字节
├── tickingBlockCount   (short)              :   2 字节
├── tickingFluidCount   (short)              :   2 字节
├── padding to 8-byte                        :   2 字节
├── states (PalettedContainer<BlockState>)   :   8 字节引用 → 详细 ↓
└── biomes (PalettedContainerRO<Holder<Biome>>) : 8 字节引用 → 详细 ↓

states (典型 5-15 种 BlockState 的地表 section):
├── PalettedContainer 对象本体              :  ~40 字节
├── ThreadingDetector                        :  ~24 字节
├── Data<BlockState>                          :  ~24 字节
│   ├── Configuration                          :  ~16 字节
│   ├── Palette<BlockState> (LinearPalette)   :  ~48 字节
│   │   └── values[16]                          :  ~80 字节 (16 引用 + 数组头)
│   └── BitStorage (SimpleBitStorage)         :  ~32 字节
│       └── raw long[256]                       : 2048 字节
                                                 ─────
                                              ≈  2300 字节

biomes (典型 1-2 种 biome 的 section):
├── ... 类似 ...                              :  ~120 字节
└── (SingleValuePalette + ZeroBitStorage)
                                                 ─────
                                              ≈  120 字节

LevelChunkSection 总计 ≈ 2.5 KB
```

加上 24 个 section / chunk × 2.5 KB = **60 KB / chunk** 仅 BlockState + biome。再加 BlockEntity（如果有）、heightmap、光照、tick 队列等，一个 chunk 平均 200-400 KB。

**视距 32 chunk² × 24 chunk = ~1024 chunk × 300 KB ≈ 300 MB**。这就是 vanilla 服务端的 chunk 内存量级。

## 1.4.12 节内本地坐标

`getBlockState(x, y, z)` 的 x/y/z 是 **section 内本地坐标 0-15**。这一节的所有 API（`getBlockState`、`setBlockState`、`getNoiseBiome`）都假设你已经把世界坐标 mod 16 算过了。

转换由调用方负责。从世界 BlockPos 到 section 本地：

```java
// 调用方代码（典型在 LevelChunk 里）
int localX = pos.getX() & 15;
int localY = pos.getY() & 15;
int localZ = pos.getZ() & 15;
section.getBlockState(localX, localY, localZ);
```

不要把世界坐标传进去——会越界（PalettedContainer.set 内部会触发 IndexOutOfBoundsException 或更糟，写到错误位置）。

`Strategy.getIndex(x, y, z)` 是把 (0..15, 0..15, 0..15) 打包成 0..4095 的下标：

```java
public int getIndex(int x, int y, int z) {
    return (y << this.sizeBits | z) << this.sizeBits | x;
}

// 代入 sizeBits = 4：
//   index = (y << 4 | z) << 4 | x = y * 256 + z * 16 + x
```

这是 1.3.11 讨论过的 Y-Z-X major 协议布局。

## 1.4.13 与 LevelChunk 的关系

`LevelChunk` 持有一个 `LevelChunkSection[]` 数组：

```java
// LevelChunk.java（节选）
private final LevelChunkSection[] sections;
```

数组长度等于该 chunk 在该维度的总 section 数（主世界 24，下界 16，末地 16）。

**section 数组下标到 section Y 坐标**：

```java
// ChunkAccess
public int getSectionIndex(int blockY) {
    return (blockY >> 4) - this.getMinSectionY();
}
```

主世界 minSectionY = -4（因为 minY = -64 = -4 * 16），所以：

```
blockY = -64 → sectionY = -4 → sectionIndex = 0
blockY = -48 → sectionY = -3 → sectionIndex = 1
...
blockY = 304 → sectionY = 19 → sectionIndex = 23
```

`LevelChunk.setBlock(pos, state, flags)` 的内部第一步就是这一转换：

```java
int sIdx = this.getSectionIndex(pos.getY());
LevelChunkSection section = this.sections[sIdx];
section.setBlockState(pos.getX() & 15, pos.getY() & 15, pos.getZ() & 15, state);
```

## 1.4.14 C++ 移植

```cpp
class LevelChunkSection {
public:
    static constexpr int WIDTH = 16;
    static constexpr int HEIGHT = 16;
    static constexpr int SIZE = 4096;
    static constexpr int BIOME_SIZE = 64;

    LevelChunkSection(const Registry<Biome>* biomes);
    LevelChunkSection(const LevelChunkSection& other) = default;   // PalettedContainer.copy
    
    const BlockState* getBlockState(int x, int y, int z) const {
        return states_.get(x, y, z);
    }
    
    const BlockState* setBlockState(int x, int y, int z, const BlockState* newState, bool acquireLock = true) {
        const BlockState* oldState = acquireLock 
            ? states_.getAndSet(x, y, z, newState) 
            : states_.getAndSetUnchecked(x, y, z, newState);
        
        // 维护计数器
        const FluidState& oldFluid = oldState->getFluidState();
        const FluidState& newFluid = newState->getFluidState();
        if (!oldState->isAir()) {
            nonEmptyBlockCount_--;
            if (oldState->isRandomlyTicking()) tickingBlockCount_--;
        }
        if (!oldFluid.isEmpty()) tickingFluidCount_--;
        if (!newState->isAir()) {
            nonEmptyBlockCount_++;
            if (newState->isRandomlyTicking()) tickingBlockCount_++;
        }
        if (!newFluid.isEmpty()) tickingFluidCount_++;
        
        return oldState;
    }
    
    bool hasOnlyAir() const { return nonEmptyBlockCount_ == 0; }
    bool isRandomlyTicking() const { return tickingBlockCount_ > 0 || tickingFluidCount_ > 0; }
    
    void recalcBlockCounts();
    void fillBiomesFromNoise(BiomeResolver& resolver, ClimateSampler& sampler, int qx, int qy, int qz);
    
    PalettedContainer<const BlockState*>& states() { return states_; }
    const PalettedContainer<Holder<Biome>>& biomes() const { return biomes_; }
    
    void writeNetwork(ByteBuf& buf) const;
    void readNetwork(ByteBuf& buf);
    int serializedSize() const;
    
private:
    int16_t nonEmptyBlockCount_ = 0;
    int16_t tickingBlockCount_ = 0;
    int16_t tickingFluidCount_ = 0;
    PalettedContainer<const BlockState*> states_;
    PalettedContainer<Holder<Biome>> biomes_;
};
```

**关键设计选择**：

1. **`const BlockState*` 不拥有**——BlockState 是全局共享 immutable，传指针即可。Section 不负责生命周期。
2. **`states_` 公开为可写引用，`biomes_` 公开为 const 引用** —— 模仿 Java 的 RO 接口语义。
3. **计数器用 `int16_t` 而非 `short`** —— 跨平台明确。值域 [0, 4096] 足够，但记得 4096 超 int8_t (max 127)。
4. **`recalcBlockCounts` 在 read 之后调用**：网络包不传计数器，需要重算。
5. **整个对象不需要 mutex**：依赖外层 chunk 线程归属（详见 0.3 / Module 4）。

**SoA 优化思考**：当前布局是 AoS（每个 section 自带它的 PalettedContainer + BitStorage）。一个常见的 SoA 优化是：

```cpp
// SoA 版本：把所有 chunk 的"是否 random ticking" 分离到一个 bit set
class ChunkManager {
    // 哪些 (chunk, sectionIdx) 在 random ticking
    boost::dynamic_bitset<> isRandomTicking_;
    
    void tickAll() {
        for (size_t bit = isRandomTicking_.find_first(); 
             bit != isRandomTicking_.npos; 
             bit = isRandomTicking_.find_next(bit)) {
            // 对该 section 跑 random tick
        }
    }
};
```

这把"扫所有 section 看哪些要 tick" 从遍历 chunk[] → section[] 数组优化为遍历 bitset。在 1024 chunk × 24 section = 24576 个 section 时，AoS 遍历是 24K 次，SoA bitset 是 384 次（24576 / 64 word）。**60× 加速**。

但 Mojang Java 没有这么做——堆栈式简单更直观，也不是性能瓶颈。C++ 引擎里值得做。

## 1.4.15 实战：手算两个数

**问题 1**：一个 16×384×16 chunk 全是 stone，section[5] 内有一个 oak_log[axis=y]。section[5] 占多少内存？

答：

- states：palette = LinearPalette[stone, oak_log]（2 entries），bits = 4（永远）。BitStorage = SimpleBitStorage(4 bit, 4096) = 256 long = 2048 bytes。
- biomes：SingleValuePalette + ZeroBitStorage = ~80 字节。
- 计数器 + 对象头：~80 字节。

总计 ≈ **2300 字节**。

**问题 2**：那 24 个 section 里有 23 个全是 air、1 个全是 stone。一个 chunk 占多少？

答：

- 23 个 air section：每个 ~200 字节（SingleValuePalette + Zero） = 4600 字节。
- 1 个 stone section：~200 字节（SingleValuePalette + Zero） = 200 字节。
- 24 个 section 引用 + 数组头：~250 字节。

总计 ≈ **5 KB**。一个全空的 chunk 比 6 KB 还小。

这就是为什么虚空之上、海洋深处的 chunk 几乎不吃内存。**Mojang 在这里把 60% 的玩家世界优化得近乎免费**。

## 1.4.16 一句话总结

`LevelChunkSection` = `PalettedContainer<BlockState>`（4096 格）+ `PalettedContainerRO<Holder<Biome>>`（64 格）+ 三个 short 计数器（非空数 / 块 random-tick 数 / 流体 random-tick 数）；计数器在 `setBlockState` 增量维护，让 `isRandomlyTicking` 退化为常数判断；biome 用粗粒度 4³ 体素，整体替换式更新；网络包传 `[short nonEmpty + states palette/storage + biomes palette/storage]`；空 section 仅 ~200 字节，普通 section ~2.5 KB。
