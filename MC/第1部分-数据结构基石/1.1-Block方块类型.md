# 1.1 Block：方块类型

## 1.1.0 你将在本节学到什么

## 1.1.1 直觉：先建立心智模型

打开 Minecraft 走到一棵橡树旁边，砍倒它，得到一堆橡木原木。把它们放回地上的不同位置：

- (10, 64, 10) 放一根，朝 Y 轴。
- (20, 64, 20) 放一根，朝 Y 轴。
- (30, 64, 30) 放一根，朝 X 轴（横放）。

世界里现在有 3 根原木。在 Java 内存里有几个对象？

**答案是**：

- 1 个 **`Block`** 对象 —— `Blocks.OAK_LOG`。它代表"橡木原木这个**类型**"。**全世界只有一个**。
- 3 种可能的 **`BlockState`** 对象（朝 X / Y / Z 三种 axis），但**全游戏只创建一次共享使用**。
- 3 个 **格位**（每个 BlockPos 一格）—— 但格位不是 Java 对象，而是 chunk section 内部 PalettedContainer 里的整数索引。

也就是说：**Block 是类型描述符（singleton）；BlockState 是该类型 + 一组属性值的具体配置（按属性穷举数量决定，全游戏共享）；世界里"某一格放了什么"只是一个引用 / 整数 ID，不是新对象**。

这个设计完全是为了内存效率。一个区块 16 × 384 × 16 ≈ 10 万格，全世界几百个 chunk，如果每格都 new 一个 `Block` 对象，光对象头就上百 MB。共享 immutable 实例 + 整数索引让平均每格只占几 bit。

这一节先讲 Block（类型）。下一节 1.2 讲 BlockState（配置）。第三节 1.3 讲 PalettedContainer（怎么把"每格的 BlockState 引用"压缩存进 chunk）。

## 1.1.2 Block 类的真身

打开 `net.minecraft.world.level.block.Block`（行 63-103）：

```java
public class Block extends BlockBehaviour implements ItemLike {
    public static final MapCodec<Block> CODEC = simpleCodec(Block::new);
    private static final Logger LOGGER = LogUtils.getLogger();
    private final Holder.Reference<Block> builtInRegistryHolder =
        BuiltInRegistries.BLOCK.createIntrusiveHolder(this);
    public static final IdMapper<BlockState> BLOCK_STATE_REGISTRY = new IdMapper<>();

    public static final int UPDATE_NEIGHBORS = 1;
    public static final int UPDATE_CLIENTS = 2;
    public static final int UPDATE_INVISIBLE = 4;
    public static final int UPDATE_IMMEDIATE = 8;
    public static final int UPDATE_KNOWN_SHAPE = 16;
    public static final int UPDATE_SUPPRESS_DROPS = 32;
    public static final int UPDATE_MOVE_BY_PISTON = 64;
    public static final int UPDATE_SKIP_SHAPE_UPDATE_ON_WIRE = 128;
    public static final int UPDATE_NONE = 4;
    public static final int UPDATE_ALL = 3;
    public static final int UPDATE_ALL_IMMEDIATE = 11;

    public static final float INDESTRUCTIBLE = -1.0F;
    public static final float INSTANT = 0.0F;
    public static final int UPDATE_LIMIT = 512;

    protected final StateDefinition<Block, BlockState> stateDefinition;
    private BlockState defaultBlockState;
    @Nullable private Item item;
    // ...
}
```

一段一段拆。

### 父类 `BlockBehaviour`

`Block extends BlockBehaviour`。`BlockBehaviour`（在同一包下）是巨大的"行为基类"，定义所有方块都会用到的几十个虚方法：`getDestroyProgress`、`getCollisionShape`、`getOcclusionShape`、`onPlace`、`onRemove`、`tick`、`randomTick`、`neighborChanged`、`use`、`getDrops`、`getLightBlock`、`getLightEmission`、⋯⋯

**为什么要拆出 BlockBehaviour 这一层？** 因为 Mojang 想把"配置式构造方块"和"重写方法定义自定义方块"分开：

- 简单方块（不需要重写任何方法、纯走配置）：`new Block(BlockBehaviour.Properties.of()...)` 即可。
- 复杂方块（需要重写 `onPlace` 干自定义事）：继承 `Block` 或更深层的子类（`SlabBlock`、`StairBlock`、`ButtonBlock`...），然后重写。

**1.21 后 Mojang 大量推进"组合优于继承"**：行为通过 `BlockBehaviour.Properties` 链式配置（`strength(2.0f)`、`sound(SoundType.WOOD)`、`lightLevel(s -> 7)` ⋯⋯），而不是为每个新方块新建一个子类。但旧版本沉淀下来的子类继承树仍然庞大。

### `static final MapCodec<Block> CODEC`

这是 Block 类型的 datapack codec（参考 0.5）。它让 datapack 可以在 JSON 里写 `"type": "minecraft:block"` 来引用 Block 类型，但**实际上 datapack 不能新增 Block 类型**——因为 Block 是静态注册表，运行时不可改。这个 CODEC 主要给序列化机制用，比如把"方块替换器"配置写进 JSON。

### `Holder.Reference<Block> builtInRegistryHolder`

每个 Block 自己持有一个反向引用到 `BuiltInRegistries.BLOCK` 中的位置。这是 `createIntrusiveHolder` 的设计——让 Block 能 `O(1)` 拿到自己的 `Holder<Block>`，不用每次去 registry 查。

详见 0.4。重点：源码里看到 `block.builtInRegistryHolder()` 就是"这个 block 在 BLOCK registry 里的 Holder 引用"。

### `static final IdMapper<BlockState> BLOCK_STATE_REGISTRY`

**这个非常重要**。它是**全部 BlockState 的全局 ID 表**——不管哪个 Block，所有 BlockState（注意是 BlockState，不是 Block 自己）按它们被创建的顺序分配整数 ID。

```java
public static int getId(@Nullable BlockState state) {
    if (state == null) return 0;
    int i = BLOCK_STATE_REGISTRY.getId(state);
    return i == -1 ? 0 : i;
}

public static BlockState stateById(int id) {
    BlockState bs = BLOCK_STATE_REGISTRY.byId(id);
    return bs == null ? Blocks.AIR.defaultBlockState() : bs;
}
```

这个 ID 表的用途：

- 网络包 `ClientboundBlockUpdatePacket` 用 `int` 传 BlockState（不传 namespace string，太占带宽）。
- Heightmap 比较用（比较两个 BlockState 是不是 air）。
- 全局 palette 模式（1.3 节会讲）。

**整数 ID 是动态分配的**，不能写存档磁盘。存档里写的永远是 BlockState 的字符串完整描述（"minecraft:oak_log[axis=y]"）。

### `protected final StateDefinition<Block, BlockState> stateDefinition`

每个 Block 实例持有自己的 StateDefinition。它是**该 Block 所有可能 BlockState 的穷举集合**。1.2 节专门讲。

### `private BlockState defaultBlockState`

每个 Block 有一个**默认 BlockState**。这是放置一个新方块时（除非有玩家指定属性）的初始状态。

```java
public BlockState defaultBlockState() {
    return this.defaultBlockState;
}

protected void registerDefaultState(BlockState state) {
    this.defaultBlockState = state;
}
```

**`registerDefaultState` 通常在子类构造函数里调用**：

```java
public class CampfireBlock extends BaseEntityBlock {
    public CampfireBlock(Properties props) {
        super(props);
        this.registerDefaultState(this.stateDefinition.any()
            .setValue(LIT, true)
            .setValue(SIGNAL_FIRE, false)
            .setValue(WATERLOGGED, false)
            .setValue(FACING, Direction.NORTH));
    }
}
```

**默认状态不是属性的最小值**——是 Mojang 觉得"放下去时最自然的初始值"。例如营火的默认状态是 LIT=true、FACING=NORTH。

### 那一堆 `UPDATE_*` flag

这些是 `level.setBlock(pos, state, flags)` 的第三个参数能用的 bit 位：

| flag | 值 | 含义 |
|------|-----|-----|
| `UPDATE_NEIGHBORS` | 1 | 触发邻居 6 块的 `neighborChanged` 回调 |
| `UPDATE_CLIENTS` | 2 | 把 BlockUpdate 同步给客户端 |
| `UPDATE_INVISIBLE` | 4 | 不更新视觉、声音、粒子（只改数据） |
| `UPDATE_IMMEDIATE` | 8 | 立刻渲染重编译，不等下一帧 |
| `UPDATE_KNOWN_SHAPE` | 16 | 跳过 shape update（省时间） |
| `UPDATE_SUPPRESS_DROPS` | 32 | 替换原方块时不让它掉落物品 |
| `UPDATE_MOVE_BY_PISTON` | 64 | 标记"被活塞推动产生的更新" |
| `UPDATE_SKIP_SHAPE_UPDATE_ON_WIRE` | 128 | 红石线特别优化（1.21 实验红石用） |

**常用组合**：

| 组合 | 值 | 用途 |
|------|----|----|
| `UPDATE_ALL` | 3 (= 1 \| 2) | 通用：触发邻居 + 同步客户端 |
| `UPDATE_ALL_IMMEDIATE` | 11 (= 1 \| 2 \| 8) | 通用 + 立即渲染（命令系统等用） |
| `UPDATE_NONE` | 4 | "只改数据不动其他" —— 注意这个**等于** UPDATE_INVISIBLE，是 Mojang 一个语义别名 |
| `UPDATE_CLIENTS \| UPDATE_INVISIBLE` | 6 | 同步但不视觉 / 声音 |

**`UPDATE_NONE = 4 = UPDATE_INVISIBLE`** 是个让人困惑的命名重载——同一个数 4 既叫 `INVISIBLE` 也叫 `NONE`。读源码看到 `Block.UPDATE_NONE` 时知道它就是不触发邻居、不同步客户端、纯改数据的**最静悄悄**修改。

## 1.1.3 Block 的"实例"在哪里：Blocks 类

**Block 是一类对象，但它是 singleton-per-type**。你不会自己 `new Block()`，所有 vanilla 方块在 `net.minecraft.world.level.block.Blocks` 里有唯一公共静态字段：

```java
// Blocks.java（节选）
public class Blocks {
    public static final Block AIR    = register("air",    new AirBlock(BlockBehaviour.Properties.of()
        .replaceable().noCollission().noLootTable().air()));
    public static final Block STONE  = register("stone",  new Block(BlockBehaviour.Properties.of()
        .mapColor(MapColor.STONE).instrument(NoteBlockInstrument.BASEDRUM)
        .requiresCorrectToolForDrops().strength(1.5f, 6.0f)));
    public static final Block GRASS_BLOCK = register("grass_block", new GrassBlock(...));
    public static final Block OAK_LOG = register("oak_log", new RotatedPillarBlock(...));
    // ... 共约 1100 个 vanilla block
}
```

`register` 是个内部静态方法，把 Block 注册到 `BuiltInRegistries.BLOCK` 并返回该实例。这个机制保证：

1. **所有 Block 实例在游戏启动时被创建**（`Blocks.<clinit>` 类初始化时）。
2. **创建顺序固定** = 整数 ID 在 vanilla 里固定（mod 加进来时偏移）。
3. **运行时只读**：你从代码任何地方都能访问 `Blocks.STONE`，且永远是同一个对象。

**注册时序**：游戏启动 → `Bootstrap.bootStrap()` 触发 `Blocks` 的 `<clinit>` → 所有静态字段从上到下依次执行 `register(...)` → 1100 个 Block 全部注册完毕。

**子类规模**：vanilla 里 Block 的子类有约 200 多个。常见的有：

- `Block` 本身：朴素方块，只走 BlockBehaviour 配置（如 STONE、DIRT、COBBLESTONE）。
- `RotatedPillarBlock`：可旋转柱状（OAK_LOG、HAY_BLOCK、AMETHYST_BLOCK）。
- `SlabBlock`、`StairBlock`、`WallBlock`、`FenceBlock`：建筑组件。
- `CropBlock`、`StemBlock`、`CocoaBlock`：作物。
- `BaseEntityBlock`：带 BlockEntity 的方块（CHEST、FURNACE）。
- `LiquidBlock`：液体（虽然现在大部分液体逻辑在 `Fluid` 上，但仍有 LiquidBlock 作为方块层包装）。
- `EntityBlock`：一个 marker 接口，标记带 BlockEntity 的方块。
- ⋯⋯

具体子类不重要，**机制重要**：每个 Block 子类用同一套机制（`Properties`、`stateDefinition`、`registerDefaultState`、`tick`、`use`）来定义自己的行为。

## 1.1.4 BlockBehaviour.Properties：方块的配置链

```java
new Block(BlockBehaviour.Properties.of()
    .mapColor(MapColor.WOOD)
    .strength(2.0f, 3.0f)
    .sound(SoundType.WOOD)
    .ignitedByLava()
    .pushReaction(PushReaction.NORMAL)
    .instrument(NoteBlockInstrument.BASS)
)
```

这是 1.21 时代典型方块构造方式。`Properties` 是一个**Builder**，链式调用配置出一个 immutable 配置对象，传给 `Block` 构造函数。配置项约 30 个，含义你看链式名字就猜得出：

| Properties 方法 | 含义 |
|----------------|------|
| `mapColor(MapColor)` | 在地图上呈现的颜色 |
| `strength(destroy, blast)` | 挖掘硬度 + 抗爆炸 |
| `sound(SoundType)` | 走 / 破坏 / 放置时的声音组 |
| `lightLevel(s -> int)` | 该 BlockState 发出的光照强度（0-15） |
| `friction(0.6f)` | 摩擦力（默认 0.6，冰是 0.98） |
| `speedFactor(1.0f)` | 玩家在上面行走的速度倍率（灵魂沙是 0.4） |
| `noOcclusion()` | 不阻挡光线（玻璃用） |
| `noCollision()` | 没有碰撞盒（air、火） |
| `replaceable()` | 玩家放方块时直接替换（air、tall_grass） |
| `dynamicShape()` | shape 不能缓存，每次查询（活塞推动状态） |
| `requiresCorrectToolForDrops()` | 没有正确工具不掉落 |
| `pushReaction(PushReaction)` | 活塞推动时的行为：NORMAL/DESTROY/BLOCK/IGNORE/PUSH_ONLY |
| `instrument(NoteBlockInstrument)` | 上面放音符盒时的乐器 |
| `ignitedByLava()` | 接触熔岩自燃 |
| `randomTicks()` | 接受 random tick |
| ⋯⋯ | |

**这些配置在创建后不可改**。但**注意**：很多方块的实际行为是动态的——比如冰的发光强度可以是"if (state.LIT) 7 else 0"。这种"按 BlockState 决定行为"的字段会接受 lambda：`lightLevel(s -> s.getValue(LIT) ? 7 : 0)`。

**你写自己的 Block 时**：90% 情况只需要选合适的 Properties 配置 + 选合适的子类（`Block` 本体 / `SlabBlock` / `RotatedPillarBlock` ⋯⋯），不需要重写任何方法。这就是 Mojang "组合 > 继承" 转向的实际意义。

## 1.1.5 defaultBlockState() 调用链

最常见的一段代码：

```java
level.setBlock(pos, Blocks.OAK_LOG.defaultBlockState(), Block.UPDATE_ALL);
```

每一步：

1. **`Blocks.OAK_LOG`** —— 静态字段，访问全局唯一的 `Block` 对象。
2. **`.defaultBlockState()`** —— 返回该 Block 注册的 default BlockState 实例。
3. **`level.setBlock(pos, state, flags)`** —— 把这个 BlockState 写到指定 chunk section 的指定本地坐标。

**但默认状态不一定是你要的**——比如想放置朝 X 轴的橡木原木，需要：

```java
BlockState state = Blocks.OAK_LOG.defaultBlockState()
    .setValue(RotatedPillarBlock.AXIS, Direction.Axis.X);
level.setBlock(pos, state, Block.UPDATE_ALL);
```

`.setValue(...)` 不修改原 BlockState（它是 immutable），而是返回**对应属性已切换的另一个 BlockState 实例**。这个"返回另一个实例"本身有玄机——下一节 1.2 会讲清楚为什么 `setValue` 是 O(1) 的、不会真的去"创建"新对象。

## 1.1.6 默认方块和 air 的特殊地位

```java
public static final Block AIR = register("air", new AirBlock(...));
public static final Block CAVE_AIR = register("cave_air", new AirBlock(...));
public static final Block VOID_AIR = register("void_air", new AirBlock(...));
```

注意 **"空气"在 vanilla 里有 3 种**：

- `AIR`：通常的空气。
- `CAVE_AIR`：地下生成时打洞产生的空气。某些代码区分洞穴空气是因为它影响 ambient 音效与刷怪。
- `VOID_AIR`：Y < min_y 之下的"虚空"。访问超界 Y 时返回这个。

三者**视觉上完全一样**，只是数据 tag 不同。`isAir()` 返回 true 对所有三种都成立——因为 `AirBlock` 是它们共同基类，`isAir()` 实现就是 `instanceof AirBlock`。

**`Block.AIR` 的整数 ID 通常是 0**（注册顺序最早）。整个游戏依赖这个事实——很多代码 `if (id == 0)` 判断空气。**`stateById(0)`** 通常返回 air 的默认状态。

**`Block.STONE`** 也很重要——很多 chunk 在创建时初始化为全 stone（基底世界生成），然后 carver 雕掉、feature 装饰。

## 1.1.7 一段真实代码逐行读

打开 `Block.java` 里 `getId` 和 `stateById`（行 110-122）：

```java
public static int getId(@Nullable BlockState p_49957_) {
    if (p_49957_ == null) {
        return 0;
    } else {
        int i = BLOCK_STATE_REGISTRY.getId(p_49957_);
        return i == -1 ? 0 : i;
    }
}

public static BlockState stateById(int p_49804_) {
    BlockState blockstate = BLOCK_STATE_REGISTRY.byId(p_49804_);
    return blockstate == null ? Blocks.AIR.defaultBlockState() : blockstate;
}
```

**逐行心读**：

> "`getId(BlockState)`：把一个 BlockState 转成全局 int ID。
>
> 第一行 `@Nullable` 注解告诉我参数可能 null，要 check。null → 返回 0（air 的 ID）。
>
> 调 `BLOCK_STATE_REGISTRY.getId(state)` 反查 ID。如果返回 -1（没注册过、罕见），fall back 到 0。否则返回 ID。
>
> `stateById(int)`：反向，从 int ID 拿 BlockState。
>
> `byId` 返回 null（ID 越界）→ fall back 到 air defaultBlockState。否则返回找到的实例。"

15 秒读完。**注意**：这两个方法是**网络包 / palette / heightmap 反查的核心入口**——你在 Module 7 网络协议里会看到 `int blockId = Block.getId(state); buf.writeVarInt(blockId);` 几十处。

## 1.1.8 内存预算：一个 Block 占多大？

按 64-bit JVM、压缩 oop 关闭 / 开启分别估算：

```
Block 实例字段（典型）:
├── 对象头 (mark word + class pointer)        : 16 字节
├── BlockBehaviour.Properties 引用            : 8 字节
├── StateDefinition<Block, BlockState>        : 8 字节（指向）
├── BlockState defaultBlockState              : 8 字节
├── Item item                                 : 8 字节（@Nullable）
├── Holder.Reference<Block>                   : 8 字节
└── 其他 BlockBehaviour 字段                   : ~64 字节
                                                ─────
                                              ≈ 120 字节
```

**1100 个 vanilla Block** × **120 字节** ≈ **130 KB**。微不足道。

**`StateDefinition`** 单独算：它持有所有 state 的 immutable list。每个 BlockState 又约 200 字节（属性 map + neighbours array）。一个有 2 个 boolean + 1 个 4-value enum 属性的方块就有 2×2×4 = 16 个 BlockState = 16 × 200 = 3.2 KB。

**整个 vanilla 的 BlockState 总数** 约 26000 个（1.21）。每个 BlockState ~200 B → 总计 ~5 MB。也微不足道。

**真正吃内存的不是 Block / BlockState，而是 chunk 里的 PalettedContainer**。一个 section 1024 个 long = 8 KB；一个 chunk 24 个 section × 8 KB = 192 KB；视距 32 chunks² ≈ 1024 chunks × 192 KB ≈ 200 MB。

**这就是为什么 PalettedContainer 必须聪明压缩**——下一节 1.3 主菜。

## 1.1.9 C++ 移植设计

把 Block 落地到 C++：

```cpp
// 把"行为/配置"和"类型"分离
struct BlockProperties {
    MapColor mapColor;
    float destroyTime;
    float blastResistance;
    float friction;
    float speedFactor;
    float jumpFactor;
    SoundType sound;
    bool requiresTool;
    bool noCollision;
    bool noOcclusion;
    bool replaceable;
    bool randomTicks;
    PushReaction pushReaction;
    std::function<int(const BlockState&)> lightEmission;
    // ... ~30 字段
};

class Block {
public:
    Block(BlockProperties props, std::unique_ptr<StateDefinition> states);
    virtual ~Block() = default;

    const BlockState& defaultBlockState() const { return *defaultState_; }
    const StateDefinition& stateDefinition() const { return *states_; }
    const BlockProperties& properties() const { return props_; }

    // 虚方法（少数情况下子类重写）
    virtual void onPlace(World& world, BlockPos pos, const BlockState& state) {}
    virtual void onRemove(World& world, BlockPos pos, const BlockState& oldState) {}
    virtual void tick(World& world, BlockPos pos, const BlockState& state) {}
    virtual void randomTick(World& world, BlockPos pos, const BlockState& state) {}
    virtual void neighborChanged(World& world, BlockPos pos, const BlockState& state, BlockPos from) {}
    // ...

protected:
    BlockProperties props_;
    std::unique_ptr<StateDefinition> states_;
    const BlockState* defaultState_ = nullptr;
};

// 全局 singleton 注册表
namespace Blocks {
    extern Block* AIR;
    extern Block* STONE;
    extern Block* GRASS_BLOCK;
    extern Block* OAK_LOG;
    // ... 1100 个静态指针
}

// update flags
namespace BlockUpdateFlags {
    constexpr int NEIGHBORS  = 1;
    constexpr int CLIENTS    = 2;
    constexpr int INVISIBLE  = 4;
    constexpr int IMMEDIATE  = 8;
    // ...
    constexpr int ALL = NEIGHBORS | CLIENTS;
    constexpr int ALL_IMMEDIATE = ALL | IMMEDIATE;
    constexpr int NONE = INVISIBLE;
}
```

**关键设计选择**：

1. **Block 用指针不用值**：所有引用 Block 的地方用 `Block*`，不要拷贝。Block 是 singleton，永不复制。
2. **不用虚函数也行**：很多方块行为完全靠 `BlockProperties` 配置，不需要虚函数。有人会做"data-oriented design"——把所有 hot path 行为查询都写成 `BlockProperties` 字段（lambda 或函数指针），完全干掉虚函数。性能更好。
3. **defaultState\_ 是指向 StateDefinition 内部的指针**：StateDefinition 拥有所有 BlockState，Block 只持有指针。
4. **不要照搬 BlockBehaviour 抽象**：在 C++ 里直接把字段放进 Block 自己即可。BlockBehaviour 这层在 Java 里是历史包袱。
5. **Blocks 全局指针表**：用 `extern Block*` + 在 `.cpp` 里 `inline` 初始化，或者用 Meyer's singleton：

```cpp
namespace Blocks {
    inline Block& AIR() {
        static Block instance(BlockProperties{...}, makeStateDef());
        return instance;
    }
}
```

更稳的做法是显式写一个 `Blocks::registerAll(Registry<Block>&)` 函数，启动时调一次。这样注册顺序明确、整数 ID 稳定。

## 1.1.11 实战：在源码里找一段 Block 子类构造

打开 `D:\Minecraft\MCP-Reborn-1.21\src\main\java\net\minecraft\world\level\block\Blocks.java`，找一个简单的 `register(...)` 调用，比如：

```java
public static final Block STONE = register("stone", new Block(BlockBehaviour.Properties.of()
    .mapColor(MapColor.STONE)
    .instrument(NoteBlockInstrument.BASEDRUM)
    .requiresCorrectToolForDrops()
    .strength(1.5f, 6.0f)));
```

这行代码做了：
1. `BlockBehaviour.Properties.of()` 创建空 builder。
2. 链式调用 4 次配置。
3. `new Block(props)` 构造（调父类 BlockBehaviour 构造，存 props，构造 stateDefinition——这一步 1.2 节展开）。
4. `register("stone", block)` 把它注册到 `BuiltInRegistries.BLOCK` 并返回 block 实例。
5. 赋给静态字段 `Blocks.STONE`。

接着翻一个稍复杂的：

```java
public static final Block CAMPFIRE = register("campfire", new CampfireBlock(true, 1, ...));
```

`CampfireBlock` 是 `Block` 的子类，构造里有更多自定义。但**它仍然进同一个 register**——Mojang 的所有 vanilla block 走完全统一的注册路径。

如果你能跟着这两条 register 链子从 Java 字段读到 BlockBehaviour 构造，本节就过关了。

## 1.1.12 一句话总结

`Block` 是方块**类型描述符**，全游戏每种方块只一个 singleton 实例（`Blocks.OAK_LOG`、`Blocks.STONE`），存各种"配置式"行为（硬度、声音、光照、可推动性 ⋯⋯）；它持有 `StateDefinition`（下一节展开）枚举该类型所有可能的 BlockState；运行时通过 `BLOCK_STATE_REGISTRY` 给所有 BlockState 分配整数 ID 用于网络 / palette；`UPDATE_*` flag 是 `setBlock` 的 bit 位，最常用 `UPDATE_ALL = 3`（邻居 + 客户端同步）；写自己的 Block 时优先选合适子类 + 链式 `Properties` 配置，不要轻易重写虚方法。
