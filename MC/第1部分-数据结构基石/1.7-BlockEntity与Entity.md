# 1.7 BlockEntity 与 Entity

## 1.7.0 你将在本节学到什么

读完这一节你应当能闭着眼睛回答：

1. "实体（Entity）"和"方块实体（BlockEntity）"差别是什么？同一段代码里出现都不奇怪——它们是不是同一个东西的两个别名？
2. 一个箱子（chest）、一个熔炉（furnace）、一个唱片机（jukebox）哪些是 BlockEntity？哪些不是？为什么？
3. 一个非 BlockEntity 方块（如 stone）和一个 BlockEntity 方块（如 chest）放在世界里时，它们在 chunk section 内**多占了多少内存**？
4. 玩家放置一个箱子，这个 BlockEntity 是什么时候创建的？什么时候开始 tick？什么时候被销毁？
5. 一只僵尸是 Entity，它存在 chunk section 里吗？它的位置怎么和 chunk 关联？
6. 为什么 1.21 重新设计了 `DataComponentMap` 给 BlockEntity？为什么不像 BlockState 那样把状态全 hash 到属性里？
7. 我在 C++ 里要复现这套机制，BlockEntity 该用 ECS 还是 OOP？

## 1.7.1 概念区分：方块、方块实体、实体

先把三个名词在世界里的位置画清楚：

```
世界里的"东西"分成三类：

  ┌─────────────────────────────────────────────────────┐
  │ 1. 方块（Block / BlockState）                        │
  │    - 严格对齐到 1m 网格                              │
  │    - 每格只能一种                                    │
  │    - 状态由 ≤ ~20 个属性枚举完毕                     │
  │    - 存在 ChunkSection 的 PalettedContainer 里        │
  │    - 例：stone / oak_log / water                     │
  └─────────────────────────────────────────────────────┘

  ┌─────────────────────────────────────────────────────┐
  │ 2. 方块实体（BlockEntity）                            │
  │    - 仍然占一格 1m                                    │
  │    - 但需要 BlockState 之外的额外状态                 │
  │      （箱子里有什么物品？熔炉烧到第几 tick？）         │
  │    - 与一个 BlockState 配对："chest 方块 + 它的库存"  │
  │    - 存在 chunk 的 BlockEntity Map 里（独立于 section）│
  │    - 例：箱子、熔炉、唱片机、命令方块、潜影盒          │
  └─────────────────────────────────────────────────────┘

  ┌─────────────────────────────────────────────────────┐
  │ 3. 实体（Entity）                                     │
  │    - 浮点位置（Vec3），不对齐网格                     │
  │    - 可以移动                                          │
  │    - 例：玩家、僵尸、丢出去的物品、箭、矿车           │
  │    - 存在 ServerLevel 的 EntityManager 里              │
  └─────────────────────────────────────────────────────┘
```

**这三类是完全不同的对象**。它们都叫"X-something"是历史包袱（Mojang 早期叫 `TileEntity`，1.13+ 改名 BlockEntity）。

**BlockEntity 是方块 + 一份附加数据的组合**，不是 Entity 的子类、不是 Block 的子类。它是独立的层。

## 1.7.2 为什么需要 BlockEntity 这一层

回顾 1.2 节：BlockState 是属性枚举（启动时穷举出 ≤ 26000 个共享 immutable 实例）。

但有些方块的状态空间不可枚举：

- **箱子**：里面装的物品组合 = 27 个槽 × 任意 ItemStack 的组合 = 几乎无限多种状态。
- **熔炉**：燃烧进度 = 0..200 tick、烧的物品、燃料剩余 = 至少几千种组合。
- **告示牌**：4 行任意字符串文字 = 真正的无限状态。
- **命令方块**：任意命令字符串。
- **唱片机**：当前播放的唱片。

这些**都不能塞进 BlockState 属性穷举**。因为：

1. 状态量级太大，穷举出几亿种 BlockState 内存爆。
2. 状态需要随时改写（玩家拿物品进出箱子），immutable 共享语义不适合。

所以 Mojang 让这些方块的"特殊状态"分到另一个对象——**`BlockEntity`**。BlockState 仍然是 immutable 共享（标记"这一格是箱子，朝向北"），BlockEntity 是 mutable 单例（"这个箱子里有什么物品"）。

## 1.7.3 BlockEntity 类的真身

打开 `net.minecraft.world.level.block.entity.BlockEntity`（行 29-44）：

```java
public abstract class BlockEntity {
    private final BlockEntityType<?> type;        // 类型描述（CHEST / FURNACE / ...）
    @Nullable protected Level level;              // 反向引用到所在 Level（运行时填）
    protected final BlockPos worldPosition;       // 在世界中的绝对位置（immutable）
    protected boolean remove;                     // 是不是已经被移除
    private BlockState blockState;                // 关联的 BlockState
    private DataComponentMap components = DataComponentMap.EMPTY;

    public BlockEntity(BlockEntityType<?> type, BlockPos pos, BlockState state) {
        this.type = type;
        this.worldPosition = pos.immutable();
        this.validateBlockState(state);
        this.blockState = state;
    }
}
```

**字段含义**：

- **`type`**：BlockEntityType 实例，一个 singleton，类似 Block 与 BlockEntity 的关系。每种 BE（如 CHEST）有一个 type。
- **`level`**：反向引用到 Level。**`@Nullable`**——构造时还没有 Level，是 `setLevel` 调用后才填上的。
- **`worldPosition`**：BE 在世界里的位置。**immutable**，构造后不可改。这个字段是 BE 的"身份证"——同一格的 BE 同 worldPosition。
- **`remove`**：标记"我应该被销毁了"。block break 时设为 true，让任何持有该 BE 引用的代码知道不要再用它。
- **`blockState`**：关联的 BlockState。需要保持与 chunk section 里的同步。
- **`components`**：1.20.5+ 引入的"组件式数据"map。

**子类约 60 个**，对应 vanilla 的所有可附加额外状态的方块：

- `ChestBlockEntity` / `BarrelBlockEntity` / `ShulkerBoxBlockEntity` —— 容器类。
- `FurnaceBlockEntity` / `BlastFurnaceBlockEntity` / `SmokerBlockEntity` —— 熔烧类。
- `SignBlockEntity` —— 告示牌（文字内容）。
- `JukeboxBlockEntity` —— 唱片机（当前唱片）。
- `CommandBlockEntity` —— 命令方块（命令字符串）。
- `BeaconBlockEntity` —— 信标（启用的效果）。
- `BrewingStandBlockEntity` —— 酿造台。
- ⋯⋯

## 1.7.4 BlockEntityType：类似 Block 的工厂 + 描述

每个 BlockEntity 子类有一个对应的 `BlockEntityType<T extends BlockEntity>` 静态字段：

```java
// BlockEntityType.java（节选）
public class BlockEntityType<T extends BlockEntity> {
    public static final BlockEntityType<ChestBlockEntity> CHEST = register(
        "chest",
        BlockEntityType.Builder.of(ChestBlockEntity::new, Blocks.CHEST)
    );
    public static final BlockEntityType<FurnaceBlockEntity> FURNACE = ...;
    public static final BlockEntityType<SignBlockEntity> SIGN = ...;
    public static final BlockEntityType<MobSpawnerBlockEntity> MOB_SPAWNER = ...;
    // ... ~60 个
}
```

`BlockEntityType` 干两件事：

1. **工厂**：知道怎么 `new` 一个 T 类型的 BlockEntity（接收 BlockPos + BlockState）。
2. **白名单**：知道这个 BlockEntity type 能和**哪些 Block** 配对（一个 ChestBlockEntity 可以配 `Blocks.CHEST` 也可以配 `Blocks.TRAPPED_CHEST`，但不能配 `Blocks.STONE`）。

`type.isValid(blockState)` 判断"这个 BE type 能不能附加到这个 BlockState 上"。`BlockEntity.validateBlockState`（行 46-50）启动时和拷贝时调用：

```java
private void validateBlockState(BlockState state) {
    if (!this.isValidBlockState(state)) {
        throw new IllegalStateException("Invalid block entity " + ...);
    }
}
```

## 1.7.5 EntityBlock：标记接口

哪些 Block 会有 BlockEntity？

**`net.minecraft.world.level.block.EntityBlock`** 是个 marker 接口：

```java
public interface EntityBlock {
    @Nullable
    BlockEntity newBlockEntity(BlockPos pos, BlockState state);

    @Nullable
    default <T extends BlockEntity> BlockEntityTicker<T> getTicker(Level level, BlockState state, BlockEntityType<T> type) {
        return null;
    }
}
```

任何 `Block` 子类实现 `EntityBlock` = 它的方块需要 BlockEntity。

```java
public class ChestBlock extends AbstractChestBlock<ChestBlockEntity> implements EntityBlock {
    @Override
    public BlockEntity newBlockEntity(BlockPos pos, BlockState state) {
        return new ChestBlockEntity(pos, state);
    }
}
```

`Block` 自己不实现 EntityBlock，所以 `Blocks.STONE` 没有 newBlockEntity 方法。

**判定 + 创建**（用在 LevelChunk.setBlockState 里）：

```java
if (state.hasBlockEntity()) {
    BlockEntity be = ((EntityBlock)state.getBlock()).newBlockEntity(pos, state);
    if (be != null) chunk.setBlockEntity(be);
}
```

`state.hasBlockEntity()` 委托给 Block.hasBlockEntity()，本质是 `block instanceof EntityBlock`。

## 1.7.6 BlockEntity 在 chunk 里怎么存

ChunkAccess（1.5 节）里有：

```java
// ChunkAccess（简化）
private final Map<BlockPos, BlockEntity> blockEntities = new HashMap<>();
private final Map<BlockPos, CompoundTag> pendingBlockEntities = new HashMap<>();
```

**两个 map**：

1. `blockEntities`：实际加载的 BlockEntity 实例。key 是 BlockPos。
2. `pendingBlockEntities`：从 NBT 加载的 BlockEntity NBT 副本，但还没 deserialize 成对象。

**为什么有 pending？** 因为 chunk 加载时：

1. 第一步：先把 BlockState 数据读出来（chunk section）。
2. 第二步：BlockEntity NBT 暂时存进 `pendingBlockEntities`，**先不立刻 deserialize**。
3. 第三步：当某段代码 `getBlockEntity(pos)` 第一次调用，且 pos 在 pending 里，才**懒加载** —— 把 NBT 解出来构造 BE 对象，放入 `blockEntities`。

**懒加载**目的：很多 chunk 加载后玩家根本不打开里面的箱子，懒加载省掉了 deserialize 开销。

`getBlockEntity(pos)` 的实现：

```java
@Nullable
public BlockEntity getBlockEntity(BlockPos pos) {
    BlockEntity be = this.blockEntities.get(pos);
    if (be == null) {
        CompoundTag pending = this.pendingBlockEntities.remove(pos);
        if (pending != null) {
            be = this.promotePendingBlockEntity(pos, pending);
        }
    }
    if (be != null) return be;
    
    // 极端情况：BlockState 应该有 BE，但 chunk 里没记录
    BlockState state = this.getBlockState(pos);
    if (state.hasBlockEntity()) {
        be = ((EntityBlock)state.getBlock()).newBlockEntity(pos, state);
        if (be != null) this.setBlockEntity(be);
    }
    return be;
}
```

**`promotePendingBlockEntity`** = 从 NBT 反序列化 + 加入 blockEntities map。

## 1.7.7 BlockEntity 的 tick：Level 端独立维护

BlockEntity 的 tick 不像 BlockState random tick 那样在 LevelChunkSection 里。

`LevelChunk.tickersInLevel`（1.5.5 节看过）：

```java
private final Map<BlockPos, LevelChunk.RebindableTickingBlockEntityWrapper> tickersInLevel = Maps.newHashMap();
```

**`TickingBlockEntity`** 是个接口：

```java
public interface TickingBlockEntity {
    void tick();
    boolean isRemoved();
    BlockPos getPos();
    String getType();
}
```

**注册时机**：

1. 玩家放置一个 ChestBlock。
2. `LevelChunk.setBlockState` 看到 state.hasBlockEntity() 为 true。
3. 调 `((EntityBlock)block).newBlockEntity(pos, state)` 创建 ChestBlockEntity。
4. 调 `chunk.setBlockEntity(be)` 把 BE 放进 chunk.blockEntities。
5. 看 `((EntityBlock)block).getTicker(level, state, type)` 是否返回非 null —— 如果有，就把 BE 包装成 TickingBlockEntity 放进 `tickersInLevel`。

每 tick：

```java
// ServerLevel.tick → tickBlockEntities
for (TickingBlockEntity ticker : chunk.tickersInLevel.values()) {
    if (!ticker.isRemoved() && ticker.tickEnabled()) {
        ticker.tick();
    }
}
```

**注意只有部分 BlockEntity 需要 tick**——箱子不需要（它没有自动行为），熔炉需要（要烧物品），告示牌不需要。`getTicker` 返回 null 表示"我有 BE 数据但不需要 tick"。

## 1.7.8 BlockEntity 与 BlockState 的同步

**棘手问题**：`BlockEntity.blockState` 字段缓存了关联的 BlockState 引用。如果有人改了世界里的 BlockState（比如把熔炉点燃 / 熄灭：FurnaceBlock 状态 LIT 翻转），BE 的 blockState 字段需要同步更新。

`BlockEntity.setBlockState`：

```java
public void setBlockState(BlockState state) {
    this.validateBlockState(state);
    this.blockState = state;
}
```

调用时机：`LevelChunk.setBlockState` 看到旧方块和新方块都是同一类 BlockEntity（不是 chest → furnace 这种切换），就调 `be.setBlockState(newState)`。

## 1.7.9 BlockEntity 的销毁

BlockEntity 销毁的时序：

1. 玩家挖掉箱子 → `Level.setBlock(pos, AIR.defaultBlockState(), UPDATE_ALL)`。
2. `LevelChunk.setBlockState` 看到 oldState.hasBlockEntity() 但 newState 不是。
3. 调 `chunk.removeBlockEntity(pos)`。
4. 找到 `BlockEntity be = this.blockEntities.remove(pos)`。
5. 调 `be.setRemoved()` —— 设 `this.remove = true`。
6. 调 `level.removeBlockEntity(pos)` —— 从 ServerLevel 的全局活跃 BE 表移除（如果有）。
7. tickersInLevel 里对应的 wrapper.isRemoved() 返回 true → 下次 tick 时被跳过 → 最终被 GC 回收。

**为什么不直接 null 出引用？** 因为可能有别的代码（例如另一个 BE 或某个网络包处理器）还持有该 BE 引用。`setRemoved` flag 是优雅停机机制——所有持有者下次访问时检查 `isRemoved()` 自己释放。

## 1.7.10 序列化：每个 BE 写一个 NBT

BlockEntity 的 NBT 形态：

```
{
    id: "minecraft:chest",
    x: 10,
    y: 64,
    z: 10,
    Items: [
        { Slot: 0b, id: "minecraft:diamond", count: 32 },
        { Slot: 1b, id: "minecraft:stone",   count: 64 }
    ],
    LootTable: "minecraft:chests/abandoned_mineshaft"
}
```

`id` 是 BlockEntityType 的 ResourceLocation；x/y/z 是绝对世界坐标；其余字段由具体 BE 子类定义。

**`saveAdditional`** / **`loadAdditional`** 是子类要重写的方法：

```java
public class ChestBlockEntity extends RandomizableContainerBlockEntity {
    @Override
    protected void saveAdditional(CompoundTag tag, HolderLookup.Provider registries) {
        super.saveAdditional(tag, registries);
        if (!this.trySaveLootTable(tag)) {
            ContainerHelper.saveAllItems(tag, this.items, registries);
        }
    }

    @Override
    protected void loadAdditional(CompoundTag tag, HolderLookup.Provider registries) {
        super.loadAdditional(tag, registries);
        this.items = NonNullList.withSize(this.getContainerSize(), ItemStack.EMPTY);
        if (!this.tryLoadLootTable(tag)) {
            ContainerHelper.loadAllItems(tag, this.items, registries);
        }
    }
}
```

**chunk 序列化时遍历所有 BE**，把每个 BE 的 NBT 收集到 chunk NBT 里：

```nbt
{
    block_entities: [
        { id: "minecraft:chest", x: 10, y: 64, z: 10, Items: [...] },
        { id: "minecraft:furnace", x: 12, y: 64, z: 10, BurnTime: 100, ... },
        ...
    ],
    block_ticks: [...],
    fluid_ticks: [...],
    Heightmaps: { ... },
    sections: [...]
}
```

加载时反过程：chunk 反序列化时把所有 block_entities NBT 放进 `pendingBlockEntities`，懒加载真实对象。

## 1.7.11 1.20.5+ 的 DataComponentMap

`BlockEntity.components` 字段（行 37）是 1.20.5 引入的：

```java
private DataComponentMap components = DataComponentMap.EMPTY;
```

**背景**：1.20.5 之前，每个 ItemStack 携带一份零散的 NBT（"tag"字段）。比如附魔信息、自定义名称、损坏值都各占一个 NBT 子标签。代码层面没有结构化访问 API，全靠 string key 字符串硬查。

1.20.5 引入 **DataComponent** 系统：把所有"附加属性"统一成 `DataComponentType<T> → T` 的强类型 map。原本 ItemStack 的 NBT 改用它，然后扩展到 BlockEntity 上。

```java
// DataComponents.java
public class DataComponents {
    public static final DataComponentType<Component> CUSTOM_NAME = ...;
    public static final DataComponentType<List<Component>> LORE = ...;
    public static final DataComponentType<Integer> DAMAGE = ...;
    public static final DataComponentType<Unbreakable> UNBREAKABLE = ...;
    // ... ~70 个 component type
}

// 用法
component = blockEntity.components.get(DataComponents.CUSTOM_NAME);
```

**这给 BlockEntity 带来什么**？让一些"通用属性"（自定义名称、自定义渲染）不再需要每个 BE 子类自己存——直接放进 components map，统一管理。

**Module 2 NBT 章节会详讲 DataComponent 的内部结构**。这一节你只需要知道"这是 1.20.5 引入的横切机制，BlockEntity 是受益者之一"。

## 1.7.12 内存预算

每个 BlockEntity 实例占用大致：

```
BlockEntity 子类:
├── 对象头                                  : 16 字节
├── type (BlockEntityType 引用)             : 8 字节
├── level                                    : 8 字节
├── worldPosition (BlockPos)                 : 8 字节
├── remove (boolean)                         : 1 字节 (+ padding)
├── blockState                               : 8 字节
├── components (DataComponentMap)            : 8 字节 → 通常空 = ~16 字节
└── 子类专属字段:
    ChestBlockEntity:
    ├── items (NonNullList<ItemStack>) [27]   : ~250 字节 (27 ItemStack 引用 + array 头)
    └── lootTable, lootTableSeed              : ~16 字节
                                                ─────
                                              ≈ 350 字节 / chest

    FurnaceBlockEntity:
    ├── items[3]                                : ~50 字节
    ├── burnTime, cookingProgress, etc          : ~16 字节
                                                ─────
                                              ≈ 200 字节 / furnace

    SignBlockEntity:
    ├── frontText (4 lines)                    : ~150 字节
    ├── backText (4 lines)                     : ~150 字节
                                                ─────
                                              ≈ 350 字节 / sign
```

**对比**：纯方块（如 stone）在 chunk section 里只占 4 个 bit（palette 索引）= 0.5 字节。**Chest 比 stone 多 700 倍内存**——这就是 BlockEntity 的代价。

但好处：**只有需要复杂状态的方块才付这个代价**。整个 chunk 里 BlockEntity 数量通常 ≤ 20 个，总开销 ≤ 10 KB / chunk。

## 1.7.13 与 Entity 的对比

最后强调一次：BlockEntity ≠ Entity。

| 特征 | BlockEntity | Entity |
|------|-------------|--------|
| 位置 | BlockPos（整数） | Vec3（浮点） |
| 对齐到网格 | 是 | 否 |
| 与 chunk 关联 | 在 chunk.blockEntities | 在 ServerLevel.entityManager（按 SectionPos 索引，但跨 section 移动） |
| 存档形式 | 写入 chunk NBT 的 block_entities | 写入 entities/ 目录单独的 region 文件 |
| 网络同步 | ClientboundBlockEntityDataPacket | ClientboundAddEntityPacket + ClientboundSetEntityDataPacket |
| 销毁 | block break / setBlock 触发 | discard() / kill() |
| 例子 | 箱子、熔炉、告示牌 | 玩家、僵尸、箭、物品掉落 |

**实体也分若干类**：

- `Player` / `ServerPlayer` —— 玩家。
- `Mob`（活物）——僵尸、苦力怕、村民、狼、马 ⋯⋯
- `Projectile` —— 箭、雪球、末影珍珠 ⋯⋯
- `ItemEntity` —— 掉落在地上的物品。
- `LightningBolt` / `ExperienceOrb` / `Marker` —— 各种特殊。
- `AbstractMinecart` / `Boat` —— 载具。

实体系统是另一套独立的设计——本教程后面的 Module 4 会涉及实体 tick，但实体系统本身的架构（AI、movement、collision）超出本教程范围。

## 1.7.14 C++ 移植

```cpp
// 类型描述（singleton）
class BlockEntityType {
public:
    using FactoryFn = std::function<std::unique_ptr<BlockEntity>(BlockPos, const BlockState*)>;
    
    BlockEntityType(ResourceLocation id, FactoryFn factory, std::unordered_set<const Block*> validBlocks)
        : id_(std::move(id)), factory_(std::move(factory)), validBlocks_(std::move(validBlocks)) {}
    
    bool isValid(const BlockState& state) const {
        return validBlocks_.contains(state.block());
    }
    
    std::unique_ptr<BlockEntity> create(BlockPos pos, const BlockState* state) const {
        return factory_(pos, state);
    }
    
private:
    ResourceLocation id_;
    FactoryFn factory_;
    std::unordered_set<const Block*> validBlocks_;
};

// 注册表
namespace BlockEntityTypes {
    extern const BlockEntityType* CHEST;
    extern const BlockEntityType* FURNACE;
    extern const BlockEntityType* SIGN;
    // ...
}

// 基类
class BlockEntity {
public:
    BlockEntity(const BlockEntityType* type, BlockPos pos, const BlockState* state);
    virtual ~BlockEntity() = default;

    const BlockEntityType* type() const { return type_; }
    BlockPos pos() const { return pos_; }
    Level* level() const { return level_; }
    void setLevel(Level* l) { level_ = l; }
    bool isRemoved() const { return removed_; }
    void setRemoved() { removed_ = true; }
    const BlockState* blockState() const { return blockState_; }
    void setBlockState(const BlockState* s);

    virtual void saveAdditional(NbtCompound& tag, RegistryAccess& registries) const = 0;
    virtual void loadAdditional(const NbtCompound& tag, RegistryAccess& registries) = 0;
    
    virtual std::unique_ptr<TickingBlockEntity> getTicker(Level& level, const BlockState& state) {
        return nullptr;
    }

protected:
    const BlockEntityType* type_;
    BlockPos pos_;
    Level* level_ = nullptr;
    const BlockState* blockState_;
    bool removed_ = false;
    DataComponentMap components_;
};

// EntityBlock 标记接口
class EntityBlock : public Block {
public:
    virtual std::unique_ptr<BlockEntity> newBlockEntity(BlockPos pos, const BlockState* state) const = 0;
    virtual std::unique_ptr<TickingBlockEntity> getTicker(Level&, const BlockState&, const BlockEntityType*) const {
        return nullptr;
    }
};

// 子类
class ChestBlockEntity : public BlockEntity, public Container {
public:
    ChestBlockEntity(BlockPos pos, const BlockState* state);
    void saveAdditional(NbtCompound&, RegistryAccess&) const override;
    void loadAdditional(const NbtCompound&, RegistryAccess&) override;
    
private:
    std::array<ItemStack, 27> items_;
    std::optional<ResourceLocation> lootTable_;
    int64_t lootTableSeed_ = 0;
};

// 在 ChunkAccess 上
class ChunkAccess {
    // ...
    std::unordered_map<BlockPos, std::unique_ptr<BlockEntity>, BlockPosHash> blockEntities_;
    std::unordered_map<BlockPos, NbtCompound, BlockPosHash> pendingBlockEntities_;
    
public:
    BlockEntity* getBlockEntity(BlockPos pos);
    void setBlockEntity(std::unique_ptr<BlockEntity> be);
    void removeBlockEntity(BlockPos pos);
};
```

**关键工程选择**：

1. **`std::unique_ptr` 拥有 BlockEntity**：chunk 是唯一所有者，外部只持有裸指针。chunk 卸载时 unique_ptr 自动析构。

2. **`virtual saveAdditional/loadAdditional`**：与 Java 一致。但**不要**虚 setBlockState——它对所有 BE 同样实现。

3. **不要做 ECS**：尽管 ECS 的 SoA 内存布局对 entity（玩家、怪物的 ~10000 个实例）很有价值，但 BlockEntity 数量少（一个 chunk ~20 个）、状态各异（不同子类字段差异大）—— **OOP 更合适**。

4. **`TickingBlockEntity` 也用 OOP**：包装 BE + 是否被移除的两字段对象。每 tick 服务端遍历 chunk 的 ticker map。

5. **`pendingBlockEntities` 懒加载** ：照搬 Mojang 的设计，第一次访问才反序列化。

## 1.7.15 实战：跟踪一个箱子的生命周期

```
(1) 玩家手持箱子物品，对一个空气格右键
    → ServerboundUseItemOnPacket 到服务端
    
(2) 服务端 ChestBlock.onPlace(...) 触发
    → ServerLevel.setBlock(pos, CHEST.defaultBlockState().with(FACING, dir), UPDATE_ALL)
    
(3) LevelChunk.setBlockState
    → 看到 newState.hasBlockEntity() = true
    → 调 ((EntityBlock)Blocks.CHEST).newBlockEntity(pos, state)
       = new ChestBlockEntity(pos, state)
    → chunk.setBlockEntity(be)
    → be.setLevel(serverLevel)
    → 包装成 TickingBlockEntity 放进 tickersInLevel
       但 ChestBlockEntity.getTicker = null（箱子不需要 tick）
       所以实际不会进 tickersInLevel
    
(4) 玩家右键打开箱子
    → BE.startOpen(player)
    → 玩家 GUI 显示 27 槽
    → 玩家放入物品
    → BE.items[0] = new ItemStack(...)
    → BE.setChanged() 标 chunk dirty
    
(5) 玩家关闭 GUI
    → BE.stopOpen(player)
    
(6) chunk 卸载
    → ChunkSerializer 序列化 chunk
    → 遍历 chunk.blockEntities
    → 对 ChestBlockEntity 调 saveWithFullMetadata()
    → 写入 chunk NBT 的 block_entities 列表
    → BE 实例被 GC
    
(7) 玩家再来
    → ChunkSerializer 反序列化
    → BE NBT 暂存到 chunk.pendingBlockEntities
    → BE 实例尚未创建
    
(8) 玩家右键再打开
    → chunk.getBlockEntity(pos)
    → 看到 pendingBlockEntities 有 entry
    → promotePendingBlockEntity → 真正反序列化 → 放进 blockEntities
    → BE 现在活了
    
(9) 玩家挖掉箱子
    → ServerLevel.setBlock(pos, AIR, UPDATE_ALL)
    → LevelChunk.setBlockState 看到 oldState.hasBlockEntity = true 但 new 不是
    → 调 chunk.removeBlockEntity(pos)
    → BE.setRemoved()
    → BE 从 blockEntities 移除
    → ChestBlock 同时 dropContents（把里面的物品掉到地上变成 ItemEntity）
```

跟一遍这个流程你应该能对 BE 的生命周期有完整认知。

## 1.7.16 一句话总结

BlockEntity 是"方块附加状态容器"——给那些状态空间过大无法用 BlockState 属性枚举的方块（箱子、熔炉、告示牌、命令方块）提供 mutable 数据；它通过 `EntityBlock` 接口与 Block 关联，运行时由 `LevelChunk.setBlockState` 自动创建 / 销毁；存在 `chunk.blockEntities` 与 `chunk.pendingBlockEntities` 双 map 实现懒加载；少数需要 tick 的 BE 通过 `getTicker` 注册到 `tickersInLevel`；它和 Entity 完全是两类对象（BE 对齐网格、Entity 浮点位置）；纯方块 vs BE 的内存差距是 0.5 字节 vs 200-400 字节，但只有约 20 个 / chunk。
