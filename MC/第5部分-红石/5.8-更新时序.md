# 5.8 更新时序与 BUD

3. 两个红石组件同 tick 同时变化，谁先生效？

## 5.8.1 UPDATE_ORDER 的固定顺序

回顾 4.4.2：

```java
public interface NeighborUpdater {
    Direction[] UPDATE_ORDER = new Direction[]{
        Direction.WEST,    // 0
        Direction.EAST,    // 1
        Direction.DOWN,    // 2
        Direction.UP,      // 3
        Direction.NORTH,   // 4
        Direction.SOUTH    // 5
    };
}
```

**这个 6 元素数组在 vanilla 1.21 是 hardcoded**——所有 neighbor update 严格按这个顺序遍历邻居。

**为什么这么排**？历史原因——Notch 当年随手写下的顺序。后来玩家发现：

- `WEST < EAST` 让"东西方向"的电路有微妙的延迟差。
- `DOWN < UP` 让"上下方向"类似。
- `NORTH < SOUTH` 类似。

**这个顺序成了"红石计算 / 时序的隐式契约"**——成千上万个玩家电路依赖它。Mojang 不敢改。

## 5.8.2 BUD（Block Update Detector）

BUD 是社区发明的"利用 6 邻居更新顺序的机制"。基本思路：

```
[活塞]              [活塞]
   |                   |
[stone] [wire]     [stone] [wire]    ← 改 stone 邻居方块（如挖掉它）
            |              |
       [redstone_torch]  [redstone_torch]
```

如果在活塞**正方向**前面（WEST 或更靠前位置）改方块，活塞会**比通常时序更早**收到 neighbor update —— 在某些场景下能"作弊"性地提早响应。

**经典 BUD 例子**：

- **0-tick BUD**：用相邻方块更新触发活塞，让活塞推动比"正常 1 tick 延迟"还快。
- **方块更新探测器**：检测某个方块状态变化（如生长、年龄变化）。
- **Quasi-connectivity (QC)**：活塞上方对角线被供电时也激活——这是早期 vanilla bug，社区利用率极高。

## 5.8.3 Quasi-connectivity（QC）

Vanilla **历史遗留 bug** —— 现已成为标准红石机制：

```java
// PistonBaseBlock.getNeighborSignal
private boolean getNeighborSignal(Level level, BlockPos pos, Direction facing) {
    for (Direction dir : Direction.values()) {
        if (dir != facing && level.hasSignal(pos.relative(dir), dir)) return true;
    }
    if (level.hasSignal(pos, Direction.DOWN)) return true;
    BlockPos abovePos = pos.above();
    for (Direction dir : Direction.values()) {
        if (dir != Direction.DOWN && level.hasSignal(abovePos.relative(dir), dir)) return true;     // ★ 检测 above 周围
    }
    return false;
}
```

**关键逻辑**：活塞检测**自己上方一格的 5 邻居**（除 DOWN）。这是 QC 的实现——活塞认为"上方的相邻供电"也算"我被供电"。

**视觉表现**：

```
           [wire] ← 这个 wire 没和活塞直接接触
              ↓ 上方
   [piston]
```

正常的电路会期待：wire 不接触活塞 → 活塞不动。但 QC 让上方的 wire 经过 1 格空气仍能激活活塞。**视觉违反直觉但 vanilla 行为**。

**用途**：玩家用 QC 搭建非常紧凑的 piston circuits—— 比如 0-tick piston tower。

**1.21 实验红石的 Orientation 修正**：可选地修正 QC 行为，让信号传播更"物理直觉化"。但这会破坏老电路——所以 vanilla 仍保留 QC。

## 5.8.4 子 tick（subTickOrder）

回顾 4.3：每个 ScheduledTick 有 `subTickOrder` 字段——全局原子递增。

```java
public record ScheduledTick<T>(
    T type, BlockPos pos, long triggerTick, TickPriority priority, long subTickOrder
)

// DRAIN_ORDER comparator
(triggerTick, priority, subTickOrder) → ascending
```

**作用**：当多个 scheduled tick 同 (triggerTick, priority) 时，按 subTickOrder 升序处理 → **确定执行顺序**。

**典型场景**：单 tick 内多个红石变化触发多个 scheduledTick：

```
Tick 0 同时发生:
  Repeater A 触发 schedule (triggerTick=5, priority=HIGH, subTickOrder=100)
  Repeater B 触发 schedule (triggerTick=5, priority=HIGH, subTickOrder=101)
  Repeater C 触发 schedule (triggerTick=5, priority=HIGH, subTickOrder=102)

Tick 5 处理:
  按 subTickOrder 升序 → A 先, 然后 B, 最后 C
```

**A 比 C 早处理 1 个 subtick**——A 的 setBlock 引起的连锁反应可能让 C 看到不同的世界状态。**这种"子 tick 顺序"决定了红石电路的精确时序**。

**对玩家**：subTickOrder 不可见，但**电路行为完全确定**。同一个种子 + 同一系列玩家操作总是产生同样结果。

## 5.8.5 复杂时序：3 中继器同步

一个经典电路：3 中继器并行接收同一信号源：

```
        [wire]
       /  |  \
      ↓   ↓   ↓
   [rep_A] [rep_B] [rep_C]  ← delay = 1 / 2 / 3
       ↓   ↓   ↓
       目标方块
```

```
[Tick 0]
玩家 wire ON
  → wire BFS 分给 3 个 repeater
  → repeater_A.checkTickOnNeighbor → schedule tick triggerTick=1, subTickOrder=10
  → repeater_B → schedule tick triggerTick=2, subTickOrder=11
  → repeater_C → schedule tick triggerTick=3, subTickOrder=12

[Tick 1]
LevelTicks.tick(gameTime=1, ...):
  - 仅 repeater_A.tick → POWERED=true → setBlock + 邻居更新
  - 目标方块从 A 收到信号

[Tick 2]
  - repeater_B.tick → POWERED=true
  - 目标方块从 A + B 收到信号

[Tick 3]
  - repeater_C.tick → POWERED=true
  - 目标方块从 A + B + C 收到信号
```

**3 个中继器按 1/2/3 tick 顺序激活**——subTickOrder 在这种场景不太关键，因为 triggerTick 已经分散。

但当**多 repeater 同 tick 触发**时（罕见但可能），subTickOrder 决定先后。

## 5.8.6 NeighborUpdater 中的 BFS 顺序

CollectingNeighborUpdater.runUpdates 处理顺序：

```java
private void runUpdates() {
    while (!stack.isEmpty() || !addedThisLayer.isEmpty()) {
        // 把 addedThisLayer 倒序压入 stack
        for (int i = addedThisLayer.size() - 1; i >= 0; i--) {
            stack.push(addedThisLayer.get(i));
        }
        addedThisLayer.clear();
        
        // 处理 stack 顶 update
        NeighborUpdates current = stack.peek();
        while (addedThisLayer.isEmpty()) {
            if (current.runNext(level)) {
                // 还有下一步
            } else {
                stack.pop();
                if (stack.isEmpty()) break;
                current = stack.peek();
            }
        }
    }
}
```

**关键**：`addedThisLayer` 的 update 在当前 update 完成前**不**执行——保证当前层级处理完。"倒序 push"让最近添加的下一个执行（DFS 风格）。

**对红石**：当一个 wire 触发邻居更新（multi neighbor update），这个 multi-update 内的 6 邻居顺序按 UPDATE_ORDER；它们触发的更多 update 加到 addedThisLayer 等待。

**每个 update 完成后**才从 addedThisLayer 取下一个。这就是"层级 BFS"——保证近的先完成、远的后处理。

## 5.8.7 红石电路时序的可重现性

**给定**：
- 同一 worldSeed。
- 同一玩家操作序列（按相同时机）。
- 同一 vanilla 版本。

**结果**：同样红石电路产生**完全相同**的行为。

**保证机制**：

1. **6 邻居 UPDATE_ORDER 固定**。
2. **TickPriority 排序确定**。
3. **subTickOrder 全局递增** —— 同 tick 内多次 schedule 按时序确定。
4. **没有线程竞争** —— 全部红石计算在 server 主线程串行。
5. **没有浮点** —— 红石算法纯整数。

**这就是为什么"种子分享"文化能成立** —— 玩家分享种子坐标，朋友能精确复现完整地形 + 红石电路行为。

---

## 5.8.8 不同维度的时序

每个 ServerLevel **独立的 tick 计数 + LevelTicks + ScheduledTick subTickOrder**。

**主世界 / 下界 / 末地之间不互相同步 tick**——但每个维度内部时序确定。

**跨维度信号传输**：vanilla 没有原生方式（除非 mod）。

## 5.8.9 NeighborUpdater + scheduled tick 互动

**问题**：在 neighborChanged 钩子内调用 scheduleTick——schedule 进哪个 tick？

```java
// 假设当前是 gameTime = 100
public void neighborChanged(...) {
    level.scheduleTick(pos, this, 5);     // delay=5
    // 内部：ScheduledTick(triggerTick = 100 + 5 = 105, subTickOrder = nextAtomic())
}
```

**注意**：scheduleTick **不**触发新的 neighbor update。它只是把 ScheduledTick 加入队列。

但 `neighborChanged` 内部可能其他逻辑也调用 `setBlock`：

```java
public void neighborChanged(...) {
    if (someCondition) {
        level.setBlock(pos, newState, UPDATE_ALL);     // ★ 触发 neighbor update 链
    }
    level.scheduleTick(pos, this, 5);
}
```

**setBlock 内的邻居更新立刻处理**（添加到 stack/addedThisLayer 由 BFS 处理），而 scheduleTick 排进未来 tick。两者**互不干扰**。

## 5.8.10 一个具体 BUD 例子

**Quasi-connectivity 的 0-tick piston** 演示：

```
位置布局（俯视）：
            [wire]                  ← Y=2
         [stone] [wire]             ← Y=1（信号到 stone 上）
   [piston]                         ← Y=0（活塞朝东）
```

**触发**：玩家在 Y=1 stone 旁边的 wire 对其 neighborChanged。

```
Tick 0:
  wire (Y=1, X=2) 收到 wire (Y=2, X=1) 的 neighbor update
  → wire (Y=1, X=2).updatePowerStrength
  → 计算到 wire (Y=1, X=2) POWER = 14（来自 wire Y=2 减 1）
  → setBlock(POWER=14, flags=2) + 7 邻居更新
  
  其中一个邻居更新触发 piston (Y=0, X=0)
  → piston.neighborChanged → checkIfExtend
  → getNeighborSignal: 检查 piston 上方（Y=1）周围 → 发现 stone (Y=1, X=1) 被 wire 供 strong indirect
  → hasSignal = true
  → schedule extend BlockEvent

Tick 1: piston 推动。但因为 schedule 在 Tick 0 就发生，效果"瞬时"——只 1 tick 延迟（不是 wire 传到 piston 直接接触位置 + 1 tick 的 2-tick 延迟）。
```

这就是**0-tick** 概念——比预期省 1 tick。利用了 piston 检测 above-neighbors 的 QC 机制。

## 5.8.11 红石电路确定性的 C++ 保证

C++ 移植时要保证：

1. **6 邻居 UPDATE_ORDER 固定**：照搬 `{WEST, EAST, DOWN, UP, NORTH, SOUTH}` 数组。
2. **subTickOrder 用 `std::atomic<int64_t>`** 全局递增。
3. **TickPriority 升序处理**。
4. **不并发**：NeighborUpdater + ScheduledTick + BlockEvent 都在主线程。
5. **不浮点**：所有红石信号 / 计数用 int。

```cpp
namespace mc::redstone {

class NeighborUpdater {
public:
    static constexpr std::array<Direction, 6> UPDATE_ORDER = {
        Direction::WEST, Direction::EAST, Direction::DOWN,
        Direction::UP, Direction::NORTH, Direction::SOUTH
    };
};

}
```

## 5.8.13 一句话总结

红石电路的时序确定性由多层机制保证：固定的 `UPDATE_ORDER = {W, E, D, U, N, S}` 6 邻居顺序（成为玩家依赖的隐式契约）→ NeighborUpdater 的 BFS 算法（addedThisLayer 倒序 push 让近的先完成）→ TickPriority 字段（EXTREMELY_HIGH / VERY_HIGH / HIGH / NORMAL / LOW / VERY_LOW / EXTREMELY_LOW，让信号关 vs 开有不同优先级）→ `subTickOrder` 全局原子递增（让同 (triggerTick, priority) 的 ticks 按"先 schedule 先执行"）；活塞 QC（quasi-connectivity）让 above-neighbor 也算供电源——历史 bug 成为标准机制；BUD（Block Update Detector）利用 UPDATE_ORDER 的方向偏好做 0-tick 电路；同 worldSeed + 同操作必产生完全相同电路行为，是种子分享文化的基石。
