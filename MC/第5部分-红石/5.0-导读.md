# 第 5 部分 · 红石信号传播 —— 导读

## 你为什么需要先读这一部分

红石（redstone）是 Minecraft 最独特的子系统——它把"方块"变成了一个**电路逻辑系统**。玩家用红石线、中继器、比较器、活塞等组件可以搭出从简单门电路到完整 CPU（甚至运行 Doom）的复杂机器。

但作为引擎开发者，红石不是"魔法"——它是**第 4 部分（方块更新）的特化应用**。理解红石就是理解：

1. 信号强度怎么在 redstone wire 网格上传播。
2. 中继器、比较器、活塞各自怎么响应信号变化。
3. 1.21 实验性红石用 Orientation 系统重写 wire 算法解决了什么历史问题。
4. 经典的"BUD（Block Update Detector）"现象怎么从 6 邻居更新顺序产生。
5. 子 tick 顺序如何让看似复杂的电路时序仍然完全确定。

第 5 部分讲清楚 Mojang 的红石底层。读完后你应当能：

- 看到一段红石电路代码（如 `RedStoneWireBlock.neighborChanged`）能立刻知道它在算什么。
- 理解为什么"1.21 实验红石"对老电路有兼容性问题。
- 在 C++ 引擎里实现一个能跑 vanilla 电路的 redstone 子系统。

## 你的目标

读完这一部分你应当能：

1. 区分**信号源**（lever / button / pressure plate / observer）、**传输**（redstone wire / repeater / comparator）、**负载**（piston / lamp / door / dispenser / hopper）三类红石组件。
2. 知道**强信号**（getDirectSignal）vs **弱信号**（getSignal）的差别——为什么红石线接到方块上方块不亮，但中继器接到方块上方块会亮。
3. 看懂 `RedStoneWireBlock.calculateTargetStrength` 算法。
4. 理解 `DefaultRedstoneWireEvaluator`（vanilla）vs `ExperimentalRedstoneWireEvaluator`（1.21+ 实验）的区别。
5. 知道 Orientation 怎么让信号传播携带"来源方向"。
6. 看懂中继器的 1-4 tick 延迟、比较器的减法 / 测量两模式。
7. 理解活塞推动的 `PistonStructureResolver` 算法。
8. 拿到 C++ 移植蓝图。

## 它和其它部分的关系

```
第 4 部分（方块更新）  ← 红石建立在 4 类更新机制之上
                          - scheduled tick → 中继器延迟、火把开关
                          - neighbor update → wire 信号传播
                          - block event → 活塞推动
                          - random tick → 不用（红石不依赖随机）
        │
        ▼
第 5 部分（你在这里：红石）
        │
        └──→ 第 6 部分（流体）—— 第 4 部分的另一特化
        └──→ 第 7 部分（网络）—— 同步红石状态给客户端
```

**强依赖**：第 4 部分（NeighborUpdater / scheduled tick / block event / setBlock flag）是基础。

## 一句话预告

第 5 部分讲清楚 Minecraft 红石作为"建立在第 4 部分方块更新机制之上的电路系统"——红石线在 neighborChanged 钩子内做扁平传播算法（DefaultRedstoneWireEvaluator）；中继器用 scheduled tick 实现 1-4 tick 延迟；比较器用 scheduled tick + 测量 / 减法两模式；活塞用 block event 实现"延迟一 tick 推动 + PistonStructureResolver 决定推哪些方块"；信号强度区分**强信号**（getDirectSignal，被传输了"硬"信号）和**弱信号**（getSignal，被传输了"软"信号），让 wire 接到 stone 不能让 stone 变成信号源；1.21 实验性红石引入 Orientation（携带信号方向）解决经典 wire 更新顺序问题。
