## 3.2.1 ChunkStatus：12 阶段标签

打开 `net.minecraft.world.level.chunk.status.ChunkStatus`（行 20-31）：

```java
public static final ChunkStatus EMPTY                = register("empty",                null,                  WORLDGEN_HEIGHTMAPS, ChunkType.PROTOCHUNK);
public static final ChunkStatus STRUCTURE_STARTS     = register("structure_starts",     EMPTY,                 WORLDGEN_HEIGHTMAPS, ChunkType.PROTOCHUNK);
public static final ChunkStatus STRUCTURE_REFERENCES = register("structure_references", STRUCTURE_STARTS,      WORLDGEN_HEIGHTMAPS, ChunkType.PROTOCHUNK);
public static final ChunkStatus BIOMES               = register("biomes",               STRUCTURE_REFERENCES,  WORLDGEN_HEIGHTMAPS, ChunkType.PROTOCHUNK);
public static final ChunkStatus NOISE                = register("noise",                BIOMES,                WORLDGEN_HEIGHTMAPS, ChunkType.PROTOCHUNK);
public static final ChunkStatus SURFACE              = register("surface",              NOISE,                 WORLDGEN_HEIGHTMAPS, ChunkType.PROTOCHUNK);
public static final ChunkStatus CARVERS              = register("carvers",              SURFACE,               FINAL_HEIGHTMAPS,    ChunkType.PROTOCHUNK);
public static final ChunkStatus FEATURES             = register("features",             CARVERS,               FINAL_HEIGHTMAPS,    ChunkType.PROTOCHUNK);
public static final ChunkStatus INITIALIZE_LIGHT     = register("initialize_light",     FEATURES,              FINAL_HEIGHTMAPS,    ChunkType.PROTOCHUNK);
public static final ChunkStatus LIGHT                = register("light",                INITIALIZE_LIGHT,      FINAL_HEIGHTMAPS,    ChunkType.PROTOCHUNK);
public static final ChunkStatus SPAWN                = register("spawn",                LIGHT,                 FINAL_HEIGHTMAPS,    ChunkType.PROTOCHUNK);
public static final ChunkStatus FULL                 = register("full",                 SPAWN,                 FINAL_HEIGHTMAPS,    ChunkType.LEVELCHUNK);
```

**12 个状态**：

| Index | Status | 输入 | 输出 / 主要工作 |
|-------|--------|------|----------------|
| 0 | EMPTY | — | 占位（chunk 对象创建） |
| 1 | STRUCTURE_STARTS | EMPTY 邻居 | 决定本 chunk 是否是某结构的起点（注册 BoundingBox） |
| 2 | STRUCTURE_REFERENCES | STRUCTURE_STARTS（半径 8） | 把附近 chunk 的结构 BoundingBox 引用到本 chunk |
| 3 | BIOMES | STRUCTURE_STARTS（半径 8） | 给每个 4³ 体素分配 biome |
| 4 | NOISE | BIOMES（半径 1）+ STRUCTURE_STARTS（半径 8）| 通过 NoiseRouter 求 finalDensity，写 BlockState（fluid + 矿脉同时） |
| 5 | SURFACE | NOISE（同上 + 半径 1） | 应用 SurfaceRules 铺草 / 沙 / 雪 |
| 6 | CARVERS | SURFACE（半径 1，blockStateWriteRadius=0）| 雕刻经典管状洞穴 |
| 7 | FEATURES | CARVERS（半径 1）+ STRUCTURE_STARTS（半径 8） | 长树 / 撒矿 / 盖结构（**blockStateWriteRadius=1**，可写邻居） |
| 8 | INITIALIZE_LIGHT | FEATURES | 给光照引擎注册本 chunk |
| 9 | LIGHT | INITIALIZE_LIGHT（半径 1） | 计算天光 + 方块光 |
| 10 | SPAWN | LIGHT + BIOMES（半径 1） | 自然刷怪一次 |
| 11 | FULL | SPAWN | ProtoChunk → LevelChunk 升级 |

**`ChunkType`**：

- `PROTOCHUNK`：status < FULL 时是 ProtoChunk 实例。
- `LEVELCHUNK`：status == FULL 时是 LevelChunk。

**`heightmapsAfter`**：

- `WORLDGEN_HEIGHTMAPS = {OCEAN_FLOOR_WG, WORLD_SURFACE_WG}`：worldgen 阶段用 _WG 版（FULL 后丢弃）。
- `FINAL_HEIGHTMAPS = {OCEAN_FLOOR, WORLD_SURFACE, MOTION_BLOCKING, MOTION_BLOCKING_NO_LEAVES}`：4 种运行期 heightmap。
- 切换点在 **CARVERS**——`SURFACE` 还用 _WG 版，`CARVERS` 起改用 final 版。详见 1.6 节。

## 3.2.2 ChunkStatus 是个简单 enum 吗？

**不是**——它是个 Registry-注册的对象，每个有：

```java
public class ChunkStatus {
    private final int index;
    private final ChunkStatus parent;       // 前一个 status
    private final ChunkType chunkType;
    private final EnumSet<Heightmap.Types> heightmapsAfter;

    public boolean isOrAfter(ChunkStatus other) {
        return this.getIndex() >= other.getIndex();
    }
    
    public boolean isBefore(ChunkStatus other) {
        return this.getIndex() < other.getIndex();
    }
}
```

每个 ChunkStatus 实例知道自己的 parent（前一个）和 index（0-11）。`isOrAfter` / `isBefore` 比较走 index 整数比较。

**为什么用 `Registry.register` 而不是 enum**？因为 mod / datapack 理论上能加新 status（虽然 vanilla 没用过这能力）。Registry 注册让它可扩展。

## 3.2.3 1.21 重构：ChunkStatus → ChunkStep

**1.20 之前**：`ChunkStatus` 是个"全能类"，同时承担：

- 状态标签（"我现在到哪了"）。
- 任务体（"如何从前一个 status 推进到我"）。
- 依赖描述（"我需要哪些邻居 chunk 在哪些 status"）。
- 半径写入合约（"我能写多远的邻居"）。

**问题**：所有这些塞进一个 ChunkStatus 类，**测试困难、修改困难、并发分析困难**。1.20.x 时 Mojang 改任务体调度时一次 PR 改十几个文件。

**1.21 重构**：拆分成 4 个独立概念：

| 类 | 职责 |
|----|------|
| `ChunkStatus` | 仅状态标签（index + parent + chunkType + heightmapsAfter） |
| `ChunkStep` | 描述"如何到达此 status"——含 directDependencies / accumulatedDependencies / blockStateWriteRadius / task |
| `ChunkPyramid` | 12 个 ChunkStep 的有序集合，描述整条流水线 |
| `ChunkStatusTask` | 单步任务体，纯函数 `(WorldGenContext, ChunkStep, StaticCache2D, ChunkAccess) → CompletableFuture<ChunkAccess>` |

**好处**：

1. **`ChunkPyramid` 可数据化**——可以同时存在多个 pyramid（GENERATION_PYRAMID vs LOADING_PYRAMID）。
2. **`ChunkStatusTask` 是纯函数**——可单独测试。
3. **`ChunkStep` 是 record**——immutable、自带 equals。
4. **依赖关系显式化**——`directDependenciesByRadius` 数组直接说明"半径 N 的邻居要在哪个 status"。

## 3.2.4 ChunkStep：单步描述

```java
public record ChunkStep(
    ChunkStatus targetStatus,
    ChunkDependencies directDependencies,
    ChunkDependencies accumulatedDependencies,
    int blockStateWriteRadius,
    ChunkStatusTask task
) {
    public CompletableFuture<ChunkAccess> apply(WorldGenContext ctx, StaticCache2D<GenerationChunkHolder> cache, ChunkAccess chunk) {
        if (chunk.getPersistedStatus().isBefore(this.targetStatus)) {
            ProfiledDuration prof = JvmProfiler.INSTANCE.onChunkGenerate(...);
            return this.task.doWork(ctx, this, cache, chunk).thenApply(c -> this.completeChunkGeneration(c, prof));
        } else {
            return this.task.doWork(ctx, this, cache, chunk);    // 已经过了，直接 task（noop）
        }
    }
}
```

**5 个字段**：

- `targetStatus` —— 我推进到的目标 status。
- `directDependencies` —— 直接要求的邻居 status（半径数组）。
- `accumulatedDependencies` —— 把所有前驱 step 的 directDependencies 累加起来（让 ChunkPyramid 能算出"对一个空 chunk 来说，它需要什么"）。
- **`blockStateWriteRadius`** —— **本 step 可以写多远的邻居 chunk**（详见 3.15 节，跨 chunk 写入）。
- `task` —— 真正的工作函数。

`apply` 方法封装了"如果我已经达到目标 status 就跳过；否则真正执行 task 并推进 status"的逻辑。

## 3.2.5 ChunkDependencies：半径式依赖

打开 `ChunkDependencies`（与 `ChunkStep.Builder` 配合）：

```java
public record ChunkDependencies(ImmutableList<ChunkStatus> byRadius) {
    public int size() { return this.byRadius.size(); }
    public ChunkStatus get(int radius) { return this.byRadius.get(radius); }
    public ChunkStatus getRadiusOf(ChunkStatus status) { ... }
}
```

**`byRadius[i]`** = 半径 i 的邻居必须达到的最小 status。

**例子**：FEATURES 阶段的 directDependencies：

```
byRadius[0] = FEATURES   // 我自己要达到 FEATURES（递归）
byRadius[1] = CARVERS    // 我半径 1 的邻居要至少 CARVERS
... 因为 STRUCTURE_STARTS 半径 8 还要附加：
byRadius[8] = STRUCTURE_STARTS
```

这意味着想推进 chunk(0,0) 到 FEATURES：

- 半径 0：chunk(0,0) 自己已经在 CARVERS。
- 半径 1：(2r+1)² = 9 个 chunk 都至少 CARVERS。
- 半径 8：(2r+1)² = 17×17 = 289 个 chunk 都至少 STRUCTURE_STARTS。

**ChunkPyramid 的 accumulatedDependencies** 是把所有前驱要求**取最大**累加起来——保证一个空 chunk 想直接到 FEATURES 时所有需求都满足。

## 3.2.6 ChunkPyramid：完整流水线配方

打开 `net.minecraft.world.level.chunk.status.ChunkPyramid`：

```java
public record ChunkPyramid(ImmutableList<ChunkStep> steps) {
    public static final ChunkPyramid GENERATION_PYRAMID = new Builder()
        .step(EMPTY,                    s -> s)
        .step(STRUCTURE_STARTS,         s -> s.setTask(ChunkStatusTasks::generateStructureStarts))
        .step(STRUCTURE_REFERENCES,     s -> s.addRequirement(STRUCTURE_STARTS, 8).setTask(ChunkStatusTasks::generateStructureReferences))
        .step(BIOMES,                   s -> s.addRequirement(STRUCTURE_STARTS, 8).setTask(ChunkStatusTasks::generateBiomes))
        .step(NOISE,                    s -> s.addRequirement(STRUCTURE_STARTS, 8).addRequirement(BIOMES, 1).blockStateWriteRadius(0).setTask(ChunkStatusTasks::generateNoise))
        .step(SURFACE,                  s -> s.addRequirement(STRUCTURE_STARTS, 8).addRequirement(BIOMES, 1).blockStateWriteRadius(0).setTask(ChunkStatusTasks::generateSurface))
        .step(CARVERS,                  s -> s.addRequirement(STRUCTURE_STARTS, 8).blockStateWriteRadius(0).setTask(ChunkStatusTasks::generateCarvers))
        .step(FEATURES,                 s -> s.addRequirement(STRUCTURE_STARTS, 8).addRequirement(CARVERS, 1).blockStateWriteRadius(1).setTask(ChunkStatusTasks::generateFeatures))
        .step(INITIALIZE_LIGHT,         s -> s.setTask(ChunkStatusTasks::initializeLight))
        .step(LIGHT,                    s -> s.addRequirement(INITIALIZE_LIGHT, 1).setTask(ChunkStatusTasks::light))
        .step(SPAWN,                    s -> s.addRequirement(BIOMES, 1).setTask(ChunkStatusTasks::generateSpawn))
        .step(FULL,                     s -> s.setTask(ChunkStatusTasks::full))
        .build();
}
```

**这是整个 worldgen 的配方表**。每个 `.step(...)` 注册一个 ChunkStep——指定：

1. 目标 status。
2. 额外 dependency requirements（addRequirement(status, radius)）。
3. blockStateWriteRadius（默认 0）。
4. 任务体（`ChunkStatusTasks` 中的静态方法引用）。

**逐 step 解读**：

### EMPTY
```java
.step(EMPTY, s -> s)
```
什么都不做。chunk 对象刚 new 出来。

### STRUCTURE_STARTS
```java
.step(STRUCTURE_STARTS, s -> s.setTask(ChunkStatusTasks::generateStructureStarts))
```
对本 chunk 决定"我是不是某些 Structure 的起点"。如果是，注册 BoundingBox 到 chunk.structureStarts。

### STRUCTURE_REFERENCES
```java
.step(STRUCTURE_REFERENCES, s -> s
    .addRequirement(STRUCTURE_STARTS, 8)   // 半径 8 内邻居都要 STRUCTURE_STARTS
    .setTask(ChunkStatusTasks::generateStructureReferences))
```
扫附近 17×17 chunk 看哪些 structure 的 BoundingBox 触及本 chunk → 在本 chunk 注册 reference。

**为什么半径 8**？因为最大结构（如 mansion）的 BoundingBox 可达 ~7-8 chunk 跨度。这是 `ChunkStatus.MAX_STRUCTURE_DISTANCE = 8` 的来源。

### BIOMES
```java
.step(BIOMES, s -> s
    .addRequirement(STRUCTURE_STARTS, 8)
    .setTask(ChunkStatusTasks::generateBiomes))
```
`ChunkGenerator.createBiomes` → 对每个 4³ 体素采样 biome（详见 3.7 节）。

### NOISE
```java
.step(NOISE, s -> s
    .addRequirement(STRUCTURE_STARTS, 8)
    .addRequirement(BIOMES, 1)
    .blockStateWriteRadius(0)
    .setTask(ChunkStatusTasks::generateNoise))
```
关键阶段。`NoiseBasedChunkGenerator.fillFromNoise`：构造 NoiseChunk，对每个 cell 计算 finalDensity → 决定固体 / 空气 / 液体（详见 3.5、3.6 节）。

`blockStateWriteRadius(0)` 显式声明只写自己。

### SURFACE
```java
.step(SURFACE, s -> s
    .addRequirement(STRUCTURE_STARTS, 8)
    .addRequirement(BIOMES, 1)
    .blockStateWriteRadius(0)
    .setTask(ChunkStatusTasks::generateSurface))
```
应用 `SurfaceRules`（详见 3.8 节）。

### CARVERS
```java
.step(CARVERS, s -> s
    .addRequirement(STRUCTURE_STARTS, 8)
    .blockStateWriteRadius(0)
    .setTask(ChunkStatusTasks::generateCarvers))
```
跑 `WorldCarver` 雕洞穴（详见 3.10 节）。

### FEATURES
```java
.step(FEATURES, s -> s
    .addRequirement(STRUCTURE_STARTS, 8)
    .addRequirement(CARVERS, 1)
    .blockStateWriteRadius(1)            // ★ 唯一 > 0 的 step！
    .setTask(ChunkStatusTasks::generateFeatures))
```
**注意 `blockStateWriteRadius(1)`** —— 这是整套流水线里**唯一**允许写邻居 chunk 的 step。原因：feature（如树叶、矿脉）会跨 chunk。详见 3.15 节。

`addRequirement(CARVERS, 1)` 表示半径 1 的邻居要先做完 CARVERS——因为 feature 写到邻居的话，邻居的 carver 可能还没打洞，feature 摆放会被覆盖。

### INITIALIZE_LIGHT
```java
.step(INITIALIZE_LIGHT, s -> s.setTask(ChunkStatusTasks::initializeLight))
```
注册 chunk 给 LightEngine（不真的算光，仅初始化结构）。

### LIGHT
```java
.step(LIGHT, s -> s
    .addRequirement(INITIALIZE_LIGHT, 1)
    .setTask(ChunkStatusTasks::light))
```
真正算光照（天光下沉 + 方块光传播）。

### SPAWN
```java
.step(SPAWN, s -> s
    .addRequirement(BIOMES, 1)
    .setTask(ChunkStatusTasks::generateSpawn))
```
`NaturalSpawner.spawnMobsForChunkGeneration` 一次性刷怪（详见 3.13 节）。

### FULL
```java
.step(FULL, s -> s.setTask(ChunkStatusTasks::full))
```
ProtoChunk → LevelChunk 升级（1.5.6 节看过）。chunk 进入运行期。

## 3.2.7 LOADING_PYRAMID：从存档加载的旁路

**问题**：玩家**回到**已生成过的区域时，chunk 数据已经在 `.mca` 文件里。这种 chunk 不需要重新跑 NOISE / SURFACE / CARVERS / FEATURES——已经做过了。

**解法**：另一条 `LOADING_PYRAMID`：

```java
public static final ChunkPyramid LOADING_PYRAMID = new Builder()
    .step(EMPTY,                    s -> s)
    .step(STRUCTURE_STARTS,         s -> s.setTask(ChunkStatusTasks::loadStructureStarts))
    .step(STRUCTURE_REFERENCES,     s -> s)
    .step(BIOMES,                   s -> s)
    .step(NOISE,                    s -> s)
    .step(SURFACE,                  s -> s)
    .step(CARVERS,                  s -> s)
    .step(FEATURES,                 s -> s)
    .step(INITIALIZE_LIGHT,         s -> s.setTask(ChunkStatusTasks::initializeLight))
    .step(LIGHT,                    s -> s.addRequirement(INITIALIZE_LIGHT, 1).setTask(ChunkStatusTasks::light))
    .step(SPAWN,                    s -> s)
    .step(FULL,                     s -> s.setTask(ChunkStatusTasks::full))
    .build();
```

**几乎所有 step 都是 noop**——不重做工作。只有：

- STRUCTURE_STARTS：从 NBT 加载 structureStarts（**`loadStructureStarts`** 而非 `generateStructureStarts`）。
- INITIALIZE_LIGHT / LIGHT：重新算光（光照不持久化，磁盘上没保存）。
- FULL：升级 ProtoChunk → LevelChunk。

**为什么光照要重算**？因为光照与方块状态紧密耦合，存盘后 mod / datapack 改变会让旧光照失效。重算保证一致。

**这是 1.21 重构的优雅之处**——同一套 ChunkStep 抽象支持两条不同的流水线，区别只在 `task` 字段。

## 3.2.8 一个 chunk 怎么从 EMPTY 到 FULL

完整时序（玩家走进新区域）：

```
1. ChunkMap.requestChunk(pos, FULL)
   ▼
2. 检查磁盘：region 文件中有这个 chunk 吗？
   ├── 有  → 用 LOADING_PYRAMID
   └── 没有 → 用 GENERATION_PYRAMID

3. 假设是新 chunk，用 GENERATION_PYRAMID
   ▼
4. ChunkPyramid.getStepTo(FULL).apply(ctx, cache, chunk)
   实际上要先满足 dependencies：
   - 递归往前推 → SPAWN → LIGHT → ... → STRUCTURE_STARTS → EMPTY
   - 所有半径 8 内的邻居先到 STRUCTURE_STARTS
   - 半径 1 内的邻居先到 CARVERS
   - 半径 0（自己）从 EMPTY 一路推到 FEATURES → ... → SPAWN
   ▼
5. step.task.doWork(ctx, step, cache, chunk) 执行各阶段
   ▼
6. 每完成一个 step，chunk.persistedStatus 推进
   ▼
7. 到 FULL，ProtoChunk → LevelChunk，chunk 加入 ServerChunkCache.loadedChunks
   ▼
8. 网络层把 chunk 发给玩家客户端
```

**关键洞察**：流水线推进的"调用者"是 `ChunkMap` / `ServerChunkCache`，不是任意调用方。整个调度集中在一处。

## 3.2.9 并行性

**同 status 不同 chunk 可并行**：比如多个 chunk 同时跑 NOISE（CPU-bound，最适合并行）。

**同 chunk 不同 status 必须串行**：因为后序 step 依赖前序 step 的结果。

**Mojang 用 worker pool**（`Util.backgroundExecutor()`）：

```java
public CompletableFuture<ChunkAccess> doWork(WorldGenContext ctx, ChunkStep step, StaticCache2D cache, ChunkAccess chunk) {
    return CompletableFuture.supplyAsync(() -> {
        // 实际工作
    }, ctx.unpackTaskExecutor());     // 一个共享的后台线程池
}
```

视距 32 chunk² 的服务端，`Util.backgroundExecutor()` 通常 4-8 线程。worldgen 在玩家移动时同时跑十几个 chunk 是常见的。

**这就是 1.21 ChunkStep 重构的并发友好性**——纯函数式 `task.doWork()` 让线程池调度容易，没有共享可变状态（除 chunk 自身）。

## 3.2.10 StaticCache2D：邻居查询面板

`apply(ctx, **cache**, chunk)` 的 `cache` 参数是 `StaticCache2D<GenerationChunkHolder>`——一个 (2r+1)² 的方阵，让 task 能 O(1) 访问邻居 chunk：

```java
// task 内部
ChunkAccess neighbor = cache.get(pos.x + dx, pos.z + dz).getChunkIfPresent(neededStatus);
```

`StaticCache2D` 在 task 调用前已经预填好——所有 dependencies 都在 cache 里。task 不需要自己搞调度。

详见 3.15 节（跨 chunk 写入会用到 cache）。

## 3.2.11 ChunkStatusTasks：12 个静态任务

打开 `net.minecraft.world.level.chunk.status.ChunkStatusTasks`：

```java
public class ChunkStatusTasks {
    public static CompletableFuture<ChunkAccess> passThrough(WorldGenContext ctx, ChunkStep step, StaticCache2D cache, ChunkAccess chunk) {
        return CompletableFuture.completedFuture(chunk);    // EMPTY 用
    }

    public static CompletableFuture<ChunkAccess> generateStructureStarts(...) { ... }
    public static CompletableFuture<ChunkAccess> generateStructureReferences(...) { ... }
    public static CompletableFuture<ChunkAccess> generateBiomes(...) { ... }
    public static CompletableFuture<ChunkAccess> generateNoise(...) { ... }
    public static CompletableFuture<ChunkAccess> generateSurface(...) { ... }
    public static CompletableFuture<ChunkAccess> generateCarvers(...) { ... }
    public static CompletableFuture<ChunkAccess> generateFeatures(...) { ... }
    public static CompletableFuture<ChunkAccess> initializeLight(...) { ... }
    public static CompletableFuture<ChunkAccess> light(...) { ... }
    public static CompletableFuture<ChunkAccess> generateSpawn(...) { ... }
    public static CompletableFuture<ChunkAccess> full(...) { ... }
    public static CompletableFuture<ChunkAccess> loadStructureStarts(...) { ... }
}
```

**每个都是纯函数**——输入 (ctx, step, cache, chunk)，输出 `CompletableFuture<ChunkAccess>`。

实现都很简单——委派给 `ChunkGenerator`、`SurfaceSystem`、`WorldCarver`、`PlacedFeature`、`LightEngine`、`NaturalSpawner` 等子系统。这一层只负责调用顺序与依赖等待。

## 3.2.12 实战追踪：chunk(0, 0) 走完流水线

模拟一个新 chunk(0, 0) 走完整条 GENERATION_PYRAMID：

```
[t=0]  ChunkMap.requestChunk((0,0), FULL)
[t=0]  No disk data, use GENERATION_PYRAMID
[t=0]  ChunkAccess obj created (ProtoChunk(0,0), status=EMPTY)
[t=0]  Dependency walker:
       - To reach FULL, need (0,0) at SPAWN, no further requirements (radius 0)
       - To reach SPAWN, need (0,0) at LIGHT, BIOMES at radius 1
       - To reach LIGHT, need (0,0) at INITIALIZE_LIGHT, INITIALIZE_LIGHT at radius 1
       - ⋯
       - 累积下来：半径 8 内 17×17 = 289 chunk 都需要至少 STRUCTURE_STARTS

[t=0]  调度器创建 17×17 个 ChunkAccess 占位
[t=0]  并行推进所有 chunks 到 STRUCTURE_STARTS（worker pool）

[t=10ms]  17×17 chunks 都到 STRUCTURE_STARTS

[t=10]  推进半径 ≤8 chunks 到 STRUCTURE_REFERENCES（也需要半径 8 内 STRUCTURE_STARTS，已满足）

[t=20]  推进半径 ≤8 chunks 到 BIOMES

[t=30]  推进半径 ≤1 chunks (3×3 = 9) 到 NOISE
        chunk(0,0) 调 NoiseBasedChunkGenerator.fillFromNoise
          ├── 构造 NoiseChunk
          ├── 对每个 cell 角点求 finalDensity
          ├── 三线性插值到 4096 格
          ├── 同时跑 OreVeinifier
          └── 同时跑 Aquifer
        ~50 ms（CPU-heavy）

[t=80]  推进 9 chunks 到 SURFACE，调 SurfaceSystem
        ~10 ms

[t=90]  推进 9 chunks 到 CARVERS，跑 WorldCarver
        ~5 ms

[t=95]  推进 (0,0) 到 FEATURES（要 9 chunks 都 CARVERS，已满足）
        chunk(0,0) 调 ConfiguredFeature 列表
          - lakes
          - underground_ores → OreFeature × N
          - vegetation → TreeFeature, FlowerFeature, GrassFeature
          - top_layer → SnowAndIceFeature
        feature 可能写到邻居（半径 1 内）的 ProtoChunk
        ~20 ms

[t=115] 推进 (0,0) 到 INITIALIZE_LIGHT
        ~1 ms

[t=116] 推进 (0,0) 到 LIGHT（要邻居都 INITIALIZE_LIGHT）
        LightEngine.lightChunk
        ~5 ms

[t=121] 推进 (0,0) 到 SPAWN
        NaturalSpawner.spawnMobsForChunkGeneration
        ~2 ms

[t=123] 推进 (0,0) 到 FULL
        new LevelChunk(serverLevel, protoChunk)
        加入 ChunkSource
        ~1 ms

[t=124] chunk(0,0) ready，发给客户端
```

总耗时 ~120 ms（单核 5950X 估计）。**多 chunk 并行时，单 chunk 实际等待 < 200 ms**——玩家几乎感觉不到延迟。

## 3.2.14 C++ 移植

```cpp
namespace mc::worldgen {

class ChunkStatus {
public:
    int index() const;
    const ChunkStatus* parent() const;
    bool isOrAfter(const ChunkStatus& other) const { return index() >= other.index(); }
    
    static const ChunkStatus EMPTY, STRUCTURE_STARTS, ..., FULL;     // 12 个
};

using ChunkStatusTask = std::function<std::future<ChunkAccess*>(
    WorldGenContext&, const ChunkStep&, StaticCache2D<GenerationChunkHolder>&, ChunkAccess&
)>;

struct ChunkStep {
    const ChunkStatus* targetStatus;
    std::vector<const ChunkStatus*> directDependenciesByRadius;
    std::vector<const ChunkStatus*> accumulatedDependenciesByRadius;
    int blockStateWriteRadius;
    ChunkStatusTask task;

    int getAccumulatedRadiusOf(const ChunkStatus& status) const;
    std::future<ChunkAccess*> apply(WorldGenContext&, StaticCache2D<...>&, ChunkAccess&) const;
};

class ChunkPyramid {
public:
    static const ChunkPyramid GENERATION_PYRAMID;
    static const ChunkPyramid LOADING_PYRAMID;
    
    const ChunkStep& getStepTo(const ChunkStatus& status) const {
        return steps_[status.index()];
    }
    
private:
    std::vector<ChunkStep> steps_;
};

namespace ChunkStatusTasks {
    std::future<ChunkAccess*> passThrough(WorldGenContext&, const ChunkStep&, StaticCache2D<...>&, ChunkAccess&);
    std::future<ChunkAccess*> generateStructureStarts(...);
    std::future<ChunkAccess*> generateBiomes(...);
    std::future<ChunkAccess*> generateNoise(...);
    std::future<ChunkAccess*> generateSurface(...);
    std::future<ChunkAccess*> generateCarvers(...);
    std::future<ChunkAccess*> generateFeatures(...);
    std::future<ChunkAccess*> initializeLight(...);
    std::future<ChunkAccess*> light(...);
    std::future<ChunkAccess*> generateSpawn(...);
    std::future<ChunkAccess*> full(...);
}

}
```

**关键工程选择**：

1. **ChunkStatus 用静态 const 对象，不用 enum**：可扩展（mod 友好）+ 支持多态。
2. **ChunkStep 是 struct（值类型）**：immutable，可拷贝。
3. **ChunkStatusTask 用 `std::function`** 还是函数指针？前者灵活，后者无虚开销。**默认函数指针**，特殊情况用 std::function。
4. **ChunkPyramid 用 static const 单例**：注册期一次性构造。
5. **StaticCache2D 用模板 + std::vector 实现**：固定大小 (2r+1)²，O(1) 索引。
6. **task pool**：用 `std::async` 或自家 thread pool。每个 chunk 提交独立 task，依赖关系通过 future 链表达。

## 3.2.15 一句话总结

ChunkStatus 是 12 阶段流水线标签（EMPTY → STRUCTURE_STARTS → STRUCTURE_REFERENCES → BIOMES → NOISE → SURFACE → CARVERS → FEATURES → INITIALIZE_LIGHT → LIGHT → SPAWN → FULL）；1.21 重构把"如何推进"拆到 `ChunkStep`（含 directDependencies / accumulatedDependencies / blockStateWriteRadius / task）和 `ChunkPyramid`（12 个 step 的有序集合）；`GENERATION_PYRAMID` 是新 chunk 完整流水线，`LOADING_PYRAMID` 是从存档加载的旁路（大部分 step 是 noop）；同 status 不同 chunk 可并行（worker pool），同 chunk 不同 status 严格串行；半径式 dependencies 让结构（半径 8）+ 邻居 carver/feature（半径 1）的依赖明确；唯一 `blockStateWriteRadius > 0` 的 step 是 FEATURES（=1），是跨 chunk 写入的源头。
