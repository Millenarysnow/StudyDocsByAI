## 3.15.1 问题陈述

回顾 3.1.7 / 3.11：

- 一棵橡树的树叶半径 2，可能从树心 (15, Y, 15) 伸到 (17, Y, 17) → 跨进 +X+Z 邻居 chunk。
- 一条矿脉长 ~20 格，跨 2-3 chunk。
- 一座村庄跨 5×5 chunk。
- 一个浮岛 / 大型紫水晶簇可达 8 格半径。

**Worldgen 有跨 chunk 写入需求**——但每个 chunk 是 ProtoChunk 实例，**不能任意访问别的 chunk 的内部数据**。怎么办？

Mojang 1.21 用 **三层机制**：

```
静态契约：       ChunkStep.blockStateWriteRadius
生成期视图：     WorldGenRegion + StaticCache2D
延迟补救：       ProtoChunk.postProcessing[]
```

下面逐一讲。

---

## 3.15.2 三层机制总览

```
玩家走进新区域，要 chunk(0,0) 到 FULL
   │
   │ ChunkPyramid 决定依赖
   ▼
┌──────────────────────────────────────────────────────────────┐
│ 第一层：ChunkStep.blockStateWriteRadius                       │
│   每个 step 显式声明"我可能写多远的邻居 chunk"                │
│   FEATURES step：blockStateWriteRadius = 1                    │
│   其他 step：0                                                 │
│   ↓                                                            │
│   通过 ChunkStep.directDependenciesByRadius 配合：             │
│   FEATURES 启动前，半径 1 内邻居必须 ≥ CARVERS                │
└──────────────────────────────────────────────────────────────┘
   │
   ▼
┌──────────────────────────────────────────────────────────────┐
│ 第二层：WorldGenRegion + StaticCache2D                        │
│   FEATURES step 实际执行时，构造一个 WorldGenRegion           │
│   它内部 hold 一个 (2r+1)² 邻居 chunk 的 StaticCache2D         │
│   Feature 代码调 region.setBlock(pos, state) 透明地写邻居     │
└──────────────────────────────────────────────────────────────┘
   │
   ▼
┌──────────────────────────────────────────────────────────────┐
│ 第三层：ProtoChunk.postProcessing[]                            │
│   某些方块需要"邻居加载完才能验证支撑性"                      │
│   例：一棵藤蔓可能挂在邻居墙上——放置时邻居墙未生成            │
│   解法：把这些方块登记到 postProcessing[] 列表                 │
│   chunk 升级到 FULL 时 LevelChunk.upgrade() 重新验证          │
└──────────────────────────────────────────────────────────────┘
```

## 3.15.3 第一层：ChunkStep 的静态契约

回顾 3.2.6 的 ChunkPyramid：

```java
.step(NOISE,    s -> s.blockStateWriteRadius(0).setTask(...))     // 写半径 0
.step(SURFACE,  s -> s.blockStateWriteRadius(0).setTask(...))     // 写半径 0
.step(CARVERS,  s -> s.blockStateWriteRadius(0).setTask(...))     // 写半径 0
.step(FEATURES, s -> s.addRequirement(CARVERS, 1).blockStateWriteRadius(1).setTask(...))  // ★
```

**只有 FEATURES 是 1**——它声明"我可能向半径 1 的邻居 chunk 写入方块"。

这个声明配合：

```java
.addRequirement(CARVERS, 1)
```

意思是 "FEATURES 启动前，半径 1 内的邻居 chunk 必须已经达到 CARVERS"。

**为什么需要这个**？因为：

- 如果邻居还在 NOISE 阶段，noise 还在动 chunk 内方块。FEATURES 写入会被覆盖。
- 邻居必须至少完成 CARVERS——之后它的方块基本稳定（只剩 FEATURES 阶段会改）。

**Mojang 显式契约化**：每个 step 必须声明 writeRadius + 对应的依赖半径。这是 1.21 重构的最大改进——之前版本依赖关系隐式藏在代码里，bug 频出。

## 3.15.4 第二层：WorldGenRegion

打开 `net.minecraft.server.level.WorldGenRegion`：

```java
public class WorldGenRegion implements WorldGenLevel {
    private final StaticCache2D<GenerationChunkHolder> cache;
    private final ChunkAccess center;
    private final ServerLevel level;
    private final long seed;
    private final LevelData levelData;
    private final RandomSource random;
    private final DimensionType dimensionType;
    private final WorldGenTickAccess<Block> blockTicks;
    private final WorldGenTickAccess<Fluid> fluidTicks;
    private final BiomeManager biomeManager;
    private final ChunkStep generatingStep;
    @Nullable private Supplier<String> currentlyGenerating;
    
    // ⋯ implements WorldGenLevel ⋯
    
    @Override
    public boolean ensureCanWrite(BlockPos pos) {
        int chunkX = SectionPos.blockToSectionCoord(pos.getX());
        int chunkZ = SectionPos.blockToSectionCoord(pos.getZ());
        ChunkPos centerPos = this.center.getPos();
        int dx = Math.abs(centerPos.x - chunkX);
        int dz = Math.abs(centerPos.z - chunkZ);
        if (dx <= this.generatingStep.blockStateWriteRadius() && 
            dz <= this.generatingStep.blockStateWriteRadius()) {
            return true;     // 在写半径内：允许写
        }
        // 超出范围：报错
        Util.logAndPauseIfInIde("Detected setBlock in a far chunk [...] " +
            currentlyGenerating + " at " + pos);
        return false;
    }
    
    @Override
    public boolean setBlock(BlockPos pos, BlockState state, int flags, int recursionLevel) {
        if (!this.ensureCanWrite(pos)) return false;
        ChunkAccess chunk = this.getChunk(pos);
        BlockState old = chunk.setBlockState(pos, state, false);
        if (old != null) {
            this.level.onBlockStateChange(pos, old, state);
        }
        // ⋯
        return true;
    }
}
```

**核心**：

- **`StaticCache2D<GenerationChunkHolder> cache`** —— (2r+1)² 邻居 chunk 的查询面板。
- **`center`** —— 当前正在 generate 的 chunk。
- **`generatingStep`** —— 当前 step。决定 writeRadius。
- **`setBlock(pos, ...)`** 内部：找到 pos 所在的 ChunkAccess（可能不是 center），写入。

**Feature 代码完全透明**：调 `level.setBlockAndUpdate(pos, state)` 时它不知道写到哪个 chunk。WorldGenRegion 自动路由。

**`ensureCanWrite` 的越界保护**：如果 Feature 试图写到 r+1 之外的 chunk → 报错并丢弃。这是**1.21 的安全网**——之前版本可能默默写到错误地方导致地形损坏。

### currentlyGenerating

```java
public void setCurrentlyGenerating(@Nullable Supplier<String> name) {
    this.currentlyGenerating = name;
}
```

每次开始一个 PlacedFeature 前 Mojang 调 `setCurrentlyGenerating(() -> placedFeature.toString())`。这样如果该 feature 越界写，错误日志能直接指明是谁的锅：

```
Detected setBlock in a far chunk [...] minecraft:oak_tree at BlockPos(...)
```

## 3.15.5 StaticCache2D：邻居查询面板

```java
public class StaticCache2D<T> {
    private final int size;        // 边长
    private final int minX;
    private final int minZ;
    private final T[] cache;       // size² 数组
    
    public T get(int x, int z) {
        int dx = x - minX;
        int dz = z - minZ;
        if (dx < 0 || dx >= size || dz < 0 || dz >= size) return null;
        return cache[dx + dz * size];
    }
}
```

**简单的 2D 数组包装**——按 (x, z) chunk 坐标 O(1) 查询。

每个 ChunkStep 执行时，`StaticCache2D` 已经预填好——所有 dependency 在内。task 直接用即可。

## 3.15.6 第三层：ProtoChunk.postProcessing

某些方块**放置时无法立即验证**——需要邻居 chunk 加载完才能确认它"站得住"。例：

- **藤蔓 / 苔藓**：附着在墙上。放置时旁边墙可能还没生成（如果 feature 写在 +X 邻居上、墙在 +Z 邻居上）。
- **掉落沙 / 砾石**：需要下方支撑方块。
- **作物 / 草丛**：需要下面是泥土 / 草方块。

**解法**：登记到 `postProcessing` 列表，chunk 升级到 FULL 时**重新验证**。

```java
// ProtoChunk.java（行 258-）
public void markPosForPostprocessing(BlockPos pos) {
    if (Level.isInSpawnableBounds(pos)) {
        ChunkAccess.getOrCreateOffsetList(this.postProcessing, this.getSectionIndex(pos.getY()))
            .add(packOffsetCoordinates(pos));
    }
}
```

**`postProcessing[sectionIdx]`** 是 `ShortList`——每个 section 一个列表，存"待重验证的本地方块坐标"。

`packOffsetCoordinates(BlockPos)` 把 pos 编码成 short：4 bit X + 4 bit Z + 8 bit relative Y（在 section 内）。1 short = 1 待办方块。

### 升级时的重验证

`LevelChunk` 升级构造（1.5.6）末尾：

```java
public void upgrade() {
    for (int sectionIdx = 0; sectionIdx < this.postProcessing.length; sectionIdx++) {
        if (this.postProcessing[sectionIdx] == null) continue;
        for (short packed : this.postProcessing[sectionIdx]) {
            BlockPos pos = packedToBlockPos(packed, sectionIdx);
            BlockState state = this.getBlockState(pos);
            BlockState newState = Block.updateFromNeighbourShapes(state, this, pos);
            this.level.setBlock(pos, newState, Block.UPDATE_ALL);
        }
    }
}
```

**`Block.updateFromNeighbourShapes`** 让方块"重新询问邻居"：

- 草方块如果下面没有泥土 → 替换为空气。
- 藤蔓如果旁边没墙 → 掉落。
- 楼梯如果旁边的楼梯连接发生变化 → 更新连接形状。

这一步**保证 chunk 数据自洽**。

## 3.15.7 实战追踪：一棵橡树的跨 chunk 故事

**场景**：worldSeed=1，chunk(0,0) 在 FEATURES step 决定在 (15, 64, 15) 长一棵橡树（树心在 chunk 边界）。橡树高 5、树叶半径 2。

**时序**：

```
t0: chunk(0,0) 进入 FEATURES step
    ChunkStatusTasks.generateFeatures 调用
    构造 WorldGenRegion，cache 包含 9 个 chunk (-1..1, -1..1)
    cache 内 chunk(1,0) / chunk(1,1) / chunk(0,1) 都已 ≥ CARVERS

t1: 跑 plains biome 的 VEGETAL_DECORATION step
    抽到 oak_tree PlacedFeature
    placement modifier 决定起点：(15, 64, 15)（chunk(0,0) 内本地 (15, 15)）

t2: TreeFeature.place(ctx) 被调用
    setBlock((15, 64, 15), oak_log) — 写到 chunk(0,0).sections[8]（本 chunk）
    setBlock((15, 65, 15), oak_log) — 写到 chunk(0,0)
    setBlock((15, 66, 15), oak_log) — 写到 chunk(0,0)
    setBlock((15, 67, 15), oak_log) — 写到 chunk(0,0)
    setBlock((15, 68, 15), oak_log) — 写到 chunk(0,0)（树干完成）
    
t3: TreeFeature 调 FoliagePlacer.createFoliage
    blob_radius_2 在树心周围放叶子：
    setBlock((13, 67, 13), oak_leaves) ← 写 chunk(0,0)
    setBlock((14, 67, 13), oak_leaves) ← 写 chunk(0,0)
    setBlock((15, 67, 13), oak_leaves) ← 写 chunk(0,0)
    setBlock((16, 67, 13), oak_leaves) ← ★ 写 chunk(1,0)（cache 中取出）
    setBlock((17, 67, 13), oak_leaves) ← ★ 写 chunk(1,0)
    ⋯
    setBlock((16, 67, 16), oak_leaves) ← ★ 写 chunk(1,1)
    setBlock((17, 67, 17), oak_leaves) ← ★ 写 chunk(1,1)
    ⋯
    
t4: 跨 chunk 写入对 Feature 代码完全透明
    WorldGenRegion.setBlock 内部：
    - ChunkPos targetChunk = (pos.x >> 4, pos.z >> 4) = (1, 0) for (16, 67, 13)
    - dx = |0 - 1| = 1, 在 writeRadius=1 内 ✓
    - cache.get(1, 0) → ProtoChunk(1, 0)
    - ProtoChunk(1, 0).setBlockState((16 & 15)=0, 67 & 15, 13) = oak_leaves
    
t5: TreeFeature 完成
    chunk(0,0) 含树干 + 一部分叶子
    chunk(1,0) 含部分叶子（chunk(0,0) 写入的）
    chunk(0,1) 含部分叶子
    chunk(1,1) 含部分叶子

t6: chunk(0,0) FEATURES step 完成 → 推进到 INITIALIZE_LIGHT → ⋯ → FULL

t7: chunk(1,0) 后续也跑自己的 FEATURES step
    它**不知道也不在乎** chunk(0,0) 的橡树叶子已经写在它上面
    它根据自己的 biome / seed 决定自己长什么树（可能也是 oak_tree）
    如果 chunk(1,0) 决定在 (5, 64, 8) 长另一棵橡树，它的叶子可能与 chunk(0,0) 写过的叶子重叠
    后写覆盖前写——但因为 BlockState 共享 immutable，重叠的 oak_leaves 实际上是同一个引用，不冲突

t8: chunk(0,0) 升级到 FULL
    LevelChunk(0,0) 进入运行期
    叶子在 (15, 67, 16)（chunk(1,0) 内）也已写入

t9: 玩家走过来看到完整的橡树
```

**关键洞察**：橡树**不是"半棵半棵"分两次长**——它整棵在 chunk(0,0) 的 FEATURES step 里**一次性完成**，那一刻 chunk(0,0) 持有 cache 内 4 个 chunk 的可写引用。chunk(1,0) 后来跑自己 FEATURES 时，叶子已经存在了。

## 3.15.8 矿脉跨 chunk

矿脉是 OreVeinifier 在 NOISE 阶段嵌入。它**不需要跨 chunk 写**——因为矿脉的位置完全由噪声场决定，每个 chunk 在自己 NOISE step 时算自己的部分：

```
chunk(0,0).NOISE: 对它的 4096 个方块算 finalDensity + veinifier
  - 某格的 veinToggle / veinRidged / veinGap 决定是不是矿脉
  - 算法是 deterministic：相同 (worldSeed, x, y, z) → 相同结果

chunk(1,0).NOISE: 对它的 4096 个方块算 finalDensity + veinifier
  - 同一矿脉的 chunk(1,0) 部分由它独立算出
  - 因为 noise 连续，结果与 chunk(0,0) 的部分完美拼接
```

**这是矿脉的优雅之处**——不依赖跨 chunk 写，靠噪声连续性自然连接。

## 3.15.9 结构跨多 chunk

回顾 3.12.3 完整时序：

```
STRUCTURE_STARTS：起点 chunk 决定 PiecesContainer，含跨多 chunk 的 piece
STRUCTURE_REFERENCES：所有触及的邻居 chunk 注册 reference
FEATURES：每 chunk 各自的 generateFeatures 中：
  - 调 structureManager.startsForStructure(本 chunk SectionPos)
  - 拿到本 chunk references 的所有 StructureStart
  - 对每个 start 调 placeInChunk
  - placeInChunk 内：扫所有 piece，只生成 piece 在本 chunk box 内的部分
```

**结构不通过 WorldGenRegion 跨 chunk 写**——它通过 references 让每 chunk 各自负责自己的部分。

**为什么不用 WorldGenRegion？** 因为结构 BoundingBox 可达 5×5 chunk，超出 FEATURES 的 writeRadius=1。如果走 WorldGenRegion，FEATURES 的 writeRadius 要设到 8。但其他 feature 不需要这么大半径——会浪费 cache 空间。

**结构的方案更优雅**：先在 STRUCTURE_STARTS 阶段全局算出所有 piece，分发到每个 chunk 的 references；FEATURES 时各 chunk 自取。

## 3.15.10 边界 case

### 玩家走到生成半径边缘

视距 32 chunks 的服务端，玩家在视距边缘的 chunk(31, 0)。它需要跑 FEATURES。FEATURES 需要 chunk(32, 0) 至少 CARVERS。

**ChunkMap 的反应**：扩展生成区域，给 chunk(32, 0) 加载 / 生成到 CARVERS。这是隐式的——玩家只看到自己 chunk 慢慢加载，不会看到边界上"半棵树"。

### Feature 越界写到生成区外

WorldGenRegion.ensureCanWrite 拒绝 + 报错。这是 datapack bug 信号——modder 应当修。

### 一个 chunk 已 FULL，邻居才 FEATURES

不会发生。FULL chunk 周围的 buffer 至少 1 chunk 也是 FULL 或者更高 status。FEATURES 写到 FULL chunk 是禁忌——会触发邻居更新 / 客户端同步等运行期机制，破坏 worldgen 不变量。

### 玩家关服前结构生成途中

StructureStart 已持久化到 chunk NBT。重启后从磁盘读出，继续推进。

### 树叶飘到一个永远不会被加载的远方 chunk

不会发生。WorldGenRegion 限制 writeRadius，不能写到 cache 外。

## 3.15.11 性能

```
WorldGenRegion 构造：~50 微秒（含 cache 填充）
单个 setBlock 在 cache 内路由：~100 ns
单个 markPosForPostprocessing：~100 ns
LevelChunk.upgrade 的重验证：每 chunk 平均 0-50 个待办 → ~5-50 微秒
```

跨 chunk 机制的总开销 < 5% worldgen 时间。可忽略。

---

## 3.15.12 内存预算

```
WorldGenRegion: ~300 字节 + cache (~9 ChunkAccess 引用 × 8 字节) = ~400 字节
StaticCache2D: ~50 字节 + N × pointer
postProcessing[]: 每 chunk 24 个 ShortList。空 chunk ≈ 24 × 16 字节 = 400 字节。复杂场景几 KB。
```

## 3.15.13 C++ 移植

```cpp
namespace mc::worldgen {

template<typename T>
class StaticCache2D {
    int size_;
    int minX_, minZ_;
    std::vector<T> cache_;
public:
    StaticCache2D(int minX, int minZ, int size) 
        : size_(size), minX_(minX), minZ_(minZ), cache_(size * size) {}
    
    T& get(int x, int z) {
        int dx = x - minX_;
        int dz = z - minZ_;
        return cache_[dx + dz * size_];
    }
};

class WorldGenRegion : public WorldGenLevel {
public:
    WorldGenRegion(ServerLevel& level, StaticCache2D<GenerationChunkHolder> cache,
                   const ChunkStep& step, ChunkAccess& center)
        : level_(&level), cache_(std::move(cache)), generatingStep_(step), center_(&center) {}
    
    bool setBlock(BlockPos pos, const BlockState* state, int flags, int recursionLevel = 512) override {
        if (!ensureCanWrite(pos)) return false;
        ChunkAccess* chunk = getChunkForPos(pos);
        return chunk->setBlockState(pos, state, false);
    }
    
    void setCurrentlyGenerating(std::function<std::string()> name) {
        currentlyGenerating_ = std::move(name);
    }
    
private:
    bool ensureCanWrite(BlockPos pos) {
        int chunkX = pos.x >> 4;
        int chunkZ = pos.z >> 4;
        int dx = std::abs(center_->getPos().x - chunkX);
        int dz = std::abs(center_->getPos().z - chunkZ);
        if (dx <= generatingStep_.blockStateWriteRadius() && dz <= generatingStep_.blockStateWriteRadius()) {
            return true;
        }
        LOG_ERROR("setBlock in far chunk by {}", currentlyGenerating_ ? currentlyGenerating_() : "?");
        return false;
    }
    
    ServerLevel* level_;
    StaticCache2D<GenerationChunkHolder> cache_;
    ChunkStep generatingStep_;
    ChunkAccess* center_;
    std::optional<std::function<std::string()>> currentlyGenerating_;
};

class ProtoChunk : public ChunkAccess {
public:
    void markPosForPostprocessing(BlockPos pos) {
        int sectionIdx = sectionIndex(pos.y);
        if (postProcessing_[sectionIdx].empty()) {
            postProcessing_[sectionIdx].reserve(8);
        }
        postProcessing_[sectionIdx].push_back(packLocal(pos));
    }
    
    std::vector<std::vector<int16_t>> postProcessing_;
    
private:
    static int16_t packLocal(BlockPos pos) {
        int localX = pos.x & 15;
        int localY = pos.y & 15;
        int localZ = pos.z & 15;
        return int16_t((localX << 8) | (localZ << 4) | localY);
    }
};

class LevelChunk : public ChunkAccess {
public:
    void upgrade() {
        for (size_t sIdx = 0; sIdx < postProcessing_.size(); sIdx++) {
            for (int16_t packed : postProcessing_[sIdx]) {
                BlockPos pos = unpackToBlockPos(packed, sIdx);
                const BlockState* old = getBlockState(pos);
                const BlockState* updated = Block::updateFromNeighbourShapes(old, *this, pos);
                if (updated != old) {
                    level_->setBlock(pos, updated, BlockUpdateFlags::ALL);
                }
            }
        }
    }
};

}
```

## 3.15.14 一句话总结

跨 chunk 写入由三层保护：(1) `ChunkStep.blockStateWriteRadius` 静态契约 + `directDependenciesByRadius` 半径要求保证 FEATURES step 启动前邻居至少 CARVERS；(2) `WorldGenRegion + StaticCache2D` 让 FEATURES 中的 `setBlock` 透明路由到正确 chunk，越界（r+1 之外）触发 `ensureCanWrite` 报错；(3) `ProtoChunk.postProcessing[]` + `LevelChunk.upgrade()` 给"放置时无法立即验证支撑"的方块（藤蔓 / 落沙 / 草丛）做延迟重验证。结构不走 WorldGenRegion 跨 chunk—— 通过 STRUCTURE_REFERENCES 让每 chunk 各自部署自己的 piece 部分。矿脉不需要跨 chunk 写——靠噪声连续性自然拼接。
