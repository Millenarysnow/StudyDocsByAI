## 7.6.1 模型：服务端权威 + 客户端预测

**问题**：网络有延迟（典型 50-200 ms）。如果玩家所有行为都等服务端响应：

- 按 W → 100 ms 后才看到角色动 → 操控感糟糕。
- 挖方块 → 100 ms 后才消失 → 视觉延迟。

**解法**：客户端**乐观预测**自己玩家行为，等服务端"确认"或"回滚"。

**服务端权威**：

- 服务端是世界状态的唯一真理。
- 客户端不能直接修改世界——只能"请求"行为。
- 服务端校验合法性后**广播**结果给所有客户端。

**客户端预测**：

- 客户端不等服务端响应——立刻执行自己玩家行为。
- 同时发包给服务端"我做了 X"。
- 等服务端 ack：
  - 一致 → 确认，继续。
  - 不一致 → 服务端发"纠正包"让客户端回滚。

## 7.6.2 玩家移动：经典预测

```
[Client tick 0 - 50ms]
玩家按 W → LocalPlayer.move:
  Vec3 newPos = currentPos + velocity * dt;
  this.setPos(newPos);                          // ★ 客户端立刻更新位置
  
ServerboundMovePlayerPacket pkt = new ServerboundMovePlayerPacket.PosRot(newPos.x, newPos.y, newPos.z, ...);
connection.send(pkt);

[Server tick T - 50ms 之后]
ServerGamePacketListenerImpl.handleMovePlayer(pkt):
  PacketUtils.ensureRunningOnSameThread(...);
  
  // 验证合法性
  Vec3 oldPos = player.position();
  Vec3 newPos = pkt.position();
  if (!isValidMovement(oldPos, newPos, dt)) {
      // 不合法 → 回滚
      player.connection.send(new ClientboundPlayerPositionPacket(oldPos, ...));
      return;
  }
  
  // 合法 → 更新服务端 ServerPlayer 位置
  player.absMoveTo(newPos.x, newPos.y, newPos.z);
  
  // 广播给周围玩家
  ChunkMap.entityTrackers.get(player.id).updateMovement(newPos);
  // → broadcast ClientboundMoveEntityPacket

[Client tick 1 - 100ms]
不收到任何回包（服务端默认不发回给本玩家）
→ 客户端预测被服务端"默认确认"

[Client 持续接收 ClientboundMoveEntityPacket of other entities]
→ 渲染其他玩家 / 怪物的移动
```

**关键洞察**：

- 玩家移动是**最高频客户端行为**——每 tick 50ms 都可能发包。
- 服务端不每包都回 ack——**默认无响应即确认**。
- 仅当不合法时才发 ClientboundPlayerPositionPacket "回滚"包。

## 7.6.3 不合法移动：橡皮筋

```
[Client tick 0]
玩家用 cheat 客户端"穿墙"：发 ServerboundMovePlayerPacket(墙后位置)
[Client] LocalPlayer 立刻显示穿墙后

[Server tick T]
handleMovePlayer:
  isValidMovement: distance > 速度上限 → 不合法
  
Server → Client: ClientboundPlayerPositionPacket(原墙前位置, sequenceId=N)

[Client tick T+1]
ClientPacketListener.handlePlayerPosition:
  this.player.absMoveTo(原墙前位置);            // ★ 强制回到墙前
  → 视觉上：玩家"瞬移"回墙前 (橡皮筋)
  发 ServerboundAcceptTeleportationPacket(N)    // 确认收到
```

**橡皮筋的根本原因**：客户端预测错了。

**触发场景**：

- 网络抖动 / 丢包导致客户端 / 服务端 desync。
- 玩家用 cheat（fly / speed hack）。
- 服务端 lag 让客户端走得"太远"。

**避免**：vanilla 的客户端有"超过 5 格速度强制 teleport packet"机制——主动告诉服务端"我意外瞬移了"。

## 7.6.4 1.19+ 方块交互的 sequence ack

1.19+ 引入对**方块交互**（挖、放）的 sequence-based ack：

```java
public record ServerboundUseItemOnPacket(
    InteractionHand hand,
    BlockHitResult hitResult,
    int sequence                     // ★ 客户端递增 sequence
) implements Packet<ServerGamePacketListener> {
}

public record ClientboundBlockChangedAckPacket(int sequence) implements Packet<ClientGamePacketListener> {
}
```

**协议**：

```
[Client]
clientSequence++;     // 全局递增
ServerboundUseItemOnPacket pkt = new ServerboundUseItemOnPacket(MAIN_HAND, hit, clientSequence);
connection.send(pkt);

// 客户端预测：放方块到目标位置
ClientLevel.setBlock(targetPos, expectedState);
clientPredictedPositions.add(clientSequence, targetPos);

[Server tick T]
ServerGamePacketListenerImpl.handleUseItemOn(pkt):
  // 处理放方块
  if (canPlace) {
      ServerLevel.setBlock(targetPos, actualState, UPDATE_ALL);
      // ⋯
  } else {
      // 拒绝：客户端预测错
  }
  
  // 总是发 ack（无论成功失败）
  player.connection.send(new ClientboundBlockChangedAckPacket(pkt.sequence()));
  
  // 如果 ack 服务端版与客户端预测不同：
  // 服务端 setBlock 也会发 ClientboundBlockUpdatePacket 给本玩家
  // 客户端收到 BlockUpdate → 覆盖自己预测

[Client]
ClientPacketListener.handleBlockChangedAck(N):
  // ack 已收到：客户端预测被服务端确认
  clientPredictedPositions.remove(N);

如果预测错（服务端拒绝）：
  ClientboundBlockUpdatePacket(targetPos, AIR) 也发给本玩家
  客户端收到 → 覆盖自己之前预测的"已放方块" → 玩家看到方块消失（"取消"动画）
```

**好处**：

1. **乐观预测**：客户端立刻显示放置，无延迟感。
2. **自动纠错**：服务端拒绝时客户端立刻看到"撤销"。
3. **弱类型 ack**：sequence 单一递增 number——服务端只需 echo 回去，不用维护复杂状态。

## 7.6.5 sequence id 怎么递增

```java
// LocalPlayer
private int clientSequence;

public int generateSequence() {
    return ++this.clientSequence;
}
```

**单调递增**。每次"客户端预测的方块行为"都消耗一个 sequence。

**服务端**：

```java
// ServerPlayer
private int sequenceClock;

public void ackSequence(int sequence) {
    this.sequenceClock = Math.max(this.sequenceClock, sequence);
    this.connection.send(new ClientboundBlockChangedAckPacket(this.sequenceClock));
}
```

服务端**记录最高 ack 的 sequence**——每次处理 packet 时 ack。这让客户端能精确知道"我哪次预测被确认了"。

## 7.6.6 ack 与 BlockUpdatePacket 协调

**服务端在处理玩家放方块的同 tick 内**：

1. 改 chunk → BlockUpdate 加入 ChunkMap.broadcast 队列。
2. 调 player.ackSequence(N) → ack 包入队。

**两个包的发送顺序由 Connection 保证 FIFO**——客户端收到的顺序：

- 先 BlockUpdatePacket (UPDATE_CLIENTS broadcast)。
- 再 BlockChangedAckPacket。

**客户端处理**：

- 收到 BlockUpdate → 立刻应用 setBlock。
- 收到 BlockChangedAck → 移除"待确认预测"记录。

**关键**：BlockUpdate 包**在 ack 之前**——客户端先看到真实结果，再"标记"预测已 ack。如果 BlockUpdate 内容 ≠ 客户端预测，**视觉上玩家看到方块"撤销"**。

## 7.6.7 partialTick 插值（客户端流畅度）

回顾 4.7.8：客户端帧率 60+ FPS，服务端 20 TPS。

```java
// 客户端渲染期
float partialTick = ...;     // 0..1 浮点
double renderX = entity.lastTickX + (entity.posX - entity.lastTickX) * partialTick;
```

**关键**：客户端**接收**ClientboundMoveEntityPacket 时只更新 `entity.posX`（目标位置）。`lastTickX` 是上 tick 的位置。每帧渲染按 partialTick 算插值。

**视觉效果**：实体位置每 50 ms 跳变一次（服务端 tick），但客户端 60 FPS 渲染期间用插值平滑——玩家看到的是连续移动。

**partialTick 由谁算**：

```java
// Minecraft.runTick
float partialTick = ...;     // (now - lastTickTime) / 50_000_000ns
partialTick = Mth.clamp(partialTick, 0, 1);
```

50 ms 一拍——0% 时刚 tick、100% 时下一 tick 即将开始。

## 7.6.8 实体延迟同步

ClientboundMoveEntityPacket 不是每 tick 发——节省带宽：

```java
// ServerEntity (服务端实体追踪器)
public void sendChanges() {
    // 检查这 tick 实体是否动了"足够"
    Vec3 oldPos = ...;
    Vec3 newPos = entity.position();
    
    boolean shouldSendPos = ...;     // 距离 > 阈值 || tickCount % 60 == 0（每 3 秒强制同步）
    boolean shouldSendRot = ...;     // 旋转变化 > 1 度
    
    if (shouldSendPos && shouldSendRot) {
        broadcast(new ClientboundMoveEntityPacket.PosRot(...));
    } else if (shouldSendPos) {
        broadcast(new ClientboundMoveEntityPacket.Pos(...));
    } else if (shouldSendRot) {
        broadcast(new ClientboundMoveEntityPacket.Rot(...));
    }
    
    // 周期性 teleport (避免 delta 累积漂移)
    if (tickCount % 400 == 0) {
        broadcast(new ClientboundTeleportEntityPacket(entity));
    }
}
```

**优化**：

- 静止实体：不发 move 包。
- 微动实体：仅发 pos delta（短整数）。
- 每 20 秒发完整 teleport（防 delta 累积误差）。

## 7.6.9 玩家自己的位置同步特殊

**ServerPlayer 不通过 ClientboundMoveEntityPacket 同步给本玩家**——它只**广播给其他玩家**。

**本玩家**在客户端有 LocalPlayer 实例——客户端预测 + 直接控制。

**只有不合法时**服务端才发 ClientboundPlayerPositionPacket 强制纠正。

```java
public record ClientboundPlayerPositionPacket(
    Vec3 newPos,
    Vec3 deltaMovement,
    float yaw,
    float pitch,
    Set<RelativeMovement> relativeArguments,
    int teleportId             // 客户端 ack 时回传
) implements Packet<ClientGamePacketListener> {
}
```

`teleportId` 单调递增。客户端收到 → 应用 teleport → 发 `ServerboundAcceptTeleportationPacket(teleportId)` 确认。

**relativeArguments**：哪些字段是"绝对"哪些是"相对"。

- `RelativeMovement.X` 在 set → newPos.x 加到当前 x。
- 不在 set → newPos.x 设为新值。

**用途**：仅微调位置（如 1 格内）时只传 delta，节省精度损失。

## 7.6.10 延迟感受

```
玩家到服务器 ping 50 ms：
- 移动按 W: 客户端立刻动 → 0 ms 感知 ✓
- 挖方块: 客户端立刻碎 → ~50 ms 后 BlockUpdate 确认 → 100 ms 后下游影响（其他玩家看到）
- 攻击实体: 立刻挥剑 → ~100 ms 后实体死亡
- 看其他玩家移动: 100-150 ms 延迟（已被插值平滑）

ping 200 ms：
- 移动按 W: 客户端立刻动 ✓
- 挖方块: 客户端立刻碎 → 200 ms 后服务端处理 → 300+ ms 看到下游
- "Combat 不准确"：玩家挥剑挥到实体看似击中位置，服务端验证时实体已不在那里 → 不命中
- 其他玩家移动看起来"slow but smooth"——插值仍然平滑，但"反应快的玩家"看起来反应慢

ping 500+ ms：
- 客户端预测 vs 服务端权威严重分歧：
  - 频繁橡皮筋
  - "Hit registration 失败"
  - 体验糟糕
```

**对比**：FPS 类游戏（Counter-Strike）需要 < 50 ms ping 才"竞技公平"。Minecraft 因玩法不依赖精确反射，对 100-200 ms ping 仍可玩。

## 7.6.11 lag compensation（vanilla 没有）

很多多人游戏（CS-GO、Valorant）有 **lag compensation**——服务端在玩家击中实体时倒回历史状态校验。

**Minecraft 没有 vanilla lag compensation**：

- 玩家挥剑 → 客户端发 ServerboundInteractPacket(target_id, hit_position)。
- 服务端用**当前**位置校验，不倒回历史。
- 高 ping 玩家"打不中"快速移动的目标。

**这是 Minecraft PvP 不"竞技"的根本原因**——但简化了协议，且大部分玩家场景（建筑 / 探险 / 红石）不受影响。

## 7.6.12 一段实战：玩家挖方块 + 放方块

完整时序：

```
[Client tick 0]
玩家按住左键挖方块
ClientPlayerInteractionManager.continueDestroyBlock(pos):
  destroyProgress += 1.0 / blockHardness;
  if (destroyProgress >= 1.0) {
      destroyBlock(pos);
  }

destroyBlock(pos):
  // 客户端预测：方块消失
  ClientLevel.setBlock(pos, AIR, UPDATE_ALL | UPDATE_INVISIBLE);
  // 发包
  int seq = generateSequence();
  ServerboundPlayerActionPacket pkt = new ServerboundPlayerActionPacket(STOP_DESTROY_BLOCK, pos, dir, seq);
  connection.send(pkt);

[Network 50 ms]

[Server tick T]
ServerGamePacketListenerImpl.handlePlayerAction(pkt):
  switch (action) {
    case STOP_DESTROY_BLOCK:
      gameMode.handleBlockBreakAction(pos, action, dir, ...);
      // 检查合法性：玩家距离 / 工具 / 权限
      if (合法):
          ServerLevel.setBlock(pos, AIR, UPDATE_ALL | UPDATE_INVISIBLE);
          // 触发掉落物品 / 邻居更新等
      else:
          // 不合法：什么都不做
      break;
  }
  player.ackSequence(pkt.sequence());

[Server broadcast]
ChunkMap broadcast 给附近玩家：
  ClientboundBlockUpdatePacket(pos, AIR) → 周围玩家
  ClientboundBlockChangedAckPacket(seq) → 本玩家

[Network 50 ms]

[Client tick T+2]
本玩家收到 BlockUpdate(pos, AIR) → ClientLevel.setBlock(pos, AIR)
  → 已经是 AIR（之前预测过）→ 视觉无变化
本玩家收到 BlockChangedAck(seq) → 移除待 ack 队列

其他玩家收到 BlockUpdate(pos, AIR) → ClientLevel.setBlock → 看到方块消失

[如果服务端拒绝]
本玩家**仅**收到 BlockUpdate(pos, ORIGINAL_BLOCK)：
  → 客户端 setBlock(pos, ORIGINAL_BLOCK)
  → 视觉：方块"撤销 / 复位"——著名的"挖了又出现"现象
  
  ack 仍发：BlockChangedAck(seq) → 客户端清待 ack
```

总玩家延迟：**50ms 看不到任何延迟（客户端预测）**，100ms 后服务端确认（无视觉变化），其他玩家 100-150ms 后看到。

## 7.6.13 性能影响

```
ack 机制开销:
- 服务端：每 ServerboundUseItemOnPacket 处理后多发 1 个 ack 包（4 字节 VarInt sequence）
- 客户端：维护"待 ack 预测"列表（< 100 entries 通常）
- 总：~1% 带宽开销，~0% 处理时间

橡皮筋频率:
- 正常网络：< 0.1%（仅 cheat / 极端 lag）
- 200ms ping：~1-5%（常见 cheap rubber-banding）
- 500ms ping：~20%（不可玩）
```

## 7.6.14 C++ 移植

```cpp
namespace mc::client {

class ClientPredictor {
public:
    int nextSequence() { return ++sequence_; }
    
    void recordPrediction(int seq, BlockPos pos, const BlockState* predicted) {
        predictions_[seq] = {pos, predicted};
    }
    
    void onAck(int seq) {
        // 移除 < seq 的所有预测（隐式 ack）
        auto it = predictions_.begin();
        while (it != predictions_.end() && it->first <= seq) {
            it = predictions_.erase(it);
        }
    }
    
private:
    int sequence_ = 0;
    std::map<int, std::pair<BlockPos, const BlockState*>> predictions_;
};

class LocalPlayer {
public:
    void useItemOn(BlockPos pos, BlockHitResult hit) {
        int seq = predictor_.nextSequence();
        const BlockState* expected = computeExpectedPlacement(pos, hit);
        clientLevel_.setBlock(pos, expected, BlockUpdateFlags::ALL | BlockUpdateFlags::INVISIBLE);
        predictor_.recordPrediction(seq, pos, expected);
        
        connection_.send(ServerboundUseItemOnPacket{InteractionHand::MAIN, hit, seq});
    }
    
    void onBlockChangedAck(int sequence) {
        predictor_.onAck(sequence);
    }
    
    void onPlayerPosition(const ClientboundPlayerPositionPacket& pkt) {
        // 强制 teleport
        applyPosition(pkt.newPos, pkt.deltaMovement, pkt.yaw, pkt.pitch, pkt.relativeArguments);
        connection_.send(ServerboundAcceptTeleportationPacket{pkt.teleportId});
    }
    
private:
    ClientPredictor predictor_;
    Connection connection_;
    ClientLevel clientLevel_;
};

}
```

## 7.6.15 一句话总结

Minecraft 用**服务端权威 + 客户端乐观预测**模型——客户端立刻执行玩家行为（移动 / 挖 / 放），同时发包给服务端，等服务端 ack 或回滚；玩家移动默认无 ack（"无响应即确认"），不合法时发 ClientboundPlayerPositionPacket 强制纠正（橡皮筋）；1.19+ 引入 sequence-based ack 机制专门给方块交互——客户端递增 sequence + 服务端 echo 回 ClientboundBlockChangedAckPacket，让客户端精确知道哪次预测被确认；其他实体的位置同步通过 ClientboundMoveEntityPacket（VecDeltaCodec 1/4096 精度），客户端用 partialTick 在两个 tick 位置之间插值平滑；vanilla 无 lag compensation——高 ping 玩家"打不中"，但建筑 / 探险体验仍可玩；ping 200ms 是 Minecraft 可玩上限。
