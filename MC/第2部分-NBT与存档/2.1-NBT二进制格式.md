## 2.1.1 NBT 是什么

**NBT = Named Binary Tag**。Notch 在 Minecraft alpha 1.2（2010 年）发明的一种简单的二进制结构化数据格式。它的设计目标：

1. **自描述**：每个值前面带类型标签（id），不需要 schema 就能解析。
2. **紧凑**：紧密二进制，不像 JSON 有引号和空格。
3. **结构化**：能描述任意嵌套树（`Compound` 和 `List` 给予递归能力）。
4. **简单**：实现一个 parser 几百行代码够了。
5. **跨语言**：纯字节流，任何语言都能读（社区有 Python / Go / Rust / C++ / JS 实现）。

**为什么不用 JSON / XML / Protobuf**？2010 年的背景：

- **JSON** 当时就有，但**纯文本**——10 万方块的 chunk 用 JSON 存盘要几 MB，太慢。
- **XML** 同理 + 啰嗦得离谱。
- **Protobuf**（2008 开源）需要 schema 文件，对 Notch 一个人开发的项目太重。
- **Cap'n Proto / FlatBuffers** 当时还没有。

Notch 最后写了 NBT。后来证明这是个好选择—— NBT 的简单性让社区工具（NBTExplorer、各种 mod 工具）能快速适配，至今仍是 Minecraft 生态的事实标准。

## 2.1.2 12 种 Tag

打开 `net.minecraft.nbt.Tag`（行 11-23）：

```java
public interface Tag {
    byte TAG_END        = 0;
    byte TAG_BYTE       = 1;
    byte TAG_SHORT      = 2;
    byte TAG_INT        = 3;
    byte TAG_LONG       = 4;
    byte TAG_FLOAT      = 5;
    byte TAG_DOUBLE     = 6;
    byte TAG_BYTE_ARRAY = 7;
    byte TAG_STRING     = 8;
    byte TAG_LIST       = 9;
    byte TAG_COMPOUND   = 10;
    byte TAG_INT_ARRAY  = 11;
    byte TAG_LONG_ARRAY = 12;
    byte TAG_ANY_NUMERIC = 99;       // 不是真实 tag，是查询用的"任意数值"匹配 ID
}
```

12 种真实 tag + 1 个 END 哨兵。

| ID | 名字 | 含义 |
|----|------|------|
| 0 | END | Compound 结束哨兵（不是数据） |
| 1 | BYTE | int8（-128..127） |
| 2 | SHORT | int16（-32768..32767） |
| 3 | INT | int32 |
| 4 | LONG | int64 |
| 5 | FLOAT | f32（IEEE 754） |
| 6 | DOUBLE | f64（IEEE 754） |
| 7 | BYTE_ARRAY | int8[]，4 字节长度前缀 + 内容 |
| 8 | STRING | UTF-8 字符串，2 字节长度前缀 + 内容 |
| 9 | LIST | T[]，1 字节元素 type + 4 字节长度 + 内容 |
| 10 | COMPOUND | { String → Tag }，无序 map |
| 11 | INT_ARRAY | int32[]，4 字节长度前缀 + 内容 |
| 12 | LONG_ARRAY | int64[]，4 字节长度前缀 + 内容 |

**注意没有 boolean**——boolean 用 BYTE 替代（0 = false，非 0 = true）。

**没有专门的"对象"类型**——nested 结构靠 COMPOUND 实现。

**注意 LIST vs INT_ARRAY**——前者是 `Tag[]`（每个元素都是任意 Tag），后者是 `int[]`（紧凑的 4 字节整数数组）。同样存 100 个整数，INT_ARRAY 要 400 字节，LIST<INT> 要 100×（1 type id + 4 int 数据） = 500 字节。**性能敏感的场景永远用 INT_ARRAY / LONG_ARRAY**。

## 2.1.3 字节序与基本类型

**所有 NBT 数值都是大端字节序（big-endian）**。

**这不是 JVM 默认**——Java 的 `DataOutputStream` 默认大端，所以 NBT 的字节序契合 Java 网络字节序习惯。

**对照表**（LSB 在右）：

| 类型 | 字节数 | 例子（值 = 0x12345678） |
|------|--------|-----------------------|
| byte  | 1 | `78` |
| short | 2 | `12 34`（high byte first） |
| int   | 4 | `12 34 56 78` |
| long  | 8 | `00 00 00 00 12 34 56 78` |
| float | 4 | IEEE 754 大端，等价于 int32 比特模式 |
| double| 8 | IEEE 754 大端 |

**字符串编码**：

```
[length: u16 BE]   ← 字节数（不是字符数）
[bytes: UTF-8]     ← 内容
```

**注意是 `unsigned short` 长度前缀**，最大字符串字节数 65535。NBT 的字符串实际上是 **Modified UTF-8**（Java 内部的变种，对 NUL 字符特殊处理），但绝大多数情况和标准 UTF-8 相同。**实现时按 UTF-8 处理通常就够**——除非你要处理嵌入 NUL 字节的字符串。

**字符串可以是空字符串**（length = 0）。

## 2.1.4 Tag 的 wire layout

NBT 文件由**一个根级 Tag**组成。**根级 Tag 必须是 COMPOUND**，且必须有名字（即使名字是空字符串）。

每个 Tag 在文件中的二进制结构：

```
Named Tag = [type: u8] [name_length: u16 BE] [name: UTF-8 bytes] [payload]
                                              ↑
                                              type-specific
```

**例外**：在 LIST 或数组 tag 内部，子元素**没有 type 字段也没有 name**——LIST 的 type 一次性写在 list header 里，子元素只有 payload。

**END Tag (id=0)** 是个特例：它**没有** name 字段也没有 payload。它仅仅是 1 字节 0x00，作用是给 COMPOUND 一个结束标记。

### 所有 Tag 的 payload layout

```
END:        (no payload, just the 0x00 type byte itself)

BYTE:       [value: i8]                                    1 byte

SHORT:      [value: i16 BE]                                2 bytes

INT:        [value: i32 BE]                                4 bytes

LONG:       [value: i64 BE]                                8 bytes

FLOAT:      [value: f32 BE]                                4 bytes

DOUBLE:     [value: f64 BE]                                8 bytes

BYTE_ARRAY: [length: i32 BE] [bytes: u8 × length]          4 + n

STRING:     [length: u16 BE] [bytes: UTF-8 × length]       2 + n

LIST:       [element_type: u8] [length: i32 BE]
            [element_payload × length]                     5 + n × elt_size
            * 所有元素必须同 type，但 length=0 时 element_type 可以是 END

COMPOUND:   { [child_type: u8] [child_name_length: u16 BE]
              [child_name: UTF-8] [child_payload]
            }* terminated by [END: u8 = 0]                 ?

INT_ARRAY:  [length: i32 BE] [int32 × length × 4 bytes]    4 + n × 4

LONG_ARRAY: [length: i32 BE] [int64 × length × 8 bytes]    4 + n × 8
```

## 2.1.5 一个完整的 NBT 文件 hex dump

下面是一个最小的 NBT 文件的 hex 表示：

源数据：

```
{
    Hello: "World",
    Number: 42,
    Floats: [1.5f, 2.5f, 3.5f]
}
```

字节流（GZIP 解压后的 raw NBT）：

```
0a 00 00                                          ← ★ 根：COMPOUND id=10, name_len=0, name=""
   08 00 05 48 65 6c 6c 6f                        ← STRING id=8, name_len=5, name="Hello"
      00 05 57 6f 72 6c 64                        ← payload: length=5, "World"
   03 00 06 4e 75 6d 62 65 72                     ← INT id=3, name_len=6, name="Number"
      00 00 00 2a                                  ← payload: 42
   09 00 06 46 6c 6f 61 74 73                     ← LIST id=9, name_len=6, name="Floats"
      05                                           ← element type = FLOAT
      00 00 00 03                                  ← length = 3
      3f c0 00 00                                  ← 1.5f
      40 20 00 00                                  ← 2.5f
      40 60 00 00                                  ← 3.5f
   00                                              ← ★ END marker for root compound
```

整段 47 字节（含 GZIP 后约 50-60 字节）。

逐字段拆解：

```
0a              type=10 (COMPOUND)        ← 根标签
00 00           name_len=0, name=""        ← 根名字（空）

  08            type=8 (STRING)
  00 05         name_len=5
  48 65 6c 6c 6f name="Hello"              (ASCII)
  00 05         payload length=5
  57 6f 72 6c 64 payload="World"

  03            type=3 (INT)
  00 06         name_len=6
  4e 75 6d 62 65 72 name="Number"
  00 00 00 2a   payload=42 (0x2A)

  09            type=9 (LIST)
  00 06         name_len=6
  46 6c 6f 61 74 73 name="Floats"
  05            element_type=5 (FLOAT)
  00 00 00 03   length=3
  3f c0 00 00   1.5 (IEEE 754: sign=0, exp=127, mantissa=0.5)
  40 20 00 00   2.5
  40 60 00 00   3.5

00              END (COMPOUND 终结)
```

**这就是 NBT 的全部规范**。如果你想自己写一个 parser，知道上面这些就够了。

## 2.1.6 SNBT：人类可读的 NBT

游戏里命令系统（`/data get`、`/data merge`、`/give @s diamond_sword{Enchantments:[{id:"sharpness",lvl:5}]}`）等需要在文本里写 NBT。把 NBT 序列化成文本格式叫 **SNBT（Stringified NBT）**。

它**长得像 JSON 但不是 JSON**：

```
{
    Hello: "World",
    Number: 42,
    Floats: [F; 1.5, 2.5, 3.5],
    Bytes: [B; 1b, 2b, 3b],
    Ints: [I; 1, 2, 3],
    Longs: [L; 100L, 200L, 300L],
    Player: {
        Name: "Steve",
        Health: 20.0d
    }
}
```

**与 JSON 的差异**：

1. **类型后缀**：
   - `42` → INT
   - `42b` → BYTE
   - `42s` → SHORT
   - `42L` → LONG
   - `42.0` 或 `42.0d` → DOUBLE
   - `42.0f` → FLOAT
2. **数组前缀**：
   - `[B; ...]` → BYTE_ARRAY
   - `[I; ...]` → INT_ARRAY
   - `[L; ...]` → LONG_ARRAY
   - `[...]` → LIST（普通列表）
3. **键不需要引号**（如果是简单 ASCII 标识符）：`{key: value}` 而不是 JSON 的 `{"key": value}`。
4. **字符串可以单引号或双引号**：`'World'` 或 `"World"`。
5. **没有 `null`**——NBT 没有 null 概念，缺失的字段不存在即可。

SNBT parser / serializer 在 `net.minecraft.nbt.TagParser`、`SnbtPrinterTagVisitor`。命令系统用它，但**存档磁盘里永远是二进制 NBT，不是 SNBT**。SNBT 是给人类用的。

## 2.1.7 GZIP 压缩

**绝大多数 NBT 文件磁盘上是 GZIP 压缩过的**。GZIP 头 `1F 8B` 是二进制识别码。

典型 vanilla 文件：

| 文件 | 是否压缩 | 何处使用 |
|------|---------|---------|
| `level.dat` | GZIP | 世界元数据（种子、名字、玩家位置） |
| `players/<uuid>.dat` | GZIP | 玩家数据 |
| `data/raids.dat` | GZIP | 袭击数据 |
| `region/r.X.Z.mca` 内的 chunk 数据 | DEFLATE / GZIP / 无 / LZ4 | 单 chunk 数据（按 RegionFileVersion 决定） |
| 网络包内的 NBT | 无（已是 packet 内嵌） | 实体数据、BlockEntity 数据 |

**`level.dat` 永远 GZIP**，`.mca` 内的 chunk 默认 DEFLATE（zlib），但可换。后面 2.5 节展开。

**判断 NBT 文件是否压缩**：读前 2 字节，如果是 `1F 8B` → GZIP；否则裸 NBT。

## 2.1.8 一段实战：解码一段真实 chunk 头部

打开任何 vanilla 存档的 `region/r.0.0.mca`，跳过前 8KB（文件头）找到第一个 chunk 的数据：

```
[chunk size: u32 BE]   4 bytes
[compression type: u8] 1 byte
[compressed data: ...] 因为是 chunk-data (size-1) 字节
```

例：

```
00 00 0a c5 02 78 9c ...
```

解读：
- `00 00 0a c5` = chunk 大小 = 2757 字节（含 1 字节 compression type）。
- `02` = compression type = ZLIB（DEFLATE，默认）。
- `78 9c ...` = ZLIB 流魔数 + 数据。

ZLIB 解压后得到一个 NBT CompoundTag 流。把这个流喂给 NBT parser 就能拿到完整 chunk 数据。

后面 2.4 / 2.5 / 2.6 把这个流程完整走一遍。

## 2.1.9 几个常见误区

### 误区 1：NBT 没有 boolean 是设计缺陷？

不是。NBT 早期设计专注紧凑，1 个 BYTE = 1 字节，加 boolean 类型多此一举。社区习惯用 0/1 BYTE 表示 boolean，工具也都默认这么处理。

### 误区 2：NBT 字符串能放任何字符吗？

可以，包括 emoji、CJK 字符。Modified UTF-8 实际上能编码任何 Unicode 码点。但是**NBT 字段名**（compound key）通常用 ASCII，因为它们是程序结构标识，不是给人看的内容。

### 误区 3：LIST 内的元素能不同 type 吗？

不能。LIST 的 element_type 一次性声明，所有元素必须同 type。要混合类型只能用 COMPOUND（每个 entry 各自带 type 标识）。

### 误区 4：为什么字符串长度前缀是 u16 不是 u32？

历史原因——Notch 仿照 Java 的 `DataOutput.writeUTF()` 格式，那个就是 u16 长度。65535 字节对绝大多数字段足够。极少数超长字符串（巨型告示牌内容）会被截断或拒绝。

### 误区 5：NBT 的 List 长度是 `i32`，能放 -1 吗？

技术上能，但 Mojang 视为错误（`length < 0` 抛 NbtException）。实际限制是 `length × element_size <= NbtAccounter.quota`，通常小几个数量级。

## 2.1.10 内存预算

NBT 解析后在 JVM 内存里的代价（典型）：

```
CompoundTag (空): ~48 字节（含对象头 + HashMap 引用 + 空 HashMap）
每个 entry: ~36 字节（HashMap entry 对象 + key 指针 + value 指针）
StringTag: ~28 字节 + UTF-16 string 内部存储
ListTag: ~40 字节 + 元素指针数组
ByteArrayTag (N bytes): ~16 字节 + N 字节数据
Int/Long/Double/Float/Byte/Short Tag: ~16 字节单值（boxed）
```

**注意 NBT 在 JVM 内存里的开销远大于二进制流大小**。一个磁盘上 50 KB 的 chunk NBT，反序列化进 JVM 后可能占 ~300 KB。这就是为什么 NBT 反序列化是有性能预算的（NbtAccounter，2.3 节讲）。

## 2.1.11 C++ 移植：NBT 二进制 layout 处理

C++ 实现 NBT parser 的最小骨架：

```cpp
namespace mc::nbt {
    enum class TagType : uint8_t {
        END = 0, BYTE = 1, SHORT = 2, INT = 3, LONG = 4,
        FLOAT = 5, DOUBLE = 6, BYTE_ARRAY = 7, STRING = 8,
        LIST = 9, COMPOUND = 10, INT_ARRAY = 11, LONG_ARRAY = 12
    };

    // Big-endian 读取
    inline int16_t readBE16(std::span<const std::byte>& bytes) {
        if (bytes.size() < 2) throw std::runtime_error("EOF");
        int16_t v = (int16_t(uint8_t(bytes[0])) << 8)
                  | int16_t(uint8_t(bytes[1]));
        bytes = bytes.subspan(2);
        return v;
    }
    inline int32_t readBE32(std::span<const std::byte>& bytes) {
        if (bytes.size() < 4) throw std::runtime_error("EOF");
        int32_t v = (int32_t(uint8_t(bytes[0])) << 24)
                  | (int32_t(uint8_t(bytes[1])) << 16)
                  | (int32_t(uint8_t(bytes[2])) << 8)
                  | int32_t(uint8_t(bytes[3]));
        bytes = bytes.subspan(4);
        return v;
    }
    inline int64_t readBE64(std::span<const std::byte>& bytes) {
        // ...
    }

    inline std::string readString(std::span<const std::byte>& bytes) {
        uint16_t len = uint16_t(readBE16(bytes));
        if (bytes.size() < len) throw std::runtime_error("EOF");
        std::string s(reinterpret_cast<const char*>(bytes.data()), len);
        bytes = bytes.subspan(len);
        return s;
    }
}
```

**核心 idiom**：始终通过 `std::span<const std::byte>&` 读，每读一段就 advance span。这种方式无分配、无 copy、可组合。

## 2.1.12 一句话总结

NBT 是 Notch 2010 年发明的简单二进制结构化格式，12 种 Tag（END / 6 种基本数值 / BYTE_ARRAY / STRING / LIST / COMPOUND / INT_ARRAY / LONG_ARRAY），全部大端字节序、自描述、自带嵌套；根级必须是带名字的 COMPOUND；磁盘上通常 GZIP 压缩；命令系统用文本变种 SNBT（带类型后缀如 `42b`、数组前缀如 `[I; ...]`）；不支持 null 与 boolean（用 BYTE 替代）；LIST 内元素必须同 type；字符串是 Modified UTF-8 + u16 长度前缀。
