# 2.4 Region 文件 .mca 扇区分配

## 2.4.0 你将在本节学到什么

读完这一节你应当能闭着眼睛回答：

1. 一个 Minecraft 存档的 `region/` 目录里那些 `r.X.Z.mca` 文件到底装的是什么？为什么不是每个 chunk 一个文件？
2. 一个 `.mca` 文件能装多少 chunk？为什么是这个数？
3. 文件头部 8 KB 的内容长什么样？怎么从 `(chunkX, chunkZ)` 算出"我的 chunk 在文件偏移多少"？
4. chunk 大小变化（玩家拆楼或建房让 chunk NBT 长 / 短）时，怎么避免重写整个 .mca？
5. RegionBitmap 是什么？为什么需要它？
6. 我在 C++ 里写一个能 round-trip vanilla `.mca` 的最小读写器，需要多少代码？

---

## 2.4.1 直觉：为什么不是每 chunk 一个文件

最朴素的方案：

```
saves/world1/region/
├── chunk_-1_-1.dat
├── chunk_-1_0.dat
├── chunk_0_0.dat
├── chunk_0_1.dat
├── chunk_1_0.dat
├── chunk_1_1.dat
└── ...几万个文件
```

每个 chunk 一个 ~50 KB 文件。

**为什么 Mojang 不这么做**？

1. **小文件 IO 开销**：一个 chunk 50 KB，但 Windows / Linux 文件系统的 minimum block size 是 4 KB。每个文件实际占至少 4 KB 浪费。
2. **`open / close` 系统调用昂贵**：玩家走过几百个 chunk，要 open / close 上千次文件。
3. **目录扩展问题**：几万个文件在同一个目录，`ls` 慢、index 搜索慢。
4. **filesystem journal 开销**：每个文件 metadata（mtime、atime、size）占空间。
5. **磁盘碎片**：几万个小文件分布在硬盘各处，顺序读慢。

**Notch 早期方案**（Alpha 时期）：每 chunk 一个文件。**世界规模一大就崩**。

**Mojang 的解法（Beta 1.3，2011 年）**：把 32×32 = 1024 个 chunk 打包到一个 `.mca` 文件里。这个文件叫 **Region File**（区域文件，简称 region）。

```
region/
├── r.-1.-1.mca   ← chunks (-32..-1, -32..-1)
├── r.-1.0.mca    ← chunks (-32..-1, 0..31)
├── r.0.0.mca     ← chunks (0..31, 0..31)
└── ...
```

每个 region 大致 5-50 MB，文件数从几万降到几百。

但有个新问题：**chunk 大小不固定**。怎么把 1024 个变长 chunk 装进一个文件、又允许 chunk 变大变小不重写？答案是**扇区分配**。

## 2.4.2 .mca 文件的总体布局

```
┌─────────────────────────────────────────────────────┐
│  Sector 0:  Offset Table     (4 KiB = 1024 entries) │ ← 每个 chunk 的位置表
├─────────────────────────────────────────────────────┤
│  Sector 1:  Timestamp Table  (4 KiB = 1024 entries) │ ← 每个 chunk 的最后保存时间
├─────────────────────────────────────────────────────┤
│  Sector 2:  Chunk data start                        │
│             (chunks of variable size, sector-aligned)│
│             ...                                     │
│  Sector N:  ...                                     │
│  EOF                                                │
└─────────────────────────────────────────────────────┘

Sector size = 4096 bytes (4 KiB)
```

**关键事实**：

1. 文件按 **4 KiB 扇区** 分配。
2. **前 2 个扇区**是头部：4 KiB offset table + 4 KiB timestamp table。
3. **第 2 扇区起**是 chunk 数据，每个 chunk 占连续 N 个扇区（N 可变）。
4. chunk 之间可能有"空洞"——某个 chunk 被删除或缩小后，它原来占的扇区被标为"空闲"。

源码常量（`RegionFile.java` 行 27-35）：

```java
private static final int SECTOR_BYTES = 4096;
protected static final int SECTOR_INTS = 1024;
private static final int CHUNK_HEADER_SIZE = 5;
private static final int HEADER_OFFSET = 0;
private static final ByteBuffer PADDING_BUFFER = ByteBuffer.allocateDirect(1);
private static final String EXTERNAL_FILE_EXTENSION = ".mcc";
private static final int EXTERNAL_STREAM_FLAG = 128;
private static final int EXTERNAL_CHUNK_THRESHOLD = 256;
```

`SECTOR_BYTES = 4096`，`SECTOR_INTS = 1024`（每扇区 1024 个 int）。**两个 int 表都是 1024 entry × 4 字节 = 4 KiB = 1 扇区**。

---

## 2.4.3 Offset Table（Sector 0）

第一个 4 KiB 扇区由 1024 个 32-bit 大端 int 组成。每个 int 编码一个 chunk 的"在文件中的位置 + 大小"：

```
位 31 ... 8 | 位 7 ... 0
sector_idx  | sector_count

sector_idx (24 bit, 高 24 位):  chunk 数据起始扇区下标（值 0 = 该 chunk 不存在）
sector_count (8 bit, 低 8 位):  chunk 占用扇区数（最多 255 扇区 = 1 MiB）
```

源码（行 206-220）：

```java
private int packSectorOffset(int sectorIdx, int sectorCount) {
    return sectorIdx << 8 | sectorCount;
}

private static int getNumSectors(int packed) { return packed & 0xFF; }
private static int getSectorNumber(int packed) { return packed >> 8 & 16777215; }

private static int sizeToSectors(int sizeBytes) {
    return (sizeBytes + 4096 - 1) / 4096;       // 向上取整除以 4096
}
```

**`packed == 0` 表示"该 chunk 不存在"**。这是默认值（offset table 全 0 时整个 region 为空）。

**索引函数**：把 chunk 的 (x, z) 映射到 offset table 的 entry 下标：

```java
private static int getOffsetIndex(ChunkPos pos) {
    return (pos.x & 31) | ((pos.z & 31) << 5);
}
```

（实际实现稍微变化但思路一致）。`(x & 31, z & 31)` 是 chunk 在 region 内的本地坐标 (0..31)，打包成 0..1023 下标。

---

## 2.4.4 Timestamp Table（Sector 1）

第二个 4 KiB 扇区也是 1024 个 32-bit int，每个是该 chunk 最后保存时间（Unix epoch 秒）。

```java
private static int getTimestamp() {
    return (int)(Util.getEpochMillis() / 1000L);
}
```

**`int` 32 位 epoch 秒**——会在 2038 年溢出。但这只是元数据，不影响游戏逻辑。

---

## 2.4.5 Chunk 数据扇区

从 sector 2 起，每个 chunk 占连续若干扇区。每个 chunk 数据的开头有 5 字节的 chunk header：

```
Sector N:
┌─────────────────────────────────────────────────┐
│ [length: u32 BE]  压缩后的数据长度（不含本字段）│  4 字节
├─────────────────────────────────────────────────┤
│ [compression_type: u8]   1 / 2 / 3 / 4 / 127     │  1 字节
├─────────────────────────────────────────────────┤
│ [compressed_data: bytes × (length - 1)]          │  length-1 字节
├─────────────────────────────────────────────────┤
│ [padding to next sector boundary]                │  填到 4 KiB 倍数
└─────────────────────────────────────────────────┘
```

`length` 是 5 字节 header **之后**的数据长度（含 1 字节 compression type）。

**注意**：

- `length` 是大端 i32，最大约 2^31 ≈ 2 GiB（实际限制 256 扇区 = 1 MiB）。
- compression_type 高位（bit 7 = 0x80）= "数据在外部文件 .mcc"，下面 2.5 节展开。
- 数据本身是已压缩的（DEFLATE / GZIP / LZ4），需要先解压才能得到 NBT bytes。

## 2.4.6 读 chunk 的完整流程

打开 `RegionFile.getChunkDataInputStream`（行 114-156）：

```java
@Nullable
public synchronized DataInputStream getChunkDataInputStream(ChunkPos pos) throws IOException {
    int packedOffset = this.getOffset(pos);
    if (packedOffset == 0) return null;     // chunk 不存在

    int sectorIdx = getSectorNumber(packedOffset);
    int sectorCount = getNumSectors(packedOffset);
    int regionLen = sectorCount * 4096;
    
    ByteBuffer buf = ByteBuffer.allocate(regionLen);
    this.file.read(buf, (long)(sectorIdx * 4096));     // 1. 读所有扇区
    buf.flip();
    
    if (buf.remaining() < 5) {
        LOGGER.error("Chunk header truncated: {}", pos);
        return null;
    }
    
    int dataLen = buf.getInt();         // 2. 读 length
    byte compType = buf.get();          // 3. 读 compression type
    if (dataLen == 0) return null;
    
    int payloadLen = dataLen - 1;
    if (isExternalStreamChunk(compType)) {
        return this.createExternalChunkInputStream(pos, getExternalChunkVersion(compType));
    }
    if (payloadLen > buf.remaining()) {
        LOGGER.error("Chunk stream truncated");
        return null;
    }
    if (payloadLen < 0) {
        LOGGER.error("Negative size");
        return null;
    }
    
    return this.createChunkInputStream(pos, compType, createStream(buf, payloadLen));
}
```

**步骤**：

1. 查 offset table → 拿到 (sector_idx, sector_count)。
2. 一次 `read` 把所有扇区读进 ByteBuffer（4 KiB 对齐 IO）。
3. 从 buffer 解出 5 字节 chunk header（length + compression_type）。
4. 根据 compression_type 选解压器（GZIP / DEFLATE / 无 / LZ4）包装 InputStream。
5. 返回 DataInputStream，调用方可以直接 `NbtIo.read(dis)` 出 CompoundTag。

`synchronized` 锁是 **per-RegionFile**——一个 region 文件同一时间只允许一个线程读 / 写。这个锁很简单但足够，因为 IOWorker 单线程已经把 IO 串行化。

## 2.4.7 写 chunk：扇区分配的精髓

`getChunkDataOutputStream`（行 270-272）：

```java
public DataOutputStream getChunkDataOutputStream(ChunkPos pos) throws IOException {
    return new DataOutputStream(this.version.wrap(new RegionFile.ChunkBuffer(pos)));
}
```

返回一个特殊的 `ChunkBuffer`——它内部是个 `ByteArrayOutputStream`。所有 write 调用先写到内存 buffer，**关闭流时**才真正 flush 到文件。

**关闭时的 flush 逻辑**（`ChunkBuffer.close()` 简化）：

```java
public void close() throws IOException {
    ByteBuffer buf = ByteBuffer.wrap(this.toByteArray());     // 内存里的压缩数据
    int payloadLen = buf.remaining();
    int totalLen = payloadLen + 5;                            // 加上 header
    int sectorsNeeded = sizeToSectors(totalLen);              // ceil(totalLen / 4096)
    
    if (sectorsNeeded >= 256) {
        // 数据太大，超过单 chunk 256 扇区限制 → 写到外部 .mcc 文件
        writeChunkToExternalFile(this.pos, buf, ...);
        return;
    }

    int oldOffset = RegionFile.this.getOffset(this.pos);
    int oldSectorIdx = getSectorNumber(oldOffset);
    int oldSectorCount = getNumSectors(oldOffset);

    // ★ 决定写到哪：尝试复用旧位置
    int newSectorIdx;
    if (sectorsNeeded == oldSectorCount) {
        newSectorIdx = oldSectorIdx;     // 大小不变，原位写
    } else {
        // 大小变了，需要重新分配
        if (oldOffset != 0) {
            usedSectors.free(oldSectorIdx, oldSectorCount);    // 释放旧位置
        }
        newSectorIdx = usedSectors.allocate(sectorsNeeded);    // 找新位置
    }

    // 写 header + payload + padding
    writeChunkData(newSectorIdx, buf, payloadLen);

    // 更新 offset table 与 timestamp table
    int newPackedOffset = packSectorOffset(newSectorIdx, sectorsNeeded);
    RegionFile.this.setOffset(this.pos, newPackedOffset);
    RegionFile.this.setTimestamp(this.pos, getTimestamp());
    
    RegionFile.this.flush();    // fsync
}
```

**关键设计**：

1. **大小不变 → 原位重写**。最常见情况，几乎没开销。
2. **大小变了 → 释放旧扇区 + 分配新扇区**。释放后新分配可能"碰巧"找回原位置（如果空间够）。
3. **释放是元数据操作**——RegionBitmap 标 0；扇区里的旧数据其实还在，下次分配时被覆写。
4. **超过 256 扇区**（1 MiB）→ 走外部文件机制（2.5 节）。

## 2.4.8 RegionBitmap：扇区位图

打开 `net.minecraft.world.level.chunk.storage.RegionBitmap`：

```java
public class RegionBitmap {
    private final BitSet used = new BitSet();

    public void force(int sectorIdx, int count) {
        this.used.set(sectorIdx, sectorIdx + count);
    }

    public void free(int sectorIdx, int count) {
        this.used.clear(sectorIdx, sectorIdx + count);
    }

    public int allocate(int count) {
        int i = 0;
        while (true) {
            int j = this.used.nextClearBit(i);     // 下一个空闲位
            int k = this.used.nextSetBit(j);       // 之后的下一个占用位
            if (k == -1 || k - j >= count) {       // 找到 count 个连续空闲位
                this.force(j, count);
                return j;
            }
            i = k;
        }
    }
}
```

**核心是 first-fit 策略**：

```
扇区位图：     [SS UU SS UU UU SS SS] = sectors 0-6
              0  1  2  3  4  5  6
S = used, U = free

allocate(2) 找连续 2 个 U：
  nextClearBit(0) = 1
  nextSetBit(1) = 2
  ranges: [1..2) — only 1 free, not enough
  
  nextClearBit(2) = 3
  nextSetBit(3) = 5
  ranges: [3..5) — 2 free, enough!
  
  allocate(2) returns 3, marks 3..5 as used
```

**这是经典的 "first-fit allocator"**。Java 的 `BitSet.nextClearBit / nextSetBit` 是 word-stride（一次扫 64 bit），效率很好。

**碎片问题**：长期运行后扇区位图可能高度碎片化。Mojang 不主动 defragment——但因为 Minecraft 的常态是"chunk 大小波动很小"，碎片在实际上不严重。如果真有人想 defrag，第三方工具（如 MCEdit）能做。

`force(0, 2)` 在 RegionFile 构造时被调用，把头部 2 个扇区标记为已用：

```java
this.usedSectors.force(0, 2);
```

加载已存在的 region 时，从 offset table 重建 used 位图：

```java
// RegionFile 构造（行 82-100，简化）
for (int idx = 0; idx < 1024; idx++) {
    int packed = this.offsets.get(idx);
    if (packed != 0) {
        int sectorIdx = getSectorNumber(packed);
        int sectorCount = getNumSectors(packed);
        // ... 校验 ...
        this.usedSectors.force(sectorIdx, sectorCount);
    }
}
```

## 2.4.9 单扇区限制：256 扇区 = 1 MiB

`sectorCount` 用 8 bit 存 → 最大 255。**单 chunk 在文件内部最多 1 MiB**（255 × 4 KiB ≈ 1.02 MiB）。

**问题**：现实中复杂 chunk 偶尔超过 1 MiB（比如 1000 个 BlockEntity、复杂 jigsaw 结构、某些 mod）。

**解法**：超出阈值 (`EXTERNAL_CHUNK_THRESHOLD = 256`) 的 chunk 写到外部文件 `c.X.Z.mcc`：

```java
private Path getExternalChunkPath(ChunkPos pos) {
    String name = "c." + pos.x + "." + pos.z + ".mcc";
    return this.externalFileDir.resolve(name);
}
```

外部文件每个 chunk 一份。`.mcc` 文件就是裸压缩流，没有 region 头。

主 region 文件中该 chunk 的 entry：
- `length = 1`（dummy，仅写 1 字节 compression type 占位）。
- `compression_type` 高位 bit 7 (0x80) 设为 1，表示"外部文件指针"。

```java
private static boolean isExternalStreamChunk(byte compType) {
    return (compType & 128) != 0;
}

private static byte getExternalChunkVersion(byte compType) {
    return (byte)(compType & ~128);    // 清除高位拿到原 compression_type
}
```

读取时 `getChunkDataInputStream` 看到 external flag，转去打开 `.mcc` 文件。

后面 2.5 节再展开。

## 2.4.10 读 chunk 的 hex 实战

模拟一个真实的 `.mca` 内容（节选）：

```
Offset: 0x0000 (Sector 0 - Offset Table)
─────────────────────────────────────────────
00000000  00 00 02 03  00 00 00 00  00 00 00 00  00 00 00 00
                        ↑ 第 0 个 chunk 的 packed offset
            
解读:
  bytes [0..4) = 00 00 02 03 (大端) = 0x00000203
  sector_idx  = 0x000002 = 2     ← 从扇区 2 开始
  sector_count = 0x03    = 3     ← 占 3 个扇区 (12 KiB)

Offset: 0x1000 (Sector 1 - Timestamp Table)
─────────────────────────────────────────────
00001000  68 5b 12 e8  00 00 00 00  ...
                        ↑ epoch seconds 0x685b12e8 = 2024-06-24 ...

Offset: 0x2000 (Sector 2 - Chunk (0,0) Data Start)
─────────────────────────────────────────────
00002000  00 00 0a c5  02 78 9c ed  9c 5d 8c 1c c7 79 ...
              ↑           ↑  ↑
              size=2757   |  ZLIB magic
                          compression=2 (DEFLATE)

  bytes [0..4) = 00 00 0a c5 = 2757    ← 数据长度 (含 1 byte compression type)
  byte  [4]    = 02                     ← compression = ZLIB / DEFLATE
  bytes [5..2761) = 压缩 chunk NBT      ← 2756 字节 zlib stream
```

把 `bytes[5..2761)` 喂给 zlib 解压 → 得到原始 NBT bytes → 喂给 `NbtIo.read` → 得到 CompoundTag。

## 2.4.11 文件初始化与同步

```java
public RegionFile(RegionStorageInfo info, Path path, Path externalFileDir, RegionFileVersion version, boolean syncWrites) throws IOException {
    // ...
    this.offsets = this.header.asIntBuffer();
    this.offsets.limit(1024);
    this.header.position(4096);
    this.timestamps = this.header.asIntBuffer();

    if (syncWrites) {
        this.file = FileChannel.open(path,
            StandardOpenOption.CREATE,
            StandardOpenOption.READ,
            StandardOpenOption.WRITE,
            StandardOpenOption.DSYNC      // 每次 write 都 fsync data
        );
    } else {
        this.file = FileChannel.open(path,
            StandardOpenOption.CREATE,
            StandardOpenOption.READ,
            StandardOpenOption.WRITE
        );
    }
    
    this.usedSectors.force(0, 2);          // 扇区 0、1 永远占用（header）
    this.header.position(0);
    int read = this.file.read(this.header, 0L);
    if (read != -1 && read != 8192) {
        LOGGER.warn("Region file {} has truncated header: {}", path, read);
    }
    // ... 重建 usedSectors ...
}
```

`StandardOpenOption.DSYNC` 是关键 —— 它要求数据 write 后操作系统 fsync **数据**到磁盘（但不一定 fsync 元数据，比 SYNC 略快）。`syncWrites = true` 时启用。

`flush()` 调 `this.file.force(true)` 强制全部内容（数据 + 元数据）写盘。这是双保险。

## 2.4.12 Header 的 IntBuffer 视图

注意 RegionFile 用一个 8 KiB 的 ByteBuffer 同时表达 offset table 和 timestamp table：

```java
private final ByteBuffer header = ByteBuffer.allocateDirect(8192);
private final IntBuffer offsets;
private final IntBuffer timestamps;
```

构造时：

```java
this.offsets = this.header.asIntBuffer();   // 视图：把 header 视作 IntBuffer
this.offsets.limit(1024);                    // 只用前 1024 个 int = 前 4 KiB
this.header.position(4096);                  // 移动 byte position 到第 4096 byte
this.timestamps = this.header.asIntBuffer(); // 第二个视图：从 4096 起
```

这是 NIO 的"零拷贝视图"技巧。改 `offsets[i]` 等价于改 `header.bytes[i*4..i*4+4]`，再 `header.write(file, 0)` 一次性 flush。

## 2.4.13 完整流程：从 ChunkPos 到 CompoundTag

```
1. 给定 ChunkPos(150, -200)
2. RegionPos = (150 >> 5, -200 >> 5) = (4, -7)
3. 文件路径 = "saves/world1/region/r.4.-7.mca"
4. region-local chunk = (150 & 31, -200 & 31) = (22, 24)
5. offsetTableIdx = 22 + 24 * 32 = 790
6. 读 offsetTable[790] → packed = 0x00010503
   sector_idx = 0x000105 = 261
   sector_count = 3
7. 读文件偏移 261 * 4096 = 1069056 处的 12 KiB
8. 解出 5 字节 header: length=10693, compType=2 (DEFLATE)
9. 取剩下 10692 字节，zlib 解压 → ~50 KB raw NBT
10. NbtIo.read(decompressedBytes) → CompoundTag
11. 拿到 chunk 数据，进入第 1 部分讲过的内存数据结构
```

**这就是 Module 2 完整的"读 chunk"链条**。后面 2.6 节把 CompoundTag → SerializableChunkData → LevelChunk 这后半段补完。

## 2.4.14 内存预算

打开一个 region 文件的内存开销：

| 组件 | 大小 |
|------|------|
| RegionFile 对象 | ~80 字节 |
| `ByteBuffer header` (direct) | 8 KiB （+ JVM 外，不算 JVM heap） |
| `RegionBitmap` (BitSet) | ~50 字节 + 几 KB（按已用扇区数） |
| `FileChannel` | ~200 字节（OS handle） |

**整个 RegionFile 对象 ~10 KB direct memory + 几百字节 heap**。视距内一般同时打开 5-30 个 region 文件，总开销 < 1 MB。

## 2.4.15 C++ 移植

```cpp
namespace mc::region {
    constexpr int SECTOR_BYTES = 4096;
    constexpr int SECTOR_INTS = 1024;
    constexpr int CHUNK_HEADER_SIZE = 5;
    constexpr int EXTERNAL_STREAM_FLAG = 128;
    constexpr int EXTERNAL_CHUNK_THRESHOLD = 256;

    class RegionBitmap {
    public:
        void force(int sectorIdx, int count);
        void free(int sectorIdx, int count);
        int allocate(int count);   // first-fit
    private:
        std::vector<uint64_t> bits_;   // packed bits
    };

    class RegionFile {
    public:
        RegionFile(std::filesystem::path mcaPath, std::filesystem::path externalDir, bool syncWrites);
        ~RegionFile();
        
        // 读 chunk 数据：返回解压后的 NBT bytes，或 nullopt
        std::optional<std::vector<std::byte>> readChunkData(ChunkPos pos);
        
        // 写 chunk 数据：data 是已压缩的字节
        void writeChunkData(ChunkPos pos, std::span<const std::byte> compressed, uint8_t compressionType);
        
        // 删除 chunk
        void clearChunk(ChunkPos pos);
        
        bool doesChunkExist(ChunkPos pos);
        void flush();
        
    private:
        std::filesystem::path path_;
        std::filesystem::path externalDir_;
        std::fstream file_;
        std::array<uint32_t, SECTOR_INTS> offsets_;     // big-endian packed
        std::array<uint32_t, SECTOR_INTS> timestamps_;
        RegionBitmap usedSectors_;
        bool syncWrites_;
        std::mutex mutex_;
        
        static constexpr uint32_t packOffset(uint32_t sectorIdx, uint8_t count) {
            return (sectorIdx << 8) | count;
        }
        static constexpr uint32_t getSectorNumber(uint32_t packed) {
            return (packed >> 8) & 0xFFFFFF;
        }
        static constexpr uint8_t getNumSectors(uint32_t packed) {
            return packed & 0xFF;
        }
        static constexpr int sizeToSectors(int sizeBytes) {
            return (sizeBytes + SECTOR_BYTES - 1) / SECTOR_BYTES;
        }
        
        int offsetIndex(ChunkPos pos) const {
            return (pos.x & 31) | ((pos.z & 31) << 5);
        }
        
        void readHeader();
        void writeHeader();
    };
}
```

**关键工程选择**：

1. **`std::fstream` 还是 `mio::mmap`？** 
   - fstream：跨平台稳定，但 IO 走 stdlib buffering，多一层。
   - mmap：把整个 region 映射到内存，OS 自动 page in / out，对随机访问极快。
   - 推荐 **mmap**（用 boost::iostreams 或 mio 库），尤其因为 region 文件最大也就几 MB。
2. **大端字节序**：用 `__builtin_bswap32` 或 `std::byteswap`（C++23）。Linux 的 `ntohl/htonl` 也行。
3. **fsync 用 `std::fstream::flush() + ::fsync(fd)`**：跨平台需要 OS API。Windows 用 `FlushFileBuffers`。
4. **mutex per RegionFile**：照搬 Java synchronized。
5. **first-fit BitSet**：用 `std::bitset<...>` 不行（需要动态大小），手写 `std::vector<uint64_t>` + `std::countr_one` / `std::countr_zero` 实现 nextClearBit / nextSetBit。

## 2.4.16 实战：用 hex 编辑器手动定位一个 chunk

打开你存档里的 `region/r.0.0.mca`：

1. 跳到偏移 0：前 4 字节 = chunk (0,0) 的 packed offset（大端）。
2. 提取高 24 位 = sector_idx，低 8 位 = sector_count。
3. 跳到 `sector_idx * 4096`：那里是 chunk (0,0) 数据的 5 字节 header + 压缩内容。
4. 复制压缩内容（不含 header 的 5 字节）。
5. 用 zlib decode（python `zlib.decompress(data)`）→ 得到 raw NBT。
6. 用 NBT 工具（或自己的 parser）解析 → 得到 chunk 内容。

如果你能跑完这一步，本节就过关了。这个流程是写自己 vanilla 兼容存档读取器的"hello world"。

## 2.4.17 一句话总结

`.mca` 文件 = 32×32 chunk 的容器；前 8 KiB 是双扇区头部（4 KiB offset table + 4 KiB timestamp table，每个 entry 是 24-bit 扇区下标 + 8-bit 扇区数的 packed int）；从扇区 2 起是变长 chunk 数据，每 chunk 5 字节 header（4 字节 length + 1 字节 compression type）+ 压缩 NBT + 扇区对齐 padding；`RegionBitmap` 用 first-fit 分配空闲扇区，chunk 缩放时释放旧扇区分配新扇区；单 chunk 上限 256 扇区 = 1 MiB，超出走外部 `.mcc` 文件；`per-RegionFile mutex` + 可选 DSYNC 保证一致性。
