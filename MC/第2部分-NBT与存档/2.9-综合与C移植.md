## 2.9.2 性能 budget 汇总

每个 chunk 在 IO 层的开销（典型 50 KB chunk，DEFLATE，SSD）：

| 阶段 | 时间 | 备注 |
|------|------|------|
| Memory → SerializableChunkData | ~1 ms | 大部分是 PalettedContainer pack |
| SerializableChunkData → CompoundTag | ~2 ms | NbtCompound 对象图构造 |
| CompoundTag → raw NBT bytes | ~1 ms | DataOutputStream 写 |
| Compress (DEFLATE level 6) | ~3 ms | zlib 慢 |
| Compress (LZ4) | ~0.5 ms | 极快 |
| RegionFile 扇区写 + fsync | ~1-30 ms | SSD vs HDD 差距大 |

**总计**：~10 ms (DEFLATE/SSD) → ~50 ms (DEFLATE/HDD)。

**`IOWorker` 单线程吞吐**：~100 chunk/秒（DEFLATE）/ 500 chunk/秒（LZ4）。

视距 32 chunk² = 1024 chunk 全保存：~10 秒（DEFLATE）/ 2 秒（LZ4）。**这就是 Mojang 推荐性能敏感服务器用 LZ4 的原因**。

## 2.9.3 整套设计的关键决策回顾

### 决策 1：分层 NBT / Region / Compression

不像很多游戏直接把 chunk 数据存成自定义二进制 + 顺手压缩。Mojang 三层：

- **NBT** 是数据格式（与具体存储无关）。
- **Region** 是文件容器（与具体压缩无关）。
- **Compression** 是字节流变换（独立替换）。

每层各司其职，互不耦合。**结果**：换压缩算法不需要改 NBT 代码；改 NBT schema 不影响 region 文件格式；上层 codec 不需要知道扇区分配。

### 决策 2：自描述 NBT 而非 schema-required

Protobuf / FlatBuffers 这种格式需要 .proto 文件作 schema。NBT 不需要——type byte 自带。代价是字节稍大、性能稍差，**但**：mod 工具能在不知道 schema 的情况下读 NBT、修改、写回。社区生态因此繁荣。

### 决策 3：扇区分配 + bitmap

不像 SQLite / LSM 那种"开新文件 + compact"模式。Region 用 first-fit + bitmap 让 chunk 大小变化时免重写。**碎片化**是代价，但 Minecraft chunk 大小波动小，碎片不严重。

### 决策 4：单线程 IOWorker

不用线程池并发写。串行的好处：

- 没有 race condition。
- 一致的 "最后写胜出" 语义。
- 简单的优先级 / 取消机制。

代价：单 IO 通道——但因为 region 锁本身也串行化了，多线程也吃同一锁，没用。

### 决策 5：DFU 投资

Mojang 投入巨大精力维护 DFU 与每版本的 fix。**这是一笔技术债，但是成功的**：14 年的存档至今能开。这是 Minecraft 的护城河之一。

## 2.9.4 哪些应该照搬

| Vanilla 设计 | 照搬到 C++ |
|--------------|-----------|
| NBT 12 种 Tag + 二进制 wire 格式 | 必须照搬（vanilla 兼容） |
| Region 文件 8 KiB 头 + 4 KiB 扇区分配 | 必须照搬 |
| 5 种 compression（GZIP/DEFLATE/NONE/LZ4/CUSTOM） | 至少支持 DEFLATE，建议加 LZ4 |
| External `.mcc` 文件机制 | 必须支持（极少触发但必须容错） |
| RegionBitmap first-fit | 照搬（简单、足够好） |
| 单线程 IOWorker + pendingWrites 队列 | 照搬 |
| LRU 256 RegionFile 缓存 | 照搬 |
| NbtAccounter 字节预算 + 深度限制 | 必须实现（防御不可少） |

## 2.9.5 哪些可以替换 / 简化

| Vanilla 设计 | 替代方案 |
|--------------|---------|
| OOP `Tag` 接口层次（13 子类） | C++ `std::variant<...>` + struct（性能 5-10×） |
| `CompoundTag` 内部 HashMap | C++ `boost::container::flat_map`（小 map 更快） |
| `ListTag` 强制元素同 type | 照搬（语义对，性能也好） |
| Java `DataInputStream / DataOutputStream` | C++ `std::span<std::byte>` + 手写 BE 读写（无虚函数） |
| GZIP / ZLIB 用 JDK 内置 | C++ 用 `zlib`（系统库） |
| `LZ4BlockInputStream` | C++ 用官方 `lz4` 库 |
| `FileChannel` + `ByteBuffer` direct | C++ `std::fstream` 或 `mio::mmap`（mmap 更快） |
| `synchronized` per RegionFile | C++ `std::mutex` |
| `CompletableFuture` | C++ `std::future / std::shared_future` |
| Mojang DFU（数千行 + 200 fixes） | 跳过 / 迷你版 / JNI |

## 2.9.9 验证清单：你的实现是不是正确

逐条勾选：

- [ ] 能读 vanilla 的 `level.dat`（GZIP 压缩 NBT），所有字段值与 NBTExplorer 一致。
- [ ] 能读 vanilla 的 `r.0.0.mca`，chunk(0,0) 解出 CompoundTag，sections/heightmaps/blockEntities 都齐全。
- [ ] 能写一个 chunk 到磁盘，再读回来 round-trip 数据一致。
- [ ] 写 chunk 时，扇区分配走 first-fit；尺寸不变时**不**重新分配。
- [ ] 超过 1 MiB 的 chunk 自动写到 `.mcc` 文件，主 region 写 dummy entry with bit 7 set。
- [ ] NbtAccounter quota 触发时正确抛 NbtAccounterException，**不分配大数组**。
- [ ] IOWorker.store 主线程零阻塞，async 后台写。
- [ ] IOWorker.loadAsync 优先返回 pending 数据。
- [ ] 关闭时所有 pending 都 flush，没有数据丢失。
- [ ] LZ4 / DEFLATE 切换可配置。
- [ ] 单元测试覆盖率 > 70%。

## 2.9.12 一句话总结

第 2 部分把"chunk 怎么持久化"完整拆开：2.1-2.3 的 NBT 子栈（自描述二进制格式 + Java 对象树 + 流式 IO + 防 NBT 炸弹）；2.4-2.5 的 Region 子栈（32×32 chunk 容器 + 扇区分配 + 5 种压缩 + 外部 .mcc 溢出）；2.6 的 SerializableChunkData 桥接（连接第 1 部分的内存数据与本部分的磁盘格式）；2.7 的 IOWorker（单线程后台异步 + pendingWrites 批合并 + scanChunk 流式扫描）；2.8 的 DFU（DataVersion 单调递增 + Schema/Fix 跨版本迁移）。所有这些组合起来支撑 Minecraft 14 年的存档格式不间断兼容。
