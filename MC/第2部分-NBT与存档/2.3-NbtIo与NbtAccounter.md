## 2.3.1 NbtIo 是什么

`net.minecraft.nbt.NbtIo` 是 NBT 读写的**唯一公共入口**。它是一个 `static` utility 类——所有方法都是静态的。它包含：

1. **从 Path / InputStream 读取根级 CompoundTag**（带或不带 GZIP）。
2. **把 CompoundTag 写到 Path / OutputStream**（带或不带 GZIP）。
3. **流式解析**（不构造完整对象树，配合 StreamTagVisitor 用）。
4. **裸 read / write 任意 Tag**（罕见，给特殊场景用）。

它和 `Tag` / `TagType` 的关系：

- `TagType.load(in, acc)` 是单个 Tag 的反序列化，递归调用。
- `Tag.write(out)` 是单个 Tag 的序列化。
- `NbtIo` 是上面这俩 + IO（FileChannel / GZIPInputStream / 管理 buffer / 错误包装）的**胶水**。

## 2.3.3 一个最简单的读：level.dat

```java
NbtAccounter acc = NbtAccounter.create(2 * 1024 * 1024);   // 2 MB quota
try (InputStream in = Files.newInputStream(Path.of("saves/world1/level.dat"))) {
    CompoundTag root = NbtIo.readCompressed(in, acc);
    long seed = root.getCompound("Data").getLong("RandomSeed");
    String name = root.getCompound("Data").getString("LevelName");
    int spawnX = root.getCompound("Data").getInt("SpawnX");
    System.out.println("Seed=" + seed + " name=" + name + " spawnX=" + spawnX);
}
```

四步：

1. 创建 `NbtAccounter`（防 NBT 炸弹的字节预算）。
2. 打开文件流。
3. `readCompressed(in, acc)` 内部：包装 GZIPInputStream → DataInputStream → 调 `read(...)`。
4. 拿到根 CompoundTag，按字段访问。

`readCompressed(InputStream, NbtAccounter)` 实现：

```java
public static CompoundTag readCompressed(InputStream in, NbtAccounter acc) throws IOException {
    try (DataInputStream dis = createDecompressorStream(in)) {
        return read(dis, acc);
    }
}

private static DataInputStream createDecompressorStream(InputStream in) throws IOException {
    return new DataInputStream(new FastBufferedInputStream(new GZIPInputStream(in)));
}
```

简单的层包装。

## 2.3.4 read 的内部细节

`read(DataInput, NbtAccounter)`（行 120-127）：

```java
public static CompoundTag read(DataInput in, NbtAccounter acc) throws IOException {
    Tag tag = readUnnamedTag(in, acc);
    if (tag instanceof CompoundTag) {
        return (CompoundTag)tag;
    } else {
        throw new IOException("Root tag must be a named compound tag");
    }
}

private static Tag readUnnamedTag(DataInput in, NbtAccounter acc) throws IOException {
    byte typeId = in.readByte();
    if (typeId == 0) {
        return EndTag.INSTANCE;
    } else {
        StringTag.skipString(in);    // 读但丢弃根名字
        return readTagSafe(in, acc, typeId);
    }
}
```

**注意**：

1. 根级 tag 必须是 COMPOUND（typeId=10），其他类型抛异常。
2. 根 tag 的 name 被读出来但**丢弃**——大部分 NBT 工具都不在意根 name（习惯空字符串）。
3. `readTagSafe` 委托给 `TagTypes.getType(typeId).load(in, acc)`，把 IOException 包装为 `ReportedNbtException`（带 crash report 上下文）。

**`StringTag.skipString` 的实现**：

```java
public static void skipString(DataInput in) throws IOException {
    in.skipBytes(in.readUnsignedShort());
}
```

读 2 字节长度 → 跳过对应字节数。这就是为什么 `readUnnamedTag` 可以"读但丢弃名字"。

## 2.3.5 NBT 炸弹是什么

**NBT 炸弹**（NBT bomb）是一种基于 NBT 自描述特性的 DoS 攻击。

最简单的炸弹：

```
[type=10 COMPOUND] [name_len=0]
  [type=9 LIST] [name_len=1] [name="x"]
    [element_type=9] [length=2147483647]    ← 21 亿元素
    ... 21 亿个 LIST，每个又 21 亿元素 ...
```

构造一个嵌套 List 声明 21 亿元素的 NBT。**只占 50 字节**，但解析时会触发 21 亿次 ArrayList 分配 / 21 亿次递归调用，**直接 OOM 或 StackOverflow**。

**真实威胁场景**：

- 玩家加入服务器时发"自定义皮肤数据"（NBT）。
- mod 通过 `/give` 命令发"自定义物品 NBT"（玩家可任意构造）。
- chat 系统的 "自定义文本组件" 可包含嵌入 NBT。
- 网络 plugin channels 发自定义 NBT 包。

**任何接受外部 NBT 的入口都是攻击面**。

## 2.3.6 NbtAccounter：字节预算 + 深度限制

打开 `net.minecraft.nbt.NbtAccounter`：

```java
public class NbtAccounter {
    private static final int MAX_STACK_DEPTH = 512;
    private final long quota;
    private long usage;
    private final int maxDepth;
    private int depth;

    public NbtAccounter(long quota, int maxDepth) {
        this.quota = quota;
        this.maxDepth = maxDepth;
    }

    public static NbtAccounter create(long quota) {
        return new NbtAccounter(quota, 512);
    }

    public static NbtAccounter unlimitedHeap() {
        return new NbtAccounter(Long.MAX_VALUE, 512);
    }

    public void accountBytes(long count, long perItem) {
        this.accountBytes(count * perItem);
    }

    public void accountBytes(long delta) {
        if (this.usage + delta > this.quota) {
            throw new NbtAccounterException(
                "Tried to read NBT tag that was too big; tried to allocate: "
                + this.usage + " + " + delta + " bytes where max allowed: " + this.quota
            );
        } else {
            this.usage += delta;
        }
    }

    public void pushDepth() {
        if (this.depth >= this.maxDepth) {
            throw new NbtAccounterException("Tried to read NBT tag with too high complexity, depth > " + this.maxDepth);
        } else {
            this.depth++;
        }
    }

    public void popDepth() {
        if (this.depth <= 0) {
            throw new NbtAccounterException("NBT-Accounter tried to pop stack-depth at top-level");
        } else {
            this.depth--;
        }
    }
}
```

**两道防线**：

### 防线 1：累计字节预算

每个 Tag 在 load 时调用 `acc.accountBytes(N)`。N 是该 Tag 在 JVM 堆上的估算字节数。

例：CompoundTag 的 load：

```java
private static CompoundTag loadCompound(DataInput in, NbtAccounter acc) throws IOException {
    acc.accountBytes(48L);    // CompoundTag 自身约 48 字节
    Map<String, Tag> map = Maps.newHashMap();
    byte childType;
    while ((childType = in.readByte()) != 0) {
        String name = readString(in, acc);
        Tag tag = readNamedTagData(TagTypes.getType(childType), name, in, acc);
        if (map.put(name, tag) == null) {
            acc.accountBytes(36L);    // 每加一个 entry 约 36 字节
        }
    }
    return new CompoundTag(map);
}
```

ListTag 的 load：

```java
private static ListTag loadList(DataInput in, NbtAccounter acc) throws IOException {
    acc.accountBytes(37L);                       // ListTag 自身
    byte elementType = in.readByte();
    int length = in.readInt();
    if (elementType == 0 && length > 0) throw ...;
    acc.accountBytes(4L, (long)length);          // 每个 entry 在 ArrayList 内 4 字节
    TagType<?> tagType = TagTypes.getType(elementType);
    List<Tag> list = Lists.newArrayListWithCapacity(length);
    for (int j = 0; j < length; j++) {
        list.add(tagType.load(in, acc));         // 子元素也 account
    }
    return new ListTag(list, elementType);
}
```

ByteArrayTag / IntArrayTag / LongArrayTag 的 load：

```java
private static IntArrayTag loadIntArray(DataInput in, NbtAccounter acc) throws IOException {
    acc.accountBytes(24L);                  // 自身 + 数组 header
    int length = in.readInt();
    acc.accountBytes(4L, (long)length);     // ★ 关键：声明 length 之后立刻 account length × 4
    if (length > MAX_LENGTH) throw ...;
    int[] arr = new int[length];
    for (int i = 0; i < length; i++) arr[i] = in.readInt();
    return new IntArrayTag(arr);
}
```

**关键设计**：在**实际分配数组之前**就 account length × element_size。如果攻击者声明 `length=2_147_483_647`、`element_size=4`，account 立刻调用 `accountBytes(8 GB)` → 立刻抛异常 → **不会真分配 8 GB**。

### 防线 2：嵌套深度

`pushDepth()` / `popDepth()` 在每次进入 ListTag 或 CompoundTag 的 load 时调用：

```java
public CompoundTag load(DataInput in, NbtAccounter acc) throws IOException {
    acc.pushDepth();
    try {
        return loadCompound(in, acc);
    } finally {
        acc.popDepth();
    }
}
```

默认 `maxDepth = 512`。如果攻击者构造 1000 层嵌套 compound，第 513 层的 pushDepth 会抛异常，避免 StackOverflowError。

**为什么 512？** 这个深度对正常 NBT 数据足够（chunk NBT 实际深度不到 10），但又远低于 JVM 默认栈帧能容纳的深度（约几千），有缓冲。

## 2.3.7 quota 选择

`NbtAccounter.create(quota)` 静态工厂的 quota 应该选多少？

| 来源 | 推荐 quota |
|------|-----------|
| 信任的本地存档（level.dat、chunk NBT） | `unlimitedHeap()` 或 256 MB |
| 信任的内部数据 / mod 自带文件 | 64 MB |
| 网络包内嵌 NBT（如 BlockEntity 同步）| **2 MB** |
| 玩家命令的 NBT 字面量（如 `/give`） | **2 MB** |
| 玩家私聊中 NBT 引用 | **2 MB** |

`Mojang` 自家的网络包路径用的就是 2 MB（`NbtAccounter.create(2_097_152L)`）。这个值是经过实战检验的"够用但限制攻击"的折中。

**误区**：很多人以为 NbtAccounter 限制的是 wire 字节数。**不是**——它限制的是**反序列化后在 JVM 堆上的估算字节数**，因为后者通常是前者的 5-10 倍（NBT tag 对象头 + HashMap 内部）。

## 2.3.8 写入：write 的细节

`write(CompoundTag, Path)`：

```java
public static void write(CompoundTag root, Path path) throws IOException {
    try (
        OutputStream out = Files.newOutputStream(path, SYNC_OUTPUT_OPTIONS);
        OutputStream buffered = new BufferedOutputStream(out);
        DataOutputStream dos = new DataOutputStream(buffered);
    ) {
        write(root, dos);
    }
}

public static void write(CompoundTag root, DataOutput out) throws IOException {
    writeUnnamedTagWithFallback(root, out);
}

public static void writeUnnamedTag(Tag tag, DataOutput out) throws IOException {
    out.writeByte(tag.getId());
    if (tag.getId() != 0) {
        out.writeUTF("");    // 根 tag 名字 = 空字符串
        tag.write(out);
    }
}
```

`SYNC_OUTPUT_OPTIONS`（行 26-28）：

```java
private static final OpenOption[] SYNC_OUTPUT_OPTIONS = new OpenOption[]{
    StandardOpenOption.SYNC,
    StandardOpenOption.WRITE,
    StandardOpenOption.CREATE,
    StandardOpenOption.TRUNCATE_EXISTING
};
```

**`StandardOpenOption.SYNC`** 强制每次写都 fsync 到磁盘。这对 `level.dat` 至关重要——如果服务器崩溃，半写的 `level.dat` 会让世界失效。SYNC 慢但保证持久化。

**`writeUnnamedTagWithFallback`** 是 1.20.5 引入的——给超长字符串一个 fallback（用 NBTLong 表达字符串长度，绕开 u16 的 65535 限制）。**普通使用不会触发**，背景见 NBT 偶尔遇到的"字符串爆 65535 字节"问题（极罕见 mod 场景）。

## 2.3.9 流式 parse：不构造对象树

有时你只想从一个超大 NBT 里**扫描某个 key**，而不需要把整棵树读进内存。这就是 `StreamTagVisitor` 的用武之地。

```java
public static void parse(DataInput in, StreamTagVisitor visitor, NbtAccounter acc) throws IOException;
```

`StreamTagVisitor` 接口（节选）：

```java
public interface StreamTagVisitor {
    enum ValueResult { CONTINUE, BREAK, HALT }
    enum EntryResult { ENTER, SKIP, BREAK, HALT }

    ValueResult visitRootEntry(TagType<?> type);
    EntryResult visitEntry(TagType<?> type);
    EntryResult visitEntry(TagType<?> type, String name);   // compound 中的 entry
    EntryResult visitElement(TagType<?> type, int index);   // list 中的元素

    ValueResult visit(byte v);
    ValueResult visit(short v);
    ValueResult visit(int v);
    ValueResult visit(long v);
    ValueResult visit(float v);
    ValueResult visit(double v);
    ValueResult visit(String v);
    ValueResult visit(byte[] v);
    ValueResult visit(int[] v);
    ValueResult visit(long[] v);

    ValueResult visitList(TagType<?> elementType, int size);
    ValueResult visitContainerEnd();
    ValueResult visitEnd();
}
```

**返回值控制 parser 行为**：

- `ENTER` / `CONTINUE`：进入 / 处理这个节点。
- `SKIP`：跳过这个节点（parser 把它的字节读完丢弃）。
- `BREAK`：跳出当前 list / compound（提前结束）。
- `HALT`：完全终止整个 parse 操作。

---

### `CollectFields`：典型流式 visitor 用例

`net.minecraft.nbt.visitors.CollectFields`（被 IOWorker 用来从 region 文件里**只读 Chunk 的 InhabitedTime / DataVersion**字段，不解析其他几十 KB 的 chunk 数据）：

```java
public class CollectFields extends CollectToTag {
    private final FieldSelector[] selectors;
    
    @Override
    public StreamTagVisitor.EntryResult visitEntry(TagType<?> type, String name) {
        for (FieldSelector sel : selectors) {
            if (sel.matches(name, type)) return EntryResult.ENTER;   // 我要这个字段
        }
        return EntryResult.SKIP;     // 跳过其他字段
    }
}
```

效果：从一个 50 KB 的 chunk NBT 里**只解析出 2 个字段**，其他 50 KB 的字节被读后丢弃，不构造任何 Tag 对象。**性能差异 100×**——这是 IOWorker 能在 ms 级扫描整个 region 的关键。

后面 2.7 节会展开 IOWorker 的具体使用。

## 2.3.10 序列化的 sizeInBytes

每个 Tag 实现 `sizeInBytes()` 估算自己在堆上的大小：

```java
// IntTag
@Override public int sizeInBytes() { return 12; }     // 8 byte 对象头 + 4 byte int

// CompoundTag
@Override public int sizeInBytes() {
    int total = 48;     // self
    for (Entry<String, Tag> e : this.tags.entrySet()) {
        total += 32;                              // map entry
        total += 28;                              // String 自身
        total += 2 * e.getKey().length();         // String 内部 UTF-16
        total += e.getValue().sizeInBytes();
    }
    return total;
}
```

这个值给 NbtAccounter 用——`accountBytes(tag.sizeInBytes())` 在 load 时累计。

## 2.3.11 错误处理

`ReportedNbtException` 是 Mojang 的"NBT 错误带上下文"包装：

```java
private static Tag readTagSafe(DataInput in, NbtAccounter acc, byte typeId) {
    try {
        return TagTypes.getType(typeId).load(in, acc);
    } catch (IOException ioexception) {
        CrashReport report = CrashReport.forThrowable(ioexception, "Loading NBT data");
        CrashReportCategory cat = report.addCategory("NBT Tag");
        cat.setDetail("Tag type", typeId);
        throw new ReportedNbtException(report);
    }
}
```

底层抛 `IOException`（数据损坏 / EOF / 格式错），上层包装成 `ReportedNbtException`（含 typeId / 类名等诊断信息）。

`NbtAccounterException`（继承 `RuntimeException`）专门给 quota / depth 超限抛——**它是 unchecked**，调用方可不显式 catch（按 fail-fast 处理）。

## 2.3.13 C++ 移植

```cpp
namespace mc::nbt {
    class NbtAccounter {
    public:
        explicit NbtAccounter(int64_t quota = std::numeric_limits<int64_t>::max(), int maxDepth = 512)
            : quota_(quota), maxDepth_(maxDepth) {}
        
        static NbtAccounter create(int64_t quota) { return NbtAccounter(quota, 512); }
        static NbtAccounter unlimitedHeap() { return NbtAccounter(); }
        
        void accountBytes(int64_t delta) {
            if (usage_ + delta > quota_) {
                throw NbtAccounterException("NBT too big: " + std::to_string(usage_) + 
                                            " + " + std::to_string(delta));
            }
            usage_ += delta;
        }
        
        void accountBytes(int64_t count, int64_t perItem) {
            accountBytes(count * perItem);
        }
        
        void pushDepth() {
            if (depth_ >= maxDepth_) throw NbtAccounterException("NBT depth too high");
            depth_++;
        }
        
        void popDepth() {
            if (depth_ <= 0) throw NbtAccounterException("popDepth at top-level");
            depth_--;
        }
        
    private:
        int64_t quota_;
        int64_t usage_ = 0;
        int maxDepth_;
        int depth_ = 0;
    };

    class NbtIo {
    public:
        static CompoundTag readCompressed(std::istream& in, NbtAccounter& acc);
        static void writeCompressed(const CompoundTag& root, std::ostream& out);
        
        static CompoundTag read(std::istream& in, NbtAccounter& acc) {
            BinaryReader r(in);
            uint8_t typeId = r.readU8();
            if (typeId != uint8_t(TagType::COMPOUND))
                throw std::runtime_error("Root tag must be COMPOUND");
            r.skipString();    // 丢弃根名字
            return loadCompound(r, acc);
        }
        
        static void write(const CompoundTag& root, std::ostream& out) {
            BinaryWriter w(out);
            w.writeU8(uint8_t(TagType::COMPOUND));
            w.writeString("");
            writeCompound(root, w);
        }
    };

    // GZIP 用 zlib
    class GzipDecompressor {
        // 包装 std::istream → 解压 stream
    };
}
```

**关键工程选择**：

1. **`NbtAccounter` 用栈对象传引用**：每次 IO 创建一个，不要全局单例。
2. **`std::istream` 传引用**：parser 不拥有流。
3. **GZIP 用 `zlib`**（系统库）或 `boost::iostreams`：跨平台稳定。
4. **错误用异常**：parse 失败立刻栈展开，不要返回 error code（NBT 解析中途失败基本无法继续）。
5. **对外只暴露 `read/write`**，内部 `loadCompound/loadList` 等是 private helper。

## 2.3.14 一句话总结

`NbtIo` 是 NBT 流式读写唯一公共入口，封装了 GZIP 压缩、SYNC fsync、根级 COMPOUND 检查、错误包装；`NbtAccounter` 是防 NBT 炸弹的双道防线——累计字节预算（限制反序列化后堆开销）+ 嵌套深度限制（默认 512，防 StackOverflow）；不可信来源用 `create(2 MB)`，本地信任用 `unlimitedHeap()`；`StreamTagVisitor` 让你流式扫描某字段而不构造完整对象树（IOWorker 的 CollectFields 在 region 扫描时就靠它达到 100× 加速）。
