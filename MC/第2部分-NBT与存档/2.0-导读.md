# 第 2 部分 · NBT 与存档 —— 导读

## 你为什么需要先读这一部分

第 1 部分讲了 chunk 在内存里长什么样。这一部分回答另一个问题：**这些数据怎么写到磁盘？怎么从磁盘读回来？**

听起来是个"序列化"的小问题，但 Mojang 在这一栈里堆了相当多的工程巧思：

1. **NBT** —— Notch 在 alpha 时期发明的二进制格式，自描述、紧凑、跨语言、适合脚本工具读取。
2. **Region 文件 (.mca)** —— 一个文件装 32×32 = 1024 个 chunk，靠扇区分配 + bitmap 实现"chunk 大小动态变化时不重整文件"。
3. **5 种压缩家族** —— GZIP / DEFLATE / 不压缩 / LZ4 / 外部文件指针，让单 chunk 既可极致紧凑也可超大溢出。
4. **`SerializableChunkData`** —— 1.21 引入的 chunk 序列化数据载体类，把"chunk 内存形态"和"chunk NBT 形态"清晰解耦。
5. **`IOWorker`** —— 一个独立线程做磁盘 IO，主 tick 线程零阻塞。
6. **`DataFixerUpper`** —— Mojang 自家的"NBT 跨版本迁移框架"，让 1.6 时代的存档也能在 1.21 打开。

这些机制是"教程意义"上不性感的（不像 worldgen 那样视觉酷炫），但它们是 Minecraft 长期可玩的根基——一个 2010 年的存档至今还能打开就靠这套。

读完这一部分你应当能：

1. 拿到一个 `.mca` 文件，闭着眼说出每个字节的含义、能用 hex 编辑器手动定位某个 chunk。
2. 知道一个 chunk 从内存到磁盘走过哪些层（PalettedContainer → SerializableChunkData → CompoundTag → 压缩流 → Region 扇区 → fsync）。
3. 区分 NBT、SNBT、JSON 三种格式各自的角色。
4. 写一个 C++ 的 NBT 库 + Region 文件读写器（**完整可用**，不是教学玩具），能 round-trip 真实的 vanilla 存档。
5. 理解 IOWorker 单线程 region 写入为什么不是性能瓶颈。
6. 知道 DataFixerUpper 是怎么回事，并能决定自己的引擎要不要走这个路线。

## 它和其它部分的关系

```
第 0、1 部分（已完成）
        │
        ▼
第 2 部分（你在这里）
        │
        ├── NBT 格式与读写         ── 0
        ├── Region 文件 (.mca)     ── 1
        ├── SerializableChunkData ── 2  ← 桥接第 1 部分的 chunk 数据结构
        ├── IOWorker 异步 IO       ── 3
        └── DataFixerUpper        ── 4
        │
        ▼
第 3 部分以及之后所有模块
        ↑
       因为 worldgen / 红石 / 流体 / 网络的所有数据
       最终都要经过本部分的 NBT / Region 流水线写盘
```

**第 2 部分自包含**：除了"第 1 部分讲的 chunk 数据结构"作为序列化对象，这一部分内部不依赖别的模块。可以独立读完。
