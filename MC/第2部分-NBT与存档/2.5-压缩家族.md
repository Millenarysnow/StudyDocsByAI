# 2.5 压缩家族 与外部 .mcc 文件

## 2.5.0 你将在本节学到什么

读完这一节你应当能闭着眼睛回答：

1. `.mca` 文件里同一个 chunk 可能用 GZIP、ZLIB、不压缩、LZ4 几种格式之一——为什么 Mojang 留这么多选择？
2. compression_type 为什么有个 127？Mojang 真的支持自定义压缩吗？
3. 1 MiB 的单 chunk 上限怎么破？外部 `.mcc` 文件怎么工作？读 chunk 时如何区分外部 / 内部？
4. 服务器 `server.properties` 里的 `region-file-compression` 选什么最快？最省？
5. 为什么有些 mod / 玩家偏好 LZ4 而非默认 DEFLATE？
6. 我在 C++ 里要支持全 5 种压缩方案，需要哪些库？

## 2.5.1 五种压缩格式

打开 `net.minecraft.world.level.chunk.storage.RegionFileVersion`（行 24-56）：

```java
public class RegionFileVersion {
    private static final Int2ObjectMap<RegionFileVersion> VERSIONS = new Int2ObjectOpenHashMap<>();
    private static final Object2ObjectMap<String, RegionFileVersion> VERSIONS_BY_NAME = new Object2ObjectOpenHashMap<>();

    public static final RegionFileVersion VERSION_GZIP = register(
        new RegionFileVersion(1, null,
            in -> new FastBufferedInputStream(new GZIPInputStream(in)),
            out -> new BufferedOutputStream(new GZIPOutputStream(out))
        )
    );

    public static final RegionFileVersion VERSION_DEFLATE = register(
        new RegionFileVersion(2, "deflate",
            in -> new FastBufferedInputStream(new InflaterInputStream(in)),
            out -> new BufferedOutputStream(new DeflaterOutputStream(out))
        )
    );

    public static final RegionFileVersion VERSION_NONE = register(
        new RegionFileVersion(3, "none",
            FastBufferedInputStream::new,
            BufferedOutputStream::new
        )
    );

    public static final RegionFileVersion VERSION_LZ4 = register(
        new RegionFileVersion(4, "lz4",
            in -> new FastBufferedInputStream(new LZ4BlockInputStream(in)),
            out -> new BufferedOutputStream(new LZ4BlockOutputStream(out))
        )
    );

    public static final RegionFileVersion VERSION_CUSTOM = register(
        new RegionFileVersion(127, null, throwOp, throwOp)
    );

    public static final RegionFileVersion DEFAULT = VERSION_DEFLATE;
    private static volatile RegionFileVersion selected = DEFAULT;
}
```

**5 个 RegionFileVersion 实例**：

| ID | 名字 | 压缩算法 | 用法 |
|----|------|---------|------|
| 1 | GZIP | GZIP（DEFLATE + headers） | 历史兼容（早期 Beta） |
| 2 | DEFLATE | 纯 zlib DEFLATE | **默认**，速度 / 比率折中 |
| 3 | NONE | 不压缩 | 调试 / 测试 |
| 4 | LZ4 | LZ4 | 速度优先（1.20.5+） |
| 127 | CUSTOM | — | 占位，未实现（mod 自定义入口） |

## 2.5.2 各压缩格式的特性对比

| 格式 | 压缩比 | 压缩速度 | 解压速度 | 库依赖 |
|------|-------|---------|---------|-------|
| GZIP | ~80% | 中 | 中 | JDK 内置 |
| DEFLATE | ~80% | 中 | 中 | JDK 内置 |
| NONE | 0% | 极快 | 极快 | 无 |
| LZ4 | ~50% | **极快** | **极快** | net.jpountz.lz4 |
| CUSTOM | 视情况 | — | — | mod 自定义 |

**典型 chunk** 50 KB raw NBT：
- GZIP / DEFLATE: ~10-12 KB（80% 压缩）。
- LZ4: ~25 KB（50% 压缩）但读写**3-5×** 快。
- NONE: 50 KB（节省 CPU 但磁盘 IO 翻 5 倍）。

**为什么 GZIP 和 DEFLATE 同时存在？** 历史包袱。Beta 时期 Mojang 用 GZIP（带文件头校验和等），1.0 之后切换到纯 DEFLATE（更紧凑，跳过 GZIP 头节省 ~18 字节/chunk）。两者都保留向后兼容。

**LZ4 何时引入？** 1.20.5（2024 年）。Mojang 官方建议**写盘性能敏感的服务器**用 LZ4——它压得比 zlib 差但写盘时间短。**默认仍是 DEFLATE**，因为绝大多数玩家在意磁盘空间。

**`server.properties` 配置**：

```
region-file-compression=lz4
```

调用 `RegionFileVersion.configure("lz4")` 切换。客户端不可配，永远默认 DEFLATE。

## 2.5.3 RegionFileVersion 类的设计

构造：

```java
private RegionFileVersion(int id, @Nullable String optionName,
                          StreamWrapper<InputStream> inputWrapper,
                          StreamWrapper<OutputStream> outputWrapper) {
    this.id = id;
    this.optionName = optionName;
    this.inputWrapper = inputWrapper;
    this.outputWrapper = outputWrapper;
}

@FunctionalInterface
interface StreamWrapper<O> {
    O wrap(O original) throws IOException;
}
```

**用 `StreamWrapper<I/O>` 函数式接口包装解 / 压缩**：每种 version 持有两个 lambda：

- `inputWrapper.wrap(InputStream)` → 返回解压后的 InputStream。
- `outputWrapper.wrap(OutputStream)` → 返回压缩前的 OutputStream（写进去的数据会被压缩后再写到底层）。

调用方简单：

```java
DataInputStream chunkData = new DataInputStream(version.wrap(rawSectorBytes));
NbtIo.read(chunkData, ...);
```

**这是经典的 Decorator 模式**——每种 version 是一个 decorator 工厂。统一接口，运行时按 compression_type 字节选择。

`fromId(int)` 静态方法（行 82-84）：

```java
@Nullable
public static RegionFileVersion fromId(int id) {
    return VERSIONS.get(id);
}
```

读 chunk 时，从 5 字节 chunk header 的 1 字节 compression_type 来选 version。

## 2.5.4 写入时的 compression：单 region 单 version

**重要事实**：一个 region 文件**整体**用一种 compression。所有写入这个 region 的 chunk 都用同一种压缩。

**为什么不允许混用**？理论上可以，每个 chunk 的 header 都带自己的 compression_type。但实际上 Mojang 选择"一个 region 一种 version"——构造 RegionFile 时确定，所有写入用 `RegionFileVersion.getSelected()`：

```java
public RegionFile(...) throws IOException {
    this(info, path, externalDir, RegionFileVersion.getSelected(), syncWrites);
}
```

**读取时仍然每个 chunk 看自己的 compression_type 字节**（即使整个 region 都是 DEFLATE 写入的）——这保证了**已存在的旧 region 文件能被新版打开**：旧 chunk 是 GZIP？没问题，按它自己的 header 类型解压。

**结论**：升级压缩格式（如从 DEFLATE 切到 LZ4）是 read-compatible / write-incompatible：

- 旧 region 仍可被读出来。
- 新写入的 chunk 用新格式。
- 旧 region 里没改过的 chunk 仍是旧格式。
- 改过的 chunk 用新格式（覆盖原扇区或重新分配）。

**长期下来同一 region 内可能 GZIP / DEFLATE / LZ4 chunk 混存**——这是合法的，每个 chunk 自己 header 说明类型即可。

## 2.5.5 selected 全局变量

```java
private static volatile RegionFileVersion selected = DEFAULT;
public static RegionFileVersion getSelected() { return selected; }

public static void configure(String name) {
    RegionFileVersion v = VERSIONS_BY_NAME.get(name);
    if (v != null) {
        selected = v;
    } else {
        LOGGER.error("Invalid `region-file-compression` value...");
    }
}
```

**全局可变状态**——`selected` 字段是 `volatile static`。`configure(...)` 在服务端启动读 server.properties 时调用一次，整个进程生命周期不再变。

C++ 移植可以直接用全局静态指针 + 启动期一次性配置。

## 2.5.6 EXTERNAL_STREAM_FLAG：单 chunk 1 MiB 上限的破解

回到 2.4 节。`compression_type` 是 1 字节，但 Mojang 用了它的 **bit 7 (0x80)** 作为 "external file flag"：

```java
// RegionFile.java
private static final int EXTERNAL_STREAM_FLAG = 128;          // 0x80
private static final int EXTERNAL_CHUNK_THRESHOLD = 256;       // 扇区数

private static boolean isExternalStreamChunk(byte compType) {
    return (compType & 128) != 0;
}

private static byte getExternalChunkVersion(byte compType) {
    return (byte)(compType & ~128);    // 清除 bit 7 拿到真 compression
}
```

**当 chunk 数据超过 256 扇区（1 MiB）时**：

1. 把数据写到一个独立的 `c.X.Z.mcc` 文件（X、Z 是 chunk 全局坐标，**不是** region-local）。
2. `.mcc` 文件就是裸压缩流，没有 region header。
3. 在主 region 文件中给这个 chunk 写 entry：
   - `length = 1`（dummy）。
   - `compression_type = (real_compression | 0x80)` ——bit 7 标记"我在外部"。

读取时：

```java
// RegionFile.getChunkDataInputStream
if (isExternalStreamChunk(compType)) {
    return this.createExternalChunkInputStream(pos, getExternalChunkVersion(compType));
}
```

`createExternalChunkInputStream`（行 191-200）：

```java
@Nullable
private DataInputStream createExternalChunkInputStream(ChunkPos pos, byte realCompType) throws IOException {
    Path path = this.getExternalChunkPath(pos);
    if (!Files.isRegularFile(path)) {
        LOGGER.error("External chunk path {} is not file", path);
        return null;
    } else {
        return this.createChunkInputStream(pos, realCompType, Files.newInputStream(path));
    }
}

private Path getExternalChunkPath(ChunkPos pos) {
    String name = "c." + pos.x + "." + pos.z + ".mcc";
    return this.externalFileDir.resolve(name);
}
```

**`.mcc` 文件命名**：`c.<chunkX>.<chunkZ>.mcc`，放在和 `.mca` 同目录下。

**典型场景**：极少见。你需要一个 chunk NBT > 1 MiB 才触发，意味着这个 chunk 有：
- 几千个 BlockEntity（村庄边界 + 巨型村庄 + 大量 mod 物品）。
- 极复杂的 jigsaw 结构。
- mod 注入了超大数据。

vanilla 玩家 90% 的存档不会出现 `.mcc` 文件。

## 2.5.7 写 chunk 时检测溢出

`RegionFile.ChunkBuffer.close()`（简化）：

```java
public void close() throws IOException {
    ByteBuffer buf = ByteBuffer.wrap(this.toByteArray());
    int payloadLen = buf.remaining();
    int totalLen = payloadLen + 5;
    int sectorsNeeded = sizeToSectors(totalLen);

    if (sectorsNeeded >= EXTERNAL_CHUNK_THRESHOLD) {
        // 走外部文件
        Path externalPath = getExternalChunkPath(this.pos);
        Files.write(externalPath, ...);     // 写裸数据到 .mcc

        // 主 region 写一个 dummy entry
        int sectorIdx = usedSectors.allocate(1);     // 仅占 1 扇区
        ByteBuffer dummy = ByteBuffer.allocate(SECTOR_BYTES);
        dummy.putInt(1);                              // length = 1
        dummy.put((byte)(version.getId() | EXTERNAL_STREAM_FLAG));    // compression | 0x80
        // 剩余 4091 字节为 0 padding
        file.write(dummy, sectorIdx * SECTOR_BYTES);
        offsets.put(offsetIdx, packSectorOffset(sectorIdx, 1));
    } else {
        // 走内部
        // ... 正常扇区分配 ...
    }
}
```

**注意 `.mcc` 仍然占用主 region 的 1 个扇区**——这个扇区放 dummy header 标记"我在外部"。这设计上简化了"扫描所有 chunk 是否存在"的逻辑——只看 offset table 即可。

## 2.5.8 Custom Compression：留给 mod 的扩展点

```java
public static final RegionFileVersion VERSION_CUSTOM = register(
    new RegionFileVersion(127, null,
        in -> { throw new UnsupportedOperationException(); },
        out -> { throw new UnsupportedOperationException(); }
    )
);
```

**Mojang vanilla 不实现 CUSTOM**——它只是占位。读到 compression_type = 127 的 chunk，会触发 `RegionFile.createChunkInputStream`（行 171-189）的特殊分支：

```java
if (regionfileversion == RegionFileVersion.VERSION_CUSTOM) {
    String s = new DataInputStream(stream).readUTF();
    ResourceLocation rl = ResourceLocation.tryParse(s);
    if (rl != null) {
        LOGGER.error("Unrecognized custom compression {}", rl);
        return null;
    } else {
        LOGGER.error("Invalid custom compression id {}", s);
        return null;
    }
}
```

它读出一个 ResourceLocation 字符串（mod 的自定义压缩 ID），然后**直接报错返回 null**。设计意图：mod 可以注册自己的 RegionFileVersion 实现（通过反射或 mixin 替换 VERSIONS map），让 chunk 用自定义压缩存盘。Forge / Fabric 提供这种扩展。

**对你的引擎**：CUSTOM 不需要实现。如果你的引擎只支持 vanilla 兼容，看到 compression_type = 127 报错即可。

## 2.5.9 LZ4 是怎么集成的

LZ4 用的库是 `net.jpountz.lz4.lz4-java`：

```java
import net.jpountz.lz4.LZ4BlockInputStream;
import net.jpountz.lz4.LZ4BlockOutputStream;
```

**LZ4 Block 格式**：把数据分成块（默认 64 KiB），每块独立压缩 + 4 字节 magic + 8 字节 metadata + 压缩数据。比纯 LZ4 raw stream 慢一点点，但有 frame-level recovery（一块坏了不影响其他块）。

**vanilla 配置 `region-file-compression=lz4`** 后，新写入的 chunk 用这种格式。LZ4 实测：

- **DEFLATE**：50 KB raw → 10 KB on disk，写 ~3 ms。
- **LZ4**：50 KB raw → 25 KB on disk，写 ~0.6 ms。

**SSD 用户**：磁盘空间便宜，写盘时间贵 → LZ4 划算。
**HDD 用户 / 云存储**：磁盘空间贵，写盘 IO 慢 → DEFLATE 划算。

## 2.5.10 完整的 chunk header 格式（含外部 flag）

回到 2.4.5 的 chunk header，加上 external flag 之后完整解读：

```
chunk header @ sector boundary:
┌──────────────────────────────────────────────────────────┐
│ [4 bytes BE]  length (含 1 byte compression type)         │
├──────────────────────────────────────────────────────────┤
│ [1 byte]      compression_type:                            │
│                  bit 7:    external_flag (0 = inline, 1 = .mcc) │
│                  bits 0-6: real compression id (1/2/3/4/127)    │
├──────────────────────────────────────────────────────────┤
│ [length-1 bytes]  payload                                  │
│   if external:   only filler / unused                      │
│   if internal:   compressed NBT bytes                      │
├──────────────────────────────────────────────────────────┤
│ [padding]  to next sector boundary                         │
└──────────────────────────────────────────────────────────┘
```

External 时 `length = 1`，payload 是 0 字节（只有 1 字节 compression_type 占位）。

## 2.5.11 完整的写 chunk 决策树

```
1. 序列化 CompoundTag → byte[]
2. 用 RegionFileVersion.getSelected() 压缩 → compressed byte[]
3. compressed.length 超过单扇区 (4 KiB - 5 byte header)?
   ├── 不超：sectorsNeeded = ceil((compressed.length + 5) / 4096)
   │
   ├── sectorsNeeded < 256?
   │   ├── 是：内部 chunk
   │   │   ├── 复用旧扇区？(尺寸不变)
   │   │   │   └── yes：原位写
   │   │   └── 否：分配新扇区，释放旧扇区
   │   │
   │   └── 否：外部 chunk
   │       ├── 写裸 compressed → .mcc 文件
   │       └── 主 region 写 dummy 1-sector entry
   │
   └── 写完更新 offset_table[idx] / timestamp_table[idx] / fsync
```

## 2.5.12 实战：手算一个 LZ4-compressed chunk header

某 chunk 在 LZ4 模式下：

1. raw NBT 50 KB。
2. LZ4 压缩 → 22 KB。
3. 加 5 byte header → 22 KB + 5 = 22533 字节。
4. sectorsNeeded = ceil(22533 / 4096) = 6。
5. 内部 chunk，bit 7 = 0。compression_type = 4 (LZ4)。

写入 region：

```
Sector N:    [22533 (BE i32: 00 00 58 05)] [04 (LZ4)] [22528 字节 LZ4 stream] [padding 21 字节]
Sector N+1: 继续 LZ4 stream...
...
Sector N+5: 末尾 + padding
```

主 region offset_table[idx] = `(N << 8) | 6`。

## 2.5.13 内存预算

5 种 RegionFileVersion 实例都是 singleton，开销 ~80 字节 × 5 = 400 字节。`VERSIONS` map 1 KB。可忽略。

每次读 / 写时，inputWrapper / outputWrapper 创建一个解 / 压缩 stream 包装器：~200 字节临时分配。

## 2.5.14 C++ 移植

```cpp
namespace mc::region {

enum class CompressionType : uint8_t {
    GZIP = 1,
    DEFLATE = 2,
    NONE = 3,
    LZ4 = 4,
    CUSTOM = 127
};

constexpr uint8_t EXTERNAL_STREAM_FLAG = 0x80;

class CompressionVersion {
public:
    using DecompressFn = std::function<std::vector<std::byte>(std::span<const std::byte>)>;
    using CompressFn   = std::function<std::vector<std::byte>(std::span<const std::byte>)>;

    CompressionType id;
    std::string optionName;
    DecompressFn decompress;
    CompressFn   compress;

    static const CompressionVersion& byId(uint8_t id) {
        switch (CompressionType(id & ~EXTERNAL_STREAM_FLAG)) {
            case CompressionType::GZIP:    return GZIP();
            case CompressionType::DEFLATE: return DEFLATE();
            case CompressionType::NONE:    return NONE();
            case CompressionType::LZ4:     return LZ4();
            default: throw std::runtime_error("Invalid compression");
        }
    }
    
    static const CompressionVersion& GZIP();
    static const CompressionVersion& DEFLATE();
    static const CompressionVersion& NONE();
    static const CompressionVersion& LZ4();
    static const CompressionVersion& selected();
    static void configure(const std::string& name);
};

inline bool isExternalChunk(uint8_t compType) {
    return (compType & EXTERNAL_STREAM_FLAG) != 0;
}

}
```

**库依赖**：

- **zlib**（系统库）：DEFLATE / GZIP。GZIP 比 DEFLATE 多个 18 字节文件头，编程上几乎一样。
- **lz4**（github.com/lz4/lz4）：LZ4。轻量 C 库，集成简单。
- **NONE**：直接 memcpy / span 即可。

每个压缩函数最简实现（DEFLATE 例）：

```cpp
std::vector<std::byte> deflateCompress(std::span<const std::byte> input) {
    z_stream strm{};
    deflateInit(&strm, Z_DEFAULT_COMPRESSION);

    strm.next_in = (Bytef*)input.data();
    strm.avail_in = uInt(input.size());

    std::vector<std::byte> output;
    output.reserve(input.size() / 2);

    std::array<std::byte, 4096> buf;
    while (strm.avail_in > 0 || /* not done */) {
        strm.next_out = (Bytef*)buf.data();
        strm.avail_out = buf.size();
        int r = deflate(&strm, strm.avail_in == 0 ? Z_FINISH : Z_NO_FLUSH);
        size_t written = buf.size() - strm.avail_out;
        output.insert(output.end(), buf.begin(), buf.begin() + written);
        if (r == Z_STREAM_END) break;
    }
    deflateEnd(&strm);
    return output;
}
```

外部 .mcc 文件读写：

```cpp
std::filesystem::path externalChunkPath(std::filesystem::path regionDir, ChunkPos pos) {
    return regionDir / ("c." + std::to_string(pos.x) + "." + std::to_string(pos.z) + ".mcc");
}
```

## 2.5.15 一句话总结

`.mca` 支持 5 种 compression：1=GZIP（历史），2=DEFLATE（默认），3=NONE（调试），4=LZ4（速度优先 1.20.5+），127=CUSTOM（mod 扩展占位）；`compression_type` 字节的 bit 7 是 external flag——置位时数据在 `c.X.Z.mcc` 外部文件，绕开单 chunk 256 扇区 = 1 MiB 限制；同一 region 整体用一种 version 写，但读时按每 chunk 自己的 header 类型解，新旧格式可混存；服务器 `region-file-compression=lz4` 切换。
