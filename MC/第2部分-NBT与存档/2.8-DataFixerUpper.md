# 2.8 DataFixerUpper：跨版本兼容性

## 2.8.0 你将在本节学到什么

读完这一节你应当能闭着眼睛回答：

## 2.8.1 问题陈述

**Minecraft 14 年来格式变化巨大**：

| 版本 | 关键格式变化 |
|------|-------------|
| Beta 1.3 (2011) | 引入 `.mca` region 格式 |
| 1.2 (2012) | Anvil 文件格式 + 256 高度 |
| 1.7 (2013) | 区块数据扩展（biome 字节、heightmap） |
| 1.8 (2014) | 方块 / 物品 ID 扩展，支持 mod tag |
| 1.13 (2018) | **"Flattening"**——方块 ID 整数 → 字符串 |
| 1.14 (2019) | 大型生物群系、新农作物 / 蜜蜂 NBT |
| 1.16 (2020) | 下界改造，下界 biome 拓展 |
| 1.17 (2021) | Y 高度从 256 → 384，扩展为 -64..320 |
| 1.18 (2021) | 新世界生成（noise router、climate） |
| 1.20.5 (2024) | DataComponent 系统替代 ItemStack tag |
| 1.21 (2024) | ChunkStatusTasks 重构 |

如果你 2011 年存了一个世界，按 2024 年的格式它**完全打不开**——名字、字段、值的语义都变了。

**Mojang 不能强行让玩家"舍弃旧存档"**——这会摧毁玩家信任。所以必须支持旧存档透明升级。

**DataFixerUpper（DFU）** 是这个升级机制的实现。

---

## 2.8.2 DFU 是什么

**DataFixerUpper** 是 Mojang 在 GitHub 开源的库（github.com/Mojang/DataFixerUpper），后来内嵌到 Minecraft 自身。它有两个职责：

### 职责 1：Codec 系统（已在 0.5 节讲过）

`Codec<T>` / `DynamicOps` / `RecordCodecBuilder` —— "双向序列化器"。这部分我们已经熟悉了。

### 职责 2：Data Fixer

把"旧格式数据"按一系列规则迁移到"新格式数据"。这是本节主题。

**两个职责共享一些抽象**（`Type` / `TypeFamily` / `Pointer`），但概念上是两个独立子系统。

---

## 2.8.3 DataVersion：单调递增的格式版本号

每个 NBT 数据（chunk、玩家、level.dat、物品）都带一个 `DataVersion` 字段：

```json
{
    "DataVersion": 4189,    // 1.21.4 的 DataVersion
    "Status": "minecraft:full",
    ...
}
```

**`DataVersion`** 是个**全 Minecraft 共用**的单调递增整数。每发布一个新版本就 +N。

| 版本 | DataVersion |
|------|-------------|
| 1.13 | 1519 |
| 1.14.4 | 1976 |
| 1.16.5 | 2586 |
| 1.17.1 | 2730 |
| 1.18.2 | 2975 |
| 1.19.4 | 3337 |
| 1.20.1 | 3465 |
| 1.20.4 | 3700 |
| 1.20.6 | 3839 |
| 1.21 | 3953 |
| 1.21.4 | 4189 |

打开存档时：

1. 读 `level.dat`，提取 `DataVersion`。
2. 如果 DataVersion < 当前版本 → 触发 DFU 升级。
3. DFU 按版本顺序应用所有"中间版本"的 fix 规则。

`DataFixers.getDataFixer()`（Mojang 内部静态）是入口：

```java
DataFixer fixer = DataFixers.getDataFixer();
Dynamic<Tag> dyn = new Dynamic<>(NbtOps.INSTANCE, oldNbt);
Dynamic<Tag> upgraded = fixer.update(References.LEVEL, dyn, oldDataVersion, newDataVersion);
CompoundTag upgradedNbt = (CompoundTag) upgraded.getValue();
```

## 2.8.4 Schema：一个版本时刻的"格式快照"

**Schema** 描述某个 DataVersion 时，所有 NBT 数据的 type 形状。例如：

```java
public class V1450 extends NamespacedSchema {
    public V1450(int dataVersion, Schema parent) { super(dataVersion, parent); }

    @Override
    public Map<String, Supplier<TypeTemplate>> registerEntities(Schema schema) {
        Map<String, Supplier<TypeTemplate>> map = super.registerEntities(schema);
        schema.register(map, "minecraft:cat", () -> 
            DSL.optionalFields("Owner", DSL.string(), "OwnerUUID", DSL.string()));
        return map;
    }
}
```

**Schema 的两个核心方法**：

- `registerTypes` —— 注册各 NBT 类型族（chunk / level / player / entity / blockEntity / item ⋯⋯）的形状。
- `registerEntities` / `registerBlockEntities` —— 注册某个 entity / blockEntity 类型的字段集。

每个 Schema 对应一个 DataVersion——比如 `V1450` 是 DataVersion 1450 时刻的 schema，`V1460` 是 1460 时刻的。

**Schemas 的家族**：

```java
public class DataFixers {
    private static final BiFunction<Integer, Schema, Schema> SAME = Schema::new;
    
    private static DataFixer createFixerUpper() {
        DataFixerBuilder builder = new DataFixerBuilder(SharedConstants.getCurrentVersion().getDataVersion().getVersion());
        addFixers(builder);
        return builder.buildUnoptimized();    // 或 buildOptimized()
    }

    private static void addFixers(DataFixerBuilder builder) {
        Schema schema = builder.addSchema(99, V99::new);
        builder.addFixer(new EntityIdFix(schema, ...));
        
        Schema schema100 = builder.addSchema(100, V100::new);
        builder.addFixer(new EntityRemoveBaseAttributeName(schema100, ...));
        
        // ... 上百个 schema + fix ⋯⋯
        
        Schema schemaCurrent = builder.addSchema(4189, V4189::new);
    }
}
```

**`addFixers` 在源码里有几千行**——每个版本的所有格式变更都在这里登记。Mojang 自己有一份完整的"fix history"。

## 2.8.5 Fix：单条迁移规则

一个 Fix 是**输入旧格式 → 输出新格式**的纯函数。继承 `DataFix` 抽象类。

最简单的例子：**把方块 NBT 中 `"id": "stone"` 改成 `"id": "minecraft:stone"`**：

```java
public class AddDefaultNamespaceFix extends DataFix {
    public AddDefaultNamespaceFix(Schema schema, boolean changesType) {
        super(schema, changesType);
    }

    @Override
    public TypeRewriteRule makeRule() {
        Type<?> blockTagType = this.getInputSchema().getType(References.BLOCK_NAME);
        return this.fixTypeEverywhereTyped("AddDefaultNamespace", blockTagType, typed -> {
            return typed.update(DSL.remainderFinder(), dyn -> {
                String name = dyn.asString().result().orElse("minecraft:air");
                if (!name.contains(":")) {
                    return dyn.createString("minecraft:" + name);
                }
                return dyn;
            });
        });
    }
}
```

**逐字段读**：

- `getInputSchema()` —— 拿到这个 Fix 输入端的 schema（"上一个版本"）。
- `getType(References.BLOCK_NAME)` —— 取"方块名"这个类型族的 type 描述。
- `fixTypeEverywhereTyped(name, type, transform)` —— 对所有数据中匹配该 type 的位置应用 transform 函数。
- `typed.update(DSL.remainderFinder(), dyn -> ...)` —— 修改 typed 中那个 type 的具体值。

效果：扫描整个 NBT 树，**找到任何标记为 BLOCK_NAME 的字符串**，如果它没有冒号，前面加 `"minecraft:"`。

**这就是 1.13 "Flattening" 的一部分**——把硬编码的整数 ID 改成字符串后，又要把无前缀字符串改成全限定字符串。

## 2.8.6 Type / TypeFamily：DFU 的类型系统

DFU 内置一个**轻量的类型系统**描述 NBT 形状：

```java
DSL.string()                               // 字符串
DSL.intType()                              // int
DSL.list(DSL.string())                     // List<String>
DSL.compoundList(DSL.string(), DSL.intType())  // List<{String -> int}>
DSL.fields("name", DSL.string(),
           "count", DSL.intType())          // { name: String, count: int }
DSL.optionalFields("Owner", DSL.string()) // { Owner?: String }
DSL.named("minecraft:item",
          DSL.fields(...))                  // tagged compound
```

这些 DSL 函数生成 `TypeTemplate`，组合起来描述任意 NBT 形状。

**TypeFamily** 是"按 DataVersion 索引的 type 簇"——同一个概念（如 "Item"）在不同版本有不同 type。DFU 知道 v1500 的 Item 形状是 X、v1600 的形状是 Y，能精确计算两个版本之间需要怎样的 transform。

**对引擎移植**：这套类型系统是 DFU 的**最复杂部分**，背后有不少范畴论概念（Functor / monad / contravariance）。1:1 复刻在 C++ 里**非常痛苦**，性价比低。

## 2.8.7 完整的更新流程

```java
// 假设玩家加载一个 1.16 存档（DataVersion 2586）
CompoundTag oldChunkNbt = ...;       // 从磁盘读出来的 NBT
int oldVersion = oldChunkNbt.getInt("DataVersion");        // 2586

DataFixer fixer = DataFixers.getDataFixer();
int currentVersion = SharedConstants.getCurrentVersion().getDataVersion().getVersion();   // 4189

Dynamic<Tag> dyn = new Dynamic<>(NbtOps.INSTANCE, oldChunkNbt);
Dynamic<Tag> upgraded = fixer.update(References.CHUNK, dyn, oldVersion, currentVersion);
CompoundTag newChunkNbt = (CompoundTag) upgraded.getValue();
// 现在 newChunkNbt 是 1.21.4 格式
```

**DFU 内部**：

1. 找出从 oldVersion 到 currentVersion 之间的所有 fix（按 DataVersion 升序）。
2. 依次应用每个 fix 的 TypeRewriteRule。
3. 整个过程是纯函数式（不修改输入）。

**性能**：对一个普通 chunk（50 KB NBT）从 1.16 升级到 1.21，几十个 fix，总时间 5-50 ms。比正常加载慢，但是**只发生一次**（升级后写回新格式）。

## 2.8.8 Mojang 实际的 fix 例子（节选）

打开 `com.mojang.datafixers.fixes.OptionsAccessibilityOnboardFix`（其实在 vanilla mc/datafixers 包）：

```java
public class OptionsAccessibilityOnboardFix extends DataFix {
    public OptionsAccessibilityOnboardFix(Schema schema, boolean changesType) {
        super(schema, changesType);
    }

    @Override
    public TypeRewriteRule makeRule() {
        return this.fixTypeEverywhereTyped("OptionsAccessibilityOnboardFix", 
            this.getInputSchema().getType(References.OPTIONS),
            t -> t.update(DSL.remainderFinder(), 
                d -> d.set("onboardAccessibility", d.createString("false"))));
    }
}
```

**这是 1.20.4 时新增**：给玩家选项添加一个 `onboardAccessibility` 字段，旧版本没这个字段——fix 给所有旧 options 加上 `"false"` 默认值。

**复杂例子**：1.13 的 "Flattening" 把方块 ID 1 → "minecraft:stone"，2 → "minecraft:grass_block"，⋯⋯。这个 fix 是个超长 lookup table（几千行 hardcoded），按旧 ID 整数查新字符串。

源码在 `net.minecraft.util.datafix.fixes.*` —— 整个包有约 200 个 fix 类。

## 2.8.9 不同 References 类别

DFU 把 NBT 数据按"用途"分类：

```java
public class References {
    public static final TypeReference LEVEL = ...;
    public static final TypeReference PLAYER = ...;
    public static final TypeReference CHUNK = ...;
    public static final TypeReference HOTBAR = ...;
    public static final TypeReference OPTIONS = ...;
    public static final TypeReference STRUCTURE = ...;
    public static final TypeReference STATS = ...;
    public static final TypeReference SAVED_DATA = ...;
    public static final TypeReference ADVANCEMENTS = ...;
    public static final TypeReference POI_CHUNK = ...;
    public static final TypeReference WORLD_GEN_SETTINGS = ...;
    public static final TypeReference ENTITY_CHUNK = ...;
    public static final TypeReference DATA_COMPONENTS = ...;
    public static final TypeReference VILLAGER_TRADE = ...;
    // ⋯⋯ 共 ~30 个
}
```

**调用 `fixer.update(reference, dyn, oldVer, newVer)` 时必须指明 reference**——DFU 才知道这堆数据是 chunk 还是 player，应用相应 fix 集合。

**典型用法**：
- `ChunkSerializer.read(...)` 用 `References.CHUNK`。
- `LevelStorageSource.read(...)` 用 `References.LEVEL`。
- `Player.read(...)` 用 `References.PLAYER`。

## 2.8.10 Optimized vs Unoptimized

```java
DataFixer fixer = builder.buildOptimized();    // 或 buildUnoptimized()
```

**两种构建策略**：

- **Unoptimized**：每个 fix 独立应用 → 每个版本之间扫一遍 NBT 树。慢但简单。
- **Optimized**：DFU 静态分析所有 fix → 合并多个 fix 为一次扫描，避免重复遍历。**首次构建慢**（几秒），后续 fix 操作快。

vanilla 客户端用 **Optimized**——预付出几秒的构建开销，运行时 fix 快 5-10×。

## 2.8.11 你的引擎要不要实现 DFU？

**首要决策**：你的 C++ 引擎是要打开 vanilla 存档？还是只读自己产生的存档？

| 场景 | 是否需要 DFU |
|------|-------------|
| 只想自己引擎独立运行（自己存档） | **不需要**——你定义自己的 DataVersion，每个版本只兼容向下一格 |
| 想读 vanilla 玩家的存档（mod 工具、第三方编辑器） | **需要**——必须实现 DFU 或调用 Mojang 的库 |
| 与 vanilla 客户端互联（你做服务端） | **可选**——如果你只支持当前版本协议，不严格需要 DFU；但你必须正确序列化 NBT 让 vanilla 客户端理解 |

**实现 DFU 的选项**：

1. **跳过**：自己定义 DataVersion，每发布新版本写一组 fix。复杂度可控。
2. **JNI 调用 Java DFU**：跑一个 JVM，通过 JNI 用 Mojang 的 DFU。代价是依赖 JVM 运行时。
3. **手写 mini DFU**：实现最关键的几个 fix（如 1.13 Flattening）。够覆盖玩家存档但不能保证旧版本完整兼容。
4. **完整 C++ 复刻**：~5000 行代码，加上 Mojang 200 个 fix 的 C++ 翻译。**约 1-2 人月工作量**。

**我的建议**：第一版引擎跳过 DFU，只支持 1.21 当前版本格式。等真要兼容旧版时再补。

## 2.8.12 真实场景：升级一个 1.18 存档到 1.21

```
玩家把 1.18 存档拷贝到 1.21 客户端
  ▼
启动 1.21，选择该存档进入
  ▼
LevelStorage 读 level.dat
  → DataVersion = 2975 (1.18.2)
  → 当前 = 4189 (1.21.4)
  ▼
DataFixer.update(References.LEVEL, levelDat, 2975, 4189)
  → 应用 1.18.2 → 1.19 → 1.19.4 → 1.20 → ⋯ → 1.21.4 之间所有 LEVEL fix
  → 几百毫秒
  ▼
显示 "Optimizing world..." 进度条
  ▼
对每个 chunk:
  RegionFile.read(pos) → CompoundTag
  → DataVersion = 2975
  → DataFixer.update(References.CHUNK, ..., 2975, 4189)
  → 写回新 NBT
  ▼
所有 chunk 升级完毕（分钟级）
  ▼
正常进入游戏
```

**升级是 destructive 的** —— 写回后旧 1.18 客户端不能再读这存档。Mojang 在升级前会提示"备份"。

## 2.8.13 NbtUtils.addCurrentDataVersion

每次 chunk 写盘都会自动注入当前 DataVersion：

```java
// NbtUtils.java
public static CompoundTag addCurrentDataVersion(CompoundTag tag) {
    return addDataVersion(tag, SharedConstants.getCurrentVersion().getDataVersion().getVersion());
}

public static CompoundTag addDataVersion(CompoundTag tag, int version) {
    tag.putInt("DataVersion", version);
    return tag;
}
```

调用方：

```java
public static CompoundTag write(SerializableChunkData chunk) {
    CompoundTag root = NbtUtils.addCurrentDataVersion(new CompoundTag());
    // ... 其余字段 ...
}
```

**保证**：写出去的每个 NBT 文件都带正确的 DataVersion，下次读时 DFU 知道从哪个版本开始升级。

## 2.8.14 C++ 移植：迷你 DFU

如果你决定支持几个旧版本（比如向下兼容到 1.18），可以实现一个简化版：

```cpp
namespace mc::datafix {

class DataFixer {
public:
    using Fix = std::function<void(NbtCompound&)>;
    
    void registerFix(Reference ref, int sinceVersion, Fix fix) {
        fixes_[ref].push_back({sinceVersion, std::move(fix)});
    }
    
    void update(Reference ref, NbtCompound& tag, int fromVersion, int toVersion) {
        auto& fixes = fixes_.at(ref);
        for (auto& [version, fix] : fixes) {
            if (version > fromVersion && version <= toVersion) {
                fix(tag);
            }
        }
    }

private:
    enum class Reference { LEVEL, CHUNK, PLAYER, ITEM, ENTITY };
    struct FixEntry { int sinceVersion; Fix fix; };
    std::map<Reference, std::vector<FixEntry>> fixes_;
};

// 使用
DataFixer fixer;

fixer.registerFix(Reference::CHUNK, 2975, [](NbtCompound& chunk) {
    // 1.19.0 引入了 yPos 字段
    if (!chunk.contains("yPos")) {
        chunk["yPos"] = -4;
    }
});

fixer.registerFix(Reference::CHUNK, 3700, [](NbtCompound& chunk) {
    // 1.20.4 重命名了 "block_ticks" 字段（hypothetical）
    // ⋯⋯
});

// 加载时
NbtCompound chunkNbt = readFromDisk(...);
int oldVer = chunkNbt.getInt("DataVersion").value_or(0);
fixer.update(Reference::CHUNK, chunkNbt, oldVer, CURRENT_DATA_VERSION);
```

**简化版的代价**：

- 不能精确推断 type（没有 DSL.string() 之类的 type system）。
- 全程操作 raw NBT（容易写错）。
- fix 顺序需要手动维护（按版本号排）。
- 没有 "type-aware" 的全局 transform（如 "找到所有 BLOCK_NAME 字符串加前缀"——你得自己写遍历）。

**对自己引擎可接受**——但不要拿来读 vanilla 存档，会漏掉 Mojang 的复杂 fix。

## 2.8.15 一句话总结

DataFixerUpper（DFU）是 Mojang 自家开源库（github.com/Mojang/DataFixerUpper），承担"NBT 跨版本格式迁移"——每个 NBT 数据带 `DataVersion` 整数，加载时 DFU 应用从旧版本到当前的所有 fix 规则；**Codec 系统**和 **Data Fixer 系统**虽然同库但概念独立；Schema 描述某 DataVersion 时刻的 type 形状，Fix 是单条迁移规则（输入旧 → 输出新）；vanilla 内置 ~200 个 fix 覆盖 14 年的格式变更；自己的引擎可选迷你版（vector<FixFunction>）或跳过 DFU 只支持当前格式。
