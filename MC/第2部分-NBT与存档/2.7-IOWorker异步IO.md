# 2.7 IOWorker 异步 IO

## 2.7.0 你将在本节学到什么

读完这一节你应当能闭着眼睛回答：

1. 服务端 tick 线程每 tick 50 ms。如果中间夹一次磁盘写盘（10-50 ms），TPS 就崩了。Mojang 怎么避免这事？
2. `IOWorker` 是什么？它有几个线程？怎么调度优先级？
3. 同一个 chunk 在 1 秒内被改 5 次，IOWorker 写盘几次？

5. `synchronize(boolean)` 这个方法什么时候被调用？为什么要用 boolean 区分？
6. `scanChunk(pos, visitor)` 让 IOWorker 流式扫描某 chunk 的某个字段——这有什么用？
7. C++ 里复刻这套机制要用 thread pool 还是单线程 + 队列？

---

## 2.7.1 问题陈述

回顾 0.2 节：服务端 tick 线程每 50 ms 一拍，要做完世界更新 + 实体 tick + 网络处理一切事。

如果在 tick 线程里直接 fsync 一个 chunk：
- 序列化 ~3 ms。
- 压缩 ~5 ms。
- 写到 region 文件 ~5 ms（SSD）/ ~50 ms（机械盘）。
- fsync ~1-50 ms。

**单 chunk 写盘 ≥ 14 ms**——一次写盘能让 TPS 跌到 14/s。卸载 100 个 chunk 一次 = 1.4 秒卡顿。

**Mojang 的解法**：把所有磁盘 IO 推到**单独的后台线程**——`IOWorker`。tick 线程只把"我想保存这个 chunk"的指令塞进队列，立刻返回，**主线程零阻塞**。

---

## 2.7.2 IOWorker 是什么

`net.minecraft.world.level.chunk.storage.IOWorker` 是一个**单实例（per-dimension）的异步 IO 调度器**：

```java
public class IOWorker implements ChunkScanAccess, AutoCloseable {
    private final AtomicBoolean shutdownRequested = new AtomicBoolean();
    private final PriorityConsecutiveExecutor consecutiveExecutor;
    private final RegionFileStorage storage;
    private final SequencedMap<ChunkPos, PendingStore> pendingWrites = new LinkedHashMap<>();
    private final Long2ObjectLinkedOpenHashMap<CompletableFuture<BitSet>> regionCacheForBlender = new Long2ObjectLinkedOpenHashMap<>();
    private static final int REGION_CACHE_SIZE = 1024;

    protected IOWorker(RegionStorageInfo info, Path regionDir, boolean syncWrites) {
        this.storage = new RegionFileStorage(info, regionDir, syncWrites);
        this.consecutiveExecutor = new PriorityConsecutiveExecutor(
            IOWorker.Priority.values().length,
            Util.ioPool(),
            "IOWorker-" + info.type()
        );
    }
}
```

**核心字段**：

- `consecutiveExecutor`：执行队列（带优先级）。所有 IO 操作通过它串行调度。
- `storage`：底层 `RegionFileStorage`（包装多个 RegionFile）。
- `pendingWrites`：**待写队列**——主线程"想写"的 chunk 先进这里，后台线程慢慢消化。
- `regionCacheForBlender`：1.18 边界融合的 LRU 缓存（用于检测某 region 是否含旧版本 chunk）。

**注意 `pendingWrites` 是 `SequencedMap`**——保留插入顺序，按"先想保存的先 flush"。

---

## 2.7.3 PriorityConsecutiveExecutor：单线程 + 优先级

```java
import net.minecraft.util.thread.PriorityConsecutiveExecutor;
```

这是 Mojang 自家的 executor。两个特性：

1. **单线程**：所有任务串行执行，避免 region 文件并发访问。
2. **优先级**：任务可标 FOREGROUND / BACKGROUND，前者优先调度。

**为什么单线程？** 因为 `RegionFile` 自己的 `synchronized` 锁已经按 region 串行化了。再多线程也吃同一个锁，没用。

**为什么 IOWorker 整体用单线程**？还有一个理由：保持**"先 store 的先生效"**语义。如果用线程池，task A 写 chunkX、task B 写同一个 chunkX，可能 B 先完成 → 用 A 的旧数据覆盖了 B 的新数据。串行执行就没这问题。

`Util.ioPool()` 是底层线程池——但 PriorityConsecutiveExecutor 只从中借**一个**线程做任务，不并行。

**两个优先级**：

```java
enum Priority {
    FOREGROUND,    // 主线程提交的"我要立即处理"
    BACKGROUND     // 自我重新调度的"消耗 pendingWrites 队列"
}
```

FOREGROUND 任务（如 store / loadAsync）插队到队列前面。BACKGROUND 任务（自调度的 storePendingChunk）排在后面。这样**新到的 store 请求先入 pendingWrites**，**消耗 pendingWrites 在空闲时进行**。

## 2.7.4 store：主线程的"塞队列"操作

打开 `IOWorker.store`（行 124-135）：

```java
public CompletableFuture<Void> store(ChunkPos pos, @Nullable CompoundTag tag) {
    return this.store(pos, () -> tag);
}

public CompletableFuture<Void> store(ChunkPos pos, Supplier<CompoundTag> tagSupplier) {
    return this.<CompletableFuture<Void>>submitTask(() -> {
        CompoundTag tag = tagSupplier.get();
        PendingStore pending = this.pendingWrites.computeIfAbsent(pos, p -> new PendingStore(tag));
        pending.data = tag;
        return pending.result;
    }).thenCompose(Function.identity());
}
```

**两层 future**：

- 外层 `submitTask` 提交一个"把 chunk 加进 pendingWrites"的小任务（FOREGROUND 优先级，立刻执行）。
- 内层任务返回 `pending.result`——这是真正"已经写到磁盘"的 future。
- `.thenCompose(Function.identity())` 把双层 future 拍平成一层。

**关键设计**：

1. 主线程调用 `iow.store(pos, tag)` 立刻返回一个 `CompletableFuture<Void>`，**不等磁盘**。
2. 内部"加进 pendingWrites" 这个小操作也是异步的——但它是 FOREGROUND 优先级，几乎瞬间完成。
3. 真正的磁盘写发生在 BACKGROUND 任务（`storePendingChunk`）里。

**`PendingStore` 数据结构**（IOWorker 内部）：

```java
private static class PendingStore {
    @Nullable CompoundTag data;
    final CompletableFuture<Void> result = new CompletableFuture<>();
    
    PendingStore(@Nullable CompoundTag data) { this.data = data; }
    
    @Nullable
    CompoundTag copyData() { return this.data == null ? null : this.data.copy(); }
}
```

**重要**：`data` 字段是 `volatile`-ish 的——后续的 store 调用如果对同一 chunk pos，会**覆盖**这个字段，而**不**新建 entry。

效果：**一个 chunk 在被 background 实际写盘之前被 store 100 次，只占一个 PendingStore，最后用最新数据写一次**。这就是"批合并 / 去重"。

## 2.7.5 storePendingChunk：后台 flusher

```java
private void storePendingChunk() {
    Entry<ChunkPos, PendingStore> entry = this.pendingWrites.pollFirstEntry();
    if (entry != null) {
        this.runStore(entry.getKey(), entry.getValue());
        this.tellStorePending();      // 调度下一次
    }
}

private void tellStorePending() {
    this.consecutiveExecutor.schedule(
        new StrictQueue.RunnableWithPriority(Priority.BACKGROUND.ordinal(), this::storePendingChunk)
    );
}

private void runStore(ChunkPos pos, PendingStore pending) {
    try {
        this.storage.write(pos, pending.data);     // 真正写盘
        pending.result.complete(null);              // 通知 future
    } catch (Exception e) {
        pending.result.completeExceptionally(e);
        LOGGER.error("Failed to store chunk {}", pos, e);
    }
}
```

**自我递归式调度**：

1. `storePendingChunk` 处理一个 entry。
2. 处理完调 `tellStorePending` 给自己排个 BACKGROUND 任务。
3. 因为 BACKGROUND 优先级低，如果有 FOREGROUND 任务插进来（store / loadAsync），先做那个，再回到 storePendingChunk。

**结果**：BackgroundFlusher 是个"懒贪婪"消费者，**主线程不忙时才慢慢消化 pendingWrites**。

**触发点**：`tellStorePending()` 也在 `submitTask / submitThrowingTask` 的尾部调用：

```java
private <T> CompletableFuture<T> submitTask(Supplier<T> task) {
    return this.consecutiveExecutor.scheduleWithResult(Priority.FOREGROUND.ordinal(), p -> {
        if (!this.shutdownRequested.get()) {
            p.complete(task.get());
        }
        this.tellStorePending();    // ★ 每个 FOREGROUND 任务完成后都插一个 BACKGROUND 检查
    });
}
```

每次 FOREGROUND 任务做完就排个 BACKGROUND，确保 pendingWrites 不会无限堆积。

## 2.7.6 loadAsync：读取的优先

```java
public CompletableFuture<Optional<CompoundTag>> loadAsync(ChunkPos pos) {
    return this.submitThrowingTask(() -> {
        PendingStore pending = this.pendingWrites.get(pos);
        if (pending != null) {
            return Optional.ofNullable(pending.copyData());     // ★ 优先读 pending
        }
        try {
            return Optional.ofNullable(this.storage.read(pos));
        } catch (Exception e) {
            LOGGER.warn("Failed to read chunk {}", pos, e);
            throw e;
        }
    });
}
```

**关键**：**读取优先看 pendingWrites**——如果某 chunk 刚被 store 但还没真正写到磁盘，`loadAsync` 直接从 pending 拿数据。**保证一致性**：玩家修改 chunk → 立刻读它 → 看到自己的修改（即使磁盘还是旧版本）。

**`copyData()` 返回深拷贝**——避免 caller 修改影响 pending 还未写盘的数据。

## 2.7.7 synchronize：等待所有写完成

```java
public CompletableFuture<Void> synchronize(boolean flushFsync) {
    CompletableFuture<Void> waitAll = this.<CompletableFuture<Void>>submitTask(() ->
        CompletableFuture.allOf(
            this.pendingWrites.values().stream()
                .map(p -> p.result)
                .toArray(CompletableFuture[]::new)
        )
    ).thenCompose(Function.identity());

    return flushFsync 
        ? waitAll.thenCompose(v -> this.submitThrowingTask(() -> {
            try {
                this.storage.flush();    // ★ fsync 全部 region 文件
                return null;
            } catch (Exception e) { throw e; }
        }))
        : waitAll.thenCompose(v -> this.submitTask(() -> null));
}
```

**两种语义**：

- `synchronize(false)`：等待所有 pendingWrites 写到 OS 缓冲（不强制 fsync）。返回时所有 chunk 都"逻辑上保存了"。
- `synchronize(true)`：上面 + 调 `storage.flush()` 强制 fsync 所有 region 文件到磁盘。**真正写盘完成**。

**调用时机**：

| 场景 | 用 false 还是 true |
|------|-------------------|
| 玩家保存命令 `/save-all` | true |
| 服务器关闭 | true |
| 维度切换、内部 checkpoint | false |
| 自动保存（每 6000 tick = 5 分钟） | true |

**性能考虑**：fsync 是慢操作（HDD 几十 ms / SSD 几 ms × N region 文件）。但保证持久化。

## 2.7.8 scanChunk：流式扫描

```java
@Override
public CompletableFuture<Void> scanChunk(ChunkPos pos, StreamTagVisitor visitor) {
    return this.submitThrowingTask(() -> {
        PendingStore pending = this.pendingWrites.get(pos);
        if (pending != null) {
            if (pending.data != null) {
                pending.data.acceptAsRoot(visitor);     // 内存版直接 accept
            }
        } else {
            this.storage.scanChunk(pos, visitor);       // 磁盘版流式 parse
        }
        return null;
    });
}
```

**用途**：从 region 文件**只读取某 chunk 的某些字段**，不全解析。

**典型用例**（IOWorker 内部 `createOldDataForRegion` 行 88-118）：

```java
private CompletableFuture<BitSet> createOldDataForRegion(int rx, int rz) {
    return CompletableFuture.supplyAsync(() -> {
        ChunkPos min = ChunkPos.minFromRegion(rx, rz);
        ChunkPos max = ChunkPos.maxFromRegion(rx, rz);
        BitSet result = new BitSet();
        ChunkPos.rangeClosed(min, max).forEach(pos -> {
            CollectFields collector = new CollectFields(
                new FieldSelector(IntTag.TYPE, "DataVersion"),
                new FieldSelector(CompoundTag.TYPE, "blending_data")
            );
            try {
                this.scanChunk(pos, collector).join();
            } catch (Exception e) {
                LOGGER.warn("Failed to scan chunk {}", pos, e);
                return;
            }
            if (collector.getResult() instanceof CompoundTag tag && this.isOldChunk(tag)) {
                int idx = pos.getRegionLocalZ() * 32 + pos.getRegionLocalX();
                result.set(idx);
            }
        });
        return result;
    }, Util.backgroundExecutor());
}
```

**这段代码做的事**：扫整个 region 的 1024 个 chunk，对每个 chunk **只读 DataVersion 和 blending_data 两个顶层字段**（不解析 sections / blockEntities 等几十 KB 数据），快速判定哪些是"旧版本 chunk"（需要边界融合）。

**性能差异**：

- 全解析：1024 chunks × 50 KB × 反序列化开销 ≈ 数秒。
- 流式扫描：1024 chunks × 几个字段 × 1 ms ≈ 1 秒。

**这就是 1.18+ 边界融合（"老 chunk + 新 chunk 之间地形顺滑过渡"）能在合理时间完成的原因**。

`CollectFields` 是 `StreamTagVisitor` 的子类（2.3.9 节看过）——只 ENTER 匹配的字段，SKIP 其他。

## 2.7.9 RegionFileStorage：单线程多 RegionFile 管理

`IOWorker` 持有一个 `RegionFileStorage`：

```java
public class RegionFileStorage implements AutoCloseable {
    public static final String ANVIL_EXTENSION = ".mca";
    private static final int MAX_CACHE_SIZE = 256;
    private final Long2ObjectLinkedOpenHashMap<RegionFile> regionCache = new Long2ObjectLinkedOpenHashMap<>();
    private final RegionStorageInfo info;
    private final Path folder;
    private final boolean sync;

    public RegionFileStorage(RegionStorageInfo info, Path folder, boolean sync) {
        this.folder = folder;
        this.sync = sync;
        this.info = info;
    }

    private RegionFile getRegionFile(ChunkPos pos) throws IOException {
        long regionLong = ChunkPos.asLong(pos.getRegionX(), pos.getRegionZ());
        RegionFile cached = this.regionCache.getAndMoveToFirst(regionLong);
        if (cached != null) return cached;
        if (this.regionCache.size() >= MAX_CACHE_SIZE) {
            this.regionCache.removeLast().close();    // LRU evict
        }
        Files.createDirectories(this.folder);
        Path mcaPath = this.folder.resolve("r." + pos.getRegionX() + "." + pos.getRegionZ() + ".mca");
        RegionFile rf = new RegionFile(this.info, mcaPath, this.folder, this.sync);
        this.regionCache.putAndMoveToFirst(regionLong, rf);
        return rf;
    }

    @Nullable
    public CompoundTag read(ChunkPos pos) throws IOException {
        RegionFile rf = this.getRegionFile(pos);
        try (DataInputStream is = rf.getChunkDataInputStream(pos)) {
            if (is == null) return null;
            return NbtIo.read(is);
        }
    }

    public void write(ChunkPos pos, @Nullable CompoundTag tag) throws IOException {
        RegionFile rf = this.getRegionFile(pos);
        if (tag == null) {
            rf.clear(pos);
        } else {
            try (DataOutputStream os = rf.getChunkDataOutputStream(pos)) {
                NbtIo.write(tag, os);
            }
        }
    }

    public void scanChunk(ChunkPos pos, StreamTagVisitor visitor) throws IOException {
        RegionFile rf = this.getRegionFile(pos);
        try (DataInputStream is = rf.getChunkDataInputStream(pos)) {
            if (is != null) NbtIo.parse(is, visitor, NbtAccounter.unlimitedHeap());
        }
    }

    public void flush() throws IOException {
        for (RegionFile rf : this.regionCache.values()) rf.flush();
    }
}
```

**核心**：

1. **LRU cache 256 个 RegionFile**——按"最近用过"排序，超过 256 时关闭最久未用的。
2. **`getRegionFile(pos)`** 按需打开 region 文件。每次 read / write / scan 都走它。
3. **`tag == null` 等于删除 chunk**（`rf.clear(pos)`）。
4. 这一层不是线程安全的——**只在 IOWorker 单线程内调用**保证安全。

## 2.7.10 完整调用链回顾

服务器整体写盘的全栈：

```
ServerChunkCache.save(force)
  ▼
ChunkMap.save(chunk)
  ▼
SerializableChunkData.copyOf(...).write(...)
  ▼ (返回 CompoundTag)
ChunkMap.write(pos, tag) → IOWorker.store(pos, tag)
  ▼ (CompletableFuture 立刻返回)
[主线程继续 tick]

[后台 IOWorker 线程：]
  storePendingChunk
    ▼
  RegionFileStorage.write(pos, tag)
    ▼
  RegionFile.getChunkDataOutputStream(pos)
    ▼
  RegionFileVersion.wrap(buffer)            ← 压缩
    ▼
  NbtIo.write(tag, dos)                     ← 序列化
    ▼
  ChunkBuffer.close()                       ← 实际写到 region 文件
    ▼
  扇区分配 + 写 + 更新 offset table + fsync
```

主线程从入口到返回 CompletableFuture 通常 **< 50 微秒**。所有真正的 IO 在后台。

## 2.7.11 关闭流程

```java
@Override
public void close() throws IOException {
    if (this.shutdownRequested.compareAndSet(false, true)) {
        this.consecutiveExecutor.scheduleWithResult(...).join();    // 等所有 pending
        this.storage.close();
    }
}
```

**关闭顺序**：

1. 设 `shutdownRequested = true` → 后续提交的任务直接 noop。
2. 等所有 pending 写完。
3. 关 RegionFileStorage（关所有 RegionFile + fsync）。

**保证**：服务器关闭后**不会丢失任何 stored chunk**——只要 store() 调用过、就会被持久化。

`/stop` 命令的内部最后一步就是 `iow.close()`。

## 2.7.12 内存预算

```
IOWorker:
├── consecutiveExecutor (Java task queue)        ~10 KB
├── pendingWrites (LinkedHashMap)                取决于 pending 数量
│   每个 PendingStore: ~30 KB (CompoundTag) × N
├── regionCacheForBlender (LRU 1024)              ~1 MB
└── storage (RegionFileStorage)
    └── regionCache (LRU 256)
        每个 RegionFile: ~10 KB (含 8 KB direct buffer)
        总计: ~2.5 MB

总计: ~5-50 MB（取决于 pending 数）
```

正常情况 pending 队列保持 < 100 entry——主线程产生速度远低于 IO 消化速度。**只有在玩家飞行 + 大量 chunk 卸载** 时 pending 会短暂飙到几千，内存峰值 ~100 MB。

## 2.7.13 C++ 移植

```cpp
namespace mc::io {

class IOWorker {
public:
    IOWorker(std::filesystem::path regionDir, RegionStorageInfo info, bool syncWrites)
        : storage_(std::move(regionDir), info, syncWrites),
          worker_([this]{ this->run(); }) {}

    ~IOWorker() {
        shutdown_.store(true);
        cv_.notify_all();
        worker_.join();
    }

    std::future<void> store(ChunkPos pos, NbtCompound&& tag) {
        std::lock_guard lock(mutex_);
        auto& pending = pendingWrites_[pos];
        pending.data = std::make_unique<NbtCompound>(std::move(tag));
        if (!pending.promise.valid()) {
            pending.promise = std::promise<void>();
        }
        cv_.notify_all();
        return pending.promise.get_future();
    }

    std::future<std::optional<NbtCompound>> loadAsync(ChunkPos pos) {
        return std::async(std::launch::async, [this, pos] {
            std::lock_guard lock(mutex_);
            auto it = pendingWrites_.find(pos);
            if (it != pendingWrites_.end() && it->second.data) {
                return std::optional(NbtCompound(*it->second.data));
            }
            return storage_.read(pos);
        });
    }

    std::future<void> synchronize(bool fsync) {
        return std::async(std::launch::async, [this, fsync] {
            std::unique_lock lock(mutex_);
            cv_.wait(lock, [this] { return pendingWrites_.empty(); });
            if (fsync) storage_.flush();
        });
    }

    std::future<void> scanChunk(ChunkPos pos, StreamTagVisitor& visitor);

private:
    void run() {
        while (!shutdown_.load()) {
            ChunkPos pos;
            std::unique_ptr<NbtCompound> data;
            std::promise<void> promise;
            
            {
                std::unique_lock lock(mutex_);
                cv_.wait(lock, [this] { return shutdown_ || !pendingWrites_.empty(); });
                if (shutdown_) break;
                
                auto it = pendingWrites_.begin();
                pos = it->first;
                data = std::move(it->second.data);
                promise = std::move(it->second.promise);
                pendingWrites_.erase(it);
            }
            
            try {
                storage_.write(pos, data ? *data : NbtCompound{});
                promise.set_value();
            } catch (...) {
                promise.set_exception(std::current_exception());
            }
        }
    }

    struct PendingStore {
        std::unique_ptr<NbtCompound> data;
        std::promise<void> promise;
    };

    std::filesystem::path regionDir_;
    RegionFileStorage storage_;
    std::map<ChunkPos, PendingStore, ChunkPosOrder> pendingWrites_;    // sequenced
    std::mutex mutex_;
    std::condition_variable cv_;
    std::atomic<bool> shutdown_{false};
    std::thread worker_;
};

}
```

**关键工程选择**：

1. **`std::thread` + `std::condition_variable`**：替代 Mojang 的 PriorityConsecutiveExecutor。简单可靠。
2. **没有显式优先级**：因为 store 直接写共享 map，loadAsync 有自己的 thread；不像 Java 那样需要插队。
3. **`pendingWrites_` map 用 `std::map` 加自定义 comparator**：保留插入顺序需要双结构（`std::list<ChunkPos>` + `std::unordered_map<ChunkPos, iter>`）。简化版直接用 map。
4. **`std::shared_future` 给多次 await**：上面用 `std::future`（一次性），如果有多人想等同一个 store，改 `shared_future`。
5. **`storage_` 不需要 mutex**：仅在 worker_ 线程访问。
6. **关闭时 `cv_.notify_all`** 让 worker 醒来 check shutdown_。

## 2.7.14 一句话总结

`IOWorker` = 单后台线程 + `pendingWrites` 队列，让主 tick 线程零阻塞地"提交"chunk 写盘任务；同一 chunk 多次 store 自动批合并（共享同一 PendingStore 直到真正写出）；`loadAsync` 优先看 pending 保证读到自己刚写的数据；`synchronize(true)` 强制等所有 pending 完成 + fsync，用于关服 / `/save-all`；`scanChunk + StreamTagVisitor + CollectFields` 让"扫一整个 region 只看每 chunk 一两个字段"达到 100× 加速；底层 `RegionFileStorage` 用 LRU 256 缓存打开的 RegionFile，避免反复 open/close。
