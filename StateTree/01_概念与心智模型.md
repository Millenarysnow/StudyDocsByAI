# 01. 概念与心智模型

## 一、StateTree 是什么？

**StateTree（状态树）** 是 UE5.0 引入、5.1 之后正式作为生产就绪功能推出的一种**通用分层状态机**。它不是单纯的"AI 框架"，而是被设计为可以驱动任何"有状态数据"的逻辑系统：

- AI 行为决策（最常见）
- 格斗游戏的连招选择
- 动画状态选择
- 任务系统流程
- UI 状态流
- 大规模实体处理（Mass Framework）

它的本质是把两种传统范式融合在一起：

```
       行为树（Behavior Tree）             状态机（State Machine）
        ┌──────────────────┐             ┌────────────────────┐
        │  分层结构 (Tree) │             │  显式状态 (State)  │
        │  选择器 (Select) │             │  过渡  (Transition)│
        │  优先级遍历      │             │  事件驱动          │
        └──────────────────┘             └────────────────────┘
                  │                                │
                  └──────────┬─────────────────────┘
                             ▼
                   ┌──────────────────────┐
                   │     StateTree        │
                   │  分层 + 数据绑定     │
                   │  显式状态 + 过渡     │
                   │  按需重评估          │
                   └──────────────────────┘
```

## 二、核心组成元素

### 1. State（状态）

状态是树的节点。状态有几种类型（源码 `EStateTreeStateType`）：

| 类型 | 说明 |
|------|------|
| **State** | 普通状态，可以有 Tasks、子状态、Enter Conditions、Transitions |
| **Group** | 分组状态，**没有 Tasks**，只能有子状态、Enter Conditions、Transitions |
| **Linked** | 链接到当前 StateTree 资产内的另一个 Subtree（子树状态）|
| **Linked Asset** | 链接到**外部**的另一个 StateTree 资产 |
| **Subtree** | 可被 Linked 状态引用的子树入口 |

### 2. Task（任务）

任务是真正"做事情"的单元：

- 移动到位置
- 播放动画
- 等待时间
- 注册事件监听
- 声明智能对象

每个 Task 在状态激活时 EnterState，在状态退出时 ExitState，在中间每帧 Tick。

### 3. Transition（过渡）

定义状态切换规则。Transition 不是"状态选择"本身，而是**触发状态选择的事件**。可以挂在任何状态上。

### 4. Enter Condition（进入条件）

决定一个状态能否被选中的前置条件。在状态选择阶段评估。

### 5. Evaluator（求值器）

向树暴露外部数据。在 5.5 之后**官方推荐改用 Global Task**，因为 Global Task 功能更强大且统一。

### 6. Parameters（参数）

类似行为树的 Blackboard Key：
- 可以是树级（全局参数）
- 可以是状态级（State Parameters）
- 可以是 Subtree 参数（被链接时传入）

### 7. Property Ref（属性引用）

5.4 之后引入的"可读写引用"，弥补了普通 Binding 是值传递的不足。蓝图版本叫 `FStateTreeBlueprintPropertyRef`，C++ 版本叫 `FStateTreePropertyRef`。

### 8. Schema（架构）

决定一个 StateTree 资产可以使用哪些节点、上下文数据是什么。常见的 Schema：

| Schema | 用途 |
|--------|------|
| **StateTreeComponentSchema** | 普通 Actor 用 |
| **StateTreeAIComponentSchema** | AI 用，额外提供 AIController |
| **MassStateTreeSchema** | Mass 实体用 |
| **GameplayInteractionStateTreeSchema** | 智能对象交互用 |
| **AvalancheTransitionTreeSchema** | Motion Design 转场用 |

可以自定义 Schema 来约束节点、提供专用上下文。

## 三、StateTree 的核心设计哲学（最关键的两点）

### 哲学 1：**激活链上所有状态同时活跃**

这是 StateTree 与传统状态机最大的区别。

传统状态机：
```
当前活动状态 = StateA   （只有一个）
切换到 StateB 时：
当前活动状态 = StateB
```

StateTree：
```
激活链 = Root → A → B → C  （叶子是 C，但 Root/A/B 也都活跃）
所有 active 状态上的 Task 都在并发执行
```

**这带来的能力**：
- 父状态可以放"资源持有"、"事件监听"等任务，子状态共享这些资源
- 中间状态可以放共用的 Transition（兜底打断），子状态享有
- 数据可以从父任务流向子任务（Bindings）

**这带来的代价**：
- 一个 Task 完成可能影响整个链
- Enter/Exit 事件可能在同一个 Task 上多次触发

### 哲学 2：**状态选择是按需触发的**

传统行为树：
```
每帧从根开始重新遍历整棵树 → 找到合适的叶子 → 执行
```

StateTree：
```
启动时选一次状态 → 进入活动状态
之后只在 Transition 触发时才重新选择
```

**这带来的好处**：性能更好，不需要每帧遍历整棵树。

**代价**：必须显式定义"什么时候应该重新评估"（即各种 Transition）。

## 四、与行为树（Behavior Tree）的详细对比

| 维度 | Behavior Tree | StateTree |
|------|---------------|-----------|
| 每帧评估 | 持续从根开始遍历 | 仅在 Transition 触发时重选 |
| 活动节点 | 通常一条路径 | **整条激活链都活跃** |
| 数据共享 | 通过 Blackboard | 通过 Bindings + Property Ref |
| 打断性 | 强（任何 Decorator 失败立即打断） | 基于 Transition 显式定义 |
| 节点数量级 | 大（Decorator/Service/Composite 等） | 少（State/Task/Transition/Condition） |
| 心智模型 | 决策树 | 分层状态机 |
| 适合场景 | "持续决策，随时打断" | "明确阶段，事件驱动" |
| 调试难度 | 中等 | 较高（多状态并发） |
| 性能 | Tick 开销固定 | 仅活跃状态消耗 |

### 一个对比例子：AI 巡逻 + 看到敌人战斗

**行为树写法**：
```
Selector (root)
├── Sequence: Combat
│   ├── Decorator: HasEnemy（每帧检查，作为中断条件）
│   ├── MoveToEnemy
│   ├── Attack
├── Sequence: Patrol
│   ├── PatrolPoint
│   ├── Wait
```

**StateTree 写法**：
```
Root
├── Combat
│   ├── Transition: On Tick + 没敌人 → Patrol
│   ├── Move To Enemy
│   └── Attack
└── Patrol
    ├── Transition: On Tick + 看到敌人 → Combat
    ├── Patrol Point
    └── Wait
```

注意 StateTree 里的 **`On Tick` Transition** 充当了行为树中 `Decorator + Observer Aborts` 的角色 —— 持续监控条件并打断。

## 五、与传统有限状态机（FSM）的对比

| 维度 | Traditional FSM | StateTree |
|------|----------------|-----------|
| 层级 | 通常单层 | 分层（树形） |
| 同时活跃状态数 | 1 | **多个**（整条激活链） |
| 数据流 | 通常通过单一 Blackboard | 节点间 Binding |
| 选择器 | 无 | 有（继承自行为树） |
| 进入条件 | 转换条件 | 状态本身有 Enter Condition |

如果你只用过 UE 的 AnimGraph State Machine 或 Unity 的 Animator State Machine，StateTree 一开始会让你混乱 —— 因为它不像那种"只有一个 active state"的简单模型。

## 六、什么时候用 StateTree，什么时候用别的？

### 适合用 StateTree

- AI 有清晰的"阶段"概念（Idle、Combat、Flee、Dead）
- 多个阶段共享某些资源/任务
- 需要事件驱动的状态切换
- 需要在大规模实体（Mass Framework）上跑
- 不希望每帧遍历整棵树

### 适合用 Behavior Tree

- AI 决策非常密集，每帧都要重新评估
- 大量需要 Decorator 打断的场景
- 团队对行为树更熟悉，培训成本更低
- 现有项目已经在用 BT，不想迁移

### 适合用普通 FSM

- 状态数少（< 5）
- 没有层级关系
- 没有复杂的数据共享
- 比如简单的 UI 状态

### 也可以混用！

UE 官方甚至推荐过混用：
- **高频决策用 BT，长时动作用 ST**
- ST Task 中可以调用 BT，反之亦可

## 七、读完这一章你应该理解的核心概念

1. ✅ StateTree 是分层状态机，融合了行为树和状态机
2. ✅ 整条激活链都是 active 的，不是只有一个状态
3. ✅ Task 才是真正干活的，State 只是容器
4. ✅ 状态切换通过 Transition 触发，不是每帧重选
5. ✅ Schema 决定了 StateTree 能用什么节点
6. ✅ 它不只是 AI 用的，任何"有阶段"的逻辑都可以用
