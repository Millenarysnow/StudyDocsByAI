# 03. 反直觉点与陷阱

> StateTree 的设计虽然强大，但有几个非常容易让人懵的"反直觉"行为。这一章逐个拆解，每个都有源码佐证和解决方案。

---

## 反直觉 #1：子状态激活时，父状态也同步激活

### 现象

```
Root
 └─ A (父状态，有 Task_A)
     └─ B (父状态，有 Task_B)
         └─ C (叶子，有 Task_C)  ← 选中这个
```

**结果**：A、B、C **三个状态全部激活**，Task_A、Task_B、Task_C **同时并发运行**！

### 源码佐证

```cpp
// FStateTreeActiveStates 是一个数组结构
// 选中 C 时，ActiveStates 数组里会被 push: [A, B, C]
// 所有 ActiveStates 上的 Tasks 都会被 Tick
for (state in CurrentFrame.ActiveStates)
    for (task in state.Tasks)
        task.Tick(...)
```

官方文档原文：
> "When a State is selected, the selected State and all its parent States become active. **All Tasks are executed for all active States**, starting from the root, down to the selected State."

### 为什么这么设计？

为了实现"分层数据共享"：
- A 的 Task 算出"目标位置" → C 的 Task 用 Binding 直接读
- B 的 Task 注册"群体声明" → 整条链共享
- A 的 Transition 监控"全局打断条件" → C 也享有

### 解决方案

**这不是 bug，是设计**。你需要：
1. 习惯"激活链"的概念，把父状态的 Task 想成"在子状态期间一直存在"
2. 父状态的 Task 通常用于**资源持有 / 事件监听 / 公共数据计算**
3. 叶子状态的 Task 才是真正的**动作**

## 反直觉 #2：同一状态内 Tasks 是并行的，不是顺序的

### 现象

你在一个 State 里放了 Task1、Task2、Task3：

```
State X
├── Task1: 走到位置
├── Task2: 播放语音
└── Task3: 显示 UI 提示
```

**结果**：三个 Task **同时 EnterState、同时 Tick**，不是 Task1→Task2→Task3 这样顺序执行！

### 源码佐证

```cpp
// 进入状态时
for (task in state.Tasks)
    task.EnterState(...)  // 一个个调用，但都进入"运行中"状态
```

### 谁会先触发 Transition？

**任何一个 Task 完成都会触发 Transition 评估**（5.6 之前）：

```cpp
// 简化逻辑
if (任一 Task 返回 Succeeded/Failed):
    bHasPendingCompletedState = true
    → 进入 Transition 评估
```

### 解决方案

#### 想要顺序执行？

**拆成子状态链 + Next 过渡**：

```
ParentState
├── Task: 共享资源
├── Child1
│   ├── Task: Step1
│   └── Transition: Next → Child2
├── Child2
│   ├── Task: Step2
│   └── Transition: Next → Child3
└── Child3
    └── Task: Step3
```

#### 想要并行但等所有完成才过渡？

**UE 5.6+** 提供了 State 级别的 `EStateTreeTaskCompletionType::All`：

源码定义（`StateTreeTasksStatus.h`）：
```cpp
UENUM()
enum class EStateTreeTaskCompletionType : uint8
{
    All,  // 全部 Task 完成才算 State 完成
    Any,  // 任一 Task 完成就触发（默认，老行为）
};
```

在编辑器中可以为每个 State 选择 All 或 Any 模式。

#### 5.6 之前怎么办？

**只让其中一个 Task 调用 FinishTask**，其他 Task 永远返回 Running：

```cpp
// MyDialogTask.cpp
EStateTreeRunStatus FMyDialogTask::Tick(...) const override
{
    // 永远返回 Running，让别的 Task 决定何时结束
    return EStateTreeRunStatus::Running;
}
```

或者用 `bConsideredForCompletion = false` 标记某些 Task 不参与完成判定（5.6+）。

## 反直觉 #3：任何 Task 完成都会触发 Transition（"谁先完成谁说了算"）

### 现象

```
State X
├── Task A: 5秒后 Finish
└── Task B: 10秒后 Finish

Transitions:
├── On State Completed → Y
```

**结果**：5 秒时 Task A 完成 → 立即跳到 Y，**Task B 被强制 Exit，没跑完！**

### 源码佐证

`FinishTask` 实现：

```cpp
// StateTreeExecutionContext.cpp
void FStateTreeExecutionContext::FinishTask(const FStateTreeTaskBase& Task, EStateTreeFinishTaskType FinishType)
{
    // ...
    FTasksCompletionStatus StateTasksStatus = ...;
    StateTasksStatus.SetStatusWithPriority(StateTaskIndex, TaskStatus);
    Exec.bHasPendingCompletedState = Exec.bHasPendingCompletedState
        || StateTasksStatus.IsCompleted();  // ← 任一完成就标记
}
```

### 解决方案

参考反直觉 #2 的 5.6 All/Any 模式，或：

**让父级 Task 不调用 FinishTask**：
```cpp
// Task B：永远返回 Running
EStateTreeRunStatus Tick(...) override {
    return EStateTreeRunStatus::Running;
}
```

**5.6+ 用 `bConsideredForCompletion = false`**：
```cpp
FMyTask() {
    bConsideredForCompletion = false;  // 即使 Finished，也不触发 Transition
}
```

## 反直觉 #4：父状态的 Task 会收到多次 EnterState / ExitState

### 现象

```
Parent
├── Task: 注册事件监听器
├── Child1
├── Child2
├── Child3

Child1 → Next → Child2 → Next → Child3
```

你以为 Parent 的 Task 只会 EnterState 一次（Child1 进入时）、ExitState 一次（Child3 退出时）。

**实际**：
- 进入 Child1：Parent.Task **EnterState**（OK）
- Child1 → Child2：Parent.Task **ExitState + EnterState 再来一次！**
- Child2 → Child3：又一次 **ExitState + EnterState**
- 最终退出：再 **ExitState**

如果你在 EnterState 里 `RegisterListener()`，在 ExitState 里 `UnregisterListener()`，就会反复注册注销，引起各种 bug。

### 源码佐证

切换状态时，引擎会调用 `EnterState` 和 `ExitState` 给所有"可能受影响"的状态。`Transition.ChangeType` 会标记是 `Changed`（真的进出）还是 `Sustained`（持续保持）。

```cpp
UENUM()
enum class EStateTreeStateChangeType : uint8
{
    None,
    Changed,    // 状态真的从激活变非激活，或反之
    Sustained,  // 状态在父→子重选时保持激活
};
```

默认情况下，**Sustained 状态的 Task 仍然会收到 EnterState 和 ExitState 调用**（只是 ChangeType = Sustained）。

### 解决方案

**关闭 `bShouldStateChangeOnReselect`**：

源码：
```cpp
/**
 * If set to true, the task will receive EnterState/ExitState even if the state was previously active.
 * Generally this should be true for action type tasks, like playing animation,
 * and false on state like tasks like claiming a resource that is expected to be acquired on child states.
 */
uint8 bShouldStateChangeOnReselect : 1;
```

#### C++ 写法

```cpp
USTRUCT()
struct FSTT_RegisterListener : public FStateTreeTaskCommonBase
{
    GENERATED_BODY()

    FSTT_RegisterListener()
    {
        // 子状态切换时不重发 Enter/Exit
        bShouldStateChangeOnReselect = false;
    }

    virtual EStateTreeRunStatus EnterState(...) const override
    {
        // 只有真的进入时才注册
        RegisterListener();
        return EStateTreeRunStatus::Running;
    }

    virtual void ExitState(...) const override
    {
        // 只有真的退出时才注销
        UnregisterListener();
    }
};
```

#### 蓝图写法

蓝图 Task 的 Class Defaults 中有同名属性 `Should State Change on Reselect`，取消勾选即可。

#### 一个折中方案

如果不想关掉这个标志（因为某些场景下需要），可以在 EnterState/ExitState 里检查 ChangeType：

```cpp
EStateTreeRunStatus EnterState(FStateTreeExecutionContext& Context, const FStateTreeTransitionResult& Transition) const override
{
    if (Transition.ChangeType == EStateTreeStateChangeType::Sustained)
    {
        // 这是 Reselect 引起的事件，跳过
        return EStateTreeRunStatus::Running;
    }
    // 真的进入
    RegisterListener();
    return EStateTreeRunStatus::Running;
}
```

## 反直觉 #5：Transition 自下而上评估，但 Task 自上而下执行

### 现象

| 操作 | 顺序 |
|------|------|
| EnterState | **根 → 叶**（A → B → C） |
| Tick | **根 → 叶**（A → B → C） |
| ExitState | **叶 → 根**（C → B → A） |
| StateCompleted | **反向**（源码注释明确） |
| Transition 评估 | **叶 → 根**（C → B → A）|

### 为什么？

- **EnterState 根→叶**：父先初始化，子才能用父的数据
- **ExitState 叶→根**：子先清理，父最后释放资源（类似 RAII）
- **Transition 评估叶→根**：让子状态的 Transition 优先级高，子可以"否决"父的过渡

### 源码佐证

```cpp
// EnterState：从 0 到 N-1（即根到叶）
for (int32 i = 0; i < ActiveStates.Num(); ++i)
    Tasks[ActiveStates[i]].EnterState(...);

// ExitState：从 N-1 到 0（叶到根）
for (int32 i = ActiveStates.Num() - 1; i >= 0; --i)
    Tasks[ActiveStates[i]].ExitState(...);

// Transition 评估同 ExitState 方向
```

### 实战影响

**如果你在父 Task 的 EnterState 里依赖子 Task 的输出 → 不会工作！**
因为父的 EnterState 比子先调用。

**如果你在父 Task 的 ExitState 里依赖子 Task 还没清理的状态 → 不会工作！**
因为子的 ExitState 比父先调用。

## 反直觉 #6：Tick 型 Transition 不依赖子节点是否完成

### 现象

```
B
└── Transition B1: On Tick + 条件 X → 跳到别处
└── C (叶子)
    └── Task: 跑 5 秒
```

**问**：B1 的 On Tick 检测会等 C 的 Task 跑完吗？

**答**：不会！**B 一激活就开始每帧检测**，3 秒时条件 X 命中，**C 还没完成就被强制 Exit**！

### 源码佐证

`On Tick` Transition 是每帧无条件评估的。源码 `GetTriggerTransitionEvent`：

```cpp
else if (EnumHasAnyFlags(Transition.Trigger, EStateTreeTransitionTrigger::OnTick))
{
    // Dummy event to make sure we iterate the transition loop once.
    OutTransitionEvents.Emplace(FStateTreeSharedEvent());
}
```

每帧 Tick 阶段，无论子节点状态如何，所有 active 状态上的 `On Tick` Transition 都会被评估。

### 这正是 On Tick 的设计意图

它就是用来**打断子状态执行**的，相当于行为树的 Decorator + Observer Aborts。

### 实战建议

- 父状态放 `On Tick`：监控全局打断条件（死亡、目标丢失、检测到敌人等）
- 子状态/叶子放 `On State Completed`：自然完成后的下一步
- **不要把"等子状态完成"用 `On Tick` 实现** —— 用 `On State Completed`！

## 反直觉 #7：状态切换时只回退到"共同祖先"，子和父的 Task 不重启

### 现象

```
当前激活链：Root → A → B → C
Transition 目标：D（路径：Root → A → B → D）
共同祖先：[Root, A, B]
```

**结果**：
- C 的 Task **ExitState** 被调用
- D 的 Task **EnterState** 被调用
- A、B 的 Task **不会真的退出和重新进入**

但前面说过，默认情况下它们会收到 Sustained 类型的 Exit/Enter 事件（除非 `bShouldStateChangeOnReselect = false`）。

### 源码佐证

`GetStatesListToState` 函数会向上遍历到 Root，对比新旧两条链找到第一个不同的状态作为分叉点。

```cpp
// 简化逻辑
for (i = 0; i < min(OldChain, NewChain); ++i)
    if (OldChain[i] != NewChain[i])
        分叉点 = i; break;

// 只 ExitState OldChain[分叉点 ~ 末尾]
// 只 EnterState NewChain[分叉点 ~ 末尾]
```

### 实战影响

**这是一个好设计**（避免不必要的重启），但你需要意识到：

1. 父状态的 Task 在子状态切换时**仍然在跑**（持有的资源不会丢）
2. 父状态的 Task 的 Tick 不会重新计数（如果它在累计时间，时间不会重置）
3. 但默认会收到 Sustained 的 Enter/Exit 事件 → 见反直觉 #4

## 反直觉 #BONUS：Task Bindings 是按值传递的

### 现象

你在 Task A 里 `OutputProperty = SomePtr->Value`，然后 Task B 通过 Binding 读 Task A 的 OutputProperty。

如果 `SomePtr` 在运行中变化了，Task B 读到的是**旧值**！

### 原因

Bindings 在 Tick / EnterState 前**复制**到 Task 的实例数据中，不是引用。

源码标志位：
```cpp
uint8 bShouldCopyBoundPropertiesOnTick : 1;
uint8 bShouldCopyBoundPropertiesOnExitState : 1;
```

### 解决方案

#### 5.4+ 使用 PropertyRef

C++ 用 `FStateTreePropertyRef`，蓝图用 `FStateTreeBlueprintPropertyRef`，可以实现真正的引用绑定。

#### 通过 Output 在 Tick 里更新

Task A 在 Tick 里持续更新 OutputProperty，下一帧 Task B 就能拿到最新值。

#### 通过 Event 通知

Task A 检测到变化时发送 Event，挂 `On Event` Transition。

## 反直觉总结表

| # | 反直觉点 | 解决方案 |
|---|---------|---------|
| 1 | 子节点激活时父也激活，所有 Task 并发运行 | 习惯，把父 Task 当作"长期存在的资源" |
| 2 | 同状态多 Task 是并行的，不是顺序的 | 用子状态链 + Next；或 5.6 All 完成模式 |
| 3 | 任一 Task 完成就触发 Transition | 5.6 用 `bConsideredForCompletion = false`；旧版让 Task 永远 Running |
| 4 | 父 Task 会收到多次 Enter/Exit | 关 `bShouldStateChangeOnReselect`，或检查 ChangeType |
| 5 | Tick 根→叶，ExitState 叶→根，Transition 评估叶→根 | 习惯，按方向写依赖 |
| 6 | On Tick Transition 每帧评估，不等子状态 | 这是设计，不要用 On Tick 等子完成 |
| 7 | 状态切换只回退到共同祖先 | 习惯，配合 #4 关闭 Reselect 事件 |
| Bonus | Bindings 按值传递 | 用 PropertyRef，或 Tick 持续更新 |

---

## 一句话总结

**StateTree 的所有反直觉都源于一个核心事实**：

> **整条激活链都是活跃的，不是只有叶子；Task 的执行是并发的，不是顺序的。**

理解这一点后，所有"奇怪"的行为都变得可以预测。
