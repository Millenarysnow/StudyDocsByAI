# 08. 最佳实践与避坑清单

> 这是一份"实战前必读"的清单。本章节内容主要来自社区踩坑总结、官方文档、源码分析。

---

## 一、设计阶段的最佳实践

### ✅ DO

#### 1. 先想清楚 Schema

不同 Schema 决定了 Task 能在哪些 StateTree 中运行。**不要自己继承 `FStateTreeTaskBase`**，至少继承 `FStateTreeTaskCommonBase`，这样大多数 Schema 都能用。

#### 2. State 命名清晰，按行为分组

```
✅ 好的命名：
Combat
├── Approach
├── Attack
└── Retreat

❌ 不好的命名：
State1
├── State1_1
├── State1_2
└── State1_3
```

#### 3. 父状态放共享逻辑，叶子状态放具体动作

```
✅ 推荐结构：
Combat (父，挂资源声明、感知监听)
├── Approach (叶，移动)
├── Attack (叶，开火)
└── Retreat (叶，撤退)

❌ 不推荐：
Combat
├── Approach (父，又有任务又有子)
│   ├── Move
│   └── ...
```

#### 4. 用颜色 / 主题标记不同分组

5.4+ 可以为状态设置颜色主题：
- 🔵 Combat states
- 🟢 Peaceful states  
- 🔴 Critical/Death states
- 🟡 Investigation states

---

### ❌ DON'T

#### 1. 不要在一个 State 里堆超过 5 个 Task

如果有那么多并行需求，说明应该拆成子状态。

#### 2. 不要嵌套超过 6 层

激活链最大 8 层（`MaxStates = 8`），但实际超过 6 层就难维护。用 Subtree 拆分。

#### 3. 不要把所有逻辑塞进一个 StateTree 资产

复杂行为应该用 Linked Asset 拆分，每个资产单一职责。

## 二、Task 编写最佳实践

### ✅ DO

#### 1. InstanceData 用独立 USTRUCT

所有运行时数据放 InstanceData 中，**不要用成员变量**！

```cpp
// ✅ 正确
USTRUCT()
struct FMyTaskInstanceData
{
    UPROPERTY()
    float Time;
};

USTRUCT()
struct FMyTask : public FStateTreeTaskCommonBase
{
    using FInstanceDataType = FMyTaskInstanceData;
    // 没有任何成员变量！
};

// ❌ 错误
struct FMyTask : public FStateTreeTaskCommonBase
{
    float Time;  // ← 这是 task 类的成员！多个实例会共享！
};
```

为什么？因为同一个 Task 类的多个实例（多个 Actor 各跑一份 StateTree）会共用同一个 Task struct 的 instance，但 InstanceData 是每个实例独立的。

#### 2. EnterState 默认返回 Running

```cpp
EStateTreeRunStatus EnterState(...) const override
{
    // 初始化数据
    Data.Time = 0.0f;
    return EStateTreeRunStatus::Running;  // ← 默认这个
}
```

只在**真的瞬时完成**（如计算一个值就完事）才返回 Succeeded/Failed。

#### 3. 父级 Task 关闭 Reselect 行为

```cpp
FParentTask()
{
    bShouldStateChangeOnReselect = false;  // 子状态切换不重发 Enter/Exit
}
```

#### 4. 用 Visual Logger 调试

```cpp
UE_VLOG(Context.GetOwner(), LogTemp, Verbose, 
    TEXT("MyTask: Time=%f"), Data.Time);
```

#### 5. 异步 Task 用 WeakExecutionContext

```cpp
FStateTreeWeakExecutionContext WeakContext = Context.MakeWeakExecutionContext();
SomeAsyncOp.OnComplete.BindLambda([WeakContext, this]()
{
    auto Strong = WeakContext.MakeStrongExecutionContext();
    if (Strong.IsValid())
        Strong.FinishTask(*this, EStateTreeFinishTaskType::Succeeded);
});
```

---

### ❌ DON'T

#### 1. 不要在 Task 中保存 ExecutionContext 引用

```cpp
// ❌ 极其错误！Context 生命周期只在调用栈内
FStateTreeExecutionContext* SavedContext;

EStateTreeRunStatus EnterState(FStateTreeExecutionContext& Context, ...) const override
{
    SavedContext = &Context;  // ← 等回调来时这个引用早就失效
}
```

正确做法：用 `FStateTreeWeakExecutionContext`。

#### 2. 不要在 Task 中用 const 修饰 InstanceData

C++ Task 的虚函数都是 `const`，但你需要修改 InstanceData。**InstanceData 通过 Context 取出来是非 const 引用**，可以修改：

```cpp
EStateTreeRunStatus Tick(...) const override  // 注意 const
{
    FInstanceDataType& Data = Context.GetInstanceData(*this);  // 非 const 引用
    Data.Time += DeltaTime;  // ✅ 可以修改
}
```

#### 3. 不要在 Tick 里做昂贵的操作

每帧 Tick 的 Task 数量可能很多（多个 AI），所以 Tick 内：
- 避免 LineTrace（用 EQS 或 AI 感知系统）
- 避免遍历整个世界（用 Subsystem 缓存）
- 避免重复内存分配
- 避免大量字符串拼接

## 三、Transition 设计最佳实践

### ✅ DO

#### 1. 顺序：具体 > 通用

```
✅ 正确顺序：
├── On State Failed → ErrorHandler
├── On State Succeeded → NextStep
└── On State Completed → Cleanup  (兜底)

❌ 错误顺序：
├── On State Completed → Cleanup  ← 永远先命中，下面没机会
├── On State Failed → ErrorHandler
└── On State Succeeded → NextStep
```

#### 2. 用 NextSelectableState 而不是 NextState

```
✅ NextSelectableState 会跳过 Enter Condition 失败的兄弟
❌ NextState 失败就整个失败
```

#### 3. 父状态放兜底 Transition

```
ParentState
├── Transition: On Tick + 全局打断条件 → 别处  (Priority: High)
├── Transition: On State Failed → 兜底状态
├── Transition: On State Completed → 父结束
└── 各种子状态
```

#### 4. Critical Priority 用于"永不忽略"的过渡

```
RootState
└── Transition: On Tick + Health <= 0 → DeathState  [Critical]
```

死亡过渡不应该被任何子状态的 Transition 覆盖。

---

### ❌ DON'T

#### 1. 不要用 On Tick 等待子状态完成

```
❌ 错误：
ParentState
└── Transition: On Tick + 子状态完成了 → NextState

✅ 正确：
ParentState
└── Transition: On State Completed → NextState
```

`On Tick` 是用来打断的，不是等待的。

#### 2. 不要在多条 Transition 中同时使用 OnCompleted 和 OnSucceeded/OnFailed

```
❌ 容易混乱：
├── On State Completed → A
├── On State Succeeded → B  ← 这条永远不会命中（Completed 包含 Succeeded）
└── On State Failed → C
```

要么全用具体的（Succeeded/Failed），要么只用 Completed。

#### 3. 不要用过于昂贵的 Transition Condition

```
❌ 不好：
On Tick + 条件: LineTrace 整个世界  ← 每帧执行！

✅ 好：
On Tick + 条件: 检查缓存的 bSeesEnemy 标志  ← 由 Evaluator 异步更新
```

## 四、性能优化清单

### 1. 使用 ScheduledTick（5.5+）

```cpp
// 在 Task 中标记不参与每帧调度
FMyListenerTask()
{
    bShouldCallTick = false;
    bShouldCallTickOnlyOnEvents = true;  // 仅事件来时 Tick
    bConsideredForScheduling = true;
}
```

### 2. 关闭不必要的功能

```cpp
FMyEventOnlyTask()
{
    bShouldCallTick = false;                         // 不 Tick
    bShouldCopyBoundPropertiesOnTick = false;        // 不复制（如果不 Tick）
    bShouldStateChangeOnReselect = false;            // 不响应 Reselect
}
```

### 3. 状态级 CustomTickRate

不需要高频反应的状态：

```
GuardPatrol State
├── CustomTickRate = 0.5 (每 0.5 秒一次)
└── ...
```

### 4. 大规模 AI 用 Mass

> 100 个 AI Actor 实例 → 考虑迁移到 Mass + StateTree

### 5. 性能分析

```
stat StateTree         # StateTree 整体性能
stat StateTree_Async   # 异步 Tick 性能
```

## 五、调试技巧

### 1. StateTree Debugger（编辑器内）

最强大的工具。可以：
- 实时高亮激活链
- 录制运行轨迹回放
- 查看每个 Binding 的实时值
- 追踪每次 Transition

### 2. Visual Logger

```cpp
UE_VLOG(Context.GetOwner(), LogStateTree, Log, 
    TEXT("Entered state with target=%s"), *Target.ToString());
```

游戏内打开 Visual Logger（控制台 `vislog`），可以回放某个时刻 Actor 的 Log + 几何调试可视化。

### 3. Gameplay Debugger

按下 `'` 键（默认）打开。Tick 哪个 Actor 它就显示哪个的 StateTree 状态。

需要在 Task 中实现：
```cpp
#if WITH_GAMEPLAY_DEBUGGER
virtual FString GetDebugInfo(const FStateTreeReadOnlyExecutionContext& Context) const override
{
    return FString::Printf(TEXT("Time=%.1fs"), Data.Time);
}
#endif
```

### 4. 日志命令（真正可用的）

在控制台 / Output Log 输入：

```
log LogStateTree Verbose
```

开启后所有 StateTree 内部事件（状态选择、Transition、Task Enter/Exit）都会打印到 Output Log。

可选级别：`VeryVerbose` / `Verbose` / `Log` / `Display` / `Warning` / `Error`

### 5. StateTree Trace（Unreal Insights，最强大）

启动编辑器/游戏时加参数：

```
-trace=default,statetreedebug
```

然后在 StateTree 资产编辑器点 **Debug** 按钮，可以：
- 回放所有 Trace 事件
- 查看每次 Transition 的评估源、目标、条件结果
- 查看每个 Task 的 Enter/Tick/Exit 时刻和返回值
- 查看 Binding 的实时值

这是官方推荐的主要调试手段。

### 6. 真正存在的控制台变量（5.7 源码）

基于源码 `StateTreeExecutionContext.cpp` 确认，只有 5 个 CVar，都是**功能开关**（用于版本迁移），不是调试工具：

```
StateTree.CopyBoundPropertiesOnNonTickedTask 0/1
StateTree.TickGlobalNodesFollowingTreeHierarchy 0/1
StateTree.GlobalTasksCompleteOwningFrame 0/1
StateTree.SetDeprecatedTransitionResultProperties 0/1
StateTree.TargetStateRequiresTheSameEventForStateSelectionAsTheRequestedTransition 0/1
```

源码中有 `StateTreeTestSuite` 模块，学习引擎行为最好的途径：

## 六、版本兼容性注意事项

### 5.5 之前 → 5.5+ 升级

主要变化：
1. **Evaluator 弱化**：尽量改用 Global Task
2. **新增 ScheduledTick**：性能优化机会
3. **Linked Asset Bug 修复**：之前的 workaround 可以删了
4. **Utility Selection 引入**：可以重构原本的复杂选择逻辑

### 5.5 → 5.6 升级

主要变化：
1. **Task `bConsideredForCompletion` 标志**：可以让 Task "不参与" State 完成判定
2. **State `EStateTreeTaskCompletionType::All` 模式**：等所有 Task 完成才触发过渡
3. **PropertyRef 蓝图支持完善**

### 5.6 → 5.7 升级

主要变化：
1. 各种小 Bug 修复
2. 性能优化（特别是 Mass 集成）
3. 状态选择规则更精细化（`EStateTreeStateSelectionRules`）

## 七、常见问题集（FAQ）

### Q1: 我的 Task 不 Tick 了，怎么回事？

**Checklist**：
1. `bShouldCallTick == true`？（5.7 默认 true，但子类可能改了）
2. State 是否被 ScheduledTick 让睡眠了？
3. Tree 的 `TreeRunStatus` 是 Running 吗？

### Q2: Bindings 显示有问题？

1. 重新 Compile StateTree 资产
2. 检查 Property 的 Category 设置（Input/Output/Context/Parameter）
3. 数据源在新 Task 之前吗？（同状态的后续 Task / 子状态不能绑定）

### Q3: Linked Asset 编译失败？

1. Schema 兼容吗？
2. Parameters 类型一致吗？
3. 是不是有循环引用？

### Q4: 状态切换太频繁/抖动？

1. 给 Transition 加 Delay
2. 检查 Enter Condition 是否瞬变
3. 用 Hysteresis（迟滞）：进出条件不同

### Q5: 子状态切换时父 Task 行为异常？

99% 是 `bShouldStateChangeOnReselect` 的问题。在父 Task 上关闭它。

### Q6: 在编辑器中改了参数运行没生效？

试试：
1. 编译 StateTree 资产（Ctrl+S 不够，需要 Compile 按钮）
2. 重启 PIE

### Q7: 怎么从 BT 迁移到 ST？

渐进式：
1. 新行为优先用 ST
2. 复杂的 BT 转换需要重新设计（不是 1-to-1 翻译）
3. ST Task 中可以调用 BT，反之亦可，可以混用

## 九、关键技术决策点

### 用 BT 还是 ST？

| 选 BT | 选 ST |
|-------|-------|
| 大量 Decorator 中断需求 | 明确阶段，事件驱动 |
| 团队对 BT 熟悉 | 新项目，没历史包袱 |
| 简单 AI（< 10 个状态） | 复杂分层 AI |
| 已有 BT 工具/教学 | 想要更好的性能 |

### 用 Evaluator 还是 Global Task？

5.5+ 几乎总是 Global Task。Evaluator 仅向后兼容。

### 用 PropertyRef 还是 Bindings？

| 用 Bindings | 用 PropertyRef |
|-------------|---------------|
| 简单值传递 | 需要写回外部 |
| 性能敏感 | 需要双向数据流 |
| 不需要修改 Source | 类似 Blackboard 的写回需求 |

### 用 Subtree 还是 Linked Asset？

| 用 Subtree | 用 Linked Asset |
|------------|-----------------|
| 同资产内复用 | 跨资产共享 |
| 紧密耦合的逻辑 | 多个 AI 共用的行为模板 |
| 不需要独立编辑 | 需要独立维护 |

## 十、最终避坑速查（Cheat Sheet）

| 症状 | 大概率原因 | 解决 |
|------|-----------|------|
| Task 不 Tick | bShouldCallTick = false | 构造函数里设 true |
| 父 Task 频繁 Enter/Exit | Sustained 事件 | 关 bShouldStateChangeOnReselect |
| 一个 Task 完成就跳走 | Any 完成模式 | 5.6+ 用 All 模式或 bConsideredForCompletion=false |
| 状态切换不响应 | Transition 顺序问题 | 检查具体 trigger 在通用 trigger 之前 |
| Binding 数值是旧的 | 值复制 + 没每帧 Tick | 用 PropertyRef 或确保 Tick |
| 状态选择失败 | Enter Condition 失败 | 用 NextSelectableState 而非 NextState |
| 频繁状态抖动 | 进出条件相同 | 加 Delay 或用 Hysteresis |
| Linked Asset 异常 | 5.4 之前的已知 Bug | 升级到 5.5+ |
| Tree 卡住不动 | 单帧 Iter 5 次用尽 | 检查是否有立即完成的循环 |
| 性能差 | 每帧无脑 Tick | 启用 ScheduledTick + CustomTickRate |
| 数据混乱 | 用了类成员变量 | 全部移到 InstanceData |
